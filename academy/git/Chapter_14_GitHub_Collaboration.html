14.1

What is collaboration in GitHub?

Source S15 · Chapter manual · 1. What is collaboration in GitHub?

GitHub collaboration is the process of coordinating changes to a shared codebase. Contributors work on branches or forks, propose changes through pull requests, discuss implementation, run automated checks and integrate approved work.

Plan work
Issue / task
Develop
Branch or fork
Propose
Pull request
Review
Comments + checks
Integrate
Merge

Collaboration provides traceability: teams can see why a change was made, who reviewed it, which checks ran and when it was merged.

14.2

Adding collaborators

Source S15 · Chapter manual · 2. Adding collaborators

For a repository you own or administer, you can grant another GitHub user access. In organizations, teams are often preferred because they simplify onboarding and access management.

  1. Open the repository.
  2. Navigate to Settings and the access-management area.
  3. Choose the option to add people or teams.
  4. Search for the correct GitHub username or team.
  5. Select the minimum permission needed.
  6. Send the invitation if authorized.
  7. Verify that access is accepted and appropriate.

Permission levels may include Read, Triage, Write, Maintain and Admin, depending on repository and organization context.

Do not add external collaborators to company repositories without approval. Review access periodically and remove it when the business need ends.
14.3

Forking repositories

Source S15 · Chapter manual · 3. Forking repositories

A fork is a GitHub-hosted copy of another repository under a different owner or namespace. It allows a contributor to experiment and publish changes without direct write access to the source repository.

Original repository
OWNER/project
Fork
YOUR-USER/project

The fork is a separate hosted repository, connected by contributor workflow rather than automatically sharing future commits.

When to fork

  • Contributing to open-source projects.
  • Working in a repository where you do not have direct push permission.
  • Maintaining an experimental copy of a project.

Forking does not mean every later change in the original repository automatically appears in your fork. You synchronize it explicitly.

14.4

Cloning a forked repository

Source S15 · Chapter manual · 4. Cloning a forked repository

After creating a fork on GitHub, clone your fork to your computer. The cloned repository's default remote is normally named origin and points to your fork.

# Clone your fork git clone https://github.com/YOUR-USER/project.git cd project # Confirm the remote git remote -v # Typical output: # origin https://github.com/YOUR-USER/project.git (fetch) # origin https://github.com/YOUR-USER/project.git (push)

Use your own fork URL in the command. Do not copy the placeholder literally.

14.5

Understanding the upstream repository

Source S15 · Chapter manual · 5. Understanding the upstream repository

In a fork workflow, upstream is a conventional remote name pointing to the original repository from which you forked. This meaning is different from a branch's upstream tracking configuration, although both use the word upstream.

# Add the original project as a second remote git remote add upstream https://github.com/ORIGINAL-OWNER/project.git # Inspect both remotes git remote -v
Remote nameCommon meaning in fork workflow
originYour fork, where you can push your contribution branches.
upstreamThe original source repository, from which you fetch updates.
Remote names are conventions, not special Git keywords. A team can use different names if documented consistently.
14.6

Synchronizing forked repositories

Source S15 · Chapter manual · 6. Synchronizing forked repositories

Synchronizing keeps your local branch and fork aligned with new commits in the original repository. A common workflow is to fetch upstream, update local main, then push that update to origin.

# Fetch latest commits from original repository git fetch upstream # Switch to local main and integrate upstream main git switch main git merge --ff-only upstream/main # Update your fork on GitHub git push origin main # Start new work from the updated main git switch -c feature/my-contribution

If your local main has diverged, --ff-only may refuse to merge. Inspect the graph and follow the project's documented merge or rebase policy rather than forcing an update.

Alternative: rebase a feature branch

git fetch upstream git switch feature/my-contribution git rebase upstream/main # If the branch was already pushed, coordinate before # updating the remote branch after rewriting its history.
Rebasing rewrites commit IDs. Do not rebase shared branches without coordination. If a force push is required, use the safer --force-with-lease only when permitted and understood.
14.7

What is a pull request?

Source S15 · Chapter manual · 7. What is a pull request?

A pull request (PR) is a GitHub collaboration proposal to merge changes from a source branch into a target branch. It provides a place for discussion, review, automated checks and change tracking.

A pull request does not itself merge code. It is a proposal until someone with the required permission completes the merge or an approved automation does so.

Typical PR information

  • Source and target branches.
  • Title and description explaining purpose and scope.
  • Changed files and line-by-line diff.
  • Reviewers and assignees.
  • Linked issues and project items.
  • Automated status checks and review conversations.
14.8

Creating a pull request

Source S15 · Chapter manual · 8. Creating a pull request
  1. Create a feature branch from the intended base branch.
  2. Make focused commits and test the changes locally.
  3. Push the branch to GitHub.
  4. Open the repository's Pull requests tab and choose New pull request, or use the prompt for a recently pushed branch.
  5. Select the correct base repository/branch and compare branch.
  6. Review the diff and confirm only intended files are included.
  7. Write a descriptive title and structured description.
  8. Link related issues, assign reviewers and create the pull request.
git switch main git pull --ff-only git switch -c feature/add-customer-check # Make changes, validate and commit git add sql/customer_check.sql git commit -m "Add customer quality check" # Push branch git push -u origin feature/add-customer-check

Suggested PR description

## Purpose Explain the business or technical reason for this change. ## Changes - Added customer validation query. - Added tests for null and duplicate keys. ## Validation - SQL checks passed. - Test data scenarios reviewed. ## Deployment impact Describe dependencies, configuration and rollout. ## Rollback Describe how to revert safely.
14.9

Reviewing pull requests

Source S15 · Chapter manual · 9. Reviewing pull requests

Reviewers inspect the proposed changes before they are integrated. A review should focus on correctness, maintainability, security, tests and impact—not merely formatting.

Review process

  1. Read the PR title and description to understand intent.
  2. Inspect the changed files and overall diff.
  3. Check that the implementation matches the requirement.
  4. Review error handling, security and performance.
  5. Check tests and CI results.
  6. Leave specific, actionable comments.
  7. Submit a review decision: comment, approve or request changes, according to policy.

Data Engineering review examples

  • SQL: join cardinality, filters, null handling, duplicate handling and query performance.
  • ADF: dependencies, parameters, retry behavior, linked services and environment configuration.
  • Databricks: notebook reproducibility, schema evolution, cluster assumptions and data quality.
  • Fabric: workspace references, semantic model impacts, refresh behavior and deployment configuration.
14.10

Approving pull requests

Source S15 · Chapter manual · 10. Approving pull requests

An approval is a formal positive review signal. Depending on branch protection rules, one or more approvals may be required before merging.

  • Approve only after reviewing the relevant changes.
  • Confirm required checks have passed or understand any permitted exceptions.
  • Check whether new commits after approval invalidate the approval under repository rules.
  • Follow CODEOWNERS or designated reviewer requirements where configured.
An approval is not a guarantee that a change is defect-free. It records a review decision; tests, deployment controls and monitoring remain important.
14.11

Requesting changes

Source S15 · Chapter manual · 11. Requesting changes

Use Request changes when the PR should not be merged until specific issues are addressed. Explain the problem, impact and expected correction.

Effective review comment

Example: “This join can return duplicate customer rows when the source contains multiple active records. Please confirm the intended grain and add a deterministic deduplication rule or validation before merging.”

Good comments are respectful, specific, actionable and tied to the code or requirement. Distinguish blocking defects from optional suggestions.

14.12

Merging pull requests

Source S15 · Chapter manual · 12. Merging pull requests

When review and required checks are complete, an authorized user can merge the PR using one of the repository's permitted merge methods.

MethodEffectCommon reason
Create a merge commitPreserves branch history and creates a merge commit.Keep explicit PR integration history.
Squash and mergeCombines PR commits into one commit on the base branch.Keep main history concise.
Rebase and mergeReplays commits onto the base branch without a merge commit.Maintain linear history.

Available options are controlled by repository settings. Confirm the selected base branch and deployment sequence before merging.

After merging

  • Confirm the PR is merged and the target branch contains the change.
  • Delete the feature branch if it is no longer needed.
  • Update local repositories.
  • Monitor deployment and data outcomes.
  • Close or update linked work items.
14.13

Closing a pull request without merging

Source S15 · Chapter manual · 13. Closing a pull request without merging

A PR can be closed without merging when the work is abandoned, superseded, duplicated or no longer required. Closing does not integrate its changes into the target branch.

Before closing, add a short explanation, link the replacement PR or issue if one exists, and confirm whether the branch should be retained for future work. Reopen the PR if the repository workflow and its state permit it.

Closing a PR and deleting its source branch are separate actions. Check whether the branch contains work that should be preserved.
14.14

Resolving pull request conflicts

Source S15 · Chapter manual · 14. Resolving pull request conflicts

A PR has a merge conflict when its source branch cannot be integrated cleanly with the target branch. The conflict must be resolved using the repository's approved workflow.

Resolve locally

git fetch origin git switch feature/add-customer-check git merge origin/main # Inspect conflicts git status # Edit conflicted files, remove markers and validate git add sql/customer_check.sql git commit # Push the resolution git push origin feature/add-customer-check

Alternatively, a team may rebase the feature branch onto the latest target branch. The chosen approach should match team policy. After resolving, rerun tests and inspect the final diff.

Do not resolve SQL or pipeline conflicts by blindly choosing “ours” or “theirs”. Check the intended business logic, schema and downstream effects.
14.15

Pull request templates

Source S15 · Chapter manual · 15. Pull request templates

A pull request template provides a consistent structure for submissions. GitHub can automatically populate the PR description from a repository template.

Common location

.github/ └── pull_request_template.md

Example template

## Summary Describe what changed and why. ## Related issue Closes # ## Change type - [ ] Feature - [ ] Bug fix - [ ] Documentation - [ ] Maintenance ## Validation - [ ] Unit tests passed - [ ] SQL / data checks completed - [ ] CI checks passed ## Data and deployment impact Describe schema, pipeline, configuration or refresh impacts. ## Security - [ ] No secrets or sensitive data added ## Rollback plan Describe safe recovery steps.

Templates reduce missing information but do not replace thoughtful review. Keep them concise enough that contributors will complete them.

Reference: Using templates for issues and pull requests.

What is Collaboration in GitHub?

Source S40 · 1. What is Collaboration in GitHub?

1.1 Definition

Collaboration on GitHub means multiple people contributing to the same project through a controlled process: branches or forks for isolated work, pull requests for review and discussion, and protected branches for quality.

1.2 Two collaboration models

Model Who Flow
Shared repository Team members with write access (companies) Clone → branch → push branch → PR within the same repo
Fork and pull External contributors without write access (open source) Fork → clone fork → branch → push to fork → PR to original

1.3 Collaboration features

Pull requests, code review, comments and suggestions, issues, projects, discussions, CODEOWNERS, branch rulesets, CI status checks, notifications, mentions.

14.18

Forking Repositories

Source S40 · 3. Forking Repositories

3.1 Definition

A fork is a copy of a repository under your own account on GitHub, which shares history with the original. You can push freely to your fork and propose changes back via pull requests.

3.2 When to fork

  • Contributing to open-source projects.
  • When you don't have write access to the original.
  • To experiment from someone else's project.
  • (In some companies) inner-source contributions across teams.

3.3 How

  1. Open the original repository (e.g. github.com/company/retail-data-platform).
  2. Click Fork → choose owner → optionally Copy the main branch only → Create fork.
  3. Result: github.com/ravi/retail-data-platform ("forked from company/retail-data-platform").
gh repo fork company/retail-data-platform --clone

3.4 Fork vs clone vs branch

Fork Clone Branch
Where GitHub (server-side) Your computer Inside a repository
Purpose Own copy to propose changes Work locally Isolate a change
Needs write access to original No No (to read) Yes (to push)

14.20

Upstream Repository

Source S40 · 5. Upstream Repository

The upstream remote points to the original repository so you can receive its updates.

git remote add upstream https://github.com/company/retail-data-platform.git
git remote -v
# origin    https://github.com/ravi/retail-data-platform.git      (your fork – push here)
# upstream  https://github.com/company/retail-data-platform.git   (original – fetch from here)

Prevent accidental pushes to upstream:

git remote set-url --push upstream DISABLE

Synchronizing Forked Repositories

Source S40 · 6. Synchronizing Forked Repositories

Your fork does not update automatically when the original changes.

6.1 Command line

git fetch upstream
git switch main
git merge upstream/main        # or: git rebase upstream/main
git push origin main           # update your fork on GitHub

Update your feature branch too:

git switch fix/typo-readme
git rebase main                # or merge
git push --force-with-lease    # if rebased and already pushed

6.2 GitHub web

On your fork's page, click Sync fork → Update branch.

6.3 GitHub CLI

gh repo sync ravi/retail-data-platform -b main
14.22

Pull Requests

Source S40 · 7. Pull Requests

7.1 Definition

A pull request (PR) is a request to merge changes from one branch (head/compare) into another (base), combined with a space for discussion, review, automated checks and approval.

7.2 Anatomy of a PR

Tab / Area Contents
Conversation Description, comments, review summaries, timeline, merge box
Commits Commits included
Checks CI results (GitHub Actions, external checks)
Files changed Diff with line comments and suggestions
Sidebar Reviewers, assignees, labels, projects, milestone, linked issues

7.3 PR lifecycle

Branch pushed → PR opened (draft/ready) → CI checks → Review (comments / changes requested)
  → Author updates → Approved → Merge (merge/squash/rebase) → Branch deleted → Issue closed
14.23

Creating Pull Requests

Source S40 · 8. Creating Pull Requests

8.1 Push your branch

git switch -c feature/DE-1423-scd2-customer
# commits...
git push -u origin feature/DE-1423-scd2-customer

8.2 On GitHub

  1. Click Compare & pull request (banner) or Pull requests → New pull request.
  2. Choose base (main) and compare (your branch). For forks: base repository = original, head repository = your fork.
  3. Write a clear title: feat(sql): implement SCD Type 2 for dim_customer.
  4. Fill in the description (what, why, how tested, screenshots, Closes #42).
  5. Add reviewers, assignees, labels, project, milestone.
  6. Choose Create pull request or Create draft pull request (not ready for review; can't be merged).

8.3 GitHub CLI

gh pr create --base main --title "feat(sql): SCD2 for dim_customer" \
  --body "Implements SCD Type 2. Closes #42" --reviewer priya --label enhancement
gh pr create --draft --fill
gh pr status
gh pr view --web

8.4 Good PR practices

  • Small and focused (one purpose).
  • Self-review the diff before requesting review.
  • Explain why, not just what.
  • Include test evidence (row counts, screenshots of pipeline runs).
  • Keep the branch up to date with main.
14.24

Reviewing Pull Requests

Source S40 · 9. Reviewing Pull Requests

9.1 How to review

  1. Open the PR → Files changed.
  2. Use Viewed checkboxes to track progress; switch to split view if helpful.
  3. Click + on a line (or drag across lines) to add a comment.
  4. Use suggestions for small fixes the author can apply in one click:
```suggestion
    WHERE is_active = 1
```
  1. Choose Add single comment or Start a review (batch comments).
  2. Click Review changes → write a summary → choose Comment, Approve or Request changes → Submit review.

9.2 What to look for (Data Engineering checklist)

  • Correctness of joins, filters, aggregations and business rules.
  • Idempotency (can the load run twice safely?).
  • Handling of NULLs, duplicates, late-arriving data.
  • Performance (partitioning, indexes, avoiding SELECT *, broadcast joins).
  • Schema changes are backwards-compatible.
  • No hard-coded environment names, paths or secrets.
  • Tests added/updated; CI green.
  • Naming conventions and readability.
  • Documentation updated.

9.3 Review etiquette

Be specific and kind, explain reasoning, distinguish blocking issues from nits (prefix "nit:"), and respond promptly.

9.4 CLI review

gh pr checkout 57
gh pr diff 57
gh pr review 57 --comment -b "Looks good, one question on the MERGE key"
14.25

Approving Pull Requests

Source S40 · 10. Approving Pull Requests
  • Review changes → Approve → Submit review, or gh pr review 57 --approve.
  • Approvals count toward branch protection's required approvals.
  • If the ruleset has Dismiss stale approvals when new commits are pushed, new commits reset approvals.
  • Code owner approval may be required for files listed in CODEOWNERS.
  • Authors cannot approve their own PRs.
14.26

Requesting Changes

Source S40 · 11. Requesting Changes
  • Review changes → Request changes → Submit review, or gh pr review 57 --request-changes -b "Please add tests for null dates".
  • Blocks merging (when reviews are required) until the reviewer approves or the review is dismissed.
  • The author pushes fixes to the same branch — the PR updates automatically — then clicks Re-request review.
  • Resolve conversations when addressed (Resolve conversation), especially if conversation resolution is required.
14.27

Merging Pull Requests

Source S40 · 12. Merging Pull Requests

12.1 Merge methods

Method Result on base branch When to use
Create a merge commit All commits + a merge commit (--no-ff) Preserve full history
Squash and merge One commit containing all changes Clean history; messy branch commits
Rebase and merge Each commit replayed linearly, no merge commit Linear history with meaningful commits

12.2 Merge prerequisites

Required approvals, passing status checks, resolved conversations, branch up to date (if required), no conflicts.

12.3 Options

  • Auto-merge — enable on the PR; GitHub merges automatically once requirements are met.
  • Merge queue — for busy repos; PRs are tested together with the latest base before merging.
  • Delete branch button after merging (or auto-delete setting).
gh pr merge 57 --squash --delete-branch
gh pr merge 57 --auto --squash

12.4 After merging

git switch main
git pull
git branch -d feature/DE-1423-scd2-customer
git fetch --prune

Pull request vs. branch (S41)

S41 asks how a pull request differs from a branch: a branch is a Git ref holding commits; a pull request is a platform object that proposes merging one branch into another and holds the review conversation, checks and approvals. Deleting the branch after merging keeps the PR record.

Best practices

Course addition · best practices
  • Small PRs (< ~400 changed lines) with a clear title, description, linked issue and test evidence.
  • Use draft PRs for early feedback; mark ready when checks pass.
  • Review for correctness, security, data impact and readability; use suggestions for small fixes.
  • Require CI checks and code-owner reviews; dismiss stale approvals.
  • Choose the merge method per repository policy and delete branches afterwards.

Chapter 14 Interview Questions

Source S15 · Chapter manual · interview
1. What is a GitHub collaborator?

A user or team granted access to a repository.

2. What is a fork?

A GitHub-hosted copy of a repository under another owner or namespace.

3. Difference between clone and fork?

Fork creates a hosted copy on GitHub; clone downloads a repository to a local machine.

4. What is origin in a fork workflow?

Usually the contributor's fork.

5. What is upstream in a fork workflow?

Usually the original source repository.

6. How do you synchronize a fork?

Fetch upstream, update local main according to policy and push the update to origin.

7. What is a pull request?

A proposal to merge changes from a source branch into a target branch, with discussion and checks.

8. Does opening a PR merge code?

No. It proposes the change; merging is a separate action.

9. What should a reviewer check?

Correctness, maintainability, tests, security, performance and operational impact.

10. What does Approve mean?

The reviewer gives a positive review decision, subject to repository rules.

11. When should you request changes?

When blocking issues must be corrected before merge.

12. Name common PR merge methods.

Merge commit, squash and merge, and rebase and merge.

13. How do you resolve a PR conflict locally?

Fetch target changes, merge or rebase the target into the source branch, resolve, test and push.

14. What happens when a PR is closed without merging?

Its changes are not integrated into the target branch.

15. What is a PR template?

A repository template that provides a standard structure for pull request descriptions.

Beginner
What is a pull request?

A request to merge changes from one branch into another, with discussion, reviews and automated checks before merging.

What is a fork?

A server-side copy of a repository under your account, used to propose changes without write access to the original.

Intermediate
How do you keep a fork up to date?

Add the original as upstream, fetch it, fast-forward or rebase your branches onto upstream/main, push to your fork (or use "Sync fork").

Compare the three GitHub merge methods.

Merge commit keeps all commits plus a merge commit; squash combines into one commit; rebase replays commits linearly without a merge commit.

Advanced
Why do workflows triggered by PRs from forks not get secrets?

To prevent untrusted code from exfiltrating secrets; pull_request from forks gets a read-only GITHUB_TOKEN. pull_request_target runs in the base context and must never check out and execute untrusted PR code with secrets — since actions/checkout@v7 (June 2026) checkout refuses to fetch fork PR code in such workflows by default.

Scenario
A PR has 60 files and 3,000 changed lines. What do you do as a reviewer?

Ask the author to split it (by component: SQL, ADF, Python) or into preparatory refactors and behaviour changes; review commits separately; insist on tests.
