7.1

What is branching?

Source S08 · Chapter manual · 1. What is branching?

A branch is a movable name that points to a commit. It gives a developer an independent line of development. When a new commit is made on a branch, the branch reference advances to that commit.

Example: your stable warehouse code is on main. You need to implement a customer validation rule. Create feature/customer-validation, make and test the changes there, then merge them after review.

main
A → B
feature/customer-validation
A → C → D

Both branches share earlier history and then advance independently.

Key concept: A branch is not normally a complete copy of the project. It is a lightweight reference to a commit; Git reuses its object database.

Why branches are useful

  • Isolation: experimental changes do not immediately affect stable code.
  • Parallel development: several developers can work on separate tasks.
  • Code review: changes can be reviewed before integration.
  • Release management: a release can be stabilized while new work continues.
  • Recovery: unfinished or risky work can remain separate from production-ready code.
7.2

How Git branches work internally

Source S08 · Chapter manual · 2. How Git branches work internally

Git stores commits in a directed acyclic graph (DAG). A commit points to its parent commit or commits. A branch name points to the latest commit on that line.

Commit A
Commit B
Commit C

The main reference may point to Commit C. Creating a new branch at this point makes another reference to the same commit.

Local branch references live under refs/heads/. For example, refs/heads/main identifies the local main branch.

git branch feature/customer-check git show-ref --heads git log --oneline --decorate --graph --all

Branch names move as commits are added. Commit IDs identify individual commit objects. This is why creating many branches is inexpensive compared with copying the entire project.

7.4

Create, list and switch branches

Source S08 · Chapter manual · 4. Create, list and switch branches

Use git branch to inspect or create local branches. Creating a branch does not switch to it.

git branch # list local branches git branch feature/new-report # create branch git branch -v # list with latest commit git branch -a # local and remote-tracking branches git branch --show-current # current branch # Create and switch in one step git switch -c feature/new-report # Switch between branches git switch main git switch feature/new-report # Older equivalent syntax git checkout -b feature/another-change git checkout main

git switch is the modern command focused on switching branches. git checkout remains supported and is also used for other checkout operations.

What happens during a switch?

  • HEAD is updated to identify the selected branch.
  • The index and working tree are updated to match the selected commit, subject to safety checks.
  • Git may refuse if local uncommitted changes would be overwritten.
Best practice: Run git status before switching. Commit or stash unrelated work rather than assuming every uncommitted change can safely follow you.
7.5

Rename and delete branches

Source S08 · Chapter manual · 5. Rename and delete branches
# Rename a local branch git branch -m old-name new-name # Rename the current branch git branch -m feature/better-name # Safely delete a merged local branch git branch -d feature/old-report # Force deletion, even if unmerged git branch -D experiment/temp

The -d option checks whether Git considers the branch merged. -D forces deletion and may remove easy access to unmerged work.

Warning: Inspect the branch and preserve any needed commits before using -D. Deleting a local branch does not delete the branch on GitHub or another remote. Remote deletion is a separate operation.
7.6

HEAD and detached HEAD

Source S08 · Chapter manual · 6. HEAD and detached HEAD

HEAD identifies the current checkout. In normal branch-based work, HEAD is a symbolic reference to a local branch such as main.

HEAD
main
Commit C

HEAD symbolically points to main; main points to the current commit.

Detached HEAD occurs when you check out a commit ID or tag rather than a local branch. It is useful for inspecting an older version, but commits created there are not automatically attached to a named branch.

git switch --detach a1b2c3d # inspect or test the older version # Return to a branch git switch main # Preserve a commit made while detached git switch -c experiment/keep-work
If you create commits in detached HEAD and want to keep them, create a branch pointing to the commit before switching away.
7.7

Feature-branch workflow example

Source S08 · Chapter manual · 7. Feature-branch workflow example

Scenario: add a SQL data-quality validation to a warehouse project.

git switch main git pull --ff-only git switch -c feature/customer-quality-check # Edit and validate the SQL file git status git diff git add sql/customer_quality_check.sql git commit -m "Add customer quality validation" # Publish the branch for review git push -u origin feature/customer-quality-check

Open a pull request, request review, address feedback, run checks and merge according to team policy. After merging, update main and delete the finished feature branch when appropriate.

Data Engineering branch examples

  • feature/adf-customer-ingestion — new ADF ingestion pipeline.
  • bugfix/sql-null-handling — correct null handling in a stored procedure.
  • feature/databricks-orders-dq — add notebook-based validation.
  • hotfix/fabric-refresh-failure — urgent production correction.

What is Branching?

Source S40 · 1. What is Branching?

1.1 Definition

Branching means diverging from the main line of development to work independently, without affecting the main line. In Git, a branch is a lightweight, movable pointer to a commit.

1.2 Visual

main:              A ── B ── C ─────────── G   (merge)
                              \           /
feature/orders:                D ── E ── F

Commits D, E, F are made on feature/orders; main is unaffected until the merge at G.

1.3 Real-time example

You need to add an orders load pipeline while production customer loads keep running from main. You create feature/orders-load, work there for three days, and merge only when it is reviewed and tested.

7.10

Why Do We Need Branches?

Source S40 · 2. Why Do We Need Branches?
Reason Explanation
Isolation Unfinished work doesn't break the stable code
Parallel development Many developers/features progress simultaneously
Code review Each branch becomes a focused pull request
Experimentation Try ideas safely; delete the branch if they fail
Release management Stabilise a release while new development continues
Hotfixes Fix production quickly without shipping unfinished features
Environment flow Promote tested code through Dev → Test → Prod
Traceability Branch names link work to tickets (feature/DE-1423-...)

Without branches: everyone commits to one line; a half-finished change blocks a release; an urgent fix must wait.

7.11

How Git Branches Work Internally

Source S40 · 3. How Git Branches Work Internally

3.1 A branch is a file containing a hash

cat .git/refs/heads/main
# 9c8b7a6d5e4f3a2b1c0d9e8f7a6b5c4d3e2f1a0b

Creating a branch writes one tiny file — that's why it's instant, regardless of project size.

3.2 Commits move the current branch

Before commit:    A ── B ── C   ← main ← HEAD
After commit:     A ── B ── C ── D   ← main ← HEAD

Only the branch HEAD points to moves.

3.3 Two branches on the same commit

git branch feature/x

A ── B ── C   ← main ← HEAD
              ← feature/x

Both names point to C. After switching to feature/x and committing, only feature/x moves.

3.4 Where branches are stored

Kind Location
Local branches .git/refs/heads/
Remote-tracking branches .git/refs/remotes/origin/
Packed refs .git/packed-refs
7.12

Main Branch

Source S40 · 4. Main Branch
  • The primary branch of most modern repositories; represents stable, production-ready code.
  • Default branch on GitHub, GitLab and Azure Repos since 2020.
  • Usually protected: no direct pushes; changes arrive via pull requests with reviews and passing CI.
  • Deployments to production are typically made from main (or from tags on main).
git config --global init.defaultBranch main
7.13

Master Branch

Source S40 · 5. Master Branch
  • The historical default branch name in Git and older repositories.
  • Functionally identical to main — the name has no special meaning to Git.
  • Many organisations renamed master to main.

Renaming master to main:

git branch -m master main
git push -u origin main
# On GitHub/Azure Repos: set default branch to main in settings
git push origin --delete master

Teammates update their clones:

git fetch origin
git branch -m master main
git branch -u origin/main main
git remote set-head origin -a
7.14

Development Branch

Source S40 · 6. Development Branch
  • Commonly named develop or dev.
  • An integration branch where completed features are merged before release (used in Git Flow).
  • Always contains the latest delivered development changes for the next release.
  • Deployed automatically to a Dev/Integration environment.
git switch -c develop main
git push -u origin develop
7.15

Feature Branch

Source S40 · 7. Feature Branch
  • Created for one feature, user story or task.
  • Naming: feature/<ticket>-<short-description>, e.g. feature/DE-1423-orders-load.
  • Branched from main (GitHub Flow) or develop (Git Flow).
  • Short-lived: merged via PR and deleted.
git switch main && git pull
git switch -c feature/DE-1423-orders-load
7.16

Release Branch

Source S40 · 8. Release Branch
  • Created when the code is ready to be prepared for a release, e.g. release/2.4.0.
  • Only bug fixes, documentation and release metadata (version numbers) go here — no new features.
  • Deployed to Test/UAT for validation.
  • Merged into main (and tagged) and back into develop.
git switch -c release/2.4.0 develop
7.17

Hotfix Branch

Source S40 · 9. Hotfix Branch
  • Created from main (or the production tag) to fix a critical production issue immediately.
  • Naming: hotfix/<version-or-ticket>, e.g. hotfix/2.4.1 or hotfix/DE-1501-null-dates.
  • Merged into main (tagged) and into develop/active release branches so the fix isn't lost.
git switch -c hotfix/2.4.1 v2.4.0

Branch types summary:

Branch Created from Merged into Lifetime
main — — Permanent
develop main — Permanent
feature/* develop or main develop or main Days
release/* develop main + develop Days–weeks
hotfix/* main main + develop Hours–days
7.18

Creating Branches

Source S40 · 10. Creating Branches
git branch feature/dim-product                 # create (stay on current branch)
git switch -c feature/dim-product              # create and switch (recommended)
git checkout -b feature/dim-product            # create and switch (older syntax)
git switch -c hotfix/null-dates a1b2c3d        # create from a specific commit
git switch -c release/2.4.0 v2.4.0-rc1         # create from a tag
git switch -c feature/x origin/feature/x       # create from a remote branch
git branch --track feature/x origin/feature/x  # create with tracking

Tip Always update your base branch first: git switch main && git pull, then create your branch.

7.20

Switching Branches

Source S40 · 12. Switching Branches
git switch main                    # switch to an existing branch
git switch -                       # switch back to the previous branch
git checkout main                  # older syntax
git switch -c new-branch           # create and switch
git switch --discard-changes main  # switch, throwing away local edits

What happens: Git updates the working directory and staging area to match the target branch's latest commit and moves HEAD.

If you have uncommitted changes:

  • If they don't conflict with the target branch, Git carries them over.
  • If they conflict, Git refuses: commit them, stash them (git stash), or discard them first.
error: Your local changes to the following files would be overwritten by checkout:
        sql/procedures/usp_load_customers.sql
Please commit your changes or stash them before you switch branches.

Renaming Branches

Source S40 · 13. Renaming Branches
git branch -m new-name                  # rename current branch
git branch -m old-name new-name         # rename another branch
git branch -M old-name new-name         # force (overwrite existing name)

Renaming a branch that exists on the remote:

git branch -m feature/oders feature/orders
git push origin -u feature/orders
git push origin --delete feature/oders
7.22

Deleting Branches

Source S40 · 14. Deleting Branches
git branch -d feature/dim-product       # safe delete — only if merged
git branch -D feature/dim-product       # force delete — even if not merged
git push origin --delete feature/dim-product   # delete on remote
git fetch --prune                        # remove stale remote-tracking branches

Safe delete error:

error: The branch 'feature/dim-product' is not fully merged.
If you are sure you want to delete it, run 'git branch -D feature/dim-product'.

Note You cannot delete the branch you're currently on — switch away first. A force-deleted branch can be recovered from the reflog.

7.23

Understanding HEAD

Source S40 · 15. Understanding HEAD

15.1 Definition

HEAD is a pointer to your current position in the repository — normally a symbolic reference to the current branch, which in turn points to a commit.

cat .git/HEAD
# ref: refs/heads/feature/dim-product

HEAD → feature/dim-product → commit E

15.2 Behaviour

  • git switch main changes HEAD to ref: refs/heads/main.
  • git commit moves the branch that HEAD points to.
  • HEAD~1, HEAD^ are references relative to HEAD.
git rev-parse HEAD
git log -1 HEAD
git symbolic-ref HEAD
7.24

Detached HEAD State

Source S40 · 16. Detached HEAD State

16.1 Definition

Detached HEAD means HEAD points directly to a commit instead of to a branch.

Normal:    HEAD → main → C
Detached:  HEAD → B      (no branch)

16.2 How it happens

git switch --detach a1b2c3d     # check out a commit
git checkout a1b2c3d            # same (older syntax)
git checkout v1.0.0             # checking out a tag
git checkout origin/main        # checking out a remote-tracking branch

Git warns:

You are in 'detached HEAD' state. You can look around, make experimental
changes and commit them, and you can discard any commits you make in this
state without impacting any branches by switching back to a branch.

16.3 Uses

  • Inspect old code (e.g. reproduce a bug in release v1.0.0).
  • Run tests on a historical commit.
  • CI systems often build in detached HEAD.

16.4 Risk

New commits in detached HEAD belong to no branch. When you switch away, they become unreachable and will eventually be garbage-collected.

16.5 Keeping work done in detached HEAD

git switch -c fix/from-old-version      # create a branch at the current commit
# or after switching away:
git reflog                              # find the commit
git branch rescued <sha>

16.6 Leaving detached HEAD

git switch main

Real-time scenarios

Source S08, S40 · Testing an old release in detached HEAD

Support asks how v1.0.0 behaved. git switch --detach v1.0.0, run the tests, then git switch -. If a fix is made there, git switch -c hotfix/RDP-140-v1-fix before switching away so the commit is not lost.

Course addition · Started coding on main by mistake

No commit yet: git switch -c feature/RDP-110-x — uncommitted changes move with you. Already committed (not pushed): create the branch, then reset main to origin/main (Chapter 6 scenario).

Best practices

Course addition · best practices
  • Never commit directly to main; protect it on the server.
  • Branch from an up-to-date main; keep branches short-lived (days, not weeks).
  • Name branches by type and work item.
  • Delete branches after merge; prune remote-tracking refs (fetch.prune true).
  • Use git switch/git restore instead of git checkout in new scripts and docs.

Chapter 7 Interview Questions

Source S08 · Chapter manual · interview
1. What is a Git branch?

A movable reference to a commit representing a line of development.

2. Does creating a branch copy the entire repository?

No. It creates a lightweight reference; Git reuses commit and object data.

3. Difference between git branch and git switch?

git branch manages branch references; git switch changes the checked-out branch.

4. Does git branch feature-x switch to it?

No. It creates the branch only.

5. What is HEAD?

The reference identifying the current checkout, normally pointing symbolically to a local branch.

6. What is detached HEAD?

HEAD points directly to a commit rather than to a local branch.

7. How do you create and switch to a branch?

git switch -c branch-name.

8. How do you delete a merged local branch?

git branch -d branch-name.

9. Difference between -d and -D?

-d checks merged status; -D forces deletion.

10. Are feature and hotfix branches special Git objects?

No. They are workflow and naming conventions.

11. Can two branches point to the same commit?

Yes. Newly created branches often start at the same commit.

12. How do you list remote-tracking branches?

git branch -r; git branch -a lists local and remote-tracking branches.

13. Does deleting a local branch delete the remote branch?

No. Remote deletion is separate.

14. Why prefer short-lived feature branches?

They reduce divergence and make review and integration easier.

15. How do you preserve detached HEAD work?

Create a branch at that commit with git switch -c branch-name.

Beginner
What is a branch in Git?

A lightweight movable pointer (a ref) to a commit; new commits on the branch move the pointer forward.

How do you create and switch to a branch in one command?

git switch -c <name> (or git checkout -b <name>).

Intermediate
What is HEAD?

A reference to the current position — normally a symbolic ref to the checked-out branch; in detached state it holds a commit ID directly.

What is the difference between git branch -d and -D?

-d deletes only if the branch is merged into its upstream or HEAD; -D forces deletion.

Advanced
Where are branches stored?

As files under .git/refs/heads/ or as entries in .git/packed-refs (and, with the reftable backend, in reftable files).

Scenario
You made two commits in detached HEAD and switched back to main. How do you recover them?

Git prints the commit ID when you leave; otherwise use git reflog to find it and git branch rescue <sha>.

Key takeaways
  • Branches are cheap pointers; HEAD points to the current branch.
  • git switch -c creates and switches; git branch lists, renames and deletes.
  • Detached HEAD is safe for inspection; create a branch to keep commits.
  • Project branches follow type/RDP-id-description.
