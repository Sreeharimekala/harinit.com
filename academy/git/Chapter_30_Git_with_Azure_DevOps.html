Learning objectives

Chapter introduction

What it is. Azure DevOps is Microsoft's suite for planning (Boards), source control (Repos), CI/CD (Pipelines), testing (Test Plans) and packages (Artifacts). Azure Repos hosts Git repositories with branch policies and pull requests; Azure Pipelines runs YAML pipelines with environments and approvals.

Why it matters. Many Microsoft data teams run ADF, Databricks, Fabric and SQL deployments from Azure DevOps; its branch policies and environments are the enterprise control points.

Where it is used. Enterprise data platforms, regulated industries, organizations standardized on Azure and Entra ID.

In this course's project. Stage 7 (alternative path): the platform repository is mirrored/hosted in Azure Repos project RDP, protected with branch policies, linked to Azure Boards work items, and delivered by a multi-stage YAML pipeline Dev → Test → Prod with approvals.

Source S40 · earlier complete course

This chapter covers Azure DevOps — Azure Repos, connecting local Git, branch policies, pull requests, code reviews, Azure Boards integration, Azure Pipelines (YAML, build and release), Git-based deployment, multiple environments and CI/CD best practices.

Learning objective By the end of this chapter, you should be able to run a complete Git + CI/CD process for a data platform on Azure DevOps.

Branch Policies

Source S40 · 5. Branch Policies

Repos → Branches → main → … → Branch policies:

Policy Purpose
Require a minimum number of reviewers e.g. 2; options: allow requestors to approve own changes (off), prohibit most recent pusher from approving, reset votes on new pushes
Check for linked work items Every PR linked to a Boards item
Check for comment resolution All comments resolved
Limit merge types Allow only e.g. Squash or Merge (no fast-forward)
Build validation A pipeline must succeed for the PR (with expiry)
Status checks External services post statuses
Automatically included reviewers Required reviewers by path, e.g. /sql/* → DBA group

Plus branch security (… → Branch security): deny Force push, Bypass policies, Contribute for most groups. Policies can be set across all repositories in a project (Project settings → Repositories → Policies).

Note With policies on main, direct pushes are blocked — all changes go through PRs.

Pull Requests

Source S40 · 6. Pull Requests

6.1 Create

  • After pushing a branch, Repos shows Create a pull request; or Repos → Pull requests → New pull request.
  • Choose source → target branch, title, description (supports Markdown and PR templates in .azuredevops/pull_request_template.md), reviewers (required/optional), work items, tags.
  • Create as draft if not ready.
az repos pr create --source-branch feature/DE-1600-dim-store --target-branch main \
  --title "feat(sql): add dim_store" --work-items 1600 --reviewers "sql-team"

6.2 Complete (merge)

Click Complete (when policies pass) and choose the merge type:

Merge type Result
Merge (no fast-forward) Merge commit preserving branch history
Squash commit One commit on target
Rebase and fast-forward Commits replayed linearly
Semi-linear merge Rebase then merge commit

Options: Complete associated work items, Delete source branch, customise commit message. Set auto-complete to merge automatically when policies pass.

6.3 Abandon / reactivate

Abandon closes the PR without merging; it can be reactivated later.

YAML Pipelines

Source S40 · 10. YAML Pipelines

10.1 Structure

trigger:                    # CI trigger
  branches:
    include: [main]
  paths:
    include: [python/*, sql/*]

pr:                         # PR trigger (for GitHub repos; Azure Repos uses build validation policy)
  branches:
    include: [main]

schedules:
  - cron: "0 1 * * *"
    displayName: Nightly
    branches:
      include: [main]
    always: true

pool:
  vmImage: ubuntu-latest

variables:
  - name: pythonVersion
    value: '3.11'
  - group: rdp-common       # variable group

stages:
  - stage: Build
    jobs:
      - job: Test
        steps:
          - task: UsePythonVersion@0
            inputs:
              versionSpec: $(pythonVersion)
          - script: pip install -r python/requirements.txt pytest
            displayName: Install dependencies
          - script: pytest python/tests --junitxml=test-results.xml
            displayName: Run tests
          - task: PublishTestResults@2
            condition: always()
            inputs:
              testResultsFiles: test-results.xml

10.2 Key syntax

Element Example
Variable usage $(pythonVersion) (runtime), ${{ variables.x }} (compile time), $[ ... ] (runtime expression)
Conditions condition: and(succeeded(), eq(variables['Build.SourceBranch'], 'refs/heads/main'))
Dependencies dependsOn: Build
Templates - template: templates/deploy.yml with parameters:
Predefined variables Build.SourceBranch, Build.BuildId, Build.SourceVersion, System.DefaultWorkingDirectory, Pipeline.Workspace

10.3 Templates for reuse

# templates/deploy.yml
parameters:
  - name: environment
    type: string
  - name: serviceConnection
    type: string
jobs:
  - deployment: Deploy_${{ parameters.environment }}
    environment: rdp-${{ parameters.environment }}
    pool: { vmImage: ubuntu-latest }
    strategy:
      runOnce:
        deploy:
          steps:
            - task: AzureCLI@2
              inputs:
                azureSubscription: ${{ parameters.serviceConnection }}
                scriptType: bash
                scriptLocation: inlineScript
                inlineScript: ./scripts/deploy.sh ${{ parameters.environment }}

Build and Release Pipelines

Source S40 · 11. Build and Release Pipelines

11.1 Classic vs YAML

Classic Build + Release pipelines YAML multi-stage pipelines
Definition UI designer Code in repository
Versioned with code No Yes
Reviewable in PRs No Yes
Release stages/approvals Release pipeline stages Stages + environments with checks
Recommendation Legacy/existing setups Recommended for new work

11.2 Multi-stage YAML: build → release

trigger:
  branches: { include: [main] }

stages:
  - stage: Build
    jobs:
      - job: Build
        pool: { vmImage: ubuntu-latest }
        steps:
          - task: UsePythonVersion@0
            inputs: { versionSpec: '3.11' }
          - script: |
              pip install build pytest -r python/requirements.txt
              pytest python/tests
              python -m build python/
            displayName: Test and build wheel
          - task: CopyFiles@2
            inputs:
              Contents: |
                python/dist/**
                adf/**
                databricks/**
                sql/**
              TargetFolder: $(Build.ArtifactStagingDirectory)
          - publish: $(Build.ArtifactStagingDirectory)
            artifact: drop

  - stage: DeployDev
    dependsOn: Build
    jobs:
      - template: templates/deploy.yml
        parameters: { environment: dev, serviceConnection: sc-rdp-dev }

  - stage: DeployTest
    dependsOn: DeployDev
    jobs:
      - template: templates/deploy.yml
        parameters: { environment: test, serviceConnection: sc-rdp-test }

  - stage: DeployProd
    dependsOn: DeployTest
    condition: and(succeeded(), eq(variables['Build.SourceBranch'], 'refs/heads/main'))
    jobs:
      - template: templates/deploy.yml
        parameters: { environment: prod, serviceConnection: sc-rdp-prod }

Deployment jobs automatically download the drop artifact into $(Pipeline.Workspace)/drop.

30.26

Git-Based Deployment

Source S40 · 12. Git-Based Deployment
  • Every deployment starts from Git: a commit on main or a tag triggers the pipeline.
  • The pipeline records the source version (Build.SourceVersion) and links to commits and work items.
  • Tag-based releases:
trigger:
  tags:
    include: ['v*']
  • Tag the repository after a successful production deployment (optional step using git tag with persistCredentials: true on checkout and Contribute/Create tag permission for the build service).
  • Rollback: re-run the pipeline for a previous run/tag or revert in Git and redeploy.
  • No manual changes in Test/Prod — all through the pipeline.

Managing Multiple Environments

Source S40 · 13. Managing Multiple Environments

13.1 Environments

Pipelines → Environments → New environment (rdp-dev, rdp-test, rdp-prod) → Approvals and checks:

Check Use
Approvals Named approvers/groups for Prod
Branch control Only refs/heads/main / tags may deploy
Business hours Deploy only in change windows
Exclusive lock One deployment at a time
Invoke Azure Function / REST API Custom gates (e.g. change ticket approved)
Query Azure Monitor alerts Block if alerts are active

Deployment history per environment shows which run/commit is deployed.

13.2 Configuration per environment

  • Variable groups per environment (rdp-dev-vars, rdp-prod-vars), linked to Azure Key Vault for secrets.
  • Service connections per environment (prefer workload identity federation — no secrets).
  • Parameter files (ADF ARM parameters, bundle targets, Fabric parameter.yml) for environment-specific values.
variables:
  - ${{ if eq(parameters.environment, 'prod') }}:
    - group: rdp-prod-vars
  - ${{ else }}:
    - group: rdp-dev-vars
30.28

CI/CD Best Practices

Source S40 · 14. CI/CD Best Practices
  1. Pipelines as code (YAML) reviewed in PRs.
  2. PR build validation on every PR to main.
  3. Build once, deploy many — promote the same artifact.
  4. Small, frequent changes with fast feedback.
  5. Automated tests at multiple levels (unit, data quality, integration).
  6. Secrets in Key Vault; workload identity federation for service connections; never secrets in YAML.
  7. Approvals and checks for Test/Prod; branch control.
  8. Templates for reuse and consistency across projects.
  9. Idempotent deployments — re-running is safe.
  10. Version and tag releases; traceability to work items.
  11. Rollback plan documented and tested.
  12. Monitor pipeline health and deployment metrics (lead time, deployment frequency, change failure rate, MTTR — DORA metrics).
  13. Least-privilege pipeline permissions; protect pipeline YAML with branch policies.
  14. Keep agents updated; use self-hosted agents in a VNet for private resources.

Added topics, conflicts & verification

Source conflict — `AB#` usage in Azure Repos

S31 shows AB#1234 in an Azure Repos commit. S40 distinguishes GitHub (AB#) from Azure Repos (#). Resolution (verified with Microsoft Learn): AB#ID is the syntax for GitHub commits/PRs/issues connected to Azure Boards (newer state-transition forms like Fixes AB#ID are also supported); Azure Repos uses #ID mentions or explicit links.

Command reference

Branch policies (Azure Repos)
Syntax
Project settings → Repositories → <repo> → Policies → Branch policies → main
Purpose
Protect main and require PRs.
Key parameters
  • Require a minimum number of reviewers (e.g. 2; reset votes on new pushes)
  • Check for linked work items (Required)
  • Check for comment resolution (Required)
  • Limit merge types (e.g. squash, no fast-forward)
  • Build validation (run pipeline on PR; policy required)
  • Automatically included reviewers (by path, e.g. /adf/* → ADF team)
  • Status checks from external services
Expected output
TF402455: Pushes to this branch are not permitted; you must use a pull request to update this branch.
Example
az repos policy approver-count create --repository-id <id> --branch main --minimum-approver-count 2 --creator-vote-counts false --allow-downvotes false --reset-on-source-push true --blocking true --enabled true
Common mistakes
Build validation pipeline path filter excludes folders, so changes skip validation.
Work item linking
Syntax
Azure Repos commit/PR: "#1234" mention, or Development section of the work item
GitHub → Azure Boards (Azure Boards app): "AB#1234" in commit message / PR title or description
Purpose
Traceability between Boards and code.
Example
git commit -m "feat(adf): add orders pipeline #1234"           # Azure Repos
git commit -m "feat(adf): add orders pipeline AB#1234"         # GitHub repo connected to Azure Boards
Common mistakes
Using AB# in Azure Repos (not needed) or plain #1234 in GitHub (links to GitHub issue #1234 instead).
YAML pipeline skeleton (pipelines/azure-pipelines.yml)
Syntax
trigger · pr · variables · stages → jobs/deployment jobs → steps
Purpose
CI/CD as code stored next to the platform code.
Example
trigger:
  branches: { include: [main] }
  tags: { include: ['v*'] }
pr:
  branches: { include: [main] }
variables:
  - group: rdp-common
stages:
- stage: Build
  jobs:
  - job: build
    pool: { vmImage: ubuntu-latest }
    steps:
    - task: UsePythonVersion@0
      inputs: { versionSpec: '3.12' }
    - script: pip install -r python/ingestion/requirements-dev.txt && pytest -q python
      displayName: Python tests
    - task: NodeTool@0
      inputs: { versionSpec: '20.x' }
    - script: npm ci && npm run build export $(Build.SourcesDirectory)/adf $(adfDevResourceId) "ArmTemplate"
      workingDirectory: build
      displayName: Export ADF ARM template
    - publish: build/ArmTemplate
      artifact: adf
- stage: Deploy_Test
  dependsOn: Build
  condition: and(succeeded(), eq(variables['Build.SourceBranch'], 'refs/heads/main'))
  jobs:
  - deployment: adf_test
    environment: rdp-test
    pool: { vmImage: ubuntu-latest }
    strategy:
      runOnce:
        deploy:
          steps:
          - download: current
            artifact: adf
          - task: AzureResourceManagerTemplateDeployment@3
            inputs:
              azureResourceManagerConnection: sc-rdp-test
              resourceGroupName: rg-rdp-test
              location: westeurope

              csmParametersFile: $(Pipeline.Workspace)/adf/ARMTemplateParametersForFactory.json
              overrideParameters: -factoryName adf-rdp-test

Putting approvals in YAML — approvals and checks are configured on the environment (Pipelines → Environments → rdp-prod → Approvals and checks), not in the file.

Continuous project — Stage 7: CI/CD

Continuous project · Stage 7 — Azure DevOps path for the platform
  1. Repos: create project RDP, import the GitHub repository (Repos → Import repository) or push the mirror remote from Chapter 11.
  2. Policies on main: 2 reviewers, linked work items required, comment resolution required, squash merge only, build validation with azure-pipelines.yml (PR trigger), auto-reviewers /adf/* → ADF team.
  3. Boards: user story #1234 "Orders pipeline"; branch feature/1234-orders-pipeline created from the work item (Create branch), so it is linked automatically.
  4. Service connections: sc-rdp-test / sc-rdp-prod using workload identity federation (no secrets).
  5. Environments: rdp-test (no approval), rdp-prod (approvers: Priya; check: business hours; exclusive lock).
  6. Pipeline: commit pipelines/azure-pipelines.yml; run on PR → Build only; merge → Build + Deploy_Test; tag v1.1.0 → Build + Deploy_Test + Deploy_Prod after approval.
  7. Trace: work item #1234 → Development section shows branch, commits, PR, build and release.

Real-time scenarios

Source S31, S40 · Commit message links not showing on the work item

In Azure Repos use #1234; the S31 example uses AB#1234 inside Azure Repos, which is meant for GitHub repositories connected through the Azure Boards app. Also ensure the work item exists in the same organization.

Course addition · Prod deployment must wait for change approval

Add an Approvals check and optionally an Invoke REST API or ServiceNow change management check on environment rdp-prod; the stage waits until all checks pass.

Beginner
What are the main Azure DevOps services?

Boards, Repos, Pipelines, Test Plans and Artifacts.

What is a branch policy?

A rule on a branch in Azure Repos requiring PRs with conditions such as reviewers, linked work items, comment resolution and successful builds.

Intermediate
How do you link a commit to a work item?

In Azure Repos mention #<id> in the commit message or PR (or link from the work item). From GitHub with the Azure Boards app use AB#<id>.

Where are approvals configured for YAML deployments?

On the environment's "Approvals and checks", referenced by deployment jobs via environment:.

Advanced
Explain build validation policy.

A PR policy that queues a pipeline for the PR's merge result and blocks completion until it succeeds (optionally with path filters and expiry).

Classic release pipelines vs multi-stage YAML?

YAML pipelines are versioned with the code, reviewable in PRs and reusable via templates; environments provide approvals and deployment history. Classic releases are UI-defined.

Scenario
Your org uses GitHub for code but Azure Boards for planning and Azure Pipelines for deployment. How do you wire it?

Install Azure Boards app on GitHub and use AB#id; create an Azure Pipelines GitHub service connection (GitHub App) so pipelines trigger on GitHub events; protect GitHub branches with required checks from Azure Pipelines.
