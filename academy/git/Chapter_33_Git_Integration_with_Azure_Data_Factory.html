Learning objectives

Chapter introduction

What it is. Azure Data Factory (ADF) Git integration: connecting a factory to Azure Repos or GitHub, the collaboration branch, feature branches, saving vs publishing, the publish branch (adf_publish), ARM templates, and CI/CD across Dev/Test/Prod — including automated publishing with the @microsoft/azure-data-factory-utilities npm package.

Why it matters. Without Git mode, ADF changes go straight to the live factory with no review or history. With Git mode and CI/CD, pipelines are reviewed, tested and promoted like any code.

Where it is used. Every production ADF (and Synapse pipelines, which work similarly).

In this course's project. Stage 6: adf-rdp-dev is connected to the platform repo (root folder /adf), collaboration branch main; Meera builds pl_ingest_orders on a feature branch; CI exports ARM templates and deploys to adf-rdp-test and adf-rdp-prod.

33.18

Introduction to ADF Git Integration

Source S40 · 1. Introduction to ADF Git Integration

1.1 Two authoring modes

Mode Behaviour
Live mode (Data Factory mode) Every save goes directly to the factory service — no history, no branches, no review
Git mode ADF Studio saves resource definitions (JSON) to a Git repository branch; the factory service is only updated when you publish

1.2 What gets stored in Git

Each ADF resource is saved as a JSON file:

adf/
├── pipeline/
│   └── PL_Load_Customers.json
├── dataset/
│   └── DS_ADLS_Customers_Csv.json
├── linkedService/
│   ├── LS_ADLS.json
│   └── LS_KeyVault.json
├── dataflow/
├── trigger/
│   └── TR_Daily_0200.json
├── integrationRuntime/
├── managedVirtualNetwork/
├── factory/
│   └── adf-rdp-dev.json           # factory-level settings (e.g. global parameters)
└── publish_config.json            # publish branch setting

1.3 Benefits

Version history, branches and parallel development, pull request reviews, ability to save incomplete work (Git mode allows saving resources that don't validate yet), CI/CD to Test/Prod, rollback.

33.21

Connecting ADF to Git

Source S40 · 4. Connecting ADF to Git

4.1 Steps

  1. Open ADF Studio (adf.azure.com) for the Development factory.
  2. Manage hub → Source control → Git configuration → Configure (also available from the home page banner Set up code repository).
  3. Choose Azure DevOps Git or GitHub and fill in the settings above.
  4. Tick Import existing resources to copy the factory's current resources into the collaboration branch (choose the branch to import into).
  5. Apply. ADF Studio now shows a branch dropdown in the top bar.

4.2 Permissions

  • Configuring Git requires the Data Factory Contributor role (or higher) on the factory.
  • Developers need Data Factory Contributor on the Dev factory and write access to the repository.

4.3 Best practice

Important Configure Git only on the Development factory. Test/UAT and Production factories should not be Git-connected — they are updated only by the CI/CD pipeline.

4.4 Disconnecting / switching repositories

Manage → Git configuration → Disconnect (requires typing the factory name). Unpublished changes stay in the repository; reconnect to another repo if needed.

33.22

Collaboration Branches

Source S40 · 5. Collaboration Branches

5.1 Definition

The collaboration branch (usually main) is the integration branch where all developers' changes are merged via pull requests. It is the only branch from which you can publish to the Dev factory service (classic publish).

5.2 Rules

  • Protect it with branch policies/rulesets (PR + approvals + validation).
  • Don't develop directly on it.
  • Changing the collaboration branch later is possible in Git configuration (Edit).
33.23

Publish Branch

Source S40 · 6. Publish Branch

6.1 Definition

The publish branch (default adf_publish) is where ADF writes the generated ARM templates when you click Publish in classic mode.

adf_publish/
└── adf-rdp-dev/
    ├── ARMTemplateForFactory.json
    ├── ARMTemplateParametersForFactory.json
    ├── globalParameters/
    └── linkedTemplates/
        ├── ArmTemplate_master.json
        ├── ArmTemplate_0.json
        └── ArmTemplateParameters_master.json

6.2 Characteristics

  • Managed by ADF — don't edit it manually and don't merge it into main.
  • Its name is set in Git configuration or in publish_config.json in the collaboration branch root folder:
{ "publishBranch": "factory/adf_publish" }
  • With automated publishing (section 12) the publish branch is not needed.

Feature Branches

Source S40 · 7. Feature Branches

7.1 Creating

In ADF Studio, branch dropdown → + New branch → name feature/DE-1800-orders-pipeline (based on the collaboration branch). Or create it in Git and select it in ADF Studio.

7.2 Working

  • Triggers can't be fired from a feature branch until published.

33.25

Saving ADF Changes

Source S40 · 8. Saving ADF Changes
  • Save (individual resource) or Save all writes JSON to the current branch.
  • In Git mode, Save = commit: each save creates a commit in the repository (commit message generated automatically, e.g. "Updating pipeline PL_Load_Orders").
  • You can save incomplete/invalid resources in Git mode (unlike live mode) — validation happens at publish/build.
  • Use Validate all before creating a PR.
33.26

Committing ADF Changes

Source S40 · 9. Committing ADF Changes
  • Commits are created by ADF Studio on save, authored by your signed-in identity.
  • Editing outside ADF Studio: you can clone the repo and edit JSON in VS Code (e.g. bulk rename parameters), commit and push — then Refresh in ADF Studio. Validate in ADF Studio afterwards.
  • View history in Azure Repos/GitHub (git log -- adf/pipeline/PL_Load_Orders.json).
git log --oneline -- adf/pipeline/PL_Load_Orders.json
git diff main feature/DE-1800-orders-pipeline -- adf/
33.27

Creating Pull Requests

Source S40 · 10. Creating Pull Requests
  1. In ADF Studio branch dropdown → Create pull request (opens Azure DevOps/GitHub with source = feature branch, target = collaboration branch).
  2. Fill in title, description, reviewers, linked work item.
  3. CI build validation runs (npm run build validate — section 14).
  4. Reviewers inspect the JSON diff — check activity changes, parameters, dataset paths, linked service references, retry/timeout policies, hard-coded values.

ADF review checklist: parameterised paths and names, Key Vault for secrets, retry/timeout settings, naming conventions, no debug-only settings, triggers intended, global parameters, failure handling (on-failure paths, alerts).

33.28

Merging ADF Branches

Source S40 · 11. Merging ADF Branches
  • Complete the PR (squash or merge commit per team policy) → changes land in main.
  • Delete the feature branch.
  • In ADF Studio, switch to main and Refresh to see merged changes.
  • Conflicts: JSON conflicts happen when two developers edit the same resource. Resolve in the PR conflict editor or locally in VS Code (keep valid JSON!), then validate in ADF Studio.

Tip Avoid two people editing the same pipeline simultaneously — split large pipelines into parent/child pipelines.

33.29

Publishing ADF Changes

Source S40 · 12. Publishing ADF Changes

12.1 Classic (manual) publish

  1. Switch to the collaboration branch in ADF Studio.
  2. Click Publish → review the pending changes → OK.
  3. ADF updates the Dev factory service (live) and generates ARM templates into the publish branch.
  4. Release pipelines pick up the templates from adf_publish.

12.2 Automated publish (recommended)

Use the @microsoft/azure-data-factory-utilities npm package in a build pipeline to validate and generate ARM templates directly from the collaboration branch — no manual Publish click, no dependency on adf_publish.

adf/build/package.json:

{
  "scripts": {
    "build": "node node_modules/@microsoft/azure-data-factory-utilities/lib/index"
  },
  "dependencies": {
    "@microsoft/azure-data-factory-utilities": "^1.0.0"
  }
}

Commands:

npm run build validate <rootFolder> <factoryResourceId>
npm run build export <rootFolder> <factoryResourceId> "ArmTemplate"

Then, in Git configuration, enable Disable publish (from ADF studio) so nobody publishes manually.

33.30

ARM Templates

Source S40 · 13. ARM Templates

13.1 What they contain

  • ARMTemplateForFactory.json — the full factory definition (pipelines, datasets, linked services, triggers, data flows, IRs, global parameters).
  • ARMTemplateParametersForFactory.json — parameter values (factory name, linked service connection properties, URLs, Key Vault base URLs...).
  • linkedTemplates/ — split templates for large factories (ARM limits).

13.2 Parameterisation

By default ADF parameterises selected properties (e.g. connection strings, URLs). Customise using arm-template-parameters-definition.json in the root folder (or Manage → ARM template → Edit parameter configuration):

{
  "Microsoft.DataFactory/factories/linkedServices": {
    "*": {
      "properties": {
        "typeProperties": {
          "url": "=",
          "baseUrl": "=",
          "connectionString": "|:-connectionString:secureString"
        }
      }
    }
  },
  "Microsoft.DataFactory/factories/triggers": {
    "properties": {
      "pipelines": [{ "parameters": { "*": "=" } }],
      "typeProperties": { "recurrence": { "interval": "=", "frequency": "=" } }
    }
  }
}

13.3 Overriding per environment

-factoryName "adf-rdp-prod"
-LS_ADLS_properties_typeProperties_url "https://strdpprod.dfs.core.windows.net/"
-LS_KeyVault_properties_typeProperties_baseUrl "https://kv-rdp-prod.vault.azure.net/"

Global parameters are included in the ARM template (enable Include global parameters in ARM template in Manage → ARM template for older factories).

33.31

ADF CI/CD Deployment

Source S40 · 14. ADF CI/CD Deployment

14.1 Flow

feature branch ──PR──► main ──► Build pipeline: npm validate + export ARM ──► artifact
                                     │
                                     ├──► Deploy Test factory  (stop triggers → ARM deploy → start triggers)
                                     └──► Deploy Prod factory  (approval → same steps)

14.2 Azure DevOps YAML pipeline

trigger:
  branches: { include: [main] }
  paths: { include: [adf/*] }

pool: { vmImage: ubuntu-latest }

variables:
  adfRoot: $(Build.Repository.LocalPath)/adf
  devFactoryId: /subscriptions/<sub-id>/resourceGroups/rg-rdp-dev/providers/Microsoft.DataFactory/factories/adf-rdp-dev

stages:
- stage: Build
  jobs:
  - job: BuildArm
    steps:
    - task: NodeTool@0
      inputs: { versionSpec: '18.x' }
    - script: npm install
      workingDirectory: $(adfRoot)/build
    - script: npm run build validate $(adfRoot) $(devFactoryId)
      workingDirectory: $(adfRoot)/build
      displayName: Validate ADF resources
    - script: npm run build export $(adfRoot) $(devFactoryId) "ArmTemplate"
      workingDirectory: $(adfRoot)/build
      displayName: Generate ARM templates
    - publish: $(adfRoot)/build/ArmTemplate
      artifact: adf-arm

- stage: DeployProd
  dependsOn: Build
  jobs:
  - deployment: DeployADF
    environment: adf-prod                       # approvals configured here
    strategy:
      runOnce:
        deploy:
          steps:
          - task: AzurePowerShell@5
            displayName: Stop triggers (pre-deployment)
            inputs:
              azureSubscription: sc-rdp-prod
              ScriptPath: $(Pipeline.Workspace)/adf-arm/PrePostDeploymentScript.Ver2.ps1
              ScriptArguments: >-
                -armTemplate "$(Pipeline.Workspace)/adf-arm/ARMTemplateForFactory.json"
                -ResourceGroupName rg-rdp-prod -DataFactoryName adf-rdp-prod
                -predeployment $true -deleteDeployment $false
              azurePowerShellVersion: LatestVersion
          - task: AzureResourceManagerTemplateDeployment@3
            displayName: Deploy ARM template
            inputs:
              deploymentScope: Resource Group
              azureResourceManagerConnection: sc-rdp-prod
              action: Create Or Update Resource Group
              resourceGroupName: rg-rdp-prod
              location: Central India
              templateLocation: Linked artifact
              csmFile: $(Pipeline.Workspace)/adf-arm/ARMTemplateForFactory.json
              csmParametersFile: $(Pipeline.Workspace)/adf-arm/ARMTemplateParametersForFactory.json
              overrideParameters: >-
                -factoryName adf-rdp-prod
                -LS_ADLS_properties_typeProperties_url "https://strdpprod.dfs.core.windows.net/"
              deploymentMode: Incremental
          - task: AzurePowerShell@5
            displayName: Start triggers & clean up (post-deployment)
            inputs:
              azureSubscription: sc-rdp-prod
              ScriptPath: $(Pipeline.Workspace)/adf-arm/PrePostDeploymentScript.Ver2.ps1
              ScriptArguments: >-
                -armTemplate "$(Pipeline.Workspace)/adf-arm/ARMTemplateForFactory.json"
                -ResourceGroupName rg-rdp-prod -DataFactoryName adf-rdp-prod
                -predeployment $false -deleteDeployment $true
              azurePowerShellVersion: LatestVersion

Note The pre/post-deployment PowerShell script is published in Microsoft's ADF CI/CD documentation (and can be exported along with the ARM template by the npm package). It stops active triggers before deployment, restarts them afterwards, and removes resources deleted from the source.

14.3 GitHub Actions alternative

Use actions/setup-node, run the same npm commands, then azure/arm-deploy@v2 (with azure/login OIDC) and azure/powershell@v2 for the trigger script — or the community/Microsoft ADF deploy actions.

Development vs Test vs Production Environments

Source S40 · 15. Development vs Test vs Production Environments
Aspect Development Test / UAT Production
Factory adf-rdp-dev adf-rdp-test adf-rdp-prod
Git connected Yes No No
Who changes it Developers via ADF Studio branches + publish/CI CI/CD pipeline only CI/CD pipeline only, with approvals
Data sources Dev storage, Dev SQL Test copies Production
Linked services Dev Key Vault, Dev URLs Overridden ARM parameters Overridden ARM parameters
Triggers Usually stopped or limited As needed for testing Active schedules
Integration runtimes Dev IRs (self-hosted IR shared/linked if needed) Test IRs Prod IRs (same IR names across environments)

Environment rules:

  • Same resource names across factories (only parameters differ).
  • Secrets in Azure Key Vault — linked services reference secrets; each environment has its own Key Vault, URL overridden by ARM parameter.
  • Use managed identity for ADF to access storage/SQL/Key Vault.
  • Keep self-hosted integration runtime names identical (or use linked IRs).

ADF Git Troubleshooting

Source S40 · 16. ADF Git Troubleshooting
Problem Cause Solution
Publish button disabled Not on the collaboration branch, or publish disabled Switch to main; use CI publishing
"Publish branch is out of sync" / stale adf_publish Manual edits or conflicts in publish branch Use Overwrite live mode carefully, or rebuild via npm package
Changes made in live mode not in Git Someone edited live (Git disconnected or live mode) Manage → Git configuration → Overwrite live mode (Git → live) or import live resources to a branch, then review
Missing resources after switching branch Branch doesn't contain them Merge from main; refresh
JSON merge conflict Two edits to same resource Resolve in VS Code, keep valid JSON, validate in ADF Studio
ARM deployment fails: trigger is active Triggers must be stopped to update Run pre-deployment script
ARM template size limit exceeded Large factory Use linked templates (generated automatically)
Linked service points to Dev in Prod Property not parameterised Add to arm-template-parameters-definition.json; override
Deleted pipeline still in Prod Incremental ARM deployment doesn't delete Post-deployment script with -deleteDeployment $true cleanup
Git config error: permission/authorisation Missing repo access or org approval of ADF GitHub app Grant access; approve OAuth app
Cross-tenant Azure DevOps sign-in issues Tenant mismatch Use Cross tenant sign in option or align tenants
33.34

Managing Multiple Developers

Source S40 · 17. Managing Multiple Developers
  1. One feature branch per developer per task; collaboration branch protected.
  2. Small, modular pipelines — parent/child pipelines, reusable datasets with parameters — so developers rarely edit the same JSON.
  3. Naming conventions (PL_, DS_, LS_, TR_, DF_) and folders in ADF Studio.
  4. Communicate ownership of shared linked services and global parameters (often owned by a lead).
  5. Sync frequently: merge main into feature branches (in Azure Repos/GitHub or locally) and refresh ADF Studio.
  6. PR reviews with build validation (npm validate).
  7. No manual publishing — CI generates ARM from main.
  8. Debug on feature branches; don't trigger production-like schedules from Dev.
  9. Document the process in the repo README.

Forgetting to stop triggers before deployment and start them after — use the PrePostDeploymentScript (Ver2) from Microsoft with -predeployment $true/$false.

Real-time scenarios

Source S34, S40 · Two developers edited the same pipeline JSON

ADF stores one pipeline per JSON file; parallel edits conflict at PR time. Resolve in the PR/IDE carefully (activities array), validate JSON, re-open the branch in ADF Studio and run Validate all. Prevention: split large pipelines (Execute Pipeline activity), one owner per pipeline per sprint.

Course addition · Someone published from ADF Studio and overwrote the CI deployment

Classic Publish and automated publish were both in use. Disable the publish button in Git configuration and restrict Data Factory Contributor rights in Test/Prod to the pipeline identity.

Best practices

Course addition · best practices
  • Only Dev is Git-connected; Test/Prod deployed by CI/CD from ARM templates.
  • Feature branch per change; PR + build validation (npm validate) before merge.
  • Automated publish with the npm package; disable manual publish.
  • Secrets only via Key Vault-linked services; managed identities for data stores.
  • Stop/start triggers around deployments; parameterize environment values; keep ARM template size under limits (linked templates).

Beginner
What is the collaboration branch in ADF?

The branch (usually main) that holds the integrated factory definition and from which publishing/ARM generation happens.

What does "Save" do in ADF Git mode?

Commits the changed resource JSON to the current Git branch.

Intermediate
What is adf_publish?

The default publish branch where classic Publish writes generated ARM templates for deployment.

Why connect only the Dev factory to Git?

Higher environments must be deployed reproducibly from reviewed artifacts; direct edits there cause drift.

Advanced
Explain automated publishing for ADF.

The @microsoft/azure-data-factory-utilities npm package validates resources and exports ARM templates from the collaboration branch in a build pipeline, removing the manual Publish step.

Why stop triggers before deploying?

Deploying active triggers can fail or cause runs during deployment; the pre/post-deployment script stops and restarts only affected triggers.

Scenario
Prod linked service points to the Dev Key Vault after deployment. What went wrong?

The Key Vault URL wasn't parameterized or overridden; expose it via arm-template-parameters-definition.json and pass the Prod value in the deployment parameters.
