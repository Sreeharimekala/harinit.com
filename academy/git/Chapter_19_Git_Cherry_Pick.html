Learning objectives

Chapter introduction

What it is. git cherry-pick applies the change introduced by existing commit(s) onto the current branch as new commit(s).

Why it matters. It lets you deliver a specific fix to another line (a release or hotfix branch) without merging everything else from the source branch.

Where it is used. Back-porting fixes to release branches, rescuing a commit from an abandoned branch, moving a commit made on the wrong branch.

In this course's project. Stage 5: a data-quality fix made on main is cherry-picked to release/1.0 for an urgent patch release.

19.1

What is Cherry-Pick?

Source S20 · Chapter manual · 1. What is Cherry-Pick?

Cherry-pick applies the change introduced by one or more existing commits onto the current branch. Git creates new commit(s) on the destination branch, so the resulting commit IDs differ from the originals. It copies changes, not the original branch ancestry.

Commands and example

git switch release/2.4
git cherry-pick a1b2c3d
19.2

Why use Cherry-Pick?

Source S20 · Chapter manual · 2. Why use Cherry-Pick?

Use cherry-pick when a specific fix is needed on another branch but the rest of the source branch is not ready. For example, a critical null-handling fix may need to go to a production maintenance branch while a larger feature remains under development.

Commands and example

# A fix is committed on develop
git switch release/2.4
git cherry-pick <fix-commit-sha>
19.3

Cherry-picking a single or multiple commits

Source S20 · Chapter manual · 3. Cherry-picking a single or multiple commits

A single SHA applies one commit. Multiple SHAs can be supplied in the desired order. Review dependencies: a commit may rely on schema changes or helper functions from earlier commits. Cherry-picking only the final dependent commit may fail to compile or behave correctly.

Commands and example

git cherry-pick a1b2c3d

# Apply selected commits in the specified order
git cherry-pick a1b2c3d d4e5f6a
19.4

Cherry-picking commit ranges

Source S20 · Chapter manual · 4. Cherry-picking commit ranges

A range such as A..B selects commits reachable from B but not A; it excludes A. Use A^..B when you intend to include A as well. Inspect the selected commits before applying the range, because range selection can include more commits than expected.

Commands and example

git log --oneline A..B
git cherry-pick A..B

# Include A itself
git cherry-pick A^..B
19.5

Resolving conflicts

Source S20 · Chapter manual · 5. Resolving conflicts

If the patch cannot be applied cleanly, Git pauses and reports conflicts. Inspect git status, edit files to the intended final state, stage the resolutions, and continue. Run tests after the operation; a conflict-free cherry-pick can still introduce a logical problem.

Commands and example

git cherry-pick <commit-sha>
git status
# Resolve conflict markers and validate the files
git add sql/customer_reconciliation.sql
git cherry-pick --continue
19.6

Aborting or continuing cherry-pick

Source S20 · Chapter manual · 6. Aborting or continuing cherry-pick

Use git cherry-pick --continue after resolving and staging conflicts. Use git cherry-pick --abort to cancel the operation and return to the pre-operation state. --skip omits the current commit; use it only when intentionally excluding that change.

Commands and example

git cherry-pick --continue
# Or cancel the in-progress operation:
git cherry-pick --abort

# Skip current commit only if its change is intentionally not required:
git cherry-pick --skip
19.7

Cherry-Pick vs Merge vs Rebase

Source S20 · Chapter manual · 7. Cherry-Pick vs Merge vs Rebase

Cherry-pick applies selected commit changes and creates new commits. Merge integrates branch histories and preserves ancestry. Rebase replays a series of commits onto a new base and rewrites those commits. Prefer merge when the complete branch history belongs together; cherry-pick for a targeted patch; rebase for updating/cleaning a private feature branch.

Commands and example

git merge feature/customer-dq
git rebase origin/main
git cherry-pick <one-specific-fix>
19.8

Real-time development use cases

Source S20 · Chapter manual · 8. Real-time development use cases

Typical uses include backporting a production fix to supported release branches, moving a small bug fix from development to a hotfix branch, and applying a carefully selected configuration correction. Avoid using cherry-pick as a routine substitute for a coherent merge strategy; repeated cherry-picks can create duplicate-looking commits and complicate history.

Commands and example

# Create a hotfix branch from the production release
git switch -c hotfix/late-order-null release/2.4

# Apply the approved fix from develop
git cherry-pick <fix-sha>

# Validate and publish the hotfix branch
pytest
git push -u origin hotfix/late-order-null
19.9

Practical safeguards

Source S20 · Chapter manual · 9. Practical safeguards

Before cherry-picking, confirm the commit SHA, inspect its patch and parent context, check dependencies, and confirm the destination branch. If the same change has already been applied, Git may report an empty cherry-pick or conflicts. Do not blindly resolve by accepting one side; understand the intended result.

Commands and example

git show --stat <commit-sha>
git show --format=fuller <commit-sha>
git switch release/2.4
git status
git cherry-pick <commit-sha>
git log --oneline -5

19.12

Cherry-Picking a Single Commit

Source S40 · 3. Cherry-Picking a Single Commit
git log main --oneline -5          # find the commit
# f00ba12 fix(sql): correct tax rounding

git switch release/2.4
git cherry-pick f00ba12

[release/2.4 7e6d5c4] fix(sql): correct tax rounding
 Date: Thu Nov 26 15:10:00 2026 +0530
 1 file changed, 2 insertions(+), 2 deletions(-)

Useful options:

git cherry-pick -x f00ba12     # append "(cherry picked from commit f00ba12...)" to the message — recommended for traceability
git cherry-pick -e f00ba12     # edit the message
git cherry-pick -n f00ba12     # apply changes without committing (--no-commit)
git cherry-pick -s f00ba12     # add Signed-off-by line
19.13

Cherry-Picking Multiple Commits

Source S40 · 4. Cherry-Picking Multiple Commits
git cherry-pick a1b2c3d e4f5a6b 9c8b7a6

Commits are applied in the order listed. Combine several into one commit:

git cherry-pick -n a1b2c3d e4f5a6b
git commit -m "Back-port orders fixes to release 2.4"
19.14

Cherry-Picking Commit Ranges

Source S40 · 5. Cherry-Picking Commit Ranges
git cherry-pick a1b2c3d..e4f5a6b      # commits AFTER a1b2c3d up to and including e4f5a6b
git cherry-pick a1b2c3d^..e4f5a6b     # INCLUDING a1b2c3d
git cherry-pick main~3..main          # last 3 commits of main

Note A..B excludes A. Use A^..B to include it.

19.15

Resolving Cherry-Pick Conflicts

Source S40 · 6. Resolving Cherry-Pick Conflicts

Conflicts happen when the target branch's code differs from the source context:

error: could not apply f00ba12... fix(sql): correct tax rounding
hint: After resolving the conflicts, mark them with "git add/rm <pathspec>", then run "git cherry-pick --continue".

git status
# edit conflicted files, remove markers
git add sql/procedures/usp_load_sales.sql
git cherry-pick --continue
19.16

Aborting Cherry-Pick

Source S40 · 7. Aborting Cherry-Pick
git cherry-pick --abort

Returns the branch to the state before the cherry-pick operation started (including multi-commit sequences).

To undo a completed cherry-pick: git reset --hard HEAD~1 (unpushed) or git revert HEAD (pushed).

19.17

Continuing Cherry-Pick

Source S40 · 8. Continuing Cherry-Pick
git cherry-pick --continue    # after resolving conflicts
git cherry-pick --skip        # skip the current commit in a sequence
git cherry-pick --quit        # stop, keeping commits already picked
19.18

Cherry-Pick vs Merge vs Rebase

Source S40 · 9. Cherry-Pick vs Merge vs Rebase
Aspect Cherry-pick Merge Rebase
Scope Selected commits Entire branch Entire branch
Creates New commits (copies) Merge commit (or fast-forward) New copies of all branch commits
History Duplicate changes with different IDs Preserves both histories Linear, rewritten
Risk Duplicates; later merges may conflict or double-apply Low Rewrites history
Best for Hotfix back-ports, rescuing commits Integrating features Updating/cleaning own branches

Tip Prefer merging when you want everything from a branch. Use cherry-pick for specific changes, and always use -x to record where they came from.

Check which commits are already applied (by content) to another branch:

git cherry -v release/2.4 main     # "+" = not yet in release/2.4, "-" = equivalent exists

Real-Time Development Use Cases

Source S40 · 10. Real-Time Development Use Cases

10.1 Back-port a production fix

main has a fix for incorrect sales tax rounding (f00ba12). Release 2.4 is in UAT and needs it:

git switch release/2.4
git pull
git cherry-pick -x f00ba12
git push

10.2 Commit on the wrong branch

git switch feature/orders
git cherry-pick 1a2b3c4           # commit accidentally made on main
git switch main
git reset --hard HEAD~1           # remove it from main (if not pushed)

10.3 Salvage from an abandoned branch

git log experiment/delta-tuning --oneline
git switch -c feature/partition-optimisation main
git cherry-pick -x 5d6e7f8        # only the useful optimisation commit

10.4 Hotfix to multiple supported versions

for b in release/2.3 release/2.4; do
  git switch "$b" && git cherry-pick -x f00ba12 && git push
done

Added topics, conflicts & verification

Patches: format-patch and am (S41)

S41 discusses creating and applying patches. Correct workflow: git format-patch -1 <sha> (or origin/main..HEAD) writes .patch files with author and message; the receiver applies them with git am *.patch (keeps authorship) or git apply file.patch (changes only, no commit). Check first with git apply --check file.patch. S41's answer ("fetch the patch with git fetch <remote> <branch>, then git apply <patch-file>") is incomplete: git fetch downloads commits, not a patch file. Either merge/cherry-pick the fetched commits, or create a file with git format-patch (or obtain one) and then apply it.

Command reference

git cherry-pick
Syntax
git cherry-pick [-x] [-n] [-m <parent>] <commit>…
git cherry-pick <A>^..<B>
git cherry-pick --continue | --skip | --quit | --abort
Purpose
Apply the changes of given commits as new commits on the current branch.
Key parameters
  • -x — append "(cherry picked from commit …)" to the message
  • -n / --no-commit — apply to index/working tree only
  • -m 1 — pick a merge commit relative to parent 1
  • --signoff — add Signed-off-by
  • A^..B — range including A
Expected output
[release/1.0 6d5c4b3] fix(dq): allow zero-amount promotional orders
 Date: Tue Nov 24 16:02:11 2026 +0530
 1 file changed, 2 insertions(+), 1 deletion(-)
Example
git switch release/1.0
git cherry-pick -x 8e7f6a5
git cherry-pick -x 1a2b3c4^..4d5e6f7     # several consecutive commits
Common mistakes
Cherry-picking many commits instead of merging a branch; picking a commit that depends on earlier unpicked commits.
git cherry / git log --cherry-pick
Syntax
git cherry -v <upstream> [<head>]
git log --oneline --cherry-pick --right-only <upstream>...<head>
Purpose
Find commits whose changes are not yet in another branch (compares patch IDs, so cherry-picked copies count as present).
Expected output
+ 8e7f6a5 fix(dq): allow zero-amount promotional orders
- 4c3b2a1 docs: update runbook
Example
git cherry -v release/1.0 main     # "+" = not yet in release/1.0, "-" = equivalent change already there
Common mistakes
Comparing commit IDs manually — cherry-picked commits have different IDs.

Real-time scenarios

Source S20, S40 · Commit made on the wrong branch

Meera committed an ADF change on main locally (not pushed). git switch feature/RDP-104-adf-orders-pipeline, git cherry-pick <sha>, then git switch main && git reset --hard origin/main.

Course addition · Cherry-pick results in an empty commit

The change already exists on the target (for example applied through another fix). Git reports that the cherry-pick is empty; use git cherry-pick --skip, or --allow-empty if you deliberately want the record.

Best practices

Course addition · best practices
  • Prefer merging branches; cherry-pick selected fixes only.
  • Use -x when back-porting from public branches.
  • Pick oldest first; check dependencies; test after picking.
  • Fix on main first, then back-port — avoids the fix being lost in the next release.
  • Use git cherry to verify what is missing.

Chapter 19 Interview Questions

Source S20 · Chapter manual · interview

1. What is cherry-pick?

It applies the change introduced by selected commit(s) onto the current branch.

2. Does cherry-pick preserve the original commit ID?

No. It creates a new commit with a different ID.

3. When is cherry-pick useful?

When a targeted fix is needed on another branch without merging all source-branch work.

4. How do you cherry-pick one commit?

Run git cherry-pick <sha>.

5. How do you cherry-pick multiple commits?

Provide multiple commit SHAs in the intended order.

6. What does A..B select?

Commits reachable from B but not A; A itself is excluded.

7. How do you include A in a range?

Use A^..B.

8. How do you inspect a commit before cherry-picking?

Use git show <sha>.

9. How do you continue after resolving conflicts?

Stage resolved files and run git cherry-pick --continue.

10. How do you cancel a cherry-pick?

Run git cherry-pick --abort.

11. What does cherry-pick --skip do?

It skips the current commit in an in-progress sequence.

12. How does cherry-pick differ from merge?

Cherry-pick applies selected changes; merge integrates branch histories.

13. How does cherry-pick differ from rebase?

Cherry-pick selects individual commits; rebase replays a branch's commit series onto a new base.

14. What is a backport?

Applying a fix from a newer development line to an older supported release line.

15. What risk comes from cherry-picking dependent commits?

The selected change may rely on code or schema changes that were not applied.

Beginner
What does git cherry-pick do?

Applies the changes of one or more existing commits onto the current branch as new commits.

How do you abort a cherry-pick with conflicts?

git cherry-pick --abort.

Intermediate
Why use -x?

It records the original commit ID in the new commit message for traceability.

Cherry-pick vs merge?

Merge integrates all commits of a branch; cherry-pick copies selected changes, creating new commits with new IDs.

Advanced
How does git cherry know a change was already applied if IDs differ?

It compares patch IDs (a hash of the diff), so equivalent changes are recognized.

Scenario
A hotfix is needed in v1.2 and v1.3 release branches and in main. Process?

Fix on main via PR (or a hotfix branch merged to main), then cherry-pick -x the fix into release/1.3 and release/1.2, test each, tag patch versions, deploy.
