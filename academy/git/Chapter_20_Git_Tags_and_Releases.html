20.1

What are Git Tags?

Source S21 · Chapter manual · 1. What are Git Tags?

A Git tag is a named reference to a specific commit, commonly used to mark releases such as v1.0.0. Unlike a branch, a tag is intended to identify a fixed point in history rather than move forward as new commits arrive. Tags are useful for release notes, deployment traceability and rollback investigation.

Commands and example

git tag
git log --oneline --decorate -10
git tag v1.0.0
20.2

Lightweight vs annotated tags

Source S21 · Chapter manual · 2. Lightweight vs annotated tags

A lightweight tag is essentially a named pointer to a commit. An annotated tag is a Git object containing a tagger, date, message and optionally a cryptographic signature. Annotated tags are generally preferred for formal releases because they carry release metadata.

Commands and example

# Lightweight
git tag v1.2.0

# Annotated
git tag -a v1.2.0 -m "Release version 1.2.0"

# Signed annotated tag (requires signing configuration)
git tag -s v1.2.0 -m "Signed release 1.2.0"
20.3

Creating and viewing tags

Source S21 · Chapter manual · 3. Creating and viewing tags

By default, a tag created without a commit argument points to the current HEAD. You can tag a specific historical commit by supplying its SHA. Use git show to inspect an annotated tag and the commit it identifies. Use patterns to list a release family.

Commands and example

git tag -a v2.1.0 -m "Production release 2.1.0"
git tag -a v2.0.1 <commit-sha> -m "Maintenance release 2.0.1"
git tag --list
git tag --list "v2.*"
git show v2.1.0
20.4

Deleting tags

Source S21 · Chapter manual · 4. Deleting tags

Delete a local tag with git tag -d. Deleting a local tag does not automatically delete a tag already pushed to a remote. To remove a remote tag, use the remote deletion syntax and coordinate with the team because consumers may already have fetched it.

Commands and example

git tag -d v2.0.1

# Delete a remote tag
git push origin --delete v2.0.1
20.5

Pushing and fetching tags

Source S21 · Chapter manual · 5. Pushing and fetching tags

A normal git push does not necessarily publish every local tag. Push one tag explicitly or use --tags to push all tags. Fetch tags from a remote with git fetch --tags. Be careful with bulk operations in repositories that contain many tags.

Commands and example

git push origin v2.1.0
git push origin --tags
git fetch origin --tags
git ls-remote --tags origin
20.6

Semantic versioning

Source S21 · Chapter manual · 6. Semantic versioning

Semantic Versioning uses MAJOR.MINOR.PATCH. Increase MAJOR for incompatible public changes, MINOR for backward-compatible functionality, and PATCH for backward-compatible bug fixes. Pre-release identifiers such as -rc.1 can identify release candidates. Teams should define what compatibility means for their data contracts, SQL interfaces and pipeline outputs.

Commands and example

v1.0.0   # first stable release
v1.1.0   # backward-compatible feature
v1.1.1   # backward-compatible fix
v2.0.0   # breaking change
v2.0.0-rc.1 # release candidate
20.7

Version management and release branches

Source S21 · Chapter manual · 7. Version management and release branches

A release process should define when a release branch is created, how fixes are backported, who approves release candidates, and how tags are created. Some teams release directly from the main branch; others maintain short-lived release branches for stabilization and patch support. Keep the branch strategy aligned with deployment environments and support policy.

Commands and example

git switch -c release/2.3
# Stabilize, test and approve release changes
git tag -a v2.3.0 -m "Release 2.3.0"
git push -u origin release/2.3
git push origin v2.3.0
20.8

Creating releases on GitHub

Source S21 · Chapter manual · 8. Creating releases on GitHub

A GitHub Release is a hosting-platform release record associated with a Git tag. It can include a title, release notes, links and downloadable assets. Creating a GitHub Release commonly creates or selects a tag, but the Git tag itself is the underlying source-control reference. Draft notes, review them, and publish only after approval.

Commands and example

# Create and push the tag locally first
git tag -a v2.4.0 -m "Release 2.4.0"
git push origin v2.4.0

# On GitHub:
# Repository → Releases → Draft a new release
# Choose tag v2.4.0, add title/notes/assets, then publish
20.9

Production deployment tagging

Source S21 · Chapter manual · 9. Production deployment tagging

A production tag should identify the exact source commit deployed. Create it only after required reviews, automated checks and release approval. Record environment, deployment time, build identifier and change reference in the release notes or deployment system. Never move an existing production tag to a different commit without an explicit, auditable correction process.

Commands and example

# Confirm the commit that was approved and deployed
git log -1 --oneline
git status

# Create an annotated deployment tag
git tag -a prod-2026.11.26 <approved-commit-sha> -m "Production deployment 2026-11-26"
git push origin prod-2026.11.26

# Verify the tag target
git show --no-patch prod-2026.11.26
20.10

Release traceability for Data Engineering

Source S21 · Chapter manual · 10. Release traceability for Data Engineering

For an ADF, Databricks, Fabric or SQL deployment, tag the repository commit that represents the deployed code and configuration. Keep environment-specific secrets outside Git. Link the release to pipeline run IDs, change tickets and validation evidence in the release record. A Git tag alone does not deploy anything; CI/CD automation or an approved deployment process performs the deployment.

Commands and example

# Example release evidence checklist
# - Git tag: v3.2.0
# - Commit SHA: recorded in deployment record
# - Change ticket: CHG-12345
# - CI build: build-9081
# - Target: Production
# - Validation: row counts, schema checks, pipeline health
git show v3.2.0

What are Git Tags?

A tag is a named, permanent reference to a specific commit, typically used to mark release points (v1.0.0). Unlike branches, tags do not move when new commits are added.

20.12

Lightweight Tags

Source S40 · 2. Lightweight Tags
  • Simply a name pointing to a commit — no extra metadata.
  • Stored as a file in .git/refs/tags/ containing the commit hash.
  • Good for private/temporary bookmarks.
git tag v1.0.0-local
git tag before-refactor a1b2c3d
git cat-file -t v1.0.0-local      # commit
20.13

Annotated Tags

Source S40 · 3. Annotated Tags
  • Stored as a full tag object in the Git database with tagger name, email, date, message and optional signature.
  • Recommended for releases.
  • git describe uses annotated tags by default.
git tag -a v1.0.0 -m "Release 1.0.0: customer and orders loads"
git cat-file -t v1.0.0            # tag
git cat-file -p v1.0.0

object 9c8b7a6d...
type commit
tag v1.0.0
tagger Ravi Kumar <ravi.kumar@company.com> 1795002012 +0530

Release 1.0.0: customer and orders loads

Signed tags:

git tag -s v1.0.0 -m "Signed release 1.0.0"     # GPG or SSH signing (Chapter 23)
git tag -v v1.0.0                               # verify
Lightweight Annotated
Metadata None Tagger, date, message, signature
Git object No (just a ref) Yes (tag object)
Use Temporary/private Public releases
20.14

Creating Tags

Source S40 · 4. Creating Tags
git tag -a v1.0.0 -m "Release 1.0.0"            # tag current commit (HEAD)
git tag -a v0.9.0 a1b2c3d -m "Retro-tag 0.9.0"  # tag an older commit
git tag -a v1.0.0 -F release-notes.md           # message from a file
git tag -f -a v1.0.0 -m "..."                   # move/replace an existing tag locally (avoid for published tags)
20.15

Viewing Tags

Source S40 · 5. Viewing Tags
git tag                      # list all (alphabetical)
git tag -l "v1.*"            # filter
git tag --sort=-v:refname    # sort by version, newest first
git tag -n                   # show first line of annotation
git show v1.0.0              # tag details + commit + diff
git describe --tags          # nearest tag, e.g. v1.0.0-3-g9c8b7a6 (3 commits after v1.0.0)
git log --oneline --decorate # tags shown next to commits
git ls-remote --tags origin  # tags on the remote
20.16

Deleting Tags

Source S40 · 6. Deleting Tags
git tag -d v1.0.0-rc1                 # delete locally
git push origin --delete v1.0.0-rc1   # delete on remote
git push origin :refs/tags/v1.0.0-rc1 # older syntax

Warning Avoid deleting or moving tags that others have fetched or that were deployed — it breaks traceability. Create a new version instead (v1.0.1). On GitHub, protect tags with rulesets.

20.17

Pushing Tags

Source S40 · 7. Pushing Tags

git push does not push tags by default.

git push origin v1.0.0            # one tag
git push origin --tags            # all local tags (lightweight and annotated)
git push --follow-tags            # push commits + annotated tags reachable from them (recommended)
git config --global push.followTags true
20.18

Fetching Tags

Source S40 · 8. Fetching Tags
git fetch --tags                  # fetch all tags
git fetch origin tag v1.0.0       # one tag
git pull --tags
git switch --detach v1.0.0        # check out code at a tag (detached HEAD)
git switch -c hotfix/1.0.1 v1.0.0 # branch from a tag

git fetch normally fetches tags that point to fetched commits automatically.

20.19

Semantic Versioning

Source S40 · 9. Semantic Versioning

9.1 Format

MAJOR.MINOR.PATCH[-PRERELEASE][+BUILD]
   2  .  5  .  1   -rc.1        +20261126
Part Increment when Example
MAJOR Incompatible/breaking change (dropped column, changed API, renamed table) 1.9.3 → 2.0.0
MINOR Backward-compatible new functionality (new table, new pipeline) 2.4.3 → 2.5.0
PATCH Backward-compatible bug fix 2.5.0 → 2.5.1
Pre-release Not yet stable 2.6.0-alpha.1, 2.6.0-beta.2, 2.6.0-rc.1
Build metadata Build info (ignored for precedence) +build.45

9.2 Rules

  • Start at 0.1.0 for initial development; 1.0.0 = first stable release.
  • Reset lower numbers when incrementing: 1.4.7 → 2.0.0, 1.4.7 → 1.5.0.
  • Precedence: 1.0.0-alpha < 1.0.0-beta < 1.0.0-rc.1 < 1.0.0.
  • Tag names conventionally prefix with v: v2.5.1.

9.3 Data Engineering examples

Change Version bump
Add region column (nullable) to dim_customer MINOR
Rename cust_id to customer_id in a published view MAJOR
Fix wrong join in usp_load_sales PATCH
New orders pipeline MINOR

Version Management

Source S40 · 10. Version Management

10.1 Where the version lives

Project type File
Python package pyproject.toml (version = "2.5.0")
Generic VERSION file
SQL project .sqlproj DacVersion
Databricks bundle Wheel version / bundle variables
Changelog CHANGELOG.md

10.2 Practices

  • Single source of truth for the version.
  • Bump the version in a commit (chore(release): 2.5.0) before tagging.
  • Maintain CHANGELOG.md (Keep a Changelog format) or generate it from Conventional Commits.
  • Automate with tools like semantic-release, release-please or GitVersion (derive version from Git history/tags).
  • Use git describe --tags to embed the version in builds:
VERSION=$(git describe --tags --always)
echo $VERSION      # v2.5.0-4-g1a2b3c4

Creating Releases on GitHub

Source S40 · 11. Creating Releases on GitHub
  1. Releases → Draft a new release.
  2. Choose a tag (existing or new; pick target branch).
  3. Title, Generate release notes, edit as needed.
  4. Attach assets (e.g. rdp_etl-2.5.0-py3-none-any.whl, RetailDW.dacpac, ADF ARM templates).
  5. Mark as pre-release or latest.
  6. Publish.

CLI and automation:

gh release create v2.5.0 --title "v2.5.0" --generate-notes dist/*.whl

# .github/workflows/release.yml
on:
  push:
    tags: ['v*.*.*']
permissions:
  contents: write
jobs:
  release:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - run: gh release create "$GITHUB_REF_NAME" --generate-notes
        env:
          GH_TOKEN: ${{ github.token }}
20.22

Release Branches

Source S40 · 12. Release Branches

12.1 Purpose

A release branch (release/2.5) isolates a version for stabilisation and long-term maintenance while development continues on main/develop.

12.2 Flow

main/develop  ●──●──●──●──●──●──●──►
                    \
release/2.5          ●──●(v2.5.0)──●(v2.5.1)──►   (fixes only; tags for each release)

git switch -c release/2.5 main
# stabilisation fixes...
git tag -a v2.5.0 -m "Release 2.5.0"
git push origin release/2.5 --follow-tags

# later, patch
git cherry-pick -x <fix-from-main>
git tag -a v2.5.1 -m "Patch 2.5.1"
git push origin release/2.5 --follow-tags

Merge release fixes back into main/develop (or cherry-pick) so they aren't lost.

20.23

Production Deployment Tagging

Source S40 · 13. Production Deployment Tagging

13.1 Why tag deployments

  • Exact answer to "What code is running in production?"
  • Easy rollback: redeploy the previous tag.
  • Audit trail: who released what and when.
  • Release notes generated between tags.

13.2 Patterns

Pattern Example
Release version tags v2.5.0 triggers the production pipeline
Environment deployment tags prod-2026-11-26-01 created by the pipeline after a successful deploy
Build number tags build-1452

13.3 Tag-triggered deployment

# GitHub Actions
on:
  push:
    tags: ['v*.*.*']
jobs:
  deploy-prod:
    runs-on: ubuntu-latest
    environment: prod
    steps:
      - uses: actions/checkout@v4
      - run: echo "Deploying ${GITHUB_REF_NAME} to production"

# Azure Pipelines
trigger:
  tags:
    include: ['v*']

13.4 Rollback

git switch --detach v2.4.3       # inspect previous release
# re-run the deployment pipeline for tag v2.4.3

13.5 Protect tags

GitHub Rulesets → Tag rules: restrict creation/deletion/updates of v* tags to release managers.

Real-time scenarios

Source S21, S40 · Which code is running in production?

The deployment record shows v1.0.1. git show v1.0.1 --stat and git log v1.0.0..v1.0.1 --oneline show exactly what changed; git diff v1.0.0 v1.0.1 -- sql/ limits to SQL.

Course addition · A tag was created on the wrong commit and already pushed

Preferred: create a new version tag (e.g. v1.0.2). If you must move it (and nobody deployed it): delete remotely and locally, recreate, push, and tell everyone to git fetch --tags --force. Never silently move release tags.

Best practices

Course addition · best practices
  • Annotated (ideally signed) tags for releases; v prefix + SemVer.
  • Tag only tested commits on main/release branches; deploy production from tags.
  • Protect release tags with rulesets; never re-use or move published tags.
  • Generate release notes from PR titles — write good PR titles.
  • Push tags explicitly or enable push.followTags.

Use git tag -d <tag>.

Use git push origin <tag>.

11. How do you fetch tags?

Use git fetch --tags.

12. What does MAJOR mean in SemVer?

An incompatible change to the public interface or compatibility contract.

13. What does MINOR mean?

A backward-compatible addition of functionality.

14. What does PATCH mean?

A backward-compatible bug fix.

15. Does creating a tag deploy software?

No. A tag identifies a commit; a deployment pipeline or process performs deployment.

1. Which command creates an annotated tag?

  1. git tag v1
  2. git tag -a v1 -m "msg"
  3. git branch -t v1
  4. git release v1
-a (or -s) creates a tag object.

2. What does git push origin --delete v1.0.0 do?

  1. Deletes the local tag
  2. Deletes the tag on the remote
  3. Deletes the release assets only
  4. Deletes the commit
Delete locally with git tag -d.

3. In SemVer, a backward-compatible new feature increments…

  1. MAJOR
  2. MINOR
  3. PATCH
  4. Build metadata
Features → minor.

4. v1.4.0-3-g9c8d7e6 from git describe means…

  1. Version 1.4.0.3
  2. 3 commits after tag v1.4.0, at commit 9c8d7e6
  3. 3 tags after v1.4.0
  4. Pre-release 3
The g prefixes the abbreviated object name.

5. What does a successful git tag -a v1.0 -m "x" print?

  1. Tag 'v1.0' created
  2. Nothing
  3. Created tag v1.0 at HEAD
  4. [new tag] v1.0

Summary & completion checklist

Key takeaways
  • Tags name commits permanently; use annotated (signed) tags for releases.
  • Tags must be pushed explicitly; protect and never move published release tags.
  • SemVer communicates impact; releases add notes and assets.
  • Deploy and roll back by tag for full traceability.
Source S21 · Chapter manual · summary
  • Explain lightweight and annotated tags
  • Create, inspect, delete, push and fetch tags
  • Apply semantic versioning consistently
  • Understand GitHub releases and release branches
  • Tag production deployments in a traceable way
Safety reminder: Before rewriting or discarding history, check whether commits are shared, inspect the working tree, and preserve important work. Prefer reversible, auditable operations on shared branches.
