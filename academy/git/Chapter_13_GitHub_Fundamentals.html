13.1

What is GitHub?

Source S14 · Chapter manual · 1. What is GitHub?

GitHub is an online platform for hosting Git repositories and coordinating software development. Git performs version control; GitHub provides a web interface and collaboration services around repositories.

Git

Tracks snapshots, branches, commits and merges in a distributed repository.

GitHub

Hosts repositories and adds pull requests, issues, reviews, permissions, Actions and project planning.

Common uses

  • Store application source code, SQL scripts, Python packages and infrastructure definitions.
  • Review changes before merging them into protected branches.
  • Track bugs, enhancements and technical work through Issues.
  • Automate tests and deployments with GitHub Actions.
  • Publish release notes, packages and project documentation.

Official website: GitHub. Documentation: GitHub Docs.

13.2

GitHub architecture and concepts

Source S14 · Chapter manual · 2. GitHub architecture and concepts

GitHub is a hosted service that stores Git repositories and exposes collaboration features. A developer normally edits files in a local clone and synchronizes commits with a hosted repository.

Developer workstation
Working tree + local Git
↔
GitHub repository
Branches + commits
→
Collaboration layer
PRs · Issues · Reviews
→
Automation
Actions · Checks · Releases

Conceptual view: Git stores repository history; GitHub adds hosted collaboration and automation services.

Important objects and terms

  • Account: a user identity on GitHub.
  • Organization: a shared account space for teams and repositories.
  • Repository: project files and Git history, with GitHub settings and collaboration features.
  • Branch: a line of development within a repository.
  • Commit: a recorded snapshot and metadata.
  • Pull request: a proposal to merge changes between branches or repositories.
  • Issue: a tracked task, bug, question or enhancement.
  • Actions workflow: automation triggered by repository events or schedules.
GitHub is not a replacement for Git. Local Git commands still create commits and manage local history; push and fetch exchange commits with the hosted repository.
13.3

GitHub account management

Source S14 · Chapter manual · 3. GitHub account management

Create or access an account using the official GitHub sign-up page. For work, follow your employer's account, SSO and organization policies.

Account security checklist

  • Use a unique, strong password and a password manager.
  • Enable multi-factor authentication (MFA) using an approved method.
  • Keep recovery codes in a secure location separate from the account.
  • Review active sessions and authorized applications periodically.
  • Use SSH keys or a credential manager rather than storing passwords in scripts.
  • Keep personal and employer identities separate when policy requires it.

Profile and settings

Profile settings commonly include display name, avatar, public profile details, email visibility, notification preferences, authentication, SSH/GPG keys, applications and account security. Available settings may vary by account type and organizational policy.

Never publish personal contact information or secrets in a public profile or repository unless you deliberately intend them to be public.

Reference: GitHub account and profile documentation.

13.5

Creating a repository

Source S14 · Chapter manual · 5. Creating a repository

A repository is the home for project files and Git history. Create a repository from the GitHub dashboard or the new repository page.

  1. Select the owner: your account or an organization where you have permission.
  2. Enter a concise repository name, such as data-engineering-practice.
  3. Add a short description that explains the project's purpose.
  4. Select Public or Private visibility according to the data and organization policy.
  5. Optionally initialize with a README, .gitignore template and license.
  6. Create the repository and copy its clone URL if you will work locally.

Suggested starter layout

data-engineering-practice/ ├── README.md ├── .gitignore ├── sql/ │ ├── staging/ │ └── warehouse/ ├── python/ ├── notebooks/ ├── pipelines/ └── docs/

Choose a repository name that remains useful as the project grows. Avoid embedding confidential project, customer or environment details in a public repository name or description.

13.6

Repository settings

Source S14 · Chapter manual · 6. Repository settings

Repository settings control how a repository is presented, accessed and governed. You generally need administrator or appropriate repository permissions to change many settings.

Setting areaTypical controls
GeneralName, description, website, features, default branch, archive or transfer options.
AccessCollaborators, teams and permission levels.
BranchesDefault branch and branch protection/rulesets.
ActionsWorkflow permissions, runners and allowed actions.
SecuritySecurity features and analysis settings, where available.
Webhooks / integrationsConnections to external systems and event notifications.

Recommended baseline

  • Set a meaningful description and default branch.
  • Protect important branches with pull-request and status-check rules.
  • Grant least-privilege access.
  • Enable suitable security features and secret scanning where available.
  • Review Actions permissions and third-party integrations.
  • Define how the repository is archived, transferred or retired.
Do not change company repository settings without authorization. Organization policies may override or restrict repository-level options.

Reference: Repository branches and merge configuration.

13.7

README files

Source S14 · Chapter manual · 7. README files

A README.md is commonly the first document a visitor sees in a repository. It explains what the project does and how someone can use, test or contribute to it.

Recommended README structure

  1. Project title and concise purpose.
  2. Overview and business or technical context.
  3. Architecture or workflow diagram, if useful.
  4. Prerequisites and supported versions.
  5. Installation or setup instructions.
  6. Configuration instructions without secrets.
  7. How to run, test and validate.
  8. Folder structure and important components.
  9. Contribution guidelines and support contacts, if appropriate.
  10. License and release information.

Example README for a data project

# Retail Data Engineering A learning project for ingesting retail source data and transforming it into a reporting warehouse. ## Components - SQL transformations - Python validation utilities - Pipeline configuration - Data quality tests ## Prerequisites - Git - Python (supported project version) - SQL development environment ## Setup 1. Clone the repository. 2. Create a local virtual environment. 3. Install approved dependencies. 4. Configure local connection settings securely. ## Validation Run the unit tests and SQL validation scripts before submitting a pull request. ## Security Never commit credentials, production extracts or secrets.

A README should be accurate and maintained. Avoid documenting passwords, private endpoints or production connection strings.

13.9

Repository descriptions

Source S14 · Chapter manual · 9. Repository descriptions

A repository description is a short summary shown in repository listings and search results. It should quickly tell a reader what the project is and why it exists.

Good description checklist

  • State the main purpose in one sentence.
  • Use recognizable technical terms where relevant.
  • Avoid vague text such as “my files” or “project code”.
  • Do not include confidential names, URLs or operational details.
  • Keep it consistent with the README.

Example: “SQL and Python utilities for learning retail data ingestion, validation and warehouse transformations.”

13.10

Repository visibility

Source S14 · Chapter manual · 10. Repository visibility

Repository visibility determines who can view repository content. The exact options and organization restrictions depend on the account and hosting configuration.

VisibilityWho can view?Typical use
PublicAnyone on the internet.Open-source software, public examples and learning projects.
PrivateOnly authorized users and teams.Company source code, internal projects and restricted work.
InternalAvailable to members of an enterprise, where supported and enabled.Sharing across an organization without making content public.
Before changing visibility: check for secrets, customer information, proprietary SQL, internal URLs, data extracts and intellectual-property restrictions. A visibility change can expose the entire repository history, not just the latest files.

Public visibility does not grant everyone write access. Read access and write permissions are separate controls.

13.11

Repository topics

Source S14 · Chapter manual · 11. Repository topics

Topics are short tags that describe a repository and help users discover related projects. Examples include python, sql, data-engineering, azure, databricks and etl.

Topic selection guidelines

  • Choose a small number of accurate topics.
  • Prefer established terms used by the community.
  • Include the primary language, platform and project domain.
  • Remove topics that no longer describe the project.
  • Do not use unrelated trending topics to attract traffic.

Topics improve discoverability; they do not change Git behavior or grant permissions.

13.12

Repository collaborators and permissions

Source S14 · Chapter manual · 12. Repository collaborators and permissions

Collaborators are people who have been granted access to work on a repository. In an organization, access is often managed through teams rather than individual invitations.

Permission conceptTypical ability
ReadView and clone repository content.
TriageManage issues and pull requests without code write access.
WritePush branches and contribute changes.
MaintainManage repository activities without all administrative powers.
AdminManage repository settings and access.

Exact permission names and available roles may vary by repository type and plan. Grant only the access needed for a person's responsibilities, review access periodically and remove access when it is no longer required.

Reference: Managing people with repository access.

13.13

GitHub notifications

Source S14 · Chapter manual · 13. GitHub notifications

Notifications help users follow events such as pull-request reviews, issue mentions, discussions and repository activity. Users can receive notifications in the GitHub web interface, email or supported integrations.

Common notification reasons

  • You were assigned an issue or pull request.
  • You were requested as a reviewer.
  • Someone mentioned your username.
  • You are participating in a discussion or conversation.
  • You are watching a repository or selected activity.

Managing notification volume

  • Use Watch settings to select the activity you want to follow.
  • Use the notification inbox to mark items read, save them or filter them.
  • Unsubscribe from conversations that no longer require your attention.
  • Configure email and web notifications according to your role.
  • Use mentions and review requests intentionally.

Reference: Managing subscriptions and notifications.

13.14

GitHub search

Source S14 · Chapter manual · 14. GitHub search

GitHub search can find repositories, code, issues, pull requests, users, commits and documentation. Search results are subject to permissions and the indexing behavior of the selected search type.

Examples of search qualifiers

# Repositories by language language:python data-engineering # Repositories by topic topic:databricks topic:sql # Issues in a repository repo:OWNER/REPO is:issue is:open # Pull requests assigned to you is:pr is:open assignee:@me # Issues labelled as bugs is:issue label:bug is:open # Search code for a term in a repository repo:OWNER/REPO "CREATE TABLE"

Search qualifiers narrow the result set. Replace OWNER/REPO with the actual repository identifier. Code search syntax and availability can evolve; consult the official search syntax documentation.

Reference: Searching on GitHub.

13.15

GitHub releases

Source S14 · Chapter manual · 15. GitHub releases

A GitHub Release packages a named version of a project around a Git tag. A release can include release notes, downloadable assets and links to source code for that tag.

Tag vs release

Git tagGitHub Release
A Git reference marking a specific commit.A GitHub publishing layer associated with a tag.
Can be created locally and pushed.Created and managed through GitHub or supported tooling.
Identifies a version in repository history.Can add notes, assets and a published release page.

Typical release workflow

# Create an annotated tag for a validated version git switch main git pull --ff-only git tag -a v1.0.0 -m "Release version 1.0.0" # Publish the tag git push origin v1.0.0

After pushing a tag, create a GitHub Release for that tag, write user-focused release notes, list breaking changes and attach approved build artifacts if needed.

Do not publish database exports, credentials, internal configuration or restricted deployment artifacts as release assets.

Reference: Releasing projects on GitHub.

README Files

Source S40 · 7. README Files

7.1 Purpose

README.md is the front page of a repository — GitHub renders it under the file list. It tells people what the project is and how to use it.

7.2 What a good README contains

  1. Project name and one-line description
  2. Architecture overview (diagram)
  3. Folder structure
  4. Prerequisites
  5. Setup / installation steps
  6. How to run and test
  7. Deployment / CI/CD notes
  8. Configuration and environments
  9. Contributing guidelines link
  10. Owners / contacts, licence

7.3 Example

# Retail Data Platform

Batch pipelines that load retail sales data into the enterprise data warehouse.

## Architecture
Source systems → ADF (ingestion) → ADLS (bronze) → Databricks (silver/gold) → Synapse/Fabric → Power BI

## Repository structure
| Folder | Contents |
|---|---|
| `sql/` | Warehouse tables, views, procedures |
| `python/` | ETL modules and tests |
| `adf/` | Data Factory pipelines |
| `databricks/` | Notebooks and bundle config |

## Getting started
1. Clone: `git clone https://github.com/company/retail-data-platform.git`
2. Create a virtual environment: `python -m venv .venv`
3. Install: `pip install -r python/requirements.txt`
4. Test: `pytest python/tests`

## Contributing
See [CONTRIBUTING.md](CONTRIBUTING.md).

Other special files GitHub recognises: CONTRIBUTING.md, CODE_OF_CONDUCT.md, SECURITY.md, LICENSE, CODEOWNERS, SUPPORT.md, .github/pull_request_template.md, .github/ISSUE_TEMPLATE/.

13.30

GitHub Releases

Source S40 · 15. GitHub Releases

15.1 Definition

A release is a GitHub object built on a Git tag that packages a version of your project with release notes and optional downloadable assets (wheels, zip files, DACPACs, ARM templates).

15.2 Create a release (web)

  1. Repository → Releases → Draft a new release.
  2. Choose a tag — existing (v1.0.0) or create new on publish (select target branch/commit).
  3. Release title (e.g. v1.0.0 – Customer and Orders loads).
  4. Click Generate release notes (lists merged PRs and contributors since the previous release).
  5. Attach binaries (drag and drop).
  6. Tick Set as a pre-release or Set as the latest release.
  7. Publish release (or Save draft).

15.3 Using GitHub CLI

gh release create v1.0.0 --title "v1.0.0" --generate-notes
gh release create v1.1.0 dist/rdp_etl-1.1.0-py3-none-any.whl --notes-file CHANGELOG.md
gh release list

Syntax

gh release create <tag> [--notes "<text>"] [--prerelease] [files…]
Purpose
Do common GitHub tasks from the terminal (also usable in Actions with GITHUB_TOKEN).

Running gh against the wrong repository — it uses the current folder's remote unless you pass -R owner/repo.

Best practices

Course addition · best practices
  • Organization-owned repositories, team-based access, least privilege.
  • README with purpose, layout, setup, contribution and contacts; keep docs next to code.
  • Use topics and description for discoverability.
  • Enable automatic head-branch deletion and choose allowed merge methods deliberately.
  • Use releases (with generated notes) for every production version.

Chapter 13 Interview Questions

Source S14 · Chapter manual · interview
1. What is GitHub?

A platform for hosting Git repositories and collaborating through pull requests, issues, reviews, automation and project tools.

2. Difference between Git and GitHub?

Git is distributed version control; GitHub is a hosting and collaboration platform built around Git.

3. What is a GitHub repository?

A hosted project space containing files, Git history and collaboration settings.

4. What is the dashboard?

The signed-in starting area for navigating repositories, issues, pull requests, projects and activity.

5. What is repository visibility?

A control that determines who can view repository contents, such as public or private; internal visibility is available in some enterprise contexts.

6. What is README.md?

A Markdown document that explains a repository's purpose, setup, usage and contribution process.

7. What is Markdown?

A lightweight text syntax that GitHub renders into formatted content.

8. What are repository topics?

Tags that describe a repository and improve discovery.

9. What are collaborators?

Users or teams granted access to a repository.

10. What is least privilege?

Granting only the minimum access required for a person's role.

11. What is the difference between a tag and a release?

A tag marks a commit; a GitHub Release adds a published release page and optional notes and assets around a tag.

12. What are GitHub notifications?

Updates about activity such as mentions, assignments, review requests and watched repositories.

13. What is a search qualifier?

A filter such as repo:, language:, is:issue or label: that narrows search results.

14. Can public repositories be pushed to by everyone?

No. Public read visibility is separate from write permission.

15. What should be checked before making a repository public?

Secrets, proprietary code, sensitive data, internal URLs, history and organizational policy.

What is the purpose of a README file?

To explain what the project is, how to install/run it and how to contribute; GitHub renders it on the repository page.

What are repository topics?

Keywords that classify a repository and make it discoverable in search.

Intermediate
Which GitHub role lets someone manage issues and PRs but not push code?

Triage.

What is the difference between a tag and a GitHub release?

A tag is a Git ref to a commit; a release is a GitHub object built on a tag with notes, assets and a page.

Scenario
How would you structure access for a 30-person data department on GitHub?

One organization; teams per function (engineers, leads, analysts, platform) with Write/Maintain/Read; CODEOWNERS per folder; rulesets on main; SSO enforced; no individual collaborator grants except external contractors with expiry.
