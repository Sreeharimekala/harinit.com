Learning objectives

Chapter introduction

What it is. The synchronization commands — fetch, pull, push — and the remote-tracking branches (origin/main) that record what the remote looked like at your last fetch.

Why it matters. Misunderstanding pull vs fetch, or forcing a push, is the most common cause of lost or duplicated work in teams.

Where it is used. Many times a day by every developer; in CI pipelines; in IDE "Sync" buttons.

In this course's project. Stage 4: the team adopts fetch + review + pull --ff-only/--rebase on feature branches, and push --force-with-lease only on personal feature branches after a rebase.

12.1

Remote repositories recap

Source S13 · Chapter manual · 1. Remote repositories recap

A remote repository is another copy of a Git repository, commonly hosted on GitHub, GitLab, Bitbucket or an internal Git server. Your local repository can communicate with one or more remotes.

Git assigns a short name to each remote URL. The conventional name origin is commonly assigned to the repository from which you cloned, but it is only a name—not a special Git keyword.

# List configured remotes git remote # Show remote names and their URLs git remote -v # Add a remote git remote add origin https://github.com/your-org/data-platform.git # Remove a remote configuration git remote remove origin
Important: git remote remove origin removes the remote configuration from your local repository. It does not delete the hosted repository or its branches.
12.2

What is a remote-tracking branch?

Source S13 · Chapter manual · 2. What is a remote-tracking branch?

A remote-tracking branch is a local reference that records the last known state of a branch from a remote. It is maintained by Git and normally updated when you fetch from that remote.

For example, origin/main means “the last fetched state of the main branch on the remote named origin.” It is stored locally under refs/remotes/origin/main.

The remote branch exists on the server. origin/main is your local record of its last fetched commit.

Do not confuse these: main is usually a local branch; origin/main is a remote-tracking branch. You normally commit on main, not directly on origin/main.
12.3

Branch naming and Git references

Source S13 · Chapter manual · 3. Branch naming and Git references

Git references (refs) are names that point to commits. The most common branch-related references are:

  • refs/heads/main — local branch named main.
  • refs/remotes/origin/main — remote-tracking branch for main on remote origin.
  • HEAD — indicates the currently checked-out commit or, commonly, the current local branch.
# List local branches git branch # List remote-tracking branches git branch -r # List local and remote-tracking branches git branch -a # Show full reference names git show-ref

Example output from git branch -a:

* main feature/customer-load remotes/origin/HEAD -> origin/main remotes/origin/main remotes/origin/develop remotes/origin/feature/customer-load

origin/HEAD is a symbolic reference that usually indicates the remote's default branch (here, origin/main). It is not the same as your local HEAD.

12.4

Upstream tracking relationship

Source S13 · Chapter manual · 4. Upstream tracking relationship

A local branch can be configured to track a remote-tracking branch. This association is often called its upstream branch. It gives Git a default source for pulling and a default destination for pushing in common workflows.

Local branch
main
upstream of
Remote-tracking branch
origin/main

The local main branch is configured to track origin/main.

# Show tracking relationship and ahead/behind status git branch -vv # Show upstream configured for current branch git rev-parse --abbrev-ref --symbolic-full-name @{upstream} # Set upstream for current branch git branch --set-upstream-to=origin/main main

Typical git branch -vv output:

* main a1b2c3d [origin/main: ahead 1] Add customer validation develop d4e5f6a [origin/develop] Update ingestion pipeline

Here, local main has one commit not yet present in origin/main. The tracking information is a comparison with the most recently fetched remote-tracking reference; fetch first if you need an up-to-date view.

Tracking a branch when creating it

# Create a local branch that tracks origin/develop git switch --track origin/develop # Equivalent explicit form git switch -c develop --track origin/develop

12.6

git fetch in detail

Source S13 · Chapter manual · 6. git fetch in detail

git fetch contacts a remote, downloads commits and objects that are missing locally, and updates the relevant remote-tracking references. It does not automatically change your checked-out files or merge changes into your current local branch.

# Fetch from the default remote git fetch # Fetch from a named remote git fetch origin # Fetch all configured remotes git fetch --all # Fetch and remove stale remote-tracking refs for branches deleted on remote git fetch --prune

Before and after fetch

Before fetch
origin/main
Commit A
fetch
After fetch
origin/main
Commit C

The remote-tracking reference advances from A to C. Your local main branch and working files remain unchanged by fetch alone.

After fetching, inspect the changes before integrating them:

git fetch origin git log --oneline --decorate --graph main..origin/main git diff main..origin/main git status -sb
Safe review pattern: Fetch first, inspect incoming commits and differences, then merge or rebase when appropriate. This is especially useful before updating production SQL or pipeline code.
12.7

git pull in detail

Source S13 · Chapter manual · 7. git pull in detail

git pull is a convenience command that performs a fetch and then integrates the fetched changes into the current branch. By default, the integration is usually a merge; options or configuration can make it rebase instead.

# Pull from the configured upstream git pull # Explicit remote and branch git pull origin main # Fetch and rebase local commits on top of upstream git pull --rebase # Only allow a fast-forward update git pull --ff-only
ModeBehaviorWhen useful
Default mergeFetches, then merges upstream into current branch.When merge commits are acceptable in your team's workflow.
--rebaseFetches, then replays local commits on top of upstream.When your team prefers a linear history.
--ff-onlyUpdates only if a fast-forward is possible; otherwise stops.When you want to avoid an automatic merge commit.
Remember: Pull changes your current branch and potentially your working tree. If you want to inspect incoming work first, use git fetch.
12.8

git push and tracking setup

Source S13 · Chapter manual · 8. git push and tracking setup

git push publishes local commits to a remote repository. It does not normally push every local branch automatically; the destination depends on the command, upstream configuration and push settings.

# Push local main to origin/main explicitly git push origin main # First push of a new branch and set its upstream git push -u origin feature/customer-load # Push the current branch to its configured upstream git push # Push all local branches (use intentionally) git push --all origin

The -u option (same as --set-upstream) configures the upstream relationship. After the first push, a plain git push and git pull can usually use that relationship.

Shared repository safety: Avoid git push --force on shared branches unless your team explicitly approves it. If rewriting history is necessary, understand the impact and prefer --force-with-lease where appropriate.

12.11

Understanding ahead, behind and diverged

Source S13 · Chapter manual · 11. Understanding ahead, behind and diverged

After fetching, Git can compare your local branch with its upstream branch.

  • Ahead 2: your local branch has two commits not present in its upstream.
  • Behind 3: the upstream has three commits not present in your local branch.
  • Ahead 2, behind 3: both sides have unique commits; the branches have diverged.
# Refresh remote-tracking references first git fetch # Show branch tracking and ahead/behind information git branch -vv # Compact status git status -sb # Commits on local branch but not upstream git log --oneline @{upstream}..HEAD # Commits on upstream but not local branch git log --oneline HEAD..@{upstream}
Ahead/behind counts are only as current as your last fetch. A stale remote-tracking branch can make the counts out of date.
12.12

Common problems and troubleshooting

Source S13 · Chapter manual · 12. Common problems and troubleshooting

Fatal: no upstream configured

Cause: The current local branch has no upstream branch configured.

git push -u origin feature/my-change # or configure an existing upstream git branch --set-upstream-to=origin/feature/my-change

Updates were rejected because the remote contains work

Cause: The remote branch has commits your local branch does not contain, so a non-fast-forward push would overwrite remote history.

git fetch origin git log --oneline --graph --decorate --all # Integrate using the team's preferred method: git pull --rebase # Resolve conflicts if needed, then: git push

Remote branch was deleted but still appears locally

git fetch --prune # Or prune one remote git remote prune origin

Wrong remote URL

git remote -v git remote set-url origin https://github.com/your-org/data-platform.git

Cannot find remote branch

git fetch origin git branch -r # Check exact spelling and remote name

Local branch tracks the wrong upstream

git branch --set-upstream-to=origin/main main git branch -vv
12.13

Best practices

Source S13 · Chapter manual · 14. Best practices
  • Run git fetch before comparing your branch with the remote.
  • Use git branch -vv to verify upstream configuration.
  • Use git push -u when publishing a new branch for the first time.
  • Prefer git pull --ff-only or an explicitly agreed merge/rebase policy so integration behavior is predictable.
  • Do not commit directly to protected production branches unless your team's process permits it.
  • Use git fetch --prune periodically to clean stale remote-tracking references.
  • Never store passwords, access tokens, connection strings or secrets in source control.
  • For shared SQL, ADF, Databricks or Fabric projects, coordinate branch updates and pull-request reviews before deployment.
12.14

What is Git Push?

Source S40 · 1. What is Git Push?

1.1 Definition

git push uploads local commits (and the objects they need) to a remote repository and updates the remote branch to point to your latest commit.

Local:   A ── B ── C ── D (main)              Remote before: A ── B (main)
git push origin main     ─────────────►        Remote after:  A ── B ── C ── D (main)

1.2 Rules

  • Only committed work is pushed.
  • By default, the remote must be able to fast-forward — otherwise the push is rejected.
  • You need write permission, and branch protection rules must allow it.
12.15

What is Git Pull?

Source S40 · 2. What is Git Pull?

2.1 Definition

git pull downloads commits from the remote and integrates them into your current branch. It is two commands in one:

git pull  =  git fetch  +  git merge  origin/<branch>     (default)
git pull --rebase  =  git fetch  +  git rebase  origin/<branch>

2.2 Effect

Your working directory and local branch are updated; conflicts may occur.

12.16

What is Git Fetch?

Source S40 · 3. What is Git Fetch?

3.1 Definition

git fetch downloads commits, branches and tags from the remote and updates your remote-tracking branches (origin/main), without modifying your local branches or working files.

3.2 Why fetch first?

You can review what changed before integrating:

git fetch
git log --oneline main..origin/main
git diff main origin/main -- sql/

Handling Rejected Pushes

Source S40 · 11. Handling Rejected Pushes

11.1 The error

To https://github.com/ravi/retail-data-platform.git
 ! [rejected]        main -> main (fetch first)
error: failed to push some refs to 'https://github.com/ravi/retail-data-platform.git'
hint: Updates were rejected because the remote contains work that you do not
hint: have locally. This is usually caused by another repository pushing to
hint: the same ref.

11.2 Cause

Someone pushed new commits to the remote branch after your last fetch. Your push would overwrite them, so Git refuses.

11.3 Fix

git pull --rebase          # replay your commits on top of the remote ones (clean history)
# or
git pull                   # merge remote into yours (creates a merge commit)
# resolve conflicts if any
git push

11.4 Other rejection reasons

Message Cause Fix
protected branch hook declined / GH006 Branch protection — direct push to main not allowed Push to a feature branch and open a PR
Permission denied / 403 No write access or wrong credentials Request access; fix credentials
pre-receive hook declined Server-side policy (e.g. secret detected, file too large) Remove the offending content
src refspec main does not match any No commits yet, or branch has another name Commit first; check git branch
File ... exceeds GitHub's file size limit of 100.00 MB Large file Remove from history, use Git LFS
12.25

Non-Fast-Forward Errors

Source S40 · 12. Non-Fast-Forward Errors

12.1 What it means

A push is non-fast-forward when the remote branch contains commits that are not ancestors of your local branch — your history and the remote's history have diverged.

Remote:  A ── B ── X
Local:   A ── B ── C

Updating the remote to C would lose X.

 ! [rejected]        main -> main (non-fast-forward)
hint: Updates were rejected because the tip of your current branch is behind
hint: its remote counterpart.

12.2 Common causes

  • A teammate pushed (X) while you committed (C).
  • You amended or rebased commits that were already pushed.

12.3 Solutions

Situation Solution
Teammate pushed new work git pull --rebase (or git pull) then git push
You rewrote your own feature branch git push --force-with-lease
You rewrote a shared branch by mistake Don't force; restore: git reset --hard origin/<branch> and redo changes properly
12.26

Resolving Remote Conflicts

Source S40 · 13. Resolving Remote Conflicts

When pulling produces conflicts:

With merge (git pull):

git pull
# CONFLICT (content): Merge conflict in sql/views/vw_sales.sql
# edit files, remove markers
git add sql/views/vw_sales.sql
git commit                 # completes the merge
git push

With rebase (git pull --rebase):

git pull --rebase
# CONFLICT ... could not apply c3d4e5f
# edit files
git add sql/views/vw_sales.sql
git rebase --continue      # repeat for each conflicting commit
git push
# give up instead:
git rebase --abort

Tip If you're unsure, git fetch first and inspect git diff HEAD origin/main to see what's coming before integrating.

12.27

Force Push and Its Risks

Source S40 · 14. Force Push and Its Risks

14.1 What it does

git push --force        # or: git push -f

Overwrites the remote branch with your local branch regardless of what's on the remote.

14.2 Risks

  • Deletes teammates' commits pushed since your last fetch.
  • Breaks other people's clones (their history no longer matches).
  • Bypasses review and can destroy audit history.
  • Can trigger incorrect deployments.

14.3 Legitimate uses

  • After git commit --amend or git rebase -i on your own feature branch.
  • Removing accidentally pushed secrets (combined with secret rotation).

14.4 Golden rules

  • Never force-push main, develop or release branches. Protect them with "Block force pushes".
  • Prefer --force-with-lease.
  • Tell your team if you must force-push a shared branch.
12.28

Safe Force Push Using --force-with-lease

Source S40 · 15. Safe Force Push Using --force-with-lease

15.1 How it works

--force-with-lease overwrites the remote branch only if it is still at the commit your origin/<branch> remote-tracking branch says it is. If someone else pushed in the meantime, the push is rejected instead of deleting their work.

git rebase -i main                    # rewrite your feature branch
git push --force-with-lease

 ! [rejected]        feature/orders -> feature/orders (stale info)

— meaning someone pushed new commits; fetch, integrate, then retry.

15.2 Even safer

git push --force-with-lease --force-if-includes

--force-if-includes (Git 2.30+) also verifies that the remote tip you are overwriting was actually incorporated into your local branch — protecting against background git fetch (e.g. by IDEs) updating origin/<branch> without you noticing.

git config --global alias.pushf "push --force-with-lease --force-if-includes"

15.3 Comparison

Option Overwrites teammate's new commits?
--force Yes — always
--force-with-lease No — rejects if remote moved since your last fetch
--force-with-lease --force-if-includes No — also safe against background fetches

Added topics, conflicts & verification

Source conflict — Default behaviour of `git pull`

S13, S38 and S41 describe git pull as "fetch + merge" by default (S13 also shows the --rebase and --ff-only modes). S40 describes the configurable behaviour. Resolution (verified against git-pull docs): pull fast-forwards when you are only behind; when branches have diverged you must choose via --rebase, --no-rebase, --ff-only or the pull.rebase/pull.ff settings — otherwise Git 2.33+ stops with an error. "fetch + merge" describes --no-rebase, not an unconditional default.

Multiple remotes and pushing everywhere (S38)

With several remotes (origin, azure), push explicitly: git push azure main. git fetch --all updates every remote. A remote can have several push URLs (git remote set-url --add --push origin <url>), but mirroring is usually better handled by a CI job.

hint: your next pull:

...

Example
git config --global pull.rebase true     # team choice for feature branches
git pull                                    # rebases local commits on origin/<branch>
git switch main && git pull --ff-only       # main never gets accidental merge commits
Common mistakes
Pulling with uncommitted changes that conflict; using --rebase on a branch others have based work on.

Real-time scenarios

Source S13, S40 · "fatal: Need to specify how to reconcile divergent branches"

The developer has local commits and the remote has new ones; no pull strategy is configured. Choose per policy: git pull --rebase on personal feature branches, --no-rebase if the team merges, --ff-only on main (then rebase/merge explicitly). Persist with git config pull.rebase true or pull.ff only.

Course addition · A force push erased a colleague's commit

Recovery: the colleague still has the commit locally (or in their reflog) — they push it again to a branch; or find it on the hosting platform's PR/activity view. Prevention: protect branches (block force pushes) and use --force-with-lease.

Best practices

Course addition · best practices
  • Fetch often; pull deliberately.
  • Configure a pull strategy explicitly (pull.rebase or pull.ff).
  • pull --ff-only on main; rebase only branches nobody else builds on.
  • Never --force shared branches; prefer --force-with-lease (and --force-if-includes).
  • Push small, frequent commits; delete merged remote branches.

Chapter 12 Interview Questions

Source S13 · Chapter manual · interview
1. What is a remote-tracking branch?

A local reference that records the last fetched state of a branch on a remote repository, such as origin/main.

2. Is origin/main a branch on the remote server?

Not in your local naming context. It is a local remote-tracking reference representing the remote's main branch.

3. What is the difference between main and origin/main?

main is a local branch; origin/main is your local record of the remote branch.

4. Does git fetch modify my working files?

Not by itself. It downloads objects and updates remote-tracking references without integrating them into the checked-out branch.

5. What does git pull do?

It fetches from a remote and then integrates the changes into the current branch, usually by merge unless rebase behavior is selected.

6. What is an upstream branch?

The branch configured as the tracking counterpart for a local branch, commonly used as the default pull source and push destination.

7. What does git push -u origin feature/x do?

It pushes the local branch to the remote and sets its upstream tracking relationship.

8. How do you list remote-tracking branches?

Use git branch -r; use git branch -a to show local and remote-tracking branches.

9. What is the purpose of git branch -vv?

It displays local branches, their latest commits, upstream branches and ahead/behind status.

10. Does git remote remove origin delete the GitHub repository?

No. It removes the remote's local configuration only.

11. Why can a push be rejected as non-fast-forward?

The remote branch contains commits not included in the local branch. Fetch and integrate those commits before pushing.

12. What does git fetch --prune do?

It removes local remote-tracking references for branches that no longer exist on the remote.

13. Is origin a reserved keyword?

No. It is a conventional remote name and can be changed or replaced.

14. How can you check the upstream of the current branch?

Use git rev-parse --abbrev-ref --symbolic-full-name @{upstream} or git branch -vv.

15. When should you use fetch instead of pull?

When you want to review incoming commits or differences before integrating them into your current branch.

Beginner
What is the difference between git fetch and git pull?

Fetch downloads commits and updates remote-tracking branches only; pull fetches and then integrates (merge, rebase or fast-forward) into the current branch.

What is origin/main?

A remote-tracking branch: your local, read-only record of where main was on origin at the last fetch.

Intermediate
Why is a push rejected as non-fast-forward?

The remote branch contains commits that are not in your local branch; pushing would discard them.

What does git pull --rebase do?

Fetches, then replays your local commits on top of the updated remote branch, producing linear history without a merge commit.

Advanced
Explain --force-with-lease and why it is safer than --force.

It overwrites the remote branch only if it still points to the commit your remote-tracking branch recorded; if someone pushed meanwhile, the push is refused.

What changed in git pull behaviour in recent Git versions?

Since Git 2.33, if the branches have diverged and no strategy is configured or given, pull errors with "Need to specify how to reconcile divergent branches" instead of merging silently.

Scenario
CI fails because a branch "behind main by 20 commits" is tested. How do you update it?

git fetch, then git rebase origin/main (or git merge origin/main), fix conflicts, run tests, push (--force-with-lease after a rebase). On GitHub the "Update branch" button does the merge/rebase server-side.

  • fetch is always safe; pull integrates using merge, rebase or fast-forward — configure which.
  • push must fast-forward; rejected pushes mean "integrate first".
  • Use --force-with-lease only on your own branches; protect shared branches.
