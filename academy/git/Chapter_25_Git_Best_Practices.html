Learning objectives

Chapter introduction

What it is. The habits and team standards that make Git work at scale: commit hygiene, branch naming, pull-request and code-review standards, conflict avoidance, keeping branches current, protecting production, managing permissions, clean history and a written team Git standard — supported by hooks, bisect and blame.

Why it matters. Tools don't create quality; consistent practice does. A written standard turns tribal knowledge into something new joiners and auditors can follow.

Where it is used. CONTRIBUTING.md, PR templates, rulesets/policies, pre-commit hooks, CI checks.

In this course's project. Stage 8: the team publishes CONTRIBUTING.md, adds pre-commit hooks (format, lint, secret scan), and uses git bisect to find a regression in a DQ rule.

25.1

Meaningful commit messages

Source S26 · Chapter manual · 1. Meaningful commit messages

A good commit message explains the intent of a focused change. Use an imperative subject, keep it concise and add a body when reasoning or risk needs explanation. Reference work items where team policy requires it. Avoid vague messages.

Commands and practical example

git commit -m "Add null checks to order ingestion"
# For a detailed message, run git commit and write a subject and body.
25.2

Small and frequent commits

Source S26 · Chapter manual · 2. Small and frequent commits

Keep commits logically focused and small enough to review. A commit should ideally build or pass relevant tests on its own. Avoid mixing unrelated formatting, refactoring and feature changes.

Commands and practical example

git add sql/order_load.sql
git diff --cached
git commit -m "Handle late-arriving orders"
25.3

Branch naming standards

Source S26 · Chapter manual · 3. Branch naming standards

Agree on a predictable convention identifying work type and ticket number. Use lowercase and hyphens. Examples: feature/123-customer-check, bugfix/456-null-date and hotfix/789-prod-timeout.

Commands and practical example

git switch -c feature/123-customer-quality-check
git switch -c bugfix/456-null-date
git switch -c hotfix/789-prod-timeout
25.4

Pull request best practices

Source S26 · Chapter manual · 4. Pull request best practices

A pull request should state the problem, solution, scope, testing evidence, deployment considerations and rollback approach. Keep it focused, link the issue and request reviewers with relevant domain knowledge. Merge only after required checks and approvals pass.

Commands and practical example

# PR description template
## Problem
## Solution
## Scope / impacted pipelines and tables
## Testing evidence
## Deployment plan
## Rollback plan
## Related issue / change ticket
25.5

Code review standards

Source S26 · Chapter manual · 5. Code review standards

Review correctness, security, maintainability, tests, performance and operational impact. For SQL and data pipelines, check schema compatibility, incremental-load behavior, idempotency, duplicate handling, row-count validation, retry behavior and secret handling.

Commands and practical example

# Review checklist
# [ ] Correctness and edge cases
# [ ] Tests and validation evidence
# [ ] SQL / Spark performance
# [ ] Schema compatibility
# [ ] Secrets and permissions
# [ ] Monitoring, retries and rollback
25.6

Avoiding unnecessary commits

Source S26 · Chapter manual · 6. Avoiding unnecessary commits

Do not commit temporary debug output, generated files, credentials, local settings or unrelated formatting. Use .gitignore and staged-diff review. Amend only unpublished commits; for shared history, prefer a new corrective commit or coordinate a rewrite.

Commands and practical example

git status --short
git diff
git diff --cached
git status --ignored
25.7

Managing merge conflicts

Source S26 · Chapter manual · 7. Managing merge conflicts

Prevent conflicts by communicating ownership of shared files, keeping branches current, making focused changes and integrating regularly. When conflicts occur, understand both sides, resolve intended behavior, run tests and ask the owner if business logic is unclear.

Commands and practical example

git fetch origin
git merge origin/main
git status
# Resolve files, then:
git add <resolved-files>
git commit
25.8

Keeping branches updated

Source S26 · Chapter manual · 8. Keeping branches updated

Fetch frequently and integrate the latest base branch according to team policy. Use merge for shared branches when preserving history matters; rebase private feature branches when allowed. Avoid long-lived branches that drift from integration.

Commands and practical example

git fetch origin
git switch feature/customer-dq
git rebase origin/main
# Alternative for shared branch: git merge origin/main
25.9

Protecting production branches

Source S26 · Chapter manual · 9. Protecting production branches

Require pull requests, approvals and successful CI checks for production branches. Disable force pushes and deletion unless a controlled exception is required. Keep emergency bypass access limited, documented and audited.

Commands and practical example

# Repository rules:
# Require PR before merge
# Require approvals and status checks
# Require conversation resolution
# Restrict force pushes and deletion
25.10

Managing repository permissions

Source S26 · Chapter manual · 10. Managing repository permissions

Apply least privilege and team-based permissions. Remove access when roles change. Review outside collaborators and machine identities. Document who owns each repository and who can administer or bypass protections.

Commands and practical example

# Review repository collaborators and teams
# Review organization team roles and access policy
25.11

Maintaining clean history

Source S26 · Chapter manual · 11. Maintaining clean history

Choose a history policy—merge commits, squash merges or rebase merges—and document it. Keep commit messages useful and avoid rewriting shared history casually. Use signed commits or tags where provenance requirements justify them.

Commands and practical example

git log --graph --oneline --decorate --all
git branch -avv
git remote -v

Team Git standards

Source S26 · Chapter manual · 12. Team Git standards

Document branch names, commit format, PR templates, reviewers, required tests, merge strategy, release tags, hotfix handling, secret scanning, repository ownership and cleanup expectations. Keep standards proportionate to repository risk and team size.

Commands and practical example

# Example lightweight policy
# 1. Branch: type/ticket-short-description

Meaningful Commit Messages

Source S40 · 1. Meaningful Commit Messages
  • Use imperative, specific subjects: Fix duplicate orders caused by missing join key.
  • Keep subject ≤ 50 characters; body wrapped at 72; explain why.
  • Adopt Conventional Commits (feat, fix, docs, refactor, test, ci, chore).
  • Reference tickets (Refs: DE-1423, Fixes #42, AB#1423).
  • Enforce with a commit-msg hook or CI (e.g. commitlint).
Avoid Prefer
changes feat(sql): add dim_store table
fixed fix(adf): retry copy on transient 503 errors
asdf refactor(etl): extract date parsing into utils
25.14

Small and Frequent Commits

Source S40 · 2. Small and Frequent Commits
  • Atomic commits — one logical change per commit (it should build and pass tests).
  • Commit early, commit often; push at least daily.
  • Benefits: easier review, precise git revert, effective git bisect, fewer conflicts, less lost work.
  • Use git add -p to separate unrelated changes in the same file.
  • Clean up "wip" commits before merging (interactive rebase or squash merge).

Branch Naming Standards

Source S40 · 3. Branch Naming Standards
feature/DE-1423-orders-incremental-load
bugfix/DE-1501-null-order-date
hotfix/2.5.1-tax-rounding
release/2.6.0
chore/upgrade-pyspark
  • Lower-case, hyphen-separated, type prefix, ticket ID.
  • Enforce with rulesets (branch name patterns) or a pre-push hook.
  • Document in CONTRIBUTING.md.
25.16

Pull Request Best Practices

Source S40 · 4. Pull Request Best Practices

For authors:

  • Keep PRs small (< 400 changed lines) and focused on one purpose.
  • Use the PR template: summary, ticket, testing evidence, checklist.
  • Self-review the diff first; ensure CI is green.
  • Rebase/merge main to keep the PR current.
  • Use draft PRs for early feedback.
  • Respond to every comment; resolve conversations.

For the team:

  • Required reviewers via CODEOWNERS.
  • Merge strategy agreed (e.g. squash merge).
  • Auto-delete branches after merge.
  • Link PRs to work items.
25.17

Code Review Standards

Source S40 · 5. Code Review Standards
Area Reviewer checks
Correctness Business logic, joins, filters, aggregations, edge cases
Data quality NULLs, duplicates, late-arriving data, idempotent loads
Performance Partitioning, indexes, predicate pushdown, avoiding SELECT *, Spark shuffles
Security No secrets, least privilege, PII handling/masking
Maintainability Naming, readability, modularity, comments where needed
Tests Unit tests, data validation, CI passing
Compatibility Schema changes don't break downstream consumers
Documentation README, data dictionary, runbooks updated

Etiquette: review within one working day; be specific and respectful; label nits; approve when good enough — not perfect; use suggestions for small fixes.

25.18

Avoiding Unnecessary Commits

Source S40 · 6. Avoiding Unnecessary Commits
  • Don't commit generated files, build outputs, logs, data or dependencies (.gitignore).
  • Don't commit debug prints or commented-out code.
  • Don't mix formatting-only changes with logic changes (separate commits/PRs).
  • Squash "fix typo"/"wip" commits before merging.
  • Avoid empty merge commits from git pull on feature branches (git pull --rebase).
  • Don't commit unrelated file-mode or line-ending changes (core.fileMode, .gitattributes).
25.19

Managing Merge Conflicts

Source S40 · 7. Managing Merge Conflicts
  • Integrate main into feature branches frequently.
  • Keep branches short-lived.
  • Organise code into small files (one SQL object per file).
  • Agree on formatters (SQLFluff, Ruff/Black) and run them automatically.
  • Enable rerere and merge.conflictstyle zdiff3.
  • Resolve with the author of the other change when unsure.
  • Run tests after resolving; never commit conflict markers (CI git diff --check).

Keeping Branches Updated

Source S40 · 8. Keeping Branches Updated
git fetch origin
git switch feature/my-work
git rebase origin/main      # or: git merge origin/main
git push --force-with-lease # if rebased
  • Enable GitHub's Always suggest updating pull request branches / Require branches to be up to date.
  • Use merge queues on busy repositories.
  • Delete merged branches to reduce clutter.
25.21

Protecting Production Branches

Source S40 · 9. Protecting Production Branches
  • Rulesets/branch policies on main and release/*: PR required, approvals, Code Owner review, status checks, conversation resolution, block force pushes and deletion.
  • Restrict bypass to a small emergency group (audited).
  • Require signed commits where compliance demands.
  • Deploy production only from protected branches or tags through CI/CD with environment approvals.
  • Protect release tags (v*) with tag rulesets.
25.22

Managing Repository Permissions

Source S40 · 10. Managing Repository Permissions
  • Grant access through teams, not individuals.
  • Least privilege: most developers need Write, few need Admin.
  • Use CODEOWNERS for ownership of areas.
  • Require SSO and 2FA for the organisation.
  • Review access quarterly; remove leavers immediately.
  • Use deploy keys / GitHub Apps / service principals for automation, not personal accounts.
  • Monitor the audit log.
25.23

Maintaining Clean History

Source S40 · 11. Maintaining Clean History
  • Choose a merge strategy that matches your needs (squash for clean mainline; merge commits for full traceability).
  • Rebase/clean local feature branches before merging; never rewrite shared history.
  • Meaningful commit messages and tags for releases.
  • Use git log --first-parent main to read mainline history.
  • Revert instead of resetting shared branches.

Team Git Standards

Source S40 · 12. Team Git Standards

Document standards in CONTRIBUTING.md and enforce them with automation.

# Contributing to retail-data-platform

## Branching
- Branch from `main`: `feature/<ticket>-<desc>`, `bugfix/...`, `hotfix/...`
- Keep branches < 3 days; sync with main daily.

## Commits
- Conventional Commits: `type(scope): description`
- Reference tickets in the footer.

## Pull requests
- Use the PR template; < 400 lines; 1 approval + Code Owner; CI green.
- Squash merge; branch auto-deleted.

## Code standards
- SQL: one object per file, `CREATE OR ALTER`, SQLFluff clean.
- Python: Ruff + pytest; no secrets; config via environment.
- Notebooks: logic in modules, notebooks as thin orchestration.

## Security
- No secrets in Git. Use Key Vault / secret scopes.
- pre-commit hooks must be installed: `pre-commit install`.

## Releases
- Semantic versioning; tag `vX.Y.Z` on main; deploy via pipeline only.

Automation that enforces standards:

Formatting/linting pre-commit (Ruff, SQLFluff, trailing whitespace)
Secrets gitleaks, push protection

Command reference

pre-commit framework
Syntax
pip install pre-commit
pre-commit install
pre-commit run --all-files
Purpose
Run checks automatically before each commit (client-side pre-commit hook).
Example
# .pre-commit-config.yaml
repos:
  - repo: https://github.com/pre-commit/pre-commit-hooks
    rev: v5.0.0
    hooks:
      - id: trailing-whitespace
      - id: end-of-file-fixer
      - id: check-json
      - id: check-added-large-files
        args: ["--maxkb=5000"]
      - id: detect-private-key
  - repo: https://github.com/astral-sh/ruff-pre-commit
    rev: v0.8.0
    hooks:
      - id: ruff
      - id: ruff-format
Common mistakes
Treating client hooks as enforcement — they can be skipped with --no-verify; the same checks must run in CI. Pin rev versions and update them with pre-commit autoupdate.
git blame
Syntax
git blame [-L <start>,<end>] [-w] [-M] [-C] <file>
git config blame.ignoreRevsFile .git-blame-ignore-revs
Purpose
Show which commit last changed each line.
Expected output
7a8b9c0d (Asha Rao 2026-11-20 10:15:02 +0530 12)     WHERE c.IsActive = 1
Example
git blame -L 10,30 -w -C sql/warehouse/usp_load_dim_customer.sql
git log -S "IsActive" --oneline -- sql/       # commits that added/removed the string
Common mistakes
Blaming a formatting commit — list mass-reformat commits in .git-blame-ignore-revs (GitHub honours it too).
git bisect
Syntax
git bisect start [<bad> [<good>]]
git bisect good | bad | skip
git bisect run <cmd>
git bisect reset
Purpose
Binary-search history for the commit that introduced a bug.
Expected output
3c4d5e6f is the first bad commit
commit 3c4d5e6f…
Author: Ravi Kumar <ravi.kumar@retail-example.com>
    feat(dq): tighten quantity rule
Example
git bisect start HEAD v1.0.0
git bisect run python -m pytest python/dq/tests/test_orders_rules.py -q
git bisect reset
Common mistakes
Forgetting git bisect reset — you remain in detached HEAD.

Real-time scenarios

Source S26, S40 · Reviews take a week and PRs pile up

Measure PR size and age; set a review SLA, limit PR size, use CODEOWNERS to route reviews, and enable auto-merge after approvals and checks.

Course addition · Formatting commit pollutes blame

Add its SHA to .git-blame-ignore-revs and configure blame.ignoreRevsFile; GitHub's blame view respects the file automatically.

Best practices

Course addition · best practices
  • Write the standard down and enforce it with tools (hooks + CI + rulesets).
  • Small, focused commits and PRs; integrate daily.
  • Automate formatting/linting so reviews focus on logic and data impact.
  • Use bisect and blame for investigation, not for blame culture.

Chapter 25 Interview Questions

Source S26 · Chapter manual · interview

1. What makes a good commit message?

A concise imperative subject that explains intent, with a body for important context.

2. Why keep commits small?

They are easier to review, test, revert and troubleshoot.

3. Give an example branch naming convention.

feature/123-customer-quality-check or hotfix/789-prod-timeout.

4. What should a pull request description include?

Problem, solution, scope, tests, deployment and rollback details, and related issue.

5. What should a reviewer check in a data pipeline change?

Correctness, schema compatibility, idempotency, data quality, performance, security and operational behavior.

6. When should you amend a commit?

Usually when it has not been shared and the change is still part of local cleanup.

7. How can conflicts be reduced?

Keep branches current, communicate ownership, make focused changes and integrate frequently.

8. Should you blindly accept ours or theirs during a conflict?

No. Understand both changes and validate the intended combined behavior.

9. When is rebase suitable?

Often for private feature branches when team policy allows history rewriting.

10. When is merge safer?

For shared branches or when preserving integration history matters.

11. Why protect main or production branches?

To require review, checks and controlled access before important changes land.

12. What is least privilege in repository access?

Granting only the minimum role and permissions required.

13. Why define a merge strategy?

It keeps history consistent and makes auditing and troubleshooting predictable.

14. What should a team Git standard document?

Branching, commits, PRs, reviews, tests, merges, releases, permissions and secret handling.

15. What is a useful data engineering PR validation checklist?

Schema checks, row counts, duplicate handling, incremental-load behavior, retries, monitoring and rollback.

Beginner
Name three Git best practices.

Small focused commits with clear messages; short-lived branches merged via reviewed PRs; never commit secrets or generated files.

Intermediate
What are Git hooks?

Scripts in .git/hooks (or managed by frameworks) that run on events like pre-commit, commit-msg, pre-push; server-side hooks/rulesets enforce policies centrally.

What does git blame do?

Shows, per line, the last commit, author and date that changed it.

Advanced
How does git bisect run work?

It repeatedly checks out midpoint commits and runs your command; exit code 0 = good, 1–127 (except 125) = bad, 125 = skip, until the first bad commit is found.

Scenario
You join a team with no Git standards and frequent production incidents from unreviewed changes. What do you implement first?

Protect main (PR + checks + no force push), CODEOWNERS, a PR template, CI with tests, then a written CONTRIBUTING.md and pre-commit hooks; measure and iterate.
