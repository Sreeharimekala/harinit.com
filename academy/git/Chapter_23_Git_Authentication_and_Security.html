Learning objectives

Chapter introduction

What it is. Securing Git work: authentication (HTTPS with credential managers and tokens, SSH keys), 2FA, organization and repository permissions, branch protection, signed commits and tags, secret management, removing exposed credentials and preventing leaks.

Why it matters. Repositories contain the blueprint of your data platform. Leaked tokens or connection strings in Git history are among the most common causes of cloud breaches.

Where it is used. Developer machines, CI/CD, platform governance (GitHub organization / Azure DevOps project settings).

In this course's project. Stage 8 (governance): SSH Ed25519 keys and fine-grained PATs for developers, OIDC for pipelines, Key Vault for secrets, push protection and pre-commit secret scanning, signed release tags, and a drill for removing a leaked connection string.

23.1

HTTPS authentication

Source S24 · Chapter manual · 1. HTTPS authentication

HTTPS remotes use a provider-supported credential flow, commonly browser sign-in through a credential manager or a token. Do not embed credentials in remote URLs or scripts. Follow current organizational identity requirements.

Commands and practical example

git remote -v
git remote set-url origin https://github.com/ORG/REPO.git
git config --show-origin --get-all credential.helper
23.2

SSH authentication

Source S24 · Chapter manual · 2. SSH authentication

SSH uses a key pair: a private key stays on your machine and a public key is registered with the hosting service. Protect the private key with a passphrase and never upload it to a repository, ticket or chat.

Commands and practical example

ssh -V
ssh-keygen -t ed25519 -C "your_email@example.com"
ssh-add ~/.ssh/id_ed25519
ssh -T git@github.com
23.3

Generating SSH keys

Source S24 · Chapter manual · 3. Generating SSH keys

Generate an Ed25519 key where supported, protect it with a passphrase and add the public key to your GitHub account. On managed devices, follow key-management policy and verify the host fingerprint.

Commands and practical example

ssh-keygen -t ed25519 -C "your_email@example.com"
cat ~/.ssh/id_ed25519.pub
ssh -T git@github.com
23.4

Configuring SSH keys in GitHub

Source S24 · Chapter manual · 4. Configuring SSH keys in GitHub

Copy only the public key ending in .pub into account SSH-key settings. Give it a recognizable title, review key usage and remove keys that are no longer needed. Never share the private key file.

Commands and practical example

# Display the public key
cat ~/.ssh/id_ed25519.pub
# Then add it under GitHub account Settings > SSH and GPG keys
ssh -T git@github.com
23.5

Personal Access Tokens (PAT)

Source S24 · Chapter manual · 5. Personal Access Tokens (PAT)

A PAT authorizes supported Git hosting or API operations. Prefer fine-grained tokens where available, grant only required repositories and permissions, set an expiry and rotate or revoke tokens according to policy. Treat every token like a password.

Commands and practical example

# Do not paste a real token into commands or scripts.
# Use an approved credential manager.
git config --show-origin --get-all credential.helper
23.6

Credential managers

Source S24 · Chapter manual · 6. Credential managers

Credential managers securely store and retrieve credentials, often integrating with browser sign-in and operating-system secure storage. Avoid plaintext credential storage. Git Credential Manager is commonly available with Git for Windows.

Commands and practical example

git config --show-origin --get-all credential.helper
git credential-manager --version
git config --global credential.helper manager

Two-factor authentication

Source S24 · Chapter manual · 7. Two-factor authentication

2FA adds a second verification factor to account sign-in. Enable it for personal and organization accounts and store recovery codes securely. 2FA does not make a leaked PAT safe; revoke exposed tokens separately.

Commands and practical example

# GitHub: Settings > Password and authentication
# Enable 2FA and store recovery methods securely.

23.11

Signed commits

Source S24 · Chapter manual · 11. Signed commits

Commit signing allows a hosting provider or reviewer to verify that a commit was signed by a key associated with an identity. Git supports GPG and other signing methods, including SSH signing in supported versions. A signature does not prove code is safe.

Commands and practical example

git config --global commit.gpgsign true
git config --global user.signingkey <KEY-ID>
git commit -S -m "Add source validation"
git log --show-signature -1
23.12

GPG signatures

Source S24 · Chapter manual · 12. GPG signatures

GPG signing uses a private signing key to sign commits or tags; the corresponding public key can be published for verification. Protect the private key, configure Git's signing key and verify signatures after signing. Follow organizational key-rotation requirements.

Commands and practical example

gpg --list-secret-keys --keyid-format LONG
git config --global gpg.format openpgp
git config --global user.signingkey <KEY-ID>
git commit -S -m "Signed change"
23.13

Git secrets management

Source S24 · Chapter manual · 13. Git secrets management

Never commit passwords, API keys, PATs, private keys, connection strings or production secrets. Use an approved secret manager or CI/CD secret store and inject secrets at runtime. Ignore rules and scanning are supporting controls, not secure storage.

Commands and practical example

# Example .gitignore entries
.env
.env.*
*.pem
*.pfx
secrets/
local.settings.json
23.14

Removing exposed credentials

Source S24 · Chapter manual · 14. Removing exposed credentials

If a secret is exposed, assume it is compromised. Revoke or rotate it immediately at the issuing system, assess access logs and downstream impact, notify security, and replace it through the approved secret store. History rewriting does not invalidate clones, caches or forks.

Commands and practical example

# Incident response:
# 1. Revoke/rotate credential at source.
# 2. Notify security / incident response.
# 3. Assess logs and affected systems.
# 4. Remove from current code and deploy safe config.
# 5. Follow approved history-cleanup procedure.
23.15

Preventing accidental secret commits

Source S24 · Chapter manual · 15. Preventing accidental secret commits

Combine .gitignore, secret-scanning alerts, push protection, pre-commit scanning, code review and least-privilege credentials. Test scanners with safe dummy patterns only. Avoid secrets in command arguments, shell history, logs or screenshots.

Commands and practical example

git status --short
git diff --cached --name-only
git diff --cached
23.16

HTTPS Authentication

Source S40 · 1. HTTPS Authentication

1.1 How it works

When you push/pull over HTTPS, Git asks a credential helper for credentials. The host verifies them and checks your permissions.

1.2 Credential options for HTTPS

Option Notes
Git Credential Manager (browser/OAuth sign-in) Recommended; tokens stored securely; supports GitHub, Azure DevOps, Bitbucket, GitLab
Personal Access Token (PAT) as password Works everywhere; must be stored securely and rotated
GitHub CLI (gh auth login + gh auth setup-git) Configures Git to use the CLI's token
Account password Not accepted by GitHub for Git operations

1.3 Example

git clone https://github.com/company/retail-data-platform.git
# Git Credential Manager opens a browser window → sign in → done

1.4 Updating stored credentials

  • Windows: Credential Manager → Windows Credentials → git:https://github.com → edit/remove.
  • macOS: Keychain Access → search github.com.
  • CLI: git credential reject or git credential-manager erase (feed it protocol=https/host=github.com).
23.17

SSH Authentication

Source S40 · 2. SSH Authentication

2.1 How it works

SSH uses public-key cryptography:

  • Private key — stays on your computer (~/.ssh/id_ed25519). Never share it.
  • Public key — uploaded to GitHub/Azure DevOps (~/.ssh/id_ed25519.pub).
  • During connection, the server challenges your client to prove possession of the private key.

2.2 Advantages

No tokens to type; keys can be protected with a passphrase and loaded into an agent; good for Linux servers and automation.

2.3 SSH URL format

git@github.com:company/retail-data-platform.git
git@ssh.dev.azure.com:v3/contoso/DataPlatform/retail-data-platform
23.18

Generating SSH Keys

Source S40 · 3. Generating SSH Keys

3.1 Check for existing keys

ls -al ~/.ssh

3.2 Generate a new key (Ed25519 recommended)

ssh-keygen -t ed25519 -C "ravi.kumar@company.com"

Enter file in which to save the key (/home/ravi/.ssh/id_ed25519): [Enter]
Enter passphrase (empty for no passphrase): ********

If a system requires RSA (some older servers / Azure DevOps setups):

ssh-keygen -t rsa -b 4096 -C "ravi.kumar@company.com"

3.3 Add the key to the SSH agent

# Linux / Git Bash
eval "$(ssh-agent -s)"
ssh-add ~/.ssh/id_ed25519

# macOS (store passphrase in Keychain)
ssh-add --apple-use-keychain ~/.ssh/id_ed25519

Windows PowerShell (OpenSSH service):

Get-Service ssh-agent | Set-Service -StartupType Automatic
Start-Service ssh-agent
ssh-add $env:USERPROFILE\.ssh\id_ed25519

Configuring SSH Keys in GitHub

Source S40 · 4. Configuring SSH Keys in GitHub
  1. Copy the public key:
cat ~/.ssh/id_ed25519.pub          # Linux/macOS/Git Bash
clip < ~/.ssh/id_ed25519.pub       # Git Bash on Windows → clipboard
  1. GitHub → Settings → SSH and GPG keys → New SSH key.
  2. Title: Work laptop; Key type: Authentication Key; paste; Add SSH key.
  3. If your organisation uses SAML SSO, click Configure SSO → Authorize for the org.
  4. Test:
ssh -T git@github.com
# Hi ravi! You've successfully authenticated, but GitHub does not provide shell access.
  1. Switch your remote to SSH:
git remote set-url origin git@github.com:company/retail-data-platform.git

Multiple accounts (~/.ssh/config):

Host github-work
    HostName github.com
    User git
    IdentityFile ~/.ssh/id_ed25519_work

Host github-personal
    HostName github.com
    User git
    IdentityFile ~/.ssh/id_ed25519_personal

git clone git@github-work:company/retail-data-platform.git

Port 22 blocked? Use SSH over 443:

Host github.com
    HostName ssh.github.com
    Port 443
    User git
23.20

Personal Access Tokens (PAT)

Source S40 · 5. Personal Access Tokens (PAT)

5.1 Definition

A PAT is a revocable token used instead of a password for HTTPS Git operations and API calls.

5.2 GitHub token types

Type Characteristics
Fine-grained (recommended) Limited to specific repositories, granular permissions (e.g. Contents: read/write), mandatory expiration, org approval possible
Classic Broad scopes (repo, workflow...), access to all repos you can access

5.3 Creating a fine-grained token

GitHub → Settings → Developer settings → Personal access tokens → Fine-grained tokens → Generate new token → name, expiration, resource owner, selected repositories, permissions (e.g. Contents: Read and write) → Generate → copy it once.

5.4 Using it

git clone https://github.com/company/retail-data-platform.git
Username: ravi
Password: <paste token>

Azure DevOps PAT: User settings → Personal access tokens → New token → scope Code (Read & write).

5.5 Best practices

  • Shortest practical expiration; least privilege.
  • Store in a credential manager or secret store — never in code or scripts.
  • Revoke immediately if exposed.
  • For automation prefer GitHub Apps, GITHUB_TOKEN in Actions, OIDC/workload identity federation or service principals over personal tokens.

Credential Managers

Source S40 · 6. Credential Managers

6.1 Definition

A credential helper stores and supplies credentials to Git so you don't type them every time.

Helper Platform Storage
Git Credential Manager (GCM) Windows, macOS, Linux OS secure store (Windows Credential Manager, macOS Keychain, Linux secret service)
osxkeychain macOS Keychain
libsecret Linux GNOME Keyring / KWallet
cache Linux/macOS Memory, for a timeout (--timeout=3600)
store Any Plain text ~/.git-credentials — avoid 
git config --global credential.helper manager         # GCM (Windows default)
git config --global credential.helper osxkeychain
git config --global credential.helper "cache --timeout=3600"
git config --global --get credential.helper

GCM supports OAuth browser login, MFA, Azure DevOps Entra ID authentication, and multiple accounts.

Two-Factor Authentication

Source S40 · 7. Two-Factor Authentication

7.1 Definition

2FA requires a second factor in addition to your password when signing in to GitHub.

7.2 Methods

Method Notes
Authenticator app (TOTP) Microsoft/Google Authenticator, 1Password...
Passkeys / security keys Phishing-resistant (recommended)
GitHub Mobile Push approval
SMS Least secure; fallback only

7.3 Setup

GitHub → Settings → Password and authentication → Enable two-factor authentication → scan QR code → enter code → save recovery codes (download and store safely) → optionally add passkeys.

7.4 Effect on Git

2FA applies to web sign-in. Command-line Git uses tokens/SSH keys/GCM (which handles the 2FA sign-in). Organisations can require 2FA for all members.

23.26

Signed Commits

Source S40 · 11. Signed Commits

11.1 Why sign

Anyone can set user.name/user.email to any value. Signing cryptographically proves the commit was created by the holder of a key associated with your account. GitHub shows a Verified badge.

11.2 Signing options

Method Key
GPG OpenPGP key
SSH (Git 2.34+) Your SSH key
S/MIME (X.509) Corporate certificate (gitsign/smimesign)

11.3 SSH signing (simplest)

git config --global gpg.format ssh
git config --global user.signingkey ~/.ssh/id_ed25519.pub
git config --global commit.gpgsign true
git config --global tag.gpgsign true

On GitHub: Settings → SSH and GPG keys → New SSH key → Key type: Signing Key → paste the same public key.

git commit -m "feat: signed commit"
git log --show-signature -1

(For local verification of SSH signatures, configure gpg.ssh.allowedSignersFile.)

23.27

GPG Signatures

Source S40 · 12. GPG Signatures

12.1 Generate a GPG key

gpg --full-generate-key          # choose ECC (ed25519) or RSA 4096, validity, name, email (must match a verified GitHub email)
gpg --list-secret-keys --keyid-format=long

sec   ed25519/3AA5C34371567BD2 2026-11-26 [SC]
uid                 [ultimate] Ravi Kumar <ravi.kumar@company.com>

12.2 Configure Git

git config --global user.signingkey 3AA5C34371567BD2
git config --global commit.gpgsign true
git config --global gpg.program "C:/Program Files (x86)/GnuPG/bin/gpg.exe"   # Windows if needed

12.3 Add to GitHub

gpg --armor --export 3AA5C34371567BD2

Copy the block (-----BEGIN PGP PUBLIC KEY BLOCK----- ... ) → GitHub Settings → SSH and GPG keys → New GPG key.

12.4 Use and verify

git commit -S -m "fix: signed with GPG"
git tag -s v1.0.0 -m "Signed release"
git verify-commit HEAD
git verify-tag v1.0.0
git log --show-signature

Git Secrets Management

Source S40 · 13. Git Secrets Management

13.1 What counts as a secret

Passwords, connection strings, storage account keys, SAS tokens, API keys, PATs, Databricks tokens, service principal secrets, private keys (.pem, .pfx), .env files, local.settings.json.

13.2 Where secrets should live

Context Secret store
Azure resources Azure Key Vault
ADF / Synapse / Fabric Key Vault-backed linked services / connections
Databricks Secret scopes (Key Vault-backed) — dbutils.secrets.get(scope, key)
GitHub Actions Repository/environment/org secrets; prefer OIDC for Azure login
Azure Pipelines Secret variables, variable groups linked to Key Vault, service connections
Local development .env (git-ignored), OS keychain, az login

13.3 Code pattern

# Bad
conn = "Server=sql.company.com;User=etl;Password=P@ssw0rd!"

# Good (Databricks)
password = dbutils.secrets.get(scope="kv-rdp", key="sql-etl-password")

# Good (Python, environment variable injected by CI/Key Vault)
import os
password = os.environ["SQL_ETL_PASSWORD"]

Commit .env.example with variable names and dummy values; ignore the real .env.

23.29

Removing Exposed Credentials

Source S40 · 14. Removing Exposed Credentials

Important The first and most important step is to revoke/rotate the secret. Once pushed, assume it has been copied — history rewriting alone does not make it safe.

14.1 Response steps

  1. Rotate/revoke the credential immediately (Key Vault, Azure portal, GitHub token settings).
  2. Check logs for misuse of the credential.
  3. Remove it from current code and replace with a secret-store reference; commit.
  4. Purge it from history (if required by policy):
pip install git-filter-repo

# Remove an entire file from all history
git filter-repo --path config/secrets.json --invert-paths

# Or replace secret strings everywhere
cat > replacements.txt <<'EOF'
P@ssw0rd!==>***REMOVED***
regex:AccountKey=[A-Za-z0-9+/=]+==>AccountKey=***REMOVED***
EOF
git filter-repo --replace-text replacements.txt

(Alternative tool: BFG Repo-Cleaner — bfg --replace-text passwords.txt.)

  1. Force-push the rewritten history and tags (temporarily allow force-push on protected branches):
git remote add origin <url>        # filter-repo removes origin as a safety measure
git push origin --force --all
git push origin --force --tags
  1. Ask collaborators to re-clone (old clones still contain the secret).
  2. Contact GitHub Support to remove cached views and PR references if needed.
  3. Document the incident and add prevention controls.

14.2 If the secret is only in your last local commit (not pushed)

git rm --cached .env
echo ".env" >> .gitignore
git commit --amend --no-edit

Preventing Accidental Secret Commits

Source S40 · 15. Preventing Accidental Secret Commits
Layer Control
Repository .gitignore for .env, *.pem, *.pfx, local.settings.json, secrets.*
Developer machine Pre-commit hooks with gitleaks / detect-secrets / git-secrets
Platform GitHub secret scanning + push protection (blocks pushes containing known secret patterns); Azure DevOps GitHub Advanced Security
CI Secret scanning job on every PR
Process Code review checklist, training
Architecture Key Vault, managed identities, OIDC — so there are fewer secrets to leak

Pre-commit configuration:

# .pre-commit-config.yaml
repos:
  - repo: https://github.com/gitleaks/gitleaks
    rev: v8.21.2
    hooks:
      - id: gitleaks
  - repo: https://github.com/pre-commit/pre-commit-hooks
    rev: v5.0.0
    hooks:
      - id: detect-private-key
      - id: check-added-large-files

pip install pre-commit
pre-commit install
pre-commit run --all-files

(Update rev: values to the latest releases when you set this up.)

CI job:

- uses: actions/checkout@v4
  with: { fetch-depth: 0 }
- uses: gitleaks/gitleaks-action@v2
  env:
    GITHUB_TOKEN: ${{ secrets.GITHUB_TOKEN }}

git clone --mirror git@github.com:retail-data/enterprise-retail-data-platform.git
cd enterprise-retail-data-platform.git
printf 'Password=Sup3rS3cret!==>Password=***REMOVED***\n' > ../replacements.txt
git filter-repo --replace-text ../replacements.txt
git push --force --mirror
Common mistakes
Purging history instead of rotating the secret — once pushed, assume it was copied. Forks, clones, PR refs and caches may still contain it; contact GitHub Support for cached views if needed.

Chapter 23 Interview Questions

Source S24 · Chapter manual · interview

1. What is the difference between HTTPS and SSH authentication?

HTTPS uses a provider-supported credential flow; SSH authenticates with a key pair.

2. Which SSH key is shared with GitHub?

The public key; the private key must remain secret.

3. What is a PAT?

A token that authorizes specified Git hosting or API operations.

4. Why use fine-grained PATs?

They can limit access to selected repositories and permissions.

5. Why use a credential manager?

It stores and retrieves credentials through secure operating-system or browser integrations.

6. What does 2FA protect?

It adds a second factor to account sign-in; exposed tokens still require revocation.

7. What is least privilege?

Granting only the minimum access required to perform a task.

8. What is branch protection?

Rules that require checks/reviews and restrict unsafe changes to important branches.

9. What does a signed commit provide?

A verifiable signature that supports commit provenance and integrity checks.

10. Does a signed commit prove code is safe?

No. It verifies a signature, not code quality or absence of vulnerabilities.

11. Where should application secrets be stored?

In an approved secret manager or CI/CD secret store, not in Git.

12. Does .gitignore remove a tracked secret?

No. It only prevents eligible untracked paths from being added by default.

13. What is the first action after a secret leak?

Revoke or rotate the credential at its issuing system immediately.

14. Does deleting a secret from the latest commit remove it from history?

No. Earlier commits may still contain it.

15. Why are secret scanners useful?

They detect credential patterns before or after code reaches the repository.

Beginner
Why can't you use your GitHub password with Git over HTTPS?

GitHub removed password authentication for Git operations; use a credential manager (OAuth), a personal access token, or SSH.

Which SSH key type does GitHub recommend?

Ed25519 (ssh-keygen -t ed25519); RSA 4096 only for legacy systems.

Intermediate
What are signed commits?

Commits with a cryptographic signature (GPG, SSH or S/MIME) proving the committer's identity; platforms show them as Verified.

How do pipelines authenticate to Azure without secrets?

OIDC / workload identity federation: the CI platform issues a short-lived token that Entra ID trusts for a federated credential.

Advanced
Why is removing a secret from the latest commit not enough?

It remains in history, clones, forks and caches; you must rotate the credential and, if required, purge history with git filter-repo and force-push.

Scenario
Push protection blocked your push because of a storage key in a notebook. What now?

Remove the key from all commits being pushed (amend/interactive rebase), use a Databricks secret scope or Key Vault, and rotate the key if it is real; bypass only for confirmed false positives with justification.
