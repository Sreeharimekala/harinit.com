Chapter introduction

What it is. Advanced internals and recovery: plumbing vs porcelain commands, cat-file, hash-object, ls-tree, rev-parse, reflog, fsck, the commit graph, recovering lost commits, maintenance and dealing with corruption.

Where it is used. Incident recovery, scripting/automation (plumbing output is stable), audits.

22.1

Plumbing commands

Source S23 · Chapter manual · 1. Plumbing commands

Plumbing commands expose lower-level object and repository operations. They are useful for diagnostics and scripting, while porcelain commands such as status, add and commit provide user-oriented workflows.

Commands and practical example

git status
git add file.sql
git commit -m "Add validation"
git cat-file -p HEAD
22.2

Porcelain commands

Source S23 · Chapter manual · 2. Porcelain commands

Porcelain is the user-facing command layer designed around common workflows. Examples include git status, add, commit, switch, merge and log. Porcelain output is generally more suitable for human use than low-level object output.

Commands and practical example

git status
git switch main
git add .
git commit -m "Update pipeline logic"
22.3

git cat-file

Source S23 · Chapter manual · 3. git cat-file

cat-file inspects objects. Use -t for type, -s for size and -p to pretty-print content. It can inspect blobs, trees, commits and annotated tag objects.

Commands and practical example

git cat-file -t HEAD
git cat-file -s HEAD
git cat-file -p HEAD
22.4

git hash-object

Source S23 · Chapter manual · 4. git hash-object

hash-object computes an object ID for file content. With -w it writes the object into the object database. Writing a blob does not stage the file or create a commit.

Commands and practical example

git hash-object sample.sql
git hash-object -w sample.sql
git cat-file -p <object-id>
22.5

git ls-tree

Source S23 · Chapter manual · 5. git ls-tree

ls-tree lists entries in a tree object. Use -r to recurse through subdirectories and inspect how committed paths map to object IDs and modes.

Commands and practical example

git ls-tree HEAD
git ls-tree -r HEAD
git ls-tree -l HEAD
22.6

git rev-parse

Source S23 · Chapter manual · 6. git rev-parse

rev-parse resolves revision expressions and reports repository paths or object-format information. It is frequently used in scripts to resolve symbolic names and relative commit expressions.

Commands and practical example

git rev-parse HEAD
git rev-parse HEAD~3
git rev-parse --show-toplevel
git rev-parse --show-object-format
22.7

git reflog

Source S23 · Chapter manual · 7. git reflog

The reflog records local updates to HEAD and references, including commits, resets, rebases and branch switches. It can locate commits no longer reachable from a branch. Reflogs are local and expire; they are not a remote backup.

Commands and practical example

git reflog
git reflog show --date=iso HEAD
git show HEAD@{2}
22.8

git fsck

Source S23 · Chapter manual · 8. git fsck

fsck checks object validity and connectivity. It can report dangling or unreachable objects. During recovery, inspect candidates first; do not prune objects while investigating missing work.

Commands and practical example

git fsck --full
git fsck --full --no-reflogs --unreachable
git fsck --lost-found
22.9

Understanding commit graphs

Source S23 · Chapter manual · 9. Understanding commit graphs

Commits form a directed acyclic graph. Parent links establish ancestry; branches and tags point into the graph. A merge commit joins histories by recording multiple parents. Commit-graph files can accelerate graph traversal.

Commands and practical example

git log --graph --oneline --decorate --all
git merge-base main feature/reporting
git commit-graph write --reachable
22.10

Recovering lost commits

Source S23 · Chapter manual · 10. Recovering lost commits

Inspect reflog for the previous commit. If found, create a branch at that object ID so the commit becomes reachable again. If reflog is insufficient, fsck may reveal dangling commits. Inspect candidates before restoring them.

Commands and practical example

git reflog
git branch recovery/restore-work <commit-sha>
git fsck --full --no-reflogs --unreachable
git show <candidate-sha>
22.11

Git maintenance

Source S23 · Chapter manual · 11. Git maintenance

Modern Git maintenance can perform tasks such as incremental repacking and commit-graph updates. Use scheduled maintenance for large repositories and avoid aggressive pruning during recovery or concurrent repository activity.

Commands and practical example

git maintenance start
git maintenance run
git maintenance stop
git count-objects -v
22.12

Repository corruption troubleshooting

Source S23 · Chapter manual · 12. Repository corruption troubleshooting

Make a copy before repair attempts. Check disk space, permissions and filesystem health; run fsck; inspect pack integrity; and compare with a trusted remote clone. A remote cannot restore uncommitted local-only content that was never stored as an object.

Commands and practical example

git fsck --full
git count-objects -v
git verify-pack -v .git/objects/pack/*.idx
git remote -v
git fetch --all --prune

Git Plumbing Commands

Source S40 · 1. Git Plumbing Commands

1.1 Definition

Plumbing commands are low-level commands that perform a single internal operation. They have stable output designed for scripts and tools.

1.2 Common plumbing commands

Command Purpose
git hash-object Compute/store an object
git cat-file Read object type, size, content
git update-index Modify the index
git write-tree Create a tree from the index
git commit-tree Create a commit object from a tree
git update-ref Create/move a reference safely
git symbolic-ref Read/write symbolic refs (HEAD)
git ls-tree List tree contents
git ls-files List index contents
git rev-parse Resolve names to hashes, repo paths
git rev-list List commits/objects reachable
git for-each-ref Iterate over refs with formatting
git read-tree Read a tree into the index
git diff-tree, git diff-index, git diff-files Low-level diffs
git merge-base Find common ancestor
git show-ref List refs

1.3 Build a commit using only plumbing

mkdir plumbing-demo && cd plumbing-demo && git init -q -b main

echo "SELECT 1;" > test.sql
BLOB=$(git hash-object -w test.sql)                      # 1. store blob
git update-index --add --cacheinfo 100644 "$BLOB" test.sql   # 2. stage it
TREE=$(git write-tree)                                   # 3. create tree
COMMIT=$(echo "First commit via plumbing" | git commit-tree "$TREE")   # 4. create commit
git update-ref refs/heads/main "$COMMIT"                 # 5. point main at it

git log --oneline       # shows the commit
git status              # clean

This is exactly what git add + git commit do behind the scenes.

22.14

Git Porcelain Commands

Source S40 · 2. Git Porcelain Commands

2.1 Definition

Porcelain commands are the user-friendly, high-level commands you use daily. They combine many plumbing operations and their output may change between versions (not meant for parsing — though many offer --porcelain for stable machine output).

Porcelain Built on
git add hash-object, update-index
git commit write-tree, commit-tree, update-ref
git branch update-ref, for-each-ref
git log rev-list + formatting
git checkout/switch read-tree, checkout-index, symbolic-ref
git merge merge-base, merge machinery, commit-tree 
git status --porcelain=v2      # stable, script-friendly output
22.15

git cat-file

Source S40 · 3. git cat-file

3.1 Purpose

Show the type, size or content of any object.

git cat-file -t <obj>      # type: blob, tree, commit, tag
git cat-file -s <obj>      # size
git cat-file -p <obj>      # pretty-print content
git cat-file -e <obj>      # exit 0 if object exists
git cat-file blob HEAD:README.md

3.2 Batch mode (scripts)

git rev-list --objects --all | git cat-file --batch-check='%(objecttype) %(objectname) %(objectsize) %(rest)' | sort -k3 -n | tail

Lists the largest objects in history — useful for repository cleanup.

22.16

git hash-object

Source S40 · 4. git hash-object

4.1 Purpose

Compute the object ID for content and optionally write it into the object database.

git hash-object file.sql               # compute only
git hash-object -w file.sql            # compute and store
echo "content" | git hash-object --stdin -w
git hash-object -t tree <file>         # specify type (rare)

4.2 Uses

  • Understanding content addressing.
  • Checking whether a file's content already exists in the repo: git cat-file -e $(git hash-object file).
  • Scripts that create objects programmatically.
22.17

git ls-tree

Source S40 · 5. git ls-tree

5.1 Purpose

List the contents of a tree object (a commit's snapshot or a directory).

git ls-tree HEAD                  # top-level
git ls-tree -r HEAD               # recursive (all files)
git ls-tree -r --name-only HEAD   # just paths
git ls-tree -r -l HEAD            # include sizes
git ls-tree v1.0.0 sql/           # a folder at a tag
git ls-tree -d HEAD               # only directories

5.2 Use case

List exactly which files were in the release deployed to production: git ls-tree -r --name-only v2.4.0 -- adf/pipeline/.

22.18

git rev-parse

Source S40 · 6. git rev-parse

6.1 Purpose

Translate revision names into hashes and answer questions about the repository. Heavily used in scripts and CI.

git rev-parse HEAD                 # full hash
git rev-parse --short HEAD         # short hash
git rev-parse main~2               # resolve expressions
git rev-parse v1.0.0^{commit}      # commit a tag points to
git rev-parse --abbrev-ref HEAD    # current branch name (or "HEAD" if detached)
git rev-parse --abbrev-ref @{u}    # upstream branch
git rev-parse --show-toplevel      # repository root path
git rev-parse --git-dir            # path to .git
git rev-parse --is-inside-work-tree
git rev-parse --verify feature/x   # fail if ref doesn't exist

6.2 CI example

BRANCH=$(git rev-parse --abbrev-ref HEAD)
SHA=$(git rev-parse --short HEAD)
echo "Building ${BRANCH}@${SHA}"
22.19

git reflog

Source S40 · 7. git reflog

7.1 Definition

The reflog ("reference log") is a local, private log of every update to HEAD and each branch tip — commits, checkouts, resets, rebases, merges, amends, pulls.

git reflog                        # HEAD history
git reflog show main              # a branch's history
git reflog --date=iso
git log -g --oneline              # reflog as a log

9c8b7a6 HEAD@{0}: reset: moving to HEAD~2
4d5e6f7 HEAD@{1}: commit: Add fact_sales table
1a2b3c4 HEAD@{2}: checkout: moving from main to feature/sales

7.2 Key facts

  • Local only — not pushed or cloned.
  • Entries expire (90 days reachable / 30 days unreachable by default).
  • Stored in .git/logs/.
  • The single most important recovery tool.
22.20

git fsck

Source S40 · 8. git fsck

8.1 Purpose

File System Check — verifies the connectivity and validity of objects in the database and reports problems and dangling objects.

git fsck                     # check
git fsck --full              # thorough check including packs
git fsck --unreachable       # objects not reachable from refs
git fsck --lost-found        # write dangling objects to .git/lost-found/
git fsck --no-reflogs        # treat reflog-only objects as unreachable

8.2 Output types

Message Meaning
dangling commit <sha> Commit not referenced by any branch/tag (e.g. after reset or dropped stash)
dangling blob <sha> File content staged but never committed (e.g. git add then reset)
missing blob <sha> Corruption — referenced object absent
broken link from tree ... Corruption

Understanding Commit Graphs

Source S40 · 9. Understanding Commit Graphs

9.1 The DAG

Git history is a Directed Acyclic Graph (DAG): commits are nodes, parent links are edges pointing backwards, and there are no cycles.

A ◄─ B ◄─ C ◄─ E ◄─ M (main)
      ▲              │
      └── D ◄────────┘   (M has parents E and D)

9.2 Viewing

git log --oneline --graph --all --decorate
git log --graph --format='%h %d %s' --date-order
git log --first-parent main          # mainline only
git log --ancestry-path A..B         # commits on the path between A and B
git merge-base --all main feature    # common ancestors
git rev-list --count main            # number of commits
git rev-list --left-right --count main...feature   # ahead/behind counts

9.3 Commit-graph file

.git/objects/info/commit-graph caches graph data for speed:

git commit-graph write --reachable --changed-paths
git config --global fetch.writeCommitGraph true

Recovering Lost Commits

Source S40 · 10. Recovering Lost Commits

10.1 Recovery checklist

Step Command
1. Look in the reflog git reflog / git reflog show <branch>
2. Inspect candidate git show <sha>
3. Recover to a branch git branch rescue <sha>
4. Not in reflog? Find dangling commits git fsck --lost-found or git fsck --unreachable (look for "dangling commit" / "unreachable commit" lines)
5. Inspect dangling commits git show <sha> / git log <sha>
6. Dropped stash? git fsck --unreachable (find the unreachable commit) → git stash apply <sha>
7. Was it pushed? Fetch from remote; check PR refs; ask teammates

10.2 Scenarios

# Deleted branch
git branch -D feature/orders
git reflog | grep "feature/orders"
git branch feature/orders 4d5e6f7

# Bad rebase
git reflog
git reset --hard HEAD@{7}         # the entry before "rebase (start)"

# Amended away a commit
git reflog                        # the original commit is still listed
git branch original-commit HEAD@{1}

# Staged file content lost after reset --hard (never committed)
git fsck --lost-found
ls .git/lost-found/other/         # dangling blobs written as files
git cat-file -p <blob-sha> > recovered.sql

Repository Corruption Troubleshooting

Source S40 · 12. Repository Corruption Troubleshooting

12.1 Symptoms

error: object file .git/objects/ab/cdef... is empty
fatal: loose object abcdef... is corrupt
error: inflate: data stream error (incorrect header check)
fatal: bad object HEAD
fatal: not a git repository (or any of the parent directories)
error: index file smaller than expected

12.2 Common causes

  • Power loss or crash during a Git operation.
  • Disk errors.
  • Syncing .git with OneDrive/Dropbox/Google Drive.
  • Antivirus interference.
  • Manually editing files in .git.

12.3 Step-by-step recovery

  1. Stop and back up the whole folder (including .git).
  2. Diagnose: git fsck --full.
  3. Corrupt index:
rm .git/index
git reset            # rebuild index from HEAD (working files untouched)
  1. Empty/corrupt loose objects: delete the empty files, then recover them from a remote:
find .git/objects -type f -empty -delete
git fetch origin                 # re-downloads missing objects that exist remotely
git fsck --full
  1. Corrupt HEAD/ref: edit .git/HEAD to ref: refs/heads/main, or reset a ref with a hash found in git reflog/packed-refs.
  2. Last resort: fresh clone and copy over uncommitted/unpushed work:
git clone <url> ../rdp-fresh
# copy changed files from the corrupted working directory
# for unpushed commits that are still readable: git format-patch origin/main..main  → git am in the fresh clone

12.4 Prevention

Keep repos out of sync folders, push frequently, use reliable disks, run git fsck occasionally, avoid manual .git edits.

Real-time scenarios

Source S23, S40 · Corrupted local repository after a cloud-sync conflict

git status fails with error: object file ... is empty / fatal: loose object ... is corrupt. Do not keep committing. Back up the folder, run git fsck --full, then the simplest fix: clone fresh from the remote and copy over uncommitted files. Never keep a working repository inside OneDrive/Google Drive synced folders.

Course addition · Find which commit introduced a regression

git bisect start, git bisect bad (current), git bisect good v1.0.0; Git checks out midpoints; mark each good/bad (or git bisect run pytest -q) until it reports the first bad commit; git bisect reset. (S41 topic, see Chapter 25.)

Best practices

Course addition · best practices
  • Use plumbing commands (stable output) in scripts.
  • Know reflog → fsck → remote as the recovery order.
  • Avoid storing repositories in file-sync folders.
  • Back up important repos (platform backups or git bundle --all).
  • Do not run gc --prune=now during incident recovery.

Chapter 22 Interview Questions

Source S23 · Chapter manual · interview

1. What is a porcelain command?

A user-facing command that performs a higher-level Git workflow.

2. What is a plumbing command?

A lower-level command exposing repository and object operations.

3. What does git cat-file -t do?

It reports an object's type.

4. What does git cat-file -p do?

It pretty-prints an object's content.

5. Does hash-object -w stage a file?

No. It stores an object but does not update the index.

6. What does git ls-tree show?

Entries in a tree object, including modes, object types, IDs and names.

7. What is reflog useful for?

Finding recent local reference positions, including commits lost after reset or rebase.

8. Is reflog shared with the remote?

No, reflogs are local.

9. What does git fsck check?

Object validity and connectivity; it can report dangling or unreachable objects.

10. What is a dangling commit?

A commit object not currently reachable through normal references, though it may still exist.

11. How can a lost commit be recovered?

Find it in reflog or fsck output and create a branch pointing to its SHA.

12. What is a commit graph?

The DAG formed by commit parent relationships.

13. What should you do before corruption repair?

Make a copy, preserve evidence, inspect with fsck and compare against a trusted clone.

14. Can a remote recover never-committed work?

No. Git cannot retrieve content that was never stored as an object.

15. What does rev-parse --show-toplevel return?

The path to the working tree's top-level directory.

Beginner
What is the reflog?

A local log of where HEAD and branch tips pointed over time, used to recover lost commits.

Intermediate
Plumbing vs porcelain?

Porcelain commands are user-facing (status, commit); plumbing commands are low-level building blocks with stable output for scripts (cat-file, rev-parse, update-ref).

How do you recover a deleted branch?

Find its last commit in the reflog (or git fsck) and run git branch <name> <sha>.

Advanced
What is a dangling commit?

A commit not reachable from any ref (often after amend/rebase/branch deletion); it remains until gc prunes it.

What is a Git bundle used for?

Moving repository data offline or as a backup; it can be cloned or fetched from like a remote.

Scenario
A colleague force-pushed main and the old commits are gone from the server. How do you restore them?

Anyone who fetched before has them in their origin/main reflog (git reflog show origin/main); push the old tip to a branch, restore main via PR or admin action, then enable protection against force pushes.
