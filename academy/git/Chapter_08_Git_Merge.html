Learning objectives

Chapter introduction

What it is. Merging joins two lines of development. Git looks at the tip of your current branch, the tip of the branch you are merging, and their merge base (the most recent common ancestor), and produces a result that contains both sets of changes.

Why it matters. Every branch you create must eventually be integrated. How you merge decides what your history looks like, how easy it is to roll back a feature, and how often your team fights conflicts.

Where it is used. Locally (git merge), and on every hosting platform through pull requests (GitHub "Create a merge commit / Squash and merge / Rebase and merge", Azure Repos "Merge (no fast forward) / Squash commit / Rebase / Semi-linear merge").

In this course's project. The Enterprise Retail Data Platform team merges SQL, Python and ADF feature branches into main several times a day; this chapter shows each merge type on real project files.

8.1

What is merging and why merge branches?

Source S09 · Chapter manual · 1–2. What is merging and why merge branches?

Merging integrates changes from one branch into another. A common workflow is to switch to the target branch (often main) and merge a completed feature branch.

git switch main
git merge feature/customer-report

Merge integrates parallel work while preserving the relevant commit history. Always inspect the target branch and working tree before starting.

8.2

Fast-forward merge

Source S09 · Chapter manual · 3. Fast-forward merge

A fast-forward merge is possible when the target branch is an ancestor of the branch being merged and no divergent target-side commits need combining. Git simply advances the target branch pointer.

A
→
B
→
C
feature tip

main points to B; merging advances main to C. No merge commit is needed.

git switch main
git merge feature/report
8.3

Three-way merge and merge strategy

Source S09 · Chapter manual · 4–5. Three-way merge and merge strategy

A three-way merge uses three points: the common ancestor, the current branch tip, and the other branch tip. Git combines changes from both sides and may create a merge commit.

Base A
↙
B: main
↘
D: merge
C: feature
↗

Conceptual divergent history; merge commit D has two parents.

Git's modern default merge strategy for ordinary two-head merges is ort. Older documentation and Git versions commonly refer to the recursive strategy. The recursive strategy was the traditional default before Git 2.34; it is useful to recognize the term, but ort is the modern default.

8.4

Merge commits, no-fast-forward, and squash merge

Source S09 · Chapter manual · 6–8. Merge commits, no-fast-forward, and squash merge
TechniqueResultTypical reason
Normal mergeFast-forward when possible; otherwise usually a merge commit.Integrate work with natural history.
--no-ffCreates a merge commit even if fast-forward is possible.Preserve an explicit branch integration point.
--squashStages combined changes as one new snapshot; does not create a merge commit or record merge parent relationship.Keep target history compact.
# Force a merge commit
git merge --no-ff feature/customer-report

# Squash feature changes into the index
git merge --squash feature/customer-report
git status
git commit -m "Add customer report"

Squash merge preserves the resulting content but not the original feature commits as ancestors of the target branch.

8.5

Merging feature branches

Source S09 · Chapter manual · 9. Merging feature branches
  1. Update your local target branch according to team policy.
  2. Switch to the target branch.
  3. Merge the feature branch.
  4. Resolve conflicts if required.
  5. Run tests and validation.
  6. Push the updated target branch and remove the feature branch when appropriate.
git switch main
git pull
git merge --no-ff feature/customer-dq
# run tests
git push

In hosted platforms, this process is often performed through a pull request or merge request, where reviewers and automated checks validate the change.

8.6

Aborting a merge

Source S09 · Chapter manual · 10. Aborting a merge

If a merge is in progress and you decide not to continue, use:

git merge --abort

This attempts to restore the pre-merge state. It is most reliable when you had no uncommitted changes before starting the merge. If you had local edits, preserve them carefully before attempting complex recovery.

8.7

Merge conflicts and resolving them

Source S09 · Chapter manual · 11–12. Merge conflicts and resolving them

A merge conflict occurs when Git cannot automatically reconcile changes, commonly because both branches edited overlapping lines or one branch deleted a file modified by the other.

Conflict markers in a file may look like:

<<<<<<< HEAD
SELECT CustomerID, Name FROM dbo.Customer;
=======
SELECT CustomerID, Name, Status FROM dbo.Customer;
>>>>>>> feature/customer-status

The section above ======= is the current branch version; below it is the incoming branch version. These markers are temporary and must be resolved manually or with a merge tool.

Resolution steps

  1. Run git status to identify conflicted paths.
  2. Open each conflicted file and decide the correct combined result.
  3. Remove conflict markers and validate the content.
  4. Stage resolved files using git add.
  5. Complete the merge with git commit if Git has not already completed it.
  6. Run tests and inspect the final diff.
git status
# edit conflicted files
git add sql/customer_query.sql
git diff --check
git status
git commit
8.8

Preventing merge conflicts

Source S09 · Chapter manual · 13. Preventing merge conflicts
  • Integrate small changes frequently rather than keeping branches open for long periods.
  • Keep feature branches focused and short-lived.
  • Coordinate ownership of shared files and high-change areas.
  • Communicate schema, interface, and pipeline contract changes early.
  • Pull or fetch and integrate target-branch changes regularly.
  • Use automated tests, formatting, and validation checks.
  • Avoid unrelated formatting changes in the same commit as functional changes.

Conflicts are a normal part of parallel development; good collaboration reduces their frequency and makes resolution safer.

8.9

Best practices for merging

Source S09 · Chapter manual · 14. Best practices for merging
  • Review the pull/merge request and understand all changed files.
  • Ensure the source branch is based on an appropriate current target.
  • Run unit tests, SQL validation, linting, and relevant pipeline checks.
  • Use consistent merge, squash, or rebase policies across the team.
  • Do not resolve conflicts by blindly accepting one side.
  • Keep merge commits and messages meaningful.
  • Protect the default branch and require review for production-bound changes.
8.10

What is Merging?

Source S40 · 1. What is Merging?

1.1 Definition

Merging is the process of integrating the changes from one branch into another, combining their histories.

1.2 Key rule

You always merge into the branch you are currently on:

git switch main                  # target branch
git merge feature/dim-product    # source branch

1.3 What Git does

  1. Finds the merge base (the best common ancestor).
  2. Compares changes on each side since the base.
  3. Combines them automatically where possible.
  4. Creates a merge commit (unless fast-forward), or stops for you to resolve conflicts.
8.11

Why Do We Merge Branches?

Source S40 · 2. Why Do We Merge Branches?
  • To deliver a finished feature into main/develop.
  • To bring the latest main into your feature branch (stay up to date, reduce conflicts).
  • To merge a release branch into main for production and back into develop.
  • To propagate a hotfix into all active branches.
  • To combine work from multiple developers.
8.12

Fast-Forward Merge

Source S40 · 3. Fast-Forward Merge

3.1 When it happens

If the target branch has no new commits since the source branch was created, Git simply moves the target pointer forward. No merge commit is created; history stays linear.

Before:                                After git merge feature:
main:    A ── B                         main:    A ── B ── C ── D
                \                                            ▲
feature:         C ── D                 feature: ────────────┘

3.2 Example

git switch main
git merge feature/dim-product

Updating 3f2a7d1..9c8b7a6
Fast-forward
 sql/tables/dim_product.sql | 5 +++++

3.3 Options

git merge --ff-only feature/x     # merge only if fast-forward is possible, else fail
8.13

Three-Way Merge

Source S40 · 4. Three-Way Merge

4.1 When it happens

When both branches have new commits after they diverged.

main:      A ── B ── E ───────── M
                 \              /
feature:          C ──── D ────

4.2 The three versions

Version Commit
Base (common ancestor) B
Ours (current branch tip) E
Theirs (branch being merged) D

For each change: if only one side changed a region, take that side; if both changed it identically, take it; if both changed it differently → conflict.

git merge-base main feature/orders    # shows B
git merge feature/orders

Merge made by the 'ort' strategy.
8.14

Recursive Merge Strategy

Source S40 · 5. Recursive Merge Strategy

5.1 Definition

recursive was Git's default strategy for merging two branches until Git 2.33. It handles cases where there is more than one common ancestor (criss-cross merges) by first merging those ancestors into a virtual base, then doing the three-way merge. It also detects renames.

5.2 ORT — the modern default

Since Git 2.34, the default is ort ("Ostensibly Recursive's Twin") — a rewrite of recursive that is much faster and handles renames better, with the same results in normal cases. Requests for -s recursive are now served by ort.

5.3 All strategies

Strategy Use
ort (default) Two-branch merges
recursive Legacy name; maps to ort in recent Git
resolve Simple three-way merge, one ancestor only
octopus Merge more than two branches at once (no conflicts allowed)
ours Record a merge but keep the current branch's content entirely
subtree Merge a project into a subdirectory

5.4 Strategy options (-X)

git merge -X ours   feature/x     # on conflicting hunks, prefer current branch
git merge -X theirs feature/x     # on conflicting hunks, prefer incoming branch
git merge -X ignore-space-change feature/x
git merge -X find-renames=40% feature/x

Note -s ours (strategy) discards all of the other branch's changes; -X ours (option) only decides conflicting hunks.

8.15

Merge Commits

Source S40 · 6. Merge Commits

6.1 Definition

A merge commit is a commit with two (or more) parents, recording that two lines of history were joined.

git cat-file -p HEAD

tree 1a2b3c...
parent e5f6a7b...      ← first parent (main)
parent d4e5f6a...      ← second parent (feature)
author ...
Merge branch 'feature/orders'

6.2 Viewing

git log --merges              # only merge commits
git log --no-merges           # exclude them
git log --first-parent main   # mainline history (one commit per merged feature)
git show --stat HEAD          # merge summary

6.3 Custom message

git merge feature/orders -m "Merge feature/orders: orders load pipeline (DE-1423)"
8.16

No-Fast-Forward Merge

Source S40 · 7. No-Fast-Forward Merge

7.1 Definition

--no-ff forces Git to create a merge commit even when a fast-forward is possible.

Fast-forward:    A ── B ── C ── D                         (feature history disappears into main)

--no-ff:         A ── B ─────────── M
                       \          /
                        C ────── D                        (feature visible as a group)

7.2 Example

git merge --no-ff feature/dim-product -m "Merge feature/dim-product"

7.3 Why use it

  • Keeps a record that a feature branch existed.
  • Makes it easy to revert a whole feature (git revert -m 1 <merge>).
  • Standard in Git Flow and the default "Merge" completion type in Azure DevOps PRs.
git config --global merge.ff false   # always create merge commits (optional)
8.17

Squash Merge

Source S40 · 8. Squash Merge

8.1 Definition

A squash merge combines all commits from the source branch into a single new commit on the target branch.

feature:  C (wip) ── D (fix typo) ── E (add tests)
                     ▼ squash
main:     A ── B ── S   ("feat: orders load pipeline")

8.2 Command line

git switch main
git merge --squash feature/orders-load
git commit -m "feat: orders load pipeline (DE-1423)"
git branch -D feature/orders-load     # -D required: Git doesn't see it as merged

8.3 Pros and cons

Pros Cons
Clean main history — one commit per feature Individual commit history of the feature is lost on main
Removes WIP/typo commits Branch not recognised as merged; continuing to use it causes duplicate conflicts
Easy to revert a feature Large squashes are harder to bisect

Hosting platforms provide "Squash and merge" on pull requests.

8.4 Merge type comparison

Type Merge commit History on main Typical use
Fast-forward No Linear, all commits Small, up-to-date branches
Three-way Yes Branching Default when diverged
--no-ff Always Feature grouped Git Flow, auditability
Squash No (one new commit) Linear, one commit per feature Clean history from messy branches
8.18

Merging Feature Branches

Source S40 · 9. Merging Feature Branches

9.1 Recommended steps

# 1. Update main
git switch main
git pull

# 2. Update the feature branch with main and test
git switch feature/orders-load
git merge main               # or: git rebase main
# run tests

# 3. Merge (usually done via Pull Request on the platform)
git switch main
git merge --no-ff feature/orders-load
git push

# 4. Clean up
git branch -d feature/orders-load
git push origin --delete feature/orders-load

9.2 Merging main into a feature branch

Keeping a long-running feature branch current reduces final conflicts:

git switch feature/orders-load
git fetch origin
git merge origin/main

9.3 Preview before merging

git log main..feature/orders-load --oneline      # commits that will be merged
git diff main...feature/orders-load --stat       # changes that will be merged
git merge --no-commit --no-ff feature/orders-load   # merge but stop before committing (inspect, then commit or abort)
8.19

Aborting a Merge

Source S40 · 10. Aborting a Merge

If a merge has conflicts and you want to go back to the state before the merge:

git merge --abort

Other options:

git reset --merge          # similar to --abort
git reset --hard ORIG_HEAD # undo a completed (unpushed) merge

Tip Start merges with a clean working directory (commit or stash first) so --abort can restore everything reliably.

8.20

Understanding Merge Conflicts

Source S40 · 11. Understanding Merge Conflicts

11.1 Definition

A merge conflict occurs when Git cannot automatically decide how to combine changes and needs a human to choose.

11.2 Causes

Conflict type Cause
Content conflict Both branches changed the same lines of the same file
Modify/delete One branch modified a file, the other deleted it
Rename/rename Both branches renamed the same file differently
Rename/modify One renamed, the other modified (usually auto-resolved by rename detection)
Add/add Both branches added a file with the same path but different content
Binary conflict Both changed a binary file (Git can't merge contents)

11.3 What you see

Auto-merging sql/procedures/usp_load_customers.sql
CONFLICT (content): Merge conflict in sql/procedures/usp_load_customers.sql
Automatic merge failed; fix conflicts and then commit the result.

git status

You have unmerged paths.
Unmerged paths:
        both modified:   sql/procedures/usp_load_customers.sql

11.4 Conflict markers

<<<<<<< HEAD
    SELECT * FROM customers WHERE is_active = 1;
=======
    SELECT * FROM customers WHERE status IN ('ACTIVE','VIP');
>>>>>>> feature/vip-customers
Marker Meaning
<<<<<<< HEAD Start of your current branch's version
======= Separator
>>>>>>> branch End of the incoming branch's version
||||||| base (seven pipe characters) (with diff3/zdiff3 style) the original base version 
git config --global merge.conflictstyle zdiff3   # show the base too — makes decisions easier
8.21

Resolving Merge Conflicts

Source S40 · 12. Resolving Merge Conflicts

12.1 Create a conflict to practise

git switch main
git switch -c feature/vip-customers
sed -i "s/status = 'ACTIVE'/status IN ('ACTIVE','VIP')/" sql/procedures/usp_load_customers.sql
git commit -am "Include VIP customers"

git switch main
sed -i "s/status = 'ACTIVE'/is_active = 1/" sql/procedures/usp_load_customers.sql
git commit -am "Use is_active flag"

git merge feature/vip-customers     # CONFLICT

12.2 Resolution steps

  1. Identify conflicted files: git status or git diff --name-only --diff-filter=U.
  2. Understand both sides: git log --merge -p, talk to the other developer if needed.
  3. Edit the file — keep yours, theirs, or combine — and remove all markers:
    SELECT * FROM customers
    WHERE is_active = 1
      AND status IN ('ACTIVE','VIP');
  1. Mark resolved: git add sql/procedures/usp_load_customers.sql
  2. Verify no markers remain: git diff --check / search for <<<<<<<.
  3. Test the result.
  4. Complete: git commit (or git merge --continue).

12.3 Shortcuts

git checkout --ours   path/file    # take current branch version for the whole file
git checkout --theirs path/file    # take incoming version
git restore --source=main path/file
git mergetool                       # open configured visual merge tool

In VS Code, use Accept Current / Accept Incoming / Accept Both or the 3-way Merge Editor.

12.4 Resolving modify/delete conflicts

CONFLICT (modify/delete): sql/views/vw_old.sql deleted in feature/x and modified in HEAD.
  • Keep the file: git add sql/views/vw_old.sql
  • Delete it: git rm sql/views/vw_old.sql

8.23

Best Practices for Merging

Source S40 · 14. Best Practices for Merging
  1. Start with a clean working directory.
  2. Update both branches (git pull) before merging.
  3. Merge into protected branches only through pull requests.
  4. Run tests after merging and after resolving conflicts.
  5. Never commit conflict markers — add a CI check (git diff --check).
  6. Write meaningful merge commit messages that reference tickets.
  7. Choose a consistent merge style for the team (merge, squash, or rebase).
  8. Delete merged branches.
  9. Don't resolve conflicts you don't understand — ask the other author.
  10. Keep main always deployable.

Command reference

git merge <branch>
Syntax
git merge [--ff | --no-ff | --ff-only] [--squash] [-s <strategy>] [-X <option>] [-m <msg>] <branch>…
Purpose
Integrate the history of <branch> into the current branch.
Key parameters
  • --ff (default) — fast-forward when possible, otherwise create a merge commit
  • --no-ff — always create a merge commit, even when fast-forward is possible
  • --ff-only — refuse to merge unless a fast-forward is possible (safe for updating local main)
  • --squash — stage the combined changes but do not commit or record the merge
  • -s ort — merge strategy (default for two heads since Git 2.34)
  • -X ours|theirs — strategy option: prefer one side only for conflicting hunks
Behaviour
Finds the merge base, applies both sides' changes, and either moves the branch pointer (fast-forward) or creates a commit with two parents. Leaves conflict markers and stops if it cannot reconcile overlapping edits.
Expected output
Updating 3f1c2a9..8d4e7b1
Fast-forward
 sql/warehouse/dim_customer.sql | 12 ++++++++++++
 1 file changed, 12 insertions(+)

(or, for a three-way merge)
Merge made by the 'ort' strategy.
Example
git switch main
git pull --ff-only
git merge --no-ff feature/RDP-101-dim-customer -m "Merge RDP-101 customer dimension"
Common mistakes
Merging while the working tree has uncommitted changes; merging into the wrong branch (always check git branch --show-current); expecting -X ours to discard all of the other branch (it only resolves conflicting hunks — non-conflicting changes from the other side are still merged).
Troubleshooting
Commit or stash first. If you merged into the wrong branch and have not pushed: git reset --hard ORIG_HEAD. If already pushed: git revert -m 1 <merge-commit>.
git merge --abort
Syntax
git merge --abort
Purpose
Stop an in-progress merge and try to reconstruct the pre-merge state.
Behaviour
Only valid while MERGE_HEAD exists. Equivalent to git reset --merge. If you had uncommitted changes before starting the merge, they may not be recoverable — that is why you should start merges from a clean tree.
Expected output
(no output on success; `git status` shows the branch clean again)
Example
git merge feature/RDP-104-orders
# CONFLICT ... decide to stop
git merge --abort
git status
Common mistakes
Running git reset --hard instead — this also discards uncommitted work unrelated to the merge.
Troubleshooting
fatal: There is no merge to abort (MERGE_HEAD missing). means no merge is in progress; check git status.
git merge --squash <branch>
Syntax
git merge --squash <branch>
Purpose
Combine all changes of a branch into a single new commit on the current branch.
Behaviour
Updates the index and working tree, does not create a commit and does not record <branch> as a parent. You must run git commit. Afterwards git branch -d <branch> will refuse (branch is "not fully merged") — use -D once you are sure.
Expected output
Squash commit -- not updating HEAD
Automatic merge went well; stopped before committing as requested
Example
git switch main
git merge --squash feature/RDP-112-dq-rules
git commit -m "Add data-quality rules for orders (RDP-112)"
Common mistakes
Continuing to work on the squashed branch and merging it again — Git re-applies the old commits and produces conflicts.
Troubleshooting
Delete a squash-merged branch and start a new branch from the updated main.
git merge-base / git branch --merged
Syntax
git merge-base <a> <b>
git branch --merged [<commit>]
git branch --no-merged [<commit>]
Purpose
Find the common ancestor of two branches; list branches already (or not yet) integrated.
Expected output
3f1c2a9d0b7e5c4a8f2e1d6b9c0a7e3f5d2b1c4e
Example
git merge-base main feature/RDP-101-dim-customer
git branch --merged main      # safe to delete
git branch --no-merged main   # still has unique work
Common mistakes
Running git branch --merged without naming a branch — it compares with the current branch.
git checkout --ours / --theirs <path>
Syntax
git checkout --ours <path>
git checkout --theirs <path>
(Git 2.23+: git restore --ours|--theirs <path>)
Purpose
During a conflicted merge, take one whole side of a file.
Behaviour
In a merge, ours = the branch you are on, theirs = the branch being merged. In a rebase the meaning is swapped (ours = the branch being rebased onto). The file is still unmerged until you git add it.
Example
git checkout --theirs adf/pipeline/pl_load_orders.json
git add adf/pipeline/pl_load_orders.json
Common mistakes
Using it for JSON/ARM files when both sides changed different properties — you silently drop the other side's change.

Continuous project — Stage 3: Branching

Continuous project · Stage 3 — Branching: integrate three parallel features into `main`

Asha (SQL), Ravi (Python) and Meera (ADF) each worked on a branch created from the same main commit.

# 1. Asha's branch is directly ahead of main -> fast-forward is possible,
#    but the team policy is to keep an explicit integration point:
git switch main
git pull --ff-only
git merge --no-ff feature/RDP-101-dim-customer -m "Merge RDP-101: customer dimension"

# 2. Ravi's ingestion branch touches different folders -> clean three-way merge
git merge feature/RDP-102-orders-ingest
#   Merge made by the 'ort' strategy.

# 3. Meera's branch also edited sql/warehouse/dim_customer.sql -> conflict
git merge feature/RDP-103-customer-status
#   CONFLICT (content): Merge conflict in sql/warehouse/dim_customer.sql
git status                       # "both modified: sql/warehouse/dim_customer.sql"
# edit the file: keep Asha's column list AND Meera's Status column
git add sql/warehouse/dim_customer.sql
git diff --cached --check        # no leftover markers / whitespace errors
python -m pytest tests/ -q       # project tests still pass
git commit                       # accept the prepared merge message
git log --oneline --graph -8     # inspect the result
git push origin main
git branch -d feature/RDP-101-dim-customer feature/RDP-102-orders-ingest feature/RDP-103-customer-status

Result: main contains two merge commits and one fast-forward-prevented merge; every feature can be reverted as a unit with git revert -m 1 <merge>.

Real-time scenarios

Source S09, S40 · Two engineers changed the same stored procedure

Both added columns to usp_load_dim_customer. The merge stops with a conflict. Resolution: keep both columns, re-order to match the target table, run the procedure against a dev database, add the file, commit. Lesson: agree file ownership or split large procedures to reduce overlap.

Course addition · A feature merged too early must be removed from `main` (already pushed)

Do not reset shared history. Find the merge commit (git log --merges --oneline) and run git revert -m 1 <merge-sha>. -m 1 tells Git that parent 1 (the mainline) is the version to keep. Note: if the feature is later re-merged, you must first revert the revert, otherwise its earlier commits are considered already merged.

Course addition · ADF JSON conflict after two people edited the same pipeline

ADF stores each pipeline as one JSON file, so concurrent edits of one pipeline conflict even when the changes are logically independent. Resolve by opening both versions, merging activity arrays carefully, validating the JSON (python -m json.tool file.json), and validating the factory in ADF Studio before committing. Long-term fix: one owner per pipeline per sprint (see Chapter 33).

Best practices

Course addition · best practices
  • Start every merge from a clean working tree (git status shows nothing to commit).
  • Update the target first with git pull --ff-only, then merge.
  • Prefer short-lived branches and frequent integration — conflicts grow with branch age.
  • Pick one PR merge style per repository and enforce it in branch protection / branch policies.
  • After resolving conflicts, always run git diff --check and the test suite before committing.
  • Delete merged branches (git branch -d) and enable automatic head-branch deletion on GitHub.

Source S09 · Chapter manual · interview

Interview questions

  1. What is a fast-forward merge? — A branch pointer advances because it has no divergent commits to reconcile.
  2. What is a three-way merge? — Git combines two branch tips using their common ancestor.
  3. What is --no-ff? — It forces a merge commit.
  4. What is squash merge? — It combines changes into one staged snapshot/commit without retaining feature commits as ancestors.
  5. What causes conflicts? — Overlapping or incompatible edits that Git cannot resolve automatically.
  6. How do you abort a merge? — git merge --abort.
  7. What is the modern default merge strategy? — ort for ordinary two-head merges in modern Git.

Beginner
What is the difference between a fast-forward merge and a three-way merge?

Fast-forward happens when the current branch has no commits that the other branch lacks; Git just moves the pointer. A three-way merge is needed when both branches have new commits; Git uses the merge base and both tips and normally records a merge commit with two parents.

What does git merge --abort do?

It stops an in-progress merge (while MERGE_HEAD exists) and tries to restore the state before the merge started.

Intermediate
Why would a team use --no-ff?

To always record an explicit merge commit, so the feature appears as a group of commits that can be reverted with a single git revert -m 1 and the history shows where integration happened.

What does git merge --squash do differently from a normal merge?

It stages the combined result but records no merge relationship; you create one ordinary commit. The feature branch is therefore not considered merged, and its individual commits are not in the target history.

In a merge conflict, what do ours and theirs mean?

Ours is the branch checked out (the target); theirs is the branch being merged. During a rebase the meaning is reversed.

Advanced
What is the ort strategy and how does -X ours differ from -s ours?

ort ("Ostensibly Recursive's Twin") replaced recursive as the default two-head strategy in Git 2.34. -X ours is a strategy option: non-conflicting changes from both sides are merged and only conflicting hunks prefer our side. -s ours is a strategy that ignores the other branch's content completely and just records the merge.

How do you undo a pushed merge commit and why is -m required?

git revert -m 1 <merge>; a merge commit has two parents, so Git must be told which parent is the mainline whose content should be restored.

Scenario
A pull request shows "This branch has conflicts that must be resolved". What do you do locally?

git switch feature/x, git fetch origin, then git merge origin/main (or rebase if the team allows), resolve conflicts, run tests, push the branch. The PR updates automatically.

After merging, a colleague says their changes in config.json disappeared although there was no conflict. What could have happened?

Someone resolved an earlier conflict by taking a whole side (--ours/--theirs or a GUI "accept current"), or used -s ours. Check with git log -p --follow config.json and git show <merge> (combined diff) and restore the lost lines in a new commit.

Key takeaways
  • A merge combines histories using the merge base and two tips; fast-forward only moves a pointer.
  • --no-ff preserves an integration point, --squash compresses a feature into one commit, --ff-only guarantees no merge commit.

  • Undo locally with git reset --hard ORIG_HEAD; undo shared merges with git revert -m 1.
