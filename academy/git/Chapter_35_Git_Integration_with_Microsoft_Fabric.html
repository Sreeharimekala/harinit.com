Learning objectives

Chapter introduction

What it is. Microsoft Fabric Git integration connects a workspace to a branch/folder in Azure DevOps or GitHub. Supported items (notebooks, pipelines, lakehouses, semantic models, reports and more) are serialized as folders of definition files. Changes flow by Commit (workspace → Git) and Update (Git → workspace). Promotion uses deployment pipelines or code-first tools such as fabric-cicd and the Fabric REST APIs.

Why it matters. Fabric is SaaS — without Git, there is no history, review or reproducible promotion of reports and models.

Where it is used. Power BI/Fabric development teams, lakehouse engineering, enterprise BI release management.

In this course's project. Stage 6: workspace RDP-Dev connects to the platform repo folder /fabric on main; Neha branches out to a feature workspace for KPI changes; Prod is deployed with fabric-cicd from the pipeline (or Fabric deployment pipelines Dev → Test → Prod).

Introduction to Fabric Git Integration

Source S40 · 1. Introduction to Fabric Git Integration

1.1 Definition

Fabric Git integration connects a Fabric workspace to a branch (and folder) of a Git repository. Supported Fabric items are serialised into text files (definitions) that can be committed, versioned, reviewed and deployed.

1.2 Key concepts

Concept Meaning
Workspace ↔ branch One workspace connected to one branch/folder at a time
Item definitions Each item stored as a folder of files (e.g. .platform metadata + content files)
Commit Workspace → Git
Update Git → Workspace
Status Each item shows Synced, Uncommitted, Update required, Conflict or Unsupported

1.3 What is in Git — and what isn't

In Git Not in Git
Item definitions: notebooks, data pipelines, semantic models (TMDL), reports (PBIR), lakehouse metadata (not data), warehouse/SQL database projects, environments, Spark job definitions, KQL items, etc. (list keeps growing — check "supported items" in Fabric docs) Data in lakehouses/warehouses/files, connections/credentials, workspace permissions and settings, unsupported item types

1.4 Prerequisites

  • Fabric capacity (or Power BI Premium/PPU depending on items).
  • Tenant admin enables Git integration settings (and GitHub integration if needed).
  • Workspace admin role to connect a workspace; contributors can commit/update per permissions.
  • Access to the Git repository.
35.17

GitHub Integration

Source S40 · 2. GitHub Integration
  • Supported for GitHub.com (cloud) repositories (check docs for GitHub Enterprise support status).
  • Authenticate with a GitHub personal access token (fine-grained recommended: Contents read/write on the repo) or a GitHub connection created in Fabric.
  • Provide repository URL, branch and Git folder.
  • Tenant setting Users can sync workspace items with GitHub repositories must be enabled.

Azure DevOps Integration

Source S40 · 3. Azure DevOps Integration
  • Supported for Azure DevOps Services (cloud) Git repositories.
  • Authentication with the user's Microsoft Entra ID identity (same tenant as Fabric, or cross-tenant with configured connections), or service principal/connection depending on configuration.
  • Provide organisation, project, repository, branch, folder.

Connecting Fabric Workspaces to Git

Source S40 · 4. Connecting Fabric Workspaces to Git

4.1 Steps

  1. Open the workspace → Workspace settings → Git integration.
  2. Choose Azure DevOps or GitHub.
  3. Sign in / add the connection (GitHub: PAT + repo URL).
  4. Select organisation/project/repository (Azure DevOps) or repository URL (GitHub), branch (or create a new branch) and Git folder (e.g. /fabric).
  5. Connect and sync.

4.2 Initial sync direction

  • Empty workspace + populated repo folder → items are created in the workspace from Git.
  • Populated workspace + empty folder → workspace items are committed to Git.
  • Both have content → Fabric asks which direction to sync (workspace → Git or Git → workspace).

4.3 Repository layout example

Workspace Git Synchronization

5.1 Source control panel

Open Source control (button in the workspace toolbar, showing a count of changes):

Tab Direction Purpose
Changes Workspace → Git Items changed in the workspace; select and Commit
Updates Git → Workspace Commits in the branch not yet in the workspace; Update all
Branches — Branch out to a new workspace, switch branch, checkout (depends on version)

5.2 Item status

Status Meaning
Synced Workspace and Git match
Uncommitted changes Edited in workspace, not committed
Update required Git has newer changes
Conflict Changed in both
Unsupported Item type not supported for Git

The workspace shows the connected branch and last sync time/commit.

35.21

Updating Workspace from Git

Source S40 · 6. Updating Workspace from Git
  1. After a PR is merged into the branch the workspace is connected to, the source control icon shows updates.
  2. Source control → Updates → Update all.
  3. Fabric applies the incoming changes: creates, modifies or deletes items in the workspace.

Notes:

  • Update is all-or-nothing for the incoming commits.
  • If the workspace has uncommitted changes to items that also changed in Git → conflict (section 9).
  • Some items need follow-up after update (e.g. refresh a semantic model, rebind connections, publish an environment).
  • Automate updates via the Fabric Git REST APIs (Update From Git) in CI/CD.
35.22

Committing Workspace Changes

Source S40 · 7. Committing Workspace Changes
  1. Edit items in the workspace (notebook, pipeline, report...).
  2. Source control → Changes lists modified/new/deleted items.
  3. Select items, write a commit message (e.g. feat(fabric): add orders silver notebook), Commit.
  4. The commit goes to the connected branch.

Best practice: connect your personal development workspace to a feature branch; commit there; open the PR in Azure DevOps/GitHub; never commit directly to main (protect it).

35.23

Branch Management

Source S40 · 8. Branch Management

8.1 Recommended development pattern — workspace per developer

Repo: main ◄──PR── feature/ravi-orders ◄── Ravi's workspace (WS_RDP_Dev_Ravi)
           ◄──PR── feature/priya-model  ◄── Priya's workspace (WS_RDP_Dev_Priya)
   │
   └── Shared Dev workspace (WS_RDP_Dev) connected to main → Update all after merges

8.2 Branch out

Source control → Branches → Branch out to new workspace (or Branch out to another workspace): creates a new branch from the current one and connects a new/isolated workspace to it — fastest way to get a private development environment.

8.3 Switching / creating branches

  • Workspace settings → Git integration → change branch (all items sync to that branch's state — commit first!).
  • Checkout new branch from the source control panel (useful when resolving conflicts).

8.4 Client-side development

Clone the repo locally, edit item files (e.g. TMDL/PBIP with Power BI Desktop, notebooks in VS Code), commit/push to a branch, then Update the connected workspace.

35.24

Conflict Resolution

Source S40 · 9. Conflict Resolution

9.1 When conflicts occur

An item has uncommitted workspace changes and new Git changes at the same time, or Git contains incompatible changes.

9.2 Options

Method How
Resolve in UI Source control → choose per item: Accept incoming changes (Git wins) or Keep current content (workspace wins), then Update/Commit
Checkout new branch Commit the workspace state to a new branch, then resolve the conflict between branches in Git (PR or locally), merge, and update the workspace
Revert workspace Undo uncommitted changes (Undo in Changes) and update from Git
Resolve in Git Edit item files (JSON/TMDL/PY) locally, merge, push

9.3 Prevention

Workspace per developer, small focused changes, frequent update/commit, avoid editing the same item concurrently (e.g. one semantic model owner per sprint).

Deployment Pipelines

Source S40 · 10. Deployment Pipelines

10.1 Definition

Fabric deployment pipelines move content between stages/workspaces — typically Development → Test → Production (up to 10 stages) — from the Fabric UI or REST API.

10.2 Features

  • Compare stages (differences highlighted per item).
  • Deploy all or selected items to the next stage.
  • Deployment rules — change data source connections or parameter values per stage (e.g. lakehouse/database for Test vs Prod).
  • Deployment history and auto-binding of dependent items within the stage.
  • Permissions per stage (who can deploy to Prod).
  • Automate via REST API (e.g. from Azure Pipelines/GitHub Actions).

10.3 Combining Git and deployment pipelines

Feature workspaces ──Git PR──► main ──► Dev workspace (Git-connected, Update from Git)
                                             │
                               Deployment pipeline: Dev → Test → Prod
                               (rules for data sources; approvals via process/API)
35.26

Fabric CI/CD

Source S40 · 11. Fabric CI/CD

11.1 Common options

Option Description
A. Git + deployment pipelines Dev workspace synced to main; deployment pipelines promote to Test/Prod
B. Git-based per environment Each environment workspace connected to its own branch (e.g. main → Dev, release → Test/Prod) or folder; CI calls the Fabric Git APIs (Update From Git) after merges
C. Build-and-release from repo (code-first) CI/CD deploys item definitions from the repository to non-Git-connected Test/Prod workspaces using the Fabric REST APIs or the open-source fabric-cicd Python library, applying environment-specific parameters

11.2 fabric-cicd example (option C)

pip install fabric-cicd

# deploy/deploy_fabric.py
import sys
from azure.identity import ClientSecretCredential
from fabric_cicd import FabricWorkspace, publish_all_items, unpublish_all_orphan_items

env = sys.argv[1]                      # "TEST" or "PROD"
workspace_ids = {"TEST": "<test-ws-guid>", "PROD": "<prod-ws-guid>"}

credential = ClientSecretCredential(tenant_id="<tenant>", client_id="<sp-id>", client_secret="<from-pipeline-secret>")

ws = FabricWorkspace(
    workspace_id=workspace_ids[env],
    environment=env,                       # selects values in parameter.yml
    repository_directory="fabric",
    item_type_in_scope=["Notebook", "DataPipeline", "Environment", "SemanticModel", "Report"],
    token_credential=credential,
)
publish_all_items(ws)
unpublish_all_orphan_items(ws)            # remove items deleted from the repo

# fabric/parameter.yml — environment-specific find & replace
find_replace:
  - find_value: "11111111-dev-lakehouse-guid"
    replace_value:
      TEST: "22222222-test-lakehouse-guid"
      PROD: "33333333-prod-lakehouse-guid"

(Check the fabric-cicd documentation for the current parameter file schema and authentication options.)

11.3 Azure DevOps pipeline (outline)

trigger:
  branches: { include: [main] }
  paths: { include: [fabric/*] }

stages:
- stage: DeployTest
  jobs:
  - deployment: Test
    environment: fabric-test
    pool: { vmImage: ubuntu-latest }
    strategy:
      runOnce:
        deploy:
          steps:
          - checkout: self
          - script: pip install fabric-cicd azure-identity
          - script: python deploy/deploy_fabric.py TEST
- stage: DeployProd
  dependsOn: DeployTest
  jobs:
  - deployment: Prod
    environment: fabric-prod          # approval
    pool: { vmImage: ubuntu-latest }
    strategy:
      runOnce:
        deploy:
          steps:
          - checkout: self
          - script: pip install fabric-cicd azure-identity
          - script: python deploy/deploy_fabric.py PROD

Use a service principal (tenant setting must allow service principals to use Fabric APIs) and store secrets in Key Vault-linked variable groups or use workload identity federation.

35.27

Managing Semantic Models

Source S40 · 12. Managing Semantic Models

12.1 Format

Semantic models are stored in TMDL (Tabular Model Definition Language) — human-readable, one file per table/role/culture, producing clear diffs:

table Sales
    measure 'Total Sales' = SUM(Sales[amount])
        formatString: "#,0.00"

    column order_id
        dataType: int64
        sourceColumn: order_id

12.2 Workflow

  • Develop with Power BI Desktop projects (PBIP) saving TMDL + PBIR locally → commit → PR; or edit in the Fabric service and commit.
  • Review measure/relationship changes in PR diffs.
  • After deployment: refresh the model; set data source credentials/connections per environment (deployment rules or parameters).
  • Large models: use incremental refresh policies; avoid committing data (.pbix contains data — prefer PBIP).
  • Tools: Tabular Editor, sempy / semantic-link for testing (e.g. Best Practice Analyzer rules in CI).
35.28

Managing Notebooks

Source S40 · 13. Managing Notebooks

13.1 Format

Fabric notebooks are stored as notebook-content.py (source with cell markers and metadata, including default lakehouse binding).

13.2 Practices

  • Parameterise (parameter cell) — environment-specific values injected by pipelines.
  • Keep reusable logic in Environment custom libraries (wheels) or shared notebooks.
  • Default lakehouse binding differs per environment → handle via fabric-cicd parameters, deployment rules, or by referencing lakehouses through parameters/notebookutils.
  • No secrets in code — use Key Vault via notebookutils.credentials.getSecret(...).
  • Clear outputs; review code diffs in PRs.
35.29

Managing Data Pipelines

Source S40 · 14. Managing Data Pipelines

14.1 Format

Fabric data pipelines are stored as pipeline-content.json — similar structure to ADF pipeline JSON.

14.2 Practices

  • Parameterise sources/sinks, workspace and item IDs; avoid hard-coded GUIDs (they differ per environment).
  • Use connections (stored outside Git) for credentials.
  • Replace environment-specific IDs during deployment (parameter.yml find & replace, deployment rules).
  • Schedules are configured per environment (check whether they are part of the definition for your item version).
  • Review activity changes in PR JSON diffs; use naming conventions (PL_, NB_, LH_, SM_, RPT_).
35.30

Fabric Git Limitations and Best Practices

Source S40 · 15. Fabric Git Limitations and Best Practices

15.1 Limitations (verify current documentation — these evolve)

  • Not all item types are supported; unsupported items are not synced.
  • Data is never stored in Git — only definitions.
  • A workspace connects to one branch/folder at a time.
  • Size limits on commits/items and number of items per commit.
  • Some properties (connections, sensitivity labels, certain settings, permissions) are not part of item definitions.
  • Item IDs/references (e.g. default lakehouse GUIDs) differ across workspaces and may need parameter replacement.
  • GitHub support differs from Azure DevOps (e.g. enterprise server options, authentication) — check docs.
  • Renaming/moving items and folder support behaviour depends on version.

15.2 Best practices

  1. Workspace per developer connected to feature branches; shared Dev workspace connected to main.
  2. Protect main with PR policies, reviewers and validation.
  3. Commit small, frequent changes; update often.
  4. Never edit Test/Prod workspaces manually — deploy via deployment pipelines or CI/CD.
  5. Keep environment-specific values in deployment rules/parameter files, not hard-coded.
  6. Secrets in Key Vault/connections — never in notebooks or pipeline JSON.
  7. Use service principals for automation.
  8. Prefer PBIP/TMDL over .pbix for Power BI assets.
  9. Document the branching and deployment model in the README.
  10. Periodically review unsupported items and plan manual or API-based handling for them.

Verified against official documentation (Nov 2026) — Fabric Git providers and limitations

Verified (Microsoft Learn, Nov 2026): providers are Azure DevOps (cloud), GitHub and GitHub Enterprise (cloud), including GitHub Enterprise Cloud with data residency (ghe.com) via tokens. Azure DevOps authentication can use OAuth or a service principal. Limitations include: submodules not supported, sovereign clouds not supported, commit size limited to 125 MB, tenant switches required, and only workspace admins manage the Git connection. Supported item types change frequently — check the list before planning.

Real-time scenarios

Source S36, S40 · Conflict between workspace and Git

The same report was changed in the workspace (uncommitted) and in Git. The Source control pane flags a conflict; choose the workspace or Git version, or branch out, resolve in Git (IDE), merge, and Update.

Course addition · Semantic model refresh credentials missing after deployment

Git stores definitions, not credentials or data. Configure data source credentials/connections in each environment (deployment rules or post-deployment steps); lakehouse data is not in Git.

  3. Branch out to a new workspace, change the notebook, commit, open a PR, merge into main.
  4. In the Dev workspace (connected to main), use Update all.
  5. Create a conflict and resolve it with Accept incoming and with Checkout new branch.
  6. Create a deployment pipeline Dev → Test → Prod with a data-source rule; deploy.
  7. Alternatively, deploy to a Test workspace with fabric-cicd and a parameter.yml.

Synchronizes supported workspace items with a connected Git repository and branch.

No. Git versioning and deployment pipelines are separate but complementary.

Brings incoming commits from the connected branch into the workspace.

Beginner
What does Fabric Git integration connect?

A workspace to a branch and folder of an Azure DevOps or GitHub repository.

Commit vs Update in Fabric?

Commit sends workspace changes to Git; Update applies Git changes to the workspace.

Intermediate
How do you work on a feature without disturbing the Dev workspace?

Branch out to a new workspace connected to a new feature branch, commit there, merge via PR, then Update the Dev workspace.

Deployment pipelines vs Git integration?

Git integration provides version control for a workspace; deployment pipelines promote content between stage workspaces with rules. They are complementary.

Advanced
What is fabric-cicd?

A Python library for code-first deployment of Fabric item definitions from a repository to workspaces, with environment parameterization, suitable for CI/CD pipelines.

Scenario
Prod report points to the Test lakehouse after promotion. Fix?

Add deployment rules (deployment pipelines) or parameter.yml replacements (fabric-cicd) so data source/lakehouse references are environment-specific; redeploy.
