What it is. Versioning Python data-engineering code: project structure (src layout, pyproject.toml), dependency files, virtual environments (never committed), .gitignore, modules and packages, configuration and environment-specific settings, unit testing in CI, and deployment of built packages.

Managing Virtual Environments

Source S40 · 4. Managing Virtual Environments

4.1 Why

Isolate project dependencies from other projects and the system Python.

cd python
python -m venv .venv
source .venv/bin/activate          # Linux/macOS/Git Bash
.venv\Scripts\activate             # Windows CMD/PowerShell
pip install -e ".[dev]"            # editable install of the package + dev tools
deactivate

4.2 Rules

  • Never commit .venv/ — it's large and machine-specific.
  • Recreate from requirements/lock files.
  • Pin the Python version (.python-version for pyenv, requires-python in pyproject.toml).
  • In VS Code select the interpreter: Ctrl+Shift+P → Python: Select Interpreter → .venv.

Managing Python Modules

Source S40 · 6. Managing Python Modules

6.1 Modular design

Small, focused modules with clear responsibilities make reviews easier and conflicts rarer.

# src/rdp_etl/transform.py
from datetime import date
import pandas as pd

def clean_orders(df: pd.DataFrame) -> pd.DataFrame:
    """Remove orders with missing dates or negative amounts and standardise types."""
    out = df.dropna(subset=["order_date"])
    out = out[out["amount"] >= 0].copy()
    out["order_date"] = pd.to_datetime(out["order_date"]).dt.date
    return out

def add_fiscal_year(df: pd.DataFrame) -> pd.DataFrame:
    out = df.copy()
    out["fiscal_year"] = [d.year + 1 if d.month >= 4 else d.year for d in out["order_date"]]
    return out

6.2 Imports and packaging

from rdp_etl.transform import clean_orders
  • Install the package in editable mode for development (pip install -e .).
  • Build a wheel to deploy to Databricks/Fabric/Functions: python -m build.

Managing Environment-Specific Settings

Source S40 · 8. Managing Environment-Specific Settings

8.1 Pattern — base + environment overlay + secrets at runtime

# src/rdp_etl/config.py
import os
from pathlib import Path
import yaml
from azure.identity import DefaultAzureCredential
from azure.keyvault.secrets import SecretClient

CONFIG_DIR = Path(__file__).resolve().parents[2] / "config"

def load_config(env: str | None = None) -> dict:
    env = env or os.getenv("RDP_ENV", "dev")
    with open(CONFIG_DIR / "base.yaml") as f:
        cfg = yaml.safe_load(f)
    with open(CONFIG_DIR / f"{env}.yaml") as f:
        cfg.update(yaml.safe_load(f))
    cfg["env"] = env
    return cfg

def get_secret(cfg: dict, name: str) -> str:
    client = SecretClient(vault_url=cfg["key_vault_url"], credential=DefaultAzureCredential())
    return client.get_secret(name).value

8.2 Rules

  • Same code in every environment; only configuration differs.
  • Environment chosen by an environment variable (RDP_ENV) set by the pipeline/job.
  • Secrets fetched at runtime from Key Vault using managed identity / service principal (DefaultAzureCredential).
  • No if env == "prod": business logic branches scattered in code.

Unit Testing with Git Workflows

Source S40 · 9. Unit Testing with Git Workflows

9.1 Tests

# tests/test_transform.py
import pandas as pd
from rdp_etl.transform import clean_orders, add_fiscal_year

def test_clean_orders_removes_null_dates_and_negative_amounts():
    df = pd.DataFrame({
        "order_id": [1, 2, 3],
        "order_date": ["2026-04-01", None, "2026-03-31"],
        "amount": [100, 50, -5],
    })
    result = clean_orders(df)
    assert list(result["order_id"]) == [1]

def test_add_fiscal_year_april_start():
    df = clean_orders(pd.DataFrame({
        "order_id": [1, 2],
        "order_date": ["2026-04-01", "2026-03-31"],
        "amount": [10, 10],
    }))
    assert list(add_fiscal_year(df)["fiscal_year"]) == [2027, 2026]

PySpark tests use a local session fixture:

# tests/conftest.py
import pytest
from pyspark.sql import SparkSession

@pytest.fixture(scope="session")
def spark():
    return SparkSession.builder.master("local[1]").appName("tests").getOrCreate()

9.2 Tests in the Git workflow

Developer: write code + tests → pre-commit (ruff) → commit → push
PR: CI runs pytest + coverage → required status check → review → merge

Python Deployment Using GitHub Actions

Source S40 · 10. Python Deployment Using GitHub Actions
# .github/workflows/python.yml
name: Python CI/CD

on:
  pull_request:
    paths: ['python/**']
  push:
    branches: [main]
    tags: ['v*.*.*']

permissions:
  contents: read
  id-token: write

jobs:
  test:
    runs-on: ubuntu-latest
    strategy:
      matrix:
        python-version: ['3.10', '3.11']
    defaults:
      run:
        working-directory: python
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-python@v5
        with:
          python-version: ${{ matrix.python-version }}
          cache: pip
      - run: pip install -e ".[dev]"
      - run: ruff check .
      - run: pytest --cov=rdp_etl --cov-report=xml

  build:
    needs: test
    if: github.event_name == 'push'
    runs-on: ubuntu-latest
    defaults:
      run:
        working-directory: python
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-python@v5
        with: { python-version: '3.11' }
      - run: pip install build && python -m build
      - uses: actions/upload-artifact@v4
        with:
          name: rdp-etl-wheel
          path: python/dist/*.whl

  publish:
    needs: build
    if: startsWith(github.ref, 'refs/tags/v')
    runs-on: ubuntu-latest
    environment: prod
    steps:
      - uses: actions/download-artifact@v4
        with: { name: rdp-etl-wheel, path: dist }
      - uses: azure/login@v2
        with:
          client-id: ${{ vars.AZURE_CLIENT_ID }}
          tenant-id: ${{ vars.AZURE_TENANT_ID }}
          subscription-id: ${{ vars.AZURE_SUBSCRIPTION_ID }}
      # Option A: upload wheel to a Databricks Unity Catalog volume / workspace (Chapter 34)
      # Option B: publish to Azure Artifacts feed with twine
      - run: echo "Publish dist/*.whl to the target environment"

Deployment targets for Python data code: Databricks (wheel or bundle), Microsoft Fabric (environment custom libraries), Azure Functions (Azure/functions-action), container images (Docker → ACR → Container Apps/AKS), Azure Artifacts feed.

Best practices

Course addition · best practices
  • src layout + pyproject.toml; installable package; tests next to the package.
  • Never commit virtual environments, caches, build output or .env.
  • Pin/lock dependencies for deployment; update via Dependabot/Renovate PRs.
  • Config via environment variables + per-environment config files without secrets; identities via managed identity/DefaultAzureCredential.
  • Lint + test on every PR; build once, deploy the same wheel everywhere.

No. Question Short answer
1 What should not be committed in a Python project? venvs, caches, build outputs, secrets, data
2 Why pin dependencies? Reproducible builds across machines and CI
3 What is the src layout? Package under src/ so tests use the installed package

Beginner
Should a virtual environment be committed?

No. Commit dependency declarations (pyproject.toml/requirements/lock); each developer and pipeline creates its own environment.

What goes in .gitignore for Python?

.venv/, __pycache__/, *.pyc, caches, dist/, build/, *.egg-info/, .env, coverage output.

Intermediate
How do you manage environment-specific configuration?

Environment variables or per-environment config files without secrets; secrets from Key Vault/managed identity; same code and artifact everywhere.

Why use the src layout?

It ensures tests run against the installed package, not accidental imports from the working directory.

Scenario
Production broke after a dependency released a new major version. How do you prevent this?

Pin/lock dependencies for deployments, let Dependabot open PRs for updates, run tests in CI before merging upgrades, and deploy built artifacts instead of resolving dependencies at deploy time.
