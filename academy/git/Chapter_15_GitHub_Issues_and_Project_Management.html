15.1

What are GitHub Issues?

Source S16 · Chapter manual · 1. What are GitHub Issues?

GitHub Issues are work-tracking records associated with a repository or organization. They can represent bugs, enhancements, technical tasks, questions or operational follow-ups.

Typical issue fields and features

  • Title and description.
  • Assignees responsible for progress.
  • Labels for categorization and priority.
  • Milestones for grouping work toward a target.
  • Comments and references to related code.
  • Links to pull requests and Projects.

Issues provide a visible discussion and history for work. They are not a substitute for a detailed incident-management system where formal incident processes are required.

15.2

Creating issues

Source S16 · Chapter manual · 2. Creating issues
  1. Open the repository and select Issues.
  2. Choose New issue.
  3. Enter a clear, action-oriented title.
  4. Describe the current behavior, expected behavior and business impact.
  5. Add reproduction steps, logs or screenshots only when safe and useful.
  6. Set labels, assignees and milestone as appropriate.
  7. Submit the issue.

Example issue: data quality defect

Title: Duplicate customer keys in daily dimension load ## Problem The daily customer dimension load contains duplicate business keys after the source extract is processed. ## Expected result One deterministic record per business key. ## Actual result Some customer keys appear more than once. ## Validation - Identify duplicate source keys. - Confirm the intended survivor rule. - Add a regression test. ## Impact Downstream customer reporting may be overstated.

Use sanitized examples. Never attach customer PII, production extracts, credentials or restricted logs to an issue unless the approved system and access controls explicitly permit it.

15.3

Assigning issues

Source S16 · Chapter manual · 3. Assigning issues

Assigning an issue makes ownership visible. GitHub supports assigning one or more users depending on repository configuration and current product behavior.

Good assignment practices

  • Assign an accountable owner, not every person who may contribute.
  • Use labels or Projects to identify supporting teams.
  • Reassign when ownership changes and record the reason for handover.
  • Set realistic due dates or milestones using the team's planning process.
  • Review unassigned and stale issues regularly.

Assignment indicates responsibility; it does not by itself guarantee progress or define a service-level commitment.

Issue templates

Source S16 · Chapter manual · 5. Issue templates

Issue templates help requesters provide the information needed to triage a bug or enhancement. GitHub supports issue forms and Markdown templates in the repository's .github directory.

Example bug report template (Markdown)

--- name: Bug report about: Report a reproducible defect title: "[BUG] " labels: bug assignees: "" --- ## Summary Describe the issue. ## Steps to reproduce 1. 2. 3. ## Expected behavior ## Actual behavior ## Environment - Component: - Version: - Environment: ## Evidence Attach sanitized logs or screenshots. ## Impact Describe affected functionality.

For structured forms, GitHub Issue Forms support fields such as text areas, dropdowns and checkboxes. Keep required fields relevant so users can submit issues without unnecessary friction.

15.6

Linking issues with commits

Source S16 · Chapter manual · 6. Linking issues with commits

GitHub can recognize issue references in commit messages and display cross-links between the commit and issue. This improves traceability from a requirement or defect to the code change.

Reference an issue

git commit -m "Handle null customer keys ( #42 )"

A plain issue reference such as #42 can create a link. Closing keywords such as Fixes #42 have special behavior when used in supported contexts.

git commit -m "Fixes #42: handle null customer keys"
A closing keyword in a commit message only closes the issue automatically when the commit reaches the repository's default branch through a supported workflow. Check GitHub's current rules for cross-repository references and branch behavior.
15.7

Linking pull requests with issues

Source S16 · Chapter manual · 7. Linking pull requests with issues

Pull requests can link to issues so reviewers understand why a change is being made. A PR description can use closing keywords.

Fixes #42 Closes #57 Resolves #61

When the PR is merged into the repository's default branch, GitHub can automatically close the linked issue. You can also manually link an issue to a PR without using a closing keyword.

Why link work items?

  • Connect business requirements and defects to implementation.
  • See which PR addresses a particular issue.
  • Track whether work has been merged.
  • Improve auditability and release communication.
15.8

GitHub Projects

Source S16 · Chapter manual · 8. GitHub Projects

GitHub Projects provides a flexible way to plan and track work across issues and pull requests. A Project can be organized with views, fields, filters, grouping and automation.

Common Project capabilities

  • Table view for spreadsheet-like tracking.
  • Board view for status-based workflows.
  • Roadmap view for date-oriented planning, where available.
  • Custom fields such as Status, Priority, Iteration, Estimate and Target date.
  • Saved filters and grouping for different audiences.
  • Automation to update fields or archive completed items, depending on configuration.

A Project can span multiple repositories, which is useful when one delivery initiative requires SQL, application, pipeline and documentation changes.

Reference: Planning and tracking with GitHub Projects.

15.9

Kanban boards

Source S16 · Chapter manual · 9. Kanban boards

A Kanban board visualizes work as cards moving through workflow columns. In GitHub Projects, a board view can group items by a Status field.

Backlog
Not started
Ready
In progress
Review
Done

Example workflow; adapt columns to the team's real process.

Kanban practices

  • Define what each status means.
  • Set work-in-progress limits if the team uses them.
  • Make blockers visible.
  • Keep cards small enough to complete and review.
  • Move items when the state changes, not merely at reporting time.
  • Review aging items and bottlenecks regularly.

Kanban is a flow-management method. A board alone does not create a disciplined process; the team must agree on policies and maintain the board.

15.10

Managing sprint activities

Source S16 · Chapter manual · 10. Managing sprint activities

Teams using Scrum-like iterations can configure GitHub Projects with an Iteration field and a view filtered to the active sprint. GitHub Project capabilities and iteration settings may vary over time.

Example sprint workflow

  1. Backlog refinement: clarify issue scope, acceptance criteria and dependencies.
  2. Sprint planning: select work based on capacity and priority.
  3. During sprint: update status, record blockers and link PRs.
  4. Daily coordination: review work in progress and resolve impediments.
  5. Sprint review: demonstrate completed work and record feedback.
  6. Retrospective: capture improvement actions as issues.

Example project fields

FieldExample valuesWhy it helps
StatusBacklog, Ready, In progress, Review, DoneShows workflow state
PriorityP0, P1, P2, P3Supports ordering
IterationSprint 14, Sprint 15Groups time-boxed work
Estimate1, 2, 3, 5, 8Optional sizing
OwnerTeam memberMakes accountability visible
ComponentSQL, ADF, Databricks, FabricSupports filtering
Do not use estimates as a substitute for capacity planning or as an individual performance score. Keep sprint commitments realistic and account for support work and unplanned incidents.
15.11

Tracking development progress

Source S16 · Chapter manual · 11. Tracking development progress

GitHub provides several ways to understand progress: issue states, pull-request states, Project fields, milestones, review status and automation checks.

Useful team indicators

  • Open issues by priority and component.
  • Items blocked or waiting for review.
  • Work completed within an iteration or milestone.
  • Pull-request review time and aging.
  • Build and test success rates.
  • Work in progress and items carried over.

Use metrics to identify workflow bottlenecks and improve delivery. Avoid treating raw issue counts or commit counts as direct measures of individual productivity.

Example weekly review

QuestionEvidence to inspect
Are priorities clear?Issue labels, milestone and Project priority.
Is work moving?Cards in progress, review and blocked states.
Are changes safe?PR approvals, test checks and deployment outcomes.
Where are delays?Aging items, review queues and dependencies.
15.12

GitHub Discussions

Source S16 · Chapter manual · 12. GitHub Discussions

GitHub Discussions provides a forum-style space for conversations that are not necessarily actionable work items. It is useful for questions, ideas, announcements and community knowledge sharing.

FeatureBest suited for
IssuesTrackable work: bug, task, enhancement or action with ownership.
DiscussionsOpen-ended questions, proposals, announcements and knowledge exchange.
Pull requestsReview and integrate a concrete code change.

Example categories

  • Q&A — technical questions and accepted answers.
  • Ideas — proposals for future improvements.
  • Announcements — project updates and release news.
  • General — open-ended community discussion.

A discussion can be converted or linked to an issue when the conversation results in actionable work. Use moderation and category settings appropriate to the project.

Reference: GitHub Discussions documentation.

Linking Issues with Commits

Source S40 · 6. Linking Issues with Commits

Reference an issue number in a commit message to create a link in the issue's timeline:

git commit -m "fix(sql): route null order dates to quarantine (#42)"

Other repositories: company/other-repo#42.

Closing keywords in a commit message close the issue when the commit reaches the default branch:

close, closes, closed, fix, fixes, fixed, resolve, resolves, resolved

Fixes #42"

GitHub Projects

Source S40 · 8. GitHub Projects

8.1 Definition

GitHub Projects is a flexible planning tool — a spreadsheet/board/roadmap built on top of issues and pull requests, which can span multiple repositories in an organisation or user account.

8.2 Creating a project

Your profile or Organization → Projects → New project → choose a template (Team planning, Kanban, Feature release, Roadmap) or blank.

8.3 Key concepts

Concept Description
Items Issues, PRs, or draft items
Fields Built-in (Assignees, Labels, Milestone, Repository) and custom (Status, Priority, Estimate, Iteration, Start/Target date, Team)
Views Table, Board, Roadmap; filtered, grouped, sorted; saved as tabs
Workflows Built-in automations (item added → set Status; PR merged → Done; issue closed → Done; auto-add from repo filter; auto-archive)
Insights Charts (burn-up, items by status/assignee)

8.4 Adding items

  • In the project: type # and search issues/PRs, or paste a URL.
  • From an issue sidebar → Projects.
  • Auto-add workflow: e.g. add all issues with label area:adf from retail-data-platform.

Managing Sprint Activities

Source S40 · 10. Managing Sprint Activities

10.1 Iterations

Add an Iteration field (e.g. 2-week sprints, starting Monday). GitHub creates Sprint 1, Sprint 2, ... and supports breaks.

10.2 Sprint workflow

  1. Backlog refinement — create/label issues, add Estimate (story points) and Priority.
  2. Sprint planning — set Iteration = current sprint for chosen items; check total estimate vs capacity (table view grouped by assignee, with field sum).
  3. Daily stand-up — Board view filtered to iteration:@current.
  4. Sprint review — filter iteration:@current status:Done.
  5. Retrospective — record actions as issues or in Discussions.
  6. Carry over — move unfinished items to the next iteration.

Useful filters: iteration:@current, iteration:@next, assignee:@me, -status:Done.

Best practices

Course addition · best practices
  • One issue per deliverable; acceptance criteria in the issue.
  • Consistent label taxonomy and milestones per release.
  • Always link PRs with closing keywords; branch names contain the issue/ticket ID.
  • Use Projects automation instead of manual column moves.
  • Use Discussions for questions/ideas, issues for actionable work.

A grouping of issues and PRs associated with a target or delivery objective.

5. What is an issue template?

A reusable structure that helps requesters provide consistent information.

6. How can a commit reference an issue?

Include the issue number, such as #42, in the commit message.

7. What does Fixes #42 do?

In supported contexts, it links the issue and can automatically close it when the commit reaches the default branch.

8. How do you link a PR to an issue?

Reference the issue in the PR description; closing keywords can close it when the PR is merged into the default branch.

9. What is GitHub Projects?

A flexible planning and tracking tool with views, fields, filters and automation.

10. What is a Kanban board?

A visual workflow board where cards move through defined status columns.

11. Can GitHub Projects support sprint planning?

Yes, teams can configure iteration fields and views to support sprint-like planning.

12. What should be tracked during a sprint?

Status, ownership, priority, blockers, review progress and completed outcomes.

13. What is a useful development progress metric?

For example, aging work items, review wait time, blocked work or test success rate.

14. Difference between Issues and Discussions?

Issues track actionable work; Discussions support open-ended conversation and knowledge sharing.

15. Should commit count be used to measure developer performance?

No. It is a weak proxy; use delivery outcomes and team workflow signals responsibly.

Intermediate
What is the difference between labels and milestones?

Labels classify (type, area, priority); milestones group issues/PRs toward a target date or release and show progress.

What does GitHub Projects offer beyond a Kanban board?

Custom fields (iteration, estimate, single-select), table and roadmap views, filters, charts and built-in automations, across multiple repositories.

Search commits and PRs for the ID (git log --grep "RDP-107"), open the linked PR from the issue's Development section, and list the merge commit(s); the release notes show which version included it.
