2.1

What is Git?

Source S03 · Chapter manual · 1. What is Git?

Definition

Git is a free, open-source, distributed version control system (DVCS) used to track changes in files and coordinate work among multiple people. It was designed to handle projects of different sizes with speed and reliability.

Git records project history through commits. A repository can contain files, branches, tags, and the history of changes. Developers can work in their local repositories and exchange changes with remote repositories.

What problems does Git solve?

  • Tracks how files change over time.
  • Helps developers work on separate features using branches.
  • Supports combining changes from different contributors.
  • Allows developers to inspect and compare committed versions.
  • Supports local commits without an internet connection.
  • Connects local work with shared remote repositories.

Example

Suppose you are developing a customer data application. You create customer.py, then add validation, logging, and database integration. Git lets you record these milestones as commits rather than maintaining manually named copies of the file.

git init
git add customer.py
git commit -m "Add customer module"

# Make another change, then record it
git add customer.py
git commit -m "Add customer validation"
Important: Git is the version control engine. GitHub, GitLab, Bitbucket, and Azure Repos are platforms that can host Git repositories and provide collaboration features. Git does not require GitHub.
2.2

History and Evolution of Git

Source S03 · Chapter manual · 2. History and Evolution of Git

Background: Linux kernel development

Before Git, the Linux kernel development community used a combination of tools and workflows to coordinate a large, distributed group of contributors. In the early 2000s, the community used BitKeeper, a proprietary distributed version control system, under a no-cost arrangement.

In 2005, the relationship around the use of BitKeeper changed. The Linux kernel community needed a replacement that could support its scale, distributed workflow, speed, and integrity requirements.

Creation of Git

Linus Torvalds created Git in 2005 to support Linux kernel development. Git was designed around fast performance, distributed development, strong data integrity, and efficient handling of large projects with many contributors.

High-level timeline

PeriodMilestone
Before 2005The Linux kernel community used BitKeeper and other development practices to coordinate contributions.
2005Linus Torvalds created Git for Linux kernel development.
2005 onwardGit became an open-source project and grew beyond its original use case.
2008GitHub launched as a hosted platform for Git repositories and collaboration.
2010s onwardGit became a widely adopted foundation for software development, code review, and CI/CD workflows.
TodayGit is used across application development, cloud engineering, data platforms, infrastructure as code, and open-source projects.

Why Git became widely adopted

  • Developers can work with repository history locally.
  • Branching and merging support parallel development.
  • It is open source and runs on major operating systems.
  • It integrates with many hosting, IDE, and automation platforms.
  • It supports both small projects and very large codebases.
Git and GitHub are different milestones: Git was created in 2005; GitHub launched in 2008 and provides a hosted collaboration platform for Git repositories.
2.3

Why Was Git Developed?

Source S03 · Chapter manual · 3. Why Was Git Developed?

Git was created to meet the demanding requirements of Linux kernel development. The project involved a large number of contributors, frequent changes, and a need to integrate work efficiently across a distributed community.

Key design requirements

  1. Performance: common operations needed to be fast, including history inspection, comparisons, and branching.
  2. Distributed development: developers needed complete local repositories so they could work independently.
  3. Integrity: Git needed a reliable way to identify stored content and detect unexpected changes.
  4. Efficient branching and merging: contributors needed to develop and integrate work in parallel.
  5. Scalability: the system needed to support a large project and many contributors.
  6. Open development: the tool needed to be available to the community under an open-source license.

How those requirements appear in Git today

Original needGit capability
Work independentlyLocal repositories and local commits
Integrate parallel workBranches, merges, rebases, and cherry-picks
Inspect project historyCommits, logs, diffs, and references
Protect data integrityContent-addressed object storage and object checksums
Handle large development activityEfficient local operations and repository storage mechanisms
2.4

Features of Git

Source S03 · Chapter manual · 4. Features of Git

4.1 Distributed architecture

Each clone is a repository with the project history needed for normal Git work. Developers can make commits locally and synchronize later.

4.2 Local operations

Commands such as git status, git diff, and git log usually operate locally and do not need a network connection.

4.3 Branching and merging

Branches let developers isolate work. Changes can later be merged into another branch.

git branch feature/customer-validation
git switch feature/customer-validation
# Make changes and commit them
git switch main
git merge feature/customer-validation

4.4 Data integrity

Git identifies objects using content-derived hash identifiers. Modern Git repositories use SHA-1 by default for compatibility, and Git also supports repositories initialized with SHA-256 object format. Hashes help identify objects and detect accidental corruption; they should not be treated as a substitute for security controls.

4.5 Staging area

Git provides an intermediate area called the index or staging area. You choose which changes should be included in the next commit.

4.6 Commit history

Each commit records a snapshot of the project, metadata such as author and commit message, and links to parent commit(s).

4.7 Multiple collaboration platforms

Git can work with remote repositories hosted on GitHub, GitLab, Bitbucket, Azure Repos, or a server managed by an organization.

4.8 Open source and cross-platform

Git is open-source software and is available for Windows, Linux, and macOS.

4.9 Flexible workflows

Teams can use feature branching, Git Flow, GitHub Flow, trunk-based development, or a workflow tailored to their release process.

4.10 Tool integration

Git integrates with editors, IDEs, code review tools, build systems, test automation, and CI/CD platforms.

2.5

Git Architecture

Source S03 · Chapter manual · 5. Git Architecture

Understanding Git architecture is essential because it explains where changes exist before and after a commit.

5.1 The four main areas

  1. Working tree: the checked-out files and folders that you view and edit.
  2. Staging area (index): the proposed content for the next commit.
  3. Local repository: the committed objects and history stored in the .git directory.
  4. Remote repository: another repository, usually hosted on a server or platform, used to exchange work with others.
YOUR LOCAL COMPUTER ┌─────────────────────────────────────────┐ │ Working tree │ │ Edit files │ │ │ │ │ │ git add │ │ ▼ │ │ Staging area (index) │ │ │ │ │ │ git commit │ │ ▼ │ │ Local repository (.git) │ └───────────────────┬─────────────────────┘ │ git push / fetch ▼ Remote repository (GitHub / Azure Repos)

5.2 How data moves through the areas

CommandTypical effect
git statusShows the state of the working tree and staging area.
git add fileStages the current content of the file.
git commitCreates a commit from the staged snapshot.
git pushTransfers local commits to a remote repository.
git fetchDownloads remote objects and updates remote-tracking references without integrating them into the current branch.
git pullFetches and then integrates changes into the current branch, usually by merge or rebase depending on configuration and options.

5.3 The .git directory

When you initialize or clone a repository, Git creates a .git directory. This is where Git stores repository data and metadata.

Typical internal components include:

ComponentPurpose
objects/Stores Git objects such as blobs, trees, commits, and tags.
refs/Stores references such as branch and tag references.
HEADIndicates the current checkout position, commonly a branch reference.
indexStores the staging area information.
configContains repository-specific configuration.
logs/Contains reference logs when reflogs are enabled for those references.
Note: The exact contents of .git can vary by repository format, Git version, and configuration. Do not manually edit internal files unless you know precisely what you are doing.
2.6

How Git Works Internally

Source S03 · Chapter manual · 6. How Git Works Internally

Git stores repository data as objects. The main object types are blob, tree, commit, and annotated tag.

6.1 Blob object

A blob stores the content of a file. It stores file data, not the filename or directory path. The tree object records the name and relationship to the blob.

Example: the text content of customer.sql is stored as a blob object. If another file has identical content, Git can reuse the same object.

6.2 Tree object

A tree represents a directory snapshot. It contains entries that associate names and file modes with blob objects or other tree objects.

A tree helps Git represent the directory structure of a project at a particular commit.

6.3 Commit object

A commit points to a top-level tree and records metadata such as author, committer, timestamp, message, and parent commit reference(s).

A normal commit usually has one parent. A merge commit usually has two or more parents. The first commit in a repository has no parent.

6.4 Tag object

An annotated tag object can point to another Git object, usually a commit, and include a tagger, date, message, and optional signature. A lightweight tag is simply a reference to an object and does not create a separate tag object.

6.5 How the objects relate

Commit object (message, author, parent, tree) | ▼ Tree object / | \ ▼ ▼ ▼ Blob Blob Tree (file A) (file B) | ▼ Blob (file C)

6.6 Content-addressed storage

Git calculates an object identifier from an object's type, size, and content. The identifier is used to locate that object. This means object identity is based on content rather than a user-assigned filename.

6.7 Snapshot-based model

Git is commonly described as snapshot-based. A commit records the state of the tracked project at that point in history. Git uses object reuse and compression to store data efficiently; it does not simply save a full independent copy of every file for every commit.

6.8 References and HEAD

  • Branch: a movable reference that normally points to the latest commit on that line of development.
  • Tag: a reference commonly used to mark a release or important point in history.
  • HEAD: identifies the current checkout position. In a normal branch checkout, HEAD points symbolically to that branch.
  • Remote-tracking branch: a local reference that records the last known position of a branch on a remote, such as origin/main.

6.9 Explore Git internals with commands

# Show the current repository state
git status

# Display commit history
git log --oneline --graph --decorate --all

# Show the current HEAD reference
git symbolic-ref HEAD

# Display the object type for a commit
git cat-file -t HEAD

# Display a commit object's contents
git cat-file -p HEAD

# Show files and object identifiers in the current tree
git ls-tree HEAD

Some commands require an initialized repository with at least one commit. git symbolic-ref HEAD may behave differently when HEAD is detached.

2.7

Git Workflow

Source S03 · Chapter manual · 7. Git Workflow

A Git workflow is the sequence of steps a developer or team follows to make, record, share, review, and integrate changes.

7.1 Basic local workflow

Create / edit files ↓ Inspect changes (git status / git diff) ↓ Stage selected changes (git add) ↓ Commit changes (git commit) ↓ Inspect history (git log)

7.2 Collaborative workflow

Clone or update repository ↓ Create or switch to a feature branch ↓ Make changes and test ↓ Stage and commit ↓ Push branch to remote ↓ Create pull request ↓ Review and address feedback ↓ Merge approved changes ↓ Deploy through release process

7.3 Example commands

# Clone a remote repository
git clone <repository-url>

# Create and switch to a feature branch
git switch -c feature/customer-validation

# Check status
git status

# Stage a selected file
git add customer.py

# Commit the change
git commit -m "Add customer validation"

# Push the branch to the remote
git push -u origin feature/customer-validation

7.4 Why use branches?

Branches allow developers to isolate work from the main development line. A feature can be developed, tested, and reviewed before integration. Branching does not automatically guarantee conflict-free work; overlapping changes may still need to be reconciled.

7.5 Common workflow models

WorkflowDescription
Centralized workflowDevelopers collaborate around a shared main branch, often with direct commits or controlled reviews.
Feature branch workflowEach feature or fix is developed in a separate branch and integrated after review.
Git FlowA structured model using long-lived branches such as main and develop, plus feature, release, and hotfix branches.
GitHub FlowA lightweight branch-based workflow centered on short-lived branches and pull requests.
Trunk-based developmentDevelopers integrate small changes frequently into a shared trunk, often using short-lived branches and feature flags.

What is Git?

Source S40 · 1. What is Git?

1.1 Definition

Git is a free and open-source distributed version control system (DVCS) designed to track changes in files and coordinate work among multiple people, handling everything from small scripts to very large projects with speed and efficiency.

1.2 Key characteristics

  • Distributed — every developer's clone contains the full project history.
  • Snapshot-based — each commit stores a snapshot of the whole project (unchanged files are referenced, not copied).
  • Local-first — almost every operation (commit, log, diff, branch, merge) runs on your machine without a network.
  • Integrity — every object is identified by a cryptographic hash; any corruption is detected.
  • Branch-friendly — creating, switching and merging branches is fast and cheap.

1.3 Snapshots, not differences

Many older systems (CVS, SVN) store a base file plus a list of changes (deltas) over time. Git thinks of data as a series of snapshots:

Delta-based (SVN):        Snapshot-based (Git):

Version 1: File A         Commit 1: [A1] [B1] [C1]
Version 2: Δ A            Commit 2: [A2] [B1] [C1]   ← B and C unchanged: linked, not copied
Version 3: Δ A, Δ C       Commit 3: [A2] [B1] [C2]

(Internally Git still compresses similar objects using deltas inside packfiles — but conceptually every commit is a full snapshot.)

1.4 Real-time example

You run git commit after editing usp_load_customers.sql. Git:

  1. Stores the new content of usp_load_customers.sql as an object.
  2. Records a snapshot (tree) of the entire project, re-using objects for files that didn't change.
  3. Creates a commit pointing to that snapshot, with your name, the time, a message and the previous commit.

You can return to that exact project state at any time.

2.1 Background

The Linux kernel is one of the largest open-source projects in the world, with thousands of contributors.

Why Was Git Developed?

Source S40 · 3. Why Was Git Developed?

3.1 The immediate reason

When the Linux kernel lost free access to BitKeeper, the community needed a replacement. None of the available free systems met the kernel's requirements, so Linus Torvalds built one.

3.2 Design goals

Goal Meaning How Git achieves it
Speed Operations must be fast, even for huge projects Local operations, efficient storage, compressed packfiles
Simple design A small, clear data model Four object types (blob, tree, commit, tag) and references
Non-linear development Thousands of parallel branches Branches are lightweight pointers; powerful merging
Fully distributed No dependency on one central server Every clone is a complete repository
Large project support Handle the Linux kernel efficiently in speed and size Content-addressed storage, delta compression
Data integrity Detect corruption or tampering Every object named by a hash of its content

3.3 Problems Git solved compared with older tools

  • Slow, server-dependent operations (SVN/CVS)
  • Expensive, painful branching and merging
  • A single point of failure (central server)
  • No offline work
  • Proprietary licensing (BitKeeper)

Features of Git

Source S40 · 4. Features of Git

4.1 Distributed architecture

Every clone is a full backup of the repository, including all history. You can work, commit, branch and view history without a network.

4.2 Speed and performance

Because operations are local, commands like git log, git diff and git commit are near-instant.

4.3 Branching and merging

Branches cost almost nothing to create. Teams use feature branches, release branches and hotfix branches freely. Git has sophisticated merge algorithms (three-way merge, ort strategy, rename detection).

4.4 Staging area

Git has an intermediate area (the index) where you prepare exactly what goes into the next commit — even parts of a file.

4.5 Data integrity

Every file, directory and commit is checksummed (SHA-1, with SHA-256 support). It is impossible to change content without Git knowing.

4.6 Non-linear development

Multiple lines of development can exist and be combined in many ways (merge, rebase, cherry-pick).

4.7 Free and open source

Git is licensed under GPL v2 — free to use, study and modify.

4.8 Cross-platform

Runs on Windows, Linux and macOS, with identical commands.

4.9 Efficient storage

Identical files are stored only once; packfiles compress history.

4.10 Large ecosystem

GitHub, GitLab, Bitbucket, Azure Repos, VS Code, Visual Studio, JetBrains IDEs, CI/CD systems and cloud data services all integrate with Git.

4.11 Security features

Signed commits and tags (GPG or SSH), protected branches on hosting platforms, and hooks for policy enforcement.

Feature Benefit to a Data Engineer
Distributed Work on SQL/Python scripts offline
Branching Develop a new pipeline without breaking production
Staging area Commit the SQL change and the Python change separately
Integrity Trust that the deployed code is exactly what was reviewed
Ecosystem Connect ADF, Databricks and Fabric directly to the repo

2.16

How Git Works Internally

Source S40 · 6. How Git Works Internally

6.1 Content-addressable storage

Git is, at its core, a key–value database. You give it content; it stores it and returns a key — the hash (SHA-1, 40 hex characters) of that content. The same content always produces the same key.

echo "hello" | git hash-object --stdin
# ce013625030ba8dba906f756967f9e9ca394464a

6.2 Four object types

Object Stores
Blob The contents of a file (no filename)
Tree A directory: names, permissions and pointers to blobs/sub-trees
Commit Pointer to the top tree + parent commit(s) + author + committer + message
Tag An annotated, named pointer to an object (usually a commit) 
commit a1b2c3 ──► tree (project root)
   │                 ├── blob  README.md
   │                 └── tree  sql/
   │                         └── blob usp_load_customers.sql
   └── parent ──► commit 9f8e7d ──► tree ...

6.3 References

  • A branch is a small file in .git/refs/heads/ containing a commit hash.
  • HEAD is a file (.git/HEAD) that points to the current branch.
  • A tag is a reference in .git/refs/tags/.

6.4 What happens during git add and git commit

  1. git add file.sql → Git compresses the file content, stores it as a blob in .git/objects, and records the path + blob hash in the index.
  2. git commit → Git builds tree objects from the index, creates a commit object pointing to the root tree and the previous commit, and moves the current branch reference to the new commit.

(Explored in depth in Phase 7.)

Beginner
What are the three local areas in Git?

The working tree (files you edit), the staging area or index (what will go into the next commit) and the local repository (.git, the committed history).

Who created Git and why?

Linus Torvalds in 2005, after the Linux kernel project lost free use of BitKeeper; he needed a fast, distributed system with strong integrity.

Intermediate
Why is Git called "distributed"?

Every clone contains the full history and can commit, branch and merge independently; synchronization with other repositories is explicit (fetch/push).

How does Git ensure data integrity?

Every object is addressed by a hash of its content; commits include the hashes of their tree and parents, so altering history changes all subsequent IDs and is detectable (git fsck).

Advanced
What is changing in Git 3.0?

The documented breaking changes include main as the default initial branch name, SHA-256 as the default hash for new repositories and the reftable format as the default reference backend. Existing SHA-1 repositories continue to work. (Release date not fixed at the time of writing.)

Scenario
A data engineer asks why notebooks should be in Git if Databricks already keeps revision history. What do you answer?

Workspace revision history is per-notebook and per-workspace; Git gives branching, reviews, history across all assets (SQL, ADF, notebooks), tags for releases and CI/CD deployment to other environments.

Key takeaways
  • Git is a distributed, snapshot-based VCS created in 2005; it is maintained by Junio C Hamano and a large community.
