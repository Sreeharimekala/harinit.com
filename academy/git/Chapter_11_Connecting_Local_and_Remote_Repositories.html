11.1

Connecting a local repository to GitHub

Source S12 · Chapter manual · 1. Connecting a local repository to GitHub

Assume you already have a project on your computer and want to publish it to a new GitHub repository. The local project has its own Git history, and the GitHub repository will become a remote destination.

Step 1 — Create an empty remote repository

On GitHub, create a repository and copy its HTTPS or SSH URL. If you already have local project files and commits, creating the remote without an initial README, license, or .gitignore avoids an unnecessary unrelated initial history.

Step 2 — Open your local project folder

cd C:\Projects\CustomerETL

# Confirm that this is a Git repository
git status

Step 3 — Add the GitHub repository as a remote

# HTTPS example
git remote add origin https://github.com/your-org/CustomerETL.git

# SSH example
git remote add origin git@github.com:your-org/CustomerETL.git

Step 4 — Confirm the branch name and push

git branch -M main
git push -u origin main

The -u option sets the upstream tracking relationship for the local branch. On later pushes and pulls, Git can often infer the remote branch.

Expected result: Your local commits are uploaded to the remote main branch, and your local main branch tracks origin/main.
11.2

Adding remote repositories

Source S12 · Chapter manual · 2. Adding remote repositories

A remote is a named reference to another Git repository. You can configure more than one remote for a local repository—for example, a personal fork and the original organization repository.

Syntax

git remote add <remote-name> <repository-url>

Examples

# Add the primary shared repository
git remote add origin https://github.com/company/CustomerETL.git

# Add another remote, perhaps your fork or a secondary server
git remote add backup https://github.com/my-account/CustomerETL.git

Remote names are labels chosen locally. origin is conventional, but it is not a reserved keyword.

Verify the remote

git remote
git remote -v
Adding a remote does not upload or download files. It only records the remote name and URL in your local Git configuration.
11.3

Understanding origin

Source S12 · Chapter manual · 3. Understanding origin

origin is the conventional default name Git assigns to the remote when you clone a repository. When you manually connect a local repository, you commonly choose the same name.

Local repository
CustomerETL
origin →
GitHub repository
company/CustomerETL

Think of origin as a nickname for a repository URL. You can inspect it, rename it, or remove it.

# View origin URL
git remote get-url origin

# View all remote URLs
git remote -v

# Push local main to origin's main
git push origin main

Do not confuse origin with a branch. origin is a remote name; origin/main is a remote-tracking branch reference.

11.4

Understanding upstream

Source S12 · Chapter manual · 4. Understanding upstream

The word upstream is used in two related Git contexts:

  1. Branch upstream/tracking branch: The remote branch that a local branch is configured to track, such as local main tracking origin/main.
  2. Upstream remote in a fork workflow: A remote commonly named upstream that points to the original repository from which your fork was created.

Branch tracking example

# Push and set upstream tracking on first push
git push -u origin main

# See tracking information
git branch -vv

# Push or pull without specifying remote and branch
git push
git pull

Fork workflow example

Original project
upstream
→ fork
Your hosted fork
origin
→ clone
Your local repo
# Your fork is normally origin
git remote add origin https://github.com/my-account/project.git

# Original repository is added as upstream
git remote add upstream https://github.com/original-owner/project.git

# Download original repository updates
git fetch upstream
The remote name upstream is a convention, not a special Git keyword. In a normal non-fork project, your local branch may track origin/main and that is also its upstream branch.
11.5

Viewing remote repositories

Source S12 · Chapter manual · 5. Viewing remote repositories

Use these commands to inspect remote names, URLs, and tracking branches.

CommandPurpose
git remoteList configured remote names.
git remote -vShow fetch and push URLs for each remote.
git remote show originShow remote details, tracked branches, and push/pull configuration (may contact the remote).
git branch -rList remote-tracking branches known locally.
git branch -vvShow local branches and their upstream tracking branches.
git remote get-url originPrint the fetch URL for a remote.
git remote -v
git remote show origin
git branch -r
git branch -vv

Remote-tracking references such as origin/main are local records of the last fetched state of the remote branch. They are updated by fetch operations, not by continuously monitoring the server.

11.6

Changing remote URLs

Source S12 · Chapter manual · 6. Changing remote URLs

If a repository moves to a new URL, or you want to change from HTTPS to SSH, update the remote URL rather than deleting and recreating the remote.

# Change origin URL
git remote set-url origin git@github.com:company/CustomerETL.git

# Verify the new URL
git remote -v

Change fetch and push URLs separately (advanced)

# Set a separate push URL
git remote set-url --push origin <push-url>

# Inspect fetch and push URLs
git remote -v

Most users should use the same fetch and push URL unless there is a specific organizational workflow requiring separate endpoints.

11.7

Removing remote repositories

Source S12 · Chapter manual · 7. Removing remote repositories

Remove a remote configuration when it is no longer needed.

# Remove the remote named backup
git remote remove backup

# Alternative syntax
git remote rm backup

# Verify
git remote -v

Removing a remote does not delete the hosted repository and does not delete your local commits. It removes the local configuration for that remote and its associated remote-tracking references.

Before removing a remote, confirm that you no longer need it for fetch, push, or collaboration. Removing origin does not remove your working files or local Git history.
11.8

Pushing local code to GitHub

Source S12 · Chapter manual · 8. Pushing local code to GitHub

git push sends local commits to a remote repository. A push updates a remote branch when Git can apply the update safely and the server permits it.

First push and set tracking

git push -u origin main

Push a branch

git switch -c feature/customer-validation
# edit, stage, and commit
git add .
git commit -m "Add customer validation checks"

git push -u origin feature/customer-validation

Push later commits

git push

Push all local branches (use deliberately)

git push --all origin

Tags are pushed separately unless included explicitly:

git push origin v1.0.0
# Or push all local tags
git push origin --tags
Avoid casual force pushes. A normal push may be rejected if the remote has commits you do not have. Fetch and integrate those changes rather than overwriting teammates' work. If history rewriting is required and authorized, prefer --force-with-lease over plain --force, and coordinate with collaborators.
11.9

Pulling code from GitHub

Source S12 · Chapter manual · 9. Pulling code from GitHub

git pull fetches remote changes and then integrates them into the current branch. Depending on configuration and options, integration may use merge or rebase.

# Pull the configured upstream branch
git pull

# Explicit remote and branch
git pull origin main

# Fetch and rebase local commits on top of remote updates
git pull --rebase origin main

Before pulling

  • Check the current branch using git status.
  • Preserve or commit local changes that might conflict.
  • Confirm you are pulling the intended remote and branch.
  • Follow your team's merge-versus-rebase policy.
A pull is not simply a download. It also integrates the fetched changes into your current branch, which can create a merge commit or trigger conflict resolution.
11.10

Fetching remote changes

Source S12 · Chapter manual · 10. Fetching remote changes

git fetch downloads objects and references from a remote and updates remote-tracking branches. It does not merge those changes into your current local branch.

# Fetch from origin
git fetch origin

# Fetch from all configured remotes
git fetch --all

# Fetch and remove stale remote-tracking references
git fetch --prune origin

Inspect before integrating

# Compare current local branch with fetched remote-tracking branch
git log --oneline --left-right main...origin/main

# See file differences
git diff main origin/main

# After reviewing, merge if appropriate
git merge origin/main

Fetch is useful when you want to review incoming changes before deciding whether to merge or rebase them.

11.11

Cloning repositories

Source S12 · Chapter manual · 11. Cloning repositories

git clone creates a local copy of an existing remote repository. It downloads the repository data and sets up a remote (normally named origin) pointing to the source URL.

Clone using HTTPS

git clone https://github.com/company/CustomerETL.git

Clone using SSH

git clone git@github.com:company/CustomerETL.git

Choose a local folder name

git clone https://github.com/company/CustomerETL.git CustomerETL-Dev

Clone a specific branch

git clone --branch release/2.5.0 --single-branch https://github.com/company/CustomerETL.git

Inspect the cloned repository

cd CustomerETL
git remote -v
git branch -a
git status

A normal clone configures local branch tracking for the branch you cloned and creates remote-tracking references for the remote branches it fetched.

Clone vs init + remote add

git clonegit init + git remote add
Copies an existing repository and its history into a new local directory.Starts a new local repository, then records a remote URL.
Creates origin automatically in the clone.You choose the remote name and add it yourself.
Use when the project already exists remotely.Use when a project starts locally and you want to connect it to a remote.
11.12

End-to-end workflows

Source S12 · Chapter manual · End-to-end workflows

Workflow A — Publish a new local project to GitHub

# Create and initialize local project
mkdir SalesAnalytics
cd SalesAnalytics
git init -b main

# Create files, then stage and commit
Set-Content README.md "# Sales Analytics"
git add README.md
git commit -m "Create sales analytics project"

# Add GitHub remote and publish
git remote add origin https://github.com/company/SalesAnalytics.git
git push -u origin main

Workflow B — Clone and contribute to an existing project

# Clone the repository
git clone https://github.com/company/SalesAnalytics.git
cd SalesAnalytics

# Create a feature branch
git switch -c feature/monthly-sales-report

# Make changes and commit
git add .
git commit -m "Add monthly sales report"

# Publish feature branch
git push -u origin feature/monthly-sales-report

Workflow C — Sync safely before starting work

git status
git fetch origin
git log --oneline --left-right HEAD...origin/main

# If main is the intended integration branch:
git switch main
git pull --ff-only origin main

--ff-only tells Git to update only when a fast-forward is possible. If local and remote histories have diverged, it stops rather than creating a merge commit; investigate and integrate according to team policy.

11.15

Understanding Origin

Source S40 · 3. Understanding Origin
  • origin is simply the default name Git gives to the remote you cloned from (or the name you choose when adding your main remote).
  • It is a convention, not a keyword — you could rename it.
  • origin/main is the remote-tracking branch for main on origin.
git remote rename origin github

The remote configuration lives in .git/config:

[remote "origin"]
    url = https://github.com/ravi/retail-data-platform.git
    fetch = +refs/heads/*:refs/remotes/origin/*

The fetch line (refspec) means: copy every branch from the remote into refs/remotes/origin/.

11.16

Understanding Upstream

Source S40 · 4. Understanding Upstream

"Upstream" has two common meanings:

4.1 Upstream branch (tracking branch)

The remote branch that a local branch tracks. It lets you run git push, git pull and git status without naming the remote branch.

git push -u origin feature/orders       # -u / --set-upstream
git branch --set-upstream-to=origin/main main
git branch -u origin/main               # short form for current branch
git rev-parse --abbrev-ref @{upstream}  # show it (@{u})
git status
# Your branch is ahead of 'origin/main' by 2 commits.

4.2 Upstream remote (fork workflow)

When you fork a repository, origin is your fork and upstream is the original repository:

company/retail-data-platform   ← upstream (original)
        │ fork
ravi/retail-data-platform      ← origin (your fork)
        │ clone
local repository

git remote add upstream https://github.com/company/retail-data-platform.git
git fetch upstream
git merge upstream/main

11.20

Pushing Local Code to GitHub

Source S40 · 8. Pushing Local Code to GitHub
git push                          # push current branch to its upstream
git push origin main              # explicit remote and branch
git push -u origin feature/orders # first push of a new branch, set upstream
git push origin local:remote      # push local branch to a differently named remote branch
git push --all                    # all branches
git push --tags                   # all tags
git push origin --delete feature/old

Push only sends commits — uncommitted changes stay local.

11.21

Pulling Code from GitHub

Source S40 · 9. Pulling Code from GitHub
git pull                          # fetch + merge upstream of current branch
git pull origin main              # fetch origin/main and merge into current branch
git pull --rebase                 # fetch + rebase your local commits on top
git pull --ff-only                # only update if fast-forward possible
git pull --autostash              # stash local edits, pull, re-apply

Set a default behaviour:

git config --global pull.rebase false   # merge (default)
git config --global pull.rebase true    # rebase
git config --global pull.ff only        # fail instead of creating merge commits
11.22

Fetching Remote Changes

Source S40 · 10. Fetching Remote Changes
git fetch                         # fetch from origin
git fetch origin                  # same
git fetch upstream                # from another remote
git fetch --all                   # all remotes
git fetch --prune                 # also delete remote-tracking branches removed on server
git fetch origin main             # one branch

After fetching, inspect before integrating:

git log --oneline main..origin/main     # commits on remote not yet in local
git diff main origin/main
git merge origin/main                   # integrate when ready

Tip git fetch is always safe — it never changes your working files or local branches.

11.23

Cloning Repositories

Source S40 · 11. Cloning Repositories

11.1 Syntax

git clone <url> [folder]

11.2 Examples

git clone https://github.com/ravi/retail-data-platform.git
git clone https://github.com/ravi/retail-data-platform.git rdp-dev2     # custom folder name
git clone -b develop <url>                    # check out a specific branch
git clone --depth 1 <url>                     # shallow clone (latest commit only) – fast for CI
git clone --filter=blob:none <url>            # partial clone (download file contents on demand)
git clone --recurse-submodules <url>          # include submodules
git clone --bare <url>                        # bare copy (mirroring)
git clone --mirror <url>                      # full mirror including all refs

11.3 What clone does

  1. Creates the folder and .git directory.
  2. Downloads all objects and history.
  3. Adds the remote as origin.
  4. Creates remote-tracking branches (origin/*).
  5. Checks out the default branch and sets it to track origin/<default>.
11.24

Understanding Remote Tracking Branches

Source S40 · 12. Understanding Remote Tracking Branches

12.1 Definition

A remote-tracking branch (e.g. origin/main) is a read-only local reference that records where a branch was on the remote the last time you communicated with it (fetch/pull/push).

Local branch:            main          ← you commit here
Remote-tracking branch:  origin/main   ← updated only by fetch/pull/push
Remote branch:           main on GitHub

12.2 Commands

git branch -r                     # list remote-tracking branches
git branch -vv                    # local branches with upstream and ahead/behind
git status                        # ahead/behind summary
git switch feature/orders         # if origin/feature/orders exists, creates a local tracking branch automatically
git switch -c my-copy origin/feature/orders

12.3 Ahead and behind

main [origin/main: ahead 2, behind 1]
  • Ahead 2 — two local commits not yet pushed.
  • Behind 1 — one remote commit not yet integrated.

12.4 Stale remote-tracking branches

When someone deletes a branch on GitHub, your origin/feature/x remains until you prune:

git fetch --prune
git remote prune origin
git config --global fetch.prune true

Upstream tracking
Syntax
git push -u origin <branch>

Link a local branch to a remote branch so git pull, git push and git status know the counterpart.

branch 'feature/RDP-102-orders-ingest' set up to track 'origin/feature/RDP-102-orders-ingest'.
Example

Troubleshooting
Use git push -u origin x once, or set push.autoSetupRemote true (Git 2.37+).

Real-time scenarios

Source S12, S40 · Repository moved to a new organization

GitHub redirects the old URL for a while, but update it: git remote set-url origin git@github.com:new-org/repo.git, then git fetch. Update CI service connections and ADF/Databricks/Fabric Git settings too.

Course addition · "Your branch is ahead of 'origin/main' by 3 commits"

You committed locally but did not push. Push (if allowed) or move those commits to a feature branch and open a PR if main is protected.

Best practices

Course addition · best practices
  • Use git clone for onboarding rather than copying folders.
  • Push new branches with -u (or enable push.autoSetupRemote).
  • Fetch with --prune (or fetch.prune true) to remove stale remote-tracking branches.
  • Keep remote names meaningful: origin, upstream (forks), azure (mirror).
  • Use shallow/partial clones in CI only.

Practical Lab & exercises

Course addition · graded exercises

  1. Clone a repository and run git branch -a and git remote show origin.

    You see remotes/origin/* refs and the tracking configuration.

Chapter 11 Interview Questions

Source S12 · Chapter manual · interview

1. How do you connect an existing local repository to GitHub?

Create a remote repository, add its URL with git remote add origin URL, then push the branch with git push -u origin main.

2. What is origin?

A conventional remote name, commonly assigned by clone. It is a local nickname for a repository URL.

3. What is the difference between origin and upstream?

They are often remote names. In a fork workflow, origin commonly points to your fork and upstream to the original project. Separately, a branch's upstream means its configured tracking branch.

4. What does git remote -v show?

It lists configured remotes and their fetch and push URLs.

5. How do you change a remote URL?

Use git remote set-url origin NEW_URL.

6. Does removing a remote delete the remote repository?

No. It removes the remote configuration from your local repository only.

7. What does git push -u do?

It pushes the branch and sets its upstream tracking relationship for future operations.

8. What is the difference between git fetch and git pull?

Fetch downloads remote updates without integrating them into the current branch. Pull fetches and then integrates.

9. What is git clone?

It creates a local copy of an existing repository, including its Git history, and normally configures the source as origin.

10. What is a remote-tracking branch?

A local reference representing the last fetched state of a branch on a remote, such as origin/main.

11. Why might a push be rejected as non-fast-forward?

The remote branch has commits not contained in the local branch. Fetch and integrate the remote work before pushing.

12. Can a repository have multiple remotes?

Yes. A repository can have multiple named remotes, each with its own fetch and push URLs.

13. What is the difference between clone and init?

Clone copies an existing repository. Init creates a new local repository in a directory.

14. How do you list remote-tracking branches?

Use git branch -r.

15. How do you remove stale remote-tracking branches?

Use git fetch --prune or git remote prune origin.

Copies the whole repository, creates the origin remote, remote-tracking branches, and checks out the default branch with upstream tracking.

How do you see which remotes are configured?

Intermediate
What is an upstream branch?

The remote branch that a local branch tracks; used as the default for pull/push and for ahead/behind counts.

How do you change a remote's URL?

git remote set-url origin <new-url>.

Advanced
What is the difference between a shallow and a partial clone?

Shallow (--depth) truncates history; partial (--filter=blob:none) keeps full history but downloads file contents on demand.

Scenario
A colleague's new branch is visible on GitHub but git switch feature/x fails locally. Why?

Your remote-tracking refs are outdated; run git fetch — then git switch feature/x creates a local branch tracking origin/feature/x.
