Learning objectives

Chapter introduction

What it is. Branching strategies: naming conventions, branch lifetimes, and team workflows such as feature branching, Git Flow, GitHub Flow and trunk-based development, plus release and hotfix management and branch protection.

Why it matters. A shared strategy decides how fast changes reach production, how releases are stabilized, and how emergencies are fixed without disrupting ongoing work.

Where it is used. Team agreements in CONTRIBUTING.md, enforced through branch protection / rulesets (GitHub) or branch policies (Azure Repos) and CI/CD triggers.

In this course's project. The team chooses GitHub Flow with short-lived feature branches, release tags and hotfix/* branches, and protects main.

9.1

Branch naming conventions

Source S10 · Chapter manual · 1. Branch naming conventions

Consistent branch names make work easier to find and automate. A useful pattern is type/short-description, optionally including a work-item ID.

TypeExample
Featurefeature/123-customer-dq
Bug fixbugfix/456-null-date
Hotfixhotfix/789-prod-load-failure
Releaserelease/2.5.0
Experimentexperiment/new-dedupe-rule

Use lowercase, hyphens, concise names, and the team's agreed ticket format. Avoid spaces and vague names such as test or mybranch.

9.2

Long-lived vs short-lived branches

Source S10 · Chapter manual · 2. Long-lived vs short-lived branches
Short-livedLong-lived
Created for a focused task and merged/deleted quickly.Exists across multiple development cycles.
Reduces divergence and integration risk.Can support structured release or integration workflows.

Long-lived branches are not automatically wrong, but they require disciplined synchronization, ownership, and release policies.

9.3

Feature branch workflow

Source S10 · Chapter manual · 3. Feature branch workflow
  1. Start from the agreed base branch.
  2. Create a focused feature branch.
  3. Make small commits and test locally.
  4. Push the branch and open a pull/merge request.
  5. Address review comments and automated checks.
  6. Merge using the team's chosen strategy.
  7. Delete the completed feature branch.
git switch main
git pull
git switch -c feature/customer-dq
# make changes
git add .
git commit -m "Add customer data quality checks"
git push -u origin feature/customer-dq
9.4

Git Flow workflow

Source S10 · Chapter manual · 4. Git Flow workflow

Git Flow is a structured branching model with long-lived main and develop branches, plus supporting feature, release, and hotfix branches.

main
Production releases
develop
Integration
feature/*
New work
release/*
Stabilization
hotfix/*
Urgent fixes

Typical flow: feature branches merge into develop; a release branch is cut from develop for stabilization; release changes are merged to main and back to develop; hotfixes branch from main and are merged back to main and develop. Exact steps vary by team.

Git Flow can suit scheduled releases and maintenance lines, but it may introduce overhead for teams that deploy continuously.

9.5

GitHub Flow workflow

Source S10 · Chapter manual · 5. GitHub Flow workflow

GitHub Flow is a lightweight workflow centered on one deployable main branch and short-lived topic branches.

  1. Create a branch from main.
  2. Commit changes with descriptive messages.
  3. Open a pull request for discussion and review.
  4. Run automated checks and address feedback.
  5. Merge the pull request.
  6. Deploy or release from main according to the team's process.

It is well suited to teams that integrate and deploy frequently.

9.6

Trunk-based development

Source S10 · Chapter manual · 6. Trunk-based development

Trunk-based development emphasizes frequent integration into a single shared trunk (often main). Developers may commit directly in small teams or use very short-lived branches and pull requests.

  • Integrate small changes frequently.
  • Use automated tests and fast CI feedback.
  • Keep incomplete features hidden with feature flags where appropriate.
  • Avoid long-running divergent branches.

It reduces long-lived integration work but depends on strong automation, disciplined code review, and deployable software practices.

9.7

Release management

Source S10 · Chapter manual · 7. Release management

Release management coordinates the code, testing, versioning, deployment, and support activities required to deliver a software or data-platform release.

  • Agree release scope and cutoff.
  • Use tags or version identifiers to mark release points.
  • Stabilize changes and apply only approved fixes.
  • Run regression tests and deployment validation.
  • Document release notes, rollback steps, and known issues.
  • Merge release fixes back into active development branches.
# Create a release branch
git switch -c release/2.5.0

# After stabilization, tag the release commit
git tag -a v2.5.0 -m "Release 2.5.0"
9.8

Hotfix management

Source S10 · Chapter manual · 8. Hotfix management

A hotfix is an urgent change needed to address a production issue. In a Git Flow-style model, a hotfix branch is commonly created from the production branch, tested, merged into main, and also integrated into develop or active release lines.

git switch main
git pull
git switch -c hotfix/customer-load-null-failure
# implement and test the fix
git add .
git commit -m "Fix null handling in customer load"
# submit for review and merge through the team's process

For a data pipeline incident, include validation of data correctness, rerun/recovery steps, and monitoring checks—not only code-level tests.

9.9

Branch protection

Source S10 · Chapter manual · 9. Branch protection

Branch protection is configured on a hosting platform (for example GitHub or Azure Repos), not by the local git branch command. Rules can restrict direct pushes and require reviews or successful checks.

  • Require pull requests for changes to main.
  • Require one or more approvals.
  • Require CI checks, tests, and status checks to pass.
  • Require conversations to be resolved.
  • Restrict force pushes and branch deletion.
  • Require signed commits where organizational policy demands it.

Apply protections based on risk and team size; document emergency break-glass procedures.

9.10

Managing multiple developers

Source S10 · Chapter manual · 10. Managing multiple developers
  • Agree on branch naming and ownership conventions.
  • Use pull/merge requests for review and visibility.
  • Keep commits focused and communicate breaking changes.
  • Define code owners for sensitive or shared assets.
  • Use automated checks to make quality repeatable.
  • Document how to resolve conflicts and how to release.

For SQL and data-platform work, coordinate changes to shared schemas, stored procedures, pipeline interfaces, environment configuration, and deployment order.

9.11

Managing parallel development

Source S10 · Chapter manual · 11. Managing parallel development

Parallel development works best when work is divided by clear interfaces and ownership. Teams should agree on contracts before multiple branches change related components.

  • Break large work into independently testable tasks.
  • Agree on schema/API contracts early.
  • Use mocks or test fixtures while dependent components are developed.
  • Integrate frequently and avoid large batches.
  • Use feature flags or staged rollout for incomplete functionality.
9.12

Handling multiple feature branches

Source S10 · Chapter manual · 12. Handling multiple feature branches

When working on multiple features, keep each branch focused and understand its base commit. Avoid mixing unrelated changes. If one feature depends on another, communicate the dependency and decide whether to merge the prerequisite first or rebase the dependent branch.

git branch --list
git switch feature/customer-dq
git status

# Update a feature branch from main (team policy may prefer merge)
git fetch origin
git merge origin/main

Do not blindly merge or rebase every branch. Review dependencies, tests, and the team's history policy.

Branch Naming Conventions

Source S40 · 1. Branch Naming Conventions

1.1 Recommended pattern

<type>/<ticket-id>-<short-description>
Type prefix Use Example
feature/ New functionality feature/DE-1423-orders-incremental-load
bugfix/ Non-urgent bug fix bugfix/DE-1501-null-order-date
hotfix/ Urgent production fix hotfix/2.4.1-sales-tax-rounding
release/ Release preparation release/2.5.0
chore/ Maintenance chore/upgrade-pyspark-3.5
docs/ Documentation docs/update-runbook
test/ Test-only changes test/add-transform-tests
experiment/ or spike/ Prototype spike/delta-liquid-clustering
users/<name>/ Personal branches (Azure DevOps convention) users/ravi/adf-refactor

1.2 Rules

  • Lower-case letters, digits and hyphens; use / to group.
  • Include the ticket ID for traceability.
  • Short but descriptive (3–6 words).
  • No spaces, no special characters (~ ^ : ? * [ \), don't end with .lock or /.
  • Avoid names that collide with other branches (feature and feature/x cannot both exist).

Long-Lived vs Short-Lived Branches

Source S40 · 2. Long-Lived vs Short-Lived Branches
Aspect Long-lived branches Short-lived branches
Examples main, develop, release/* (for supported versions) feature/*, bugfix/*, hotfix/*
Lifetime Months/years Hours–days
Protection Protected; PR-only Owned by developer
Purpose Represent environments/releases/integration Deliver one change
Deleted after merge No Yes

Problems with long-lived feature branches: large painful merges ("merge hell"), late integration bugs, stale code, difficult reviews. Aim for feature branches that live less than a few days.

9.16

Feature Branch Workflow

Source S40 · 3. Feature Branch Workflow

3.1 Description

All development happens on dedicated feature branches; main only receives reviewed, tested work via pull requests.

main      ●────────●───────────●──────
           \      /  \        /
feature/a   ●──●─●    \      /
feature/b              ●──●─●

3.2 Steps

  1. git switch main && git pull
  2. git switch -c feature/DE-1423-orders-load
  3. Commit work; push regularly.
  4. Open a pull request.
  5. Review + CI.
  6. Merge; delete branch.

3.3 When to use

Almost every team — it is the foundation of GitHub Flow and Git Flow.

9.17

Git Flow Workflow

Source S40 · 4. Git Flow Workflow

4.1 Description

A structured model (by Vincent Driessen, 2010) with two permanent branches and three supporting types.

main      ●──────────────────────●───────────●─────    (v1.0)  (v1.0.1)
           \                    / \         /
hotfix      \                  /   ●───────●
             \                /             \
release       \        ●────●                \
               \      /      \                \
develop  ●──────●────●────────●────────────────●───
                 \  /
feature           ●●
Branch From Into Purpose
main — — Production releases (tagged)
develop main — Integration of next release
feature/* develop develop New features
release/* develop main + develop Stabilise a release
hotfix/* main main + develop Urgent production fixes

4.2 Commands (plain Git)

# Feature
git switch -c feature/orders develop
git switch develop && git merge --no-ff feature/orders

# Release
git switch -c release/1.2.0 develop
git switch main && git merge --no-ff release/1.2.0 && git tag -a v1.2.0 -m "Release 1.2.0"
git switch develop && git merge --no-ff release/1.2.0

# Hotfix
git switch -c hotfix/1.2.1 main
git switch main && git merge --no-ff hotfix/1.2.1 && git tag -a v1.2.1 -m "Hotfix 1.2.1"
git switch develop && git merge --no-ff hotfix/1.2.1

(The git flow extension automates these: git flow init, git flow feature start orders, etc.)

4.3 Pros and cons

Pros Cons
Clear structure for scheduled releases Complex; many merges
Supports multiple versions in production Slower delivery
Release stabilisation without blocking development Long-lived develop can drift
9.18

GitHub Flow Workflow

Source S40 · 5. GitHub Flow Workflow

5.1 Description

A lightweight workflow with one long-lived branch (main), always deployable.

main  ●──────●──────●──────●──────   (deploy after each merge)
        \   /  \   /
         ●─●    ●─●   feature branches + PRs

5.2 Six steps

  1. Create a branch from main.
  2. Make commits.
  3. Open a pull request (early, even as a draft).
  4. Discuss and review; CI runs.
  5. Deploy (optionally from the branch to a test environment) and verify.
  6. Merge into main and deploy to production.

5.3 When to use

Continuous delivery, SaaS, data platforms with automated testing, small-to-medium teams.

9.19

Trunk-Based Development

Source S40 · 6. Trunk-Based Development

6.1 Description

Developers integrate small changes into the trunk (main) at least daily, either directly or via very short-lived branches (< 1 day). Incomplete functionality is hidden behind feature flags. Releases are cut from trunk (optionally via short release branches).

main  ●─●─●─●─●─●─●─●─●─●   (many small commits per day, CI on each)
        \/    \/
       tiny branches (hours)

6.2 Requirements

  • Strong automated test suite and fast CI.
  • Feature flags / configuration toggles.
  • Code review that keeps up (small PRs, pair programming).

6.3 Comparison of workflows

Aspect Feature branch Git Flow GitHub Flow Trunk-based
Long-lived branches main main, develop main main
Release style Any Scheduled versions Continuous Continuous
Complexity Low High Low Low (needs discipline)
Merge frequency Per feature Per feature/release Per feature Multiple times a day
Best for Most teams Versioned products, regulated releases Web/SaaS, data platforms Mature DevOps teams

Recommendation for Data Engineering teams GitHub Flow with short-lived feature branches, PRs to main, and CI/CD promoting the same build through Dev → Test → Prod environments with approvals.

9.20

Release Management

Source S40 · 7. Release Management

7.1 Definition

Release management is planning, building, stabilising, versioning and deploying a set of changes to production in a controlled way.

7.2 Using Git

  1. Decide scope — which merged features go into release 2.5.0.
  2. Cut a release branch (Git Flow) or choose a commit on main (GitHub Flow).
  3. Stabilise — only fixes on the release branch.
  4. Version — update version files, CHANGELOG.
  5. Tag — git tag -a v2.5.0 -m "Release 2.5.0".
  6. Deploy — CI/CD triggered by the tag.
  7. Merge back — release fixes into develop/main.
  8. Publish release notes — GitHub/Azure DevOps release.
git switch -c release/2.5.0 develop
echo "2.5.0" > VERSION && git commit -am "chore: bump version to 2.5.0"
git switch main && git merge --no-ff release/2.5.0
git tag -a v2.5.0 -m "Release 2.5.0"
git push origin main --follow-tags
git switch develop && git merge --no-ff release/2.5.0 && git push
git branch -d release/2.5.0
9.21

Hotfix Management

Source S40 · 8. Hotfix Management

8.1 Definition

A hotfix is an urgent fix to production that cannot wait for the next scheduled release.

8.2 Process

# 1. Branch from what is in production
git switch -c hotfix/2.5.1 v2.5.0

# 2. Fix and test
git commit -am "fix(sql): correct sales tax rounding in usp_load_sales"

# 3. Merge into main and tag
git switch main
git merge --no-ff hotfix/2.5.1
git tag -a v2.5.1 -m "Hotfix 2.5.1"
git push origin main --follow-tags

# 4. Bring the fix back into develop (and any open release branch)
git switch develop
git merge --no-ff hotfix/2.5.1           # or cherry-pick the fix commit
git push

# 5. Clean up
git branch -d hotfix/2.5.1

8.3 Rules

  • Keep hotfixes minimal — only the fix.
  • Still require review (fast-track approvers).
  • Always merge the fix back so it isn't lost in the next release.
9.22

Branch Protection

Source S40 · 9. Branch Protection

9.1 Definition

Branch protection is a set of server-side rules that restrict how important branches can be changed.

9.2 Common rules

Rule Purpose
Require a pull request before merging No direct pushes
Required number of approvals (e.g. 2) Peer review
Dismiss stale approvals on new commits Re-review after changes
Require review from Code Owners Experts approve their areas
Require status checks to pass CI must be green
Require branches to be up to date Test against latest main
Require conversation resolution All comments addressed
Require signed commits Verified authorship
Require linear history No merge commits (squash/rebase only)
Block force pushes No history rewriting
Block deletions Branch can't be deleted
Restrict who can push/merge Only release managers

9.3 Where to configure

  • GitHub: Settings → Rules → Rulesets (or classic Branches → Branch protection rules).
  • Azure DevOps: Repos → Branches → … → Branch policies.
  • GitLab: Settings → Repository → Protected branches.

9.24

Managing Parallel Development

Source S40 · 11. Managing Parallel Development

11.1 Scenarios

  • Several features in progress for the same release.
  • Developing the next release while fixing the current one.
  • Two developers needing each other's unmerged work.

11.2 Techniques

  • Feature flags — merge incomplete work safely, switched off.
  • Stacked branches — branch B based on branch A; rebase B after A merges (git rebase --onto main A B).
  • Release branches — stabilise while main/develop move on.
  • Cherry-pick — port a specific fix between lines of development.
  • git worktree — check out multiple branches simultaneously in separate folders:
git worktree add ../rdp-hotfix hotfix/2.5.1
cd ../rdp-hotfix        # work on the hotfix while your feature folder stays untouched
git worktree list
git worktree remove ../rdp-hotfix
9.25

Handling Multiple Feature Branches

Source S40 · 12. Handling Multiple Feature Branches

12.1 Keeping track

git branch -vv                         # upstream + ahead/behind
git branch --no-merged main            # what is still open
git branch --sort=-committerdate       # most recent first
git for-each-ref --format='%(refname:short) %(committerdate:relative) %(authorname)' refs/heads/

12.2 Keeping them updated

for b in feature/a feature/b; do
  git switch "$b" && git merge main || break
done

12.3 Dependencies between features

  • Merge the dependent feature first, then rebase the other onto main.
  • Or base feature B on feature A, and change its PR target to main after A merges.

12.4 Cleaning up

git fetch --prune
git branch --merged main | grep -v "^\*\|main\|develop" | xargs -r git branch -d

Fixing in production config only, or fixing on develop/a feature branch so the fix waits for unrelated work.

Real-time scenarios

Source S10, S40 · Parallel features touching the same SQL procedure

Asha and Karan both need usp_load_fact_sales. Agree on sequencing (one merges first, the other rebases or merges main into their branch daily), or split the procedure. Small, frequent merges keep conflicts small.

Course addition · Production bug during a release freeze

Create hotfix/* from the production tag or main, fix, PR, tag v1.0.1, deploy. In Git Flow also merge the hotfix into develop (and any open release branch) so the bug does not return.

Best practices

Course addition · best practices
  • Write the strategy down and enforce it with protection rules, not memory.
  • Keep branches short-lived; integrate at least daily.
  • Use tags for releases; deploy production from tags or protected release branches.
  • Use feature flags/config switches for unfinished features in trunk-based setups.
  • Use CODEOWNERS to route reviews to the right experts.

Beginner
What is a feature branch?

A short-lived branch created for a single feature or work item and merged back (usually via pull request) when complete.

Why protect the main branch?

To prevent unreviewed, untested or accidental changes (direct pushes, force pushes, deletions) on the branch that represents production-ready code.

Intermediate
Compare Git Flow and GitHub Flow.

Git Flow uses main and develop plus feature/release/hotfix branches — suited to scheduled versioned releases. GitHub Flow uses only main plus short-lived branches merged via PR and deployed continuously.

What is trunk-based development?

Developers integrate small changes into the trunk at least daily, relying on strong CI and feature flags; long-lived branches are avoided.

Advanced
How do you handle a hotfix when a release branch is open in Git Flow?

Branch hotfix from main, fix, merge into main and tag; then merge into the open release branch (instead of develop), which later reaches develop when the release finishes.

Scenario
Your data team deploys ADF, Databricks and SQL together weekly; the business wants hotfixes within hours. Which strategy?

GitHub Flow with release tags: main always deployable, weekly tag for scheduled release, hotfix branches from main merged via fast-tracked PR and tagged as patch versions; CI/CD deploys from tags with approvals.
