Learning objectives

Chapter introduction

What it is. The three main undo tools: git reset (move the branch pointer and optionally reset index/working tree), git revert (add a new commit that inverts an earlier one), and git restore (restore files in the working tree or index).

Why it matters. Choosing the wrong one either destroys work (reset --hard) or rewrites shared history. Choosing the right one makes every mistake recoverable.

Where it is used. Daily local corrections; production rollbacks via revert; CI cleanup.

In this course's project. Stage 5: Asha unstages a file with restore --staged, Ravi drops two local commits with reset, and Priya rolls back a faulty pushed DQ rule with revert.

18.1

Understanding the three areas

Source S19 · Chapter manual · 1. Understanding the three areas

Git changes can exist in three important places: the working tree (files on disk), the index/staging area (the next commit snapshot), and the commit history (HEAD and its ancestors). Reset, revert and restore operate on different parts of this model. Always inspect git status before choosing an undo command.

Commands and example

git status
git diff                 # working tree vs index
git diff --staged        # index vs HEAD
git log --oneline -5
18.2

Understanding reset

Source S19 · Chapter manual · 2. Understanding reset

git reset moves the current branch reference (and HEAD) to a chosen commit. Depending on the mode, it also updates the index and working tree. The default mode is mixed. Reset is commonly used to adjust local history or unstage changes; hard reset can discard uncommitted work.

Commands and example

git reset --soft HEAD~1
git reset --mixed HEAD~1
git reset --hard HEAD~1
18.3

Soft, mixed and hard reset

Source S19 · Chapter manual · 3. Soft, mixed and hard reset

Soft reset moves HEAD but leaves the index and working tree unchanged, so the changes from removed commits remain staged. Mixed reset moves HEAD and resets the index, leaving working files unchanged (changes become unstaged). Hard reset moves HEAD and resets both index and working tree to the target; uncommitted changes can be lost.

Commands and example

# Keep changes staged
git reset --soft HEAD~1

# Keep changes in files, but unstage them (default)
git reset --mixed HEAD~1

# Destructive: make index and working tree match target
git reset --hard HEAD~1
18.4

Understanding revert

Source S19 · Chapter manual · 4. Understanding revert

git revert creates a new commit that applies the inverse of an earlier commit. It does not move the branch backwards or erase the original commit. This makes it the normal choice for undoing a change that has already been pushed or shared. Reverting a merge commit requires choosing the mainline parent with -m.

Commands and example

git revert a1b2c3d
# Revert a range carefully, reviewing the generated commits
git revert start_commit^..end_commit

# Merge commit example: select mainline parent 1
git revert -m 1 <merge-commit>
18.5

Understanding restore

Source S19 · Chapter manual · 5. Understanding restore

git restore restores file content in the working tree or index. It does not move HEAD. Use --staged to unstage a file (restore the index version from HEAD by default), and --source to choose a different source commit.

Commands and example

# Discard unstaged edits to one file
git restore sql/customer_load.sql

# Unstage a file, keeping its working-tree edits
git restore --staged sql/customer_load.sql

# Restore a file from a previous commit
git restore --source=HEAD~1 -- sql/customer_load.sql
18.6

Reset vs Revert vs Restore

Source S19 · Chapter manual · 6. Reset vs Revert vs Restore

Use reset to move a branch pointer and optionally reset index/working tree; use revert to add a compensating commit; use restore to copy file content into the working tree or index. The correct choice depends on whether the commit is shared and whether you want to preserve current file edits.

Commands and example

# Local unpublished commit: move HEAD but keep changes staged
git reset --soft HEAD~1

# Shared/pushed commit: create an inverse commit
git revert <commit>

# Unstage a file without discarding its edits
git restore --staged <file>
18.7

Undoing latest or multiple commits

Source S19 · Chapter manual · 7. Undoing latest or multiple commits

For a local commit that has not been shared, soft or mixed reset can undo one or more commits while retaining their changes. For a pushed commit, use revert. To undo several local commits, choose the correct target such as HEAD~3; verify the resulting status and log before pushing.

Commands and example

# Undo last commit, keep changes staged
git reset --soft HEAD~1

# Undo last three local commits, keep file edits but unstage
git reset HEAD~3

# Undo a pushed commit safely
git revert <commit-sha>
18.8

Removing staged files and recovering modified files

Source S19 · Chapter manual · 8. Removing staged files and recovering modified files

To unstage a file while retaining its edits, use git restore --staged. To discard unstaged edits and restore the index version, use git restore. These commands are not interchangeable. Review diffs first because restoring the working-tree version discards edits that exist only in that file.

Commands and example

git diff --staged
git restore --staged data_quality.sql

git diff
git restore data_quality.sql
18.9

Recovering deleted files

Source S19 · Chapter manual · 9. Recovering deleted files

If a tracked file was deleted in the working tree but the deletion is not committed, restore it from the index/HEAD using git restore. If the deletion was committed, restore the file from a commit where it existed, then commit the restoration. If the file was never tracked or committed, Git may not be able to recover it.

Commands and example

# Recover an uncommitted deletion
git restore -- path/to/file.sql

# Recover from a known earlier commit
git restore --source=<commit-sha> -- path/to/file.sql
git add path/to/file.sql
git commit -m "Restore deleted SQL file"
18.10

Safe recovery techniques and troubleshooting

Source S19 · Chapter manual · 10. Safe recovery techniques and troubleshooting

Before destructive operations, create a backup branch or copy important files. Use git reflog to find recent HEAD positions after a reset or rebase. Reflog is local and expires according to repository settings; it is a recovery aid, not a permanent backup. Never assume hard-reset work can always be recovered.

Commands and example

git branch backup/before-reset
git reflog --date=local
# If the desired commit is found:
git switch -c recovery/previous-state <commit-sha>
git status
git log --oneline --decorate -10
18.11

Real-time scenarios

Source S19 · Chapter manual · 11. Real-time scenarios

Scenario A: a local commit contains changes you still need — use soft reset. Scenario B: a bad commit is already on the shared main branch — revert it. Scenario C: a file is staged accidentally — restore --staged. Scenario D: an unwanted local edit should be discarded — restore the file after inspecting the diff. Scenario E: a hard reset moved the branch unexpectedly — inspect reflog and create a recovery branch if the commit is available.

Commands and example

# A: keep changes staged
git reset --soft HEAD~1

# B: undo a shared commit
git revert <bad-commit>

# C: unstage only
git restore --staged <file>

# D: discard working-tree edits (destructive for that file)
git restore <file>

# E: inspect recent HEAD movements
git reflog
18.12

Understanding Reset

Source S40 · 1. Understanding Reset

1.1 Definition

git reset moves the current branch pointer (and HEAD) to a specified commit, and depending on the mode, also resets the staging area and working directory.

1.2 The three trees

Tree Meaning
HEAD Last commit snapshot (branch pointer)
Index Staging area (proposed next commit)
Working directory Your files

reset modes decide which trees are changed:

Mode HEAD/branch Index Working directory
--soft ✔ moved — —
--mixed (default) ✔ moved ✔ reset —
--hard ✔ moved ✔ reset ✔ reset

1.3 Path form

git reset <file> (no commit) only updates the index for that path — i.e. unstages it. It doesn't move the branch.

18.13

Soft Reset

Source S40 · 2. Soft Reset
git reset --soft HEAD~1
  • Moves the branch back one commit.
  • Changes from the undone commit remain staged.
  • Working directory untouched.

Use cases:

  • Re-do the last commit with a different message or extra files.
  • Squash the last N commits into one:
git reset --soft HEAD~3
git commit -m "feat: orders incremental load"
18.14

Mixed Reset

Source S40 · 3. Mixed Reset
git reset HEAD~1          # --mixed is the default
git reset --mixed HEAD~1
  • Moves the branch back.
  • Changes remain in the working directory, unstaged.

Use cases:

  • Undo a commit and re-stage selectively into several smaller commits.
  • Unstage everything: git reset.
  • Unstage one file: git reset sql/views/vw_test.sql.
18.15

Hard Reset

Source S40 · 4. Hard Reset
git reset --hard HEAD~1
  • Moves the branch back.
  • Index and working directory reset — uncommitted changes and the undone commits' changes are discarded.

Use cases:

  • Throw away bad local commits completely.
  • Make your branch identical to the remote: git reset --hard origin/main.
  • Abandon all local edits: git reset --hard (resets to HEAD).

Warning Uncommitted changes destroyed by --hard are not recoverable via Git. Committed work can be recovered via git reflog for a limited time.

Visual summary:

              A ── B ── C (main, HEAD)
git reset --soft  B  → main=B; C's changes STAGED
git reset --mixed B  → main=B; C's changes UNSTAGED in files
git reset --hard  B  → main=B; C's changes GONE
18.16

Understanding Revert

Source S40 · 5. Understanding Revert

5.1 Definition

git revert <commit> creates a new commit that undoes the changes introduced by the specified commit. Existing history is not modified.

A ── B ── C ── D          git revert B          A ── B ── C ── D ── B'   (B' = inverse of B)

5.2 Commands

git revert 3f2a7d1                      # opens editor for message "Revert ..."
git revert 3f2a7d1 --no-edit
git revert HEAD                          # undo the latest commit
git revert HEAD~3..HEAD                  # revert last 3 commits (3 revert commits)
git revert --no-commit HEAD~3..HEAD      # stage all reverts; then one commit
git commit -m "Revert orders feature (DE-1423)"
git revert -m 1 <merge-sha>              # revert a merge commit (keep parent 1)
git revert --continue | --abort | --skip # during conflicts

5.3 Reverting a merge — note

After reverting a merge, if you later want to re-merge the same branch, Git thinks those commits are already merged. You must revert the revert first: git revert <revert-commit-sha>.

18.17

Understanding Restore

Source S40 · 6. Understanding Restore

6.1 Definition

git restore (Git 2.23+) restores file content in the working directory and/or staging area from another source (index, HEAD, or any commit). It never moves branches or creates commits.

6.2 Commands

git restore <file>                          # working dir ← index (discard unstaged edits)
git restore --staged <file>                 # index ← HEAD (unstage)
git restore --staged --worktree <file>      # both
git restore --source=HEAD~2 <file>          # working dir ← file from 2 commits ago
git restore --source=v1.0.0 -- sql/         # folder from a tag
git restore -p <file>                       # interactive hunk selection
git restore .                               # discard all unstaged changes
18.18

Reset vs Revert vs Restore

Source S40 · 7. Reset vs Revert vs Restore
Aspect git reset git revert git restore
Works on Commits / branch pointer (or index for paths) Commits Files
Creates a commit No Yes No
Rewrites history Yes No No
Safe for pushed/shared commits No Yes N/A
Affects working directory --hard only Yes (applies inverse) Yes (default)
Typical question it answers "Remove these local commits" "Undo this pushed commit" "Discard/unstage changes to this file"

Decision guide:

Is the change committed?
 ├── No → git restore (discard) / git restore --staged (unstage)
 └── Yes → Has it been pushed/shared?
           ├── No  → git reset (soft/mixed/hard) or git commit --amend
           └── Yes → git revert

Undoing the Latest Commit

Source S40 · 8. Undoing the Latest Commit
Goal Command
Undo commit, keep changes staged git reset --soft HEAD~1
Undo commit, keep changes unstaged git reset HEAD~1
Undo commit and discard changes git reset --hard HEAD~1
Just fix the message/content git commit --amend
Commit was already pushed git revert HEAD then git push
18.20

Undoing Multiple Commits

Source S40 · 9. Undoing Multiple Commits

Local (not pushed):

git log --oneline -5
git reset --hard HEAD~3          # remove last 3 commits
git reset --soft HEAD~3          # or keep their changes staged
git reset --hard a1b2c3d         # back to a specific commit

Pushed:

git revert --no-commit HEAD~3..HEAD
git commit -m "Revert last three commits (bad orders logic)"
git push

Non-contiguous commits:

git revert c3d4e5f a1b2c3d
18.21

Removing Staged Files

Source S40 · 10. Removing Staged Files
git restore --staged sql/views/vw_test.sql     # unstage one file
git restore --staged .                         # unstage everything
git reset                                      # same as above
git rm --cached secrets.env                    # remove from index AND stop tracking (file stays on disk)

Note git restore --staged keeps the file tracked but unstaged; git rm --cached stages its deletion from the repository.

18.22

Recovering Modified Files

Source S40 · 11. Recovering Modified Files

You edited a file and want the committed version back:

git restore python/etl/transform.py                 # discard unstaged edits
git restore --staged --worktree python/etl/transform.py   # discard staged and unstaged
git restore --source=HEAD~1 python/etl/transform.py       # previous commit's version
git checkout HEAD -- python/etl/transform.py              # older equivalent

Want to keep a copy of your edits first? git stash push -- python/etl/transform.py.

18.23

Recovering Deleted Files

Source S40 · 12. Recovering Deleted Files

12.1 Deleted but not committed

rm sql/views/vw_sales.sql
git restore sql/views/vw_sales.sql

12.2 Deletion staged

git rm sql/views/vw_sales.sql
git restore --staged --worktree sql/views/vw_sales.sql

12.3 Deletion committed

git log --diff-filter=D --oneline -- sql/views/vw_sales.sql    # find the commit that deleted it
# e.g. 7a8b9c0 Remove sales view
git restore --source=7a8b9c0~1 sql/views/vw_sales.sql           # restore from the commit before
git add sql/views/vw_sales.sql && git commit -m "Restore vw_sales"

(Or git revert 7a8b9c0 if that commit only deleted the file.)

18.24

Safe Recovery Techniques

Source S40 · 13. Safe Recovery Techniques
  1. Create a backup branch before risky operations: git branch backup/before-reset.
  2. Use the reflog to find previous positions: git reflog, git reset --hard HEAD@{n}.
  3. Use ORIG_HEAD right after reset/merge/rebase: git reset --hard ORIG_HEAD.
  4. Stash instead of discarding when unsure: git stash -u.
  5. Dry-run destructive commands: git clean -n.
  6. Prefer revert for anything already pushed.
  7. Find lost objects with git fsck --lost-found.
  8. Check the remote — teammates' clones or the server may still have commits.
  9. Read git status — it tells you exactly which undo command to use.

Real-Time Troubleshooting Scenarios

Source S40 · 14. Real-Time Troubleshooting Scenarios
# Scenario Solution
1 Committed to main instead of a feature branch (not pushed) git branch feature/x → git reset --hard origin/main → git switch feature/x
2 Committed with the wrong message (not pushed) git commit --amend -m "correct message"
3 Forgot a file in the last commit git add file → git commit --amend --no-edit
4 Pushed a commit that broke production git revert <sha> → push → deploy
5 Merged a feature that must be rolled back git revert -m 1 <merge-sha>
6 Accidentally ran git reset --hard and lost commits git reflog → git reset --hard HEAD@{1}
7 Staged a large data file by mistake git restore --staged data/big.csv + add to .gitignore
8 Committed a large file (not pushed) git rm --cached data/big.csv → git commit --amend
9 Deleted a branch with unmerged work git reflog → git branch <name> <sha>
10 Want to discard all local changes and match remote git fetch → git reset --hard origin/main → git clean -fd
11 Need a file as it was in last release git restore --source=v2.4.0 path/file
12 Want to undo git add . git restore --staged .
13 Committed a password and pushed Rotate the secret first; then remove from history (Chapter 23)
14 Rebase went wrong git rebase --abort or git reset --hard ORIG_HEAD

Added topics, conflicts & verification

Source conflict — What does `git reset --mixed` do?

S41 states that git reset --mixed undoes changes in the working directory and the index. S19/S40 say it keeps the working tree. Resolution (git-reset docs): --mixed resets the index but not the working tree; only --hard discards working-tree changes. S41 is incorrect on this point.

Source conflict — `reset --hard` for unpushed commits

S41 answers "how to revert the previous commit" with git reset --hard HEAD~1 (alongside --soft/--mixed). Resolution: reset does not revert; it removes commits from the branch. acceptable only for unpushed commits and only when you intend to discard their changes; prefer --mixed/--soft to keep the work, and revert for pushed commits.

Command reference

git reset
Syntax
git reset [--soft | --mixed | --hard | --keep] [<commit>]
git reset [<commit>] -- <path>
Purpose
Move the current branch to <commit>, optionally resetting index and working tree.
Expected output
HEAD is now at 3f1c2a9 Add orders table
(printed by --hard; --mixed prints "Unstaged changes after reset:" with file list)
Example
git reset --soft HEAD~3      # squash last 3 commits: re-commit as one
git reset HEAD~1             # undo last commit, keep changes unstaged
git reset --hard origin/main # discard local commits and changes (dangerous)
Common mistakes
reset --hard with uncommitted work — it cannot be recovered; resetting a pushed branch and force-pushing.
Troubleshooting
Committed work: git reset --hard ORIG_HEAD or git reflog → git reset --hard HEAD@{n}.
git revert
Syntax
git revert <commit>…
git revert -m 1 <merge-commit>
git revert --no-commit <A>..<B>
git revert --continue | --abort
Purpose
Create commit(s) that undo the changes of earlier commits.
Expected output
[main 4c3b2a1] Revert "feat(dq): reject orders with zero quantity"
 1 file changed, 3 deletions(-)
Example
git revert 7f3e2d1
git revert -m 1 9a8b7c6           # undo a merged PR
git revert --no-commit HEAD~3..HEAD && git commit -m "Revert RDP-125 changes"
Common mistakes
Reverting a merge and later re-merging the same branch — Git thinks the old commits are already merged. Revert the revert first.
git restore
Syntax
git restore [--staged] [--worktree] [--source=<tree-ish>] <pathspec>…
Purpose
Restore files in the working tree and/or index from the index, HEAD or a commit (Git 2.23+).
Key parameters
  • (no option) — working tree from index
  • --staged — index from HEAD (unstage)
  • --staged --worktree — both from HEAD
  • --source=v1.0.0 — take content from a commit/tag
Example
git restore --staged sql/tests/test_dim_customer.sql
git restore python/dq/rules/orders_rules.py
git restore --source=HEAD~2 -- sql/warehouse/usp_load_fact_sales.sql
git restore --source=HEAD~1 -- deleted/file.sql   # bring back a file deleted in the last commit
Common mistakes
Expecting restore to undo a commit — it only changes files.

Real-time scenarios

Source S19, S40 · Deleted file needs to come back

Deleted and not committed: git restore <file>. Deleted in a commit: find it with git log --diff-filter=D --oneline -- <path>, then git restore --source=<that-commit>~1 -- <path>.

Course addition · Developer ran `git reset --hard` and lost committed work

git reflog shows the previous position (HEAD@{1}); git reset --hard HEAD@{1} or git branch rescue HEAD@{1}. Uncommitted changes are gone — commit or stash more often.

Best practices

Course addition · best practices
  • Pushed? → revert. Not pushed? → reset/amend/rebase are fine.
  • Prefer --mixed/--soft over --hard; check git status and git stash first.
  • Use git restore and git restore --staged rather than overloaded checkout/reset for files.
  • Revert merges with -m 1 and document the reason in the message.
  • Know ORIG_HEAD and the reflog.

Practical Lab & exercises

Course addition · graded exercises

  1. Make three commits; run git reset --soft HEAD~2 then commit once.

    History has the first commit plus one combined commit.

  2. Run git reset --mixed HEAD~1.

    The last commit is gone; its changes are unstaged.

  3. Revert a commit and inspect the new commit with git show.

    Inverse diff with message Revert "...".

  4. Delete a file in a commit, then restore it with git restore --source.

    File back in the working tree, ready to commit.

  5. Run reset --hard HEAD~2 and recover with the reflog.

    Original commits are back.

Chapter 18 Interview Questions

Source S19 · Chapter manual · interview

1. What does git reset change?

It moves the current branch/HEAD to a target commit and, depending on mode, updates the index and working tree.

2. What does --soft do?

Moves HEAD only; changes remain staged.

3. What does --mixed do?

Moves HEAD and resets the index; working-tree changes remain.

4. What does --hard do?

Moves HEAD and resets index and working tree; uncommitted changes may be lost.

5. What is git revert?

It creates a new commit that reverses the effect of an earlier commit.

6. Why is revert safer for shared history?

It preserves existing history and adds a compensating commit.

7. What does git restore do?

It restores file content in the working tree or index.

8. How do you unstage a file but keep edits?

Use git restore --staged file.

9. How do you discard unstaged edits?

Use git restore file after reviewing the diff.

10. How do you recover an uncommitted deletion of a tracked file?

Use git restore -- path.

11. How do you restore a file from an earlier commit?

Use git restore --source=commit -- path.

12. How do you inspect previous HEAD positions?

Use git reflog.

13. Can reflog recover every deleted file?

No. It records reference movements, not arbitrary untracked file contents.

14. How do you undo a pushed commit?

Usually use git revert.

15. What should you do before hard reset?

Inspect status and diffs, and create a backup branch if there is any uncertainty.

6 How do you recover a deleted committed file? Find deleting commit, git restore --source=<sha>~1 <file>

8 What is ORIG_HEAD? Ref to HEAD before a reset/merge/rebase
Beginner
How do you unstage a file?

git restore --staged <file> (or git reset <file>).

What is the difference between reset and revert?

Reset moves the branch pointer (rewrites history); revert creates a new commit that undoes a previous one (safe for shared history).

Intermediate
Explain --soft, --mixed and --hard.

Soft moves HEAD only; mixed also resets the index (default); hard also resets the working tree, discarding uncommitted changes.

How do you undo a pushed merge?

git revert -m 1 <merge-commit>.

Advanced
What is ORIG_HEAD?

A ref Git sets before operations that move HEAD drastically (reset, merge, rebase), allowing git reset --hard ORIG_HEAD to undo them.

Scenario
A release contains three bad commits mixed with good ones on main. How do you roll back only the bad ones?

git revert <c1> <c2> <c3> (newest first, or --no-commit then one commit), resolve conflicts, test, merge via PR, redeploy.
