Source S37 · project briefBeginner
Objective and implementation

Create a local repo, add README/.gitignore, stage files, commit, inspect log and push to a remote.

Expected deliverable: Deliverable: repository URL, meaningful commits and README.
Acceptance criteria

Business scenario

The retail analytics team keeps SQL scripts and Python helpers in a shared network folder (final_v2.sql, load_final_ASHA.py). Management asks for a version-controlled repository with clean history before the platform build starts.

Requirements

  • Local repository initialized with main as default branch.
  • README, .gitignore and .gitattributes committed first.
  • At least five meaningful commits (Conventional Commits style) adding SQL and Python files.
  • Demonstrate status, diff, log, rename, untrack, restore and amend.
  • Repository pushed to GitHub (private) with upstream tracking.

Architecture

Prerequisites

Git 2.23+ installed and configured (user.name, user.email, init.defaultBranch), GitHub account, VS Code (optional).

Repository structure

retail-git-basics/
├── README.md
├── .gitignore
├── .gitattributes
├── sql/
│   ├── source/dbo.Customer.sql
│   └── warehouse/usp_load_dim_customer.sql
└── python/
    └── extract_customers.py

Step-by-step implementation and commands

git init -b main retail-git-basics && cd retail-git-basics
printf "# Retail Git Basics\n\nVersioned SQL and Python for the retail team.\n" > README.md
printf ".venv/\n__pycache__/\n*.log\n.env\n" > .gitignore
printf "* text=auto\n*.sql text eol=lf\n*.py text eol=lf\n" > .gitattributes
git add README.md .gitignore .gitattributes
git commit -m "chore: initialize repository with README and attributes"

mkdir -p sql/source sql/warehouse python
# create the three files with your editor
git add sql/source/dbo.Customer.sql
git commit -m "feat(sql): add source table dbo.Customer"
git add sql/warehouse/usp_load_dim_customer.sql
git commit -m "feat(sql): add dim_customer load procedure"
git add python/extract_customers.py
git commit -m "feat(python): add customer extract script"

# practise inspection and undo
git status -sb
git diff                       # after editing a file
git diff --staged              # after staging it
git restore --staged python/extract_customers.py
git restore python/extract_customers.py
git mv python/extract_customers.py python/extract_customer.py
git commit -m "refactor(python): rename extract script"
git log --oneline --graph --stat -5

# fix the last commit message (not pushed yet)
git commit --amend -m "refactor(python): rename customer extract script"

# publish
git remote add origin git@github.com:<you>/retail-git-basics.git
git push -u origin main

Expected results

  • git log --oneline lists 5+ commits with conventional messages; the rename shows as rename python/{extract_customers.py => extract_customer.py} in --stat.
  • git status ends with nothing to commit, working tree clean.
  • GitHub shows the files and README; git branch -vv shows [origin/main].

Validation steps

  • git ls-files contains no .env, .venv or log files.
  • git log --follow -- python/extract_customer.py shows history before the rename.
  • git check-ignore -v .env reports the .gitignore rule.

Troubleshooting

Problem Fix
Author identity unknown Configure user.name/user.email
error: src refspec main does not match any Make the first commit; check branch name
Permission denied (publickey) Add SSH key (Chapter 23) or use HTTPS + GCM
Push rejected because remote has a README git pull --rebase origin main, then push

Interview questions

Why commit .gitignore and .gitattributes first?

So that no unwanted files are ever tracked and line endings are normalized from the first commit — avoiding later history rewrites and noisy diffs.

How did you rename a file while keeping its history visible?

git mv (or delete+add — Git detects renames); git log --follow shows history across the rename.

Expected deliverable: Deliverable: branch graph and merge notes.
Acceptance criteria
  • Repository structure and README explain the project.
  • Changes are committed with meaningful messages.
  • Branch/PR or deployment workflow is demonstrated where relevant.
  • Evidence of validation and a short lessons-learned note are included.

Business scenario

Two features — a product dimension (SQL) and an orders extract (Python) — must be developed in parallel and integrated into main without breaking it.

Requirements

  • Two feature branches from the same main commit.
  • One fast-forward merge and one --no-ff merge; one squash merge.
  • One deliberate conflict resolved correctly.
  • Graph of the final history documented in docs/merge-notes.md.

Architecture

Prerequisites

Project 1 repository (or any repo with a few commits on main).

Repository structure

retail-git-basics/
├── sql/warehouse/usp_load_dim_product.sql   (feature/product)
├── python/extract_orders.py                (feature/orders)
└── docs/merge-notes.md

Step-by-step implementation and commands

git switch main
git switch -c feature/RDP-107-dim-product
# add sql/warehouse/usp_load_dim_product.sql
git add sql/warehouse/usp_load_dim_product.sql
git commit -m "feat(sql): add dim_product load"
git switch main
git switch -c feature/RDP-102-orders-extract
# add python/extract_orders.py ; also edit README line 3
git add . && git commit -m "feat(python): add orders extract"

# 1) fast-forward demo with a tiny docs branch
git switch main && git switch -c docs/readme-typo
# fix a typo in README
git commit -am "docs: fix README typo"
git switch main && git merge docs/readme-typo           # Fast-forward

# 2) --no-ff merge
git merge --no-ff feature/RDP-107-dim-product -m "Merge RDP-107: dim_product"

# 3) conflict: README line 3 was also edited on the orders branch
git merge --squash feature/RDP-102-orders-extract       # may report CONFLICT in README.md
git status
# edit README.md, keep both changes
git add README.md
git commit -m "feat(python): add orders extract (RDP-102, squashed)"

git log --oneline --graph --all
git branch -d docs/readme-typo feature/RDP-107-dim-product
git branch -D feature/RDP-102-orders-extract             # squash-merged: -d refuses

Expected results

  • First merge prints Fast-forward; second creates a merge commit with two parents; squash produces a single commit and Git prints Squash commit -- not updating HEAD.
  • Conflict markers resolved; git diff --check prints nothing.

Validation steps

  • git log --merges --oneline shows exactly one merge commit.
  • git cat-file -p <merge-sha> shows two parent lines.
  • docs/merge-notes.md explains when each merge type is used.

Troubleshooting

Problem Fix
Your local changes ... would be overwritten on switch Commit or stash first
git branch -d refuses after squash Expected — use -D after verifying content is on main
Conflict markers committed Fix file, git diff --check, new commit

Interview questions

Why did git branch -d refuse to delete the squash-merged branch?

Squash merge does not record the branch commits as ancestors of main, so Git considers the branch not fully merged.

When would you choose --no-ff?

To keep an explicit integration point so the feature can be identified and reverted as a unit.

Earlier course version of this project (S40)

Objective: Practise branching and every merge type.

Steps:

# Fast-forward merge
git switch -c feature/dim-product
echo "CREATE TABLE dw.dim_product (product_id INT PRIMARY KEY, product_name NVARCHAR(100));" > sql/tables/dw.dim_product.sql
git add . && git commit -m "feat(sql): add dim_product"
git switch main
git merge feature/dim-product              # Fast-forward

# Three-way merge
git switch -c feature/fact-sales
echo "CREATE TABLE dw.fact_sales (sale_id BIGINT, product_id INT, customer_id INT, amount DECIMAL(18,2));" > sql/tables/dw.fact_sales.sql
git add . && git commit -m "feat(sql): add fact_sales"
git switch main
echo "## Tables" >> README.md && git commit -am "docs: list tables"
git merge feature/fact-sales -m "Merge feature/fact-sales"   # merge commit

# No-fast-forward merge
git switch -c feature/dim-date
echo "CREATE TABLE dw.dim_date (date_key INT PRIMARY KEY, full_date DATE);" > sql/tables/dw.dim_date.sql
git add . && git commit -m "feat(sql): add dim_date"
git switch main
git merge --no-ff feature/dim-date -m "Merge feature/dim-date"

# Squash merge
git switch -c feature/views
echo "CREATE OR ALTER VIEW dw.vw_sales AS SELECT * FROM dw.fact_sales;" > sql/views/dw.vw_sales.sql
git add . && git commit -m "wip"
sed -i 's/SELECT \*/SELECT sale_id, amount/' sql/views/dw.vw_sales.sql && git commit -am "fix"
git switch main
git merge --squash feature/views
git commit -m "feat(sql): add vw_sales view"

# Clean up
git branch -d feature/dim-product feature/fact-sales feature/dim-date
git branch -D feature/views
git log --oneline --graph --all

Done when: the graph shows a fast-forward, a three-way merge, a --no-ff merge and a squash commit, and you can explain each.

Objective and implementation

Fork or share a repository, create separate branches, open PRs, review, request changes and merge.

Expected deliverable: Deliverable: two PRs, reviews and issue links.
Acceptance criteria

  • Changes are committed with meaningful messages.
  • Branch/PR or deployment workflow is demonstrated where relevant.
  • Evidence of validation and a short lessons-learned note are included.

Business scenario

Ravi (ingestion) and Asha (SQL) must deliver features together on GitHub with reviews, issue tracking and protected main.

Requirements

  • Organization or shared repository with main protected (PR required, 1 approval, no force push).
  • Two issues, two branches, two PRs (one from a fork, one from a shared branch).
  • Review cycle: comment, suggestion, request changes, approve.
  • Issues closed automatically by PR keywords; Project board updated.

Architecture

Prerequisites

Two GitHub accounts (or a partner), Projects 1–2 skills, gh CLI (optional).

Repository structure

Use the Project 1 repository, add .github/pull_request_template.md and .github/CODEOWNERS.

Step-by-step implementation and commands

# Owner: protection + template
# Settings -> Rules -> New branch ruleset: target main; require PR (1 approval); block force pushes
mkdir -p .github
printf "## Summary\n\n## Linked issue\nCloses #\n\n## Testing\n- [ ] Tests pass\n" > .github/pull_request_template.md
printf "/sql/ @asha-r\n/python/ @ravi-k\n" > .github/CODEOWNERS
git switch -c chore/collab-setup && git add .github && git commit -m "chore: PR template and CODEOWNERS"
git push -u origin chore/collab-setup && gh pr create --fill && gh pr merge --squash --delete-branch

# Developer A (collaborator)
gh issue create --title "Add dim_store load" --label "type:feature"
git switch main && git pull --ff-only
git switch -c feature/RDP-201-dim-store
# ... commit work ...
git push -u origin feature/RDP-201-dim-store
gh pr create --title "feat(sql): dim_store load (RDP-201)" --body "Closes #<issue>"

# Developer B (fork)
gh repo fork <owner>/retail-git-basics --clone
cd retail-git-basics && git remote -v          # origin = fork, upstream = original
git switch -c feature/RDP-202-orders-retry
# ... commit ...
git push -u origin feature/RDP-202-orders-retry
gh pr create --repo <owner>/retail-git-basics --base main --title "feat(python): retry (RDP-202)" --body "Closes #<issue>"

# Keeping the fork current
git fetch upstream && git rebase upstream/main && git push --force-with-lease

Expected results

  • Direct git push origin main is rejected by the ruleset.
  • Both PRs show reviews; one passes through "Changes requested" before approval.
  • Issues close on merge; Project items move to Done.

Validation steps

  • PR timeline shows review events and linked issue.
  • git log --oneline main shows two squash commits referencing the issues.

Troubleshooting

Problem Fix
GH006/GH013 protected branch errors Push a branch and open a PR
Fork PR has conflicts git fetch upstream, rebase/merge upstream/main, push
Reviewer not requested automatically CODEOWNERS path/owner wrong or owner lacks write access

Interview questions

How do you keep a fork in sync?

Add the original repo as upstream, fetch it, rebase or fast-forward your branch onto upstream/main, push to your fork (or use Sync fork / gh repo sync).

How do issues close automatically?

Closing keywords (Closes #n) in the PR description, merged into the default branch.

Source S37 · project briefIntermediate
Objective and implementation

Create conflicting edits to the same lines and different files, resolve carefully, run tests and document decisions.

Expected deliverable: Deliverable: resolved merge commit and test evidence.
Acceptance criteria
  • Repository structure and README explain the project.
  • Changes are committed with meaningful messages.
  • Branch/PR or deployment workflow is demonstrated where relevant.
  • Evidence of validation and a short lessons-learned note are included.

Business scenario

A release is blocked by conflicts: SQL procedure edited on two branches, an ADF pipeline JSON changed in parallel, a file deleted on one side and modified on the other.

Requirements

  • Reproduce three conflict types: content, JSON structure, modify/delete.
  • Resolve each with a documented decision; validate JSON and SQL.
  • Show abort and retry, and ours/theirs usage (with the rebase inversion).
  • Tests or validation evidence attached.

Architecture

Prerequisites

Projects 1–2; Python 3 for JSON validation.

Repository structure

conflict-lab/
├── sql/usp_load_fact_sales.sql
├── adf/pipeline/pl_ingest_orders.json
└── python/legacy_loader.py

Step-by-step implementation and commands

# set up conflicting branches
git switch -c branch-a
# edit line 10 of usp_load_fact_sales.sql; add activity "CopyOrders" to the JSON; delete legacy_loader.py
git add -A && git commit -m "branch-a changes"
git switch main && git switch -c branch-b
# edit the same SQL line differently; add activity "CopyReturns" in the same array position; modify legacy_loader.py
git add -A && git commit -m "branch-b changes"

git switch main && git merge branch-a          # fast-forward
git merge branch-b
#   CONFLICT (content): Merge conflict in sql/usp_load_fact_sales.sql
#   CONFLICT (content): Merge conflict in adf/pipeline/pl_ingest_orders.json
#   CONFLICT (modify/delete): python/legacy_loader.py deleted in HEAD and modified in branch-b. ...
git status
git log --merge --oneline                     # commits touching conflicted files

# 1) SQL: combine both edits manually, then
git add sql/usp_load_fact_sales.sql
# 2) JSON: keep both activities, fix commas/brackets
python -m json.tool adf/pipeline/pl_ingest_orders.json > /dev/null && git add adf/pipeline/pl_ingest_orders.json
# 3) modify/delete: decision = keep deletion (legacy code retired)
git rm python/legacy_loader.py
git diff --cached --check
git commit -m "Merge branch-b: combine fact_sales logic and both copy activities"

# practise abort + rebase variant
git switch branch-b && git rebase main         # conflicts again? 'ours' = main here, 'theirs' = branch-b commit
git rebase --abort

Expected results

  • Three different conflict messages appear; after resolution git status is clean and the merge commit exists.
  • python -m json.tool exits without error; SQL file contains both intended changes.

Validation steps

  • git show --cc HEAD (combined diff) reviewed and explained in docs/conflict-decisions.md.
  • No <<<<<<< markers: git grep -n "<<<<<<<" returns nothing.

Troubleshooting

Problem Fix
Lost the other side's change after "accept current" git checkout -m <file> re-creates conflict markers (before commit)
Merge got messy git merge --abort and start again
JSON valid but ADF rejects it Validate in ADF Studio (Validate all) — references may be broken

Interview questions

How do you recreate conflict markers after a wrong resolution (before committing)?

git checkout -m <file> (or git restore --merge <file>) re-creates the conflicted state.

What is a modify/delete conflict and how do you resolve it?

One side deleted a file the other modified; resolve by git add (keep) or git rm (delete) according to the decision.

Earlier course version of this project (S40)

Objective: Resolve every major type of conflict confidently.

Scenarios to create and resolve:

# Conflict type How to create
1 Content conflict Edit the same WHERE line of usp_load_customers.sql on two branches
2 Modify/delete Delete dw.vw_sales.sql on one branch, modify it on another
3 Rename/modify Rename extract_orders.py on one branch, edit it on another (observe auto-resolution)
4 Add/add Create config/settings.yaml with different content on two branches
5 Rebase conflict Rebase a 3-commit branch where 2 commits conflict with main
6 Remote conflict Push from rdp-dev2; edit same line in the other clone; git pull --rebase
7 Stash conflict Stash a change, commit a conflicting change, git stash pop

Resolution techniques to use at least once each:

git status
git diff --name-only --diff-filter=U
git config --global merge.conflictstyle zdiff3
# manual edit / VS Code merge editor
git checkout --ours <file>      # or --theirs
git rm <file>                   # for modify/delete when choosing delete
git add <file>

Interview questions

Walk me through your end-to-end CI/CD for a data platform.

PR validation per component (tests, DACPAC, ADF npm validate, bundle validate) as required checks; build artifacts once on main; auto-deploy Test with integration/DQ tests; tag → approval → Prod using OIDC and Key Vault; release notes and deployment history; rollback by redeploying previous tag artifacts.
