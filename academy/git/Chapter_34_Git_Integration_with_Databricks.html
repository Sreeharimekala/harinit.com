Learning objectives

Chapter introduction

What it is. Databricks integrates with Git through Git folders (formerly Repos) in the workspace and through Declarative Automation Bundles (formerly Databricks Asset Bundles) for deploying jobs, pipelines and notebooks as code via the Databricks CLI.

Why it matters. Notebooks are code. Git folders give branching and PRs in the workspace; bundles give repeatable deployments to dev/test/prod workspaces from CI/CD.

Where it is used. Lakehouse transformation layers (bronze/silver/gold), Lakeflow/DLT pipelines, ML code.

In this course's project. Stage 6: Karan works in a Git folder on feature/RDP-115-silver-orders; the databricks/ folder contains databricks.yml defining the rdp_orders job; CI validates the bundle on PRs and deploys to test and prod targets.

Introduction to Databricks Git Folders

Source S40 · 1. Introduction to Databricks Git Folders

1.1 Definition

Git folders (previously called Databricks Repos) are workspace folders that are linked to a remote Git repository. They let you clone a repo into the workspace and perform Git operations — branch, pull, commit, push, merge, rebase — from the Databricks UI.

1.2 Supported providers

GitHub, GitHub Enterprise, Azure DevOps (Azure Repos), GitLab, Bitbucket Cloud/Server, AWS CodeCommit.

1.3 What can be versioned

Asset How it's stored
Notebooks (Python, SQL, Scala, R) Source files (.py, .sql, .scala, .r) with Databricks markers, or .ipynb
Python modules Regular .py files
SQL files, YAML, JSON, configs Workspace files
Bundle configuration databricks.yml and resources/*.yml
Tests tests/ folder

1.4 Git folders vs Asset Bundles

  • Git folders — interactive development in the workspace.
  • Asset Bundles — packaging and deployment of code + jobs/pipelines as infrastructure-as-code to each environment.

34.19

Cloning Repositories

Source S40 · 5. Cloning Repositories
  • Creating a Git folder clones the repository's default branch into the workspace.
  • Each developer should clone into their own user folder — not a shared folder — to avoid overwriting each other's work.
  • Large repos: use sparse checkout; note workspace limits on repository/file sizes (check current docs).
  • Production code should not run from personal Git folders — use bundles/jobs pointing to Git references (sections 11–14).

34.21

Notebook Version Control

Source S40 · 7. Notebook Version Control

7.1 Notebook source format

A Python notebook committed via Git folders looks like:

# Databricks notebook source
# MAGIC %md
# MAGIC # Load silver orders

# COMMAND ----------

from rdp_etl.transform import clean_orders_spark

# COMMAND ----------

dbutils.widgets.text("env", "dev")
env = dbutils.widgets.get("env")

df = spark.read.table(f"rdp_{env}.bronze.orders")
clean_orders_spark(df).write.mode("overwrite").saveAsTable(f"rdp_{env}.silver.orders")

Markers (# COMMAND ----------, # MAGIC) keep cells and magic commands; diffs are readable in PRs.

7.2 Outputs

By default outputs are not committed (clean diffs, no data leakage). For .ipynb notebooks, admins/users can configure whether outputs are committed (.databricks/commit_outputs) — keep it off unless needed.

7.3 Best practices

  • Notebooks are thin orchestration; business logic in Python modules (testable).
  • Parameterise with widgets/job parameters — no hard-coded environment names.
  • No secrets — use dbutils.secrets.get(scope, key).

Python File Version Control

Source S40 · 8. Python File Version Control

Git folders support arbitrary files, so you can keep a proper package next to notebooks:

databricks/
├── notebooks/
│   └── load_silver_orders.py
├── src/
│   └── rdp_etl/
│       ├── __init__.py
│       └── transform.py
└── tests/
    └── test_transform.py

Import modules from notebooks in the same Git folder:

import sys, os
sys.path.append(os.path.abspath("../src"))     # relative to notebook; the repo root is often on sys.path already
from rdp_etl.transform import clean_orders_spark

# src/rdp_etl/transform.py
from pyspark.sql import DataFrame, functions as F

def clean_orders_spark(df: DataFrame) -> DataFrame:
    return (df.filter(F.col("order_date").isNotNull())
              .filter(F.col("amount") >= 0)
              .withColumn("order_date", F.to_date("order_date")))

Use %autoreload during development, and unit-test modules locally/CI with pytest + local Spark.

Pulling and Pushing Changes

Source S40 · 10. Pulling and Pushing Changes

10.1 Daily workflow in Databricks

1. Git dialog → Pull (on main) to get latest
2. Create branch feature/DE-1900-silver-orders
3. Edit notebooks/modules; run interactively
4. Git dialog → review diff → commit message → Commit & Push
5. Open PR in GitHub / Azure DevOps (link shown in dialog)
6. Review, CI checks, merge
7. Pull main again; delete feature branch

10.2 Local IDE workflow (alternative)

Develop in VS Code with the Databricks extension / Databricks Connect, use normal Git CLI, and sync to the workspace or deploy via bundles — the same repository works in both places.

# edit in VS Code; run with Databricks Connect

11.2 Jobs from Git

Databricks Jobs can run code directly from a Git provider reference (branch, tag or commit) instead of workspace copies:

git_source:
  git_url: https://github.com/company/retail-data-platform
  git_provider: gitHub
  git_tag: v2.6.0

This guarantees production runs exactly the tagged code. (Bundles are usually preferred for full deployment.)

11.3 Production Git folders (legacy pattern)

Some teams keep a Git folder in a shared production location updated by CI via the Repos API (databricks repos update <id> --branch main). Bundles are now the recommended approach.

34.26

Databricks Asset Bundles

Source S40 · 12. Databricks Asset Bundles

12.1 Definition

Databricks Asset Bundles (DABs) describe Databricks resources — jobs, Lakeflow/Delta Live Tables pipelines, ML experiments, models, dashboards, clusters — together with source files, in YAML stored in Git, and deploy them with the Databricks CLI to one or more targets (environments).

12.2 Project layout

databricks/
├── databricks.yml
├── resources/
│   ├── load_orders_job.yml
│   └── orders_pipeline.yml
├── src/
│   ├── notebooks/load_silver_orders.py
│   └── rdp_etl/...
└── tests/

12.3 databricks.yml

bundle:
  name: retail-data-platform

include:
  - resources/*.yml

variables:
  catalog:
    description: Unity Catalog name per environment
    default: rdp_dev

targets:
  dev:
    mode: development            # prefixes resources with [dev <user>], pauses schedules
    default: true
    workspace:
      host: https://adb-1111111111111111.11.azuredatabricks.net

  test:
    workspace:
      host: https://adb-2222222222222222.22.azuredatabricks.net
    variables:
      catalog: rdp_test

  prod:
    mode: production
    workspace:
      host: https://adb-3333333333333333.33.azuredatabricks.net
      root_path: /Workspace/Shared/.bundle/${bundle.name}/${bundle.target}
    variables:
      catalog: rdp_prod
    run_as:
      service_principal_name: 00000000-0000-0000-0000-000000000000

12.4 Job resource

# resources/load_orders_job.yml
resources:
  jobs:
    load_orders:
      name: load_orders_${bundle.target}
      tasks:
        - task_key: silver_orders
          notebook_task:
            notebook_path: ../src/notebooks/load_silver_orders.py
            base_parameters:
              catalog: ${var.catalog}
          environment_key: default        # serverless; or job_cluster_key for classic clusters
      environments:
        - environment_key: default
          spec:
            client: "1"
      schedule:
        quartz_cron_expression: "0 0 2 * * ?"
        timezone_id: Asia/Kolkata
      email_notifications:
        on_failure: [data-team@company.com]

(Adjust compute configuration — serverless environments or job clusters — to what your workspace supports.)

12.5 CLI commands

databricks bundle init                     # create from a template (default-python, etc.)
databricks bundle validate -t dev          # check configuration
databricks bundle deploy -t dev            # upload files + create/update resources
databricks bundle run -t dev load_orders   # run a job/pipeline
databricks bundle summary -t dev           # what's deployed
databricks bundle destroy -t dev           # remove deployed resources

12.6 Why bundles

Everything as code in Git; reproducible deployments per environment; reviewable in PRs; easy CI/CD; development mode isolates each developer's copies.

34.27

CI/CD with Databricks

Source S40 · 13. CI/CD with Databricks

13.1 Authentication for CI

  • Use a service principal per environment (Microsoft Entra ID or Databricks-managed).
  • OAuth machine-to-machine (client ID + secret) or workload identity federation (GitHub OIDC / Azure DevOps) — avoid personal tokens.

13.2 GitHub Actions pipeline

# .github/workflows/databricks.yml
name: Databricks CI/CD

on:
  pull_request:
    paths: ['databricks/**']
  push:
    branches: [main]
    paths: ['databricks/**']
  workflow_dispatch:

jobs:
  validate:
    runs-on: ubuntu-latest
    defaults: { run: { working-directory: databricks } }
    env:
      DATABRICKS_HOST: ${{ vars.DATABRICKS_HOST_DEV }}
      DATABRICKS_CLIENT_ID: ${{ secrets.DATABRICKS_CLIENT_ID_DEV }}
      DATABRICKS_CLIENT_SECRET: ${{ secrets.DATABRICKS_CLIENT_SECRET_DEV }}
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-python@v5
        with: { python-version: '3.11' }
      - run: pip install pytest pyspark==3.5.* && pytest tests
      - uses: databricks/setup-cli@main
      - run: databricks bundle validate -t dev

  deploy-test:
    if: github.ref == 'refs/heads/main'
    needs: validate
    runs-on: ubuntu-latest
    environment: test
    defaults: { run: { working-directory: databricks } }
    env:
      DATABRICKS_HOST: ${{ vars.DATABRICKS_HOST }}
      DATABRICKS_CLIENT_ID: ${{ secrets.DATABRICKS_CLIENT_ID }}
      DATABRICKS_CLIENT_SECRET: ${{ secrets.DATABRICKS_CLIENT_SECRET }}
    steps:
      - uses: actions/checkout@v4
      - uses: databricks/setup-cli@main
      - run: databricks bundle deploy -t test
      - run: databricks bundle run -t test load_orders     # smoke test

  deploy-prod:
    needs: deploy-test
    runs-on: ubuntu-latest
    environment: prod                                       # required reviewers
    defaults: { run: { working-directory: databricks } }
    env:
      DATABRICKS_HOST: ${{ vars.DATABRICKS_HOST }}
      DATABRICKS_CLIENT_ID: ${{ secrets.DATABRICKS_CLIENT_ID }}
      DATABRICKS_CLIENT_SECRET: ${{ secrets.DATABRICKS_CLIENT_SECRET }}
    steps:
      - uses: actions/checkout@v4
      - uses: databricks/setup-cli@main
      - run: databricks bundle deploy -t prod

(Environment-scoped vars/secrets hold each environment's host and service principal.)

13.3 Azure DevOps pipeline (outline)

steps:
  - script: curl -fsSL https://raw.githubusercontent.com/databricks/setup-cli/main/install.sh | sh

34.28

Deploying Notebooks Across Environments

Source S40 · 14. Deploying Notebooks Across Environments

14.1 Environment strategy

Environment Workspace Catalog Deployed by
Dev Dev workspace (users' Git folders + bundle deploy -t dev development mode) rdp_dev Developers
Test Test workspace rdp_test CI/CD on merge to main
Prod Prod workspace rdp_prod CI/CD with approval (tag/main)

14.2 Rules

  • Same code, different configuration: bundle variables/targets set catalog names, cluster sizes, schedules, permissions.
  • Run as service principal in Test/Prod.
  • Lock down Prod workspace: users can view but not edit deployed bundle files; changes only via CI/CD.
  • Secrets via Databricks secret scopes backed by Azure Key Vault per environment.
  • Promote by tag: deploy v2.6.0 to Prod; rollback by redeploying the previous tag.
  • Legacy approaches (still seen): Workspace import/export via CLI/REST (databricks workspace import-dir), Repos API updating a production Git folder — prefer bundles for new work.

Real-time scenarios

Source S35, S40 · Notebook diff is unreadable in PRs

.ipynb files contain JSON with outputs. Use source format (.py) for notebooks in Git, or clear outputs before committing; configure the Git folder's default notebook format accordingly.

Course addition · Developer's Git folder shows a conflict on pull

Resolve in the Git dialog (choose changes / edit), or reset the branch to remote if local work isn't needed; for complex conflicts, resolve locally with your IDE and push.

  • Notebooks as thin orchestration; logic in tested Python modules.
  • Source-format notebooks and no outputs in Git.
  • Service principals and OAuth/OIDC for CI/CD; no personal tokens in pipelines.
  • Bundle variables/targets for environment differences; validate bundles on every PR.

Beginner
What is a Databricks Git folder?

A workspace folder linked to a Git repository branch, letting you clone, branch, commit, pull and push notebooks and files from the workspace.

Intermediate
What are Declarative Automation Bundles (formerly Databricks Asset Bundles)?

YAML-defined collections of Databricks resources (jobs, pipelines, etc.) plus code, deployed with databricks bundle deploy to targets like dev/test/prod.

Why avoid running production jobs from personal Git folders?

They depend on a user's branch state and identity; production should run deployed, reviewed versions under a service principal.

Advanced
How does mode: development differ from mode: production in a bundle target?

Development mode prefixes resource names per user, pauses schedules and allows concurrent personal deployments; production mode enforces stricter checks (e.g. run_as, no personal prefixes).

Scenario
Design Databricks CI/CD for three workspaces.

Repo with databricks.yml + targets per workspace; PR → bundle validate + unit tests; merge → deploy test + run integration; tag → approval → deploy prod as service principal; secrets via secret scopes/Key Vault; Unity Catalog per environment.
