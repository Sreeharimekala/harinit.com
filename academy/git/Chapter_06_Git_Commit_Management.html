6.1

What is a commit?

Source S07 · Chapter manual · 1. What is a commit?

A Git commit is a recorded snapshot of the project content represented by the staging area at the time the commit is created. It is saved in the local repository's object database and connected to the existing history.

A commit is more than a simple “save”. It records a project state that can be inspected, compared, checked out, or used as the base for later work.

Example

git status
git add sql/load_customers.sql
git commit -m "Add active customer filter"

The commit contains the staged version of sql/load_customers.sql. Any unstaged edits made after staging are not included in that commit.

Remember: A commit is local by default. It is not automatically uploaded to GitHub, GitLab, Bitbucket, or Azure Repos. Sharing commits normally requires git push.
6.2

Understanding commit history

Source S07 · Chapter manual · 2. Understanding commit history

Commit history is the sequence and graph of commits connected through parent relationships. On a simple branch, commits often appear as a linear sequence. When branches merge, the history becomes a graph.

Commit A
Initial project
→
Commit B
Add SQL logic
→
Commit C
Add validation
→
Commit D
Fix null handling

Simplified linear history: each commit points to its parent.

# View history
git log

# Compact history
git log --oneline

# Visualize branches and merges
git log --oneline --graph --decorate --all

# Show the most recent 10 commits
git log -10

Git history is not just a numbered list. Branches are references to commits, and merge commits can have more than one parent. The graph records how lines of development connect.

6.3

Anatomy of a Git commit

Source S07 · Chapter manual · 3. Anatomy of a Git commit

A commit object contains key pieces of metadata and a reference to the top-level tree representing the project snapshot.

Commit componentDescription
TreeIdentifies the top-level directory snapshot for this commit. Trees reference files (blobs) and subdirectories (other trees).
ParentIdentifies the previous commit or commits from which this commit was created. The initial commit has no parent.
AuthorName, email, and timestamp associated with the original author of the change.
CommitterName, email, and timestamp for the person who created this commit object. This can differ from the author, for example after a patch is applied.
MessageHuman-readable explanation of the commit.
Commit IDHash identifying the commit object and its contents.

Conceptual commit structure

tree      <tree-object-id>
parent    <parent-commit-id>
author    Developer Name <developer@example.com> <timestamp>
committer Developer Name <developer@example.com> <timestamp>

Add active customer filter

This is a simplified illustration of the commit object's textual representation. Git hashes the object content, including its header and message, to calculate the object ID.

Inspect commit metadata

# Show latest commit details and patch
git show

# Show commit metadata without the patch
git show --no-patch --format=fuller HEAD

# Show raw commit object content
git cat-file -p HEAD
6.4

Commit ID (SHA)

Source S07 · Chapter manual · 4. Commit ID (SHA)

Every commit object is identified by a hash, commonly called its commit hash or SHA. The ID is calculated from the commit object's content, so changing the commit message, tree, parent, or metadata produces a different commit ID.

In many existing repositories, object IDs use SHA-1 and are displayed as 40 hexadecimal characters. Git also supports repositories using the SHA-256 object format, where IDs are longer. Do not assume every repository uses the same hash length.

# Show full commit IDs
git log --format="%H %s"

# Show abbreviated commit IDs
git log --oneline

# Show the current commit ID
git rev-parse HEAD

Full and abbreviated IDs

  • Full ID: The complete object identifier.
  • Abbreviated ID: A shorter prefix that Git can resolve uniquely in that repository at that time.
  • HEAD: A symbolic reference to the current checkout; on a branch, it normally points to that branch.
A commit ID is content-derived, not a sequential number such as commit 1, commit 2, commit 3. Two repositories can have different commits with different IDs even if their histories look similar.
6.5

Parent commits

Source S07 · Chapter manual · 5. Parent commits

A parent commit is the commit from which a new commit directly follows. Parent links are what allow Git to build the history graph.

  • An initial/root commit has no parent.
  • A normal commit usually has one parent.
  • A merge commit usually has two or more parents.

Simple history

A
Root
→
B
Parent: A
→
C
Parent: B

Merge history

A
→
B
→
D
Merge commit
C
↗

Conceptual illustration: merge commit D connects two lines of development and has both B and C as parents.

# Show parent commit IDs for HEAD
git rev-list --parents -n 1 HEAD

# Show the first parent of HEAD
git rev-parse HEAD^

# Show the commit before HEAD
git show HEAD~1

HEAD~1 means the first-parent commit one step back. The caret notation such as HEAD^2 can refer to the second parent of a merge commit.

6.6

Writing meaningful commit messages

Source S07 · Chapter manual · 6. Writing meaningful commit messages

A commit message explains the purpose of a change. Good messages make history easier to review, troubleshoot, audit, and understand months later.

Recommended approach

  • Keep the subject concise and specific.
  • Use an imperative verb: Add, Fix, Update, Remove, or Refactor.
  • Explain the reason or context in the body when the change is not self-explanatory.
  • Separate the subject from the body with a blank line.
  • Follow your team's convention, such as ticket IDs or Conventional Commits, if one exists.
Weak messageBetter message
updateUpdate customer extraction filter
fix bugFix null handling in customer validation
changesAdd retry handling to source ingestion
final codeRemove duplicate rows from sales staging load

Example for a Data Engineering project

Fix duplicate customer records in daily load

Deduplicate source rows using CustomerID and UpdatedAt
before merging records into the warehouse dimension.

This prevents the daily load from failing when the source
delivers multiple updates for the same customer.
6.7

Single-line commits

Source S07 · Chapter manual · 7. Single-line commits

A single-line commit uses a concise subject message. This is suitable for a small, self-contained change whose purpose is clear.

git add sql/load_customers.sql
git commit -m "Add active customer filter"

Other examples:

git commit -m "Create customer validation script"
git commit -m "Fix date conversion in sales load"
git commit -m "Update pipeline deployment parameters"

Keep the message focused on the change. Avoid putting a long explanation into an oversized subject line; use a multi-line message when more context is needed.

6.8

Multi-line commits

Source S07 · Chapter manual · 8. Multi-line commits

A multi-line commit message has a subject followed by a blank line and a descriptive body. The subject summarizes the change; the body explains what changed and why.

Using the configured text editor

git commit

Git opens the editor configured for your environment. Enter the subject, a blank line, and then the body. Save and close the editor to complete the commit.

Using multiple -m options

git commit \
  -m "Fix customer load duplicate handling" \
  -m "Deduplicate source records by CustomerID and UpdatedAt.
This prevents duplicate source rows from breaking the
warehouse load."

In PowerShell or Windows Command Prompt, you can enter the command on one line if shell continuation syntax differs:

git commit -m "Fix customer load duplicate handling" -m "Deduplicate source records by CustomerID and UpdatedAt to prevent duplicate rows from breaking the warehouse load."
The exact style is a team convention. A useful message answers: What changed? and, when needed, Why was it necessary?
6.9

Amending previous commits

Source S07 · Chapter manual · 9. Amending previous commits

git commit --amend replaces the latest commit with a new commit. It is commonly used to add a missed file or correct the latest commit message.

Add a forgotten file to the latest commit

# Stage the file you forgot
git add README.md

# Create a replacement for the latest commit
git commit --amend --no-edit

Change the latest commit message

git commit --amend -m "Improve customer validation rules"

Amending creates a new commit object with a different ID. The previous commit is no longer the branch tip, although it may remain recoverable for a time through reflog and object retention.

Shared-history warning: Amend is safest before you push the commit. If the old commit has already been shared, amending rewrites history. Coordinate with collaborators and follow team policy before force-pushing any replacement history.
6.10

Modifying commit messages

Source S07 · Chapter manual · 10. Modifying commit messages

There are different approaches depending on whether the commit is the latest commit or an older commit.

Modify the latest commit message

git commit --amend -m "Corrected latest commit message"

Modify an older commit message

Use interactive rebase to reword a commit in the current branch's recent history:

# Open an interactive rebase for the last 4 commits
git rebase -i HEAD~4

In the editor, change pick to reword beside the commit whose message you want to change. Save and close. Git then prompts you to enter a new message.

Rebase rewrites commit IDs. This is generally appropriate for unpublished local commits. Rewriting commits already used by others can disrupt shared history. Do not rebase commits that your team expects to remain unchanged on a shared branch unless the team has agreed on the procedure.
6.11

Viewing previous commits

Source S07 · Chapter manual · 11. Viewing previous commits

Git offers several ways to inspect historical commits, including summaries, patches, file-specific history, and metadata.

# List all reachable commits
git log

# Compact list
git log --oneline

# Latest five commits
git log -5 --oneline

# Show a selected commit
git show <commit-id>

# Show the commit before HEAD
git show HEAD~1

# Show a file's history
git log --follow -- sql/customer_load.sql

# Show commit metadata
git show --no-patch --format=fuller <commit-id>

--follow can follow the history of a single file across detected renames. It is intended for use with one path.

6.12

Comparing commits

Source S07 · Chapter manual · 12. Comparing commits

Use git diff to compare the project state between two commits, or between a commit and your current working state.

# Compare two commits
git diff <commit-A> <commit-B>

# Compare a commit with the current HEAD
git diff <commit-id> HEAD

# Compare only one file between commits
git diff <commit-A> <commit-B> -- sql/customer_load.sql

# Show a summary of changed files
git diff --stat <commit-A> <commit-B>

# Show names and change types only
git diff --name-status <commit-A> <commit-B>

Example scenario

You want to know what changed in the customer load script between last week's version and the current version. Find the two commit IDs using git log, then run:

git diff 1a2b3c4 5d6e7f8 -- sql/customer_load.sql

The IDs above are examples. Replace them with IDs from your own repository.

6.13

Reverting commits

Source S07 · Chapter manual · 13. Reverting commits

git revert creates a new commit that applies the inverse of the changes introduced by an earlier commit. It preserves the existing history rather than moving the branch backward.

Revert the latest commit

git revert HEAD

Revert a specific commit

git revert <commit-id>

Revert without automatically committing

git revert --no-commit <commit-id>
git status
# Review the result, then commit when ready
git commit -m "Revert customer load filter change"

Git may open an editor for the revert message. If the original change conflicts with later changes, you may need to resolve conflicts, stage the resolutions, and continue the revert.

# After resolving conflicts:
git add <resolved-files>
git revert --continue

# Cancel an in-progress revert
git revert --abort
Best for shared branches: Revert is usually the safer way to undo a commit that has already been pushed, because it adds a new corrective commit instead of rewriting shared history.
6.14

Resetting commits

Source S07 · Chapter manual · 14. Resetting commits

git reset moves the current branch reference to a selected commit. Depending on the mode, it can also reset the staging area and working tree. Unlike revert, reset does not create a new commit that reverses the changes.

ModeBranch tip / HEADIndexWorking treeTypical use
--softMoves to targetPreservedPreservedRemove latest commit but keep changes staged.
--mixed (default)Moves to targetReset to targetPreservedRemove latest commit and leave changes unstaged.
--hardMoves to targetReset to targetReset to targetDiscard local tracked changes and move branch back.

Examples

# Undo the latest commit but keep changes staged
git reset --soft HEAD~1

# Undo the latest commit and keep changes in working tree, unstaged
git reset --mixed HEAD~1

# Move branch back and discard tracked changes after target
git reset --hard HEAD~1
Danger: git reset --hard can permanently discard uncommitted tracked changes. Moving a branch backward can also remove commits from that branch's visible history. Avoid rewriting commits already shared with others unless you have coordinated the change.

Reset is not the same as deleting a commit object immediately

Reset normally moves a reference. The old commit object may still exist for a while and can often be found through the reflog. Git may eventually prune unreachable objects according to repository maintenance and retention rules.

6.15

Recovering deleted commits

Source S07 · Chapter manual · 15. Recovering deleted commits

A commit may appear to disappear after a reset, rebase, amend, or branch movement. It may still be recoverable because Git records recent movements of references in the reflog.

Step 1 — Inspect the reflog

git reflog

The reflog shows recent local updates to references such as HEAD and branch tips. You may see entries such as a previous commit, a reset, or an amend operation.

Step 2 — Identify the commit to recover

# Inspect recent HEAD movements
git reflog --date=local

# Inspect a candidate commit
git show <candidate-commit-id>

Step 3 — Create a recovery branch (recommended)

git branch recovery-work <candidate-commit-id>

This creates a branch pointing to the candidate commit without moving your current branch. Inspect the recovery branch and verify the files and history.

Step 4 — Restore the branch if appropriate

If you have confirmed that the candidate is the correct commit and understand the impact, you can switch to the recovery branch or move the intended branch reference as part of a planned recovery.

git switch recovery-work
Recovery limitations: Reflog is local to your repository and entries expire according to configuration and maintenance. Uncommitted changes that were never recorded may not be recoverable this way. If a commit has been pruned and no other copy exists, recovery may be difficult or impossible. Avoid running aggressive cleanup while investigating lost work.

Other recovery options

  • Check other local branches and tags.
  • Check remote-tracking branches with git log --all --oneline --graph.
  • Check whether a teammate or remote repository has the commit.
  • Use git fsck --no-reflogs --unreachable as an advanced diagnostic when a commit is not found in normal references. Review results carefully; not every unreachable object is a useful commit.
6.16

Choosing between amend, revert, and reset

Source S07 · Chapter manual · Choosing between amend, revert, and reset
OperationWhat it doesBest suited for
git commit --amendReplaces the latest commit with a new commit.Correcting the latest local commit or adding a forgotten staged file.
git revert <id>Creates a new commit that reverses an earlier commit's changes.Undoing a commit in shared history safely.
git reset --softMoves branch tip; preserves staged and working-tree changes.Reworking the latest local commit while keeping changes staged.
git reset --mixedMoves branch tip; resets index, keeps working-tree files.Reworking a local commit with changes left unstaged.
git reset --hardMoves branch tip and resets index and tracked working tree.Discarding local tracked changes when you are absolutely certain.
git reflogShows recent local reference movements.Finding a previous commit after a reset, amend, or rebase.
Simple rule: For a commit already shared with your team, prefer git revert. For unpublished local work, amend or reset may be appropriate when you understand the consequences.
6.17

What is a Commit?

Source S40 · 1. What is a Commit?

1.1 Definition

A commit is a permanent, immutable snapshot of the staged project at a point in time, together with metadata (author, committer, date, message) and a link to its parent commit(s).

1.2 Characteristics

  • Identified by a unique hash (SHA).
  • Immutable — any change produces a new commit with a new hash.
  • Linked to its parent(s), forming a history graph.
  • Stored in the local repository until pushed.

1.3 Think of it as

A save point in a game — you can always return to it, compare with it, or build from it.

6.18

Understanding Commit History

Source S40 · 2. Understanding Commit History

2.1 History is a chain (graph)

a1b2c3d ◄── 3f2a7d1 ◄── 9c8b7a6 ◄── e4f5a6b   (main, HEAD)
(root)                                         newest

Each commit points backwards to its parent. The branch name points to the newest commit.

2.2 Viewing history

git log --oneline
git log --oneline --graph --all
git log --stat
git log --format="%h | %an | %ad | %s" --date=short

2.3 Linear vs non-linear history

  • Linear — every commit has one parent (fast-forward merges, rebase).
  • Non-linear — merge commits with two parents show where branches were joined.

6.20

Commit ID (SHA)

Source S40 · 4. Commit ID (SHA)

4.1 Definition

The commit ID is a 40-character hexadecimal SHA-1 hash calculated from the commit's entire content (tree, parents, author, committer, dates, message).

9c8b7a6d5e4f3a2b1c0d9e8f7a6b5c4d3e2f1a0b

4.2 Properties

  • Unique — practically no two commits share a hash.
  • Deterministic — the same content always gives the same hash.
  • Tamper-evident — changing anything (even one character in the message) produces a new hash, and every descendant commit's hash changes too.
  • Short form — the first 7+ characters are usually enough: 9c8b7a6.
git rev-parse HEAD           # full hash
git rev-parse --short HEAD   # short hash
git log --abbrev-commit

Note Git can also use SHA-256 for new repositories (git init --object-format=sha256), producing 64-character IDs; hosting support is still limited.

6.22

Writing Meaningful Commit Messages

Source S40 · 6. Writing Meaningful Commit Messages

6.1 Why messages matter

Commit messages are the documentation of why code changed. During a production incident, a good message saves hours.

Bad Good
update Filter inactive customers from daily load
fixed bug Fix duplicate orders caused by missing join key
changes Add region column to dim_customer
wip Add incremental watermark to orders extract

6.2 The seven rules

  1. Separate subject from body with a blank line.
  2. Limit the subject line to about 50 characters.
  3. Capitalise the subject line.
  4. Do not end the subject line with a period.
  5. Use the imperative mood ("Add", "Fix", "Remove" — as if completing "If applied, this commit will …").
  6. Wrap the body at 72 characters.
  7. Use the body to explain what and why, not how.

6.3 Conventional Commits format

<type>(<optional scope>): <description>

[optional body]

[optional footer(s)]
Type Use
feat New feature
fix Bug fix
docs Documentation only
style Formatting, no logic change
refactor Code restructuring without behaviour change
perf Performance improvement
test Adding/fixing tests
build Build system or dependencies
ci CI/CD configuration
chore Maintenance
revert Reverting a previous commit

Examples:

feat(sql): add dim_product table
fix(etl): handle null order dates
perf(sql): add index on fact_sales.order_date
ci: run pytest on pull requests
feat(api)!: rename customer_id to cust_id     ← "!" marks a breaking change

6.4 Linking work items

fix(adf): retry copy activity on transient errors

Refs: DE-1423          (Jira)
Fixes #42              (GitHub issue — closes on merge)
AB#1423                (Azure Boards)

Multi-Line Commits

Source S40 · 8. Multi-Line Commits

Use when the reason, impact or context needs explanation.

Option 1 — multiple -m flags (each becomes a paragraph):

git commit -m "Fix duplicate customers in daily load" \

6.25

Amending Previous Commits

Source S40 · 9. Amending Previous Commits

9.1 Purpose

git commit --amend replaces the last commit with a new one — to add forgotten files, fix content or change the message.

9.2 Examples

# Forgot to include a file
git add sql/views/vw_active_customers.sql
git commit --amend --no-edit

# Fix a small mistake in the last commit's content
# (edit the file)
git add sql/procedures/usp_load_customers.sql
git commit --amend --no-edit

# Change author on the last commit
git commit --amend --author="Ravi Kumar <ravi.kumar@company.com>" --no-edit

# Reset the date to now
git commit --amend --no-edit --date=now

9.3 Rules

Warning Amending creates a new commit hash. If the original commit was already pushed, amending rewrites shared history. Only amend unpushed commits, or commits on your own branch followed by git push --force-with-lease.

6.26

Modifying Commit Messages

Source S40 · 10. Modifying Commit Messages

10.1 Last commit (not pushed)

git commit --amend -m "Add active customers view"

10.2 Older commits — interactive rebase

git rebase -i HEAD~3

Change pick to reword (or r) for the commits to rename:

pick   a1b2c3d Add staging table
reword b2c3d4e add proc          ← will prompt for a new message
pick   c3d4e5f Add view

Save, close, write the new message when prompted.

10.3 Already pushed?

  • On your own feature branch: reword, then git push --force-with-lease.
  • On a shared branch (main): do not rewrite; live with it or add a clarifying commit/PR comment.

Comparing Commits

Source S40 · 12. Comparing Commits
git diff 3f2a7d1 9c8b7a6                    # all changes between two commits
git diff 3f2a7d1 9c8b7a6 -- sql/            # only SQL folder

6.29

Reverting Commits

Source S40 · 13. Reverting Commits

13.1 Definition

git revert creates a new commit that applies the inverse of a previous commit. History is preserved — safe on shared branches.

A ── B ── C ── D        git revert C        A ── B ── C ── D ── C'   (C' undoes C)

13.2 Examples

git revert 3f2a7d1                    # opens editor with "Revert ..." message
git revert 3f2a7d1 --no-edit          # use default message
git revert HEAD~2..HEAD               # revert the last two commits (each gets a revert commit)
git revert --no-commit a1b2 c3d4      # stage several reverts, then one commit
git commit -m "Revert orders load changes"
git revert -m 1 <merge-commit>        # revert a merge, keeping the first parent's side

13.3 Conflicts

If later commits touched the same lines, resolve the conflict, git add, then git revert --continue (or --abort).

6.30

Resetting Commits

Source S40 · 14. Resetting Commits

14.1 Definition

git reset moves the current branch pointer back to an earlier commit; the later commits are no longer part of the branch.

Before: A ── B ── C ── D (main)        git reset --hard B        After: A ── B (main)

14.2 Modes

Command Commits C, D Their changes
git reset --soft B Removed from branch Kept, staged
git reset --mixed B (default) Removed Kept, unstaged
git reset --hard B Removed Discarded

14.3 Examples

git reset --soft HEAD~1      # undo the last commit, keep changes ready to re-commit
git reset --soft HEAD~3      # squash last 3 commits: then git commit -m "..."
git reset HEAD~1             # undo commit and unstage
git reset --hard HEAD~1      # throw away the last commit completely

Warning Use reset only on commits that have not been shared. For pushed commits use git revert.

6.31

Recovering Deleted Commits

Source S40 · 15. Recovering Deleted Commits

15.1 The reflog

Git records every movement of HEAD and branch pointers in the reflog. Even "deleted" commits remain in the object database until garbage collection removes them (by default, unreachable reflog entries expire after 30 days; reachable after 90 days).

git reset --hard HEAD~2     # accidentally removed two commits
git reflog

a1b2c3d HEAD@{0}: reset: moving to HEAD~2
9c8b7a6 HEAD@{1}: commit: Add fact_sales table
4d5e6f7 HEAD@{2}: commit: Add dim_product table
a1b2c3d HEAD@{3}: commit: Initial project structure

15.2 Recover

git reset --hard 9c8b7a6          # move branch back
# or keep current state and create a rescue branch:
git branch rescue-fact-sales 9c8b7a6

15.3 Recovering a deleted branch

git branch -D feature/orders      # deleted
git reflog | grep feature/orders  # find its last commit
git branch feature/orders <sha>

15.4 When reflog doesn't help

git fsck --lost-found             # lists dangling commits/blobs
git show <dangling-sha>

Added topics, conflicts & verification

Source conflict — "Fix and recommit" vs "revert" for shared mistakes

S41 suggests fixing a pushed bad commit by amending/recommitting. S07/S40 recommend revert. Resolution: for commits already pushed to a shared branch, use git revert or a new fixing commit; amend only unpushed commits. Both are valid in their own context — the deciding factor is whether history is shared.

Best practices

Course addition · best practices
  • One logical change per commit; commit often on feature branches.
  • Subject in imperative mood ("Add", "Fix"), ≤ 50 characters, no trailing period; body explains why.

Chapter 6 Interview Questions

Source S07 · Chapter manual · interview

1. What is a Git commit?

A commit is a recorded snapshot of the project content represented by the staging area, along with metadata and parent references.

2. What information does a commit contain?

It references a tree snapshot and contains parent reference(s), author and committer metadata, timestamps, and a commit message.

3. What is a commit SHA?

It is the hash-based object ID identifying the commit. Common repositories use SHA-1 IDs; Git also supports SHA-256 repositories.

4. What is a parent commit?

A parent is the commit directly preceding a commit in history. Root commits have none; merge commits usually have multiple parents.

5. What is the difference between author and committer?

The author is credited with creating the change; the committer is credited with creating the commit object. They can be different people.

6. What happens when you amend a commit?

Git creates a replacement commit for the latest commit. Its ID changes because the commit object content changes.

7. How do you change the latest commit message?

Use git commit --amend -m "New message".

8. How do you change an older commit message?

Use interactive rebase, mark the target commit as reword, and provide the new message. This rewrites history.

9. What is the difference between revert and reset?

Revert creates a new commit that reverses an earlier change. Reset moves the current branch tip and may also reset the index and working tree.

10. Which is safer for undoing a commit already pushed to a shared branch?

Usually git revert, because it preserves existing shared history and adds a corrective commit.

11. What does git reset --soft do?

It moves the branch tip to the target commit while keeping the index and working tree unchanged.

12. What does git reset --hard do?

It moves the branch tip and resets the index and tracked working tree to the target commit, potentially discarding local work.

13. What is reflog?

A local log of recent updates to references, useful for finding commits that are no longer pointed to by a branch or tag.

14. Can you recover a commit after git reset?

Often yes, if the commit remains available. Inspect git reflog, identify the commit ID, and create a recovery branch.

15. Does Git history work like a simple numbered list?

No. It is a directed graph of commits connected by parent links. Branches and merges create multiple paths through that graph.

Beginner
What is a commit ID?

A hash (SHA-1, or SHA-256 in SHA-256 repositories) computed from the commit's content, including its tree, parents, author and message. It uniquely identifies the commit.

How do you change the last commit message?

git commit --amend -m "New message" (only if not pushed).

Intermediate
What is the difference between author and committer?

Author wrote the change; committer created the commit object. They differ after rebase, cherry-pick or when applying someone else's patch.

When do you use revert instead of reset?

When the commit is already shared; revert adds a new inverse commit instead of rewriting history.

Advanced
How long can you recover a commit after git reset --hard?

While a reflog entry references it — by default 30 days for unreachable entries (gc.reflogExpireUnreachable) — and until git gc prunes the objects.

Scenario
You committed to main locally instead of a feature branch and have not pushed. Fix it.

git branch feature/RDP-120-x (keeps the commit), git reset --hard origin/main on main, then git switch feature/RDP-120-x.

  • Good messages: short imperative subject, explanatory body, ticket reference.
