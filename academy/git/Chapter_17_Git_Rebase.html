Learning objectives

Chapter introduction

What it is. Rebase moves (replays) a series of commits onto a new base commit, creating new commits with the same changes. Interactive rebase lets you reorder, edit, squash, fixup or drop commits.

Why it matters. It keeps feature branches current with main without merge commits and lets you clean up history before review — but it rewrites history, so it must be used on branches nobody else depends on.

Where it is used. Updating feature branches, cleaning commits before a PR, "Rebase and merge" PR method, git pull --rebase.

In this course's project. Stage 5: Ravi cleans five "wip" commits into two meaningful commits and rebases onto the latest main before review.

17.1

What is Git Rebase?

Source S18 · Chapter manual · 1. What is Git Rebase?

Rebase takes commits from the current branch that are not in the target base and replays them, one by one, on top of a new base. The result is a new sequence of commits with new commit IDs. Rebase changes history; it does not simply move an existing commit unchanged.

Commands and example

git switch feature/customer-dq
git fetch origin
git rebase origin/main
17.2

Why do we need rebase?

Source S18 · Chapter manual · 2. Why do we need rebase?

Rebase can bring a feature branch up to date with the latest base branch while keeping a linear-looking history. It is also used to clean up local commits before review. It is not inherently better than merge: the right choice depends on team policy, branch sharing and the need to preserve integration history.

Commands and example

git fetch origin
git rebase origin/main
# Review the resulting history
git log --oneline --graph --decorate -15
17.3

Merge vs Rebase

Source S18 · Chapter manual · 3. Merge vs Rebase

Merge combines histories and may create a merge commit; existing commits remain unchanged. Rebase replays commits onto a new base, producing new commit IDs and a more linear history. Merge is generally safe for shared branches. Rebase is most appropriate for private or coordinated feature-branch history.

Commands and example

# Merge latest main into feature
git switch feature
git merge origin/main

# Alternative: replay feature commits on latest main
git rebase origin/main
17.4

Understanding commit history and basic rebase

Source S18 · Chapter manual · 4. Understanding commit history and basic rebase

Git history is a directed acyclic graph (DAG). Rebase identifies commits reachable from the current branch but not from the selected upstream, then replays them onto the new base. Use git log --graph before and after so you can see what changed.

Commands and example

git log --oneline --graph --decorate --all
git fetch origin
git rebase origin/main
git log --oneline --graph --decorate --all
17.5

Interactive rebase

Source S18 · Chapter manual · 5. Interactive rebase

Interactive rebase opens a todo list for the selected commit range. You can choose actions such as pick, reword, edit, squash, fixup and drop. Start with a range such as HEAD~4 to review the last four commits. Do not use an interactive rebase casually on commits already shared with others.

Commands and example

git rebase -i HEAD~4
# Example todo:
# pick   a1b2c3d add source validation
# reword b2c3d4e update documentation
# squash c3d4e5f fix validation edge case
# drop   d4e5f6a temporary debug output
17.6

Squashing commits

Source S18 · Chapter manual · 6. Squashing commits

squash combines a commit with the preceding picked commit and lets you edit the combined message. fixup also combines it but discards the fixup commit's message. Squashing can create a review-friendly commit, but retain meaningful detail in the final message.

Commands and example

git rebase -i HEAD~3
# Change later commits from "pick" to "squash" or "fixup"
# Save and close the editor; review the final message
git log --oneline -5
17.7

Reordering, editing messages and dropping commits

Source S18 · Chapter manual · 7. Reordering, editing messages and dropping commits

In the interactive todo list, reorder lines to change replay order, use reword to change a message, edit to stop at a commit for changes, and drop to omit a commit. Reordering can cause conflicts or change behavior if commits depend on earlier commits. Test the final branch after rewriting.

Commands and example

git rebase -i HEAD~5
# reword <commit> improve commit message
# edit   <commit> adjust transformation logic
# drop   <commit> remove temporary debug commit
# Move todo lines to reorder
17.8

Continuing, aborting and resolving conflicts

Source S18 · Chapter manual · 8. Continuing, aborting and resolving conflicts

When a replay conflicts, Git pauses and marks conflicted files. Resolve the conflict, stage the resolved files, and run git rebase --continue. Use git rebase --skip only when you intentionally want to omit the current patch. Use git rebase --abort to return to the pre-rebase state.

Commands and example

git status
# Resolve conflict markers in files
git add sql/load_orders.sql
git rebase --continue

# If the operation should be cancelled instead:
git rebase --abort
17.9

Rebase best practices and when not to rebase

Source S18 · Chapter manual · 9. Rebase best practices and when not to rebase

Fetch before rebasing, inspect the commit range, keep a backup branch for risky rewrites, run tests afterwards, and coordinate with teammates. Do not rewrite public/shared history unless the team explicitly agrees and everyone knows how to recover. Avoid force-pushing to protected branches. If a rewritten branch must be pushed, prefer git push --force-with-lease over --force; it checks that the remote ref has not advanced unexpectedly.

Commands and example

git fetch origin
git branch backup/feature-before-rebase
git rebase origin/main
# Run tests and inspect history
git push --force-with-lease origin feature/customer-dq
17.10

Data Engineering workflow example

Source S18 · Chapter manual · 10. Data Engineering workflow example

A developer may have three local commits for a pipeline change: implementation, a correction, and documentation. Before opening a pull request, interactive rebase can combine the correction into implementation and improve the messages. If the branch is already shared, coordinate first rather than silently changing its history.

Commands and example

git log --oneline
git rebase -i HEAD~3
# Use fixup/squash/reword as appropriate
pytest
# Push normally if history was not previously shared;
# otherwise coordinate and use --force-with-lease if approved.
17.11

What is Git Rebase?

Source S40 · 1. What is Git Rebase?

1.1 Definition

git rebase re-applies (replays) commits from your branch on top of another base commit, creating new commits with new IDs. It "moves" the starting point of your branch.

1.2 Visual

Before:
main:     A ── B ── E ── F
               \
feature:        C ── D

git switch feature
git rebase main

After:
main:     A ── B ── E ── F
                          \
feature:                   C' ── D'     (C', D' are new commits with the same changes)

17.13

Merge vs Rebase

Source S40 · 3. Merge vs Rebase
Aspect Merge Rebase
What it does Joins two histories with a merge commit Replays commits onto a new base
History shape Non-linear (branches visible) Linear
Commit IDs Existing commits unchanged Rebased commits get new IDs
Rewrites history No Yes
Safe on shared/public branches Yes No
Conflict resolution Once for the whole merge Possibly once per replayed commit
Traceability Shows exactly when integration happened Hides when branches diverged
Typical use Integrating into main, shared branches Updating your own feature branch, cleanup 
Merge:   A ── B ── E ── F ── M          Rebase:  A ── B ── E ── F ── C' ── D'
               \            /
                C ──── D

Rule of thumb Rebase your own local/feature work; merge shared work.

17.14

Understanding Commit History

Source S40 · 4. Understanding Commit History

Rebase changes history, so it's important to read history before and after:

git log --oneline --graph --all
git log main..feature        # commits in feature not in main (these are what rebase will replay)
git merge-base main feature  # the current base

After rebasing, git log main..feature shows the same number of commits, but with new IDs, and git merge-base main feature equals main's tip.

Use git range-diff to compare the old and new versions of the commit series:

git range-diff ORIG_HEAD~2..ORIG_HEAD HEAD~2..HEAD
17.15

Basic Rebase

Source S40 · 5. Basic Rebase

5.1 Commands

git switch feature/orders-load
git fetch origin
git rebase origin/main

Equivalent one-liner:

git rebase origin/main feature/orders-load

5.2 Output

Successfully rebased and updated refs/heads/feature/orders-load.

5.3 Pushing after rebase

If the branch was already pushed, its history changed, so a normal push is rejected:

git push --force-with-lease

5.4 Pull with rebase

git pull --rebase                       # one-time
git config --global pull.rebase true    # default

5.5 --onto (advanced)

Move commits of feature-b that were based on feature-a onto main:

git rebase --onto main feature-a feature-b
17.16

Interactive Rebase

Source S40 · 6. Interactive Rebase

6.1 Start

git rebase -i HEAD~4        # edit the last 4 commits
git rebase -i main          # edit all commits since the branch left main

6.2 The todo list

pick a1b2c3d feat: add orders staging table
pick b2c3d4e wip
pick c3d4e5f fix typo
pick d4e5f6a feat: add orders load procedure

# Commands:
# p, pick   = use commit
# r, reword = use commit, but edit the commit message
# e, edit   = use commit, but stop for amending
# s, squash = use commit, but meld into previous commit (combine messages)
# f, fixup  = like squash, but discard this commit's message
# x, exec   = run command (the rest of the line) using shell
# b, break  = stop here (continue rebase later with 'git rebase --continue')
# d, drop   = remove commit
# l, label / t, reset / m, merge = advanced (rebase merges)

Commits are listed oldest first. Edit the commands, save and close the editor.

17.17

Squashing Commits

Source S40 · 7. Squashing Commits

Goal: combine several small commits into one meaningful commit.

pick   a1b2c3d feat: add orders staging table
squash b2c3d4e wip
squash c3d4e5f fix typo
pick   d4e5f6a feat: add orders load procedure

Git opens an editor to write the combined message. Use fixup to discard the small commits' messages automatically.

Autosquash workflow:

git commit --fixup a1b2c3d            # creates "fixup! feat: add orders staging table"
git commit --squash a1b2c3d           # creates "squash! ..." (lets you edit message)
git rebase -i --autosquash main       # fixup/squash commits placed and marked automatically
git config --global rebase.autoSquash true

Alternative (squash everything on a branch):

git reset --soft main
git commit -m "feat: orders load pipeline"
17.18

Reordering Commits

Source S40 · 8. Reordering Commits

Change the order of lines in the todo list:

pick d4e5f6a feat: add orders load procedure
pick a1b2c3d feat: add orders staging table

Note Reordering can cause conflicts if a later commit depends on an earlier one.

17.19

Editing Commit Messages

Source S40 · 9. Editing Commit Messages

Use reword:

reword a1b2c3d add tbl
pick   d4e5f6a feat: add orders load procedure

Git stops and opens the editor for the new message (e.g. feat(sql): add stg_orders staging table).

To change the content of an older commit, use edit:

edit a1b2c3d feat: add orders staging table

# Git stops at that commit
# modify files
git add sql/tables/stg_orders.sql
git commit --amend
git rebase --continue

Splitting a commit with edit:

git reset HEAD~1           # undo the commit, keep changes
git add sql/              && git commit -m "feat(sql): staging table"
git add python/           && git commit -m "feat(etl): staging loader"
git rebase --continue
17.20

Dropping Commits

Source S40 · 10. Dropping Commits

Delete the line or mark it drop:

pick a1b2c3d feat: add orders staging table
drop b2c3d4e debug: print row counts
pick d4e5f6a feat: add orders load procedure

The commit's changes disappear from the branch (recoverable via reflog).

17.21

Continuing Rebase

Source S40 · 11. Continuing Rebase

When rebase pauses (conflict, edit, break), resume with:

git rebase --continue

Other control commands:

git rebase --skip          # skip the current commit entirely
git rebase --edit-todo     # change the remaining todo list
git status                 # shows "interactive rebase in progress; onto ..."
17.22

Aborting Rebase

Source S40 · 12. Aborting Rebase
git rebase --abort

Returns the branch to exactly where it was before the rebase started. If the rebase already finished and you regret it:

git reset --hard ORIG_HEAD        # immediately after the rebase
git reflog                        # or find the pre-rebase commit
git reset --hard HEAD@{5}
17.23

Resolving Rebase Conflicts

Source S40 · 13. Resolving Rebase Conflicts

13.1 Why rebase conflicts differ

Rebase replays commits one by one, so you may resolve conflicts for several commits. During a rebase, "ours" = the branch you're rebasing onto (e.g. main) and "theirs" = your commit being replayed — the reverse of merge.

13.2 Steps

CONFLICT (content): Merge conflict in sql/procedures/usp_load_orders.sql
error: could not apply c3d4e5f... feat: add watermark

git status                         # see conflicted files
# edit, remove markers
git add sql/procedures/usp_load_orders.sql
git rebase --continue              # moves to next commit

Repeat until finished, or git rebase --abort.

13.3 Reduce repeated conflicts

git config --global rerere.enabled true     # reuse recorded resolution

Squash commits first (fewer commits to replay), or merge instead of rebase for very divergent branches.

17.24

Rebase Best Practices

Source S40 · 14. Rebase Best Practices
  1. Never rebase public/shared branches (main, develop, release/*) or commits others have based work on.
  2. Rebase your feature branch before opening or updating a PR to keep it current.
  3. Use git push --force-with-lease (never plain --force) after rebasing a pushed branch.
  4. Create a backup branch before complex rebases: git branch backup/feature-orders.
  5. Clean history with interactive rebase: one logical change per commit, clear messages.
  6. Run tests after rebasing — code that merged cleanly can still be broken.
  7. Enable rerere and rebase.autoSquash.
  8. Agree as a team on merge vs rebase policy.
17.25

When Not to Use Rebase

Source S40 · 15. When Not to Use Rebase
Situation Why not
Branch is shared and others pushed to it Rewriting breaks their history and can lose work
main/develop/release branches Protected history; audit trail
Commits already merged elsewhere Creates duplicate commits
You need an exact record of when integration happened (audits) Rebase hides it
Branch has many commits and massive divergence Many repeated conflicts; merge is simpler
Branch contains merge commits you need to keep Rebase linearises them (unless --rebase-merges)
You're unsure and under time pressure Merge is safer

Golden Rule Do not rebase commits that exist outside your repository and that people may have based work on.

Command reference

git rebase
Syntax
git rebase <upstream>
git rebase --onto <newbase> <upstream> [<branch>]
git rebase --continue | --skip | --abort
Purpose
Replay the current branch's commits (those not in <upstream>) on top of <upstream>.
Expected output
Successfully rebased and updated refs/heads/feature/RDP-102-orders-ingest.
Example
git switch feature/RDP-102-orders-ingest
git fetch origin
git rebase origin/main
# conflict -> edit, then:
git add python/ingestion/src/retail_ingest/extract_orders.py
git rebase --continue
git push --force-with-lease
Common mistakes
Rebasing main or any shared branch; using git commit instead of git rebase --continue after resolving.
Troubleshooting
git rebase --abort returns to the state before the rebase. After a finished bad rebase: git reset --hard ORIG_HEAD (or use the reflog).
git rebase -i (interactive)
Syntax
git rebase -i <base>
git rebase -i --autosquash <base>
git commit --fixup=<sha>
Purpose
Edit a list of commits: pick, reword, edit, squash, fixup, drop, reorder.
Key parameters
  • pick — keep
  • reword — keep, change message
  • edit — stop to amend
  • squash — combine with previous, merge messages
  • fixup — combine, discard this message
  • drop — remove
  • exec — run a command (e.g. tests) after a commit
Example
git rebase -i HEAD~5
# editor:
pick 1a2b3c4 feat(ingest): extract orders by watermark
fixup 2b3c4d5 wip
fixup 3c4d5e6 fix typo
pick 4d5e6f7 test(ingest): add extract tests
fixup 5e6f7a8 wip tests
Common mistakes
Squashing commits that are already in main or that colleagues pulled.
git rebase --onto
Syntax
git rebase --onto <newbase> <oldbase> <branch>
Purpose
Move a range of commits to a different base — e.g. a branch accidentally created from another feature branch.
Example
# feature/RDP-120 was created from feature/RDP-102 but should start from main
git rebase --onto main feature/RDP-102 feature/RDP-120
Common mistakes
Swapping the argument order — read it as "onto NEW, the commits after OLD, of BRANCH".

Real-time scenarios

Source S18, S40 · Rebase conflict in the middle of five commits

Git stops at the commit that conflicts. Resolve, git add, git rebase --continue; it may stop again for later commits. If it becomes confusing, git rebase --abort and use merge instead. Remember: during a rebase ours is the branch you are rebasing onto (main) and theirs is your commit being replayed.

Course addition · Colleague already pulled your branch before you rebased

Their copy has the old commits. Tell them; they should git fetch then git reset --hard origin/<branch> (if they have no own commits) or git rebase --onto origin/<branch> <old-tip> to move their own commits. Prevention: don't rebase shared branches.

Best practices

Course addition · best practices
  • Rebase only private branches; merge shared ones.
  • Clean history with interactive rebase before opening/marking a PR ready.
  • Use --force-with-lease after rebasing a pushed branch.
  • Use commit --fixup + rebase -i --autosquash for review fixes.
  • Run tests after rebasing — a clean rebase can still produce broken code.

Chapter 17 Interview Questions

Source S18 · Chapter manual · interview

1. What is Git rebase?

It replays commits from one branch onto a new base, creating new commit IDs.

2. Does rebase preserve original commit hashes?

No. Replayed commits have new IDs.

3. What is a merge base?

The best common ancestor Git uses to understand the shared history of two lines of development.

4. What is the key difference between merge and rebase?

Merge joins histories; rebase replays commits and rewrites the branch's history.

5. What does git rebase -i do?

It opens an interactive todo list for editing a range of commits.

6. What is squash?

Combines a commit with the preceding commit and allows a combined message.

7. What is fixup?

Combines a commit with the preceding commit and discards the fixup message.

8. How do you change a commit message during interactive rebase?

Mark the commit as reword.

9. How do you remove a commit in interactive rebase?

Mark it as drop or remove its todo line.

10. How do you continue after resolving a rebase conflict?

Stage resolved files and run git rebase --continue.

11. How do you cancel a rebase?

Run git rebase --abort.

12. What does --skip do?

It skips the current commit being replayed; use only when intentional.

13. Why avoid rebasing shared history?

It changes commit IDs and can disrupt teammates' branches.

14. What is force-with-lease?

A safer force-push option that refuses if the remote ref changed unexpectedly.

15. When is merge preferable?

For shared/public branches or when preserving the actual integration history matters.

Beginner
What does git rebase main do on a feature branch?

Replays the feature's commits on top of the current main, producing new commits and linear history.

What is the golden rule of rebasing?

Do not rebase commits that exist outside your repository and that others may have based work on.

Intermediate
Difference between squash and fixup in interactive rebase?

Both combine a commit into the previous one; squash lets you edit the combined message, fixup discards the fixup commit's message.

How do you abort a rebase?

git rebase --abort.

Advanced
What does git rebase --onto A B C do?

Takes commits reachable from C but not from B and replays them onto A, then moves C.

Why are "ours" and "theirs" reversed during rebase?

Rebase checks out the upstream and applies your commits one by one onto it, so the upstream is "ours" and your commit is "theirs".

Scenario
A PR has 23 commits like "wip", "fix", "fix again". The reviewer wants clean history. What do you do?

git rebase -i origin/main, group into a few meaningful commits with fixup/squash/reword, run tests, git push --force-with-lease. Or rely on "Squash and merge" if the team uses it.
