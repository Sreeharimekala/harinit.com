Chapter introduction

1.1

What is Version Control?

Source S02 · Chapter manual · 1. What is Version Control?

Definition

Version control is a system that records and manages changes made to files over time. It helps people understand how a file evolved, compare versions, collaborate, and recover earlier work when necessary.

Version control is commonly used for source code, but it can also track SQL scripts, Python files, configuration files, documentation, infrastructure definitions, and other project assets.

What can version control help you do?

  • Track changes made to files.
  • Maintain a history of committed versions.
  • Identify the author and date of a recorded change.
  • Compare versions to see what changed.
  • Restore an earlier version when appropriate.
  • Support parallel development through branches.
  • Combine work contributed by multiple developers.

Real-time example: a SQL stored procedure

Suppose you are developing USP_LOAD_CUSTOMERS.sql. The procedure changes as requirements evolve.

Version 1 — initial implementation
CREATE PROCEDURE USP_LOAD_CUSTOMERS
AS
BEGIN
    SELECT *
    FROM CUSTOMERS;
END;
Version 2 — filter active customers
CREATE PROCEDURE USP_LOAD_CUSTOMERS
AS
BEGIN
    SELECT *
    FROM CUSTOMERS
    WHERE STATUS = 'ACTIVE';
END;
Version 3 — select only required columns
CREATE PROCEDURE USP_LOAD_CUSTOMERS
AS
BEGIN
    SELECT CUSTOMER_ID,
           CUSTOMER_NAME,
           STATUS
    FROM CUSTOMERS
    WHERE STATUS = 'ACTIVE';
END;

If Version 3 introduces a defect, version control helps you inspect the change history, compare it with Version 2, and recover or reapply the correct code.

Important: Version control records changes when they are saved to the repository according to the tool's workflow. In Git, this recorded snapshot is called a commit.

Basic version control workflow

Create or edit files ↓ Review changes ↓ Record a version (commit) ↓ View and compare history ↓ Collaborate or restore when needed

Why Do We Need Version Control?

Source S02 · Chapter manual · 2. Why Do We Need Version Control?

Imagine an organization has ten developers working on one application. Each developer changes different parts of the project. The team needs a dependable way to coordinate those changes without losing work.

Typical development scenario

DeveloperResponsibility
Developer ACustomer module
Developer BOrders module
Developer CInventory module

Common situations

  1. Code overwriting: one developer may accidentally replace another developer's newer file with an older copy.
  2. No change history: when a defect appears, the team may not know which change introduced it.
  3. Difficult collaboration: sharing files by email or network folders makes parallel work difficult to coordinate.
  4. Rollback challenges: after a faulty release, the team may need to recover a previously working version.
  5. Multiple file copies: names such as final, final_v2, and final_latest make it unclear which file is authoritative.

How version control addresses these problems

ChallengeVersion control capability
Changes overwrite each otherTracks changes and supports integration of parallel work.
No historyMaintains a history of recorded changes.
Hard to collaborateSupports branches, remotes, and collaboration workflows.
Rollback is difficultAllows earlier committed states to be inspected and restored.
Unclear file ownershipRecords commit authorship and metadata.
Release tracking is difficultSupports release branches and tags.

Data Engineering example

A team maintains Azure Data Factory pipelines across Development, UAT, and Production. Two developers make separate pipeline changes. With a controlled Git workflow, they can work on separate branches, commit their changes, raise pull requests, review and merge approved work, and then deploy through the organization's release process.

Key takeaway: Version control provides a controlled, traceable way to manage changes as a project evolves and as more people contribute.
1.3

Problems Without Version Control

Source S02 · Chapter manual · 3. Problems Without Version Control

3.1 Manual file management

Project/
├── Customer.sql
├── Customer_old.sql
├── Customer_latest.sql
├── Customer_final.sql
└── Customer_final_updated.sql

Manual copies create confusion, duplication, and uncertainty about which file is current.

3.2 Loss of previous changes

If new code causes a production issue, the team may have to find a backup or reconstruct the earlier implementation manually.

3.3 No reliable accountability

Without recorded history, it can be difficult to determine who changed a file, what changed, when it changed, and why the change was made.

3.4 Collaboration conflicts

Two people can independently edit the same file. If one copy replaces the other, work can be lost. A version control system can identify overlapping changes and provide tools to reconcile them.

3.5 No dependable development history

It becomes difficult to trace feature additions, bug fixes, configuration changes, and release contents over time.

3.6 Difficult production recovery

If a release fails, the team may not have a clear, verified source version from which to recover.

3.7 Governance and audit challenges

Organizations may need evidence of approved changes and release contents. Version control supports traceability, although access controls, approvals, and audit policies must also be configured.

What is Source Code Management (SCM)?

Source S02 · Chapter manual · 4. What is Source Code Management (SCM)?

Definition

Source Code Management is the practice of managing, tracking, organizing, and controlling changes to source code throughout software development.

It helps teams maintain code in a structured way and coordinate contributions from multiple developers.

SCM commonly includes

  • Source code versioning and change tracking
  • Branch and merge management
  • Code review and collaboration workflows
  • Release and change history
  • Repository permissions and access control

Example: Python application

├── database.py
├── customer.py
├── orders.py
├── requirements.txt
└── README.md

A team can store this project in a Git repository, commit changes, use branches for new work, review pull requests, and merge approved changes.

What is Software Configuration Management?

Source S02 · Chapter manual · 5. What is Software Configuration Management?

Definition

Software Configuration Management (SCM) is a broader software engineering discipline for identifying, controlling, recording, and auditing changes to the components that make up a software system throughout its lifecycle.

Depending on context, the abbreviation SCM can mean either Source Code Management or Software Configuration Management. The latter has a wider scope than source code alone.

Configuration items can include

  • Application source code
  • Database scripts and schemas
  • Application and environment configuration
  • Infrastructure definitions
  • Build and deployment scripts
  • Documentation and release packages

Five important activities

1. Configuration identification

Identify the components that need to be controlled. For example, Python modules, SQL procedures, ADF pipeline definitions, and deployment configuration.

2. Configuration control

Control how changes are proposed, reviewed, approved, and implemented. For example, a production database change may require a change request and approval before deployment.

3. Configuration status accounting

Record and report the status of configuration items and changes.

Change IDDescriptionStatus
CHG001Customer pipeline modificationApproved
CHG002SQL procedure optimizationCompleted
CHG003Database configuration updatePending
4. Configuration auditing

Verify that the delivered configuration matches approved requirements and release records. Checks may include the correct code version, deployment scripts, and environment settings.

5. Build and release management

Control how software is packaged, tested, versioned, and released.

Development → Build → Testing → UAT → Production release

Source Code Management vs Software Configuration Management

AreaSource Code ManagementSoftware Configuration Management
ScopePrimarily source codeSoftware configuration items across the system
Main focusCode history and collaborationOverall configuration consistency and control
Typical activitiesCommit, branch, merge, reviewIdentification, control, status accounting, auditing, release management
Tools and practicesGit, SVN, repository platformsVersion control plus change, build, release, and audit processes

Benefits of Version Control

Source S02 · Chapter manual · 6. Benefits of Version Control
  1. Change tracking: committed changes include information such as author, date, and message.
  2. Version history: teams can inspect and compare earlier committed versions.
  3. Collaboration: multiple developers can work in parallel and integrate their work.
  4. Recovery: earlier committed states can be inspected and used to recover from mistakes.
  5. Branching: new features and fixes can be developed separately from the main line of work.
  6. Code review: changes can be reviewed before they are integrated.
  7. Release management: branches and tags can help identify release versions.
  8. Automation: repository events can trigger builds, tests, quality checks, and deployments through CI/CD tools.
  9. Traceability: recorded changes make it easier to investigate when and how code evolved.
A remote repository can provide another copy of repository data, but Git alone should not be treated as a complete backup, disaster recovery, or compliance solution.

1.8

Centralized vs Distributed Version Control Systems

Source S02 · Chapter manual · 8. Centralized vs Distributed Version Control Systems

8.1 Centralized Version Control System (CVCS)

A Centralized Version Control System stores the authoritative repository on a central server. Developers connect to that server to check out files, obtain updates, and commit changes.

CENTRAL SERVER (Main repository) | ┌──────────┼──────────┐ | | | Developer A Developer B Developer C | | | Working Working Working copy copy copy
How it works
  1. The organization creates a central repository.
  2. Developers check out the project or required files.
  3. They make changes in their working copies.
  4. They submit commits to the central server.
  5. Other developers update their working copies to receive changes.
Examples
  • Apache Subversion (SVN)
  • CVS
  • TFVC (Team Foundation Version Control)
Advantages
  • A central authoritative repository can simplify administration.
  • Centralized permissions and access policies are available.
  • It can fit organizations with established centralized workflows.
Disadvantages
  • Many repository operations depend on server connectivity.
  • Server availability is important for normal team operations.
  • A standard working copy generally does not contain the complete repository history.
  • Offline history operations are more limited than in a DVCS.

8.2 Distributed Version Control System (DVCS)

A Distributed Version Control System gives each developer a local repository containing the project's version history. Developers can commit locally and synchronize with remote repositories when needed.

REMOTE REPOSITORY | ┌───────────┼───────────┐ | | | Developer A Developer B Developer C | | | Local repo Local repo Local repo + history + history + history
How it works
  1. A developer clones a remote repository.
  2. The clone includes repository data and history.
  3. The developer edits files and commits locally.
  4. When ready, the developer pushes commits to a remote repository.
  5. Other developers fetch or pull changes.
Examples
  • Git
  • Mercurial
Advantages
  • Developers can commit and inspect history offline.
  • Many operations are fast because they run locally.
  • Branching and merging are flexible.
  • Multiple remotes can be configured.
Disadvantages
  • Users need to understand synchronization and branch workflows.
  • Repository data is replicated across developer machines.
  • Teams must configure permissions and governance on shared hosting platforms.

8.3 CVCS vs DVCS comparison

FeatureCVCSDVCS
Repository modelCentral authoritative repositoryLocal repositories with complete history, commonly synchronized with remotes
Local historyUsually limited in a working copyAvailable locally
Offline commitsGenerally not supported in the same waySupported
Network dependencyHigher for repository operationsLower for local operations
BranchingSupported; experience varies by toolTypically lightweight and flexible
ExamplesSVN, CVS, TFVCGit, Mercurial

8.4 Practical example

Three developers are working on a data engineering project. In a centralized system, they typically interact with the central server to submit and obtain changes. In Git, each developer can clone the repository, commit locally without internet access, and synchronize with a shared remote repository later.

Remember: Git is distributed, but teams commonly use a shared remote repository on GitHub, GitLab, Bitbucket, or Azure Repos to coordinate work.

Git vs SVN vs Mercurial vs TFS

Source S02 · Chapter manual · 10. Git vs SVN vs Mercurial vs TFS

10.1 Git

Type: Distributed Version Control System.

Git is an open-source version control system originally created by Linus Torvalds in 2005. It supports local history, offline commits, branching, merging, and synchronization with remote repositories.

Common uses: application development, database development, Data Engineering, DevOps, and infrastructure as code.

10.2 SVN (Apache Subversion)

Type: Centralized Version Control System.

SVN maintains a central repository. Developers check out working copies and commit changes to the central server. It supports versioning of files and directories and is still found in some established or legacy environments.

10.3 Mercurial

Type: Distributed Version Control System.

Mercurial is a distributed system with local repository history, offline commits, and branching and merging capabilities. It is an alternative to Git, particularly in environments that already use Mercurial.

10.4 TFS and TFVC

TFS (Team Foundation Server) was Microsoft's former name for its on-premises application lifecycle management and DevOps platform. It supported two source control options: TFVC and Git.

  • TFVC: Microsoft's centralized version control system.
  • Git in Azure DevOps: Distributed Git repositories hosted by Azure Repos.

The on-premises product evolved into Azure DevOps Server. Therefore, TFS should not be treated as a single version control architecture: the distinction between TFVC and Git matters.

What is Version Control?

Source S40 · 1. What is Version Control?

1.1 Definition

Version Control is a system that records and manages changes made to files over time.

It allows developers to:

  • Track changes made to files.
  • Maintain multiple versions of files.
  • Identify who modified a file.
  • Understand when changes were made.
  • Compare different versions.
  • Restore previous versions.
  • Collaborate with multiple developers.
  • Maintain a complete history of project changes.

Version control is commonly used in software development to manage source code. However, it can also manage SQL scripts, Python files, configuration files, documentation, infrastructure scripts, and other project assets.

1.2 Real-Time Example

Consider that you are developing a SQL stored procedure.

Initially, you create:

USP_LOAD_CUSTOMERS.sql

Version 1:

CREATE PROCEDURE USP_LOAD_CUSTOMERS
AS
BEGIN
    SELECT *
    FROM CUSTOMERS;
END;

Later, you modify the procedure to filter active customers.

Version 2:

CREATE PROCEDURE USP_LOAD_CUSTOMERS
AS
BEGIN
    SELECT *
    FROM CUSTOMERS
    WHERE STATUS = 'ACTIVE';
END;

After testing, you make another modification.

Version 3:

CREATE PROCEDURE USP_LOAD_CUSTOMERS
AS
BEGIN
    SELECT CUSTOMER_ID,
           CUSTOMER_NAME,
           STATUS
    FROM CUSTOMERS
    WHERE STATUS = 'ACTIVE';
END;

Now imagine that Version 3 introduces an issue.

You need to:

  1. Identify what changed between Version 2 and Version 3.
  2. Understand who made the modification.
  3. Find when the change was introduced.
  4. Restore the previous working version if necessary.

A version control system makes these activities manageable.

Imagine an organization has 10 developers working on the same application.

Each developer modifies different files and contributes new functionality.

Consider this scenario:

A team has three developers.

Developer B Orders module
Developer C Inventory module

All three developers work on the same project.

Developer A modifies the customer module.

Developer B modifies the orders module.

Developer A updates a file.

Developer B downloads an older copy and saves it over Developer A's changes.

Developer A's changes are lost.

Problem 2: No Change History

A production issue occurs.

The team does not know:

  • What was changed?
  • Who changed it?
  • When was it changed?
  • Why was it changed?

Problem 3: Difficult Collaboration

Multiple developers need to work on the same project.

Sharing files through email or network folders becomes difficult.

Problem 4: Rollback Difficulties

A new release introduces a production failure.

The team needs to restore the previous working version.

Without version history, this becomes complicated.

Developers maintain multiple copies:

Customer_Procedure.sql
Customer_Procedure_Final.sql
Customer_Procedure_Final_V2.sql
Customer_Procedure_Final_Updated.sql
Customer_Procedure_Final_Updated_New.sql

Nobody knows which file is the latest approved version.

2.2 How Version Control Solves These Problems

Problem Version Control Solution
Code overwriting Tracks and combines changes
No change history Maintains commit history
Difficult collaboration Enables team collaboration
Rollback difficulties Restores previous versions
Multiple file copies Maintains organized version history
Lack of accountability Records author and commit details
Code conflicts Provides conflict detection and resolution

2.3 Enterprise Example

Suppose your organization maintains an Azure Data Factory project.

There are three environments:

  • Development
  • UAT
  • Production

A developer modifies a pipeline in Development.

Another developer modifies the same pipeline.

The team needs to review both changes before publishing them to Production.

Using version control:

  1. Developers create separate branches.
  2. Each developer makes changes independently.
  3. Changes are committed to their branches.
  4. Pull requests are created.
  5. Reviewers validate the changes.
  6. Approved changes are merged.
  7. The production release is deployed.

This process improves collaboration, traceability, and deployment control.

Software Configuration Management (SCM) is a broader software engineering discipline that manages and controls changes to all important components of a software system throughout its lifecycle.

Centralized vs Distributed Version Control Systems

Source S40 · 8. Centralized vs Distributed Version Control Systems

There are two major architectures used by version control systems.

8.1 Centralized Version Control System (CVCS)

Definition

A Centralized Version Control System maintains a central repository on a server.

Developers connect to this central server to access files, download updates, and submit modifications.

The central repository acts as the primary source of version history.

Architecture
             Central Server
            (Main Repository)
                   |
       ------------|------------
       |           |           |
       |           |           |
   Developer A Developer B Developer C
       |           |           |
       |           |           |
   Local Copy  Local Copy  Local Copy
How It Works
  1. The organization creates a central repository.
  2. Developers check out the project.
  3. Developers modify files locally.
  4. Developers commit changes to the central server.
  5. Other developers update their working copies.
Examples
  • SVN (Subversion).
  • CVS.
  • TFVC (Team Foundation Version Control).
  • Perforce Helix Core.
Advantages
  • Centralized repository management.
  • Easier centralized access control.
  • Central server provides a single authoritative repository.
  • Suitable for workflows requiring centralized control.
Disadvantages
  • Network connectivity is generally required for server operations.
  • Central server availability is important.
  • Local working copies do not normally contain the complete project history.
  • Offline operations are limited compared with DVCS.

8.2 Distributed Version Control System (DVCS)

Definition

A Distributed Version Control System allows every developer to maintain a complete local repository containing the project's history.

Developers can work independently and synchronize changes with remote repositories when required.

Architecture
             Remote Repository
                    |
          -----------|-----------
          |          |          |
          |          |          |
      Developer A Developer B Developer C
          |          |          |
      Local Repo Local Repo Local Repo
      Full History Full History Full History
How It Works
  1. A developer clones the remote repository.
  2. A complete local repository is created.
  3. The developer makes changes locally.
  4. The developer commits changes locally.
  5. Changes can be synchronized with the remote repository.
  6. Other developers fetch or pull the changes.
Examples
  • Git.
  • Mercurial.
Advantages
  • Complete local repository history.
  • Supports offline commits.
  • Faster local operations.
  • Flexible branching and merging.
  • Multiple remote repositories can be configured.
Disadvantages
  • Requires understanding of branching and synchronization.
  • Repository history is duplicated across developer machines.
  • Access control and collaboration policies need proper management.

8.3 CVCS vs DVCS Comparison

Feature CVCS DVCS
Repository Central server Complete local repositories
History Primarily centralized Available locally
Offline commits Generally unavailable Supported
Network dependency Higher Lower for local operations
Branching Depends on tool Generally very flexible
Local operations Often server-dependent Generally faster
Collaboration Centralized Distributed synchronization
Examples SVN, TFVC Git, Mercurial
8.4 Practical Example

Suppose three developers are working on a data engineering project.

With CVCS:

  • They connect to a central repository.
  • They check out the required files.
  • They submit changes to the server.

With DVCS:

  • Each developer clones the repository.
  • Each developer has the complete repository history.
  • They can commit changes without internet connectivity.
  • They synchronize changes when connectivity is available.

Important: Git is a DVCS, but teams commonly use a shared remote repository on GitHub or Azure Repos to coordinate their work.

Git vs SVN vs Mercurial vs TFS

Source S40 · 10. Git vs SVN vs Mercurial vs TFS

Before Git became widely adopted, organizations used several version control systems.

Let's understand the differences.

10.1 Git

Type: Distributed Version Control System.

Git is an open-source version control system originally created by Linus Torvalds in 2005.

Key features:

  • Distributed architecture.
  • Local repository history.
  • Fast branching.
  • Efficient merging.
  • Offline commits.
  • Strong ecosystem.
  • Integration with GitHub, GitLab, Bitbucket and Azure Repos.

Common use cases:

  • Application development.
  • Data Engineering.
  • Database development.
  • DevOps.
  • Infrastructure as Code.

Official website: Git

10.2 SVN (Apache Subversion)

Type: Centralized Version Control System.

SVN maintains a central repository where developers check out files and commit changes.

Key features:

  • Centralized repository.
  • Central revision history.
  • Directory and file versioning.
  • Access control.
  • Support for binary files.

Common use cases:

  • Legacy enterprise applications.
  • Organizations with existing SVN infrastructure.
  • Projects requiring centralized version management.

Official website: Apache Subversion

10.3 Mercurial

Type: Distributed Version Control System.

Mercurial is similar to Git in its distributed architecture.

Key features:

  • Distributed repositories.
  • Offline commits.
  • Branching and merging.
  • Local repository history.
  • Cross-platform support.

Common use cases:

  • Distributed software development.
  • Projects using existing Mercurial infrastructure.

Official website: Mercurial

10.4 TFS (Team Foundation Server)

TFS is Microsoft's former name for its on-premises application lifecycle management and DevOps platform.

It supported two source control systems:

  1. TFVC (Team Foundation Version Control).
  2. Git.

Important: TFVC is centralized, whereas Git repositories in Azure DevOps use distributed version control.

TFS evolved into Azure DevOps Server for the on-premises product.

Key features:

  • Source control.
  • Work item tracking.
  • Build automation.
  • Release management.
  • Team collaboration.
  • Project management.

Common use cases:

  • Enterprise application development.
  • Microsoft technology environments.
  • Organizations using Azure DevOps Server.

Microsoft documentation: Azure DevOps Server documentation

Beginner
What is version control?

A system that records changes to files over time so you can review history, compare versions, collaborate safely and restore earlier versions.

Is Git the same as GitHub?

No. Git is the distributed version-control tool installed on your machine. GitHub is a hosting and collaboration service for Git repositories (pull requests, issues, Actions). Azure Repos, GitLab and Bitbucket are alternatives.

Intermediate
Give three advantages of a distributed VCS over a centralized one.

Full history in every clone (offline log/diff/commit), cheap local branching, and no single point of failure — any clone can restore the server.

What is the difference between SCM as "source code management" and "software configuration management"?

Source code management is the versioning of source files. Software configuration management is the broader discipline that also covers identifying configuration items, controlling changes, recording status and auditing releases; version control is one of its tools.

Branching/merging needs, offline work, platform integration (GitHub/Azure DevOps, CI/CD), repository size and binary assets (Git LFS), history preservation (git svn or a migration tool can import SVN history), training needs and a cut-over plan.
