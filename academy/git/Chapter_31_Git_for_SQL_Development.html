Learning objectives

Chapter introduction

What it is. Treating database code as source code: tables, views, stored procedures and functions as versioned scripts or a SQL database project; deployment scripts and DACPACs; SQL-specific diffs, reviews, branching and release management.

Why it matters. Most data defects originate in SQL changes. Version control plus automated build and deployment turn risky manual script execution into repeatable releases with rollback options.

Where it is used. SQL Server / Azure SQL / Synapse dedicated pools / Fabric Warehouse, with SQL database projects (DACPAC, state-based) or migration tools such as Flyway (migration-based).

In this course's project. Stage 6: the sql/ folder becomes an SDK-style SQL project RetailWarehouse.sqlproj; PRs build the DACPAC, and pipelines deploy Dev → Test → Prod with SqlPackage.

31.13

Version Controlling SQL Scripts

Source S40 · 1. Version Controlling SQL Scripts

1.1 Why version-control SQL

  • Databases are code: logic in procedures/views affects business numbers.
  • Without Git, the "truth" lives only in the database — no history, no review, no rollback.
  • Enables CI/CD, environment consistency (Dev = Test = Prod schema) and audits.

1.2 Repository structure

sql/
├── RetailDW.sqlproj              # (if using SQL Database Projects / SSDT)
├── schemas/
│   ├── stg.sql
│   └── dw.sql
├── tables/
│   ├── dw.dim_customer.sql
│   ├── dw.dim_product.sql
│   └── dw.fact_sales.sql
├── views/
│   └── dw.vw_active_customers.sql
├── functions/
│   └── dbo.fn_fiscal_year.sql
├── procedures/
│   ├── dw.usp_load_customers.sql
│   └── dw.usp_load_sales.sql
├── security/
│   └── roles.sql
├── migrations/                    # (if using migration-based approach)
│   ├── V001__create_schemas.sql
│   └── V002__add_region_to_dim_customer.sql
├── post-deploy/
│   └── seed_reference_data.sql
└── tests/
    └── test_usp_load_customers.sql   # e.g. tSQLt tests

1.3 Conventions

  • One object per file, file name = schema.object_name.sql.
  • Consistent formatting (SQLFluff) and naming (usp_, vw_, fn_, dim_, fact_).
  • Scripts should be idempotent (safe to re-run) where possible.
  • Never commit data dumps or credentials.

Managing Stored Procedures

Source S40 · 2. Managing Stored Procedures

2.1 Idempotent definition

-- sql/procedures/dw.usp_load_customers.sql
CREATE OR ALTER PROCEDURE dw.usp_load_customers
    @load_date DATE = NULL
AS
BEGIN
    SET NOCOUNT ON;
    SET XACT_ABORT ON;

    BEGIN TRY
        BEGIN TRANSACTION;

        MERGE dw.dim_customer AS tgt
        USING (
            SELECT customer_id, customer_name, email, status
            FROM stg.customer
            WHERE load_date = COALESCE(@load_date, CAST(GETDATE() AS DATE))
        ) AS src
            ON tgt.customer_id = src.customer_id
        WHEN MATCHED AND (tgt.email <> src.email OR tgt.status <> src.status) THEN
            UPDATE SET tgt.email = src.email,
                       tgt.status = src.status,
                       tgt.updated_at = SYSUTCDATETIME()
        WHEN NOT MATCHED BY TARGET THEN
            INSERT (customer_id, customer_name, email, status, created_at, updated_at)
            VALUES (src.customer_id, src.customer_name, src.email, src.status, SYSUTCDATETIME(), SYSUTCDATETIME());

        COMMIT TRANSACTION;
    END TRY
    BEGIN CATCH
        IF @@TRANCOUNT > 0 ROLLBACK TRANSACTION;
        THROW;
    END CATCH
END;

CREATE OR ALTER (SQL Server 2016 SP1+, Azure SQL, Synapse dedicated pools support CREATE OR ALTER for procedures in recent versions — verify for your platform) means the same script creates or updates the procedure.

2.2 Workflow

git switch -c feature/DE-1700-customer-status
# edit dw.usp_load_customers.sql
git diff
git commit -am "feat(sql): track customer status changes in usp_load_customers"
git push -u origin feature/DE-1700-customer-status
31.15

Managing Views

Source S40 · 3. Managing Views
-- sql/views/dw.vw_active_customers.sql
CREATE OR ALTER VIEW dw.vw_active_customers
AS
SELECT customer_id,
       customer_name,
       email
FROM dw.dim_customer
WHERE status = 'ACTIVE';

Guidelines:

  • Explicit column lists (no SELECT *) — prevents silent breaking changes.
  • Views used by reports are contracts — removing/renaming columns is a breaking (MAJOR) change.
  • Consider WITH SCHEMABINDING for critical views (prevents underlying table changes that break them).
31.16

Managing Functions

Source S40 · 4. Managing Functions
-- sql/functions/dbo.fn_fiscal_year.sql
CREATE OR ALTER FUNCTION dbo.fn_fiscal_year (@d DATE)
RETURNS INT
WITH SCHEMABINDING
AS
BEGIN
    -- Fiscal year starts 1 April (India)
    RETURN CASE WHEN MONTH(@d) >= 4 THEN YEAR(@d) + 1 ELSE YEAR(@d) END;
END;

Notes: changing a function signature affects all callers — search usages (git grep fn_fiscal_year) before changing; add unit tests (tSQLt) for business logic functions.

31.17

Managing Table Scripts

Source S40 · 5. Managing Table Scripts

Tables are different from code objects: you cannot drop and recreate them without losing data.

5.1 State-based definition (SQL Database Project)

-- sql/tables/dw.dim_customer.sql  (desired final state)
CREATE TABLE dw.dim_customer (
    customer_id    INT           NOT NULL CONSTRAINT pk_dim_customer PRIMARY KEY,
    customer_name  NVARCHAR(100) NOT NULL,
    email          NVARCHAR(200) NULL,
    status         VARCHAR(20)   NOT NULL,
    region         VARCHAR(50)   NULL,          -- added in v2.6.0
    created_at     DATETIME2     NOT NULL,
    updated_at     DATETIME2     NOT NULL
);

The deployment tool (SqlPackage) compares this with the target and generates ALTER TABLE ... ADD region ....

5.2 Migration-based change

-- sql/migrations/V002__add_region_to_dim_customer.sql
IF COL_LENGTH('dw.dim_customer', 'region') IS NULL
    ALTER TABLE dw.dim_customer ADD region VARCHAR(50) NULL;

5.3 Safe schema-change practices

  • Add columns as nullable (or with defaults) first.
  • Expand–contract for renames: add new column → backfill → update consumers → remove old column in a later release.
  • Never edit a migration that has already been applied — add a new one.
  • Review data-loss warnings (BlockOnPossibleDataLoss=True in SqlPackage).

Managing Database Deployment Scripts

Source S40 · 6. Managing Database Deployment Scripts

6.1 Two approaches

Approach How it works Tools Pros Cons
State-based (declarative) Repo holds the desired schema; tool diffs it against the target and generates a script SQL Database Projects / SSDT, DACPAC + SqlPackage, Redgate SQL Compare Simple to author; always shows full object definition Generated scripts must be reviewed; complex data migrations need pre/post scripts
Migration-based (imperative) Ordered, immutable change scripts applied once and tracked in a history table Flyway, Liquibase, DbUp, Alembic, EF migrations Full control over each change, explicit data migrations Object's current definition spread across scripts

6.2 Pre- and post-deployment scripts (state-based)

-- sql/post-deploy/Script.PostDeployment.sql
:r .\seed_reference_data.sql

-- sql/post-deploy/seed_reference_data.sql (idempotent)
MERGE dw.dim_status AS t
USING (VALUES ('ACTIVE','Active'),('INACTIVE','Inactive')) AS s(code, name)
ON t.code = s.code
WHEN NOT MATCHED THEN INSERT (code, name) VALUES (s.code, s.name);

6.3 Flyway naming

V001__create_schemas.sql            # versioned (run once, in order)
V002__create_dim_customer.sql
R__vw_active_customers.sql          # repeatable (re-run when changed)

Tracking SQL Changes

Source S40 · 7. Tracking SQL Changes
git log --oneline -- sql/procedures/dw.usp_load_customers.sql      # history of one object
git log --follow -p -- sql/views/dw.vw_active_customers.sql         # with diffs, across renames
git blame -w sql/procedures/dw.usp_load_sales.sql                   # who changed each line
git log -S "discount_amount" --oneline -- sql/                      # when a column was introduced/removed
git log --since="2026-11-01" --name-only --oneline -- sql/          # what SQL changed this month
git grep -n "dim_customer" -- sql/                                  # where an object is used

Incident example: sales totals dropped on 20 Nov. git log --since=2026-11-18 -- sql/procedures/dw.usp_load_sales.sql reveals a commit that changed an INNER JOIN to exclude orders without promotions. git revert it and redeploy.

SQL Code Review

Source S40 · 9. SQL Code Review

9.1 Checklist

Area What to check
Correctness Joins (INNER vs LEFT), filters, grouping, date boundaries, time zones
Idempotency Safe re-runs: MERGE/UPSERT, IF NOT EXISTS, CREATE OR ALTER
Data quality NULL handling, duplicates, data types, truncation
Transactions & errors XACT_ABORT, TRY...CATCH, rollback, THROW
Performance SARGable predicates, indexes, avoiding cursors/RBAR, statistics, large deletes in batches
Schema changes Backward compatibility, data-loss risk, migration order
Security No dynamic SQL injection, least privilege, no hard-coded credentials, PII masking
Standards Naming, formatting, explicit column lists, comments
Tests tSQLt/unit tests or validation queries; row-count reconciliation

Managing Database Release Versions

Source S40 · 10. Managing Database Release Versions
  • Tag each database release: v2.6.0 → exact schema version.
  • Set the DACPAC version (<DacVersion>2.6.0</DacVersion> in .sqlproj) or Flyway version history.
  • Record deployments in the database:
CREATE TABLE meta.schema_version (
    version      VARCHAR(20)  NOT NULL,
    commit_sha   CHAR(40)     NOT NULL,
    deployed_at  DATETIME2    NOT NULL DEFAULT SYSUTCDATETIME(),
    deployed_by  NVARCHAR(100) NOT NULL
);
  • Keep a CHANGELOG of schema changes; flag breaking changes for downstream consumers (reports, APIs).
  • Rollback strategy: code objects → redeploy previous tag; table changes → forward fix or explicit rollback migration (dropping columns may lose data — plan carefully; backups/point-in-time restore for emergencies).
31.23

SQL Development Branch Strategy

Source S40 · 11. SQL Development Branch Strategy
main  ──●─────────●───────────●──────►   (production schema; tags v2.5.0, v2.6.0)
         \       /  \        /
feature/  ●──●──●    ●──●──●             (one change per branch, PR to main)

Recommended:

  1. Short-lived feature branches per change (feature/DE-1700-customer-status).
  2. Each developer uses a personal/dev database (or container) to build and test the SQL project locally.
  3. PR to main → CI builds DACPAC, lints, runs tests → DBA review.
  4. Merge → CD deploys to Dev → Test → Prod with approvals.
  5. Hotfixes branch from the production tag.

Avoid: developing directly in a shared Dev database without scripts ("click-ops") — changes are lost or overwritten. If that happened, use Schema Compare (database → project) to bring changes into Git.

Database Deployment Using CI/CD

Source S40 · 12. Database Deployment Using CI/CD

12.1 GitHub Actions — build and deploy DACPAC

# .github/workflows/sql.yml
name: SQL CI/CD
on:
  pull_request:
    paths: ['sql/**']
  push:
    branches: [main]
    paths: ['sql/**']

permissions:
  id-token: write
  contents: read

jobs:
  build:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-dotnet@v4
        with: { dotnet-version: '8.0.x' }
      - run: pip install sqlfluff && sqlfluff lint sql/ --dialect tsql
      - run: dotnet build sql/RetailDW.sqlproj -c Release      # SDK-style project (Microsoft.Build.Sql)
      - uses: actions/upload-artifact@v4
        with: { name: dacpac, path: sql/bin/Release/*.dacpac }

  deploy-dev:
    if: github.ref == 'refs/heads/main'
    needs: build
    runs-on: ubuntu-latest
    environment: dev
    steps:
      - uses: actions/checkout@v4
      - uses: actions/download-artifact@v4
        with: { name: dacpac, path: dacpac }
      - uses: azure/login@v2
        with:
          client-id: ${{ vars.AZURE_CLIENT_ID }}
          tenant-id: ${{ vars.AZURE_TENANT_ID }}
          subscription-id: ${{ vars.AZURE_SUBSCRIPTION_ID }}
      - uses: azure/sql-action@v2.3
        with:
          connection-string: ${{ secrets.AZURE_SQL_CONNECTION_STRING }}
          path: './sql/RetailDW.sqlproj'
          action: 'publish'
          arguments: '/p:BlockOnPossibleDataLoss=true'

12.2 Azure Pipelines — deploy DACPAC

- task: SqlAzureDacpacDeployment@1
  inputs:
    azureSubscription: sc-rdp-prod
    AuthenticationType: servicePrincipal
    ServerName: sql-rdp-prod.database.windows.net
    DatabaseName: RetailDW
    deployType: DacpacTask
    DeploymentAction: Publish
    DacpacFile: $(Pipeline.Workspace)/drop/RetailDW.dacpac
    AdditionalArguments: /p:BlockOnPossibleDataLoss=true

12.3 Flyway example

flyway -url="jdbc:sqlserver://sql-rdp-dev.database.windows.net;databaseName=RetailDW" \
       -user="$SQL_USER" -password="$SQL_PASSWORD" \
       -locations=filesystem:sql/migrations migrate

12.4 Pipeline safety

  • Generate and publish a deploy report/script as an artifact for review before Prod.
  • Block on possible data loss.
  • Approvals on Test/Prod environments.
  • Backups / point-in-time restore available before major changes.
  • Deploy during agreed windows; coordinate with dependent pipelines (pause ADF triggers if needed).

Source S32, S40 · Reviewer must judge data-loss risk

The PR shows only ALTER TABLE ... ALTER COLUMN Region NVARCHAR(20) (shrinking). The generated script/deploy report flags possible data loss; the author adds a pre-deployment check and data migration, or keeps the column width.

Course addition · Hotfix to a stored procedure in production

Branch from main (or the production tag), change the single procedure file, PR with fast-track review, tag patch version, deploy via pipeline — no manual ALTER in SSMS against Prod.

Best practices

Course addition · best practices
  • One object per file, folder per schema/type; consistent naming (usp_, vw_, fn_ per standard).
  • Idempotent scripts (CREATE OR ALTER, IF NOT EXISTS) for anything run outside DACPAC.
  • Build DACPAC on every PR; review generated deployment scripts for Prod.
  • No credentials in code; Entra ID auth or Key Vault-backed connection strings.
  • Reference data in post-deployment MERGE scripts; never edit released migration scripts.

Beginner
Why put SQL scripts under version control?

History, reviews, rollback, collaboration and automated deployment for database objects, just like application code.

Intermediate
What is a DACPAC?

A data-tier application package containing the database model built from a SQL project; SqlPackage compares it with a target to publish changes.

State-based vs migration-based deployment?

State-based stores the desired schema and computes the diff at deploy time; migration-based stores ordered change scripts applied once each.

Advanced
How do you prevent destructive changes reaching production unnoticed?

BlockOnPossibleDataLoss=true, generate and review deploy scripts/reports in the PR or pre-prod stage, approvals on Prod, and explicit data-migration scripts.

Scenario
Two developers change the same stored procedure in parallel branches. How do you minimize pain?

Small focused changes, frequent integration, one object per file, clear ownership; resolve conflicts in the object file and rebuild/test the project before merging.
