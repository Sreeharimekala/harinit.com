Learning objectives

Chapter introduction

What it is. GitHub Actions is GitHub's built-in automation platform: workflows (YAML in .github/workflows/) triggered by events, made of jobs running on runners, with steps that run commands or reusable actions.

Why it matters. It turns every PR into an automatic quality check and every merge or tag into a repeatable deployment — with secrets, environments and approvals built in.

Where it is used. CI (lint, test, build), CD (deploy to Azure/Databricks/Fabric), scheduled jobs, repository automation.

In this course's project. Stage 7: ci.yml validates every PR (Python tests, SQL build, ADF validation, bundle validate); deploy.yml deploys to Test on merge and to Prod on tags with a required reviewer, using OIDC to Azure.

What is GitHub Actions?

Source S40 · 1. What is GitHub Actions?

1.1 Definition

GitHub Actions is GitHub's built-in automation and CI/CD platform. You define workflows in YAML files inside the repository; GitHub runs them on runners in response to events (push, pull request, schedule, manual trigger, release, etc.).

1.2 Uses

  • Continuous integration: lint, test, build on every push/PR.
  • Continuous deployment to Azure, Databricks, Fabric, AWS, Kubernetes.
  • Automation: labelling issues, releasing, dependency updates, scheduled jobs.

1.3 Pricing (summary)

Free for public repositories on GitHub-hosted runners; private repositories get monthly included minutes by plan; self-hosted runners don't consume GitHub-hosted minutes. (Check current GitHub billing documentation for exact quotas.)

Introduction to CI/CD

Source S40 · 2. Introduction to CI/CD
Term Meaning
Continuous Integration (CI) Developers merge small changes frequently; each change is automatically built and tested to detect problems early
Continuous Delivery (CD) Every validated change is automatically prepared for release; deployment to production requires approval
Continuous Deployment Every validated change is deployed to production automatically

29.22

Workflows

Source S40 · 4. Workflows

4.1 Definition

A workflow is a YAML file in .github/workflows/ that defines when and how automation runs. A repository can have many workflows.

4.2 Minimal workflow

# .github/workflows/hello.yml
name: Hello
on: push
jobs:
  greet:
    runs-on: ubuntu-latest
    steps:
      - run: echo "Hello from ${{ github.repository }} on ${{ github.ref_name }}"

4.3 Viewing runs

Repository → Actions tab → choose workflow → run → job → step logs. CLI:

gh workflow list
gh run list
gh run view <run-id> --log
gh workflow run ci.yml --ref main

4.4 Reusable workflows

# .github/workflows/deploy-template.yml
on:
  workflow_call:
    inputs:
      environment: { type: string, required: true }
    secrets:
      AZURE_CLIENT_ID: { required: true }

# caller
jobs:
  deploy-dev:
    uses: ./.github/workflows/deploy-template.yml
    with: { environment: dev }
    secrets: inherit
29.23

Events and Triggers

Source S40 · 5. Events and Triggers
on:
  push:
    branches: [main, 'release/**']
    paths: ['python/**', 'sql/**']
    tags: ['v*.*.*']
  pull_request:
    branches: [main]
    types: [opened, synchronize, reopened]
    paths-ignore: ['docs/**', '**.md']
  workflow_dispatch:                 # manual "Run workflow" button
    inputs:
      environment:
        type: choice
        options: [dev, test, prod]
        default: dev
  schedule:
    - cron: '30 1 * * *'             # daily 01:30 UTC
  release:
    types: [published]
  workflow_run:                       # after another workflow
    workflows: ["CI"]
    types: [completed]
  repository_dispatch:                # external API trigger
    types: [deploy]
Event Typical use
push CI on branches, deploy on main/tags
pull_request PR validation (runs in the PR's merge context)
workflow_dispatch Manual runs with inputs
schedule Nightly jobs, data checks
release Publish packages when a release is published
workflow_call Reusable workflows
issues, issue_comment Automation on issues

Security note pull_request_target runs with repository secrets in the base context — avoid checking out untrusted PR code in it.

29.24

Jobs

Source S40 · 6. Jobs

6.1 Definition

A job is a group of steps that run on the same runner. Jobs run in parallel by default.

jobs:
  lint:
    runs-on: ubuntu-latest
    timeout-minutes: 10
    steps: [...]
  test:
    runs-on: ubuntu-latest
    strategy:
      fail-fast: false
      matrix:
        python-version: ['3.10', '3.11', '3.12']
        os: [ubuntu-latest, windows-latest]
    steps: [...]
  deploy:
    needs: [lint, test]               # sequential dependency
    if: github.ref == 'refs/heads/main'
    runs-on: ubuntu-latest
    environment: dev
    steps: [...]

6.2 Job-level keys

Key Purpose
runs-on Runner label
needs Dependencies
if Condition
strategy.matrix Run variants in parallel
environment Deployment environment
env Job environment variables
outputs Values passed to dependent jobs
timeout-minutes Maximum run time
concurrency Limit simultaneous runs
permissions GITHUB_TOKEN permissions
container, services Run in a container; sidecar services (e.g. Postgres)
continue-on-error Don't fail the workflow if this job fails
29.25

Steps

Source S40 · 7. Steps

A step is either a shell command (run) or an action (uses). Steps run sequentially and share the runner's filesystem.

steps:
  - name: Checkout code
    uses: actions/checkout@v4
    with:
      fetch-depth: 0             # full history (needed for tags/describe)

  - name: Install dependencies
    run: |
      python -m pip install --upgrade pip
      pip install -r python/requirements.txt

  - name: Run tests
    id: tests
    working-directory: python
    shell: bash
    run: pytest -v --junitxml=results.xml

  - name: Only on failure
    if: failure()
    run: echo "Tests failed"

Step keys: name, id, uses, with, run, shell, working-directory, env, if, continue-on-error, timeout-minutes.

Pass values between steps:

  - id: version
    run: echo "value=$(git describe --tags --always)" >> "$GITHUB_OUTPUT"
  - run: echo "Version is ${{ steps.version.outputs.value }}"
29.26

Actions

Source S40 · 8. Actions

8.1 Definition

An action is a reusable unit of automation referenced with uses:.

Source Example
GitHub Marketplace actions/checkout@v4, actions/setup-python@v5, azure/login@v2, databricks/setup-cli@main
Same repository uses: ./.github/actions/sql-lint
Docker image uses: docker://alpine:3.20

8.2 Common actions

Action Purpose
actions/checkout Clone the repository into the runner
actions/setup-python / setup-node / setup-dotnet Install language runtimes (with caching)
actions/cache Cache dependencies
actions/upload-artifact / download-artifact Share files between jobs
azure/login Authenticate to Azure (OIDC)
azure/arm-deploy Deploy ARM/Bicep
azure/sql-action Deploy DACPAC/SQL to Azure SQL
databricks/setup-cli Install Databricks CLI
github/codeql-action Code scanning

8.3 Version pinning

uses: actions/checkout@v4                                       # major tag (convenient)
uses: actions/checkout@11bd71901bbe5b1630ceea73d27597364c9af683 # full commit SHA (most secure)

Pin third-party actions to a full SHA for supply-chain security; let Dependabot update them.

8.4 Composite action (create your own)

# .github/actions/sql-lint/action.yml
name: SQL lint
description: Lint SQL with SQLFluff
runs:
  using: composite
  steps:
    - run: pip install sqlfluff
      shell: bash
    - run: sqlfluff lint sql/ --dialect tsql
      shell: bash

Runners

Source S40 · 9. Runners

9.1 GitHub-hosted runners

Label OS
ubuntu-latest (ubuntu-24.04, ubuntu-22.04) Linux
windows-latest (windows-2022, windows-2025) Windows
macos-latest macOS
Larger runners More CPU/RAM, static IPs (paid)

Fresh VM for every job, preinstalled tools, managed by GitHub.

9.2 Self-hosted runners

Your own machines/VMs/containers registered to a repo, org or enterprise (Settings → Actions → Runners → New self-hosted runner).

runs-on: [self-hosted, linux, data-vnet]

Use when: access to private networks (on-prem SQL Server, private endpoints), special hardware, cost control, compliance. Caution: don't use self-hosted runners for public repositories (untrusted PR code could run on your infrastructure); keep them patched; prefer ephemeral runners (e.g. Actions Runner Controller on Kubernetes).

29.28

Workflow YAML Files

Source S40 · 10. Workflow YAML Files

10.1 Structure

name: CI                              # display name
run-name: CI for ${{ github.ref_name }} by @${{ github.actor }}

on: { ... }                           # triggers

permissions:                          # least-privilege GITHUB_TOKEN
  contents: read

env:                                  # workflow-level variables
  PYTHON_VERSION: '3.11'

concurrency:
  group: ${{ github.workflow }}-${{ github.ref }}
  cancel-in-progress: true

defaults:
  run:
    shell: bash

jobs:
  job_id:
    name: Display name
    runs-on: ubuntu-latest
    steps: [ ... ]

10.2 YAML essentials

  • Indentation with spaces (no tabs); consistent 2 spaces.
  • Lists with -; maps with key: value.
  • Multi-line strings with | (keep newlines) or > (fold).
  • Quote strings with special characters ('*', ':', on).
  • Expressions: ${{ <expression> }} — contexts like github, env, vars, secrets, matrix, steps, needs, inputs, runner; functions like contains(), startsWith(), format(), toJSON(), hashFiles(), status functions success(), failure(), always(), cancelled().

10.3 Complete CI workflow for the course project

# .github/workflows/ci.yml
name: CI

on:
  pull_request:
    branches: [main]
  push:
    branches: [main]

permissions:
  contents: read

concurrency:
  group: ci-${{ github.ref }}
  cancel-in-progress: true

jobs:
  python:
    runs-on: ubuntu-latest
    strategy:
      matrix:
        python-version: ['3.10', '3.11']
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-python@v5
        with:
          python-version: ${{ matrix.python-version }}
          cache: pip
      - run: pip install -r python/requirements.txt pytest ruff
      - run: ruff check python/
      - run: pytest python/tests -v

  sql:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - run: pip install sqlfluff
      - run: sqlfluff lint sql/ --dialect tsql

  secrets-scan:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
        with: { fetch-depth: 0 }
      - uses: gitleaks/gitleaks-action@v2
        env:
          GITHUB_TOKEN: ${{ secrets.GITHUB_TOKEN }}

Use VS Code's YAML/GitHub Actions extension for validation, or actionlint locally.

29.30

Secrets Management

Source S40 · 12. Secrets Management

12.1 Storing secrets

Settings → Secrets and variables → Actions → New repository secret (also environment and organisation secrets). Encrypted; write-only in the UI; masked in logs.

- run: ./deploy.sh
  env:
    SQL_PASSWORD: ${{ secrets.SQL_PASSWORD }}

gh secret set SQL_PASSWORD --env prod

12.2 Precedence

Environment secret > repository secret > organisation secret (same name).

12.3 GITHUB_TOKEN

Automatically created per run, scoped to the repository; control with permissions::

permissions:
  contents: read
  pull-requests: write
  id-token: write        # required for OIDC

12.4 OIDC — no stored cloud secrets (recommended)

  1. Create an Entra ID app registration / user-assigned managed identity.
  2. Add a federated credential for repo:company/retail-data-platform:environment:prod.
  3. Grant it roles on Azure resources.
  4. Workflow:
permissions:
  id-token: write
  contents: read
jobs:
  deploy:
    runs-on: ubuntu-latest
    environment: prod
    steps:
      - uses: azure/login@v2
        with:
          client-id: ${{ vars.AZURE_CLIENT_ID }}
          tenant-id: ${{ vars.AZURE_TENANT_ID }}
          subscription-id: ${{ vars.AZURE_SUBSCRIPTION_ID }}
      - run: az account show

12.5 Best practices

  • Never echo secrets; avoid passing them on command lines.
  • Environment-scoped secrets for Prod, protected by required reviewers.
  • Rotate regularly; prefer OIDC and Key Vault (azure/get-keyvault-secrets or az keyvault secret show at runtime).
  • Secrets are not passed to workflows from forked PRs.

Workflow Dependencies

Source S40 · 13. Workflow Dependencies

13.1 Between jobs — needs

jobs:
  build:   { runs-on: ubuntu-latest, steps: [...] }
  test:    { needs: build, runs-on: ubuntu-latest, steps: [...] }
  deploy-dev:
    needs: [build, test]
    runs-on: ubuntu-latest
    steps: [...]
  notify:
    needs: deploy-dev
    if: always()                   # run even if deploy failed
    runs-on: ubuntu-latest
    steps:
      - run: echo "Deploy result: ${{ needs.deploy-dev.result }}"

13.2 Passing outputs between jobs

jobs:
  version:
    runs-on: ubuntu-latest
    outputs:
      tag: ${{ steps.v.outputs.tag }}
    steps:
      - uses: actions/checkout@v4
        with: { fetch-depth: 0 }
      - id: v
        run: echo "tag=$(git describe --tags --always)" >> "$GITHUB_OUTPUT"
  deploy:
    needs: version
    runs-on: ubuntu-latest
    steps:
      - run: echo "Deploying ${{ needs.version.outputs.tag }}"

13.3 Between workflows

  • workflow_run — trigger after another workflow completes.
  • workflow_call — call a reusable workflow.
  • Artifacts — actions/upload-artifact / download-artifact (within a run; cross-run with run ID).

Scheduled Workflows

Source S40 · 14. Scheduled Workflows
on:
  schedule:
    - cron: '30 1 * * *'      # every day 01:30 UTC = 07:00 IST
    - cron: '0 3 * * 1'       # every Monday 03:00 UTC
  workflow_dispatch:           # allow manual runs too

Cron format: minute hour day-of-month month day-of-week (UTC).

Expression Meaning
0 * * * * Every hour
*/15 * * * * Every 15 minutes (minimum interval is 5 minutes)
0 2 * * 1-5 02:00 UTC weekdays
0 0 1 * * First day of each month

Notes: runs on the default branch; may be delayed at busy times; scheduled workflows in public repos are disabled after 60 days without repository activity.

Data Engineering use cases: nightly data-quality checks, dependency/security scans, drift detection (bundle validate, terraform plan), cleanup jobs.

        uses: actions/upload-artifact@v4
        with:
          name: test-results
          path: |
            test-results.xml
            coverage.xml

Test types for data projects: unit tests (PySpark with local Spark session), SQL linting, schema validation, data quality tests (Great Expectations, dbt tests, custom SQL assertions), integration tests in a Dev workspace, bundle/ADF validation.

Deployment Automation

Source S40 · 17. Deployment Automation

17.1 Environments

Settings → Environments → New environment (dev, test, prod):

  • Required reviewers (approval before the job runs).
  • Wait timer.
  • Deployment branches/tags (e.g. only main and v* tags).
  • Environment secrets and variables.

17.2 Multi-environment deployment workflow

# .github/workflows/deploy.yml
name: Deploy

on:
  push:
    branches: [main]
    tags: ['v*.*.*']

permissions:
  id-token: write
  contents: read

jobs:
  build:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - run: echo "build artifacts..."
      - uses: actions/upload-artifact@v4
        with: { name: drop, path: . }

  deploy-dev:
    needs: build
    runs-on: ubuntu-latest
    environment: dev
    steps:
      - uses: actions/download-artifact@v4
        with: { name: drop }
      - uses: azure/login@v2
        with:
          client-id: ${{ vars.AZURE_CLIENT_ID }}
          tenant-id: ${{ vars.AZURE_TENANT_ID }}
          subscription-id: ${{ vars.AZURE_SUBSCRIPTION_ID }}
      - run: ./scripts/deploy.sh dev

  deploy-prod:
    needs: deploy-dev
    if: startsWith(github.ref, 'refs/tags/v')
    runs-on: ubuntu-latest
    environment: prod                 # waits for approval
    steps:
      - uses: actions/download-artifact@v4
        with: { name: drop }
      - uses: azure/login@v2
        with:
          client-id: ${{ vars.AZURE_CLIENT_ID }}
          tenant-id: ${{ vars.AZURE_TENANT_ID }}
          subscription-id: ${{ vars.AZURE_SUBSCRIPTION_ID }}
      - run: ./scripts/deploy.sh prod

The Deployments view shows what's deployed to each environment, from which commit.

Managing Workflow Failures

Source S40 · 18. Managing Workflow Failures

18.1 Diagnose

  • Actions tab → failed run → failed job → expand the failing step log.
  • Re-run failed jobs or Re-run all jobs; enable debug logging on re-run (or set secret/variable ACTIONS_STEP_DEBUG=true, ACTIONS_RUNNER_DEBUG=true).
  • Download logs; use gh run view --log-failed.

18.2 Common failures

Symptom Likely cause Fix
Workflow didn't trigger Wrong on: filters/paths/branch; file not on default branch for schedule Fix triggers
YAML error Indentation, invalid key Validate with actionlint/VS Code
Resource not accessible by integration Insufficient GITHUB_TOKEN permissions Add permissions:
Azure login fails (OIDC) Federated credential subject mismatch, missing id-token: write Fix subject (branch/environment), permissions
Secret empty Secret not defined at that level / fork PR Define secret; avoid secrets in fork PR workflows
Tests pass locally, fail in CI Missing dependency, OS/path differences, timezone Pin dependencies, use matrix, set TZ
Timeout Long step timeout-minutes, caching, parallelism

18.3 Resilience techniques

    timeout-minutes: 30
    continue-on-error: false
    steps:
      - name: Flaky external call with retry
        run: |
          for i in 1 2 3; do ./call_api.sh && break || sleep 10; done
      - name: Notify on failure
        if: failure()
        run: curl -X POST -H 'Content-type: application/json' --data '{"text":"Deploy failed: ${{ github.run_id }}"}' "${{ secrets.TEAMS_WEBHOOK }}"
  • concurrency to avoid overlapping deployments.
  • Required status checks so failing CI blocks merging.
  • Notifications (email, Teams/Slack) on failure.
  • Keep workflows small and modular (reusable workflows) to isolate failures.

Real-time scenarios

Source S30, S40 · Required check "python (3.12)" never reports

The ruleset requires a job name that the workflow doesn't produce (renamed job or matrix change) or the workflow has a paths filter that skipped it. Align required check names with job names, or use a summary job that always runs.

Course addition · Workflow from a fork needs secrets

pull_request from forks receives no secrets by design. Run tests that need secrets after merge, or use a maintainer-triggered workflow; never check out untrusted PR code in pull_request_target with secrets.

Best practices

Course addition · best practices
  • Least-privilege permissions: at workflow/job level; OIDC instead of cloud secrets.
  • Pin actions to major versions (first-party) or full SHAs (third-party); update via Dependabot.
  • Build once, upload artifacts, deploy the same artifacts to each environment.
  • Use environments with reviewers and branch/tag restrictions for Prod; concurrency for deployments.
  • Cache dependencies; keep workflows fast; make checks required.

Beginner
Where are workflow files stored?

In .github/workflows/ as YAML files.

What is a runner?

A machine (GitHub-hosted or self-hosted) that executes a job.

Intermediate
How do jobs depend on each other?

With needs:; outputs pass data between jobs.

How do you require approval before production deployment?

Use an environment (e.g. prod) with required reviewers and reference it with environment: prod in the job.

Advanced
How does OIDC authentication to Azure work in Actions?

The job requests an OIDC token (id-token: write); azure/login exchanges it with Entra ID for an access token via a federated credential matching repo/branch/environment — no stored secret.

Difference between pull_request and pull_request_target?

pull_request runs in the PR's context with read-only token for forks; pull_request_target runs in the base repo context with secrets — dangerous if it executes PR code.

Scenario
Deployments overlap when two merges happen quickly. Fix?

Add concurrency with a group per environment and cancel-in-progress: false, so deployments queue.
