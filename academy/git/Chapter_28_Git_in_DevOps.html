Learning objectives

Chapter introduction

What it is. The role of Git in DevOps: Git as the single source of truth for code, configuration, pipelines and infrastructure; Git-based development workflows; release management; version control in production; Infrastructure as Code; and GitOps.

Why it matters. In DevOps, every change to a running system starts as a commit. That gives traceability (who/what/why), repeatability (rebuild from Git), and safe automation (pipelines triggered by Git events).

Where it is used. CI/CD on GitHub Actions and Azure Pipelines, IaC (Bicep/Terraform), GitOps controllers (Flux, Argo CD) for Kubernetes, DataOps for data platforms.

In this course's project. Stage 7 design: the Enterprise Retail Data Platform's delivery pipeline — every commit validated, every merge to main deployed to Test, every tag to Prod after approval — with infrastructure defined in infra/.

Introduction to DevOps

Source S40 · 1. Introduction to DevOps

1.1 Definition

DevOps is a set of culture, practices and tools that unify software development (Dev) and IT operations (Ops) to deliver changes faster, more reliably and more frequently, through automation, collaboration and continuous feedback.

1.2 The DevOps lifecycle

        ┌──────── Plan ◄────── Monitor ◄──────┐
        │                                      │
        ▼                                      │
      Code ──► Build ──► Test ──► Release ──► Deploy ──► Operate
Stage Data Engineering example
Plan Backlog items in Azure Boards / GitHub Projects
Code SQL, PySpark, ADF JSON in Git branches
Build Package wheel, DACPAC, ADF ARM templates, Databricks bundle
Test Unit tests, data quality checks, integration runs
Release Approve and version (tag)
Deploy Promote to Test/UAT/Prod automatically
Operate Scheduled pipelines run
Monitor Pipeline failures, data freshness, costs → feed back into Plan

1.3 Core principles

Collaboration and shared ownership, automation of everything repeatable, continuous integration and delivery, infrastructure as code, monitoring and fast feedback, small incremental changes.

1.4 DataOps

DataOps applies DevOps principles to data pipelines — adding data testing, data quality monitoring and environment management for data.

28.16

Branching Strategies in DevOps

Source S40 · 6. Branching Strategies in DevOps

6.1 Strategy → environment mapping

Option A — Single main + environment promotion (recommended):

feature/* ──PR──► main ──build once──► Dev ──approve──► Test ──approve──► Prod

Option B — Git Flow:

feature/* → develop (→ Dev)
release/* (→ Test/UAT)
main + tag (→ Prod)
hotfix/* → main + develop

Option C — Environment branches (dev, test, prod):

feature → dev branch (Dev) → PR → test branch (Test) → PR → prod branch (Prod)

Used by some ADF/Fabric setups. Risks: drift between branches, cherry-pick complexity, merge conflicts. Prefer Option A when the tooling allows.

6.2 Selection criteria

Release cadence, team size, regulatory requirements, test automation maturity, tooling constraints (e.g. Fabric workspace-branch mapping).

28.17

Release Management

Source S40 · 7. Release Management

DevOps release management with Git:

  1. Versioning — semantic versions; tag on main.
  2. Release notes — generated from PRs/Conventional Commits.
  3. Build once — artifacts produced from a specific commit.
  4. Promotion — same artifact deployed to each environment with environment-specific configuration.
  5. Approvals and gates — environment approvals, change windows, automated quality gates.
  6. Deployment strategies — blue/green, canary, feature flags (for services); for data: deploy to new schema/version and switch, backfills, run in parallel.
  7. Rollback plan — redeploy the previous tag or git revert + redeploy.
  8. Post-release verification — smoke tests, data reconciliation, monitoring.
28.18

Version Control in Production

Source S40 · 8. Version Control in Production
  • Production must run code that exactly matches a commit/tag in Git — no manual changes in Prod.
  • Disable direct editing in production tools (e.g. ADF Prod factory not Git-connected, read-only Databricks Prod workspace folders, Fabric Prod workspace updated only by pipelines).
  • Record the deployed version: tags, deployment history in GitHub Environments/Azure Pipelines, version tables or job tags.
  • Drift detection — compare the deployed state with Git (e.g. databricks bundle deploy re-applies, Terraform plan, ADF ARM what-if).
  • Hotfixes follow the same Git process (fast-track approvals), never hand edits.
-- Example: record deployed version in the warehouse
INSERT INTO meta.deployment_log (version, commit_sha, deployed_at, deployed_by)
VALUES ('v2.6.0', '9c8b7a6', SYSUTCDATETIME(), 'azure-pipelines');

Git and Infrastructure as Code

Source S40 · 9. Git and Infrastructure as Code

9.1 Definition

Infrastructure as Code (IaC) defines infrastructure (storage accounts, Databricks workspaces, Key Vaults, networks, permissions) in declarative code files stored in Git and deployed by pipelines.

9.2 Tools

Tool Format
Bicep Azure-native, concise
ARM templates Azure JSON
Terraform Multi-cloud HCL
Pulumi General-purpose languages

9.3 Example — Bicep for a data lake

// infra/main.bicep
param location string = resourceGroup().location
param env string

resource lake 'Microsoft.Storage/storageAccounts@2023-01-01' = {
  name: 'strdp${env}${uniqueString(resourceGroup().id)}'
  location: location
  sku: { name: 'Standard_LRS' }
  kind: 'StorageV2'
  properties: {
    isHnsEnabled: true
    minimumTlsVersion: 'TLS1_2'
    allowBlobPublicAccess: false
  }
}

9.4 Git workflow for IaC

Branch → change .bicep/.tf → PR → CI runs what-if / terraform plan and posts it to the PR
→ review the plan → merge → CD applies to Dev → approval → Prod

Benefits: reviewable infrastructure changes, repeatable environments, disaster recovery, drift detection, audit trail.

Note Terraform state files contain sensitive data — store state remotely (Azure Storage backend), never in Git.

28.20

GitOps Introduction

Source S40 · 10. GitOps Introduction

10.1 Definition

GitOps is an operating model where Git is the single source of truth for the desired state of systems, and an automated agent continuously reconciles the running environment to match Git.

10.2 Principles

  1. Declarative — desired state described declaratively.
  2. Versioned and immutable — stored in Git with full history.
  3. Pulled automatically — agents pull desired state (rather than pipelines pushing).
  4. Continuously reconciled — drift is detected and corrected.

10.3 How it works

Developer → PR → merge to Git (desired state)
                         │
                 GitOps agent (Argo CD / Flux) watches repo
                         │
                 Reconciles Kubernetes cluster to match Git
                         │
                 Drift? → auto-correct or alert

10.4 Push-based CI/CD vs GitOps

Aspect Push-based CI/CD GitOps (pull-based)
Who deploys Pipeline pushes to target Agent in target pulls from Git
Credentials Pipeline needs target credentials Agent inside environment
Drift handling Not automatic Continuous reconciliation
Rollback Re-run pipeline git revert
Typical use Most data platforms (ADF, Databricks, Fabric) Kubernetes workloads

GitOps ideas (declarative definitions, reconciliation, Git as truth) also apply to data platforms through bundles, Terraform and Fabric/ADF deployment from Git.

Real-time scenarios

Source S29, S40 · A hotfix must reach production today

Hotfix branch → PR with fast-track reviewers → CI → merge → tag v1.3.1 → pipeline deploys to Test (smoke tests) → Prod approval → deploy. Every step is traceable to the tag and PR.

Course addition · Someone changed an ADF pipeline directly in Prod

Treat as drift: export/compare, re-create the change through Git (branch → PR → deploy), and lock down Prod (no direct edit permissions; publish only via CI).

Best practices

Course addition · best practices
  • Everything as code: application, SQL, pipelines, infrastructure, policies.
  • Build once, promote the same artifact; parametrize per environment.
  • Protect branches and environments; require approvals for Prod.
  • Use tags/releases for production traceability; keep deployment history.
  • Detect and eliminate manual changes (drift).

Chapter 28 Interview Questions

Source S29 · Chapter manual · interview

1. What is DevOps?

A collaborative approach combining development and operations with automation and feedback.

2. Why is Git central to DevOps?

It versions changes and provides traceability and automation triggers.

3. What is CI?

Automated integration validation such as build, lint and tests.

4. What is trunk-based development?

Frequent integration into a shared mainline using short-lived branches.

5. What is GitOps?

An approach where Git stores desired state and automation reconciles environments.

2 What is Git's role in DevOps? Source of truth, collaboration, CI/CD triggers, traceability

Beginner
What role does Git play in DevOps?

Single source of truth for code and configuration; Git events (push, PR, tag) trigger CI/CD and provide traceability.

Intermediate
What is Infrastructure as Code?

Defining infrastructure in versioned files (Bicep, Terraform, ARM) deployed by automation instead of manual configuration.

What is GitOps?

An operating model where the desired system state is declared in Git and an agent continuously reconciles the running system to it (pull-based).

Advanced
Why "build once, deploy many"?

It guarantees that what was tested is exactly what reaches production; rebuilding per environment can introduce differences.

Scenario
Design branch-to-environment mapping for a data platform with weekly releases and urgent hotfixes.

Feature branches → PR validation (no deploy or ephemeral dev); main → auto deploy Test; tags → Prod with approval; hotfix branches merged to main and tagged as patch versions.
