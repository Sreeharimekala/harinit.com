Learning objectives

Chapter introduction

What it is. Git's internal architecture: a content-addressable object database (blobs, trees, commits, annotated tags), references (branches, tags, HEAD, remote-tracking refs), the index, and storage optimizations (loose objects, packfiles, garbage collection).

Why it matters. Internals explain why Git behaves as it does — why branches are cheap, why rewriting history changes IDs, how recovery is possible, and how to keep large repositories fast.

Where it is used. Troubleshooting, recovery, performance tuning, tooling, interviews.

21.1

Git object model

Source S22 · Chapter manual · 1. Git object model

Git is a content-addressable object database. Its four main object types are blob, tree, commit and annotated tag. Each object's ID is derived from its Git object representation. Commits point to trees and parents; trees point to blobs and subtrees.

Commands and practical example

git cat-file -t HEAD
git cat-file -p HEAD
git log --graph --oneline --decorate --all
21.2

Blob objects

Source S22 · Chapter manual · 2. Blob objects

A blob stores file content only. It does not store the filename, directory path or executable bit; that metadata is stored in the tree entry. Identical content can be represented by the same blob object across paths.

Commands and practical example

git hash-object -w sample.csv
git cat-file -p <blob-id>
21.3

Tree objects

Source S22 · Chapter manual · 3. Tree objects

A tree represents a directory snapshot. Entries associate names and modes with object IDs, usually blobs for files and trees for subdirectories. Trees preserve the structure of a committed snapshot.

Commands and practical example

git ls-tree HEAD
git ls-tree -r HEAD
git write-tree
21.4

Commit objects

Source S22 · Chapter manual · 4. Commit objects

A commit records a top-level tree, parent commit(s), author and committer metadata, timestamps and a message. Root commits have no parent; merge commits have multiple parents.

Commands and practical example

git cat-file -p HEAD
git show --no-patch --format=fuller HEAD
21.5

Tag objects

Source S22 · Chapter manual · 5. Tag objects

An annotated tag is a Git object containing the target object, tagger metadata and message. A lightweight tag is only a reference and does not create a tag object.

Commands and practical example

git tag v1.0-light
git tag -a v1.0.0 -m "Release 1.0.0"
git cat-file -t v1.0.0
git cat-file -p v1.0.0
21.6

SHA-1 and object identification

Source S22 · Chapter manual · 6. SHA-1 and object identification

Git historically used SHA-1 object IDs and also supports SHA-256 repositories. An object ID is calculated from the Git object representation, not simply raw file bytes. Tooling should not assume every ID is 40 hexadecimal characters.

Commands and practical example

git rev-parse --show-object-format
git rev-parse HEAD
21.7

Understanding object storage

Source S22 · Chapter manual · 7. Understanding object storage

Loose objects are compressed and stored under .git/objects using a fan-out directory: the first two hexadecimal characters form a directory and the rest form the filename. Prefer Git commands over editing these internal files directly.

Commands and practical example

git count-objects -v
git cat-file -t <object-id>
git cat-file -p <object-id>
21.8

git/objects directory

Source S22 · Chapter manual · 8. .git/objects directory

This directory contains loose objects and pack storage. A loose object's path is derived from its object ID. Git may later consolidate loose objects into packfiles for efficient storage.

Commands and practical example

git count-objects -v
find .git/objects -maxdepth 2 -type f
21.9

git/refs directory

Source S22 · Chapter manual · 9. .git/refs directory

References are names pointing to object IDs. Local branches commonly live under refs/heads, remote-tracking refs under refs/remotes and tags under refs/tags. Some refs are consolidated in packed-refs.

Commands and practical example

git show-ref
git for-each-ref --format='%(refname) %(objectname:short)'
21.10

HEAD file

Source S22 · Chapter manual · 10. HEAD file

HEAD identifies the current checkout. It normally contains a symbolic reference such as refs/heads/main; in detached-HEAD state it contains an object ID directly. Inspect it with Git commands rather than editing it manually.

Commands and practical example

git symbolic-ref -q HEAD
git rev-parse HEAD
git status --short --branch
21.11

Index file

Source S22 · Chapter manual · 11. Index file

The index, also called the staging area, records the proposed next commit snapshot, including path, mode and object ID metadata. It is a structured binary file, not merely a list of changed names.

Commands and practical example

git ls-files --stage
git diff
git diff --cached
git write-tree
21.12

Git references

Source S22 · Chapter manual · 12. Git references

A branch is a movable reference to a commit; a tag normally identifies a fixed release point. Remote-tracking refs record the last fetched state of remote branches. Git updates refs through reference-management mechanisms.

Commands and practical example

git show-ref
git branch -avv
git tag --list
21.13

Git garbage collection

Source S22 · Chapter manual · 13. Git garbage collection

Garbage collection packs loose objects and prunes eligible unreachable objects according to retention rules. Reflogs can keep otherwise unreachable commits temporarily recoverable. Avoid aggressive pruning during recovery.

Commands and practical example

git gc
git gc --auto
git prune --dry-run
21.14

Git packfiles

Source S22 · Chapter manual · 14. Git packfiles

Packfiles store many Git objects together and may use delta compression to reduce repeated content. Pack indexes let Git locate objects efficiently. They are central to repository storage efficiency.

Commands and practical example

git count-objects -v
git verify-pack -v .git/objects/pack/*.idx
21.15

Repository optimization

Source S22 · Chapter manual · 15. Repository optimization

Use normal maintenance, avoid committing generated datasets, consider Git LFS for suitable binary assets, and use commit-graph and multi-pack-index features for large repositories. Do not rewrite shared history without coordination.

Commands and practical example

git maintenance run
git commit-graph write --reachable
git multi-pack-index write
21.16

Git Object Model

Source S40 · 1. Git Object Model

1.1 Definition

Git is a content-addressable filesystem: a key–value store where every piece of data (an object) is stored under a key equal to the hash of its content. On top of this store, Git builds a version-control user interface.

1.2 The model

                  refs/heads/main
                        │
                        ▼
  commit 9c8b7a6 ─────► tree 4f1a (root)
     │                    ├── blob 7a2b   README.md
     │                    └── tree 3c9d   sql/
     │                           └── tree 8e0f  procedures/
     │                                  └── blob 1d4e  usp_load_customers.sql
     ▼ parent
  commit 3f2a7d1 ─────► tree 2b6c (root) ─── reuses blob 7a2b (README unchanged)
Object type Points to
Commit One tree + zero or more parent commits
Tree Blobs and other trees
Blob Nothing (raw content)
Tag Usually a commit

Key properties: objects are immutable; identical content is stored once; any change creates new objects up the chain (new blob → new trees → new commit).

21.17

Blob Objects

Source S40 · 2. Blob Objects

2.1 Definition

A blob (binary large object) stores the contents of a file — nothing else: no filename, no path, no permissions, no timestamp.

2.2 Demonstration

echo "SELECT 1;" > test.sql
git hash-object -w test.sql           # -w writes the object into .git/objects
# e.g. 2f1d0e9c...
git cat-file -t 2f1d0e9c               # blob
git cat-file -p 2f1d0e9c               # SELECT 1;
git cat-file -s 2f1d0e9c               # size in bytes

2.3 Implications

  • Two files with the same content (anywhere in the project or history) share one blob.
  • Renaming a file doesn't create a new blob — only the tree changes.
21.18

Tree Objects

Source S40 · 3. Tree Objects

3.1 Definition

A tree represents a directory: a list of entries, each with mode, type, hash and name.

git cat-file -p HEAD^{tree}

100644 blob 7a2b...   README.md
040000 tree 3c9d...   sql
040000 tree 5e7f...   python

git ls-tree HEAD
git ls-tree -r HEAD              # recursive: every file
git ls-tree HEAD sql/procedures/

3.2 File modes

Mode Meaning
100644 Normal file
100755 Executable file
120000 Symbolic link
040000 Directory (tree)
160000 Submodule (gitlink)
21.19

Commit Objects

Source S40 · 4. Commit Objects

4.1 Definition

A commit object records a snapshot (root tree), its parent(s), author, committer and message.

git cat-file -p HEAD

tree 4f1a2b3c...
parent 3f2a7d1c...
author Ravi Kumar <ravi.kumar@company.com> 1795002012 +0530
committer Ravi Kumar <ravi.kumar@company.com> 1795002012 +0530

Add fact_sales table

4.2 Notes

  • The root commit has no parent; merge commits have several.
  • Signed commits include a gpgsig header.
  • The commit hash covers all of this — changing any field yields a new commit.
21.20

Tag Objects

Source S40 · 5. Tag Objects

5.1 Definition

An annotated tag is stored as a tag object containing the target object hash, its type, the tag name, the tagger, date and message (plus optional signature). Lightweight tags are not objects — just refs.

git cat-file -p v1.0.0

object 9c8b7a6d...
type commit
tag v1.0.0
tagger Ravi Kumar <ravi.kumar@company.com> 1795002012 +0530

Release 1.0.0

git rev-parse v1.0.0          # hash of the tag object
git rev-parse v1.0.0^{commit} # hash of the commit it points to
21.21

SHA-1 and Object Identification

Source S40 · 6. SHA-1 and Object Identification

6.1 How the ID is calculated

Git hashes a header + content:

"<type> <size-in-bytes>\0<content>"

printf 'hello\n' | git hash-object --stdin
# ce013625030ba8dba906f756967f9e9ca394464a

printf 'blob 6\0hello\n' | sha1sum
# ce013625030ba8dba906f756967f9e9ca394464a  -

6.2 Properties

  • 160-bit SHA-1 → 40 hexadecimal characters.
  • Abbreviations (first 7+ chars) work while unambiguous: git rev-parse --short HEAD.
  • Git uses a collision-detecting SHA-1 implementation (hardened after the 2017 SHAttered attack).
  • SHA-256 repositories are supported (git init --object-format=sha256, 64-char IDs); interoperability with hosting platforms is still limited.

6.3 Integrity

Because each commit hash covers its tree and parents, the hash of the latest commit effectively fingerprints the entire history. Any corruption or tampering changes hashes and is detected (git fsck).

21.22

Understanding Git Object Storage

Source S40 · 7. Understanding Git Object Storage

7.1 Loose objects

New objects are stored individually, zlib-compressed, at:

.git/objects/<first 2 hex chars>/<remaining 38 chars>

Example: object ce0136... → .git/objects/ce/013625030ba8dba906f756967f9e9ca394464a.

7.2 Packed objects

Periodically Git packs many loose objects into packfiles for efficiency (see section 14).

7.3 Inspecting storage

find .git/objects -type f | head
git count-objects -vH

count: 34            # loose objects
size: 136.00 KiB
in-pack: 512         # objects in packfiles
packs: 1
size-pack: 2.10 MiB

7.4 Reading a raw object with Python

import zlib
data = open('.git/objects/ce/013625030ba8dba906f756967f9e9ca394464a','rb').read()
print(zlib.decompress(data))   # b'blob 6\x00hello\n'
21.23

.git/objects Directory

Source S40 · 8. .git/objects Directory
.git/objects/
├── 0a/ ... ff/          # loose objects (256 possible fan-out folders)
├── info/
│   ├── packs            # list of packfiles (for dumb HTTP)
│   ├── alternates       # optional: borrow objects from another repo
│   └── commit-graph     # optional: accelerates history traversal
└── pack/
    ├── pack-<hash>.pack # compressed objects
    ├── pack-<hash>.idx  # index into the pack
    └── pack-<hash>.rev  # reverse index (newer Git)

The two-character fan-out keeps directories small for filesystem performance.

21.24

.git/refs Directory

Source S40 · 9. .git/refs Directory

References (refs) are human-readable names that point to object hashes.

.git/refs/
├── heads/               # local branches
│   ├── main             → 9c8b7a6...
│   └── feature/orders   → 4d5e6f7...
├── remotes/
│   └── origin/
│       ├── main
│       └── HEAD         → ref: refs/remotes/origin/main
├── tags/
│   └── v1.0.0           → tag object hash
└── stash                → latest stash commit

cat .git/refs/heads/main
git show-ref
git for-each-ref --format='%(refname) %(objectname:short)'
git update-ref refs/heads/test 9c8b7a6     # plumbing: create/move a ref

Packed refs: for performance, many refs are stored in .git/packed-refs (one line each). A loose file in refs/ overrides the packed entry. (Newer Git also supports the reftable backend.)

21.25

HEAD File

Source S40 · 10. HEAD File

.git/HEAD records the current position:

ref: refs/heads/main          ← normal (symbolic ref to a branch)
9c8b7a6d5e4f3a2b...           ← detached HEAD (raw commit hash)

cat .git/HEAD
git symbolic-ref HEAD           # refs/heads/main
git rev-parse HEAD              # commit hash

Other special head files:

File Meaning
ORIG_HEAD HEAD before a reset, merge or rebase
FETCH_HEAD Branches fetched by the last git fetch
MERGE_HEAD Commit(s) being merged (during a merge)
CHERRY_PICK_HEAD Commit being cherry-picked
REVERT_HEAD Commit being reverted
REBASE_HEAD Commit being applied during rebase
21.26

Index File

Source S40 · 11. Index File

11.1 Definition

.git/index is a binary file that represents the staging area: a sorted list of every tracked path with its blob hash, file mode, stage number and cached file-system metadata (size, timestamps) used to detect changes quickly.

11.2 Inspect

git ls-files --stage

100644 7a2b... 0    README.md
100644 1d4e... 0    sql/procedures/usp_load_customers.sql

The third column is the stage number:

Stage Meaning (during conflicts)
0 Normal, no conflict
1 Common ancestor (base)
2 "Ours"
3 "Theirs" 
git ls-files -u          # show unmerged (conflicted) entries
git show :1:file.sql     # base version
git show :2:file.sql     # ours
git show :3:file.sql     # theirs

11.3 Role in commands

  • git add writes blobs and updates index entries.
  • git commit turns the index into trees (git write-tree).
  • git status compares HEAD ↔ index ↔ working directory.

21.28

Git Garbage Collection

Source S40 · 13. Git Garbage Collection

13.1 What it does

git gc housekeeps the repository:

  • Packs loose objects into packfiles.
  • Packs refs into packed-refs.
  • Expires old reflog entries.
  • Prunes unreachable objects (objects not referenced by any ref or reflog) older than the grace period (default 2 weeks).
  • Writes the commit-graph.

13.2 When it runs

Automatically (git gc --auto) after certain commands when thresholds are exceeded (e.g. ~6,700 loose objects, 50 packs).

13.3 Commands

git gc                           # normal
git gc --aggressive              # slower, better compression
git gc --prune=now               # prune unreachable objects immediately (dangerous after mistakes!)
git reflog expire --expire=now --all   # expire reflog (used before prune when purging secrets)
git prune                        # low-level pruning

13.4 Relevant settings

Setting Default Meaning
gc.auto 6700 Loose objects before auto gc
gc.autoPackLimit 50 Packs before consolidation
gc.reflogExpire 90 days Reachable reflog entries
gc.reflogExpireUnreachable 30 days Unreachable reflog entries
gc.pruneExpire 2 weeks ago Grace period for unreachable objects
21.29

Git Packfiles

Source S40 · 14. Git Packfiles

14.1 Definition

A packfile stores many objects in one file, using zlib compression and delta compression — similar objects are stored as a base object plus a list of differences.

14.2 Files

  • pack-<hash>.pack — the objects.
  • pack-<hash>.idx — an index for fast lookup by hash.

14.3 Inspecting

git verify-pack -v .git/objects/pack/pack-*.idx | sort -k3 -n | tail -5   # largest objects
git count-objects -vH

14.4 When packfiles are created

  • git gc / git repack.
  • Network transfer — git push, git fetch and git clone send packfiles.
git repack -a -d -f --depth=50 --window=250

Note This is why "Git stores snapshots" and "Git is space efficient" are both true: logically every commit is a snapshot; physically, similar content is delta-compressed in packs.

Real-time scenarios

Source S22, S40 · Why is our repository 2 GB?

git count-objects -vH shows a large size-pack. git rev-list --objects --all | git cat-file --batch-check='%(objecttype) %(objectname) %(objectsize) %(rest)' | sort -k3 -n | tail lists the largest blobs — typically CSV/Parquet samples or PBIX files committed by mistake. Remove them from history (Chapter 24) and use Git LFS or external storage.

Course addition · Same file content in two folders

Git stores one blob; both tree entries point to it. Duplicate content does not double repository size.

Best practices

Course addition · best practices
  • Let Git run gc --auto; enable git maintenance start on large repos.
  • Never edit .git internals by hand; use plumbing commands.
  • Keep large binaries out of history; watch count-objects.
  • Learn the object model — it makes rebase, reset and reflog intuitive.

Chapter 21 Interview Questions

Source S22 · Chapter manual · interview

1. What are Git's four main object types?

Blob, tree, commit and annotated-tag objects.

2. What does a blob store?

File content, not its filename or directory path.

3. What does a tree store?

A directory snapshot with names, modes and references to blobs or subtrees.

4. What does a commit point to?

A top-level tree, parent commit(s), metadata and a message.

5. What is a lightweight tag?

A reference to an object without a separate annotated tag object.

6. Where are loose objects stored?

Under .git/objects using a two-character fan-out directory.

7. What does HEAD represent?

The current checkout's symbolic branch reference or a direct object ID in detached state.

8. What is the Git index?

The staging-area structure describing the next commit snapshot.

9. What is a packfile?

A compact file containing many Git objects, often delta-compressed.

10. Does Git always use SHA-1?

No. Git supports SHA-1 and SHA-256 object formats.

11. What does git gc do?

It performs housekeeping such as packing objects and pruning eligible unreachable objects.

12. Are branches and tags the same?

No. Branches normally move as commits are added; tags usually mark a fixed object.

13. Should users edit .git internals directly?

Generally no; use Git commands to preserve repository consistency.

14. What is a tree's role?

It describes directory structure and points to blobs or subtrees.

15. What is a merge commit?

A commit with multiple parents joining lines of development.

Beginner
What are the four Git object types?

Blob (file content), tree (directory listing), commit (snapshot + metadata + parents), tag (annotated tag).

Where are objects stored?

In .git/objects, as loose files or inside packfiles.

Intermediate
How is a blob's ID calculated?

Hash of the header blob <size>\0 followed by the content (SHA-1 by default, SHA-256 in SHA-256 repositories).

What is a packfile?

A file containing many objects, delta-compressed, with an index (.idx) for fast lookup.

Advanced
Why doesn't renaming a file duplicate its content?

The blob ID depends only on content; the rename changes the tree entry name, re-using the same blob.

What does git gc do?

Packs loose objects and refs, removes unreachable objects older than the prune expiry, expires old reflog entries, and may write a commit-graph.

Scenario
Someone asks whether Git stores diffs. How do you explain?

Logically Git stores full snapshots (trees and blobs); physically packfiles store some objects as deltas for compression. Diffs shown to users are computed on demand.
