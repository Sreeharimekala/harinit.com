36.2

What is Git?

Source S40 · 1. What is Git?

Answer: Git is a free, open-source distributed version control system created by Linus Torvalds in 2005. It tracks changes to files as a series of snapshots (commits), lets many developers work in parallel using branches, and gives every developer a complete local copy of the repository history, so most operations work offline and are very fast. Every object is identified by a cryptographic hash, ensuring data integrity.

Example: "In my project we keep SQL procedures, PySpark code, ADF pipeline JSON and Databricks bundles in one Git repository, so every change is reviewed and deployed through CI/CD."

36.3

What is the difference between Git and GitHub?

Source S40 · 2. What is the difference between Git and GitHub?
Git GitHub
Version control software installed locally Cloud platform that hosts Git repositories
Tracks changes, branches, merges Adds pull requests, code review, issues, Projects, Actions (CI/CD), security scanning, permissions
Works offline, without any server Requires internet for platform features
Open source (Linus Torvalds, 2005) Company (2008), owned by Microsoft since 2018

Git can be used without GitHub (e.g. with Azure Repos, GitLab, Bitbucket or no remote at all).

36.5

Explain Git architecture.

Source S40 · 4. Explain Git architecture.

Answer: Git has four areas:

Working Directory ──git add──► Staging Area (Index) ──git commit──► Local Repository (.git) ──git push──► Remote Repository
        ▲                                                                   │   ▲                              │
        └────────────── git restore / switch ───────────────────────────────┘   └──── git fetch / git pull ────┘
  • Working directory — files you edit.
  • Staging area (index) — changes prepared for the next commit (.git/index).
  • Local repository — the .git folder with all commits (objects) and references (branches, tags, HEAD).
  • Remote repository — shared copy on GitHub/Azure Repos.

Internally, the local repository is a content-addressable object store of blobs (file content), trees (directories), commits (snapshot + parents + metadata) and tags, with refs (branches, tags, HEAD) pointing to commits.

36.6

What is a staging area?

Source S40 · 5. What is a staging area?

Answer: The staging area (also called the index) is an intermediate layer between the working directory and the repository where you choose exactly which changes go into the next commit. It lets you create focused, logical commits even when you've edited many files — or only part of a file (git add -p).

git add sql/procedures/usp_load_customers.sql   # stage
git diff --staged                                # see what's staged
git restore --staged sql/views/vw_test.sql       # unstage
git commit -m "fix(sql): exclude test customers"
36.7

What is the difference between fetch and pull?

Source S40 · 6. What is the difference between fetch and pull?
git fetch git pull
Downloads new commits/branches/tags from the remote git fetch + git merge (or git rebase with --rebase)
Updates only remote-tracking branches (origin/main) Updates your current local branch and working directory
Never changes your work — always safe Can create merge commits or conflicts
Lets you review before integrating Integrates immediately 
git fetch origin
git log --oneline main..origin/main      # review incoming changes
git merge origin/main                     # integrate when ready
# vs
git pull --rebase
36.8

What is the difference between merge and rebase?

Source S40 · 7. What is the difference between merge and rebase?
Merge Rebase
Combines branches, creating a merge commit with two parents (unless fast-forward) Replays commits on top of another base, creating new commits
Preserves true history; non-linear Produces linear, cleaner history
Doesn't rewrite history — safe on shared branches Rewrites history — only for local/private branches
Resolve conflicts once May resolve conflicts per commit 
git switch feature/orders && git merge main      # merge main into feature
git switch feature/orders && git rebase main     # rebase feature onto main
git push --force-with-lease                      # needed after rebasing a pushed branch

Golden rule: never rebase commits that others have based work on (main, develop, shared branches).

36.9

What is a detached HEAD?

Source S40 · 8. What is a detached HEAD?

Answer: Normally HEAD points to a branch, which points to a commit. In detached HEAD, HEAD points directly to a commit — e.g. after git checkout <sha>, git checkout v1.0.0, or in CI builds. You can look around and even commit, but new commits belong to no branch and become unreachable (eventually garbage-collected) when you switch away.

git switch --detach v1.0.0      # inspect a release
git switch -c hotfix/1.0.1       # keep work: create a branch here
git switch main                  # leave detached HEAD

If you already left: find the commit in git reflog and git branch rescue <sha>.

36.10

What is Git Stash?

Source S40 · 9. What is Git Stash?

Answer: git stash temporarily shelves uncommitted changes (staged and unstaged tracked files; untracked with -u) and cleans the working directory, so you can switch context — e.g. to fix a production bug — and restore the changes later.

git stash push -m "WIP orders watermark"
git switch -c hotfix/null-dates main
# ...fix...
git switch feature/orders
git stash pop             # apply and remove (apply keeps it)
git stash list
36.11

What is Cherry-Pick?

Source S40 · 10. What is Cherry-Pick?

Answer: git cherry-pick <sha> applies the changes of a specific commit onto the current branch as a new commit. Used to back-port a fix to a release branch, rescue a commit from an abandoned branch, or move a commit made on the wrong branch.

git switch release/2.4
git cherry-pick -x f00ba12      # -x records the source commit in the message
# on conflict: resolve, git add, git cherry-pick --continue (or --abort)

Risk: duplicate commits with different IDs; prefer merge when you need the whole branch.

36.12

What is Git Reset?

Source S40 · 11. What is Git Reset?

Answer: git reset moves the current branch pointer to another commit and optionally resets the staging area and working directory.

Mode Branch Staging Working dir Use
--soft moved kept kept Redo/squash commits
--mixed (default) moved reset kept Undo commits, re-stage selectively
--hard moved reset reset Discard commits and changes 
git reset --soft HEAD~1
git reset --hard origin/main
git reset sql/views/vw_test.sql     # path form = unstage

It rewrites history — use on local/unpushed commits only.

36.13

What is Git Revert?

Source S40 · 12. What is Git Revert?

Answer: git revert <sha> creates a new commit that undoes the changes of an earlier commit, without rewriting history. It is the safe way to undo commits that are already pushed/shared.

git revert 3f2a7d1
git revert -m 1 <merge-sha>          # revert a merged feature
git revert --no-commit HEAD~3..HEAD && git commit -m "Revert last 3 commits"
36.14

What is Git Restore?

Source S40 · 13. What is Git Restore?

Answer: git restore (Git 2.23+) restores files in the working directory and/or staging area. It doesn't move branches or create commits.

git restore file.sql                      # discard unstaged changes
git restore --staged file.sql             # unstage
git restore --source=HEAD~2 file.sql      # bring back an older version

Reset vs revert vs restore: reset = move branch (rewrite history); revert = new undo commit (safe); restore = file-level changes.

36.15

What is Git Reflog?

Source S40 · 14. What is Git Reflog?

Answer: The reflog is a local log of every position HEAD and branch tips have pointed to — commits, checkouts, resets, rebases, merges, amends. It's Git's safety net for recovering "lost" commits.

git reflog
# a1b2c3d HEAD@{0}: reset: moving to HEAD~2
# 9c8b7a6 HEAD@{1}: commit: Add fact_sales
git reset --hard HEAD@{1}           # or: git branch rescue 9c8b7a6

Reflog is local only (not pushed) and entries expire (default 90/30 days).

36.16

What is Git Squash?

Source S40 · 15. What is Git Squash?

Answer: Squashing combines multiple commits into one, producing a cleaner history — e.g. folding "wip" and "fix typo" commits into a single meaningful commit before merging.

# 1. Interactive rebase
git rebase -i HEAD~4        # change 'pick' to 'squash'/'fixup'
# 2. Squash merge
git merge --squash feature/orders && git commit -m "feat: orders load"
# 3. Soft reset
git reset --soft main && git commit -m "feat: orders load"
# 4. Platform: "Squash and merge" on the pull request
36.17

What is Git Flow?

Source S40 · 16. What is Git Flow?

Answer: Git Flow is a branching model with two long-lived branches and three supporting branch types:

Branch Purpose
main Production releases (tagged)
develop Integration of features for the next release
feature/* New features, from and back to develop
release/* Release stabilisation, merged into main and develop
hotfix/* Urgent production fixes from main, merged into main and develop

Suited to scheduled, versioned releases; heavier than GitHub Flow (main + short feature branches) or trunk-based development.

36.18

What is a Pull Request?

Source S40 · 17. What is a Pull Request?

Answer: A pull request (PR) — called a merge request in GitLab — is a request on a hosting platform to merge changes from one branch into another, providing a place for code review, discussion, automated CI checks and approvals before merging. Branch protection can require approvals, passing checks and resolved conversations. Merge options include merge commit, squash and rebase.

git push -u origin feature/DE-1423-scd2
gh pr create --base main --title "feat(sql): SCD2 for dim_customer" --body "Closes #42"
36.19

What is a Fork?

Source S40 · 18. What is a Fork?

Answer: A fork is a server-side copy of a repository under your own account, sharing history with the original. You push to your fork (origin) and propose changes to the original (upstream) via pull requests. Used when you don't have write access (open source, cross-team contributions).

git clone https://github.com/<you>/project.git
git remote add upstream https://github.com/<org>/project.git
git fetch upstream && git merge upstream/main && git push origin main   # sync fork

Fork vs clone: fork is on the server; clone is a local copy.

36.20

How do you resolve merge conflicts?

Source S40 · 19. How do you resolve merge conflicts?

Answer (step-by-step):

  1. Identify conflicted files: git status / git diff --name-only --diff-filter=U.
  2. Understand both sides: open the file; markers show <<<<<<< HEAD (ours), =======, >>>>>>> branch (theirs); use merge.conflictstyle zdiff3 to see the base; git log --merge -p to see the commits involved; talk to the other author if needed.
  3. Edit to the correct final content — ours, theirs, or a combination — and remove all markers (or use git checkout --ours/--theirs, VS Code merge editor, git mergetool).
  4. git add <file> to mark resolved.
  5. Complete: git commit / git merge --continue (or git rebase --continue).
  6. Run tests / validate (e.g. ADF JSON validation).
  7. Push.

Prevention: small, short-lived branches, frequent syncing with main, modular files, consistent formatting, rerere.

36.21

How do you recover a deleted commit?

Source S40 · 20. How do you recover a deleted commit?

Answer:

git reflog                          # find the commit hash before it was "deleted"
git branch rescue 9c8b7a6           # recover onto a branch
# or
git reset --hard 9c8b7a6            # move current branch back

If it's not in the reflog (e.g. dropped stash, very old): git fsck --lost-found / git fsck --unreachable | grep commit → git show <sha> → git branch rescue <sha>. If it was pushed, fetch it from the remote or a teammate's clone. Recovery is possible until garbage collection prunes unreachable objects.

36.22

How do you undo a pushed commit?

Source S40 · 21. How do you undo a pushed commit?

Answer: Use git revert — it adds a new commit that undoes the change without rewriting shared history:

git revert <sha>
git push

For a merged PR: git revert -m 1 <merge-commit-sha> (or the platform's Revert button, which opens a revert PR).

Only on a private branch nobody else uses, you may rewrite instead:

git reset --hard HEAD~1
git push --force-with-lease

If the commit contained a secret, rotate the secret first, then purge from history (git filter-repo) and force-push.

36.23

How do you manage multiple developers?

Source S40 · 22. How do you manage multiple developers?

Answer:

  • Branching strategy agreed (GitHub Flow / Git Flow) and documented in CONTRIBUTING.md.
  • One feature branch per task, named feature/<ticket>-<desc>, short-lived.
  • Pull requests with templates, CODEOWNERS for automatic reviewers, required approvals.
  • Branch protection/rulesets: no direct pushes to main, required CI checks, up-to-date branches.
  • CI on every PR (lint, tests, validation, secret scan).
  • Frequent syncing with main to reduce conflicts; small PRs.
  • Work item linking (Boards/Issues) for traceability.
  • Tool-specific practices: workspace per developer in Fabric, user Git folders in Databricks, feature branches in ADF Studio, one SQL object per file.
  • Communication: ownership of shared components (linked services, semantic models).
36.24

How do you protect production branches?

Source S40 · 23. How do you protect production branches?

Answer: Using GitHub rulesets / branch protection or Azure DevOps branch policies on main (and release/*):

  • Require pull requests; minimum approvals (e.g. 2); dismiss stale approvals; Code Owner review.
  • Require status checks (build, tests, validation) and up-to-date branches.
  • Require conversation/comment resolution; linked work items.
  • Block force pushes and deletion; restrict bypass to an audited emergency group.
  • Optionally require signed commits and linear history.
  • Protect release tags (v*).
  • Deploy production only via CI/CD from protected branches/tags, with environment approvals; no manual changes in Prod.
36.25

How do you implement Git CI/CD?

Source S40 · 24. How do you implement Git CI/CD?

Answer:

  1. Everything in Git — code, SQL, pipeline JSON, bundles, IaC, and pipeline definitions (.github/workflows/*.yml or azure-pipelines.yml).
  2. CI on pull requests — lint (Ruff, SQLFluff), unit tests (pytest), builds (wheel, DACPAC, ADF ARM via npm, bundle validate), security scans (gitleaks, CodeQL) — as required checks.
  3. Merge to main triggers build once → artifacts.
  4. CD promotes the same artifacts through Dev → Test → Prod with environment approvals, environment-specific configuration (parameter files, variable groups, bundle targets), and secrets from Key Vault/OIDC.
  5. Tag releases (v2.6.0) for production deployments and release notes.
  6. Monitor and rollback — redeploy the previous tag or revert.
on:
  pull_request: { branches: [main] }   # CI
  push: { branches: [main], tags: ['v*'] }   # CD
36.26

How do you manage Git in ADF and Databricks?

Source S40 · 25. How do you manage Git in ADF and Databricks?

Answer:

Azure Data Factory:

  • Git integration (Azure Repos or GitHub) only on the Dev factory; collaboration branch main, publish branch adf_publish, root folder /adf.
  • Developers create feature branches in ADF Studio, debug, save (commit), raise PRs into main.
  • Automated publishing with the @microsoft/azure-data-factory-utilities npm package: CI validates and exports ARM templates from main.
  • CD deploys ARM templates to Test/Prod factories with parameter overrides (arm-template-parameters-definition.json), stopping/starting triggers with the pre/post-deployment script; secrets in Key Vault.

Databricks:

  • Developers use Git folders in their user folders (linked via GitHub App / Entra ID), feature branches, Commit & Push, PRs.
  • Business logic in Python modules with pytest; notebooks as orchestration.
  • Databricks Asset Bundles (databricks.yml) define jobs/pipelines with targets for dev/test/prod.
  • CI runs tests and databricks bundle validate; CD runs databricks bundle deploy -t <target> as a service principal (OAuth/workload identity), with approvals for Prod and catalog/workspace differences handled by bundle variables.

Real-time scenarios

Course addition · STAR story 1 — Introducing a branching strategy

Situation: five engineers committed directly to main; two production incidents in a month. Task: introduce safe collaboration without slowing delivery. Action: GitHub Flow, branch naming with ticket IDs, rulesets (PR + checks), CODEOWNERS, PR template, CI with tests and DACPAC build; trained the team on rebase/merge. Result: no unreviewed changes reached production; median PR lead time under one day; releases traceable by tag.

Course addition · STAR story 2 — Recovering from a force push

Situation: a colleague force-pushed an old branch over a shared feature branch. Task: restore lost commits quickly. Action: found the previous tip in my origin/<branch> reflog (git reflog show origin/feature/x), pushed it to rescue/x, compared with git log rescue/x..feature/x, restored via PR, then enabled "block force pushes" and taught --force-with-lease. Result: zero work lost; rule prevents recurrence.

Course addition · STAR story 3 — ADF promotion without manual publish

Situation: ADF changes were published manually, overwriting each other in Test. Action: Dev-only Git mode, PR build validation with the ADF npm utilities, automated ARM export, pre/post-deployment script, environment approvals, Publish button disabled. Result: reproducible deployments, every change reviewed, rollback by redeploying the previous artifact.

Best practices

Course addition · best practices

  • For any "undo" question, first ask whether the history is shared (pushed) — it decides revert vs reset.

  • Use current terminology: main, git switch/git restore, rulesets, Declarative Automation Bundles (formerly DABs), Fabric Git integration.
  • Bring real numbers from your project (PR size, lead time, deployment frequency) into behavioural answers.

Chapter 36 Interview Questions

Scenario — core Git
You committed to main locally but main is protected. Fix without losing work.

git branch feature/RDP-160-x (keep the commit) → git reset --hard origin/main (on main) → git switch feature/RDP-160-x → git push -u origin feature/RDP-160-x → open PR.

You pushed a commit with a wrong change to a shared branch. Undo it.

git revert <sha> → push (via PR if protected). Do not reset shared history.

You pushed a merge that broke production. Undo it.

git revert -m 1 <merge-sha> → PR → deploy. Re-merging the branch later requires reverting this revert first.

Your last 4 local commits should be one commit.

git reset --soft HEAD~4 && git commit -m "…" or git rebase -i HEAD~4 (squash/fixup). Push with --force-with-lease only if the branch is yours.

You deleted a branch with unmerged work.

git reflog (or the output "Deleted branch x (was abc1234)") → git branch x abc1234. If not in reflog: git fsck --lost-found.

git pull says "Need to specify how to reconcile divergent branches".

Choose: git pull --rebase (linear, own branch), git pull --no-rebase (merge) or git pull --ff-only (fail if diverged); persist with git config pull.rebase true or pull.ff only.

Push rejected: "Updates were rejected because the remote contains work that you do not have locally".

git pull --rebase (or merge), resolve conflicts, run tests, git push.

You must switch branches urgently with uncommitted work including new files.

git stash push -u -m "WIP …" → switch → later git stash pop (resolve if conflicts; entry kept on conflict).

A fix on main is needed on release/1.4.

git switch release/1.4 && git cherry-pick -x <sha> → test → PR → tag v1.4.1.

Find which commit introduced a bug between v1.0.0 and HEAD.

git bisect start HEAD v1.0.0 → git bisect run pytest -q (or mark good/bad) → git bisect reset.

A file is listed in .gitignore but still shows changes.

It is tracked: git rm --cached <file> → commit → keep it ignored; rotate secrets if it contained any.

A 300 MB CSV was pushed last week.

Remove from history with git filter-repo --path <file> --invert-paths on a mirror clone → force-push all refs (coordinate, adjust protection temporarily) → everyone re-clones → add ignore rule/LFS + CI size check.

A password was committed and pushed.

Revoke/rotate it immediately; check audit logs; replace with Key Vault reference; then purge history (filter-repo) if required; enable push protection.

Which commits are on my branch but not on main?

git log --oneline main..HEAD; changes since merge base: git diff main...HEAD.

Who changed line 42 of a procedure and why?

git blame -L 40,45 <file> → git show <sha> → linked PR/issue.

How do you make a local branch track a remote branch?

git branch -u origin/<branch> or git push -u origin <branch> (S41 Q16).

SQL database project (one object per file) → DACPAC built in CI → SqlPackage script/report reviewed → publish with BlockOnPossibleDataLoss=true; or Flyway migrations for migration-based teams.

src layout + pyproject.toml, locked dependencies, no committed venv, tests in CI, build wheel once and deploy the same wheel to all environments; config by env vars, identity by managed identity.

GitHub Actions deploy to Azure without secrets?

GitHub: AB#1234 (Azure Boards app). Azure Repos: #1234 mention or link from the work item.

GitHub: environment with required reviewers. Azure Pipelines: approvals and checks on the environment used by the deployment job.

Behavioural
Describe a time you dealt with a bad merge or broken build caused by Git.

Use STAR story 2 or a broken-build story: identify the merge (git log --merges), revert with -m 1 to restore green, fix forward on a branch with tests, add the missing CI check as a required status.

How do you structure commits in a team project?

Small, logical commits with conventional messages and ticket references; tests with the change; clean history before review (fixup/autosquash); squash-merge features.

Stay calm and blameless: rotate the secret first, inform security, purge history if needed, enable push protection and pre-commit scanning, and document the incident.

Required scenario questions (course brief)
How do you recover a deleted commit?

Find it in git reflog (e.g. HEAD@{3}) or with git fsck --lost-found if it is no longer referenced; inspect it with git show <sha>; restore with git branch rescue <sha> (safe) or git reset --hard <sha> (moves the current branch). On a shared branch, push the rescue branch and merge via PR. Recovery works only while the objects exist (reflog expiry ~30–90 days, before gc prunes).

How do you undo a pushed commit?

git revert <sha> (merge commits: git revert -m 1 <sha>), push through a PR, redeploy. Never reset + force-push a shared branch; if history must be rewritten (secrets), coordinate, use --force-with-lease, and have everyone re-sync.

How do you resolve a merge conflict?

git status to list unmerged paths → open each file, combine the intended changes, remove markers (or git checkout --ours/--theirs deliberately) → validate (git diff --check, tests, JSON/SQL validation) → git add → git commit (or git rebase --continue/git cherry-pick --continue). Abort with git merge --abort if needed.

How do you manage multiple developers on one repository?

Branch per work item (feature/RDP-id-desc), short-lived branches, daily integration with main, PRs with CODEOWNERS reviews and required CI checks, clear ownership of hot files (e.g. ADF pipelines), CONTRIBUTING.md, small PRs, and communication about shared interfaces (schemas, pipeline parameters).

How do you protect production branches?

GitHub rulesets/branch protection or Azure Repos branch policies: PR required, minimum approvals (code owners), required status checks, conversation resolution, no force pushes/deletions, optional signed commits/linear history; restricted bypass; tag rules for v*; environments with required reviewers for production deployments.

How do you implement Git-based CI/CD?

PR → CI (lint, unit tests, builds: wheel, DACPAC, ADF ARM via npm, bundle validate) as required checks; merge → build once and publish artifacts → deploy to Dev/Test automatically; tag → approval → Prod; OIDC/workload identity for cloud auth; Key Vault for secrets; deployment history and rollback by redeploying the previous tag.

How do you manage Git across Dev, Test and Production?

One main branch (no long-lived env branches); environments are deployment targets, not branches. Promotion uses the same artifact and environment-specific parameters (ARM parameters, bundle targets, Fabric deployment rules/parameter.yml, SQL publish profiles); approvals on Prod; only Dev tools (ADF Dev factory, Fabric Dev workspace) are Git-connected.

How do you manage ADF and Databricks source code?

ADF: Dev factory in Git mode (collaboration branch main, root folder /adf), feature branches and PRs, automated publish with @microsoft/azure-data-factory-utilities, ARM deployment to Test/Prod with pre/post scripts and Key Vault references, Publish button disabled. Databricks: Git folders for development, notebooks in source format, shared logic in tested Python modules, Declarative Automation Bundles (formerly Databricks Asset Bundles) with targets deployed by CI as a service principal.

Architecture, reflog and security (quick checks)
Describe Git's architecture in three sentences.

A content-addressable object database (blobs, trees, commits, tags) addressed by SHA hashes; references (branches, tags, HEAD) that name commits; and an index that stages the next snapshot. Commands move data between the working tree, index, local repository and remotes.

What is the reflog and its limitation?

A local log of reference movements (HEAD, branches) used for recovery; it is not shared with remotes and entries expire.

How do you secure Git access in an enterprise?

SSO + 2FA, SSH Ed25519 keys or credential managers, fine-grained short-lived tokens, OIDC for automation, least-privilege teams, protected branches/tags, secret scanning with push protection, signed release tags and regular access reviews.

Corrected answers from online question banks
"git reset --mixed undoes changes in the working directory and index." Correct?

No. --mixed resets the index only; the working tree is kept. Only --hard discards working-tree changes.

"git clean removes ignored files." Correct?

Not by default. It removes untracked, non-ignored files; -x also removes ignored files, -X only ignored files. It requires -f (unless clean.requireForce=false); use -n first.

"The Linux Foundation maintains Git." Correct?

No. Git is maintained by Junio C Hamano with the community; its non-profit home is the Software Freedom Conservancy.

"git checkout always puts you in detached HEAD." Correct?

No. Checking out a branch attaches HEAD to it; only checking out a commit, tag or remote-tracking ref detaches HEAD.

"In GitFlow, feature branches are long-lived." Correct?

No. Only main and develop are long-lived; feature, release and hotfix branches are temporary.

"Delete a stash with git stash drop stash@{name}." Correct?

No. Stashes are addressed by index (stash@{0}) or reflog date syntax; the message is only a label. Use git stash list to find the index.

"Apply a patch from a remote: git fetch <remote> <branch> then git apply <patch-file>." Correct?

Incomplete. Fetch downloads commits, not patch files. Either merge/cherry-pick the fetched commits, or create a patch with git format-patch and apply it with git am (keeps authorship) or git apply.

"How to revert the previous commit: git reset --hard HEAD~1." Correct?

Reset removes the commit (only acceptable if unpushed and you want to discard it). To revert (undo with a new commit, safe for shared history) use git revert HEAD.

"git pull is always git fetch + git merge." Correct?

Partly. If only behind, it fast-forwards; if diverged, Git 2.33+ requires choosing rebase, merge or ff-only (via flags or pull.rebase/pull.ff).

What does git annotate do?

Like git blame (older output format): shows the commit and author for each line. Prefer git blame.

Why is it called a "pull request" and not a "push request"?

The contributor asks the maintainers to pull (fetch and merge) their branch into the target repository — the receiving side performs the pull.
