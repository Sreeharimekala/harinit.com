Habits That Matter in ML Teams

  • Never commit data, models, credentials or .env files — use .gitignore, DVC and a secrets manager
  • Short-lived feature branches and pull requests with review; protect main
  • Strip notebook outputs before committing (nbstripout), or move code into modules
  • Tag releases that went to production (git tag model-v1.3) and record the commit in the model registry
  • Pre-commit hooks for formatting and linting (black/ruff), plus secret scanning

Docker

"It works on my machine" is the oldest deployment problem. A Docker container packages your code with the exact Python version, libraries and system packages it needs, so it runs the same on a laptop, a CI server or a cloud cluster. An image is the recipe's result (built from a Dockerfile); a container is a running instance of it. Nearly every model deployment — Kubernetes, Azure ML, SageMaker, Vertex AI — runs containers.

Virtual machine

Emulates a whole computer with its own operating system. Strong isolation; heavy (GBs, minutes to start).

Container

Shares the host's OS kernel; packages only the app and its dependencies. Light (MBs), starts in seconds, easy to scale.

A Dockerfile for a Model API

# ---- build stage: install dependencies into a virtual environment ----
FROM python:3.12-slim AS build
WORKDIR /app
RUN python -m venv /opt/venv
ENV PATH="/opt/venv/bin:$PATH"
COPY requirements.txt .
RUN pip install --no-cache-dir -r requirements.txt     # cached layer: re-runs only if requirements change

# ---- runtime stage: small image with just what's needed ----
FROM python:3.12-slim
WORKDIR /app
COPY --from=build /opt/venv /opt/venv
ENV PATH="/opt/venv/bin:$PATH" PYTHONUNBUFFERED=1
COPY src/ src/
COPY models/churn_model.joblib models/
RUN useradd --create-home appuser
USER appuser                                            # don't run as root
EXPOSE 8000
HEALTHCHECK CMD python -c "import urllib.request; urllib.request.urlopen('http://localhost:8000/health')"
CMD ["uvicorn", "src.serve:app", "--host", "0.0.0.0", "--port", "8000"]

Good Practice

  • Use slim base images and multi-stage builds; order layers from least to most frequently changed so caching works
  • Pin versions in requirements.txt and the base image tag (better: a digest)
  • Add a .dockerignore (data, notebooks, .git, .env) to keep images small and secrets out
  • Run as a non-root user; scan images for vulnerabilities (Trivy, Docker Scout)
  • Pass configuration and secrets through environment variables or a secrets store, never baked into the image
  • For GPUs, start from CUDA-enabled images (e.g. pytorch/pytorch) and run with --gpus all
Docker packages an application with its runtime, libraries and system dependencies into an image built from a Dockerfile; containers are running instances that share the host kernel, making them lighter and faster than virtual machines and consistent across environments. A model-serving Dockerfile uses a slim pinned base image, installs dependencies before copying code so layers cache, often uses multi-stage builds, runs as a non-root user, exposes the API port and defines a health check. Images are built, tagged, pushed to registries (ACR, ECR, GCR) and run; docker compose runs multi-service setups, and good practice includes .dockerignore, vulnerability scanning and passing secrets at runtime.

Experiment Tracking with MLflow

After a month of experiments, can you say which parameters produced the model in production, on which data, with what score? MLflow records every training run — parameters, metrics, artefacts and the model itself — so runs can be compared, reproduced and promoted. Its model registry gives each model a version and an alias such as "champion", the hand-off point between training and deployment.

Track a Hyperparameter Sweep

Cell — log three runs, each with params, metrics and the modelPython
import os, warnings, logging
os.environ.update(MLFLOW_DISABLE_AGENT_HINT="1", MLFLOW_LOGGING_LEVEL="WARNING"); warnings.filterwarnings("ignore")
import mlflow, mlflow.sklearn, numpy as np
logging.getLogger("mlflow").setLevel(logging.ERROR)
from sklearn.datasets import make_classification
from sklearn.model_selection import train_test_split
from sklearn.ensemble import RandomForestClassifier
from sklearn.metrics import roc_auc_score, f1_score

mlflow.set_tracking_uri("sqlite:///mlflow.db")                   # in teams: a shared tracking server
mlflow.set_experiment("churn-model")
X, y = make_classification(n_samples=3000, n_features=15, n_informative=6, weights=[0.8, 0.2], random_state=3)
X_tr, X_te, y_tr, y_te = train_test_split(X, y, test_size=0.25, stratify=y, random_state=0)

model_uris = {}
for depth, n in [(4, 100), (8, 200), (None, 300)]:
    with mlflow.start_run(run_name=f"rf-depth{depth}") as run:
        mlflow.set_tags({"team": "retention", "data_version": "v2026.11"})
        mlflow.log_params({"max_depth": depth, "n_estimators": n})
        model = RandomForestClassifier(max_depth=depth, n_estimators=n, random_state=0, n_jobs=2).fit(X_tr, y_tr)
        p = model.predict_proba(X_te)[:, 1]
        mlflow.log_metrics({"test_auc": roc_auc_score(y_te, p), "test_f1": f1_score(y_te, p > 0.5)})
        info = mlflow.sklearn.log_model(model, name="model", input_example=X_te[:2],
                                        serialization_format="cloudpickle")   # or skops with an explicit trusted-types list
        model_uris[run.info.run_id] = info.model_uri

runs = mlflow.search_runs(order_by=["metrics.test_auc DESC"])
print(runs[["tags.mlflow.runName", "params.max_depth", "params.n_estimators", "metrics.test_auc", "metrics.test_f1"]].round(4).to_string(index=False))

What to Log

  • Parameters and config files; Git commit (logged automatically from a repo); data version (DVC hash or table snapshot)
  • Metrics on validation and test sets, per-segment metrics, training time
  • Artefacts: model, preprocessing pipeline, plots (confusion matrix, feature importance), sample predictions
  • Use mlflow.autolog() for scikit-learn, XGBoost, LightGBM, PyTorch to capture most of this automatically
  • Alternatives: Weights & Biases, Neptune, and the built-in tracking of Azure ML, SageMaker and Vertex AI
MLflow tracks experiments by logging each run's parameters, metrics, tags, artefacts and model, with search and comparison across runs; models are stored with their environment and signature. The model registry versions models, links each version to its run, and uses aliases such as champion and challenger so serving code loads models:/name@alias rather than files, making promotion and rollback a matter of moving an alias. Teams log code commit, data version, metrics, artefacts and use autologging; alternatives include Weights & Biases and the tracking built into cloud ML platforms.

Data & Model Versioning with DVC

Git is built for small text files; a 5 GB training set or a 500 MB model would wreck a repository. DVC (Data Version Control) stores large files in cheap storage (S3, Azure Blob, GCS, a shared drive) and keeps only a tiny pointer file in Git. Checking out an old commit then brings back the exact data that went with it. DVC also defines pipelines, re-running only the stages whose inputs changed.

Cell — train a pipeline, then define the APIPython
import numpy as np, pandas as pd, time
from sklearn.pipeline import make_pipeline
from sklearn.compose import make_column_transformer
from sklearn.preprocessing import OneHotEncoder, StandardScaler
from sklearn.linear_model import LogisticRegression
rng = np.random.default_rng(5); n = 3000
df = pd.DataFrame({"tenure_m": rng.integers(1, 72, n), "monthly_bill": rng.normal(700, 200, n), "support_calls": rng.poisson(1.2, n),
                   "plan": rng.choice(["basic", "standard", "premium"], n)})
df["churn"] = (rng.random(n) < 1 / (1 + np.exp(-(-0.5 - 0.05 * df.tenure_m + 0.002 * df.monthly_bill + 0.6 * df.support_calls)))).astype(int)
model = make_pipeline(make_column_transformer((StandardScaler(), ["tenure_m", "monthly_bill", "support_calls"]),
                                              (OneHotEncoder(handle_unknown="ignore"), ["plan"])),
                      LogisticRegression()).fit(df.drop(columns="churn"), df.churn)
MODEL_VERSION = "churn-classifier@champion (v1)"

from fastapi import FastAPI, HTTPException
from pydantic import BaseModel, Field
from typing import Literal

class Customer(BaseModel):                                  # the request schema = automatic validation + docs
    tenure_m: int = Field(ge=0, le=600, description="Months as a customer")
    monthly_bill: float = Field(gt=0)
    support_calls: int = Field(ge=0)
    plan: Literal["basic", "standard", "premium"]

class Prediction(BaseModel):
    churn_probability: float
    risk: Literal["low", "medium", "high"]
    model_version: str

app = FastAPI(title="Churn API", version="1.0")

@app.get("/health")
def health():
    return {"status": "ok", "model_loaded": model is not None}

@app.post("/v1/predict", response_model=Prediction)
def predict(c: Customer):
    p = float(model.predict_proba(pd.DataFrame([c.model_dump()]))[0, 1])
    return Prediction(churn_probability=round(p, 4), risk="high" if p > 0.6 else "medium" if p > 0.3 else "low", model_version=MODEL_VERSION)

@app.post("/v1/predict/batch")
def predict_batch(customers: list[Customer]):
    if len(customers) > 1000:
        raise HTTPException(status_code=413, detail="max 1000 customers per request")
    probs = model.predict_proba(pd.DataFrame([c.model_dump() for c in customers]))[:, 1]
    return {"churn_probability": np.round(probs, 4).tolist(), "model_version": MODEL_VERSION}
print("routes:", [r.path for r in app.routes if r.path.startswith(("/v1", "/health"))])

Streamlit Apps

APIs serve other programs; people need a screen. Streamlit turns a Python script into an interactive web app — sliders, file uploads, charts, tables — with no HTML or JavaScript. It's the fastest way to put a model in front of business users for a demo, an internal tool or a "what-if" calculator.

How Streamlit Works

The whole script re-runs from top to bottom every time a user changes a widget. Widgets return their current values; @st.cache_resource keeps expensive things (like a loaded model) between re-runs; st.session_state remembers values across interactions.

Canary With Automatic Rollback

Cell — staged traffic with guardrails on errors and latencyPython
rng = np.random.default_rng(9)
GUARDRAILS = {"error_rate": 0.01, "p95_latency_ms": 120}
def serve(version, n):
    """simulate n requests to a model version; v2-bad has a feature bug that errors on some inputs"""
    lat = rng.gamma(4, {"v1": 15, "v2": 14, "v2-bad": 16}[version], n)
    err = rng.random(n) < {"v1": 0.002, "v2": 0.002, "v2-bad": 0.03}[version]
    return {"error_rate": err.mean(), "p95_latency_ms": np.percentile(lat, 95)}

def canary(new, steps=(0.05, 0.25, 0.5, 1.0), requests_per_step=4000):
    for share in steps:
        m = serve(new, int(requests_per_step * share))
        ok = all(m[k] <= limit for k, limit in GUARDRAILS.items())
        print(f"  {share:>4.0%} traffic → errors {m['error_rate']:.2%}, p95 {m['p95_latency_ms']:.0f} ms  {'✓' if ok else '✗ ROLLBACK to v1'}")
        if not ok: return "v1"
    return new
for version in ("v2", "v2-bad"):
    print(f"rolling out {version}:"); print("  serving:", canary(version))
rolling out v2: 5% traffic → errors 0.00%, p95 100 ms ✓ 25% traffic → errors 0.00%, p95 112 ms ✓ 50% traffic → errors 0.15%, p95 111 ms ✓ 100% traffic → errors 0.12%, p95 108 ms ✓ serving: v2 rolling out v2-bad: 5% traffic → errors 2.50%, p95 115 ms ✗ ROLLBACK to v1 serving: v1

The faulty release is stopped at 5% of traffic instead of hitting every customer. On Kubernetes, tools like Argo Rollouts, Flagger, KServe and service meshes (Istio) automate these traffic splits; Azure ML, SageMaker and Vertex AI endpoints support weighted traffic between model deployments.

Choosing Guardrails

  • Operational: error rate, latency (p95/p99), memory, cost per 1,000 predictions
  • Model: prediction distribution shift vs champion, share of "high risk" outputs, input validation failures
  • Business (slower): conversion, complaints, approval rates — often via an A/B test after the canary
  • Always keep the previous version deployable; rollback should be one command or one alias move
Deployment strategies limit the risk of releasing models: rolling updates replace instances gradually, blue-green switches all traffic between two full environments with instant rollback, canary releases shift traffic in stages (for example 5%, 25%, 50%, 100%) while checking guardrails such as error rate and p95 latency and roll back automatically on breach, shadow deployments send copies of live requests to a challenger whose outputs are logged but not used, and A/B tests measure business impact with random splits. Guardrails combine operational, model-behaviour and business metrics, and rollback must stay trivial.

import numpy as np, pandas as pd, matplotlib.pyplot as plt
from scipy import stats
from sklearn.linear_model import LogisticRegression
from sklearn.metrics import roc_auc_score
rng = np.random.default_rng(10)
def customers(n, week):
    tenure = rng.gamma(2.5, 12 if week < 6 else 6, n)                     # from week 6: many new customers
    bill = rng.normal(700, 200, n) * (1.0 if week < 6 else 1.08)
    calls = rng.poisson(1.2, n)
    w_tenure = -0.05 if week < 9 else -0.005                                 # from week 9: tenure stops protecting
    logit = -0.6 + w_tenure * tenure + 0.002 * bill + 0.5 * calls + (0 if week < 9 else 0.4)
    y = (rng.random(n) < 1 / (1 + np.exp(-logit))).astype(int)
    return pd.DataFrame({"tenure": tenure, "bill": bill, "calls": calls}), y

ref_X, ref_y = customers(5000, 0)
model = LogisticRegression(max_iter=1000).fit(ref_X, ref_y)
ref_scores = model.predict_proba(ref_X)[:, 1]

def psi(ref, cur, bins=10):
    edges = np.unique(np.quantile(ref, np.linspace(0, 1, bins + 1))); edges[0], edges[-1] = -np.inf, np.inf
    e = np.histogram(ref, edges)[0] / len(ref); a = np.histogram(cur, edges)[0] / len(cur)
    e, a = np.clip(e, 1e-4, None), np.clip(a, 1e-4, None)
    return float(np.sum((a - e) * np.log(a / e)))

rows = []
for week in range(1, 13):
    X, y = customers(2000, week)
    s = model.predict_proba(X)[:, 1]
    rows.append({"week": week, "psi_tenure": psi(ref_X.tenure, X.tenure), "psi_bill": psi(ref_X.bill, X.bill),
                 "ks_p_tenure": stats.ks_2samp(ref_X.tenure, X.tenure).pvalue, "psi_score": psi(ref_scores, s),
                 "mean_score": s.mean(), "actual_churn": y.mean(), "auc": roc_auc_score(y, s)})

Feature Stores

Three teams compute "customer's spend in the last 30 days" three different ways, and the serving code computes it a fourth way. A feature store defines each feature once and serves it consistently: historical values for training (correct as of each past moment) and the latest values for real-time prediction. It removes duplicated work and the subtle bug of training–serving skew.
1
Feature definitions
Named, versioned transformations with owners and descriptions (spend_30d, orders_7d, days_since_last_order)
2
Offline store
Full history in the lakehouse/warehouse — used to build training sets with point-in-time joins
3
Online store
Latest value per entity in a low-latency database (Redis, Cosmos DB, DynamoDB) — used at prediction time
4
Registry & materialisation jobs
Catalogue for discovery and reuse; scheduled jobs that compute features and keep both stores in sync

The Point-in-Time Join

To train a model that predicts churn on a date, each training row may only use feature values known before that date. A plain join on customer ID would pull in future values — leakage that inflates offline accuracy.

    rng = np.random.default_rng(seed)
    df = pd.DataFrame({"tenure_m": rng.gamma(2.5, 6 if drift else 12, n).round(),

    e_ = np.unique(np.quantile(ref, np.linspace(0, 1, bins + 1))); e_[0], e_[-1] = -np.inf, np.inf

MLOps Interview Questions

Common MLOps and ML-engineering interview questions with concise answers. Many are scenario questions — answer with the steps you'd take, not just definitions.

Concepts

QuestionStrong answer
What is MLOps and how does it differ from DevOps?DevOps practices applied to ML, plus versioning data and models, experiment tracking, data/model validation, model-specific deployment and drift monitoring with retraining. (10.1)
How do you make an ML result reproducible?Git commit for code, DVC/data snapshot for data, pinned environment (requirements, Docker image), parameters in config, random seeds, everything logged in MLflow with the model. (10.1–10.4)
What does a model registry give you?Versioned models linked to their runs, aliases/stages (champion/challenger), approval workflow, and a single place serving code loads from — easy promotion and rollback. (10.3)
Why containers for ML?Identical environment everywhere; isolated dependencies (including CUDA); the deployment unit for Kubernetes and managed endpoints. (10.2)
Batch vs online inference?Batch: scheduled scoring to a table — cheap, simple, high throughput. Online: per-request API with latency limits. Choose by when the decision is made. (10.5)
What is training–serving skew?Features computed differently in training and serving (or different data), so production inputs don't match what the model learned. Prevent with shared pipeline code, feature stores and input logging. (10.11)

Scenarios

QuestionStrong answer
Accuracy dropped in production. What do you do?Check service and data-quality issues first (pipeline bugs, schema changes); compare feature distributions (PSI/KS) to training; check segment performance and label delays; distinguish data vs concept drift; fix the pipeline, recalibrate or retrain on recent data; add the missing alert. (10.10)
How would you deploy a new model version safely?Pass offline gates; shadow it on live traffic; canary 5→25→100% with error/latency/prediction guardrails and automatic rollback; A/B test for business impact; keep the old version one alias move away. (10.9)
Design CI/CD for an ML project.On PR: lint, unit, data and behavioural tests. On merge: train in a pipeline, evaluate vs champion, register if better, build image, deploy to staging, integration tests, approval, canary to prod. Scheduled/drift-triggered continuous training. (10.8)
Your API's p95 latency is too high. Options?Profile; load the model once; batch requests; smaller or quantised model; caching; async I/O; more replicas/autoscaling; move to a dedicated inference server or GPU. (10.5, 10.7)
How do you avoid leakage when building training sets from event data?Point-in-time joins (merge_asof / feature store), time-based splits, features computed only from data before the prediction time. (10.11)
When would you use Kubernetes vs a managed endpoint?Managed endpoints (Azure ML, SageMaker, Vertex) for less ops overhead; Kubernetes when you need many services, custom networking, multi-cloud portability or an existing platform team. (10.7, 10.12)
How do you decide when to retrain?Schedule (e.g. monthly) as a baseline, plus triggers from drift or performance alerts; retrain only promotes if the challenger passes gates; watch cost and label availability. (10.10, 10.13)

import numpy as np
from fastapi import FastAPI
from fastapi.testclient import TestClient
def psi(ref, cur, bins=10):
    edges = np.quantile(ref, np.linspace(0, 1, bins + 1)); edges[0], edges[-1] = -np.inf, np.inf
    e = np.clip(np.histogram(ref, edges)[0] / len(ref), 1e-4, None); a = np.clip(np.histogram(cur, edges)[0] / len(cur), 1e-4, None)
    return float(np.sum((a - e) * np.log(a / e)))
rng = np.random.default_rng(0)
print(f"PSI same distribution {psi(rng.normal(0, 1, 5000), rng.normal(0, 1, 5000)):.3f} · shifted by 0.5 sd {psi(rng.normal(0, 1, 5000), rng.normal(0.5, 1, 5000)):.3f}")
app = FastAPI()
@app.get("/health")
def health(): return {"status": "ok"}
