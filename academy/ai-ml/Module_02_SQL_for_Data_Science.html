2.1

SQL & Relational Databases

A relational database stores data in tables that are linked by keys. SQL (Structured Query Language) is the standard language for asking those tables questions. This lesson explains tables, keys and relationships, introduces the sample database used throughout the module, and shows how to run SQL yourself.

Why SQL Matters for Data Science

  • Company data — sales, customers, events — lives in databases and warehouses (PostgreSQL, SQL Server, Snowflake, BigQuery, Fabric, Databricks)
  • Filtering and aggregating in the database is far faster than downloading everything to Python
  • It's the most common skill in data job descriptions and technical interviews
  • SQL is declarative: you describe what you want; the database works out how

The complete setup script

Copy this into any SQLite tool to build the same database. It also shows DDL (CREATE TABLE with types and constraints) and DML (INSERT) — covered properly in Lesson 2.7.

CREATE TABLE customers (
    customer_id  INTEGER PRIMARY KEY,
    name         TEXT    NOT NULL,
    email        TEXT    UNIQUE,
    city         TEXT,
    region       TEXT,
    signup_date  DATE,
    segment      TEXT
);
CREATE TABLE products (
    product_id   INTEGER PRIMARY KEY,
    name         TEXT    NOT NULL,
    category     TEXT,
    unit_price   NUMERIC NOT NULL CHECK (unit_price > 0),
    unit_cost    NUMERIC
);
CREATE TABLE orders (
    order_id     INTEGER PRIMARY KEY,
    customer_id  INTEGER NOT NULL REFERENCES customers(customer_id),
    order_date   DATE    NOT NULL,
    status       TEXT,
    channel      TEXT
);
CREATE TABLE order_items (
    order_id     INTEGER NOT NULL REFERENCES orders(order_id),
    product_id   INTEGER NOT NULL REFERENCES products(product_id),
    qty          INTEGER NOT NULL CHECK (qty > 0),
    unit_price   NUMERIC NOT NULL,
    PRIMARY KEY (order_id, product_id)
);
CREATE TABLE employees (
    emp_id       INTEGER PRIMARY KEY,
    name         TEXT NOT NULL,
    manager_id   INTEGER REFERENCES employees(emp_id),
    dept         TEXT,
    salary       INTEGER
);

You write SELECT first, but the database runs clauses in this order — which explains many errors (like using a column alias in WHERE):

→
2 WHERE
→
3 GROUP BY
→
4 HAVING
→
5 SELECT

→
7 LIMIT
A relational database stores data in tables of typed columns and rows, linked by keys: a primary key uniquely identifies each row and a foreign key references another table's primary key, forming one-to-many relationships, with many-to-many relationships resolved through a bridge table such as order_items. NULL represents unknown values. SQL is declarative and largely standard across SQLite, PostgreSQL, MySQL and SQL Server, with dialect differences such as LIMIT versus TOP. Queries are written SELECT-first but logically executed FROM, WHERE, GROUP BY, HAVING, SELECT, ORDER BY, LIMIT.

SELECT, Filtering & Sorting

Most queries start the same way: choose the columns you want, keep only the rows you need, and put them in a useful order. This lesson covers SELECT, calculated columns and aliases, WHERE with all its operators (including the special rules for NULL), ORDER BY, DISTINCT and LIMIT.

NULL Needs Special Handling

Query — the wrong waySQL
SELECT name FROM customers WHERE email = NULL;      -- always returns nothing!
name ---- (0 rows)
Query — the right waySQL
SELECT name, email FROM customers WHERE email IS NULL;
name | email -----------+------ Meera Iyer | NULL Rahul Das | NULL (2 rows)

NULL means "unknown", so email = NULL is itself unknown — never true. Always use IS NULL. The same logic means WHERE email <> 'x' silently skips rows where email is NULL.

Sorting, DISTINCT and LIMIT

QuerySQL
SELECT name, category, unit_price
FROM products
ORDER BY category ASC, unit_price DESC     -- sort by category, then most expensive first
LIMIT 5;
name | category | unit_price --------------+----------+----------- Table Lamp | Decor | 1799 Wall Clock | Decor | 999 Cushion Cover | Decor | 399 Dinner Set | Dining | 4999 Coffee Mug | Dining | 249 (5 rows)

SELECT DISTINCT region, segment
FROM customers

  • Without ORDER BY, row order is not guaranteed — never rely on it
  • For pagination use LIMIT 10 OFFSET 20 (SQL Server: OFFSET 20 ROWS FETCH NEXT 10 ROWS ONLY)

SELECT chooses and computes columns, with AS aliases and decimal arithmetic (100.0) to avoid integer division; naming columns is preferred to SELECT *. WHERE filters rows using comparison operators, AND/OR/NOT with brackets, IN, inclusive BETWEEN, LIKE with % and _, and IS NULL — because comparisons with NULL are unknown, = NULL never matches. ORDER BY sorts on one or more columns (row order is otherwise undefined), DISTINCT removes duplicate result rows, and LIMIT/OFFSET (TOP or OFFSET-FETCH in SQL Server) restricts and pages results.
2.3

Aggregates, GROUP BY & HAVING

Data science starts with summaries: total revenue, average order value, customers per region. Aggregate functions collapse many rows into one number; GROUP BY does it per group; HAVING filters the groups. These three together answer the majority of business questions.

Aggregate Functions

QuerySQL
SELECT COUNT(*)                         AS line_count,
       SUM(qty)                         AS units,
       SUM(qty * unit_price)            AS revenue,
       ROUND(AVG(qty * unit_price), 2)  AS avg_line_value,
       MIN(unit_price)                  AS cheapest,
       MAX(unit_price)                  AS dearest
FROM order_items;
line_count | units | revenue | avg_line_value | cheapest | dearest -----------+-------+---------+----------------+----------+-------- 26 | 45 | 61305 | 2357.88 | 249 | 4999 (1 row)

COUNT(*) vs COUNT(column) vs COUNT(DISTINCT)

QuerySQL
SELECT COUNT(*)               AS customers,          -- all rows
       COUNT(email)           AS with_email,         -- non-NULL values only
       COUNT(DISTINCT region) AS regions,            -- unique non-NULL values
       COUNT(DISTINCT city)   AS cities
FROM customers;
customers | with_email | regions | cities ----------+------------+---------+------- 10 | 8 | 4 | 9 (1 row)

All aggregates except COUNT(*) ignore NULLs. AVG(discount) averages only the rows that have a discount — usually what you want, but be aware.

Query — revenue by category and monthSQL
SELECT p.category,
       strftime('%Y-%m', o.order_date) AS month,           -- PostgreSQL: TO_CHAR(order_date, 'YYYY-MM')
       SUM(oi.qty * oi.unit_price)     AS revenue
FROM order_items oi
JOIN products p ON p.product_id = oi.product_id
JOIN orders   o ON o.order_id   = oi.order_id
WHERE o.status <> 'Cancelled'
GROUP BY p.category, month
ORDER BY p.category, month;
category | month | revenue ---------+---------+-------- Decor | 2026-02 | 6396 Decor | 2026-03 | 4796 Dining | 2026-01 | 1494 Dining | 2026-02 | 11492 Dining | 2026-03 | 12239 Kitchen | 2026-01 | 3498 Kitchen | 2026-02 | 4798 Kitchen | 2026-03 | 13093 (8 rows)

This query previews JOIN (next lesson) to reach the category and date.

The rule: every column in SELECT must either be in GROUP BY or inside an aggregate. PostgreSQL and SQL Server reject queries that break it; SQLite and older MySQL silently return a value from an arbitrary row — a source of wrong answers.

HAVING: Filter the Groups

Query — customers with 3+ ordersSQL
SELECT customer_id, COUNT(*) AS orders
FROM orders
WHERE status <> 'Cancelled'          -- filters ROWS, before grouping
GROUP BY customer_id
HAVING COUNT(*) >= 3                 -- filters GROUPS, after aggregation
ORDER BY orders DESC;
customer_id | orders ------------+------- 1 | 4 5 | 3 (2 rows)

WHERE

Runs before grouping, on individual rows. Can't use aggregates. Use it to drop rows early (faster).

HAVING

Runs after grouping, on group results. Use it for conditions on aggregates (SUM(...) > 10000).

Aggregate functions — COUNT, SUM, AVG, MIN, MAX — summarise rows and ignore NULLs, except COUNT(*), which counts all rows; COUNT(column) counts non-null values and COUNT(DISTINCT column) unique values. GROUP BY produces one row per group, and every selected column must be grouped or aggregated. WHERE filters rows before grouping and cannot use aggregates; HAVING filters groups after aggregation. Grouping by derived values such as a month bucket is the basis of time-series summaries.

Joins

Good databases split data into separate tables so each fact is stored once. To answer real questions — "revenue by customer city" — you join them back together on their keys. This lesson covers every join type with diagrams, how to choose between them, and the classic traps: lost rows, duplicated rows and NULLs.

Joining Several Tables

Query — revenue and margin by customer regionSQL
SELECT c.region,
       COUNT(DISTINCT o.order_id)                   AS orders,
       SUM(oi.qty * oi.unit_price)                  AS revenue,
       SUM(oi.qty * (oi.unit_price - p.unit_cost))  AS margin
FROM orders o
JOIN customers   c  ON c.customer_id = o.customer_id
JOIN order_items oi ON oi.order_id   = o.order_id
JOIN products    p  ON p.product_id  = oi.product_id
WHERE o.status IN ('Delivered', 'Shipped')
GROUP BY c.region
ORDER BY revenue DESC;
region | orders | revenue | margin -------+--------+---------+------- South | 7 | 26586 | 9766 West | 5 | 15781 | 6391 North | 3 | 10141 | 4131 East | 1 | 1799 | 799 (4 rows)
Join fan-out: joining orders to order_items gives one row per item. Counting orders after that needs COUNT(DISTINCT o.order_id), and summing an order-level value (like a delivery fee) would count it once per item. Always ask: "what does one row represent after this join?"

Query — every category × every channel, including zero salesSQL
SELECT cat.category, ch.channel,
       SUM(CASE WHEN o.order_id IS NOT NULL THEN oi.qty * oi.unit_price ELSE 0 END) AS revenue
FROM (SELECT DISTINCT category FROM products) cat
CROSS JOIN (SELECT DISTINCT channel FROM orders) ch
LEFT JOIN products p     ON p.category = cat.category
LEFT JOIN order_items oi ON oi.product_id = p.product_id
LEFT JOIN orders o       ON o.order_id = oi.order_id AND o.channel = ch.channel
                        AND o.status <> 'Cancelled'
GROUP BY cat.category, ch.channel
ORDER BY cat.category, ch.channel;
category | channel | revenue ---------+---------+-------- Decor | Online | 11192 Decor | Store | 0 Dining | Online | 8734 Dining | Store | 16491 Kitchen | Online | 9994 Kitchen | Store | 11395 (6 rows)

The CROSS JOIN builds the full grid first, so combinations with no sales still appear with 0. The CASE inside SUM counts a line only when its order matched the channel (CASE is covered in Lesson 2.8).

Joins combine tables on key columns: INNER JOIN keeps matching rows only; LEFT JOIN keeps all left rows with NULLs where nothing matches (and with WHERE right.key IS NULL becomes an anti-join); FULL OUTER JOIN keeps all rows from both; CROSS JOIN produces every combination; and a self join relates rows of the same table, such as employees to managers. Conditions on the right table of a LEFT JOIN belong in ON, since WHERE turns it into an inner join. Joining to child tables fans rows out, so counts need DISTINCT and order-level values must not be summed per line — always know what one row represents.
2.5

Subqueries & CTEs

Many questions need a step-by-step answer: "first work out each customer's total, then find those above the average". A subquery is a query inside another query; a CTE (Common Table Expression, the WITH clause) gives each step a name so complex logic reads top to bottom. Recursive CTEs even walk hierarchies like org charts.

Subqueries in Three Places

1 · In WHERE — products priced above the averageSQL
SELECT name, unit_price
FROM products
WHERE unit_price > (SELECT AVG(unit_price) FROM products)      -- scalar subquery: one value
ORDER BY unit_price DESC;
name | unit_price -----------+----------- Dinner Set | 4999 Blender | 3499 Toaster | 2199 (3 rows)
2 · With IN / EXISTS — customers who bought a BlenderSQL
SELECT name FROM customers c
WHERE EXISTS (
    SELECT 1
    FROM orders o
    JOIN order_items oi ON oi.order_id = o.order_id
    JOIN products p     ON p.product_id = oi.product_id
    WHERE o.customer_id = c.customer_id          -- correlated: refers to the outer row
      AND p.name = 'Blender'
);
name ----------- Anita Rao Meera Iyer Arjun Singh (3 rows)
3 · In FROM — a derived tableSQL
SELECT segment, ROUND(AVG(order_value), 0) AS avg_order_value
FROM (
    SELECT o.order_id, c.segment, SUM(oi.qty * oi.unit_price) AS order_value
    FROM orders o
    JOIN customers c    ON c.customer_id = o.customer_id
    JOIN order_items oi ON oi.order_id = o.order_id
    WHERE o.status <> 'Cancelled'
    GROUP BY o.order_id, c.segment
) AS per_order
GROUP BY segment;
segment | avg_order_value ----------+---------------- Corporate | 4388.00 Retail | 2989.00 (2 rows)
NOT IN (subquery) returns nothing if the subquery contains a single NULL (because "x not equal to unknown" is unknown). Prefer NOT EXISTS or a LEFT JOIN anti-join for "not in" logic.

CTEs: Name Each Step

The derived-table query above is easier to read as a CTE — the steps appear in the order you think about them:

Query — customers whose spend is above the average customer'sSQL
WITH order_values AS (                     -- step 1: value of each order
    SELECT o.order_id, o.customer_id, SUM(oi.qty * oi.unit_price) AS order_value
    FROM orders o

A subquery is a query nested in WHERE (scalar comparisons, IN, EXISTS, often correlated with the outer row), in FROM as a derived table, or in SELECT. Recursive CTEs combine an anchor and a recursive member with UNION ALL to traverse hierarchies or generate series such as calendars.

Stored Procedures

SQLite doesn't have stored procedures (applications call it directly), so here are the two most common dialects. A procedure bundles steps with parameters and runs inside the database server:

PostgreSQL
CREATE OR REPLACE PROCEDURE apply_price_rise(
    p_category TEXT, p_pct NUMERIC)
LANGUAGE plpgsql
AS $$
BEGIN
    IF p_pct <= 0 OR p_pct > 0.5 THEN
        RAISE EXCEPTION 'pct must be between 0 and 0.5';
    END IF;

    UPDATE products
    SET unit_price = ROUND(unit_price * (1 + p_pct))
    WHERE category = p_category;

    INSERT INTO price_log(category, pct, changed_at)
    VALUES (p_category, p_pct, now());
END;
$$;

CALL apply_price_rise('Decor', 0.10);
SQL Server (T-SQL)
CREATE OR ALTER PROCEDURE dbo.apply_price_rise
    @category VARCHAR(50),
    @pct      DECIMAL(5,2)
AS
BEGIN
    SET NOCOUNT ON;
    IF @pct <= 0 OR @pct > 0.5
        THROW 50001, 'pct must be between 0 and 0.5', 1;

    BEGIN TRANSACTION;
        UPDATE dbo.products
        SET unit_price = ROUND(unit_price * (1 + @pct), 0)
        WHERE category = @category;

        INSERT INTO dbo.price_log(category, pct, changed_at)
        VALUES (@category, @pct, SYSUTCDATETIME());
    COMMIT;
END;

EXEC dbo.apply_price_rise @category = 'Decor', @pct = 0.10;

Indexes & Query Optimization

On 20 rows every query is instant. On 200 million, the same query can take a second or an hour depending on how it's written and whether the database can use an index. This lesson explains what an index is, how to read a query plan, and the habits that keep queries fast.

What an Index Is

Without an index: full scan

To find customer 48,213's orders, the database reads every row of orders and checks each one.

With an index on customer_id

Like a book's index: a sorted lookup structure (a B-tree) points straight to the matching rows.

See It in a Query Plan

We'll build a 200,000-row events table using a recursive CTE, then ask the database how it plans to run a query:

SetupSQL
CREATE TABLE events AS
WITH RECURSIVE n(i) AS (SELECT 1 UNION ALL SELECT i + 1 FROM n WHERE i < 200000)
SELECT i                                  AS event_id,
       (i * 7919) % 5000 + 1               AS customer_id,
       DATE('2025-01-01', '+' || (i % 450) || ' days') AS event_date,
       CASE i % 4 WHEN 0 THEN 'view' WHEN 1 THEN 'cart' WHEN 2 THEN 'view' ELSE 'purchase' END AS event_type
FROM n;

SELECT COUNT(*) AS rows FROM events;
rows ------ 200000 (1 row)

Create an index, plan againSQL
CREATE INDEX ix_events_customer ON events(customer_id);

SCAN = read the whole table; SEARCH … USING INDEX = jump to matching rows. Other databases show the same idea: PostgreSQL EXPLAIN ANALYZE (Seq Scan vs Index Scan), SQL Server "Include Actual Execution Plan" (Table/Clustered Index Scan vs Index Seek).

When an Index Can't Help

Function on the column — every entry scannedSQL
CREATE INDEX ix_events_date ON events(event_date);

EXPLAIN QUERY PLAN
SELECT COUNT(*) FROM events WHERE strftime('%Y-%m', event_date) = '2025-06';
id | parent | notused | detail ---+--------+---------+------------------------------------------------ 3 | 0 | 211 | SCAN events USING COVERING INDEX ix_events_date (1 row)
Same question as a range — index usedSQL
EXPLAIN QUERY PLAN
SELECT COUNT(*) FROM events WHERE event_date >= '2025-06-01' AND event_date < '2025-07-01';
id | parent | notused | detail ---+--------+---------+---------------------------------------------------------------------------------- 3 | 0 | 151 | SEARCH events USING COVERING INDEX ix_events_date (event_date>? AND event_date<?) (1 row)

With the function, SQLite must SCAN all 200,000 index entries and compute strftime for each; with the range it can SEARCH straight to June. Wrapping an indexed column in a function hides its order from the index — rewrite conditions so the bare column is compared to values (a sargable condition).

Choosing Indexes

Primary key (automatic)Lookups by ID

Indexes aren't free: each one slows down INSERT/UPDATE/DELETE and uses storage. Index for the queries you actually run. Columns with very few distinct values (like a yes/no flag) rarely benefit. Analytical warehouses (Fabric, Snowflake, BigQuery) use columnar storage and partitioning/clustering instead of traditional indexes.

Query Optimization Checklist

  • Select only the columns you need; avoid SELECT *
  • Filter early with sargable WHERE conditions; filter before joining where possible
  • Join on indexed key columns with matching data types
  • Prefer EXISTS to IN with large subqueries; UNION ALL to UNION when duplicates are impossible (UNION sorts to remove them)
  • Watch for join fan-out and DISTINCT used to "fix" duplicates
  • Aggregate in the database, not in Python, and LIMIT exploratory queries
  • Read the plan (EXPLAIN) before guessing
An index is a sorted structure, usually a B-tree, that lets the database find rows without scanning the whole table; query plans from EXPLAIN (EXPLAIN QUERY PLAN in SQLite, EXPLAIN ANALYZE in PostgreSQL, execution plans in SQL Server) show scans versus index searches. Indexes help on primary keys, join keys and frequent filter or sort columns; composite indexes follow leftmost-column order and covering indexes include all selected columns. Functions on indexed columns make conditions non-sargable. Indexes slow writes and use storage, and columnar warehouses rely on partitioning and clustering instead. Optimisation means selecting fewer columns, filtering early, joining on keys, avoiding fan-out and reading the plan.

7 · Cohort Retention

Group customers by the month of their first order (their cohort) and count how many ordered again in later months:

QuerySQL
WITH firsts AS (
    SELECT customer_id, MIN(strftime('%Y-%m', order_date)) AS cohort
    FROM order_totals GROUP BY customer_id
),
activity AS (
    SELECT DISTINCT t.customer_id, f.cohort, strftime('%Y-%m', t.order_date) AS month
    FROM order_totals t JOIN firsts f ON f.customer_id = t.customer_id
)
SELECT cohort,
       COUNT(DISTINCT customer_id)                                              AS customers,
       COUNT(DISTINCT CASE WHEN month > cohort THEN customer_id END)            AS came_back,
       ROUND(100.0 * COUNT(DISTINCT CASE WHEN month > cohort THEN customer_id END)
             / COUNT(DISTINCT customer_id), 0)                                  AS retention_pct
FROM activity
GROUP BY cohort
ORDER BY cohort;
cohort | customers | came_back | retention_pct --------+-----------+-----------+-------------- 2026-01 | 2 | 2 | 100.00 2026-02 | 4 | 3 | 75.00 2026-03 | 3 | 0 | 0.00 (3 rows)
Common analytics SQL patterns include N-th highest per group with DENSE_RANK; period-over-period growth with LAG over monthly aggregates; "bought both A and B" with GROUP BY and HAVING COUNT(DISTINCT) equal to the number of required values; gaps and islands, where date minus ROW_NUMBER is constant within a consecutive streak; median via ROW_NUMBER and COUNT (or PERCENTILE_CONT); funnels via per-session conditional aggregation; and cohort retention by assigning each customer's first-activity month and counting later activity.

1 · Monthly KPIs

QuerySQL
WITH order_level AS (
    SELECT o.order_id, o.customer_id, o.status,
           strftime('%Y-%m', o.order_date)           AS month,
           SUM(oi.qty * oi.unit_price)               AS revenue,
           SUM(oi.qty * (oi.unit_price - p.unit_cost)) AS margin
    FROM orders o
    JOIN order_items oi ON oi.order_id = o.order_id
    JOIN products p     ON p.product_id = oi.product_id
    GROUP BY o.order_id, o.customer_id, o.status, month
)
SELECT month,
       SUM(status IN ('Delivered', 'Shipped'))                                          AS orders,
       COUNT(DISTINCT CASE WHEN status IN ('Delivered', 'Shipped') THEN customer_id END) AS customers,
       SUM(CASE WHEN status IN ('Delivered', 'Shipped') THEN revenue ELSE 0 END)         AS revenue,
       ROUND(AVG(CASE WHEN status IN ('Delivered', 'Shipped') THEN revenue END), 0)      AS avg_order_value,
       ROUND(100.0 * SUM(CASE WHEN status IN ('Delivered', 'Shipped') THEN margin ELSE 0 END)
             / SUM(CASE WHEN status IN ('Delivered', 'Shipped') THEN revenue ELSE 0 END), 1) AS margin_pct,
       ROUND(100.0 * AVG(status IN ('Cancelled', 'Returned')), 1)                        AS lost_order_pct
FROM order_level
GROUP BY month
ORDER BY month;

2 · RFM Segmentation

RFM scores each customer on how Recently they bought, how Frequently, and how much Money they spent. We measure recency against an "as of" date of 2026-03-31:

QuerySQL
WITH rfm AS (
    SELECT customer_id,
           CAST(JULIANDAY('2026-03-31') - JULIANDAY(MAX(order_date)) AS INTEGER) AS recency_days,
           COUNT(*)                                                            AS frequency,
           SUM(order_value)                                                    AS monetary
    FROM order_totals
    WHERE order_id NOT IN (SELECT order_id FROM orders WHERE status = 'Returned')
    GROUP BY customer_id
),
scored AS (
    SELECT *,
           NTILE(3) OVER (ORDER BY recency_days DESC) AS r,     -- 3 = most recent
           NTILE(3) OVER (ORDER BY frequency)         AS f,     -- 3 = most frequent
           NTILE(3) OVER (ORDER BY monetary)          AS m      -- 3 = highest spend
    FROM rfm
)
SELECT c.name, s.recency_days, s.frequency, s.monetary, s.r || s.f || s.m AS rfm,
       CASE
           WHEN s.r = 3 AND s.f + s.m >= 5 THEN 'Champion'
           WHEN s.f + s.m >= 5             THEN 'Loyal - re-engage'
           WHEN s.r = 3                    THEN 'New / promising'
           WHEN s.r = 1                    THEN 'At risk'
           ELSE 'Needs attention'
       END AS segment
FROM scored s JOIN customers c ON c.customer_id = s.customer_id
ORDER BY s.r + s.f + s.m DESC, s.monetary DESC;

3 · Products Bought Together

QuerySQL
SELECT pa.name AS product_a, pb.name AS product_b, COUNT(*) AS orders_together
FROM order_items a
JOIN order_items b ON b.order_id = a.order_id AND b.product_id > a.product_id   -- each pair once
JOIN products pa   ON pa.product_id = a.product_id
JOIN products pb   ON pb.product_id = b.product_id
GROUP BY pa.name, pb.name
ORDER BY orders_together DESC, product_a;

The condition b.product_id > a.product_id prevents pairing a product with itself and counting (Mug, Kettle) and (Kettle, Mug) separately. On real data this is the starting point for "frequently bought together" recommendations.

4 · Customer Feature Table for Machine Learning

QuerySQL
CREATE TABLE customer_features AS
WITH lines AS (
    SELECT customer_id, order_id, order_date, status, channel, category, revenue
    FROM sales_lines
)
SELECT c.customer_id,
       c.segment,
       c.region,
       CAST(JULIANDAY('2026-03-31') - JULIANDAY(c.signup_date) AS INTEGER)            AS tenure_days,
       COUNT(DISTINCT l.order_id)                                                     AS orders,
       COALESCE(SUM(CASE WHEN l.status IN ('Delivered','Shipped') THEN l.revenue END), 0) AS revenue,
       COALESCE(ROUND(1.0 * COUNT(DISTINCT CASE WHEN l.channel = 'Online' THEN l.order_id END)
                / NULLIF(COUNT(DISTINCT l.order_id), 0), 2), 0)                         AS online_share,
       COUNT(DISTINCT l.category)                                                     AS categories_bought,
       COALESCE(MAX(l.status IN ('Cancelled', 'Returned')), 0)                        AS ever_cancel_or_return,
       CASE WHEN MAX(l.order_date) >= '2026-03-01' THEN 1 ELSE 0 END                  AS active_in_march
FROM customers c
LEFT JOIN lines l ON l.customer_id = c.customer_id
GROUP BY c.customer_id, c.segment, c.region, c.signup_date;
