12.1Ingestion Fundamentals

12.1.1What Is Data Ingestion?

Data ingestion moves data from a source system into a target platform so it can be stored, processed, analyzed, or reported.

Common sources

  • CSV, JSON, Parquet, and Avro files.
  • SQL Server, Oracle, Azure SQL Database.
  • REST APIs and event streams.
  • Enterprise applications.
  • Cloud object storage.

Common targets

  • Bronze Delta tables.
  • Streaming tables.
  • Lakehouse tables governed by Unity Catalog.
  • Curated datasets for downstream transformations.

The ingestion layer's job

Move data reliably, and record enough to know what was received, when, and whether processing completed.

12.1.2ETL Versus ELT

ETL: Extract, Transform, Load

Source → Extract → Transform → Load

  1. Extract customers from SQL Server.
  2. Remove duplicates.
  3. Standardize city names.
  4. Load the cleansed data into the target.

ELT: Extract, Load, Transform

Source → Extract → Load → Transform

  1. Read a customer CSV.
  2. Store it in a Bronze Delta table.
  3. Clean and validate in Silver.
  4. Build dimensions and facts in Gold.
FeatureETLELT
Transformation timingBefore loading the final targetAfter loading into the target
Raw data preservationDepends on designCommonly preserved in Bronze
Processing locationOften an external engineCommonly the target platform
ReprocessingMay need re-extraction if raw data wasn't keptOften possible from persisted raw data
Typical Databricks patternExternal processing, then loadBronze → Silver → Gold

ELT is common in lakehouses because it preserves source data and uses the platform's engine for transformation. ETL and ELT are patterns, not products, and one pipeline can combine both.

12.1.3Batch Ingestion

Batch ingestion processes a group of records at a time: a CSV every morning, an hourly database extract, an end-of-day order file, yesterday's transactions.

Python
source_path = (
    "/Volumes/retail_dev/landing/orders/"
    "orders_20261025.csv"
)

orders_df = (
    spark.read
    .option("header", True)
    .csv(source_path)
)

display(orders_df)

Advantages

  • Simple operational model.
  • Easy to reconcile with row counts.
  • Convenient for historical backfills.
  • Often economical.

Limitations

  • Data unavailable until the next batch.
  • Large batches create processing spikes.
  • Retry and duplicate handling must be designed carefully.

12.1.4Incremental Ingestion

Incremental ingestion processes only new or changed data. If a source table has 10 million rows and 20,000 changed since the last load, a full load extracts all 10 million; an incremental load extracts the 20,000, provided the source can identify those changes reliably.

Techniques: watermark columns, Change Tracking, CDC, transaction logs, file-arrival tracking, Auto Loader checkpoints, connector-managed sync.

SQL Server · illustrative
SELECT
    CustomerID,
    CustomerName,
    City,
    LastModifiedDate
FROM dbo.Customers
WHERE LastModifiedDate > @LastSuccessfulWatermark;
Use an overlap window

Rather than a bare > on the last watermark (say 2026-10-24 23:00:00), deliberately reread a short preceding period, then deduplicate or MERGE into the target. That guards against delayed updates and timestamp-boundary problems.

Timestamp extraction can miss changes when
  • The source doesn't update the timestamp reliably.
  • Records share a timestamp and the boundary is handled wrongly.
  • A transaction commits late with an older timestamp.
  • Rows are physically deleted, leaving nothing to find.

When inserts, updates, and deletes must be captured reliably, use CDC or change tracking.

streaming_df = (
    spark.readStream
    .format("rate")
    .option("rowsPerSecond", 10)

query = (
    streaming_df.writeStream
    .format("delta")
    .option("checkpointLocation",
            "/Volumes/retail_dev/checkpoints/rate_demo")

    .toTable("retail_dev.bronze.streaming_demo")
)
About this demo

The rate source generates synthetic rows and doesn't connect to a real broker. I added .trigger(availableNow=True) so it processes what's available and stops, because serverless compute only supports this kind of trigger. On classic compute without a trigger, the stream runs until you call query.stop(). (Verified on Spark 4: the availableNow run processed 150 rows and stopped.)

Structured Streaming gives fault-tolerant semantics when source, checkpoint, and sink are configured correctly. Don't assume every external side effect is automatically exactly-once.

Python · full load
(
    source_df.write
    .format("delta")
    .mode("overwrite")
    .saveAsTable("retail_dev.bronze.customers_snapshot")

# Only if source_df is the complete,

SQL · delta load
MERGE INTO retail_dev.silver.customers AS target
USING retail_dev.silver.customers_staging AS source
ON target.CustomerID = source.CustomerID

WHEN MATCHED THEN UPDATE SET
    target.CustomerName = source.CustomerName,
    target.City = source.City

WHEN NOT MATCHED THEN INSERT (
    CustomerID, CustomerName, City
)
VALUES (
    source.CustomerID, source.CustomerName, source.City
);

The merge handles inserts and updates but not deletes, since no deletion rule is defined. Make sure the source has at most one row per key first.

12.2File-Based Ingestion

12.2.1Uploading Files to Databricks

Files go into a storage location Databricks can read: Unity Catalog volumes, ADLS Gen2, Azure Blob Storage, Amazon S3, or Google Cloud Storage. For learning, volumes are the easiest, e.g. /Volumes/retail_dev/landing/retail/customers.csv. The volume must exist and you need privileges on it.

In production, prefer governed cloud storage and service identities over manual uploads through the UI.

Schema inference versus explicit schema

Python
# Inferred: Spark guesses types from the data
inferred_df = (
    spark.read
    .option("header", True)
    .option("inferSchema", True)
    .csv(source_path)
)

# Explicit: you define the expected columns and types
from pyspark.sql.types import StructType, StructField, StringType

customer_schema = StructType([
    StructField("CustomerID", StringType(), True),
    StructField("CustomerName", StringType(), True),
    StructField("Email", StringType(), True),
    StructField("City", StringType(), True)
])

customers_df = (
    spark.read
    .schema(customer_schema)
    .option("header", True)
    .csv(source_path)
)

Explicit schemas improve predictability but don't guarantee business validity. Define schemas intentionally and validate unexpected columns and values.

12.2.3COPY INTO

COPY INTO is a SQL command that loads files from a storage location into a Delta table and remembers which files it has already loaded, so rerunning it skips them.

SQL
-- Use a NEW table, not Chapter 11's customers_raw.
-- A schemaless placeholder lets mergeSchema define the columns.
CREATE TABLE IF NOT EXISTS retail_dev.bronze.customers_copy_raw;

COPY INTO retail_dev.bronze.customers_copy_raw
FROM (
    SELECT
        *,
        _metadata.file_path  AS _source_file,
        current_timestamp()  AS _ingested_at
    FROM '/Volumes/retail_dev/landing/retail/customers/'
)
FILEFORMAT = CSV
FORMAT_OPTIONS ('header' = 'true')
COPY_OPTIONS ('mergeSchema' = 'true');

The SELECT form adds ingestion metadata during the load. Run it twice: the second run reports 0 rows inserted, because the files are already tracked.

Important considerations

  • File tracking is tied to the target table and command.
  • Changing targets may need a deliberate replay strategy.
  • Moving files, editing them in place, or changing settings may not behave as you expect.
  • 'force' = 'true' in COPY_OPTIONS reloads files regardless; use it only for a planned replay.
  • File tracking doesn't replace batch audit and reconciliation.

Use COPY INTO when

  • Files arrive in a cloud storage location.
  • The pattern is straightforward.
  • SQL-based ingestion is enough.
  • File tracking is useful.
  • You don't need a customized streaming pipeline.

12.2.4Auto Loader

Auto Loader incrementally ingests new files from cloud storage as they arrive, continuously or on a schedule. It uses the cloudFiles streaming source.

Python
from pyspark.sql import functions as F

source_path     = "/Volumes/retail_dev/landing/retail/customers/"
checkpoint_path = "/Volumes/retail_dev/checkpoints/customers/"
schema_path     = "/Volumes/retail_dev/schemas/customers/"

customer_stream = (
    spark.readStream
    .format("cloudFiles")
    .option("cloudFiles.format", "csv")
    .option("cloudFiles.schemaLocation", schema_path)
    .option("header", True)
    .load(source_path)
)

bronze_stream = (
    customer_stream
    .withColumn("_source_file", F.col("_metadata.file_path"))
    .withColumn("_ingested_at", F.current_timestamp())
)

query = (
    bronze_stream.writeStream
    .format("delta")
    .option("checkpointLocation", checkpoint_path)
    .option("mergeSchema", "true")
    .trigger(availableNow=True)
    .toTable("retail_dev.bronze.customers_autoloader_raw")
)
Changes from older examples

F.input_file_name() is replaced by _metadata.file_path (unsupported on serverless and shared compute, as in Chapters 8 and 11), and availableNow makes it run as a scheduled batch that stops when done.

Why Auto Loader?

  • Incremental file discovery.
  • Persistent state tracking discovered and processed files.
  • Scales to millions of files.
  • Schema inference and evolution.
  • Integrates with Structured Streaming and Delta Lake.
Protect the state folders

The checkpoint and schema locations are Auto Loader's memory. Delete them and files get rediscovered and reloaded, or schema behavior changes.

COPY INTOAuto Loader
InterfaceSQL commandPython/SQL streaming source

12.2.5File Discovery

Given customers_20261023.csv, …24.csv, …25.csv, the next run should pick up only files not yet successfully processed. Approaches: COPY INTO tracking, Auto Loader's checkpoint state, explicit manifests, storage event notifications (where configured), or comparing a listing against a custom ledger.

Avoid repeatedly scanning a very large directory without considering listing cost and scalability.

12.2.6Schema Inference

Python
df = (
    spark.read
    .option("header", True)
    .option("inferSchema", True)
    .csv(source_path)
)

df.printSchema()
Possible output
root
 |-- CustomerID: string
 |-- CustomerName: string
 |-- Age: integer
 |-- CreditLimit: double

Inference is handy for exploration but risky in production: a column of integer-looking values today may hold decimals tomorrow. Note how CreditLimit became double, an imprecise type for money.

Best practice

Use explicit or controlled schemas for production contracts, especially for financial values, identifiers, and timestamps.

12.2.7Schema Evolution

Before → after
CustomerID,CustomerName,City
C001,Ravi,Hyderabad

CustomerID,CustomerName,City,Country
C002,Priya,Chennai,India

Possible policies

  1. Reject the file until the change is approved.
  2. Add the column; older rows get nulls.
  3. Capture unexpected columns in a raw/rescued column.
  4. Route the file to schema-change review.

Auto Loader controls this with cloudFiles.schemaEvolutionMode:

ModeWhen a new column appears
addNewColumns (default without a schema)The stream stops with an error, records the new column, and includes it when restarted
rescueSchema stays fixed; unexpected data goes into the _rescued_data column
failOnNewColumnsThe stream fails until you update the schema or remove the file
none (default with a provided schema)New columns are ignored

Exact behavior depends on runtime and format. Schema evolution isn't business validation: a new Country column can be structurally fine and still need quality checks.

12.2.8Tracking Processed Files

The failure scenario

  1. customers_20261025.csv arrives.
  2. The job reads it.
  3. The data is written to Bronze.
  4. The job fails before recording success.
  5. The next run tries the file again → duplicates, unless tracking is reliable.
Source fileBatchStatusRows
customers_20261024.csvB001SUCCESS1,000
customers_20261025.csvB002SUCCESS1,250
customers_20261026.csvB003FAILED0

Solutions: Auto Loader checkpoints, COPY INTO tracking, a custom ingestion ledger, or a file manifest with processing status.

Ledger columns
source_file           batch_id            start_time
source_file_id        pipeline_run_id     end_time
source_path           processing_status   source_row_count
source_modified_time                      target_row_count
file_size                                 error_message

A ledger should distinguish discovered, started, committed, and task succeeded, and retries after partial failure must not duplicate committed data.

12.2.9Handling New Files

Day 1, 2, 3 files should each be added to Bronze exactly once. Auto Loader: keep a persistent checkpoint and stable schema location. COPY INTO: keep a consistent configuration. Custom framework: a manifest with a defined recovery policy.

File name isn't always identity

If a corrected file is resent under the same name, decide whether it's a new version, a replacement, a duplicate to ignore, or a correction that needs targeted reprocessing. (By default Auto Loader won't reload a file it has seen; cloudFiles.allowOverwrites changes that.)

12.3Database Ingestion

Two broad approaches: JDBC extraction and managed connectors (12.4). JDBC is general connectivity. It isn't CDC and doesn't give efficient incremental extraction by itself.

12.3.1SQL Server to Databricks

Python
jdbc_url = (
    "jdbc:sqlserver://sqlserver-host.example.com:1433;"
    "databaseName=RetailSourceDB;"
    "encrypt=true;"
    "trustServerCertificate=false;"
)

connection_properties = {
    "user": dbutils.secrets.get(scope="retail-secrets", key="sqlserver-user"),
    "password": dbutils.secrets.get(scope="retail-secrets", key="sqlserver-password"),
    "driver": "com.microsoft.sqlserver.jdbc.SQLServerDriver"
}

customers_df = spark.read.jdbc(
    url=jdbc_url,
    table="dbo.Customers",
    properties=connection_properties
)

Prerequisites

  • Replace host, database, secret scope, and table.
  • A JDBC driver on the compute (Databricks Runtime includes the SQL Server driver).
  • Network path and firewall rules from Databricks to the database.
  • TLS settings and source permissions.
Secrets

dbutils.secrets.get reads credentials from a secret scope, and Databricks redacts them in notebook output. Prefer identity-based authentication where available. Unity Catalog connections (Lakehouse Federation) are another governed option for querying these databases.

12.3.5JDBC Parallel Extraction

A single JDBC connection can be slow for big tables. Spark reads in parallel when given a partition column and bounds:

Python
large_table_df = spark.read.jdbc(
    url=jdbc_url,
    table="dbo.LargeTransactions",
    column="TransactionID",
    lowerBound=1,
    upperBound=10000000,
    numPartitions=8,
    properties=connection_properties
)
Bounds don't filter

lowerBound/upperBound only set the partition stride. Rows outside the range still get read (by the first and last partitions). Also, numPartitions=8 means 8 concurrent connections to the source, so agree on that with the database owner.

For a strict extraction window, filter in the source query:

Python
source_query = """
(
    SELECT TransactionID, CustomerID, Amount, LastModifiedDate
    FROM dbo.LargeTransactions
    WHERE LastModifiedDate >= '2026-10-01'
      AND LastModifiedDate <  '2026-10-26'
) AS source_data
"""

incremental_df = spark.read.jdbc(
    url=jdbc_url,
    table=source_query,
    properties=connection_properties
)

A subquery passed as table needs an alias (AS source_data). Parameterize the dates in production.

12.3.6Incremental Database Extraction

SQL
SELECT OrderID, CustomerID, OrderDate, LastModifiedDate
FROM dbo.Orders
WHERE LastModifiedDate >= @StartTime
  AND LastModifiedDate <  @EndTime;

Watermark strategy

  1. Read the last successfully committed watermark.
  2. Define a bounded extraction window.
  3. Extract source records.
  4. Validate the batch.
  5. Write it to durable staging or Bronze.
  6. Apply idempotent target processing.
  7. Commit the new watermark only after all required stages succeed.

Source-side impact

  • Indexes on filter columns.
  • Query execution plans.
  • Transaction isolation.
  • Extraction concurrency.
  • Source workload and bandwidth.
  • Data volume.
  • Availability of reliable change tracking.

Don't run large repeated full scans on busy systems without the owner's agreement.

The watermark rule

Don't advance the watermark just because the source query finished. Advance it only at a clearly defined success boundary, or a failure can silently skip data.

12.3.7JDBC Limitations

JDBC alone doesn't give you a durable CDC stream, reliable delete capture, a managed ingestion control plane, schema governance, a recovery ledger, or exactly-once behavior across external systems. Those need extra design, or a managed connector.

Before choosing, verify

  7. Target and governance needs are supported.

  1. Configure the source connection.
  2. Grant the necessary source privileges.
  3. Configure networking and authentication.
  4. Select source tables or objects.
  5. Configure the destination and settings.
  6. Create the ingestion pipeline.
  7. Run the initial load.
  8. Monitor incremental updates.
  9. Review schema changes and quality results.
  10. Configure alerts and recovery procedures.

Captures the existing data, e.g. the 5 million customers present when ingestion starts.

Then: incremental sync

12.4.7Monitoring Connectors

Monitor at least

  • Execution status and source connectivity.
  • Initial-load and incremental progress.
  • Last successful update time.
  • Source and target record counts.
  • Schema-change events and rejected records.
  • Permission and network errors.
  • Lag between source change and target availability.

Use Lakeflow Connect when

  • Your source has a supported connector.
  • Managed ingestion reduces operational effort.
  • Incremental sync is required.
  • You want a managed ingestion lifecycle.
  • It meets security and networking needs.

Otherwise, use JDBC or a custom solution.

The snapshot gap

Changes made while the snapshot runs must not be lost or misapplied. Reliable CDC coordinates the snapshot with a log position or connector mechanism. Don't just run a full query and then start reading changes.

12.5.3Incremental Synchronization

Mechanisms include SQL Server CDC, SQL Server Change Tracking, Oracle log-based CDC or replication, connector-managed sync, and modification timestamps (with their limits). These aren't interchangeable.

SQL Server CDCSQL Server Change Tracking
Records the change operations and column values, per its configurationIdentifies which rows changed, not a full history of intermediate values

Choose based on required detail, retention, latency, and source configuration.

12.5.4Applying Inserts and Updates

Assuming the staging table holds the latest change per customer:

SQL
MERGE INTO retail_dev.silver.customers AS target
USING retail_dev.bronze.customer_changes_latest AS source
ON target.CustomerID = source.CustomerID

WHEN MATCHED AND source.operation = 'UPDATE'
THEN UPDATE SET
    target.CustomerName = source.CustomerName,
    target.City = source.City

WHEN NOT MATCHED AND source.operation = 'INSERT'
THEN INSERT (CustomerID, CustomerName, City)
VALUES (source.CustomerID, source.CustomerName, source.City);

A real CDC pipeline must also handle

  • Multiple changes to one key in a batch.
  • Change ordering and transaction boundaries.
  • Deletes.
  • Replayed and duplicate events.
  • Schema changes and late records.
  • Initial-snapshot consistency.

Reduce the changes to one per key by a defined ordering rule (e.g. a row_number() window, as in Chapter 11) before merging.

12.5.5Handling Deletes

Physically deleted rows leave nothing for a timestamp query to find; CDC or change tracking supplies delete information.

SQL
MERGE INTO retail_dev.silver.customers AS target
USING retail_dev.bronze.customer_changes_latest AS source
ON target.CustomerID = source.CustomerID

WHEN MATCHED AND source.operation = 'DELETE'
THEN DELETE

WHEN MATCHED AND source.operation = 'UPDATE'
THEN UPDATE SET
    target.CustomerName = source.CustomerName,
    target.City = source.City

WHEN NOT MATCHED AND source.operation = 'INSERT'
THEN INSERT (CustomerID, CustomerName, City)
VALUES (source.CustomerID, source.CustomerName, source.City);
One change per key

If a batch has both an update and a delete for one customer, determine the correct final state before merging.

Soft deletes

Some models shouldn't physically delete. Set a flag instead: WHEN MATCHED AND source.operation = 'DELETE' THEN UPDATE SET target.IsDeleted = true.

Chapter 13's AUTO CDC handles ordering, deletes, and SCD history declaratively.

12.5.6Late-Arriving Records

Examples

  • Yesterday's file arrives today.
  • A transaction commits after the window closes.
  • A CDC event is delayed.
  • A correction arrives for a closed month.

Strategies

  • Overlap windows for timestamp extraction.
  • Reconcile source and target watermarks.
  • Durable CDC offsets.
  • Process late files by source identity and version.
  • Reprocess affected partitions; recalculate Gold.

E.g. a daily pipeline processes yesterday but accepts corrections for the previous seven days. The right overlap depends on source behavior and business needs.

12.5.7Data Reconciliation

SQL
-- Row counts (compare with the source count for the same batch)
SELECT COUNT(*) AS BronzeRows
FROM retail_dev.bronze.orders_raw;

-- Business-key uniqueness
SELECT OrderID, COUNT(*) AS RecordCount
FROM retail_dev.silver.orders
GROUP BY OrderID
HAVING COUNT(*) > 1;

-- Amount totals (compare with the source over the same window)
SELECT SUM(Amount) AS TotalAmount
FROM retail_dev.silver.orders;

-- Missing records (source_snapshot_view = a placeholder source extract)
SELECT s.OrderID
FROM source_snapshot_view s
LEFT ANTI JOIN retail_dev.silver.orders t
    ON s.OrderID = t.OrderID;
A count match isn't enough

Two datasets can have equal row counts and different records. For financial data, also reconcile distinct keys, amount totals, min/max timestamps, insert/update/delete counts, and hashes or checksums where appropriate.

12.5.8Recovery After Ingestion Failures

If a file was written to Bronze but the job failed before updating status, the next run must work out whether the first write committed.

Recovery strategies

  • Reuse Auto Loader's existing checkpoint.
  • Rely on COPY INTO file tracking.
  • An ingestion ledger with idempotent writes.
  • Stable batch IDs.
  • Stage and validate before publishing.
  • Advance watermarks only at the success boundary.
  • Reconcile after recovery.
Don't reset state blindly

Never delete checkpoints, reset offsets, or change ingestion state during recovery without understanding the replay consequences. For CDC, recovery must keep the source change position aligned with the target's committed state.

12.6.4Step 3: Configure Auto Loader

Python
from pyspark.sql import functions as F

source_path = "/Volumes/retail_dev/bronze/landing/orders/"
schema_path = "/Volumes/retail_dev/bronze/ingestion_state/orders_schema/"
checkpoint_path = "/Volumes/retail_dev/bronze/ingestion_state/orders_checkpoint/"

orders_stream_df = (
    spark.readStream
    .format("cloudFiles")
    .option("cloudFiles.format", "csv")
    .option("cloudFiles.schemaLocation", schema_path)
    .option("cloudFiles.schemaEvolutionMode", "addNewColumns")
    .option("cloudFiles.schemaHints", "Amount DECIMAL(18,2)")
    .option("header", True)
    .load(source_path)
)
Why schema hints instead of .schema(...)

The original version passed an explicit .schema(initial_schema) together with addNewColumns. Auto Loader doesn't allow that combination: providing a full schema switches evolution off (mode none), and addNewColumns with a provided schema raises an error. Schema hints pin the types you care about (here Amount) while still letting Auto Loader discover new columns.

What Auto Loader infers

  • CSV columns are inferred as strings by default, which suits Bronze (Chapter 11 kept raw values as strings).
  • The hint makes Amount a DECIMAL(18,2).
  • A _rescued_data column is added automatically for values that don't fit the schema.
Strict-contract alternative

For tightly controlled sources, use "failOnNewColumns" (or "rescue") so unapproved columns stop the pipeline or land in _rescued_data until approved.

Step 4: Add metadata and write to Bronze

Python
orders_bronze_stream_df = (
    orders_stream_df
    .withColumn("_source_file", F.col("_metadata.file_path"))
    .withColumn("_ingested_at", F.current_timestamp())
    .withColumn("_source_system", F.lit("RETAIL_CSV"))
)

query = (
    orders_bronze_stream_df.writeStream
    .format("delta")
    .option("checkpointLocation", checkpoint_path)
    .option("mergeSchema", "true")
    .trigger(availableNow=True)
    .toTable("retail_dev.bronze.orders_raw")
)

query.awaitTermination()   # wait until all available files are processed

availableNow=True

Processes everything available, then stops. It isn't a permanently running stream, which makes it ideal for scheduled jobs. awaitTermination() keeps the cell running until it finishes, so later cells see the data.

Avoid duplicate ingestion

Reuse the same checkpoint path on every normal run. A new checkpoint path means a fresh memory, so every file gets reloaded. For a deliberate full replay, use a controlled backfill procedure, not casual deletion of state.

12.6.10Step 9: Add Data-Quality Checks

SQL
SELECT
    COUNT(*) AS TotalRows,
    SUM(CASE WHEN OrderID IS NULL OR TRIM(OrderID) = ''
             THEN 1 ELSE 0 END) AS MissingOrderIDs,
    SUM(CASE WHEN CustomerID IS NULL OR TRIM(CustomerID) = ''
             THEN 1 ELSE 0 END) AS MissingCustomerIDs,
    SUM(CASE WHEN _rescued_data IS NOT NULL
             THEN 1 ELSE 0 END) AS RowsWithRescuedData
FROM retail_dev.bronze.orders_raw;

I added the _rescued_data count: it catches values that didn't fit the schema (e.g. a non-numeric Amount). A production process also validates numeric and date conversion, key uniqueness, source/target counts, unexpected schema changes, file-level failures, and reconciliation with the source manifest. Bronze keeps the source values even when they fail validation.

Step 10: Schedule the pipeline

Job configuration

  • A schedule matching file-arrival frequency (or a file-arrival trigger).
  • The same checkpoint and schema locations every run.
  • Retries for transient failures, which also absorbs the schema-change restart.
  • Failure notifications.
  • Permissions for the job identity.
  • A documented schema-change and reprocessing procedure.

Record per run

  • Pipeline run ID.
  • Processing batch or execution date.
  • Files processed and records ingested (query.lastProgress gives numInputRows).
  • Schema changes observed.
  • Start and end times.
  • Final status and error details.

You'll build the job itself in Chapter 14.

Step 11: Recovery test

Stop the job mid-run (or introduce a controlled failure), then rerun with the same checkpoint path. Verify that:

  1. Previously committed data isn't duplicated.
  2. Pending files are eventually processed.
  3. The pipeline reports its final status accurately.
  4. Schema-change errors follow the documented procedure.
  5. Source and target counts reconcile.
Why this matters

A pipeline that works on the first run can still fail during retries or partial failures. Test recovery, not just success.

12.7Production Ingestion Design Checklist

Source connectivity

  • Is the source supported?
  • Network routes and firewall rules configured?
  • Authentication secure?
  • Privileges sufficient but limited?
  • Source protected from excessive load?

Ingestion strategy

  • Full, incremental, or streaming?
  • How are new records identified?
  • How are updates detected?
  • How are deletes captured?
  • Expected latency?
  • Late-arriving records?

Schema management

  • Explicit or inferred schema?
  • New column appears?
  • Column disappears?
  • Type changes?
  • Who approves breaking changes?

Reliability

  • How are processed files tracked?
  • Checkpoints stored durably?
  • Writes idempotent?
  • Partial failures recovered how?
  • Backfills performed how?
  • When is a watermark committed?

Data quality

  • Required fields validated?
  • Keys unique at the expected grain?
  • Source and target counts reconciled?
  • Invalid records retained or quarantined?
  • Quality thresholds documented?

Monitoring & governance

  • Failures alerted; freshness monitored?
  • File and row counts recorded?
  • Latest successful ingestion visible?
  • Access controls and secrets secure?
  • Sensitive fields protected; retention documented?
  • Audit and lineage available?

12.8Knowledge Check

Try answering each question before revealing the answer.

1. What is the difference between ETL and ELT?
ETL transforms data before loading the final target; ELT loads data first (e.g. into Bronze) and transforms it afterwards on the target platform.
2. When should you use batch ingestion rather than streaming?
When the business can tolerate data arriving on a schedule rather than within seconds or minutes. Batch is simpler and often cheaper.
3. What is the difference between a full load and a delta load?
A full load processes the complete dataset (deletes are reflected naturally); a delta load processes only new or changed data and must capture deletes explicitly.
4. Why can timestamp-based extraction miss changes?
Timestamps may not be updated reliably, can collide at boundaries, can belong to transactions that commit late, and can't represent physical deletes.
5. What is the difference between COPY INTO and Auto Loader?
COPY INTO is a SQL command that tracks loaded files per target table; Auto Loader is a scalable streaming source (cloudFiles) that tracks files in a checkpoint and supports schema evolution modes.
6. Why must Auto Loader's checkpoint location stay stable across normal runs?
The checkpoint records which files have been processed. A new or deleted checkpoint makes Auto Loader rediscover and reload everything.
7. What is schema evolution?
The controlled handling of changes to source columns and types, such as adding a new column, under an explicit policy.
8. Why is JDBC not equivalent to CDC?
JDBC is connectivity and extraction; CDC captures inserts, updates, and deletes through a change-tracking mechanism. JDBC alone can't see deletes or guarantee complete incremental capture.
9. How should a pipeline handle inserts, updates, and deletes?
Order and reduce changes to one per key, then apply them with a strategy such as Delta MERGE with explicit WHEN MATCHED … THEN DELETE (or soft-delete) handling.
10. Why commit a watermark only after the defined success boundary?
If it advances before the data is safely committed and a failure occurs, the next run starts after the lost data and silently skips it.
11. What is the purpose of an initial snapshot in a CDC pipeline?
It loads the existing source data before incremental change synchronization begins, coordinated so changes made during the snapshot aren't lost.
12. Why is row-count reconciliation insufficient on its own?
Two datasets can have the same row count but different records, duplicated keys, or wrong values. Also compare keys, totals, and checksums.
