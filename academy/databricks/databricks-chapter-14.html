Lakeflow Jobs and Workflow Orchestration

Run the right task at the right time, in the right order, and recover cleanly when something breaks. This chapter covers tasks and dependencies, schedules and triggers, parameters and task values, retries, timeouts, notifications, run repair, backfills, and integration with Azure Data Factory and the REST API. The project is a daily Bronze → Silver → Gold job that's safe to rerun.

Formerly Databricks Workflows. Prerequisites: notebooks, Delta Lake, and Chapter 13's declarative pipelines. Level: intermediate to advanced.

  1. Explain workflow orchestration and its role in data engineering.

  3. Create workflows with notebook, Python, SQL, and pipeline tasks.
  4. Configure task dependencies and parallel execution.
  5. Schedule jobs and trigger them from events.
  6. Configure retries, timeouts, notifications, and failure handling.
  7. Pass parameters to jobs and values between tasks.
  8. Repair failed runs and backfill historical data.
  9. Orchestrate multiple pipelines and integrate with Azure Data Factory.
  10. Build and monitor a production-style Bronze → Silver → Gold workflow.

14.1Introduction

14.1.1What Is Workflow Orchestration?

Workflow orchestration coordinates multiple tasks so they run in the correct order according to dependencies, schedules, conditions, and operational rules. A retail company might need to ingest orders, validate and clean them, remove duplicates, aggregate sales, refresh reports, and alert support if anything fails. Run independently, Gold might start before Silver finishes, or a report might refresh after ingestion failed.

Without orchestration:

Bronze ingestion    Silver cleansing
      |                   |
Runs independently  Runs independently
         \               /
          v             v
        Gold aggregation
  (may start before either finishes!)
With orchestration:

  Bronze Ingestion
         |
         v
  Silver Cleansing
         |
         v
  Gold Aggregation
         |
         v
  Refresh Reporting

An orchestrator manages

  • Execution order and dependencies.
  • Scheduling and triggers.
  • Parallel and conditional execution.
  • Retries and timeouts.
  • Failure notifications.
  • Parameter passing.
  • Run history and monitoring.
TimeActivity (6:00 AM deadline)
1:00 AMIngest source data
1:20 AMValidate and cleanse
2:00 AMAggregate sales
2:30 AMRefresh reporting datasets
3:00 AMVerify data quality
3:15 AMSend completion notification

14.1.2What Is Lakeflow Jobs?

Lakeflow Jobs is Databricks' orchestrator. A job combines tasks (notebooks, Python scripts, SQL, pipeline updates, and more) with schedules, parameters, dependencies, notifications, retries, and limits.

Retail_Daily_Sales_Job
Bronze_IngestionLoad incoming orders
Silver_CleansingValidate and clean
Gold_AggregationCalculate daily sales

Why use it?

  • Centralized workflow management.
  • Dependency-aware execution.
  • Scheduling, retries, notifications.
  • Run history and task-level monitoring.
  • Native integration with Databricks workloads.

When to use each

14.1.4Tasks and Dependencies

A task is one unit of work: run a notebook, a Python script, a SQL statement, a pipeline update, or another job. A dependency defines when a task may run relative to others. With A → B → C, if A fails, B and C don't run on the normal path.

TaskDepends onCondition
Bronze IngestionNoneStarts first
Silver CleansingBronze IngestionUpstream succeeds
Gold AggregationSilver CleansingUpstream succeeds

Dependencies prevent reading incomplete data, aggregating unvalidated records, refreshing reports too early, and continuing after a critical failure.

Best practice

Base dependencies on data requirements, not on the order you'd like tasks to appear.

14.1.5Job Scheduling

Common patterns

  • Daily: sales processing at 1:00 AM.
  • Hourly: operational metrics.
  • Weekly: weekly sales summary.
  • Event-based: when new files arrive.
  • Continuous: a new run starts as soon as the previous one ends.

Consider

  • Time zone.
  • When source data actually arrives.
  • Processing duration and retries.
  • The reporting deadline.
  • Upstream availability and maintenance windows.
  • Overlapping runs.
Start time ≠ deadline

If the workflow must finish by 6:00 AM, allow for retries and the worst-case duration, not just the typical one.

14.1.7Parameterized Execution

Parameters let the same job process different inputs without code changes. Instead of hard-coding processing_date = "2026-10-25", the job passes it in, and tomorrow it passes a different date.

ParameterExample
processing_date2026-10-25
catalogretail_dev
target_schemaanalytics
load_typeINCREMENTAL
batch_idBATCH_20261025_001

Parameters make workflows reusable, testable, easy to backfill, and portable across environments.

Never pass secrets as parameters

Parameters are visible in the job configuration and run history. Use secret scopes for passwords and tokens.

14.2.1Creating a Lakeflow Job

Steps

  1. Open Jobs & Pipelines → Create → Job.
  2. Give the job a meaningful name.
  3. Add the first task: key, type, notebook path, compute.
  4. Click + Add task for each further task, and set Depends on.
  5. Configure retries, timeouts, notifications, schedule, parameters, and permissions.
  6. Click Run now to test, then inspect the run.

14.2.2Notebook Tasks

Notebook tasks run PySpark, SQL, validation, and operational checks. Notebooks read parameters through widgets:

Python
dbutils.widgets.text("processing_date", "2026-10-25")   # default for interactive runs

processing_date = dbutils.widgets.get("processing_date")
print(f"Processing date: {processing_date}")

When the job runs, the job parameter with the same name overrides the widget default. Job parameters are passed to every notebook task automatically.

Best practices

  • Keep each notebook focused on one responsibility.
  • Don't hard-code environment-specific paths.
  • Log important execution information.
  • Validate parameters early.
  • Raise exceptions for critical failures.
  • Make data operations safe to retry. What happens if the task runs twice?

14.2.3Python Tasks

Python script tasks run a .py file for file validation, API extraction, utilities, quality checks, or metadata processing.

Python · validate_orders.py
import argparse


def main():
    parser = argparse.ArgumentParser()
    parser.add_argument("--processing-date", required=True)
    args = parser.parse_args()

    print(f"Validating orders for {args.processing_date}")
    # Add validation logic here.


if __name__ == "__main__":
    main()

Script tasks receive command-line arguments, not widgets. In the task's Parameters field, map the job parameter with a dynamic reference:

Task parameters (JSON array)
["--processing-date", "{{job.parameters.processing_date}}"]

14.2.4SQL Tasks

SQL tasks run queries or SQL files on a SQL warehouse: statements, dataset refreshes, count checks, quality checks, and SQL business logic.

SQL · summarize Gold
SELECT
    order_date,
    SUM(order_count) AS total_orders,
    SUM(total_sales) AS total_sales
FROM retail_dev.jobs_lab.sales_gold
GROUP BY order_date
ORDER BY order_date DESC;

A query that returns duplicate rows does not fail the task on its own. To make a SQL check fail the job, raise an error:

SQL · fail the task on duplicates
SELECT
    CASE
        WHEN COUNT(*) > 0
        THEN raise_error('Duplicate order IDs found in Silver')
        ELSE 'OK'
    END AS check_result
FROM (
    SELECT order_id
    FROM retail_dev.jobs_lab.orders_silver
    GROUP BY order_id
    HAVING COUNT(*) > 1
);

Tested on Spark: with no duplicates it returns OK; with duplicates it raises USER_RAISED_EXCEPTION, which fails the task.

14.2.5Pipeline Tasks

A pipeline task runs a Lakeflow Spark Declarative Pipeline update (Chapter 13) as one unit of work. The pipeline manages its own datasets, and downstream tasks wait for it to finish.

Task 1: Validate source files
            |
            v
Task 2: Run Lakeflow pipeline
            |
            v
Task 3: Reconcile Gold data
            |
            v
Task 4: Refresh reporting

Use a pipeline task when

  • Transformations already live in a pipeline.
  • The pipeline is part of a larger workflow.
  • Downstream tasks must wait for it.
  • You want central orchestration across workloads.

This avoids re-implementing Bronze/Silver/Gold as separate notebooks.

Sequential:

Orders Ingestion
      |
      v
Orders Cleansing
      |

Parallel branches:

        Source Validation
          /           \
         v             v
Customer Ingestion  Product Ingestion
         |             |
         v             v
Customer Cleansing  Product Cleansing
          \           /
           v         v
        Sales Processing

Independent branches run concurrently, and the final task waits for both. That gives shorter runtime and better use of compute, at the cost of more concurrent compute and possible contention. Use it only for genuinely independent tasks.

14.2.8Parallel Execution

         Bronze Ingestion
                |
                v
         Silver Cleansing
            /        \
           v          v
  Customer Summary  Product Summary
            \        /
             v      v
           Final Report

Performance example

Customer processing: 15 min. Product processing: 20 min.

Sequential: ~35 min.
Parallel: ~20 min (the longer branch).

Excluding overhead and contention; actual gains depend on compute.

Use parallelism when

  • Tasks don't depend on each other.
  • Source data is ready.
  • Shared resources can handle the load.
  • It actually reduces total runtime.

Avoid it when

  • Tasks modify the same target data.
  • Operations aren't safe concurrently.
  • They compete heavily for resources.
  • Order matters for correctness.

14.2.9Conditional Execution

Bronze Ingestion
        |
        v
If/else: records_ingested > 0 ?
       /          \
    true          false
      |             |
      v             v
   Silver      Notify "no data"
      |
      v
    Gold

If/else condition task

Compares two values. Either side can be a dynamic reference, such as a task value:

Left:     {{tasks.Bronze_Ingestion.values.records_ingested}}
Operator: >
Right:    0

Downstream tasks depend on the true or false outcome.

Example conditions: run Gold only if Silver validation passed; quarantine when invalid records exist; skip reporting when no new data arrived; notify when a critical task fails; backfill only for a valid date range.

Condition vs expectation

A pipeline expectation validates dataset records. A workflow condition decides which tasks run. They work well together.

14.3Production Features

14.3.1Retry Policies

Retries re-attempt a task after failure, which helps with transient problems such as network errors, temporary service unavailability, intermittent connections, and some rate limits.

Bronze Ingestion
       |
       v
    Failure
       |
       v
     Retry
       |
       +----> Success
       |
       +----> Failure (retries exhausted)
                  |
                  v
             Final Failure
Failure typeApproach
Temporary network errorRetry may help
Temporary service errorRetry may help
Invalid SQL syntaxFix the code
Missing required columnInvestigate the schema
Invalid business dataCorrect or quarantine
Permission deniedFix permissions
Wrong transformation logicFix the code

Per task you set the maximum retries and minimum interval between attempts (and optionally retry on timeout).

Retries require idempotency

A retry runs the same task again. If the task appends the same records each time, a retry creates duplicates (Chapter 11's problem). Use file tracking, MERGE, replaceWhere, or full rebuilds. The project shows how.

14.3.2Timeouts

A timeout stops a task (or job) that runs too long, so a hung task doesn't block everything. If Bronze normally takes 10 minutes, a 45-minute timeout allows variation while preventing an endless run.

ComponentTimeout
Entire job3 hours
Bronze ingestion45 minutes
Silver cleansing60 minutes
Gold aggregation30 minutes

Choosing a timeout

  • Typical and historical maximum duration.
  • Data volume and source latency.
  • Compute availability.
  • Retry time.
  • Overall deadline.

Also consider a duration warning threshold that alerts before the timeout kills the run.

Illustrative values. Base them on measured run history.

14.3.3Failure Handling

          Bronze
             |
             v
          Silver
             |
       +-----+-----+
       |           |
    Success     Failure
       |           |
       v           v
      Gold     Alert_Team  (Run if: At least one failed)
       |
       v
   Reporting

A good strategy

  1. Records the failure.
  2. Notifies the responsible team.
  3. Preserves information for investigation.
  4. Retries transient failures.
  5. Blocks incorrect downstream processing.
  6. Allows safe recovery after the fix.
Python · ✗ hides the failure
try:
    perform_critical_load()
except Exception as exc:
    print(f"Load failed: {exc}")
    # task reports SUCCESS!
Python · ✓ fails correctly
try:
    perform_critical_load()
except Exception as exc:
    print(f"Load failed: {exc}")
    raise          # task reports FAILED
Don't swallow exceptions

If the exception is caught and not re-raised, the task looks successful, and Gold happily runs on top of a failed load. The same applies to dbutils.notebook.exit(): exiting "successfully" after an error hides it.

14.3.4Notifications

Notifications can fire on job start, success, failure, and duration-threshold breaches, and can go to email or configured destinations (Slack, Microsoft Teams, PagerDuty, webhooks).

Job:     Retail_Daily_Sales_Job
Status:  Failed
Task:    Silver_Cleansing
Time:    2:15 AM
Action:  Review the failed task and
         inspect the source data.

Best practices

  1. Notify the responsible support team.
  2. Include job and task names.
  3. Include failure details or a run link.
  4. Don't alert on every retry. Enable "mute notifications until the last retry".
  5. Separate critical failures from informational events.
  6. Define an escalation path.

Combine job notifications with your organization's monitoring and incident tools. Critical data-quality failures may need their own alerts.

14.3.5Job Parameters

Job parameters (e.g. processing_date, environment, load_type) are defined once on the job and passed to tasks.

Task typeHow it receives job parameters
NotebookAutomatically, as widgets with the same name
Python script / wheelVia task arguments, e.g. "{{job.parameters.processing_date}}"
SQLAs query parameters
PipelinePipeline settings (or a full refresh option)
Dynamic dates

Don't leave 2026-10-25 hard-coded for scheduled runs. Set the parameter's default to the dynamic value {{job.start_time.iso_date}} (the run's start date). For "yesterday", compute it in the notebook from that date. Override the value manually with Run now with different parameters for backfills.

Python · validate parameters
from datetime import date

processing_date = date.fromisoformat("2026-10-25")   # raises ValueError if malformed
print(processing_date)

14.3.6Task Values

Task values let one task publish small values for downstream tasks: record counts, batch IDs, validation results, status flags.

Python · producer (task key Bronze_Ingestion)
dbutils.jobs.taskValues.set(
    key="records_ingested",
    value=150000
)
Python · consumer
records_ingested = dbutils.jobs.taskValues.get(
    taskKey="Bronze_Ingestion",
    key="records_ingested",
    default=0,
    debugValue=0   # used when run interactively
)

Outside notebooks, reference it as {{tasks.Bronze_Ingestion.values.records_ingested}} (e.g. in an if/else task). The taskKey must match the producer's task key exactly.

Without debugValue, get() raises an error when you run the notebook outside a job. Task values aren't for datasets; store data in tables.

14.3.7Repairing Failed Runs

A failed run doesn't need a full restart. Repair run reruns only the failed and selected tasks, keeping the results of successful ones.

Bronze_Ingestion   SUCCESS
       |
       v
Silver_Cleansing   FAILED
       |
       v
Gold_Aggregation   SKIPPED (upstream failed)

-> fix, then Repair run:
   reruns Silver + Gold only

Procedure

  1. Open the failed run.
  2. Identify the failed task.
  3. Inspect the error and output.
  4. Fix the underlying issue.
  5. Click Repair run.
  6. Select tasks to rerun (failed + dependents are preselected).
  7. Verify downstream results.
Repair doesn't fix data

If the failed task partially wrote its target before failing, make sure it's safe to run again. That's idempotency again.

14.3.8Restarting Failed Tasks

If A succeeds, B fails, and C doesn't run, then after fixing B, C must still run to produce the final output. Before restarting:

  • Check whether the source has changed.
  • Check whether the task wrote partial results.
  • Verify the task is idempotent.
  • Determine which downstream tasks must rerun.
  • Confirm parameters are correct.
  • Reconcile the output afterwards.

Not every run resumes at exactly the point of failure. Behavior depends on task types and run state.

14.4.1Multi-Pipeline Orchestration

          Retail_Master_Job
                  |

       |          |          |

Why

  • Domains are maintained independently.
  • Independent pipelines run in parallel.
  • Shared reporting waits for all inputs.
  • Failure handling is centralized.

Don't run pipelines in parallel if they write to the same targets or depend on each other.

14.4.2Parent and Child Workflows

A Run Job task lets a parent job trigger another job as a child, which is useful when a workflow is reused by several business processes.

Parent: Retail_Daily_Master
           |
     +-----+------+
     |            |
     v            v
Orders Job    Customer Job
     |            |
     v            v
 Sales Job    Customer Report
      \          /
       v        v
    Final Validation

Benefits

Reuse, clear responsibilities, independent development, clear ownership, organized large workflows.

Risks

More complex dependencies, harder end-to-end troubleshooting, concurrency conflicts, harder parameter propagation. For a small workflow, one job is simpler.

14.4.3Dependency Management

LevelExampleManaged by
Datasetorders_bronze → orders_silver → sales_goldThe declarative pipeline

Best practices: keep graphs understandable; no circular dependencies; wait for the right upstream outputs; use explicit task keys; document shared datasets; plan for missing upstream data; avoid needless serial execution.

14.4.4Concurrent Execution

Daily Run:      1:00 AM ================ 2:00 AM
Backfill Run:          1:30 AM ===================== 3:00 AM
                         ^ both writing the same tables?

Risks

  • Duplicate processing.
  • Conflicting writes.
  • Compute contention and cost.
  • Unpredictable completion times.
  • Incorrect watermark updates.

Controls

  • Maximum concurrent runs (default 1); with queueing on, extra runs wait instead of being skipped.
  • Can runs for different dates proceed independently?
  • Can targets handle concurrent writes safely?
  • Isolate backfills from the normal schedule.

A concurrency limit controls runs, not data correctness. You still need idempotent writes.

14.4.5Backfills

A backfill processes historical data that was missed, corrected, or must be recalculated, e.g. the job failed on 2026-10-20, 21, and 22.

Options

  • Run now with different parameters once per date.
  • A For each task that loops over a list of dates, running a nested task per date (with configurable concurrency).
  • A job with start_date/end_date parameters that iterates internally.

Before running

  1. Identify the missing dates.
  2. Verify source data exists.
  3. Confirm the transformation logic.
  4. Check whether outputs already exist.
  5. Make sure writes are safe to repeat.
  6. Validate results.
  7. Monitor resource usage.
Idempotent backfills

Processing the same date twice must not duplicate data. Either replace the date's slice atomically (Delta replaceWhere, used in the project) or MERGE on business keys.

14.4.6Scheduled Workloads

Workflow stepRunsPurpose
Source ingestionDaily at 1:00 AM (scheduled)Load source files
Silver transformationAfter ingestion succeedsClean and validate
Gold aggregationAfter Silver succeedsBusiness metrics
ReconciliationAfter Gold succeedsValidate totals
Reporting refreshAfter reconciliation succeedsPublish results

Schedule only the master job and let dependencies drive the rest. If a run overruns into the next scheduled start, the concurrency setting decides whether the new run waits or is skipped.

Let ADF orchestrate when

  • The workload is mainly Databricks.

14.5.2REST API Integration

The Jobs REST API and the Databricks SDK let external systems start, monitor, and manage jobs.

Bash
pip install databricks-sdk
Python · Databricks SDK
from databricks.sdk import WorkspaceClient

w = WorkspaceClient()   # auth from env vars / config profile, never hard-coded tokens

run = w.jobs.run_now(
    job_id=123456789,
    job_parameters={"processing_date": "2026-10-20"}
)
print(f"Run ID: {run.run_id}")          # returned immediately

finished = run.result()                 # blocks until the run ends
print(finished.state.result_state)      # e.g. SUCCESS or FAILED
Bash · REST equivalent
curl -X POST "https://$DATABRICKS_HOST/api/2.1/jobs/run-now" \
  -H "Authorization: Bearer $DATABRICKS_TOKEN" \
  -d '{"job_id": 123456789, "job_parameters": {"processing_date": "2026-10-20"}}'
Starting ≠ finishing

run-now returns a run ID immediately, before processing completes. Callers must poll jobs/runs/get (or use the SDK's .result()) to learn the outcome. Use a service principal for production authentication.

14.5.4Job Monitoring

Job level

Status, start/end, duration, failed runs, retry counts, schedule delays, concurrent runs.

Task level

Status, duration, errors, retries, upstream dependencies, compute failures.

Data level

14.6.2Step 1: Bronze Ingestion Notebook

Create notebook 01_bronze_ingestion. It validates the date, reads that day's file, adds metadata, and replaces only that date's slice of Bronze. That's why retries and backfills never duplicate rows.

Python · 01_bronze_ingestion
# 01_bronze_ingestion
from datetime import date
from pyspark.sql import functions as F

dbutils.widgets.text("catalog", "retail_dev")
dbutils.widgets.text("processing_date", "2026-10-20")

catalog = dbutils.widgets.get("catalog")
processing_date = date.fromisoformat(dbutils.widgets.get("processing_date"))  # fails fast on a bad date

source_path = (
    f"/Volumes/{catalog}/jobs_lab/landing/"
    f"orders_{processing_date:%Y%m%d}.json"
)

orders_df = (
    spark.read
    .schema("order_id STRING, customer_id STRING, order_date DATE, "
            "amount DECIMAL(18,2), status STRING, updated_at TIMESTAMP")
    .json(source_path)                     # a missing file fails the task
    .withColumn("_source_file", F.col("_metadata.file_path"))
    .withColumn("_ingested_at", F.current_timestamp())
    .withColumn("_processing_date", F.lit(processing_date))
)

records_ingested = orders_df.count()
if records_ingested == 0:
    raise RuntimeError(f"No records found in {source_path}")

# Idempotent: replace only this date's slice, so retries and backfills never duplicate
(
    orders_df.write
    .format("delta")
    .mode("overwrite")
    .option("replaceWhere", f"_processing_date = '{processing_date}'")
    .saveAsTable(f"{catalog}.jobs_lab.orders_bronze")
)

dbutils.jobs.taskValues.set(key="records_ingested", value=records_ingested)
print(f"Bronze: {records_ingested} records ingested for {processing_date}")
What makes it retry-safe

mode("overwrite") + replaceWhere atomically swaps out just the rows for _processing_date. Run it twice for the same date and Bronze still holds one copy, unlike Chapter 11's append. It also publishes records_ingested as a task value.

Step 2: Silver cleansing notebook

Create 02_silver_cleansing. It normalizes status, keeps the latest version of each order, drops invalid rows, and replaces that date's Silver slice:

Python · 02_silver_cleansing
# 02_silver_cleansing
from datetime import date
from pyspark.sql import functions as F
from pyspark.sql.window import Window

dbutils.widgets.text("catalog", "retail_dev")
dbutils.widgets.text("processing_date", "2026-10-20")

catalog = dbutils.widgets.get("catalog")
processing_date = date.fromisoformat(dbutils.widgets.get("processing_date"))

bronze_df = (
    spark.table(f"{catalog}.jobs_lab.orders_bronze")
    .filter(F.col("_processing_date") == F.lit(processing_date))
    .withColumn("status", F.upper(F.trim(F.col("status"))))
)

# Deduplicate: keep the latest version of each order_id
latest_first = Window.partitionBy("order_id").orderBy(F.col("updated_at").desc_nulls_last())

deduped_df = (
    bronze_df
    .filter(F.col("order_id").isNotNull())
    .withColumn("_rn", F.row_number().over(latest_first))
    .filter(F.col("_rn") == 1)
    .drop("_rn")
)

is_valid = (
    F.col("customer_id").isNotNull()
    & (F.col("amount") >= 0)
    & F.col("status").isin("COMPLETED", "CANCELLED", "PENDING")
)

silver_df = deduped_df.filter(is_valid).select(
    "order_id", "customer_id", "order_date", "amount",
    "status", "updated_at", "_processing_date"
)

(
    silver_df.write
    .format("delta")
    .mode("overwrite")
    .option("replaceWhere", f"_processing_date = '{processing_date}'")
    .saveAsTable(f"{catalog}.jobs_lab.orders_silver")
)

silver_count = silver_df.count()
rejected = bronze_df.count() - silver_count       # duplicates + invalid rows
dbutils.jobs.taskValues.set(key="silver_records", value=silver_count)
print(f"Silver: {silver_count} records kept, {rejected} removed for {processing_date}")

Deduplication is within the processing date. If the same order can arrive on different days, switch Silver to a MERGE on order_id (Chapter 9) or AUTO CDC (Chapter 13).

Step 3: Gold aggregation notebook

Create 03_gold_aggregation. Gold is small, so it's simply rebuilt from Silver each run. A full rebuild is naturally idempotent.

Python · 03_gold_aggregation
# 03_gold_aggregation
dbutils.widgets.text("catalog", "retail_dev")
catalog = dbutils.widgets.get("catalog")

# Rebuilt from Silver on every run, so reruns and backfills are always safe
spark.sql(f"""
    CREATE OR REPLACE TABLE {catalog}.jobs_lab.sales_gold AS
    SELECT
        order_date,
        status,
        COUNT(*)    AS order_count,
        SUM(amount) AS total_sales,
        AVG(amount) AS average_order_value
    FROM {catalog}.jobs_lab.orders_silver
    GROUP BY order_date, status
""")

print("Gold: sales_gold rebuilt from Silver")

Step 4: Validation notebook

Create 04_validate_gold. Each check raises an exception on failure, so the task fails and the job reports it:

Python · 04_validate_gold
# 04_validate_gold
from datetime import date
from pyspark.sql import functions as F

dbutils.widgets.text("catalog", "retail_dev")
dbutils.widgets.text("processing_date", "2026-10-20")

catalog = dbutils.widgets.get("catalog")
processing_date = date.fromisoformat(dbutils.widgets.get("processing_date"))

silver = spark.table(f"{catalog}.jobs_lab.orders_silver")
gold = spark.table(f"{catalog}.jobs_lab.sales_gold")

# 1. No duplicate order IDs in Silver
duplicates = silver.groupBy("order_id").count().filter(F.col("count") > 1)
if not duplicates.isEmpty():
    raise RuntimeError("Validation failed: duplicate order IDs in Silver.")

# 2. Silver has data for this processing date
if silver.filter(F.col("_processing_date") == F.lit(processing_date)).isEmpty():
    raise RuntimeError(f"Validation failed: no Silver rows for {processing_date}.")

# 3. Gold reconciles with Silver (same grain, no extra filters)
s = silver.agg(F.count("*").alias("orders"), F.sum("amount").alias("sales")).first()
g = gold.agg(F.sum("order_count").alias("orders"), F.sum("total_sales").alias("sales")).first()
if (s["orders"], s["sales"]) != (g["orders"], g["sales"]):
    raise RuntimeError(f"Reconciliation failed: Silver {s} vs Gold {g}")

# 4. Bronze task's record count (task value) is sane
ingested = dbutils.jobs.taskValues.get(
    taskKey="Bronze_Ingestion", key="records_ingested", default=0, debugValue=6
)
print(f"Validation passed: {s['orders']} orders, sales {s['sales']}, "
      f"{ingested} raw records ingested.")

isEmpty() replaces the original limit(1).count() checks (as in Chapter 8). The task-value read uses debugValue so the notebook also runs interactively.

14.7Production Implementation with a Single Lakeflow Pipeline

The notebook job teaches orchestration. But if Bronze, Silver, and Gold already live in one declarative pipeline (Chapter 13), you don't need three transformation notebooks:

       Daily Schedule
              |
              v
   Run Lakeflow Pipeline (pipeline task)
              |
              v
     Bronze -> Silver -> Gold
              |
              v
    Validate Gold (notebook/SQL task)
              |
              v
     Notify on failure

Advantages

  • Dataset dependencies stay inside the pipeline.
  • The job handles the broader workflow.
  • No duplicated transformation logic.
  • Monitoring splits cleanly: pipeline UI for datasets, job UI for tasks.
SituationRecommended design
Transformations are independent notebooksMulti-task job
Transformations are in one declarative pipelinePipeline task + validation
Workflow includes multiple external systemsLakeflow Jobs or external orchestrator, by ownership
Several independent pipelinesMulti-task job or parent workflow

Rule of thumb

For Databricks-centric work, one declarative pipeline orchestrated by a job is usually simpler than rebuilding the pipeline's dependencies as separate notebook tasks.

14.8Common Interview Questions

Try answering each before revealing the answer.

Q1. What is workflow orchestration?
Coordinating multiple tasks according to dependencies, schedules, conditions, and operational rules.
Q2. What is Lakeflow Jobs?
Databricks' orchestrator (formerly Workflows) for coordinating notebooks, scripts, SQL, pipeline updates, and other tasks with schedules, retries, and notifications.
Q3. Lakeflow Jobs vs Declarative Pipelines?
Jobs orchestrate tasks; pipelines define and manage datasets. Production systems typically run pipelines from jobs.
Q4. What is a task dependency?
The condition (e.g. "All succeeded", "At least one failed") under which a task may run relative to its upstream tasks.
Q5. What is parallel execution?
Running independent tasks simultaneously to cut total duration when resources and dependencies allow.
Q6. Why are retries important?
They recover from transient failures without manual intervention, but don't fix deterministic errors.
Q7. Why is idempotency important in a job?
Retries, repairs, and backfills run tasks more than once. Idempotent writes (replaceWhere, MERGE, full rebuilds) keep repeated runs from duplicating data.
Q8. What is a task timeout?
The maximum time a task may run before it's stopped and marked timed out.
Q9. Job parameters vs task values?
Job parameters are inputs to the whole run; task values are small outputs one task publishes for downstream tasks (dbutils.jobs.taskValues).
Q10. What is run repair?
Rerunning only failed and selected tasks of a previous run, keeping successful task results, instead of restarting everything.
Q11. What is a backfill?
Processing historical periods that were missed, corrected, or need recalculation, typically by rerunning a parameterized job per date.
Q12. How does Databricks integrate with ADF?
ADF can run a Databricks job (or notebook) as an activity, wait for it, and continue its wider Azure workflow based on the result.
Q13. Why might a job succeed while the data is wrong?
Task success only means code didn't throw. Wrong logic, incomplete sources, or swallowed exceptions all "succeed". Validation and reconciliation catch these.
Q14. When use Lakeflow Jobs instead of ADF?
For Databricks-centric workflows; ADF fits orchestration spanning many Azure services or organizations standardized on ADF.
Q15. How would you design a production sales workflow?
Ingest Bronze idempotently, cleanse and validate Silver, aggregate Gold, reconcile, with retries, timeouts, failure notifications, a schedule matched to source arrival, and monitoring against the SLA.
