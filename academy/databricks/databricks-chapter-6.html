6.1Introduction to Apache Spark

6.1.1What is Apache Spark?

Simple definition

Apache Spark is an open-source engine for processing large datasets across multiple computing resources. Instead of one computer doing everything, Spark divides data into partitions and processes them across multiple worker processes.

Suppose you have 100 million customer transactions and need total sales by customer, total sales by month, transaction counts by product, customers spending over ₹100,000, and the top 10 products by revenue. A single computer may struggle with the volume, memory, or time. Spark distributes suitable operations across executors so several partitions are processed in parallel.

A simplified architecture

What makes Spark useful?

Processing large datasets, distributed transformations, joining large tables, aggregating across millions or billions of rows, batch and streaming workloads, ETL and ELT, integrating Python, SQL, and other APIs, and building pipelines on cloud storage.

Not always faster

Spark is not automatically faster than every database or SQL engine. For small datasets, a traditional database or a simple Python script may be more efficient. Spark's benefit comes from distributing suitable workloads across available compute.

6.1.2Why do we use Spark in Databricks?

A pipeline that processes customer transactions must read files from cloud storage, validate the schema, remove invalid records, join with customer data, calculate totals by customer, and store results in a Delta table. Spark performs these transformations across distributed partitions:

Python
transactions_df = spark.read.parquet(
    "/path/to/transactions"
)

filtered_df = transactions_df.filter(
    transactions_df.amount > 0
)

customer_summary_df = (
    filtered_df
    .groupBy("customer_id")
    .sum("amount")
)
The key idea

The transformations describe what you want. Spark's execution engine decides how to execute it.

6.1.3Spark versus traditional SQL engines

Why use Spark when SQL engines already exist? They overlap in capability but differ in architecture, execution model, and workload strengths. A traditional relational database manages tables and indexes, query execution, transactions, optimization, storage, and concurrency. Spark is a distributed processing engine that works over data in many storage systems and formats, with SQL, Python, Scala, Java, Structured Streaming, and distributed DataFrames.

Does Spark always process data in memory?

No. Spark uses memory for caching and intermediate processing, but it also reads and writes disk and may spill to disk when memory is short. Its advantage is a flexible, optimized distributed execution engine, not "everything in memory."

6.1.5Distributed computing

Distributed computing divides work across multiple computing resources. One million records might be split into four partitions of 250,000, each processed by its own task, concurrently where task slots allow.

                    1,000,000 records
                            |
       +-------------+------+------+-------------+
       |             |             |             |
   P1: 250K      P2: 250K      P3: 250K      P4: 250K
       |             |             |             |
    Task 1        Task 2        Task 3        Task 4
       |             |             |             |
       +-------------+------+------+-------------+
                            |
                     Combined result

Conceptual. Real partition sizes may be uneven, and concurrency depends on cluster configuration.

Independent partitions can be processed in parallel. But some operations need data redistributed: grouping by customer_id requires all of a customer's records to come together. That redistribution is a shuffle (Section 6.3).

6.1.6In-memory processing

Spark can cache or persist data in memory to avoid repeatedly reading or recomputing it.

Python
customers_df = spark.read.parquet(
    "/path/to/customers"
)

customers_df.cache()   # marks for caching; nothing loads yet

customers_df.count()   # action: computes and populates the cache

cache() doesn't load data immediately. Because of lazy evaluation, caching materializes when an action needs the data.

Caching can help when

  • A DataFrame is reused repeatedly.
  • Recomputing it is expensive.
  • It fits reasonably in available resources.
  • The workload benefits from reuse.

Caching may not help when

  • The DataFrame is used only once.
  • The data is too large to cache efficiently.
  • It displaces other useful data from memory.
  • Recomputing is cheap.
Best practice

Cache based on measured workload behavior, not as a default for every DataFrame.

6.1.7Parallel processing

Parallel processing means multiple units of work run at the same time. With eight task slots and a stage of 100 independent tasks, Spark runs up to eight at once; the rest wait for free slots.

ConceptMeaning
PartitionsDivisions of data
TasksProcess partitions for a particular stage
Task slotsDetermine how many tasks can run concurrently
Important limitation

Not every operation scales linearly with workers. Performance can be limited by storage throughput, network bandwidth, CPU, memory, data skew, shuffle volume, driver overhead, and inherently sequential work. More workers don't guarantee proportional speed-up.

6.2Spark Architecture

How Spark actually executes a data-processing application.

6.2.1The Driver

The driver coordinates a Spark application: it creates the application context, builds and coordinates query execution, schedules jobs and tasks, tracks progress, communicates with executors, and collects results returned to it. In Databricks, your notebook or job interacts with the driver.

Python
df = spark.read.parquet("/path/to/sales")

filtered_df = df.filter(
    df.amount > 1000
)

display(filtered_df)

For DataFrame operations, the driver and Spark SQL engine build and optimize the query plan, then schedule distributed work.

Driver memory problems

✗ Risky on large data
# Pulls every row into the
# driver's Python process
all_records = df.collect()
✓ Prefer
# Distributed aggregation
df.groupBy("department").count()

# Or a small sample
df.limit(10).collect()

limit() may still do work across partitions, but it caps the rows returned to the driver.

Production rule

Avoid collecting large distributed datasets into ordinary Python lists.

6.2.2Executors

Executors are processes that run Spark tasks and can store cached data, generally on worker resources allocated to the application. They read partitions, filter, join, aggregate, write output, cache data, and report results and status to the driver.

Executor 1 -> Task 1 -> Partition 1
Executor 2 -> Task 2 -> Partition 2
Executor 1 -> Task 3 -> Partition 3
Executor 2 -> Task 4 -> Partition 4

Illustrative. Tasks are scheduled by resource availability and locality, and an executor runs many tasks over time.

DriverExecutor
Coordinates the applicationExecutes tasks
Builds and schedules workProcesses data partitions
Tracks job progressStores cached data where configured
Can collect resultsSends task results and status to the driver
Bottleneck if overloadedBottleneck from CPU, memory, or I/O limits

A cluster manager allocates resources for Spark applications. Options include Spark's standalone manager, Hadoop YARN, Kubernetes, and cloud-specific provisioning. In Databricks, the platform manages much of this lifecycle, so you generally don't configure a cluster manager as you would in a self-managed deployment.

6.2.4Jobs

A Spark job is a unit of execution triggered by an action, such as df.count(), df.collect(), or df.write.format("delta").save(...).

Python
df = spark.read.parquet("/path/to/sales")

filtered_df = df.filter(        # transformation
    df.amount > 1000
)

count = filtered_df.count()     # action: triggers a job

The resulting job may contain one or more stages.

Important

One notebook cell is not necessarily one Spark job. A cell can trigger several jobs.

6.2.5Stages

A stage is a group of tasks Spark can execute without crossing a shuffle dependency boundary.

Few stages: no regrouping
df.filter(df.amount > 1000).count()
Stage boundary: shuffle
df.groupBy("customer_id") \
  .sum("amount") \
  .show()

Grouping usually brings records with the same customer ID together, introducing a shuffle and a stage boundary.

A slow stage may indicate

  • Expensive scans.
  • Large shuffles.
  • Data skew.
  • Memory pressure.
  • Disk spill.
  • Slow output writes.

The Spark UI shows stage-level information to diagnose these.

6.2.6Tasks

A task is the unit of work Spark schedules for one partition in a stage. A stage over 200 partitions generally has about 200 tasks.

Python
df.rdd.getNumPartitions()   # e.g. 200

The task count can differ with the execution plan, partition pruning, data-source behavior, and other optimizations.

Spark schedules tasks based on available executor resources, task dependencies, data locality, resource constraints, and scheduling policies. A stage with 1,000 tasks doesn't run all 1,000 simultaneously.

6.2.7DAG — Directed Acyclic Graph

A DAG is a graph of operations with dependencies: directed (edges have direction), acyclic (no cycles), and a graph (nodes are operations, edges are dependencies).

Python
df = spark.read.parquet("/path/to/sales")

filtered_df = df.filter(
    df.amount > 1000
)

summary_df = filtered_df.groupBy(
    "customer_id"
).sum("amount")

summary_df.write.format("delta").save(
    "/path/to/output"
)
Read Sales
    |
    v
Filter Amount > 1000
    |
    v
Group By Customer
    |
    v
Sum Amount
    |
    v
Write Output

Spark uses these dependencies to plan execution, splitting work into stages where a shuffle is needed.

Narrow dependency

Each output partition depends on a limited set of input partitions, often one.

df.filter(df.amount > 1000)

Wide dependency

An output partition may depend on many input partitions, often requiring a shuffle.

df.groupBy("customer_id").sum("amount")

6.2.10Execution plans

An execution plan describes how Spark will process a query.

Python
result_df = (
    df.filter(df.amount > 1000)
      .groupBy("customer_id")
      .sum("amount")
)

result_df.explain()             # physical plan
result_df.explain("extended")   # logical + physical plans

What to look for

  • Data source scans.
  • Filters.
  • Column projections.
  • Aggregations.
  • Joins.
  • Exchanges (shuffles).
  • Broadcast operations.
  • Partition-related behavior.
A conceptual plan (read bottom-up)
Aggregate by customer_id
           |
           v
Exchange / Shuffle
           |
           v
Partial Aggregate
           |
           v

Why use explain? To check whether Spark reads more data than needed, adds an expensive shuffle, uses a broadcast join, applies filters effectively, or produces a plan far more complex than expected. It's one of your most useful performance tools.

6.3Spark Execution

How Spark turns your code into executable work.

6.3.1Transformations

A transformation defines a new dataset from an existing one: select(), filter(), where(), withColumn(), drop(), groupBy(), join(), orderBy(), distinct().

Python
df = spark.read.parquet("/path/to/sales")

filtered_df = df.filter(
    df.amount > 1000
)

selected_df = filtered_df.select(
    "customer_id",
    "amount"
)

Spark doesn't run the full computation after each transformation. It builds the plan and executes it when an action needs a result.

Some transformations trigger planning or metadata access early, and some APIs behave specially, but DataFrame transformations are generally lazy.

6.3.2Actions

Actions require Spark to produce a result or perform output.

Python
df.count()
df.collect()
df.show()
df.take(10)
df.write.format("delta").save("/path/to/output")
Be careful with repeated actions

filtered_df.count() followed by filtered_df.show() may trigger separate jobs and recompute the transformations, unless caching or other optimizations allow reuse. For an expensive DataFrame used many times, consider caching.

6.3.3Lazy evaluation

Spark defers executing transformations until an action requires a result.

Python
df = spark.read.parquet("/path/to/sales")

df1 = df.filter(df.amount > 1000)          # plan only
df2 = df1.select("customer_id", "amount")  # plan only
df3 = df2.groupBy("customer_id").sum("amount")  # plan only

df3.show()   # now the whole plan runs

Column pruning

If the query only needs customer_id and amount, Spark may skip reading other columns from a columnar source like Parquet.

Predicate pushdown

Spark may push supported filters toward the data source, reducing the data it has to process.

Laziness lets Spark optimize the whole query instead of each step in isolation. Actual optimizations depend on the source, query, and plan.

6.3.4Narrow transformations

A narrow transformation can run without redistributing records across the cluster: each partition is processed independently.

Python
df.filter(df.amount > 1000)
df.select("customer_id", "amount")
df.withColumn("tax", df.amount * 0.18)
Partition 1 -> Filter -> Output 1
Partition 2 -> Filter -> Output 2
Partition 3 -> Filter -> Output 3

6.3.5Wide transformations

A wide transformation needs data from multiple input partitions to be redistributed or coordinated, and often requires a shuffle.

Python
df.groupBy("customer_id").sum("amount")
df.repartition(20)
df.orderBy("amount")
df.distinct()
Why wide transformations can be expensive

They may require serializing records, partitioning by a key, sending data over the network, writing intermediate data to memory or disk, reading it back, and processing the new partitions, all of which consume network, CPU, memory, and disk.

6.3.6Shuffle operations

A shuffle redistributes data across partitions.

Input (spread across partitions)
customer_idamount
101100
102200
101300
103150
102400
After groupBy + sum
customer_idsum(amount)
101400
102600

Python
summary_df = df.groupBy(
    "customer_id"
).sum("amount")

Customer 101 may sit in several partitions, so Spark moves records so all of a customer's values are processed together.

What makes a shuffle expensive

  • Large input volume.
  • Many columns shuffled.
  • Too many or too few partitions.
  • Skewed keys.
  • Insufficient executor memory.
  • Disk spilling.
  • Network limits.

How to investigate

Inspect summary_df.explain(), then use the Spark UI or Databricks execution details for actual shuffle read and write metrics.

Not every shuffle is bad

Grouping, sorting, and many joins need redistribution to be correct. The goal is to avoid unnecessary shuffles and make required ones efficient.

6.3.7Job execution

Python
df = spark.read.parquet("/path/to/sales")

filtered_df = df.filter(
    df.amount > 1000
)

summary_df = filtered_df.groupBy(
    "customer_id"
).sum("amount")

summary_df.write.format("delta").save(
    "/path/to/output"
)
  1. The driver receives the operations.
  2. Spark builds the logical plan.
  3. Spark optimizes the plan.
  4. Spark creates a physical execution plan.
  5. Spark identifies stage boundaries and tasks.
  6. Tasks are scheduled on executors.
  7. Executors process the partitions.
  8. Shuffle data is exchanged where necessary.
  9. Results are written to the target.
  10. The driver tracks completion or failure.

Physical details depend on Spark version, execution mode, data source, and optimizer decisions.

6.3.8Stage boundaries

Spark often splits execution into stages at shuffle dependencies.

Python
result_df = (
    df.filter(df.amount > 1000)
      .groupBy("customer_id")
      .sum("amount")
)

Stage 1

  1. Read input partitions.
  2. Filter records.
  3. Perform partial aggregation.
  4. Write shuffle data.

Stage 2

  1. Read shuffle data.
  2. Complete the aggregation.
  3. Produce the result.

Conceptual, not a guaranteed physical plan.

Why data engineers care

A 20-minute job might show Stage 1 at 2 minutes and Stage 2 at 17, with most of Stage 2 spent in a handful of slow tasks. That points to data skew, oversized shuffle partitions, or resource limits. Stage metrics find the problem; blindly enlarging the cluster doesn't.

6.3.9Task scheduling

With a stage of 100 tasks and 20 task slots, Spark runs about 20 tasks at a time and schedules more as slots free up. Total time depends on individual task duration, scheduling overhead, and resource availability.

Too few partitions

With only two partitions, a large cluster sits mostly idle: there aren't enough independent tasks.

Too many partitions

Hundreds of thousands of tiny partitions make scheduling and per-task overhead significant.

The right count depends on data size, workload, cluster resources, shuffle behavior, storage layout, and the query plan. There is no single ideal partition count.

6.4Spark Data Structures

Spark offers several abstractions for data. For modern Databricks data engineering, the DataFrame matters most.

6.4.1RDDs

An RDD (Resilient Distributed Dataset) is a distributed collection of elements processed in parallel, which is Spark's foundational abstraction.

Python
numbers_rdd = spark.sparkContext.parallelize(
    [1, 2, 3, 4, 5]
)

squared_rdd = numbers_rdd.map(
    lambda number: number * number
)

print(squared_rdd.collect())   # [1, 4, 9, 16, 25]

What does "resilient" mean?

RDDs track the dependencies between operations (lineage), so Spark can recompute lost partitions. This supports fault tolerance.

Why less common today?

RDDs give low-level control but lack the schema-aware SQL optimization DataFrames get. For structured data, DataFrames are generally preferable.

6.4.2DataFrames

A DataFrame is a distributed collection organized into named columns, similar in concept to a relational table, though its execution and storage behavior differ.

Python
data = [
    (101, "Rahul", "IT", 85000),
    (102, "Priya", "Finance", 95000),
    (103, "Arjun", "IT", 110000)
]

columns = ["employee_id", "employee_name", "department", "salary"]

df = spark.createDataFrame(data, columns)
display(df)

# Filter
it_employees = df.filter(df.department == "IT")

# Select
selected_df = df.select("employee_id", "employee_name", "salary")

# Group and aggregate
department_summary = df.groupBy("department").avg("salary")

# The same with SQL
df.createOrReplaceTempView("employees")

result = spark.sql("""
    SELECT
        department,
        AVG(salary) AS average_salary
    FROM employees
    GROUP BY department
""")

display(result)

The SQL and DataFrame APIs often express equivalent operations, and Spark optimizes both with the same SQL execution framework.

6.4.3Datasets and their availability across Spark APIs

Spark's Dataset API is a typed distributed collection API available in Scala and Java:

Scala
case class Employee(employeeId: Int, name: String, salary: Double)

val employees = Seq(
  Employee(101, "Rahul", 85000.0),
  Employee(102, "Priya", 95000.0)
).toDS()
What about PySpark?

PySpark does not expose the strongly typed Dataset[T] API. In PySpark you work with DataFrames, Row objects, Python collections, and Python classes for application logic. For this course, focus on DataFrames and Spark SQL.

6.4.4Schema

A schema defines a DataFrame's column names, types, and metadata.

Python
df.printSchema()
root

 |-- employee_name: string (nullable = true)
 |-- department: string (nullable = true)

Inferred types depend on the source data and how the DataFrame was created.

Python · explicit schema

    StructField("employee_id", IntegerType(), False),

Note

How nullability and malformed data are enforced depends on how the DataFrame is created and the operation performed. Validate source data rather than relying on schema declarations alone.

6.4.5Columns

A Spark Column represents a column expression. df.salary and df["salary"] both refer to the salary column.

Python
from pyspark.sql.functions import col

result_df = df.select(
    col("employee_name"),
    col("salary"),
    (col("salary") * 12).alias("annual_salary")
)

# Native column expression: the preferred pattern
df = df.withColumn(
    "annual_salary",
    col("salary") * 12
)
Why this matters

No Python loop over rows is involved. You build Spark expressions that the engine optimizes and runs distributed, which is the preferred approach for ordinary column transformations.

6.4.6Rows

A Spark Row represents one record.

Python
from pyspark.sql import Row

employee = Row(
    employee_id=101,
    employee_name="Rahul",
    salary=85000
)

print(employee.employee_name)

# Retrieve a small sample to the driver
sample_rows = df.take(5)

for row in sample_rows:
    print(row)

Retrieving rows moves data from distributed processing into the driver. Use take() or limit() for small samples, never to fetch an entire large dataset.

6.4.7Partitions

A partition is a logical division of a distributed dataset, processed by tasks.

Python
print(df.rdd.getNumPartitions())

Useful for learning, but inspecting partitions via the RDD interface is no reason to redesign a DataFrame pipeline around RDDs. On compute that restricts RDD access, look at the Spark UI or query profile instead.

Partitions influence parallelism, task count, shuffle behavior, data distribution, and read/write performance. Too few underuse resources; too many add scheduling overhead.

Partition count versus file count

A DataFrame has some number of in-memory partitions; a write can produce a different number of files; and table optimization can reorganize files later. One DataFrame partition doesn't always equal one storage file.

6.5Spark Performance Basics

The goal isn't memorizing tuning parameters. It's understanding why a query is expensive and which change is likely to help.

6.5.1Partitioning

Spark partitions data during ingestion, transformation, shuffling, and writing.

Python
df = spark.read.parquet("/path/to/sales")

print(df.rdd.getNumPartitions())   # e.g. 200

# Redistribute by a column (may shuffle)
partitioned_df = df.repartition("customer_id")

200 partitions doesn't mean exactly 200 files, or that 200 tasks always run simultaneously. Repartitioning by a column helps when later operations benefit from that distribution, but it may introduce a shuffle.

Spark execution partitions

How data is divided for processing.

Storage partitioning

How persisted data is organized by column values, e.g. a Delta table partitioned by transaction date. This doesn't fix the execution partitioning of every DataFrame read from it.

6.5.2repartition()

repartition() changes the number of partitions and/or how records are distributed.

Python
# Request 20 partitions
repartitioned_df = df.repartition(20)

# 20 partitions distributed by customer_id
repartitioned_df = df.repartition(20, "customer_id")

Useful for

  • Increasing parallelism.
  • Redistributing skewed or uneven data.
  • Preparing for key-based workloads.
  • Adjusting partition count before a large write.
The cost

Repartitioning generally requires a shuffle. Don't call it repeatedly without a clear reason.

6.5.3coalesce()

coalesce() reduces the number of partitions, generally without a full shuffle.

Python
# 100 partitions -> 10
smaller_df = df.coalesce(10)

Handy for reducing many small partitions before a write when the existing layout is otherwise fine. Reducing too aggressively creates uneven work and limits parallelism.

Featurerepartition()coalesce()
Changes partition countYesCommonly reduces it
Full redistributionGenerally shufflesGenerally avoids a full shuffle
Can increase partitionsYesNo (standard DataFrame coalesce)
Can reduce partitionsYesYes
Common useRedistribute data or adjust parallelismReduce partitions with less data movement
Avoid automatic coalesce(1)

Forcing all output through one partition to get a single file creates a bottleneck on large datasets.

6.5.4Shuffle

Operations that may shuffle: groupBy(), distinct(), repartition(), many joins, some sorts, and window functions that need redistribution or sorting.

Python
summary_df = (
    df.groupBy("department")
      .sum("salary")
)

Reducing unnecessary shuffle work

  • Filter out rows you don't need.
  • Select only required columns.
  • Avoid unnecessary repartitioning.
  • Choose suitable join strategies.
  • Investigate data skew.
  • Review the physical plan.
  • Measure actual shuffle metrics.

The optimizer often pushes filters and column selection earlier anyway, so write clear queries and verify the plan.

6.5.5Data skew

Data skew happens when some partitions hold far more data or work than others.

Customer IDRecords
Customer A500,000
Customer B100,000
All others combined400,000

Partitioned by customer ID, Customer A may dominate one partition, and that task runs much longer than the rest. Because a stage usually finishes only when all its tasks finish, a few slow tasks delay the whole stage.

How to detect skew

  • A few tasks with much longer durations.
  • Large differences in task input sizes.
  • Uneven shuffle read sizes.
  • High spill in specific tasks.
  • A few partitions much larger than the rest.

Common approaches

  • Use Adaptive Query Execution.
  • Verify skew-join handling.
  • Reduce data before joins.
  • Broadcast a genuinely small dimension.
  • Salt severely skewed keys.
  • Revisit the data model or key distribution.
What is salting?

Salting appends an extra value to a heavily skewed key so its work splits across multiple partitions. It adds complexity and joins may need compensating logic, so use it only when skew is measured and simpler fixes fall short.

6.5.6Broadcast joins

A broadcast join sends a small dataset to every executor, so the large dataset can be joined locally without shuffling the large side.

Python
from pyspark.sql.functions import broadcast

# sales: 100 million rows
# departments: 50 rows
joined_df = sales_df.join(
    broadcast(departments_df),
    on="department_id",
    how="left"
)
  departments (small)
          |
   copied to every executor
   /        |         \
Exec 1    Exec 2    Exec 3
sales     sales     sales
part      part      part
   \        |         /
  joined locally:
  no large-side shuffle

Before broadcasting, consider

  • Its size in memory.
  • The number of executors.
  • Available memory.
  • Concurrent tasks.
  • Whether Spark already picks the right strategy.
Important warning

Don't broadcast a table just because it has fewer rows than the other. A small row count doesn't guarantee a small memory footprint. Spark may broadcast automatically, so check the plan before forcing it.

6.5.7Caching and persistence

Python
filtered_df = df.filter(
    df.amount > 1000
)

filtered_df.cache()      # mark for caching
filtered_df.count()      # action materializes the cache

# ...later actions may reuse it...

filtered_df.persist()    # choose a storage level (default shown)

filtered_df.unpersist()  # release when no longer needed

persist() lets you choose a storage level. For PySpark DataFrames, caching is commonly memory-and-disk, but check the behavior of your runtime.

Best practice

Cache when an expensive DataFrame is reused repeatedly, recomputing costs more than storing, and it fits available resources. Don't cache everything; cache only for a measurable benefit.

Some serverless compute doesn't support cache()/persist() in the same way. Check what your compute type allows.

6.5.8Catalyst optimizer

Catalyst is Spark SQL's query optimization framework. It transforms SQL and DataFrame queries before execution.

Python
result_df = (
    df.filter(df.amount > 1000)
      .select("customer_id", "amount")
      .groupBy("customer_id")
      .sum("amount")
)

result_df.explain("extended")

Catalyst may push filters toward sources, remove unnecessary columns, simplify expressions, reorder suitable operations, and choose physical operators from available information.

PlanDescribes
Logical planWhat the query should do
Optimized logical planA logically optimized version of the query
Physical planHow it will run, using physical operators
Important lesson

A readable query isn't necessarily executed in the order you wrote it. Spark transforms the plan while preserving the query's meaning.

6.5.9Adaptive Query Execution (AQE)

AQE lets Spark SQL revise parts of its physical plan using runtime statistics. Spark might first plan a shuffle join, then discover at runtime that one side is small enough to broadcast.

AQE can help with

  • Coalescing small shuffle partitions.
  • Handling certain skewed joins.
  • Revising join strategies.

Useful because the optimizer can't know exact sizes and distributions before running.

Verify whether AQE helped

  1. Run the query.
  2. Inspect the execution plan.
  3. Review the SQL or Spark UI.
  4. Compare initial and final plans.
  5. Examine shuffle metrics and task durations.
  6. Compare times under equal conditions.
Python
spark.conf.get(
    "spark.sql.adaptive.enabled",
    "not-set"
)

AQE is enabled by default in many modern Spark environments, but the effective setting depends on runtime and configuration. Don't change production settings without understanding the workload and your workspace's policies, and don't assume AQE speeds up every query.

6.6Hands-on Exercise: Process One Million Records

Create one million synthetic sales records and use Spark to filter, group, join, inspect plans, and compare repartitioning, coalescing, caching, and broadcast joins. No external files needed.

Environment

A Databricks Python notebook with suitable compute. It also runs locally with PySpark installed, though resources and performance differ. On serverless or shared compute, df.rdd and cache() may be restricted; use the Spark UI or query profile to see partitions and skip the caching step if needed.

Step 1: Generate one million sales records

Python
from pyspark.sql import functions as F

number_of_records = 1_000_000

sales_df = (
    spark.range(number_of_records)
    .withColumnRenamed("id", "transaction_id")
    .withColumn(
        "customer_id",
        (F.col("transaction_id") % 100_000 + 1).cast("int")
    )
    .withColumn(
        "product_id",
        (F.col("transaction_id") % 1_000 + 1).cast("int")
    )
    .withColumn(
        "quantity",
        (F.col("transaction_id") % 10 + 1).cast("int")
    )
    .withColumn(
        "amount",
        F.round(
            F.col("quantity") * (
                (F.col("product_id") % 100) + F.lit(10)
            ).cast("double"),
            2
        )
    )
)

sales_df.printSchema()
display(sales_df.limit(10))

record_count = sales_df.count()   # action
print(f"Total records: {record_count:,}")
# Total records: 1,000,000

The data is deterministic, which makes it good for comparing plans and checking expected results.

Step 2: Inspect partitions

Python
partition_count = sales_df.rdd.getNumPartitions()

print(f"Number of partitions: {partition_count}")

The count depends on your environment. It hints at how work divides into tasks; more isn't always better.

Step 3: Filter records

Python
high_value_sales_df = sales_df.filter(
    F.col("amount") > 100
)

high_value_sales_df.explain("extended")

high_value_count = high_value_sales_df.count()
print(f"High-value records: {high_value_count:,}")

Observe: Is there a Filter in the plan? How many partitions are involved? Is there a shuffle? How long did the action take? Filtering alone doesn't normally need a full shuffle.

Step 4: Group and aggregate

Python
customer_summary_df = (
    sales_df
    .groupBy("customer_id")
    .agg(
        F.count("*").alias("transaction_count"),
        F.sum("amount").alias("total_sales"),
        F.avg("amount").alias("average_sales")
    )
)

customer_summary_df.explain("extended")

display(
    customer_summary_df.orderBy(
        F.desc("total_sales")
    ).limit(20)
)

Spark reads input partitions, computes partial aggregates where possible, redistributes records as needed, combines partial results, and produces the summary. Partial aggregation reduces the data shuffled.

Step 5: Create a customer dimension table

Python
customers_df = (
    spark.range(100_000)
    .withColumnRenamed("id", "customer_number")
    .withColumn(
        "customer_id",
        (F.col("customer_number") + 1).cast("int")
    )
    .withColumn(
        "customer_name",
        F.concat(
            F.lit("Customer_"),
            F.col("customer_id").cast("string")
        )
    )
    .withColumn(
        "customer_segment",
        F.when(F.col("customer_id") % 3 == 0, F.lit("Premium"))
         .when(F.col("customer_id") % 3 == 1, F.lit("Standard"))
         .otherwise(F.lit("Basic"))
    )
    .drop("customer_number")
)

display(customers_df.limit(10))

Step 6: Join sales with customers

Python
sales_with_customers_df = sales_df.join(
    customers_df,
    on="customer_id",
    how="inner"
)

sales_with_customers_df.explain("extended")

print("Joined record count:", sales_with_customers_df.count())
# Expected: 1000000 (every transaction has a matching customer)

Inspect: broadcast or shuffle join? An Exchange operator? Input sizes? How much is shuffled? Are tasks even? The strategy depends on the optimizer, statistics, and configuration.

Step 7: Experiment with a broadcast join

Python
broadcast_join_df = sales_df.join(

    how="inner"

broadcast_join_df.explain("extended")

A controlled experiment

This isn't a blanket recommendation to broadcast a 100,000-row table. For real workloads, compare the smaller table's memory footprint with available resources; a too-large broadcast can perform poorly or fail.

Step 8: Experiment with repartition

Python
print("Original partitions:", sales_df.rdd.getNumPartitions())

Repartition by key only if a later operation benefits from the new distribution.

Step 9: Experiment with coalesce

Python
coalesced_df = sales_df.coalesce(5)

print("Coalesced partitions:", coalesced_df.rdd.getNumPartitions())

With at least five original partitions, you'll get five. With fewer, coalesce(5) doesn't increase the count. repartition(20) requests 20 and generally shuffles; coalesce(5) reduces to 5 without a full shuffle. They serve different purposes.

Step 10: Experiment with caching

Python
high_value_sales_df.cache()

Step 12: Create a final sales summary

Python
final_summary_df = (
    sales_df
    .join(customers_df, on="customer_id", how="inner")
    .groupBy("customer_segment")
    .agg(
        F.count("*").alias("transaction_count"),
        F.sum("amount").alias("total_sales"),
        F.avg("amount").alias("average_transaction_amount"),

    .orderBy("customer_segment")

6.7Common Spark Mistakes

MistakeDo this instead
1. df.collect() on large dataUse distributed transformations; aggregate before collecting a small result.
2. Calling count() unnecessarilycount() and display() each trigger computation. Don't count large DataFrames just to check progress.
3. Repartitioning every DataFrameRepartition only for a clear performance or distribution need.
4. coalesce(1) on large dataUse a single partition only for small data with a real requirement.
5. Caching everythingCache only reused, expensive results.
6. Assuming every join shufflesBroadcast and other strategies avoid large-side shuffles; check the plan.
7. Assuming more workers = fasterSkew, shuffle volume, source throughput, and sequential work all limit scaling.
8. Confusing partitions with filesExecution partitions and output files are related but different.
9. Ignoring data typesWrong types cause conversions, wrong results, or failures. Use explicit schemas where appropriate.
10. Optimizing without measurementsSee below.
Optimize methodically
  1. Inspect the plan.
  2. Measure the baseline.
  3. Identify the bottleneck.
  4. Make one targeted change.
  5. Measure again.
