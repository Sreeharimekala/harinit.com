13.1Fundamentals

13.1.1What Is a Declarative Pipeline?

An e-commerce company wants to read orders, validate them, remove duplicates, calculate sales metrics, and store the results for Power BI. Traditionally you write code for each step and manage the run order, scheduling, retries, and dependencies yourself, as you did in Chapters 11 and 12.

A declarative pipeline flips this around: you define the datasets you want and how they relate, and the framework manages execution.

Python · traditional
from pyspark.sql import functions as F

orders = spark.read.table("retail_dev.bronze.orders")

valid_orders = orders.filter(
    F.col("order_id").isNotNull()
)

deduplicated_orders = valid_orders.dropDuplicates(
    ["order_id"]
)

(deduplicated_orders.write
    .format("delta")
    .mode("overwrite")
    .saveAsTable("sales_silver"))

# ...plus scheduling, dependencies,
# retries, and orchestration
SQL · declarative
CREATE OR REFRESH MATERIALIZED VIEW valid_orders AS
SELECT *
FROM orders
WHERE order_id IS NOT NULL;

-- The framework decides when and how
-- to build and refresh this dataset.

The declarative snippet is a single dataset definition; a complete pipeline also needs a source and pipeline configuration.

What it provides

  • Declarative transformations.
  • Automatic dependency management.
  • Streaming and batch processing.
  • Built-in data-quality expectations.
  • Incremental processing.
  • Event logs for every run.
  • Managed updates and failure recovery.
Use caseExample

13.1.2Declarative Versus Imperative Programming

Imperative = how

You define each step and control execution: read, filter, dedupe, write.

orders = spark.read.table(...)
filtered = orders.filter(...)
deduped = filtered.dropDuplicates(...)
deduped.write.saveAsTable(...)

Declarative = what

You define what the result should contain.

CREATE OR REFRESH MATERIALIZED VIEW silver_orders AS
SELECT DISTINCT *
FROM bronze_orders
WHERE order_id IS NOT NULL;

DISTINCT removes identical rows, not duplicate order IDs. Business-key deduplication needs an explicit rule (see the project).

Main focusHow to process dataWhat data should look like

Data qualityCustom logicBuilt-in expectations
Incremental processingDesign it yourselfSupported for eligible patterns
MonitoringDepends on your frameworkIntegrated event log
RecoveryApplication logicManaged updates and recovery
ExamplePySpark batch scriptLakeflow dataset definitions
Does declarative mean no code?

No. You still write SQL or Python. The difference is that you describe datasets and relationships instead of implementing the whole orchestration lifecycle. You still need to understand data modeling, schema changes, data quality, and performance.

13.1.5Pipeline Configuration

Configuration defines how a pipeline runs and where its datasets live: name, default catalog and schema, compute (serverless or classic), triggered or continuous mode, development or production mode, configuration parameters, notifications, and permissions.

Development vs production mode

Development: faster iteration; compute is reused between updates and failures aren't retried automatically, so you see errors quickly.

Production: reproducibility, controlled deployment, automatic retries, and strict access control.

Keep environments out of code

Don't hard-code environment-specific paths or credentials in transformation code. Use pipeline parameters (13.5.1).

13.1.6Data Dependencies

A dataset depends on another when it reads that dataset. The framework reads those references and works out the run order. You never write "run Silver, then Gold".

SQL
CREATE OR REFRESH MATERIALIZED VIEW orders_silver AS
SELECT order_id, customer_id, amount
FROM orders_bronze
WHERE order_id IS NOT NULL;

CREATE OR REFRESH MATERIALIZED VIEW sales_gold AS
SELECT
    COUNT(*) AS order_count,
    SUM(amount) AS total_sales
FROM orders_silver;
Derived automatically:

orders_bronze
      |
      v
orders_silver
      |
      v
sales_gold

If orders_silver fails, sales_gold can't refresh correctly. The update status and graph show which downstream datasets were affected.

Best practices

  1. Keep transformations logically separated.
  2. Avoid unnecessary dependencies.
  3. Use meaningful dataset names.
  4. Validate schemas at important boundaries.
  5. Understand the graph before changing upstream definitions.

13.1.7Pipeline Execution

Triggered

Processes available work, then completes. For daily batches, hourly transforms, scheduled refreshes, periodic reporting.

1:00 AM  Ingest source files
1:05 AM  Validate Silver data
1:15 AM  Refresh Gold tables
1:20 AM  Update completes

Continuous

Stays active and processes new data as it arrives. For near-real-time analytics, continuous events, streaming ingestion, low-latency transforms. Compute keeps running, so cost differs.

FeatureTriggeredContinuous
ExecutionRuns an update and completesRemains active
Typical useBatch and scheduled processingOngoing data processing
Compute lifecycleTied to the updateMay stay active between events
LatencyTrigger frequency + run timeLower latency possible
CostSuits periodic workloadsConsider always-on compute cost
Key takeaway

Choose the mode by required freshness, source characteristics, operational needs, and cost.

13.2Building Pipelines

13.2.1Creating a Pipeline

You need

  • A Databricks workspace.
  • Permission to create pipelines.
  • Access to the target catalog and schema.
  • Compute (serverless is simplest).
  • Source data, or permission to read it.

In the workspace

  1. Open Jobs & Pipelines → Create → ETL pipeline.
  2. Name it and choose the default catalog and schema.
  3. Add SQL or Python source files.
  4. Configure compute and execution mode.
  5. Validate (Dry run), then run an update.
  6. Inspect the graph and output datasets.

UI labels change between releases.

13.2.2SQL-Based Pipelines

SQL suits transformations expressed as relational operations: filtering, joins, aggregations, window functions, standardization, and data-quality rules.

SQL · Silver
CREATE OR REFRESH MATERIALIZED VIEW orders_silver
AS
SELECT
    order_id,
    customer_id,
    order_date,
    amount,
    UPPER(TRIM(status)) AS status,
    updated_at
FROM retail_dev.bronze.orders_raw
WHERE order_id IS NOT NULL
  AND customer_id IS NOT NULL
  AND amount >= 0;
SQL · Gold
CREATE OR REFRESH MATERIALIZED VIEW sales_gold
AS
SELECT
    order_date,
    status,
    COUNT(*) AS order_count,
    SUM(amount) AS total_sales,
    AVG(amount) AS average_order_value
FROM orders_silver
GROUP BY order_date, status;
SQL · completed only
CREATE OR REFRESH MATERIALIZED VIEW completed_sales_gold
AS
SELECT
    order_date,
    COUNT(*) AS completed_order_count,
    SUM(amount) AS completed_sales
FROM orders_silver
WHERE status = 'COMPLETED'
GROUP BY order_date;

13.2.3Python-Based Pipelines

Python combines PySpark transformations with the pipeline API. For new work, use from pyspark import pipelines as dp, not the legacy import dlt.

DecoratorPurpose
@dp.tableDefines a table; returning a streaming DataFrame creates a streaming table
@dp.materialized_viewDefines a materialized view
@dp.temporary_viewDefines a temporary view used within the pipeline
@dp.expectRecords quality metrics, keeps the rows
@dp.expect_or_dropDrops violating rows
@dp.expect_or_failFails the update on violation
Python
from pyspark import pipelines as dp
from pyspark.sql import functions as F


@dp.materialized_view(name="orders_silver")
def orders_silver():
    return (
        spark.read.table("retail_dev.bronze.orders_raw")
        .filter(F.col("order_id").isNotNull())
        .filter(F.col("customer_id").isNotNull())
        .filter(F.col("amount") >= 0)
        .withColumn("status", F.upper(F.trim(F.col("status"))))
    )


@dp.materialized_view(name="sales_gold")
def sales_gold():
    return (
        spark.read.table("orders_silver")
        .groupBy("order_date", "status")
        .agg(
            F.count("*").alias("order_count"),
            F.sum("amount").alias("total_sales"),
            F.avg("amount").alias("average_order_value")
        )
    )
Pipeline files aren't normal notebooks
  • spark is provided by the pipeline runtime.
  • Each definition returns a DataFrame; never call saveAsTable() or .write for a pipeline dataset.
  • You can't run these cells interactively like a notebook; run them through a pipeline update.
  • Inspect outputs afterwards from a separate notebook or SQL query.
RequirementRecommended

Reusable relational transformationsSQL or Python

13.2.4Streaming Tables

A streaming table processes each input record once, tracking what it has already seen rather than rebuilding everything. It's ideal for ingesting files that keep arriving (orders_001.json, orders_002.json, …).

Python
from pyspark import pipelines as dp


@dp.table(name="orders_bronze")
def orders_bronze():
    return (
        spark.readStream
        .format("cloudFiles")
        .option("cloudFiles.format", "json")
        .schema("""
            order_id STRING,
            customer_id STRING,
            order_date DATE,
            amount DECIMAL(18,2),
            status STRING,
            updated_at TIMESTAMP
        """)
        .load("/Volumes/retail_dev/bronze/orders_json/")
    )
SQL equivalent
CREATE OR REFRESH STREAMING TABLE orders_bronze
AS
SELECT *
FROM STREAM read_files(
    '/Volumes/retail_dev/bronze/orders_json/',
    format => 'json',
    schema => 'order_id STRING, customer_id STRING,
               order_date DATE, amount DECIMAL(18,2),
               status STRING, updated_at TIMESTAMP'
);
Auto Loader, managed for you

This is Auto Loader from Chapter 12, but inside a pipeline you don't set checkpointLocation or cloudFiles.schemaLocation. The pipeline manages that state. In SQL, STREAM read_files(...) uses Auto Loader too.

13.2.5Materialized Views

A materialized view stores its query result and keeps it up to date through managed refreshes. A report that sums 500 million orders on every open is expensive; a materialized view stores the daily totals and maintains them as the source changes.

SQL
CREATE OR REFRESH MATERIALIZED VIEW daily_sales
AS
SELECT
    order_date,
    SUM(amount) AS total_sales,
    COUNT(*) AS order_count
FROM orders_silver
GROUP BY order_date;
FeatureRegular viewMaterialized view
Stores resultsGenerally noYes
Evaluates queryWhen queriedDuring managed refresh
Query performanceDepends on underlying queryCan speed up repeated analytics
StorageMinimalStores maintained results
MaintenanceRuns against underlying dataPlatform maintains results

Common uses: daily sales, customer purchase summaries, product metrics, monthly financials, Power BI datasets. The actual benefit depends on the query and refresh behavior.

13.2.6Temporary Views

A temporary view is a reusable intermediate result inside the pipeline, so several downstream datasets don't repeat the same logic. It is not published as a table.

Python
from pyspark import pipelines as dp
from pyspark.sql import functions as F


@dp.temporary_view(name="valid_orders_temp")
def valid_orders_temp():
    return (
        spark.read.table("retail_dev.bronze.orders_raw")
        .filter(F.col("order_id").isNotNull())
        .filter(F.col("amount") >= 0)
    )


@dp.materialized_view(name="sales_gold")
def sales_gold():
    return (
        spark.read.table("valid_orders_temp")
        .groupBy("order_date")
        .agg(F.sum("amount").alias("total_sales"))
    )
Important distinction

Don't treat a temporary view as a durable Bronze, Silver, or Gold table, and don't assume it's cached. Use a streaming table or materialized view when you need persistence.

13.2.7Incremental Processing

Full load:
  Source records:     100 million
  Records processed:  100 million

Incremental load:
  Existing records:   100 million
  New today:              200,000
  Records processed:      200,000

Incremental patterns in Lakeflow

  • Streaming ingestion and Auto Loader.
  • Streaming tables.
  • Incremental materialized-view refresh (where supported).
  • AUTO CDC processing.
SQL · concept only
SELECT *
FROM source_orders
WHERE updated_at > :last_successful_watermark;

Lakeflow doesn't fill in this placeholder for you. Watermarks need careful handling of late records, old timestamps, deletes, and retries (Chapter 12). Streaming tables avoid the problem by tracking progress themselves.

Not always incremental

Declaring a materialized view doesn't guarantee incremental refresh. Depending on the query and source changes, the framework may recompute fully. (On serverless pipelines, incremental refresh is attempted when the query supports it.)

13.3Data Quality

A pipeline can run successfully and still produce wrong results: missing IDs, duplicates, negative amounts, invalid customers or dates, unsupported statuses. Expectations validate records during processing.

13.3.1Data Quality Expectations

An expectation is a Boolean condition each record should satisfy, e.g. order_id IS NOT NULL, amount >= 0, status IN ('COMPLETED', 'CANCELLED', 'PENDING').

SQLPythonOn violation
EXPECT (…)@dp.expectRecord the metric, keep the row
EXPECT (…) ON VIOLATION DROP ROW@dp.expect_or_dropDrop the row
EXPECT (…) ON VIOLATION FAIL UPDATE@dp.expect_or_failFail the update

CREATE OR REFRESH MATERIALIZED VIEW orders_strict (
    CONSTRAINT valid_order_id
        EXPECT (order_id IS NOT NULL) ON VIOLATION FAIL UPDATE,
    CONSTRAINT valid_amount
        EXPECT (amount >= 0) ON VIOLATION FAIL UPDATE
)
AS
SELECT *
FROM retail_dev.bronze.orders_raw;
PolicyUse when
FailBad records cause financial discrepancies; the data contract is broken; a critical dataset can't tolerate invalid rows; continuing would mislead downstream users
DropThe rule is well understood; excluding rows is acceptable; invalid data is monitored or captured separately

13.3.6Handling Invalid Source Data

Four approaches

  1. Reject: exclude from Silver.
  2. Quarantine: keep invalid records in a separate dataset for correction and replay.
  3. Fail: stop on critical violations.
  4. Correct: apply a deterministic, approved fix such as UPPER(TRIM(status)), which turns completed, Completed, and COMPLETED into one value. Never "fix" ambiguous values.

13.4.1Change Data Capture (CDC)

customer_idcustomer_namecity
C101RaviHyderabad

Initial data. Then C101 moves to Bengaluru, and C102 is deleted.

customer_idoperationcity

CDC applies just these changes instead of reloading the table. A robust implementation needs a stable business key, the operation type, a reliable ordering (sequence or commit time), and handling for duplicate events, late changes, deletes, and schema evolution.

13.4.2Slowly Changing Dimensions (SCD)

When Ravi (C101) moves from Hyderabad to Bengaluru, what should the customer dimension show?

SCD Type 1: overwrite

customer_idnamecity
C101RaviBengaluru

The old city is gone. Use when history isn't needed.

SCD Type 2: keep history

citystartendcurrent
Hyderabad2025-01-012026-07-01false
Bengaluru2026-07-01NULLtrue

A new row per change. Use when reports must show history ("sales by the city the customer lived in at the time").

13.4.3AUTO CDC INTO

AUTO CDC (formerly APPLY CHANGES INTO) applies a change feed to a target streaming table. It orders changes by a sequence column, keeps the latest state, handles deletes, and can maintain SCD Type 1 or 2 for you. That's everything you'd otherwise hand-write with MERGE and window functions in Chapter 12.

Source change records
        |
        v
  Order by sequence
        |
        v
 Apply insert / update
     / delete
        |
        v
   Target table
customer_idcustomer_namecitysequence
C101RaviHyderabad1
C102PriyaChennai2
C101RaviBengaluru3

Type 1 result: C101 → Bengaluru (sequence 3 wins), C102 → Chennai.

Python · SCD Type 1 with deletes
from pyspark import pipelines as dp
from pyspark.sql import functions as F

dp.create_streaming_table(name="customers_current")

dp.create_auto_cdc_flow(
    target="customers_current",
    source="customer_changes",               # a streaming dataset of change rows
    keys=["customer_id"],
    sequence_by=F.col("sequence"),
    apply_as_deletes=F.expr("operation = 'DELETE'"),
    except_column_list=["operation", "sequence"],
    stored_as_scd_type=1
)
SQL · SCD Type 2
CREATE OR REFRESH STREAMING TABLE customers_history;

CREATE FLOW customers_history_flow AS
AUTO CDC INTO customers_history
FROM STREAM(customer_changes)
KEYS (customer_id)
APPLY AS DELETE WHEN operation = 'DELETE'
SEQUENCE BY sequence
COLUMNS * EXCEPT (operation, sequence)
STORED AS SCD TYPE 2;

For SCD Type 2, the target automatically gets __START_AT and __END_AT columns; the current row is the one where __END_AT IS NULL. I added the delete handling and column exclusion that the original example left out.

Important considerations
  • The source needs a reliable key and sequence field, and sequence values must reflect true change order.
  • Deletes must be represented in the feed to be applied.
  • Plan for duplicate and late-arriving changes.
  • Source change format and target schema must be compatible.
  • Check current docs for the options your runtime supports.

13.4.4Incremental Transformations

With 200 million historical transactions and 100,000 new ones a day, recomputing everything daily is wasteful. A streaming ingestion table processes just each day's new files (100,000 → 120,000 → 95,000), and a materialized view like SELECT order_date, SUM(amount) … GROUP BY order_date may be maintained incrementally when supported.

Most valuable when

  • History is large.
  • Changes are small relative to the total.
  • The source identifies changes reliably.
  • Transformations support incremental maintenance.

Less benefit when

  • Most historical records change often.
  • The transformation needs global recomputation.
  • The source can't reliably identify changes.

13.4.5Pipeline Event Logs

The event log records update status, dataset progress, expectation results, errors, and operational metadata. It's especially useful when the visible error message doesn't explain the root cause.

SQL · starting points
-- Recent events (pipeline ID is in the pipeline's details panel)
SELECT timestamp, event_type, level, message
FROM event_log('<pipeline-id>')
ORDER BY timestamp DESC
LIMIT 100;

-- Errors only
SELECT timestamp, message, details
FROM event_log('<pipeline-id>')
WHERE level = 'ERROR'
ORDER BY timestamp DESC;

-- Data-quality results per dataset
SELECT
    timestamp,
    origin.flow_name,
    details:flow_progress.data_quality.expectations
FROM event_log('<pipeline-id>')
WHERE event_type = 'flow_progress'
  AND details:flow_progress.data_quality IS NOT NULL
ORDER BY timestamp DESC;

details is JSON; the : syntax extracts nested fields. Availability and schema of event_log() can vary, so start with SELECT * to inspect the columns.

Investigating a failed update (e.g. schema mismatch)

  1. Identify the failed update.
  2. Find the related error event.
  3. Inspect the affected dataset.
  4. Identify the incompatible source field.
  5. Correct the schema or transformation.
  6. Rerun the update.
  7. Verify downstream datasets complete.

13.5.6Performance Tuning

SQL · select only what you need
-- Instead of
SELECT * FROM orders_silver;

-- Prefer
SELECT order_id, order_date, amount
FROM orders_silver;
SQL · filter early
SELECT order_date, SUM(amount) AS total_sales
FROM orders_silver
WHERE status = 'COMPLETED'
GROUP BY order_date;
  1. Avoid unnecessary shuffles: large joins, GROUP BY, DISTINCT. Check plans and metrics.
  2. Choose good layouts: liquid clustering, file sizes, data skipping, statistics. Don't partition on high-cardinality columns.
  3. Use incremental processing where eligible.
  4. Avoid needless full recomputation: does the requirement really need all history?
  5. Monitor skew: a few heavy keys slow joins and aggregations.
  6. Right-size compute for volume, complexity, concurrency, frequency, and latency. Bigger isn't always proportionally faster.

Step 4: Create the Silver dataset

Add to the same pipeline file. It reads the Bronze streaming table in batch mode (no STREAM):

SQL · pipeline file
CREATE OR REFRESH MATERIALIZED VIEW orders_silver (
    CONSTRAINT valid_order_id
        EXPECT (order_id IS NOT NULL) ON VIOLATION DROP ROW,
    CONSTRAINT valid_customer_id
        EXPECT (customer_id IS NOT NULL) ON VIOLATION DROP ROW,
    CONSTRAINT valid_amount
        EXPECT (amount >= 0) ON VIOLATION DROP ROW,
    CONSTRAINT valid_order_status
        EXPECT (status IN ('COMPLETED', 'CANCELLED', 'PENDING'))
        ON VIOLATION DROP ROW
)
COMMENT 'Validated orders, one row per order_id (latest version)'
AS
WITH normalized_orders AS (
    SELECT
        order_id,
        customer_id,
        order_date,
        amount,
        UPPER(TRIM(status)) AS status,
        updated_at
    FROM orders_bronze
),
ranked_orders AS (
    SELECT
        *,
        ROW_NUMBER() OVER (
            PARTITION BY order_id
            ORDER BY updated_at DESC NULLS LAST
        ) AS row_num
    FROM normalized_orders
    WHERE order_id IS NOT NULL
)
SELECT order_id, customer_id, order_date, amount, status, updated_at
FROM ranked_orders
WHERE row_num = 1;

What it does

  • Normalizes status (" cancelled " → CANCELLED).
  • Deduplicates: one row per order_id, the latest updated_at wins.
  • Validates: the expectations drop rows that break any rule and record the counts.
Notes

The WHERE order_id IS NOT NULL keeps all null-ID rows from being ranked together as one "order"; the expectation still records them. Ranking runs before validation, so if an order's latest version is invalid, the order is dropped rather than falling back to an older version. If two versions share a timestamp, add a tie-breaker such as a source sequence number.

13.8Common Interview Questions

Try answering each before revealing the answer.

Q1. What is Lakeflow Spark Declarative Pipelines?
A Databricks capability (formerly Delta Live Tables) for defining and managing data pipelines with declarative SQL and Python dataset definitions; the framework handles dependencies, execution, incremental processing, and recovery.
Q2. Streaming table vs materialized view?
A streaming table processes each new source record once (ideal for ingestion and append-style flows); a materialized view stores a query result that the platform keeps correct through managed refreshes (ideal for joins and aggregations).
Q3. Bronze, Silver, and Gold?
Bronze preserves incoming data; Silver holds validated, standardized data; Gold holds business-ready datasets and aggregations.
Q4. What are data-quality expectations?
Boolean rules declared on a dataset that validate each record, with a policy to track, drop, or fail on violations; results are recorded in the event log.
Q5. Dropping a record vs failing an update?
Dropping excludes the violating record and continues; failing stops the update when a violation occurs.
Q6. What is incremental processing?
Processing only new or changed data rather than recomputing all history.
Q7. What is CDC?
Change Data Capture identifies inserts, updates, and deletes in source data and applies them downstream, in Lakeflow via AUTO CDC.
Q8. What is SCD Type 1?
Overwrites dimension values without keeping previous versions.
Q9. What is SCD Type 2?
Keeps historical versions as separate rows, with effective start/end timestamps and a way to identify the current row.
Q10. What is the pipeline event log for?
Operational information about execution, data quality, errors, and related events, queryable with event_log().
Q11. How do you troubleshoot a pipeline failure?
Inspect the failed update, review error events, identify the affected dataset via the graph, validate its source and logic, fix, rerun, and reconcile outputs.
Q12. Does a materialized view always refresh incrementally?
No. It depends on the query, source changes, and supported incrementalization; it may fully recompute.
Q13. Why preserve Bronze data?
It's the raw reference for audits, source investigations, replay, and validating downstream transformations.
Q14. Why does business-key deduplication matter?
Multiple records for the same order or entity must be resolved by a defined rule (e.g. latest version wins). DISTINCT only removes identical rows.
Q15. What should be monitored in production?
Update status, duration, freshness, data quality, record counts, duplicates, source ingestion, and downstream business metrics.
Q16. Why can't the streaming Silver use row_number()?
Ranking window functions over an unbounded stream aren't supported in Structured Streaming. Use a batch materialized view, streaming dedup with a watermark, or AUTO CDC.
