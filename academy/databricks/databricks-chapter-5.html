Python Fundamentals for Databricks

The Python you actually need as a Databricks data engineer: core syntax and collections, functions, file and JSON processing, error handling, logging, dates, APIs, configuration, and tests, ending with a small ingestion pipeline that loads into a Delta table.

By the end of this chapter you will be able to
  • Understand Python syntax, variables, data types, and operators.
  • Work with strings, lists, tuples, sets, and dictionaries.
  • Write conditional statements, loops, and reusable functions.
  • Read and process CSV and JSON files.
  • Handle missing values, invalid records, and exceptions.
  • Use logging to monitor scripts and data-processing tasks.
  • Work with dates, APIs, configuration files, and environment variables.
  • Write reusable transformation functions and basic unit tests.
  • Build a small ingestion process that prepares JSON records for a Databricks table.
Important

You don't need to master every Python feature before learning Databricks. Focus on the skills you'll use in notebooks, PySpark transformations, ingestion pipelines, and data-quality checks. Examples throughout use practical ETL scenarios.

5.1Python Basics

5.1.1What is Python?

Python is a general-purpose language used for data engineering, data analysis, automation, API integration, machine learning, file processing, and application development. In Databricks it's commonly used with PySpark to process large datasets across many machines.

A typical Python job in Databricks

  1. Read a configuration file.
  2. Identify source and target tables.
  3. Read data using Spark.
  4. Apply transformations.
  5. Validate records.
  6. Write results to Delta tables.
  7. Log the execution status.
Division of labour

Python handles the programming logic; Spark handles distributed data processing when you use PySpark.

5.1.2Running Python in Databricks

Python
print("Hello, Databricks!")
# Hello, Databricks!

employee_name = "Rahul"
print(employee_name)
# Rahul

Python versus SQL in Databricks

Python cell
employee_count = 100
print(employee_count)
SQL cell
SELECT COUNT(*) AS employee_count
FROM main.employee_sql_lab.employees;

Use Python for programmatic logic, API integration, configuration processing, or custom functions. Use SQL when it expresses the transformation clearly and efficiently. PySpark combines Python programming with Spark's distributed processing.

5.1.9Sets

A set stores unique elements, which is useful for membership checks and comparing collections.

Python
departments = {"IT", "Finance", "IT", "HR"}
print(departments)              # duplicate "IT" removed

departments.add("Marketing")
departments.discard("HR")       # no error if missing

source_departments = {"IT", "Finance", "HR"}
target_departments = {"IT", "Finance", "Marketing"}

print(source_departments & target_departments)   # intersection
print(source_departments - target_departments)   # difference
print(source_departments | target_departments)   # union
Python · missing tables
source_tables = {"customers", "orders", "products"}
target_tables = {"customers", "orders"}

missing_tables = source_tables - target_tables
print(missing_tables)   # {'products'}
Important

Sets have no guaranteed order. Don't use them when record order matters.

5.1.12Loops

Python
# for: range(5) gives 0 through 4
for number in range(5):
    print(number)

employees = [
    {"employee_id": 101, "employee_name": "Rahul"},
    {"employee_id": 102, "employee_name": "Priya"},
    {"employee_id": 103, "employee_name": "Arjun"}
]
for employee in employees:
    print(employee["employee_name"])

# while
count = 1
while count <= 3:
    print(count)
    count += 1

# break: stop the loop (prints 1-4)
for employee_id in range(1, 10):
    if employee_id == 5:
        break
    print(employee_id)

# continue: skip this iteration (prints 1, 2, 4, 5)
for employee_id in range(1, 6):
    if employee_id == 3:
        continue
    print(employee_id)
Critical distinction: Python loops vs Spark

A loop like for employee in employees: process_employee(employee) is fine for small collections, configuration, and control flow. But never collect millions of Spark records into a Python list and process them one by one: it can exhaust driver memory and throws away distributed processing. Use PySpark DataFrame transformations instead (Chapter 7).

5.2Functions and Modules

Functions organize code into reusable units. Define a transformation once and call it everywhere it's needed.

5.2.1Defining functions

Python
def greet():
    print("Hello from Python")

greet()   # Hello from Python

def greet_employee(employee_name):
    print(f"Hello, {employee_name}")

greet_employee("Rahul")
greet_employee("Priya")

Why functions matter in data engineering

When several ingestion pipelines need the same validation, write it once:

Python
def validate_employee_id(employee_id):
    return employee_id is not None

print(validate_employee_id(101))    # True
print(validate_employee_id(None))   # False

Real validation should also reject invalid types and malformed identifiers.

5.2.2Arguments and return values

Python
def calculate_annual_salary(monthly_salary):
    return monthly_salary * 12

print(calculate_annual_salary(85000))      # 1020000

# Multiple arguments
def calculate_total_salary(base_salary, bonus):
    return base_salary + bonus

print(calculate_total_salary(85000, 10000))  # 95000

# Default arguments
def calculate_bonus(salary, bonus_percentage=10):
    return salary * bonus_percentage / 100

print(calculate_bonus(85000))       # uses 10%
print(calculate_bonus(85000, 15))   # uses 15%

# Keyword arguments
def create_employee(employee_id, employee_name, salary):
    return {
        "employee_id": employee_id,
        "employee_name": employee_name,
        "salary": salary
    }

employee = create_employee(
    employee_id=101,
    employee_name="Rahul",
    salary=85000
)
return versus print

print() displays a value. return sends a value back to the caller, so another function or pipeline step can use it.

5.3.2Reading JSON files

Python
import json

# json.loads(): parse a JSON *string*
json_text = """
{
    "employee_id": 101,
    "employee_name": "Rahul Sharma",
    "department": "IT",
    "salary": 85000
}
"""
employee = json.loads(json_text)
print(employee["employee_name"])

# json.load(): read JSON from an open *file*
with open("employee.json", "r", encoding="utf-8") as file:
    employee = json.load(file)

# A JSON array becomes a list of dictionaries
with open("employees.json", "r", encoding="utf-8") as file:
    employees = json.load(file)

for employee in employees:
    print(employee["employee_id"], employee["employee_name"])

JSON documents versus JSON Lines

JSON array: one document
[
  {"employee_id": 101, "employee_name": "Rahul"},
  {"employee_id": 102, "employee_name": "Priya"}
]
JSON Lines (JSONL / NDJSON)
{"employee_id": 101, "employee_name": "Rahul"}
{"employee_id": 102, "employee_name": "Priya"}

JSON Lines has one object per line, which suits streaming and large-file processing. Spark reads it directly; a conventional multi-line JSON document may need the multiLine option:

Python
# JSON Lines
df = spark.read.json(
    "/Volumes/main/default/files/employees.jsonl"
)

# Multi-line JSON document
df = (
    spark.read
    .option("multiLine", True)
    .json("/Volumes/main/default/files/employees.json")
)

5.3.3Working with dictionaries and lists

Python
employees = [
    {
        "employee_id": 101,
        "employee_name": "  Rahul Sharma ",
        "salary": "85000",
        "department": "IT"
    },
    {

# Loop version
transformed_employees = []

    transformed_employee = {

    return {

        "department": employee["department"].strip().upper()
    }

transformed_employees = [
    transform_employee(employee)
    for employee in employees
]

This function assumes every field exists and is valid. The hands-on project makes it robust.

5.3.4Handling missing values

Missing values can appear as a missing JSON property, JSON null (Python None), an empty string, a whitespace-only string, a missing CSV field, or a placeholder like "UNKNOWN" or "N/A". These are not automatically equivalent.

Python
employee = {"employee_id": 101, "employee_name": "Rahul", "salary": None}

if employee["salary"] is None:          # value is None
    print("Salary is missing")

if "salary" not in employee:            # key is absent
    print("Salary field is absent")

email = "   "
if email.strip() == "":                 # blank string
    print("Email is blank")

# Safe access to optional fields
employee = {"employee_id": 101, "employee_name": "Rahul"}
print(employee.get("email"))            # None

# Default value
email = employee.get("email") or "unknown@example.com"
Careful with "or"

or replaces any falsy value: an empty string, but also 0 and False. Where those are valid values, use explicit checks.

Define the business rule first
  • Missing employee ID → reject the record.
  • Missing employee name → quarantine or reject.
  • Missing email → allow NULL if email is optional.
  • Missing salary → reject, quarantine, or keep NULL per the source contract.

Don't replace every missing value with zero; that creates incorrect business results.

5.3.5Exception handling

An exception is an error raised while a program runs: a string that can't become an integer, a missing file, malformed JSON, a failed API request, a missing dictionary key.

Python
try:
    employee_id = int("ABC")
except ValueError:
    print("Invalid employee ID")

employee = {"employee_id": 101}
try:
    print(employee["employee_name"])
except KeyError:
    print("Employee name is missing")

try:
    salary = float("85000")
except ValueError:
    print("Invalid salary")
else:
    print("Salary conversion successful")
finally:
    print("Processing completed")
BlockRuns when
tryContains the operation that may fail
exceptA matching exception occurs
elseNo exception occurred in try
finallyAlways, whether it succeeded or failed
Avoid broad exception handling

except Exception: pass hides errors and makes troubleshooting very hard. Handle the exceptions you expect, and log enough information to diagnose failures.

Step 3: Create a transformation function

Uses Decimal for salary and datetime.strptime() for date validation.

Python
from datetime import datetime
from decimal import Decimal, InvalidOperation


def transform_employee(record):
    employee_id_raw = record.get("employee_id")
    employee_name_raw = record.get("employee_name")
    department_raw = record.get("department")
    salary_raw = record.get("salary")
    joining_date_raw = record.get("joining_date")

    # Validate employee ID
    if employee_id_raw is None or str(employee_id_raw).strip() == "":
        raise ValueError("Missing employee_id")

    try:
        employee_id = int(employee_id_raw)
    except (ValueError, TypeError):
        raise ValueError("Invalid employee_id")

    if employee_id <= 0:
        raise ValueError("employee_id must be positive")

    # Validate employee name
    if employee_name_raw is None:
        raise ValueError("Missing employee_name")

    employee_name = str(employee_name_raw).strip()

    if not employee_name:
        raise ValueError("Employee name cannot be blank")

    # Validate department
    if department_raw is None or not str(department_raw).strip():
        raise ValueError("Missing department")

    department = str(department_raw).strip().upper()

    # Validate salary
    if salary_raw is None or str(salary_raw).strip() == "":
        raise ValueError("Missing salary")

    try:
        salary = Decimal(str(salary_raw))
    except (InvalidOperation, ValueError, TypeError):
        raise ValueError("Invalid salary")

    if not salary.is_finite():
        raise ValueError("Salary must be a finite number")

    if salary < 0:
        raise ValueError("Salary cannot be negative")

    # Validate joining date
    if joining_date_raw is None:
        raise ValueError("Missing joining_date")

    try:
        joining_date = datetime.strptime(
            joining_date_raw,
            "%Y-%m-%d"
        ).date()
    except (ValueError, TypeError):
        raise ValueError("Invalid joining_date")

    return {
        "employee_id": employee_id,
        "employee_name": employee_name,
        "department": department,
        "salary": salary,
        "joining_date": joining_date
    }
StepAction
1Reads values from the dictionary
2Validates employee ID
3Validates employee name
4Normalizes department
5Converts salary to Decimal
6Validates joining date
7Returns a normalized dictionary

If validation fails, the function raises a ValueError describing the reason.

Step 1: Create a Spark DataFrame

from pyspark.sql.types import (
    StructType,
    StructField,
    IntegerType,
    StringType,

    DateType

schema = StructType([
    StructField("employee_id", IntegerType(), False),
    StructField("employee_name", StringType(), False),
    StructField("department", StringType(), False),
    StructField("salary", DecimalType(12, 2), False),

valid_rows = [

        record["employee_id"],
        record["employee_name"],
        record["department"],
        record["salary"],
        record["joining_date"]

    for record in valid_records
]

    valid_rows,

)

display(df)
Why specify a schema?

It defines the expected types and avoids relying on inference. The schema also declares fields non-nullable; because the Python step validated records first, accepted rows satisfy those constraints.

CREATE SCHEMA IF NOT EXISTS main.python_lab;

    employee_id INT,
    employee_name STRING,
    department STRING,

Step 3: Write the DataFrame to the table

Python
(

    .format("delta")
    .mode("append")

Why append, and its catch

append adds records without replacing existing data, which is fine for a demo, but rerunning appends the same records again. A repeatable production pipeline needs an idempotency strategy, such as deduplicating on a business key and using Delta MERGE. Avoid overwrite on production tables unless replacement is intended.

5.7Python Best Practices for Databricks Data Engineers

1. Keep transformations reusableFunctions with clear inputs and outputs instead of copied cells.

4. Separate valid and invalid recordsRejected data should carry source ID, record ID, error, ingestion time, file or batch ID, and the original record (or a reference). Handle sensitive fields per policy.
