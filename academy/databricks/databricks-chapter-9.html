9.1Delta Lake Fundamentals

9.1.1What Is Delta Lake?

Simple definition

Delta Lake is a storage layer that adds transactional and data-management capabilities to data in lake storage. It's a foundational technology of the Databricks lakehouse.

CSV, JSON, and Parquet are useful storage formats, but on their own they don't provide the transactional guarantees reliable analytical tables need. Delta Lake fills that gap by keeping a transaction log that tracks every change to a table.

Plain Parquet
customers/
    part-00000.parquet
    part-00001.parquet
    part-00002.parquet

To update customer 101, your application must read the data, produce replacement files, and coordinate them itself. Parquet has no table-level transactions, which causes trouble when several processes touch the same data.

Delta table
customers_delta/
│
├── part-00000-....parquet
├── part-00001-....parquet
├── part-00002-....parquet
│
└── _delta_log/
    ├── 00000000000000000000.json
    ├── 00000000000000000001.json
    └── ...

Parquet files hold the data; _delta_log records metadata and which files are active. Readers use a consistent table version instead of treating every file in the folder as live.

Important

Never modify the Parquet files inside a Delta table directly. That can break the relationship between the data files and the transaction log.

Key capabilities

  • ACID transactions.
  • Schema enforcement.
  • Controlled schema evolution.
  • Inserts, updates, and deletes.
  • Upserts through MERGE.
  • Table history.
  • Time travel.
  • Optimized data layout operations.
  • Integration with Databricks governance and catalogs.

9.1.2Delta Lake Versus Parquet

Parquet is a columnar file format. Delta Lake is a transactional table format that uses Parquet files plus a transaction log.

Use Parquet when

  • You need an interoperable analytical file format.
  • Data is written once and read many times.
  • You don't need transactional table operations.
  • The target system expects Parquet.

Use Delta when

  • Data is updated incrementally.
  • Multiple pipelines access the same table.
  • You need reliable inserts, updates, and deletes.
  • You need history and recovery.
  • You need schema enforcement.
  • You maintain curated reporting datasets.

9.1.3Delta Tables

A Delta table is a named or path-based dataset whose active state is managed by the transaction log. You access it by storage path or by catalog name.

Python
# Path-based
df = spark.read.format("delta").load(
    "/Volumes/main/silver/customers_delta/"
)

# Catalog-based
df = spark.table("main.silver.customers")
SQL
SELECT
    CustomerID,
    CustomerName,
    City
FROM main.silver.customers;
Important distinction

A Delta table at a path doesn't automatically have a catalog name. A catalog table is a named object with metadata, permissions, and governance. In Unity Catalog it's referenced as catalog.schema.table, e.g. main.silver.customers; the catalog and schema must exist and you need permissions.

9.1.4Delta Transaction Logs

The transaction log is one of Delta Lake's most important components. It records the changes needed to determine a table's current state: data files added, files removed from the active state, schema and metadata, protocol information, transaction IDs and application metadata, and supported table features.

The log doesn't store every row; the data stays in the data files.

Version 0:
    customers_001.parquet
    customers_002.parquet

Version 1  (new batch inserted):
    customers_001.parquet
    customers_002.parquet
    customers_003.parquet

Version 2  (existing customer updated):
    New replacement files are added.
    Previously active files may be
    removed from the current state.

Why this matters

Without the log, a reader could see incomplete or inconsistent results while a write is in progress.

Delta commits each transaction atomically, so readers always see a consistent table state. Delta uses the log to know exactly which files belong to each version.

Inspect, don't edit

_delta_log is great for understanding the architecture, but never modify it manually. Use SQL commands and Delta APIs to inspect history and change tables.

9.1.5ACID Transactions

Delta Lake provides ACID properties for supported table operations.

Atomicity

A transaction commits entirely or not at all. If a 100,000-record write fails before committing, readers see none of it.

Consistency

Transactions preserve the table's rules: schema compatibility, enforced constraints, valid metadata, protocol requirements. Business rules like unique customer IDs still need explicit implementation.

Isolation

Concurrent readers and writers are coordinated by Delta's transaction and concurrency rules. Conflicting writes are resolved per the operations, isolation settings, and runtime.

Durability

Once committed, the state persists according to the storage platform's durability guarantees.

SQL
UPDATE main.silver.customers
SET City = 'Hyderabad'
WHERE CustomerID = 101;

This changes the table atomically: no query ever sees a state where only part of the update is committed.

9.1.6Schema Enforcement

Schema enforcement blocks incompatible data from being written to a Delta table.

Target table
CustomerID   INT
CustomerName STRING
Age          INT
Incoming DataFrame
CustomerID   INT
CustomerName STRING
Age          STRING   <- mismatch
Python
from pyspark.sql.types import (
    StructType,
    StructField,
    IntegerType,
    StringType
)

schema = StructType([
    StructField("CustomerID", IntegerType(), True),
    StructField("CustomerName", StringType(), True),
    StructField("Age", StringType(), True)
])

incoming_df = spark.createDataFrame(
    [(101, "John", "35"), (102, "David", "40")],
    schema
)

Appending this to a table whose Age is an integer can fail with a schema incompatibility. The fix is to convert first, then check for conversion failures:

Python
from pyspark.sql import functions as F

corrected_df = incoming_df.withColumn(
    "Age",
    F.expr("try_cast(Age AS INT)")
)

invalid_df = corrected_df.filter(F.col("Age").isNull())

If null ages are legitimate, distinguish source nulls from conversion failures.

Benefits: prevents unintended schema changes, protects downstream queries, improves consistency, helps detect upstream source changes, and reduces surprise reporting failures.

9.1.7Schema Evolution

Schema evolution lets a table's schema change in a controlled way, for example when the source adds an Email column to CustomerID, CustomerName, City.

Python
(
    incoming_df.write
    .format("delta")
    .mode("append")
    .option("mergeSchema", "true")
    .saveAsTable("main.silver.customers")
)
Schema enforcementSchema evolution
Rejects incompatible changesAllows approved schema changes
Protects the existing data contractSupports changes to the contract
Prevents accidental driftIncorporates legitimate new fields
Don't enable it everywhere

A new column can affect downstream SQL, semantic models, reports, and contracts. Define which new columns are allowed, whether type changes are permitted, how incompatible changes are handled, which downstream systems need updates, and how changes are logged and reviewed.

9.1.8Data Reliability

Data reliability means the table consistently represents the intended business data. Delta helps through transactions, schema enforcement, and controlled changes, but it doesn't guarantee business correctness. A transaction will happily insert a customer with a negative credit limit if no constraint or validation stops it.

Reliability controls

  1. Schema validation.
  2. Required-field validation.
  3. Duplicate detection.
  4. Business-rule validation.
  5. Record count reconciliation.
  6. Incremental-load reconciliation.
  7. Transaction failure handling.
  8. Audit logging.
  9. Source-to-target comparison.
  10. Recovery and reprocessing procedures.
Example: a check constraint
SQL
ALTER TABLE main.silver.products
ADD CONSTRAINT valid_price
CHECK (Price >= 0);

Illustrative: the table needs a compatible Price column, and existing data must already satisfy the rule. Constraints don't replace comprehensive validation.

9.1.9Concurrent Reads and Writes

In enterprise environments, several jobs touch the same table: Pipeline A inserts customers, Pipeline B updates addresses, a report reads, an optimization job reorganizes files. Readers query a consistent snapshot while supported writes happen.

Optimistic concurrency control

  1. Read the relevant table state.
  2. Do the data-processing work.
  3. Attempt to commit.
  4. Check for conflicting concurrent changes.
  5. Commit, or fail if a conflict is found.

When a conflict occurs

  • Inspect the error.
  • Decide whether it's transient.
  • Refresh the relevant table state.
  • Recompute the operation where appropriate.
  • Retry with a bounded retry policy.
Don't retry blindly

Schema mismatches and invalid data won't be fixed by retrying. Only transient concurrency conflicts benefit from a retry.

9.2Creating Delta Tables

9.2.1Managed Delta Tables

A managed table's storage lifecycle is managed by the platform. In Unity Catalog, its data lives in the managed storage location configured for the catalog or schema.

SQL
CREATE TABLE main.silver.customers (
    CustomerID INT,
    CustomerName STRING,
    City STRING,
    Email STRING
)
USING DELTA;

INSERT INTO main.silver.customers
VALUES
    (101, 'John', 'Hyderabad', 'john@example.com'),
    (102, 'David', 'Chennai', 'david@example.com');

SELECT *
FROM main.silver.customers;

Advantages

  • Catalog-managed metadata.
  • Access control integration.
  • Easy table discovery.
  • Simplified lifecycle.
  • Strong Databricks SQL and Spark integration.
Important

Dropping a managed table normally removes the table and its data. Don't assume dropping is harmless.

If main.silver.customers already exists from Chapter 8 with a different schema, use a new name for these examples, or drop the old table first.

9.2.2External Delta Tables

An external table's metadata is registered in the catalog, but its data lives at a location you specify and manage separately.

SQL
CREATE TABLE main.silver.external_customers (
    CustomerID INT,
    CustomerName STRING,
    City STRING
)
USING DELTA
LOCATION 'abfss://silver@myaccount.dfs.core.windows.net/customers/';

An illustrative ADLS Gen2 location. In Unity Catalog, external locations and storage credentials must be configured; access also depends on workspace and cloud permissions.

FeatureManaged tableExternal table
Storage locationManaged by the platformSpecified external location
Catalog metadataManaged by the catalogManaged by the catalog
Data lifecycleManaged-table lifecycleManaged separately
Typical useCurated platform-managed datasetsData that must stay at a controlled location
Drop behaviorNormally removes managed dataNormally removes only the catalog entry
Recommendation

Use managed tables when you want Databricks to manage storage. Use external tables only when you have a deliberate need to control the storage location independently.

9.2.3Creating Delta Tables Using PySpark

Python
data = [
    (101, "John", "Hyderabad"),
    (102, "David", "Chennai"),
    (103, "Smith", "Bengaluru")
]

columns = ["CustomerID", "CustomerName", "City"]

df = spark.createDataFrame(data, columns)

(
    df.write
    .format("delta")
    .mode("overwrite")
    .saveAsTable("main.silver.customers")
)

customers_df = spark.table("main.silver.customers")

display(customers_df)

This creates or replaces the table depending on its current state and your permissions. In production, prefer an explicit target schema and avoid accidental overwrites.

9.2.4Creating a Delta Table Using CTAS

CTAS (CREATE TABLE AS SELECT) creates a table from a query result.

SQL
CREATE TABLE main.silver.active_customers
USING DELTA
AS
SELECT
    CustomerID,
    CustomerName,
    City
FROM main.bronze.customers
WHERE IsActive = true;

What happens

  1. Spark runs the query.
  2. The query returns the selected records.
  3. The result is written to a new Delta table.
  4. The table becomes available in the catalog.

Use cases

  • Creating curated tables.
  • Transforming during creation.
  • Materializing filtered datasets.
  • Building reporting tables.

CTAS fails if the target already exists. Use CREATE OR REPLACE TABLE ... AS SELECT when replacement is intended.

9.2.6Updating Data

SQL
UPDATE main.silver.customers
SET City = 'Hyderabad'
WHERE CustomerID = 101;

-- Multiple columns
UPDATE main.silver.customers
SET
    City = 'Hyderabad',
    Email = 'john.new@example.com'
WHERE CustomerID = 101;

-- A group of records
UPDATE main.silver.customers
SET City = 'Unknown'
WHERE City IS NULL;
Check the WHERE clause

An update without an appropriate filter modifies every row. Validate the WHERE clause before running it against production.

9.2.7Deleting Data

SQL
DELETE FROM main.silver.customers
WHERE CustomerID = 105;

-- Assumes an IsActive column exists
DELETE FROM main.silver.customers
WHERE IsActive = false;

A Delta delete changes the logical table state; the physical files may remain until retention and maintenance policies allow cleanup. Never delete the Parquet files manually.

9.2.8Dropping Tables

SQL
DROP TABLE IF EXISTS main.silver.customers;

Dropping removes the catalog registration and follows the table type's lifecycle: a managed table's data is normally deleted; an external table's files normally remain.

Before dropping a table

  1. Confirm the table name.
  2. Confirm whether it's managed or external.
  3. Check downstream dependencies.
  4. Confirm backup or recovery requirements.
  5. Review the applicable retention and recovery mechanisms.

Unity Catalog managed tables can often be recovered with UNDROP TABLE within a limited window, but treat dropping as a potentially destructive operation.

9.3Delta Lake Operations

9.3.1What Is MERGE INTO?

MERGE INTO combines source and target data by a matching condition, and is the workhorse of incremental ingestion. It can update matching records, insert unmatched ones, delete matches under conditions, and handle different source actions.

Target
CustomerIDCustomerNameCity
101JohnHyderabad
102DavidChennai
Incoming batch
CustomerIDCustomerNameCity
101JohnBengaluru
103SmithVijayawada
After the merge
CustomerIDCustomerNameCityWhat happened
101JohnBengaluruUpdated
102DavidChennaiUnchanged
103SmithVijayawadaInserted

9.3.2Basic MERGE Syntax

SQL
MERGE INTO main.silver.customers AS target
USING main.bronze.customer_updates AS source
ON target.CustomerID = source.CustomerID

WHEN MATCHED THEN
    UPDATE SET
        target.CustomerName = source.CustomerName,
        target.City = source.City

WHEN NOT MATCHED THEN
    INSERT (CustomerID, CustomerName, City)
    VALUES (source.CustomerID, source.CustomerName, source.City);
ClauseRole
MERGE INTOIdentifies the target table
USINGIdentifies the source dataset
ONDefines the matching condition
WHEN MATCHEDRecords in both source and target
WHEN NOT MATCHEDRecords only in the source
Important rule

The source must not contain multiple conflicting rows for the same target key, or the merge may fail because several source rows match one target row. Deduplicate the source first.

9.3.3Upserts

An upsert updates matching records and inserts new ones.

Python
from delta.tables import DeltaTable

target = DeltaTable.forName(spark, "main.silver.customers")

(
    target.alias("target")
    .merge(
        source_df.alias("source"),
        "target.CustomerID = source.CustomerID"
    )
    .whenMatchedUpdateAll()
    .whenNotMatchedInsertAll()
    .execute()
)

Use cases: customer master synchronization, product dimension maintenance, incremental reference data, slowly changing data, source-to-target synchronization.

Important

whenMatchedUpdateAll() updates every compatible column. Use explicit column mappings (whenMatchedUpdate(set={...})) if some columns shouldn't change, such as ingestion timestamps, audit fields, or manually maintained attributes.

9.3.4Insert-Only Operations

Adds records that don't already exist in the target.

SQL
MERGE INTO main.silver.customers AS target
USING main.bronze.new_customers AS source
ON target.CustomerID = source.CustomerID

WHEN NOT MATCHED THEN
    INSERT (CustomerID, CustomerName, City)
    VALUES (source.CustomerID, source.CustomerName, source.City);

Use cases: new customer registration, append-oriented reference data, initial population of missing entities.

Still deduplicate the source: two rows with the same new key are both "not matched" and would create duplicate target records.

9.3.5Update-Only Operations

Changes existing records and never inserts.

SQL
MERGE INTO main.silver.customers AS target
USING main.bronze.customer_updates AS source
ON target.CustomerID = source.CustomerID

WHEN MATCHED THEN
    UPDATE SET
        target.CustomerName = source.CustomerName,
        target.City = source.City;

New source customers are ignored because there's no insert clause. Use cases: updating attributes, correcting loaded data, synchronizing selected columns.

9.3.6Delete Operations Using MERGE

When a source sends an Action column (INSERT, UPDATE, DELETE):

SQL
MERGE INTO main.silver.customers AS target
USING main.bronze.customer_changes AS source
ON target.CustomerID = source.CustomerID

WHEN MATCHED AND source.Action = 'DELETE'
    THEN DELETE

WHEN MATCHED AND source.Action = 'UPDATE'
    THEN UPDATE SET
        target.CustomerName = source.CustomerName

WHEN NOT MATCHED AND source.Action = 'INSERT'
    THEN INSERT (CustomerID, CustomerName)
    VALUES (source.CustomerID, source.CustomerName);
Why explicit delete events matter

A record missing from an incremental batch doesn't mean it was deleted; it may simply not have changed. Use source delete events, tombstones, CDC, or a reliable full-snapshot comparison when you need deletion detection.

9.3.7Deduplication Using MERGE

CustomerIDCustomerNameModifiedDate
101John2026-10-24 09:00:00
101Jonathan2026-10-24 11:00:00
102David2026-10-24 10:00:00

Customer 101 appears twice. Keep the latest valid record, then merge:

Python
from pyspark.sql import Window
from pyspark.sql import functions as F
from delta.tables import DeltaTable

window_spec = (
    Window
    .partitionBy("CustomerID")
    .orderBy(
        F.col("ModifiedDate").desc_nulls_last(),
        F.col("IngestionTimestamp").desc_nulls_last()
    )
)

deduplicated_df = (
    source_df
    .withColumn("row_num", F.row_number().over(window_spec))
    .filter(F.col("row_num") == 1)
    .drop("row_num")
)

target = DeltaTable.forName(spark, "main.silver.customers")

(
    target.alias("target")
    .merge(
        deduplicated_df.alias("source"),
        "target.CustomerID = source.CustomerID"
    )
    .whenMatchedUpdateAll(
        condition="source.ModifiedDate > target.ModifiedDate"
    )
    .whenNotMatchedInsertAll()
    .execute()
)

The condition stops older source versions from replacing newer target versions, as long as timestamps are reliable. Add a deterministic tie-breaker if ordering values can be identical.

9.3.8Schema Evolution During Writes

When the source adds a field, say LoyaltyStatus:

Python
(
    incoming_df.write
    .format("delta")
    .mode("append")
    .option("mergeSchema", "true")
    .saveAsTable("main.silver.customers")
)

For MERGE, schema evolution can be enabled with MERGE WITH SCHEMA EVOLUTION INTO ... in SQL or .withSchemaEvolution() in the Python API, depending on your runtime.

Best practices

  • Review new columns before enabling them.
  • Validate each new field's type.
  • Check whether downstream reports depend on the current schema.
  • Log schema changes.
  • Avoid unintended type changes.
  • Keep schema evolution separate from data-quality validation.

9.3.9Handling Schema Mismatches

A mismatch happens when source data doesn't fit the target: CustomerID is a string in the source but an integer in the target, a required column is missing, a new column appears unexpectedly, or a type is incompatible.

Python
from pyspark.sql import functions as F

# Step 1: Inspect the source schema
source_df.printSchema()

# Step 2: Inspect the target schema
target_df = spark.table("main.silver.customers")
target_df.printSchema()

# Step 3: Convert source types
source_df = source_df.withColumn(
    "CustomerID",
    F.expr("try_cast(CustomerID AS INT)")
)

# Step 4: Find invalid values
invalid_df = source_df.filter(F.col("CustomerID").isNull())

# Step 5: Select compatible columns
source_df = source_df.select(
    "CustomerID",
    "CustomerName",
    "City",
    "ModifiedDate"
)

# Step 6: Merge only after the data passes schema and business checks

9.4Time Travel

9.4.1What Is Time Travel?

Time travel lets you query a Delta table as of a previous committed version, to investigate changes, compare results, troubleshoot accidental updates, reproduce historical queries, and support controlled recovery. It depends on retained transaction-log history and the corresponding data files still existing.

9.4.2Delta Table History

SQL
DESCRIBE HISTORY main.silver.customers;

Output can include

Version, timestamp, operation, operation parameters, user or identity, job or notebook, and operation metrics.

Python
from delta.tables import DeltaTable

delta_table = DeltaTable.forName(spark, "main.silver.customers")

history_df = delta_table.history()

display(
    history_df.select(
        "version",
        "timestamp",
        "operation",
        "operationParameters",
        "operationMetrics"
    )
)

History shows when and how the table changed, but it doesn't necessarily contain every deleted row's original contents.

9.4.3Querying Previous Versions

The timestamp must fall where history and data are still available. Use version-based travel when you need a specific committed version precisely.

9.4.5Comparing Two Versions

Python
from pyspark.sql import functions as F

old_df = (
    spark.read
    .format("delta")
    .option("versionAsOf", 2)
    .table("main.silver.customers")
)

new_df = spark.table("main.silver.customers")

# Record counts
old_count = old_df.count()
new_count = new_df.count()

print("Old count:", old_count)
print("Current count:", new_count)
print("Difference:", new_count - old_count)

# Keys present only in the newer version (not updates)
new_only_df = new_df.join(
    old_df.select("CustomerID"),
    on="CustomerID",
    how="left_anti"
)

# Changed records: join on the key, compare attributes null-safely
changed_df = (
    new_df.alias("new")
    .join(old_df.alias("old"), on="CustomerID", how="inner")
    .filter(
        ~F.col("new.CustomerName").eqNullSafe(F.col("old.CustomerName"))
        | ~F.col("new.City").eqNullSafe(F.col("old.City"))
    )
)

9.4.6Restoring a Previous Version

SQL · by version
RESTORE TABLE main.silver.customers
TO VERSION AS OF 2;
SQL · by timestamp
RESTORE TABLE main.silver.customers
TO TIMESTAMP AS OF '2026-10-24 12:00:00';
What happens during restore

A restore creates a new committed version that reflects the chosen historical state. It doesn't rewind the log or erase later history; the restore itself appears in table history.

Before restoring

A restore can remove legitimate changes made after the chosen version.

  1. Identify the incorrect operation.
  2. Find the last correct version.
  3. Compare historical and current data.
  4. Assess downstream impact.
  5. Decide between a full restore and a selective repair.
  6. Communicate with dependent consumers.

A selective correction may be safer than restoring the entire table.

9.4.7Recovery Scenarios

Scenario 1: Accidental deletion

SQL
-- The mistake
DELETE FROM main.silver.customers;

-- Inspect the version before it (say, version 4)
SELECT *
FROM main.silver.customers VERSION AS OF 4;

-- If version 4 is correct, restore it
RESTORE TABLE main.silver.customers
TO VERSION AS OF 4;

Scenario 2: Incorrect update

SQL
-- The mistake: no WHERE clause
UPDATE main.silver.customers
SET City = 'Unknown';

Compare the current state with the previous version to find affected records, then restore or repair them.

Scenario 3: Unexpected data loss

A pipeline produces fewer records than expected. Investigate recent table operations, source counts, merge conditions, delete logic, schema changes, rejected records, and previous versions.

Remember

Time travel is an investigation and recovery tool. It doesn't remove the need for source retention, backups, and tested recovery procedures.

9.5Delta Lake Maintenance

9.5.1Why Delta Maintenance Is Important

Growing tables accumulate small files, which increase file-listing overhead, query-planning overhead, metadata processing, task scheduling, and storage requests. Maintenance reorganizes the physical layout while preserving the logical contents, through OPTIMIZE, compaction, Z-Ordering, liquid clustering, VACUUM, and statistics collection.

On Unity Catalog managed tables, predictive optimization can run OPTIMIZE and VACUUM automatically where it's enabled. Check your workspace before scheduling these yourself.

9.5.2OPTIMIZE

OPTIMIZE reorganizes data files to improve layout and compact small files into appropriately sized ones. A pipeline writing small batches every few minutes can build up thousands of files; optimization combines them.

SQL
OPTIMIZE main.silver.customers;

-- One partition of a table
-- partitioned by Year and Month
OPTIMIZE main.silver.transactions
WHERE Year = 2026
  AND Month = 10;
Python
from delta.tables import DeltaTable

delta_table = DeltaTable.forName(
    spark,
    "main.silver.customers"
)

delta_table.optimize().executeCompaction()

The WHERE predicate must use the table's partition columns.

Best practice

Don't run OPTIMIZE after every small write without measuring. Schedule it based on data volume, ingestion frequency, query patterns, and performance needs.

9.5.3Compaction

Compaction combines smaller files into fewer, larger ones.

Before
customers/
    part-00001.parquet
    part-00002.parquet
    part-00003.parquet
    part-00004.parquet
    part-00005.parquet
After
customers/
    part-00010.parquet
    part-00011.parquet

Conceptual; actual file counts depend on volume, partition layout, and settings.

It reduces small-file overhead, can speed up queries, and reduces files considered during planning. It changes the physical layout, not the logical contents; the transaction log records the new state.

9.5.4Z-Ordering

Z-Ordering co-locates related values in multidimensional space, improving data skipping for suitable filters.

SQL
-- Table frequently filtered by CustomerID
OPTIMIZE main.silver.transactions
ZORDER BY (CustomerID);

-- Multiple columns
OPTIMIZE main.silver.transactions
ZORDER BY (CustomerID, TransactionDate);
Considerations
  • Z-Ordering isn't SQL result sorting and doesn't guarantee row order.
  • It has computation and maintenance costs.
  • More columns isn't always better.
  • Effectiveness depends on data distribution, file statistics, and filter patterns.
  • It can't be used on tables with liquid clustering.

Consider it when queries repeatedly filter on selective columns and the workload benefits from better data skipping.

9.5.5Liquid Clustering

Liquid clustering organizes data around clustering columns and adapts to evolving access patterns without static partitioning. For new Delta tables, Databricks generally recommends it over partitioning and Z-Ordering.

SQL
CREATE TABLE main.silver.transactions (
    TransactionID BIGINT,
    CustomerID BIGINT,
    TransactionDate DATE,
    Amount DECIMAL(12, 2)
)
USING DELTA
CLUSTER BY (CustomerID, TransactionDate);

-- Clustering is applied incrementally when you run:
OPTIMIZE main.silver.transactions;

Assumes your environment supports liquid clustering for this table type. You can change keys later with ALTER TABLE ... CLUSTER BY (...), or let Databricks choose them with CLUSTER BY AUTO where supported.

Advantages

  • Flexible data layout.
  • Improved data skipping.
  • Less static partition management.
  • Clustering keys can change through supported operations.

Considerations

  • Availability depends on your environment.
  • Not every table type or feature combination supports it.
  • Keys should reflect common query filters.
  • It doesn't replace schema or data-quality checks.
  • Review the current layout before changing clustering.
FeatureZ-OrderingLiquid clustering
PurposeImprove file-level data localityOrganize data around clustering keys

The two are alternatives, not a combination: pick one per table.

9.5.6VACUUM

VACUUM permanently removes data files that the current table state no longer needs and that are past the retention threshold. Updates and deletes leave obsolete files behind; vacuuming reclaims their storage.

SQL
-- Preview what would be removed (no deletion)
VACUUM main.silver.customers DRY RUN;

-- Default retention
VACUUM main.silver.customers;

-- Explicit retention: 168 hours = 7 days
VACUUM main.silver.customers RETAIN 168 HOURS;
Important warning

Vacuuming can permanently remove files needed for historical queries; afterwards some versions are no longer queryable. The typical default retention is seven days, but verify your table's configuration and platform safeguards. Don't shorten retention without understanding the effect on long-running readers, concurrent operations, and time travel. Always review a DRY RUN first.

9.5.7Small-File Problems

Causes

  • Frequent micro-batch writes.
  • Excessive repartitioning.
  • Over-partitioning by high-cardinality columns.
  • Writing many small DataFrames separately.
  • Inappropriate output partition counts.

Consequences

  • More metadata overhead.
  • Slower query planning.
  • More file-open operations.
  • Less efficient large scans.

Solutions

  1. Review write frequency.
  2. Avoid unnecessary partitioning.
  3. Use appropriate Spark partition counts.
  4. Run OPTIMIZE where beneficial.
  5. Use optimized writes and auto-compaction where appropriate.
  6. Monitor actual file sizes and query performance.
Fewer isn't always better

Very large files can hurt parallelism or create uneven workloads. Choose file sizes based on the workload and platform behavior.

9.5.8Data Skipping

Data skipping lets Databricks avoid files that can't contain matching records, using file-level statistics such as min and max values.

SQL
SELECT *
FROM main.silver.transactions
WHERE CustomerID = 101;
File A: CustomerID 1 – 50     -> skipped
File B: CustomerID 100 – 200  -> read

Factors: file-level data distribution, statistics availability, filter selectivity, physical layout, data types, and query predicates. Z-Ordering and clustering improve locality and can make skipping more effective, but neither guarantees a speed. Measure with query profiles and execution metrics.

9.5.9Statistics Collection

Statistics (row counts, column statistics, min/max values, file-level statistics, distribution information) help the optimizer choose join order and strategy and estimate data volume.

SQL
-- Format, location, file count,
-- size, partitions, properties
DESCRIBE DETAIL main.silver.customers;

ANALYZE TABLE main.silver.customers
COMPUTE STATISTICS;
Note

Column-level statistics can be collected with COMPUTE STATISTICS FOR ALL COLUMNS where supported. Statistics are one part of optimization; they don't replace good layout or query design.

Hands-On Project: Incremental Customer Table Using Delta Lake

Build an incremental customer pipeline that creates a target table, loads initial data, inserts, updates, and deletes from a change feed, deduplicates changes, and then uses history, time travel, and restore.

A dedicated schema

This project uses its own schema, main.delta_lab, so it doesn't collide with the main.silver.customers table used in earlier examples and in Chapter 8. Using CREATE OR REPLACE means you can rerun it cleanly, and the version numbers below will match.

Scenario: a source system sends customer changes every day. The target table must keep the latest valid state of each customer.

Initial target data
CustomerIDCustomerNameCityModifiedDate
101JohnHyderabad2026-10-20 10:00
102DavidChennai2026-10-20 11:00
103SmithBengaluru2026-10-20 12:00
Expected after processing
CustomerIDCustomerNameCity
101JohnHyderabad
102DavidVijayawada
104KumarHyderabad
Incoming changes
CustomerIDCustomerNameCityModifiedDateAction
101JohnHyderabad2026-10-25 09:00UPDATE
102DavidVijayawada2026-10-25 09:30UPDATE
104KumarHyderabad2026-10-25 10:00INSERT
103SmithBengaluru2026-10-25 10:30DELETE

Customer 103 is deleted, 102 is updated, 104 is inserted, and 101 stays logically unchanged even though the source sends an update event (only its ModifiedDate moves forward).

Step 1: Create the schema and target table

SQL
CREATE SCHEMA IF NOT EXISTS main.delta_lab;

CREATE OR REPLACE TABLE main.delta_lab.customers (
    CustomerID INT,
    CustomerName STRING,
    City STRING,
    ModifiedDate TIMESTAMP
)
USING DELTA;

Step 2: Load initial data

SQL
INSERT INTO main.delta_lab.customers
VALUES
    (101, 'John',  'Hyderabad', TIMESTAMP '2026-10-20 10:00:00'),
    (102, 'David', 'Chennai',   TIMESTAMP '2026-10-20 11:00:00'),
    (103, 'Smith', 'Bengaluru', TIMESTAMP '2026-10-20 12:00:00');

SELECT *
FROM main.delta_lab.customers
ORDER BY CustomerID;

Step 3: Create the incoming change table

SQL
CREATE OR REPLACE TABLE main.delta_lab.customer_changes (
    CustomerID INT,
    CustomerName STRING,
    City STRING,
    ModifiedDate TIMESTAMP,
    Action STRING
)
USING DELTA;

INSERT INTO main.delta_lab.customer_changes
VALUES
    (101, 'John',  'Hyderabad',  TIMESTAMP '2026-10-25 09:00:00', 'UPDATE'),
    (102, 'David', 'Vijayawada', TIMESTAMP '2026-10-25 09:30:00', 'UPDATE'),
    (104, 'Kumar', 'Hyderabad',  TIMESTAMP '2026-10-25 10:00:00', 'INSERT'),
    (103, 'Smith', 'Bengaluru',  TIMESTAMP '2026-10-25 10:30:00', 'DELETE');

Step 4: Validate the incoming data

SQL
SELECT *
FROM main.delta_lab.customer_changes
WHERE CustomerID IS NULL
   OR Action IS NULL
   OR Action NOT IN ('INSERT', 'UPDATE', 'DELETE');

Expected: no rows. This catches missing keys and unsupported actions; add checks for required attributes, timestamp validity, and key uniqueness.

The Action IS NULL check matters: NULL NOT IN (...) evaluates to unknown, not true, so a null action would otherwise slip through.

Step 5: Deduplicate the source

SQL
CREATE OR REPLACE TEMP VIEW deduplicated_customer_changes AS
SELECT
    CustomerID,
    CustomerName,
    City,
    ModifiedDate,
    Action
FROM (
    SELECT
        *,
        ROW_NUMBER() OVER (
            PARTITION BY CustomerID
            ORDER BY ModifiedDate DESC
        ) AS row_num
    FROM main.delta_lab.customer_changes
) ranked
WHERE row_num = 1;

In production, add a deterministic tie-breaker for identical timestamps.

Step 6: Apply the incremental changes

SQL
MERGE INTO main.delta_lab.customers AS target
USING deduplicated_customer_changes AS source
ON target.CustomerID = source.CustomerID

WHEN MATCHED AND source.Action = 'DELETE'
    THEN DELETE

WHEN MATCHED AND source.Action = 'UPDATE'
    AND source.ModifiedDate > target.ModifiedDate
    THEN UPDATE SET
        target.CustomerName = source.CustomerName,
        target.City = source.City,
        target.ModifiedDate = source.ModifiedDate

WHEN NOT MATCHED AND source.Action = 'INSERT'
    THEN INSERT (CustomerID, CustomerName, City, ModifiedDate)
    VALUES (source.CustomerID, source.CustomerName, source.City, source.ModifiedDate);
Implementation detail

Only records marked INSERT are inserted. An UPDATE event for a customer missing from the target is ignored, which is right for a strict change-event contract; other pipelines may treat it as an insert. Define this explicitly for your source system.

Step 7: Validate the final data

SQL
SELECT *
FROM main.delta_lab.customers
ORDER BY CustomerID;
-- Expected: 101 John Hyderabad, 102 David Vijayawada, 104 Kumar Hyderabad

SELECT COUNT(*) AS CustomerCount
FROM main.delta_lab.customers;
-- Expected: 3

SELECT
    CustomerID,
    COUNT(*) AS RecordCount
FROM main.delta_lab.customers
GROUP BY CustomerID
HAVING COUNT(*) > 1;
-- Expected: no rows

Delta doesn't enforce uniqueness of business keys, so this duplicate check stays important.

Step 8: Inspect table history

SQL
DESCRIBE HISTORY main.delta_lab.customers;
VersionOperationFrom step
0CREATE OR REPLACE TABLEStep 1
1WRITEStep 2 (initial insert)
2MERGEStep 6

On a fresh run you should see these three versions. If you rerun the project, CREATE OR REPLACE adds new versions on top of the old history, so check the actual numbers.

Step 9: Query an earlier version

SQL
-- Version 1 = the original three customers
SELECT *
FROM main.delta_lab.customers VERSION AS OF 1;

You should see customers 101, 102 (still in Chennai), and 103.

Step 10: Restore a previous version

SQL
RESTORE TABLE main.delta_lab.customers
TO VERSION AS OF 1;
Warning

This undoes the merge: customer 103 comes back, 102 returns to Chennai, and 104 disappears. That's fine in this lab, but in real work confirm the right version and downstream impact first. Run DESCRIBE HISTORY again and you'll see the restore recorded as a new version 3.

Step 11: Optimize the table

SQL
OPTIMIZE main.delta_lab.customers;

On a tiny training table this gives little or no measurable benefit; it's here to demonstrate the operation.

Step 12: Inspect table details

SQL
DESCRIBE DETAIL main.delta_lab.customers;

Review the location, file count, size, and other metadata.

Project Extensions

1. Watermark management

Track the last successfully processed modification timestamp. Advance it only after the changes are applied and reconciled.

2. Idempotent processing

Process the same batch twice. Confirm the second run adds no duplicates and doesn't replace newer data.

3. Rejected-record handling

Create a quarantine table for invalid keys, unsupported actions, or missing values, with the source batch and rejection reason.

4. Delete handling

Test what happens when:

  • A delete references an existing customer.
  • A delete references a missing customer.
  • A duplicate delete arrives.
  • An older update arrives after a newer one.

5. Time-travel investigation

Record the version before a test update, run the update, compare both versions, and restore the original in a test table.

6. Maintenance and performance

Generate a larger dataset, write many small batches, and compare query behavior before and after OPTIMIZE using query profiles and table metadata.
