Databricks Security and Administration

Secure, administer, and govern Databricks workloads in production: workspace settings, compute policies, users, groups, and service principals; Microsoft Entra ID, OAuth, secrets, and least privilege; private connectivity and network controls; Unity Catalog grants, storage credentials, external locations, row filters, and column masks; and the separation, reviews, and controls that keep production safe.

Scope

This chapter focuses on Azure Databricks with Microsoft Entra ID, Unity Catalog, and Azure networking. Most concepts apply to AWS and Google Cloud too; cloud-specific configuration differs.

By the end of this chapter you will be able to
  1. Manage workspaces, users, groups, and service principals.
  2. Implement least-privilege access.
  3. Authenticate applications securely using OAuth.
  4. Manage secrets and credentials without hardcoding them.
  5. Understand private connectivity and network security.
  6. Control data access through Unity Catalog.
  7. Implement row-level filtering and column masking.
  8. Design separate development and production environments.
  9. Apply production security and compute-governance practices.

19.1Workspace Administration

19.1.1What Is a Workspace?

A workspace is an environment where users develop, run, and manage data engineering, analytics, and ML workloads. It contains notebooks, jobs, compute, SQL warehouses, repos, workspace files, permissions, and references to governed data.

WorkspacePurposeTypical users
adb-retail-devDevelopment and experimentationData engineers and developers
adb-retail-testIntegration and UATQA and data engineers
adb-retail-prodProduction pipelines and reportingProduction service principals, authorized support engineers
A workspace is not where data lives

The data itself sits in ADLS, managed Delta tables, external databases, and so on. The workspace is the environment you work in; Unity Catalog governs the data, and one metastore can serve several workspaces.

Administrative levels

LevelMain responsibilities
Account adminAccount configuration, identity management, workspaces, metastores
Workspace adminWorkspace settings, workspace users, object permissions
Metastore adminUnity Catalog metastore administration (optional role)
Data ownerAccess and governance for particular catalogs, schemas, or tables
Data engineerDevelop and operate pipelines with explicitly granted permissions

Best practice: don't make every senior engineer a workspace admin. Grant admin rights only when required.

19.1.2Workspace Settings

Administrators may configure authentication and access, who can create compute, personal access token policies, IP access lists, network connectivity, object permissions, default compute settings, Unity Catalog integration, and identity provisioning.

Development

  • Engineers create approved dev compute.
  • Experiment with test data.
  • Debugging access available.
  • Resource limits on workloads.
  • No production credentials by default.

Production

  • Compute creation restricted.
  • Jobs run as dedicated service principals.
  • Sensitive data tightly controlled.
  • Limited interactive experimentation.
  • Changes follow a deployment process.
  • Access and activity audited.

The goal isn't an unrestricted dev environment; it's productive experimentation without exposing production data or credentials.

19.1.3Compute Policies

A compute policy limits which configurations users can create: node types, worker counts, autoscaling, runtime versions, auto-termination, access modes, and required tags. Without one, someone runs a 20-worker cluster for a tiny job, or leaves a cluster running overnight.

SettingDevelopment rule (example)
Maximum workers4
Auto-terminationRequired (10–60 min)
RuntimeApproved LTS only
Access modeStandard or dedicated
Required tagsEnvironment, Owner, CostCenter
Node typesTwo approved sizes
JSON · policy definition
{
  "spark_version": { "type": "allowlist", "values": ["auto:latest-lts"], "defaultValue": "auto:latest-lts" },
  "node_type_id": { "type": "allowlist", "values": ["Standard_D4ds_v5", "Standard_D8ds_v5"], "defaultValue": "Standard_D4ds_v5" },
  "autoscale.min_workers": { "type": "fixed", "value": 1, "hidden": true },
  "autoscale.max_workers": { "type": "range", "maxValue": 4, "defaultValue": 2 },
  "autotermination_minutes": { "type": "range", "minValue": 10, "maxValue": 60, "defaultValue": 30 },
  "data_security_mode": { "type": "allowlist", "values": ["USER_ISOLATION", "SINGLE_USER"] },
  "custom_tags.Environment": { "type": "fixed", "value": "dev" },
  "custom_tags.Owner": { "type": "unlimited", "isOptional": false },
  "custom_tags.CostCenter": { "type": "allowlist", "values": ["CC-RETAIL-01", "CC-FIN-02"] }
}

The original text described policies only in words; this is what one looks like (Compute → Policies → Create). fixed pins a value, range bounds it, allowlist restricts choices, and "isOptional": false forces users to fill it in. USER_ISOLATION and SINGLE_USER are the API names for standard and dedicated access modes. Node types are Azure examples. These are organizational rules, not Databricks defaults. Policies govern classic compute; serverless (including Free Edition) is governed by budget policies and workspace settings instead.

A user can create a notebook but lack permission to read a production table, or read a table but not create arbitrary compute. Apply compute and data governance together.

19.1.4Workspace Permissions

Workspace permissions control who can do what with notebooks, jobs, experiments, dashboards, SQL warehouses, and other objects. Levels vary by object type; for jobs they are CAN VIEW, CAN MANAGE RUN, IS OWNER, and CAN MANAGE.

GroupAccess to production job pl_customer_daily_load
Data EngineeringManage jobs in development; at most view in production
Production SupportCAN MANAGE RUN: view runs, rerun, cancel, investigate
Data Platform AdminsCAN MANAGE: change job configuration
Business AnalystsNone; they read reporting data, not ingestion jobs
Workspace permissions are not data permissions

Opening a notebook that contains spark.table("prod_catalog.finance.transactions") doesn't let you read that table; the query still passes Unity Catalog authorization. Likewise, access to a SQL warehouse doesn't grant access to every table it can query.

19.1.5User Management and Groups

In enterprises, users come from the organization's identity system rather than being added to each resource by hand. Microsoft Entra ID users and groups are provisioned into the Databricks account (through automatic identity management or SCIM) and then assigned to workspaces.

GroupPurpose
dbx-platform-adminsPlatform administration
dbx-data-engineersDevelopment and data engineering
dbx-production-supportProduction troubleshooting
dbx-business-analystsApproved reporting access
dbx-finance-readersFinance data access
dbx-customer-data-restrictedApproved access to sensitive customer data

Why groups? Granting 30 analysts one by one is unmaintainable as people join, move, and leave. Grant to a group and manage membership centrally. Reading one table takes three grants:

SQL · Unity Catalog
GRANT USE CATALOG ON CATALOG reporting           TO `dbx-business-analysts`;
GRANT USE SCHEMA  ON SCHEMA  reporting.sales     TO `dbx-business-analysts`;
GRANT SELECT      ON TABLE   reporting.sales.daily_sales TO `dbx-business-analysts`;

Run as an identity allowed to grant (the owner, or someone with MANAGE). The group also needs workspace access and a compute resource or SQL warehouse it can use. Use account-level groups for Unity Catalog grants; legacy workspace-local groups can't be granted UC privileges.

19.1.6Service Principals

A service principal is an identity for applications and automation: scheduled jobs, CI/CD deployments, API automation, external orchestrators, and programmatic administration.

Why production jobs need one

A pipeline owned by an engineer runs fine for six months. The engineer leaves, their account is disabled, and the pipeline stops. A dedicated service principal is a stable execution identity that doesn't depend on any one person. Set it as the job's Run as identity.

Azure Data Factory
        |
        | authenticates with approved credentials
        v
Databricks production workspace
        |
        | runs job as dedicated service principal
        v
Unity Catalog
        |
        | checks granted privileges
        v
Production Delta tables

Give it only what the job needs. Azure Databricks supports Databricks-managed service principals (OAuth secrets issued by Databricks; enough for Databricks-only automation) and Microsoft Entra ID-managed ones (needed when the same identity must also reach other Azure resources). Docs: Manage service principals.

19.2Identity and Authentication

19.2.1Authentication Versus Authorization

Two questions

Authentication: who are you?
Authorization: what are you allowed to do?

Signing in successfully grants nothing by itself; Databricks then evaluates the permissions of that identity.

Valid login, query denied

SELECT * FROM prod_catalog.finance.transactions; can fail because of:

  • Missing USE CATALOG.
  • Missing USE SCHEMA.
  • Missing SELECT.
  • A workspace binding restricting the catalog.
  • A row filter returning no rows (looks like empty data, not an error).

19.2.2Microsoft Entra ID Integration

Entra ID (formerly Azure AD) provides corporate sign-in and SSO, users and groups, application identities, Conditional Access and MFA through organizational policy, and lifecycle management.

Identity lifecycle

  1. User joins the organization.
  2. Added to the right groups.
  3. Gets approved workspace access.
  4. Job and data permissions assigned as needed.
  5. Changes responsibilities.
  6. Permissions reviewed and updated.
  7. Leaves the organization.
  8. Access revoked via the identity process.

Automated provisioning means leavers lose access when they're disabled in Entra ID, rather than when someone remembers. Docs: Authentication and access control.

19.2.3Service-Principal Authentication, OAuth, and Access Tokens

CI/CD pipeline
      |
      | OAuth (client ID + secret, or
      | workload identity federation)
      v
Service principal access token
      |
      | authorized API request
      v
Databricks workspace
      |
      v
Deploy job / notebook / configuration

The deployment flow

  1. Obtain a short-lived token through an approved OAuth flow.
  2. Authenticate to Databricks.
  3. Call an authorized API.
  4. Perform the deployment.
  5. Finish without exposing a reusable human credential.

OAuth is an authorization framework that grants applications access without sharing a user's password.

TermMeaning
ClientApplication requesting access
Resource serverService hosting the protected resource
Authorization serverIssues tokens
Access tokenCredential used to call an authorized resource; short-lived
ScopeThe access being requested, where applicable
Client IDIdentifies the application (for a service principal, its application ID)
Client secretConfidential credential used in machine-to-machine flows

Flows

  • Machine-to-machine (M2M): a service principal with client ID and secret. Jobs, CI/CD.
  • User-to-machine (U2M): browser sign-in for an interactive user, e.g. databricks auth login.
  • Workload identity federation: CI systems (GitHub Actions, Azure DevOps) exchange their own token, so no secret is stored at all.

Not every flow supports every API; check the docs for the integration.

Python · Databricks SDK, OAuth M2M
import os
from databricks.sdk import WorkspaceClient

# Credentials come from the environment (set by the CI system),
# never from source code
w = WorkspaceClient(
    host=os.environ["DATABRICKS_HOST"],
    client_id=os.environ["DATABRICKS_CLIENT_ID"],
    client_secret=os.environ["DATABRICKS_CLIENT_SECRET"],
)

# The SDK fetches and refreshes short-lived tokens itself
print(w.current_user.me().user_name)   # the SP's application ID

The SDK and CLI read DATABRICKS_HOST, DATABRICKS_CLIENT_ID, and DATABRICKS_CLIENT_SECRET automatically, so WorkspaceClient() with no arguments works too. Not run here (needs a workspace).

Handling tokens

A token isn't a password, but anyone holding a valid one can act with its permissions until it expires. Get it through the supported mechanism, keep it in memory, send it only to the intended service, never log it, and let it expire or revoke it.

Python · bad practice
# BAD: token in source code (leaks via Git, screenshots, shared files)
token = "dapi-example-sensitive-token"

# BAD: headers often contain "Authorization: Bearer ..."
print(request_headers)

Better practice

  • Dedicated automation identity, not a person's account.
  • OAuth instead of long-lived personal access tokens (PATs).
  • Secrets in a controlled store.
  • Minimal permissions.
  • Admins can restrict or disable PATs in workspace settings.

19.2.4Secret Management and Secret Scopes

Secrets are database passwords, API keys, client secrets, and connection credentials. Databricks secret scopes store them; on Azure a scope can be Azure Key Vault-backed (secrets stay in Key Vault, created from the workspace UI) or Databricks-backed.

Bash · Databricks CLI (Databricks-backed scope)
databricks secrets create-scope retail-dev-secrets

# Prompts for the value, so it never appears in shell history
databricks secrets put-secret retail-dev-secrets source-db-password

databricks secrets list-secrets retail-dev-secrets

# Let only the prod job's service principal read prod secrets
databricks secrets put-acl retail-prod-secrets \
    &lt;sp-application-id&gt; READ
Python · notebook
db_password = dbutils.secrets.get(
    scope="retail-dev-secrets",
    key="source-db-password",
)

print(db_password)   # shows [REDACTED] — but don't rely on that

# Redaction only catches the exact string. Transformed values
# (e.g. reversed, split, base64) are NOT redacted. Never print,
# log, or put secrets in exception messages.

Scope ACLs are READ, WRITE, and MANAGE. Separate scopes by environment and purpose (retail-dev-secrets, retail-test-secrets, retail-prod-secrets), and don't give developers access to production secrets just because they use the dev workspace.

FeatureMain purpose
Secret scopeStore and retrieve secrets in code
UC storage credentialThe identity Unity Catalog uses to reach external storage
UC external locationGovern access to a specific storage path
Managed identityIdentity-based authentication with no password or secret in code

For Azure storage, prefer identity-based access (an access connector's managed identity) over distributing storage account keys.

19.2.5Credential Management

The full lifecycle: create through an approved mechanism, distribute in a controlled way, store in an approved place, restrict access, rotate, manage expiry, revoke when compromised or unneeded, and audit access and changes.

Python · insecure
connection_string = (
    "Server=sqlserver01;"
    "Database=RetailSourceDB;"
    "User Id=admin;"                 # admin account!
    "Password=HardcodedPassword;"    # in code, in Git
)
Python · improved
jdbc_url = ("jdbc:sqlserver://sqlserver01:1433;"
            "databaseName=RetailSourceDB;"
            "encrypt=true;trustServerCertificate=false")

df = (spark.read.format("jdbc")
      .option("url", jdbc_url)
      .option("dbtable", "dbo.customers")
      .option("user", dbutils.secrets.get("retail-prod-secrets", "sql-user"))
      .option("password", dbutils.secrets.get("retail-prod-secrets", "sql-password"))
      .load())

The original's improved version fetched the password but didn't show it in use. Here the secret goes straight into the reader, the account is a dedicated read-only one rather than admin, and TLS is enforced with certificate validation. Rotating the password now means updating the secret, not the code. Where supported, managed identity is better still. On Unity Catalog, Lakehouse Federation connections can hold the credential centrally so notebooks never see it.

19.2.6Least-Privilege Access

Grant each identity only what its responsibilities require. A pipeline that reads customer data and writes a curated table needs read on its sources, write on its target, use of the containing catalog and schemas, and permission to run its job. It doesn't need workspace admin, unrelated finance tables, rights on every production catalog, control of other service principals, or unrelated secrets.

Correction: grant to service principals by application ID

The original granted to `sp-retail-customer-load`, the display name. In Unity Catalog SQL, a service principal is referenced by its application ID (a UUID), in backticks. A display name fails with a principal-not-found error. Find the ID under Settings → Identity and access → Service principals.

SQL
-- sp-retail-customer-load (application ID shown here as an example)
GRANT USE CATALOG ON CATALOG prod_catalog
  TO `6f1c2a9e-1b2d-4c3e-9f80-0a1b2c3d4e5f`;

GRANT USE SCHEMA ON SCHEMA prod_catalog.bronze
  TO `6f1c2a9e-1b2d-4c3e-9f80-0a1b2c3d4e5f`;

GRANT SELECT ON TABLE prod_catalog.bronze.customer_source
  TO `6f1c2a9e-1b2d-4c3e-9f80-0a1b2c3d4e5f`;

To write a target, add only what that operation needs: appending, updating, or deleting requires MODIFY on the table (a MERGE also needs SELECT to read it). Don't grant ALL PRIVILEGES to make a permission error disappear.

19.3Network Security

Authentication controls who gets in; network security controls how systems communicate and which paths are permitted. There are three distinct paths, each with its own controls.

  (1) Front-end              (2) Back-end                 (3) Data access
  Users / apps  ------>  Databricks control plane  <------  Compute plane  ------>  ADLS, SQL Server,
  to the workspace         (web app, APIs, jobs)          (clusters, serverless)     APIs, SaaS

19.3.1Private Connectivity

Azure Private Link creates private connections to Azure services, including Azure Databricks in supported configurations, reducing exposure to public networks. It can cover user access to the workspace (front-end), classic compute to the control plane (back-end), and serverless compute to your resources. These are separate paths; enabling one doesn't secure the others.

19.3.2Network Controls and IP Access Lists

Controls include VNet configuration, Network Security Groups, firewalls, private endpoints, IP access lists, domain-based controls, serverless egress controls, and storage firewall rules.

Correct password, connection still fails

A job can't reach sql-prod.internal.example because:

  • DNS can't resolve the hostname.
  • A firewall blocks the port.
  • The database rejects the compute network.
  • A route is missing.
  • TLS is misconfigured.
  • The database rejects the identity.

Troubleshoot both identity and network.

IP access lists

Restrict workspace or account-console access to approved ranges: office networks, the corporate VPN, admin networks.

  • Include VPN and admin paths, or you lock yourself out.
  • Include CI/CD agents and automation.
  • Test before applying broadly.
  • Document a recovery procedure.
  • Ingress lists don't control outbound traffic from compute.

19.3.3Firewalls and Secure Connectivity to Sources

A firewall between compute and, say, an on-premises SQL Server should permit only required connections; avoid unrestricted outbound access where tighter control is feasible.

Pre-deployment connectivity checklist

  • Can compute resolve the hostname?
  • Is the destination IP reachable?
  • Is the port open?
  • Does the destination accept the connection?
  • Is TLS configured correctly?
  • Is the workload using the expected identity?
  • Does the source authorize that identity?
  • Are network and auth failures logged (without credentials)?
LayerExample
IdentityDedicated DB account or managed identity
AuthenticationOAuth, integrated auth, or protected credentials
AuthorizationRead only the needed source tables
NetworkPrivate or restricted route
TransportTLS
Secret storageApproved secret manager
LoggingFailures logged, credentials never

Sources include SQL Server, Oracle, ADLS, REST APIs, SaaS, and on-prem databases. A pipeline reading RetailSourceDB should use a dedicated read-only account, never the DBA account.

This syllabus topic wasn't covered in the original text; here's the essential Azure picture.

19.4Data Security

19.4.1Unity Catalog Permissions

Unity Catalog governs access to data and related resources through grants and ownership. You've used its three-level names since Chapter 4; here's the security side.

Metastore
   |
   +-- Catalog            prod_catalog
         |
         +-- Schema         bronze / silver / gold
               |
               +-- Table      customers, orders
               +-- View       customer_summary
               +-- Function   mask_email
               +-- Volume     raw files
PrivilegePurpose
USE CATALOGUse a catalog
USE SCHEMAUse a schema
SELECTRead tables or views
MODIFYInsert, update, delete
CREATE TABLECreate tables in a schema
EXECUTERun functions
READ FILES / WRITE FILESFile access via an external location or volume
MANAGEManage grants on the object (without owning it)
Privileges inherit downward

GRANT SELECT ON SCHEMA prod_catalog.gold gives SELECT on every current and future table in that schema. That's convenient for a reporting layer but too broad when only one table is approved. You still need USE CATALOG and USE SCHEMA to reach anything.

SQL · read-only access, then review it
GRANT USE CATALOG ON CATALOG reporting                 TO `dbx-finance-readers`;
GRANT USE SCHEMA  ON SCHEMA  reporting.finance         TO `dbx-finance-readers`;
GRANT SELECT      ON TABLE   reporting.finance.monthly_revenue TO `dbx-finance-readers`;

-- Who has what on this table?
SHOW GRANTS ON TABLE reporting.finance.monthly_revenue;

-- What does one group have on the schema?
SHOW GRANTS `dbx-finance-readers` ON SCHEMA reporting.finance;

-- Remove access
REVOKE SELECT ON TABLE reporting.finance.monthly_revenue FROM `dbx-finance-readers`;

Permissions should reflect actual responsibilities, not membership of a broad technical team. Docs: Unity Catalog access control.

19.4.2Storage Credentials and External Locations

Storage credential

The identity Unity Catalog uses to reach external storage. On Azure, usually an access connector's managed identity, which is granted a role (e.g. Storage Blob Data Contributor) on the storage account. It moves storage authentication out of notebook code.

External location

Binds a storage path such as abfss://retail@stretailprod.dfs.core.windows.net/bronze/ to a storage credential, creating one governance point for that path. Without it, people reach storage through scattered keys and nobody can say who reads what.

Databricks job
      |
      v
Unity Catalog         (checks the job's grants)
      |
      v
External location     (governed path)
      |
      v
Storage credential    (managed identity)
      |
      v
Azure Data Lake Storage
SQL
CREATE EXTERNAL LOCATION IF NOT EXISTS retail_bronze_location
  URL 'abfss://retail@stretailprod.dfs.core.windows.net/bronze/'
  WITH (STORAGE CREDENTIAL retail_prod_credential)
  COMMENT 'Raw source files';

-- Let the ingestion SP read the landing files
GRANT READ FILES ON EXTERNAL LOCATION retail_bronze_location
  TO `6f1c2a9e-1b2d-4c3e-9f80-0a1b2c3d4e5f`;
External locationPurpose
retail_bronze_locationRaw source files
retail_silver_locationCleansed, standardized data
retail_export_locationApproved outbound exports

Reading a registered table and reading its underlying files are different access paths; govern both. Grant READ FILES on locations sparingly, since file access bypasses table-level row filters and masks.

19.4.3Row Filters

A row filter restricts which rows a user sees, enforced in Unity Catalog for every query and every tool. Regional managers should see only their region:

Regional manager queries sales
              |
              v
     Row filter function
              |
   +----------+----------+
   |          |          |
 North      South      West
 manager    manager    manager
   |          |          |
 North      South      West
 rows       rows       rows

How it works

  1. Write a SQL function returning BOOLEAN.
  2. Attach it: ALTER TABLE … SET ROW FILTER fn ON (column).
  3. Unity Catalog adds it to every query; rows where it's false are invisible.

One filter per table.

SQL · filter by a governed mapping table
-- Who may see which region (maintained by data owners, not users)
CREATE TABLE prod_catalog.security.region_access (user_email STRING, region STRING);

CREATE OR REPLACE FUNCTION prod_catalog.security.region_filter(row_region STRING)
RETURNS BOOLEAN
RETURN is_account_group_member('dbx-platform-admins')
    OR EXISTS (
         SELECT 1 FROM prod_catalog.security.region_access a
         WHERE a.user_email = session_user()
           AND a.region = row_region
       );

ALTER TABLE prod_catalog.gold.sales SET ROW FILTER prod_catalog.security.region_filter ON (region);

-- Remove: ALTER TABLE prod_catalog.gold.sales DROP ROW FILTER;
Never filter on a user-supplied value

A notebook parameter like region = "North" can be changed by the user. Security must be enforced in the governed layer from session_user() or group membership, which users can't fake.

The original described row filters only conceptually; this uses the documented syntax. A filtered-out user sees zero rows, not an error, which can look like missing data. Compute: SQL warehouses, standard access mode, or dedicated access mode on Runtime 15.4 LTS+.

19.4.4Column Masks

A column mask changes what a user sees in one column. General analysts get customer names but not full emails or phone numbers; approved customer-service users see full values.

SQL
CREATE OR REPLACE FUNCTION prod_catalog.security.mask_email(email STRING)
RETURNS STRING
RETURN CASE
  WHEN is_account_group_member('dbx-customer-data-restricted') THEN email
  WHEN email IS NULL THEN NULL
  ELSE concat(left(email, 1), '***@', substring_index(email, '@', -1))
END;

CREATE OR REPLACE FUNCTION prod_catalog.security.mask_phone(phone STRING)
RETURNS STRING
RETURN CASE
  WHEN is_account_group_member('dbx-customer-data-restricted') THEN phone
  WHEN phone IS NULL THEN NULL
  ELSE concat('******', right(regexp_replace(phone, '[^0-9]', ''), 4))
END;

ALTER TABLE prod_catalog.silver.customer_clean
  ALTER COLUMN email_address SET MASK prod_catalog.security.mask_email;
ALTER TABLE prod_catalog.silver.customer_clean
  ALTER COLUMN phone_number SET MASK prod_catalog.security.mask_phone;

I ran the masking expressions on Spark 4 to confirm the output above; SET MASK itself is Databricks-only. Drop a mask or filter before dropping its function, or the table becomes unreadable. For many tables, Databricks also offers centralized attribute-based access control (ABAC) with governed tags, where available.

19.4.5Data Access Auditing

Auditing answers: who ran this job, which identity executed the query, when a permission changed, who accessed a sensitive table, and who changed the job configuration. Databricks records these in system tables.

SQL · platform audit log (system.access.audit)
-- Unity Catalog permission changes in the last 7 days
SELECT event_time,
       user_identity.email AS changed_by,
       action_name,
       request_params
FROM system.access.audit
WHERE service_name = 'unityCatalog'
  AND action_name = 'updatePermissions'
  AND event_date >= current_date() - INTERVAL 7 DAYS
ORDER BY event_time DESC;

System tables must be enabled by an admin and access granted. system.access.table_lineage also shows which identities read or wrote each table. Chapter 20 uses system tables for monitoring.

SQL · application-level audit table
CREATE TABLE IF NOT EXISTS prod_catalog.ops.pipeline_security_audit (
    audit_id STRING,
    pipeline_name STRING,
    execution_identity STRING,     -- e.g. from current_user() inside the job
    environment STRING,
    action STRING,
    status STRING,
    event_timestamp TIMESTAMP
);
Two kinds of audit

Your own table records pipeline events (like Chapter 18's audit tables). It does not replace platform audit logs: a pipeline can't record actions it doesn't perform, and its rows can be edited by anyone with MODIFY. Use platform logs for security events.

19.5.4Production Security Checklist

Identity and access

  • Centralized identity management.
  • Organizational auth requirements (SSO, MFA).
  • Groups for access management.
  • Restricted admin privileges.
  • Dedicated SPs for production automation.
  • Least privilege for data and compute.
  • Periodic reviews.

Secrets and credentials

  • No hardcoded credentials.
  • Approved secret management.
  • Identity-based auth where possible.
  • Restricted production secrets.
  • Rotation and revocation procedures.
  • No secrets in logs or source control.

Network security

  • Documented inbound and outbound connections.
  • Private connectivity where required.
  • Firewall rules for needed destinations only.
  • Workspace access from approved networks.
  • DNS and routing verified.
  • Connectivity tested after changes.

Data governance

  • Tables governed by Unity Catalog.
  • Grants at the right level.
  • External storage access controlled.
  • Row filters and masks where required.
  • Sensitive-data access audited.
  • No unnecessary raw-data access.

Operations

Separate dev and prod · version control and controlled deployments · monitor failures and unusual behavior · review compute usage and cost · documented incident response and access revocation · tested recovery and rollback.

19.6.2Part B: Lab You Can Run on Free Edition

Free Edition has one user (you), so you can't test other people's access, but you can see a row filter and masks change what you see. Run in a SQL editor or notebook. Use the workspace catalog on Free Edition or retail_dev elsewhere.

SQL · 1. Set up
CREATE SCHEMA IF NOT EXISTS retail_dev.security;

CREATE OR REPLACE TABLE retail_dev.security.customers (
  customer_id INT, customer_name STRING, email_address STRING,
  phone_number STRING, region STRING
);
INSERT INTO retail_dev.security.customers VALUES
  (101, 'Customer A', 'asha.rao@example.com', '+91 98450 12345', 'North'),
  (102, 'Customer B', 'vikram@example.com',   '+91 99000 67890', 'South'),
  (103, 'Customer C', NULL,                   NULL,              'West');

-- Grant yourself North only
CREATE OR REPLACE TABLE retail_dev.security.region_access (user_email STRING, region STRING);
INSERT INTO retail_dev.security.region_access VALUES (session_user(), 'North');
SQL · 2. Create and attach the policies
CREATE OR REPLACE FUNCTION retail_dev.security.region_filter(row_region STRING)
RETURNS BOOLEAN
RETURN is_account_group_member('dbx-platform-admins')
    OR EXISTS (SELECT 1 FROM retail_dev.security.region_access a
               WHERE a.user_email = session_user() AND a.region = row_region);

CREATE OR REPLACE FUNCTION retail_dev.security.mask_email(email STRING)
RETURNS STRING
RETURN CASE
  WHEN is_account_group_member('dbx-customer-data-restricted') THEN email
  WHEN email IS NULL THEN NULL
  ELSE concat(left(email, 1), '***@', substring_index(email, '@', -1))
END;

ALTER TABLE retail_dev.security.customers
  SET ROW FILTER retail_dev.security.region_filter ON (region);
ALTER TABLE retail_dev.security.customers
  ALTER COLUMN email_address SET MASK retail_dev.security.mask_email;
SQL · 3. Observe, change access, observe again
SELECT * FROM retail_dev.security.customers;
-- Expected: only 101 / North, email shown as a***@example.com
-- (you're not in dbx-platform-admins or dbx-customer-data-restricted)

INSERT INTO retail_dev.security.region_access VALUES (session_user(), 'South');
SELECT * FROM retail_dev.security.customers;
-- Expected: 101 and 102, both emails masked. No code changed, only the mapping.

-- 4. Clean up: drop policies BEFORE their functions
ALTER TABLE retail_dev.security.customers DROP ROW FILTER;
ALTER TABLE retail_dev.security.customers ALTER COLUMN email_address DROP MASK;
SELECT * FROM retail_dev.security.customers;   -- all 3 rows, real emails
What this proves, and what was tested

Access is driven by governed data (the mapping table and group membership), not by anything the user can pass in. I verified the masking and mapping logic on Spark 4 (North visible, South and West hidden; a***@example.com; nulls preserved). The SET ROW FILTER and SET MASK statements are Databricks-only and weren't run here; the expected results follow the documented behavior. As the table owner you could simply drop the filter, which is why, in production, the owner should be a group or SP, not the users being filtered.

19.8Interview Questions and Answers

Try answering each before revealing the answer.

Q1. Workspace admin vs Unity Catalog administration?
A workspace admin manages workspace resources and settings. Unity Catalog administration (metastore admins, object owners) governs data objects, permissions, and the metastore. They can overlap but aren't interchangeable; a workspace admin doesn't automatically read all data.
Q2. Why should production jobs use service principals?
They're dedicated automation identities that don't depend on any employee, and permissions can be granted precisely to the workload.
Q3. Least privilege?
Giving an identity only the permissions its responsibilities require, rather than broad workspace or catalog access.
Q4. Authentication vs authorization?
Authentication verifies identity; authorization decides what that identity may access or do.
Q5. Why not hardcode credentials in notebooks?
They leak through Git, logs, output, and shared files, and rotation requires code changes. Use secret scopes or identity-based authentication.
Q6. Purpose of Unity Catalog?
Centralized governance of data and related assets: permissions, ownership, fine-grained controls, lineage, and auditing across workspaces.
Q7. Storage credential vs external location?
A storage credential is the identity used to reach external storage; an external location binds a storage path to that credential and is the governance point for the path.
Q8. Row filter vs column mask?
A row filter restricts which records you see; a column mask restricts which values you see in a column. Both are SQL functions attached to the table.
Q9. Securing a pipeline from Databricks to SQL Server?
Dedicated read-only workload identity, credentials from a secret scope or identity-based auth, private/restricted network path, TLS with certificate validation, and failure logging without credentials.
Q10. Separating dev and prod?
Separate workspaces and catalogs with workspace bindings, separate credentials and secret scopes, compute policies, restricted prod access, and deployment through version control and CI/CD as a service principal.
Q11. Does SELECT on a table grant everything needed?
No. You also need USE CATALOG and USE SCHEMA, workspace access, and compute or a warehouse; bindings, row filters, and masks may still restrict results.
Q12. Investigating a production permission failure?
Identify the executing principal (the job's run-as), check catalog/schema/table privileges with SHOW GRANTS, check bindings and storage or network controls, reproduce as that identity, and grant only the justified missing privilege.
Q13. How do you reference a service principal in GRANT?
By its application ID (a UUID) in backticks, not its display name.
Q14. Key Vault-backed vs Databricks-backed secret scope?
Key Vault-backed scopes read secrets that stay in Azure Key Vault (managed there); Databricks-backed scopes store secrets in Databricks. Both are read with dbutils.secrets.get.
Q15. OAuth M2M vs U2M?
M2M: a service principal authenticates with client credentials for unattended automation. U2M: an interactive user signs in through a browser.
Q16. What happens when you GRANT SELECT on a schema?
The grantee can read all current and future tables in it (with USE CATALOG/USE SCHEMA), because privileges inherit downward.
Q17. What's secure cluster connectivity?
Cluster nodes have no public IPs and no open inbound ports; they connect outbound to the control plane.
Q18. Where do you find who changed a permission?
The platform audit log, e.g. system.access.audit with service_name 'unityCatalog'.
Q19. Why can a user with READ FILES weaken table security?
Reading underlying files directly bypasses table-level row filters and column masks.
Q20. A user sees an empty table but no error. Security cause?
A row filter that returns false for every row for that user.
