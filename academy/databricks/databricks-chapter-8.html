File Formats

8.1.1Introduction to File Formats

A file format defines how data is structured and stored. Choosing the right one affects storage size, read and write performance, query speed, schema management, compression, engine compatibility, and support for incremental processing. A typical pattern: an application delivers daily CSV files, and a Databricks pipeline reads, validates, and transforms them, then stores the cleaned output as Delta.

FormatStorage typeHuman-readableSchema supportTypical use
CSVText-basedYesLimitedData exchange and source files
JSONText-basedYesEmbedded structureAPIs and semi-structured data
ParquetColumnar binaryNoYesAnalytics and data warehousing
AvroRow-oriented binaryNoYesEvent streaming and data exchange
ORCColumnar binaryNoYesAnalytical processing
TextPlain textYesNo tabular schemaLogs and unstructured data
DeltaParquet + transaction logNoYesReliable analytical pipelines

Row-based versus columnar storage

Row-based: records together
101,John,Hyderabad,50000
102,David,Chennai,60000
103,Smith,Bengaluru,55000

Good when applications read complete records. Avro is a common row-oriented format.

Columnar: values by column
CustomerID: 101, 102, 103
Name:       John, David, Smith
City:       Hyderabad, Chennai, Bengaluru
Salary:     50000, 60000, 55000

A query needing only CustomerID and Salary can skip other columns. Parquet and ORC are columnar.

Important

Delta isn't just another encoding format. It's a table format that uses Parquet data files plus a transaction log to provide table-level capabilities.

8.1.2CSV

CSV (Comma-Separated Values) stores tabular data as text: one record per line, fields usually separated by commas.

CustomerID,CustomerName,City,Age
101,John,Hyderabad,35
102,David,Chennai,40
103,Smith,Bengaluru,29

Advantages

  • Easy to understand.
  • Easy to generate and inspect.
  • Supported by almost every tool.
  • Good for exchanging data between applications.

Limitations

  • No reliable built-in data types; everything is text.
  • Type conversion is often needed.
  • Large CSVs are expensive to process.
  • Commas, quotes, and line breaks in fields need correct escaping.
  • Schema changes are hard to detect.
Python
df = (
    spark.read
    .format("csv")
    .option("header", "true")        # first row = column names
    .option("inferSchema", "true")   # infer data types
    .option("mode", "FAILFAST")      # stop on a malformed record
    .load("/Volumes/main/bronze/raw/customers.csv")
)

display(df)

Schema inference is convenient for exploration; explicit schemas are generally preferable in production ingestion.

8.1.3JSON

JSON (JavaScript Object Notation) is a text format used by REST APIs, applications, and event-producing systems. It supports nested objects and arrays.

JSON · flat
{
  "CustomerID": 101,
  "CustomerName": "John",
  "City": "Hyderabad",
  "Age": 35
}
JSON · nested
{
  "CustomerID": 101,
  "CustomerName": "John",
  "Address": {
    "City": "Hyderabad",
    "State": "Telangana"
  },
  "Orders": [
    {"OrderID": 1001, "Amount": 2500.50},
    {"OrderID": 1002, "Amount": 1500.00}
  ]
}
Python
df = (
    spark.read
    .format("json")
    .option("multiLine", "true")
    .load("/Volumes/main/bronze/raw/customers.json")
)

display(df)

Use multiLine=true when each JSON document spans multiple lines. For one complete object per line, the default reader is usually right. Common uses: API ingestion, application events, nested business data, semi-structured sources, and logs.

8.1.4Parquet

Parquet is a columnar format built for analytics, with compression, efficient column access, and typed storage. Unlike CSV, it stores data types in its schema (e.g. CustomerID integer, CustomerName string, Salary decimal).

Read
df = spark.read.parquet(
    "/Volumes/main/silver/customers/"
)

display(df)
Write
(
    df.write
    .format("parquet")
    .mode("overwrite")
    .save("/Volumes/main/silver/customers/")
)

Advantages

  • Efficient column-level reads.
  • Good compression.
  • Typed storage and nested data support.
  • Works with Spark and many engines.
  • Less I/O when selecting a subset of columns.

Use Parquet when

  • Storing large analytical datasets.
  • Building a curated data lake.
  • Processing structured data efficiently.
  • Sharing data between compatible engines.

Parquet alone doesn't give Delta-style transactional guarantees for a table being modified concurrently.

8.1.5Avro

Avro is a row-oriented binary serialization format whose data follows a schema, usually defined in JSON. The schema specifies the record name, field names and types, nullable fields, and defaults.

Avro schema
{
  "type": "record",
  "name": "Customer",
  "fields": [
    {"name": "CustomerID", "type": "long"},
    {"name": "CustomerName", "type": "string"},
    {"name": "Age", "type": ["null", "int"], "default": null}
  ]
}
Read
df = (
    spark.read
    .format("avro")
    .load("/Volumes/main/bronze/raw/customers_avro/")
)
Write
(
    df.write
    .format("avro")
    .mode("overwrite")
    .save("/Volumes/main/silver/customers_avro/")
)
Considerations
  • Confirm your Databricks runtime supports the Avro features you need.
  • Schema evolution depends on compatibility rules and how data is read.
  • Avro suits data exchange and event-oriented processing.
  • It doesn't provide Delta table transactions.

8.1.6ORC

ORC (Optimized Row Columnar) is, despite its name, a columnar format for efficient analytical queries, compression, and column access, with typed schemas and support for predicate and column pruning.

Read
df = spark.read.orc(
    "/Volumes/main/bronze/raw/customers_orc/"
)
Write
(
    df.write
    .format("orc")
    .mode("overwrite")
    .save("/Volumes/main/silver/customers_orc/")
)

ORC versus Parquet: both are columnar and analytics-friendly; choose by ecosystem, interoperability, compression, and benchmarks. In many Databricks projects, Parquet is common for general file storage and Delta is preferred for managed tables needing transactions.

8.1.7Text Files

Text files hold unstructured or semi-structured content as plain text, such as application logs.

Python

display(df)

Use cases: logs, error messages, unstructured source data, text audit files. Extracting structured fields needs further parsing.

8.1.8Delta Format

Delta Lake adds a transactional table layer on top of Parquet files and is central to Databricks lakehouse architectures.

Main components

1. Parquet data files hold the records.

2. The transaction log (_delta_log) holds history and metadata that define the current table state. It enables atomic updates, consistent reads, schema enforcement, controlled schema evolution, updates and deletes, table history, and time travel (subject to retained data and logs).

customers_delta/
│
├── part-00000-....snappy.parquet
├── part-00001-....snappy.parquet
│
└── _delta_log/
    ├── 00000000000000000000.json
    ├── 00000000000000000001.json
    └── ...
Python
# Read Delta by path
df = spark.read.format("delta").load(
    "/Volumes/main/silver/customers_delta/"
)

# Write Delta to a path
(
    df.write
    .format("delta")
    .mode("overwrite")
    .save("/Volumes/main/silver/customers_delta/")
)

# Save as a Delta table (catalog and schema must exist)
(
    df.write
    .format("delta")
    .mode("overwrite")
    .saveAsTable("main.silver.customers")
)

8.2.5Schema Inference

Schema inference lets Spark determine column types from the input.

Python

    spark.read
    .option("header", "true")

    .csv("/Volumes/main/bronze/raw/customers.csv")

df.printSchema()
root
 |-- CustomerID: integer
 |-- CustomerName: string
 |-- Age: integer
 |-- Salary: double

Advantages

  • Less code.
  • Convenient for exploration.
  • Useful when the structure is unknown.

Disadvantages

  • Extra pass to inspect input.
  • More ingestion overhead.
  • Inconsistent types when values vary.
  • May not match the business schema.
  • Less predictable production pipelines.
CustomerID,Salary
101,50000

Potential issue

The UNKNOWN value complicates numeric inference; Salary becomes a string. Define how such values are interpreted instead of assuming every value is valid.

8.2.6Explicit Schemas

An explicit schema defines names and types before reading, and is generally recommended for production.

Python
from pyspark.sql.types import (
    StructType,
    StructField,
    IntegerType,
    StringType,
    DecimalType
)

customer_schema = StructType([
    StructField("CustomerID", IntegerType(), True),
    StructField("CustomerName", StringType(), True),
    StructField("City", StringType(), True),
    StructField("Salary", DecimalType(12, 2), True)
])

df = (
    spark.read
    .format("csv")
    .option("header", "true")
    .schema(customer_schema)
    .csv("/Volumes/main/bronze/raw/customers.csv")
)

Benefits: predictable types, less reliance on inference, control over the target model, easier validation, and consistency between runs.

Important

An explicit schema doesn't automatically reject every invalid value. Depending on format, parser, and read mode, conversion failures can become nulls or malformed records. Validate important fields after reading.

8.2.7Handling Corrupt Records

Corrupt records are ones Spark can't parse against the expected format or schema: invalid CSV quoting, malformed JSON, wrong field structure, invalid data representations.

ModeBehavior
PERMISSIVEReads valid data and captures malformed records where supported
DROPMALFORMEDDrops records identified as malformed
FAILFASTThrows an error on a malformed record
Python · capture malformed CSV records
from pyspark.sql.types import (
    StructType,
    StructField,
    IntegerType,
    StringType
)

schema = StructType([
    StructField("CustomerID", IntegerType(), True),
    StructField("CustomerName", StringType(), True),
    StructField("_corrupt_record", StringType(), True)
])

df = (
    spark.read
    .format("csv")
    .schema(schema)
    .option("header", "true")
    .option("mode", "PERMISSIVE")
    .option("columnNameOfCorruptRecord", "_corrupt_record")
    .csv("/Volumes/main/bronze/raw/customers.csv")
)

When capturing malformed input this way, the corrupt-record column must be in the supplied schema. Rows that parse correctly get null in _corrupt_record; malformed rows keep their raw text there.

Malformed ≠ business-invalid

Rows like 101,John may parse perfectly even when the business requires a non-null email. That requirement must be checked separately with data-quality rules (Section 8.4).

8.2.8Handling Missing Columns

Missing columns occur when a source file lacks fields the target schema expects.

CustomerID,CustomerName,City
101,John,Hyderabad
CustomerID,CustomerName,City,Email
102,David,Chennai,david@example.com

The target expects Email, but the first file doesn't have it.

  1. Inspect the source header.
  2. Compare it with the expected schema.
  3. Identify missing and unexpected columns.
  4. Apply the agreed schema-evolution policy.
  5. Add missing optional columns as null if permitted.
  6. Reject files that violate required schema rules.
Python
from pyspark.sql import functions as F

# Add a missing optional column
if "Email" not in df.columns:
    df = df.withColumn("Email", F.lit(None).cast("string"))

# Validate required columns
required_columns = ["CustomerID", "CustomerName", "City"]

missing_columns = [
    column
    for column in required_columns
    if column not in df.columns
]

if missing_columns:
    raise ValueError(f"Missing required columns: {missing_columns}")
Important

When a folder holds CSV files with different headers, don't assume Spark aligns each file by column name. Validate individual file schemas before combining them.

Append adds new records to an existing destination.

Common uses: daily ingestion, event data, incremental processing, newly received transactions.

Risk

Append doesn't prevent duplicate business records. Process the same daily file twice and its records are appended twice. Reliable incremental pipelines use a unique key, batch ID, deduplication, or Delta MERGE.

8.3.3Overwrite Mode

Overwrite replaces the existing target data.

Python
(
    df.write
    .format("delta")
    .mode("overwrite")
    .save("/Volumes/main/silver/customers_delta/")
)

Common uses

  • Full refreshes.
  • Rebuilding a target table.
  • Reprocessing complete history.
  • Replacing data after a controlled transformation.

Risks

  • Existing data is replaced.
  • Large datasets need heavy processing.
  • Bad filtering yields an incomplete target.
  • Overwriting production affects downstream consumers.

On Delta tables an overwrite is transactional, but the logical effect is still replacement. Validate source data and target scope first.

8.3.4Error-if-Exists Mode

error / errorifexists fails when the destination already exists, which prevents accidental replacement. Useful for new immutable datasets and one-time exports.

Python
(
    df.write
    .format("parquet")
    .mode("errorifexists")
    .save("/Volumes/main/silver/new_customers/")
)

8.3.5Ignore Mode

ignore silently skips the write when the destination exists.

Python
(
    df.write
    .format("parquet")
    .mode("ignore")
    .save("/Volumes/main/silver/customers_snapshot/")
)
Not an incremental mechanism

If the destination exists, incoming records are not merged; they're dropped. Use it only when skipping is the intended behavior.

8.3.7Writing Partitioned Data

Partitioning groups data by selected column values. A transactions table (TransactionID, CustomerID, TransactionDate, Amount) can be partitioned by year and month:

Python
from pyspark.sql import functions as F

df = (
    df
    .withColumn("Year", F.year("TransactionDate"))
    .withColumn("Month", F.month("TransactionDate"))
)

(
    df.write
    .format("parquet")
    .mode("overwrite")
    .partitionBy("Year", "Month")
    .save("/Volumes/main/silver/transactions/")
)
transactions/
│
├── Year=2026/
│   ├── Month=1/
│   ├── Month=2/
│   ├── Month=3/
│   └── ...

Benefits

  • May reduce data scanned.
  • Organizes data by common filters.
  • Can speed up suitable queries.
Avoid over-partitioning

Don't partition by high-cardinality columns like CustomerID, TransactionID, or order IDs. Too many partitions create many small directories and files and increase metadata overhead. Partition by common query filters and data volume. For Delta tables, liquid clustering (Chapter 9) is often a better choice.

8.3.10Controlling Output File Counts

Each DataFrame partition can become a separate output file.

Python
# Check the partition count (not available on serverless compute)
print(df.rdd.getNumPartitions())

# Request eight partitions (shuffles data)
df_repartitioned = df.repartition(8)

(
    df_repartitioned.write
    .format("parquet")
    .mode("overwrite")
    .save("/Volumes/main/silver/customers/")
)

# Reduce partitions, usually without a full shuffle
df_coalesced = df.coalesce(2)

Use repartition() to

redistribute data, increase parallelism, or balance the partition layout.

Use coalesce() to

reduce partitions while avoiding a full shuffle.

Important warning

Don't use coalesce(1) indiscriminately on large data; it concentrates work in one partition. And a single partition doesn't guarantee a single file when writing with partitionBy(). The actual file count can also differ from the requested partition count.

Best practice

Optimize output file sizes and parallelism rather than targeting an arbitrary file count.

Chapter 8 · Lesson 8.4

Data Quality

8.4.1Introduction to Data Quality

Data quality is whether incoming data meets defined technical and business requirements. A pipeline can succeed technically while producing wrong data, so execution status alone isn't enough.

Quality dimensions

  • Completeness.
  • Uniqueness.
  • Validity.
  • Consistency.
  • Accuracy.
  • Timeliness.

Example: order pipeline rules

  • OrderID is not null and is unique.
  • OrderDate is valid.
  • TotalAmount is non-negative.
  • Every order references a valid customer.
  • Record count is within an acceptable range.

8.4.2Duplicate Detection

CustomerIDCustomerName
101John
102David
101John
Python
from pyspark.sql import functions as F

# Detect duplicate keys
duplicate_keys = (
    df.groupBy("CustomerID")
    .count()
    .filter(F.col("count") > 1)
)

display(duplicate_keys)

# Remove completely identical rows
df_distinct = df.distinct()

# Remove duplicates by key
df_deduplicated = df.dropDuplicates(["CustomerID"])
Important distinction

distinct() removes rows identical across all columns. dropDuplicates(["CustomerID"]) keeps one row per customer but doesn't define which when other columns differ. For deterministic deduplication, apply a business rule:

Python · keep the latest record
from pyspark.sql import Window
from pyspark.sql import functions as F

window_spec = (
    Window
    .partitionBy("CustomerID")
    .orderBy(
        F.col("UpdatedAt").desc_nulls_last(),
        F.col("IngestionTimestamp").desc_nulls_last()
    )
)

df_deduplicated = (
    df
    .withColumn("row_num", F.row_number().over(window_spec))
    .filter(F.col("row_num") == 1)
    .drop("row_num")
)

If both ordering columns tie, add another deterministic tie-breaker such as a source sequence number or unique ingestion ID.

8.4.3Null Validation

Python
from pyspark.sql import functions as F

# Find nulls
display(df.filter(F.col("CustomerID").isNull()))

# Count nulls in one column
display(
    df.select(
        F.count(F.when(F.col("CustomerID").isNull(), 1))
         .alias("NullCustomerIDCount")
    )
)

# Null counts for several columns
required_columns = ["CustomerID", "CustomerName", "City"]

null_counts = df.select([
    F.count(F.when(F.col(c).isNull(), 1)).alias(c)
    for c in required_columns
])

display(null_counts)

# Split into valid and rejected
valid_df = df.filter(
    F.col("CustomerID").isNotNull()
    & F.col("CustomerName").isNotNull()
)

rejected_df = df.filter(
    F.col("CustomerID").isNull()
    | F.col("CustomerName").isNull()
)

Write the valid and rejected DataFrames to separate destinations.

8.4.4Invalid Data Detection

Invalid data breaks a technical or business rule: negative prices, invalid emails, quantities ≤ 0, out-of-range dates, unsupported statuses.

Python
# Order amounts
invalid_orders = df.filter(
    F.col("TotalAmount").isNull()
    | (F.col("TotalAmount") < 0)
)

# Quantities
invalid_items = df.filter(
    F.col("Quantity").isNull()
    | (F.col("Quantity") <= 0)
)

# Status values
allowed_statuses = ["NEW", "PROCESSING", "COMPLETED", "CANCELLED"]

invalid_statuses = df.filter(
    ~F.col("OrderStatus").isin(allowed_statuses)
    | F.col("OrderStatus").isNull()
)
Good practice

Keep business validation rules separate from transformation logic so the pipeline is easier to maintain and rules can be tested independently.

8.4.5Schema Validation

Schema validation checks the source structure against the expected contract: required columns exist, unexpected columns follow policy, names and types match, and nullability complies.

Python · missing and unexpected columns
expected_columns = {"CustomerID", "CustomerName", "City"}

actual_columns = set(df.columns)

missing_columns = expected_columns - actual_columns
unexpected_columns = actual_columns - expected_columns

if missing_columns:
    raise ValueError(f"Missing columns: {sorted(missing_columns)}")

print("Unexpected columns:", sorted(unexpected_columns))
Python · data types
expected_types = {
    "CustomerID": "int",
    "CustomerName": "string",
    "City": "string"
}

actual_types = {
    field.name: field.dataType.simpleString()
    for field in df.schema.fields
}

for column_name, expected_type in expected_types.items():
    actual_type = actual_types.get(column_name)

    if actual_type != expected_type:
        raise ValueError(
            f"{column_name}: expected {expected_type}, found {actual_type}"
        )

Expected type strings must match Spark's representation: bigint (long) is not int. Validate the schema before writing to a curated production table.

8.4.6Data Type Validation

Check that values can be interpreted as the required types.

Python
# try_cast returns null instead of raising an error
df_typed = df.withColumn(
    "TotalAmount",
    F.expr("try_cast(TotalAmount AS DECIMAL(12,2))")
)

invalid_amounts = df_typed.filter(F.col("TotalAmount").isNull())

The last check also catches values that were null in the source; keep the raw value in a separate column if you need to report conversion failures separately.

Recommended approach

  1. Preserve the raw source value.
  2. Convert it to the expected type.
  3. Identify conversion failures.
  4. Reject or quarantine invalid records.
  5. Write valid records to the curated dataset.
  6. Record the number of failed conversions.

8.4.7Record Count Validation

Python
source_count = source_df.count()
valid_count = valid_df.count()
rejected_count = rejected_df.count()

assert source_count == (valid_count + rejected_count)

Valid only when every source record lands in exactly one of the two datasets. If duplicates are removed, track that count separately.

Performance consideration

Repeated count() calls may trigger several Spark jobs and reread data. For large data, persist an expensive intermediate DataFrame when you need multiple actions, then unpersist it.

8.4.8Rejecting Bad Records

Decide how invalid records are handled: fail the whole batch, reject only invalid records, quarantine them for investigation, or accept with warnings where rules permit.

Python
valid_df = df.filter(
    F.col("CustomerID").isNotNull()
    & F.col("CustomerName").isNotNull()
)

rejected_df = df.filter(
    F.col("CustomerID").isNull()
    | F.col("CustomerName").isNull()
)

# Valid records
(
    valid_df.write
    .format("delta")
    .mode("append")
    .saveAsTable("main.silver.customers")
)

# Rejected records
(
    rejected_df.write
    .format("delta")
    .mode("append")
    .saveAsTable("main.quarantine.rejected_customers")
)

A real pipeline should also record the source file, ingestion timestamp, batch ID, and rejection reason. Assumes the target schemas exist and the job has permissions.

8.4.9Logging Rejected Records

Rejected records should be traceable.

from pyspark.sql import functions as F

rejected_df = (
    rejected_df

Chapter 8 · Lesson 8.5

Incremental Data Processing

8.5.1Introduction

Incremental processing loads only new or changed records instead of reprocessing everything. If 20,000 of 10 million customer records change daily, a full refresh processes all 10 million; a good incremental pipeline processes the changes.

It can reduce

  • Processing time.
  • Compute consumption.
  • Source-system load.
  • Data movement.
  • End-to-end latency.
But it requires

Reliable change identification and recovery logic.

8.5.2Full Loads

A full load reads the complete source and replaces the target.

Python
source_df = spark.read.csv(
    "/Volumes/main/bronze/raw/customers.csv",
    header=True,
    inferSchema=True
)

(
    source_df.write
    .format("delta")
    .mode("overwrite")
    .saveAsTable("main.silver.customers")
)

Advantages

  • Simple to implement and reason about.
  • Reflects deletions when the source snapshot is complete.
  • Good for small datasets and initial loads.

Disadvantages

  • Reprocesses unchanged records.
  • Expensive for large datasets.
  • Longer processing time.
  • Replacement behavior needs careful control.

Typical uses: initial loads, small reference tables, periodic full synchronization, rebuilding a target.

8.5.3Incremental Loads

Common approaches: watermark-based loading, timestamp extraction, increasing primary keys, Change Data Capture (CDC), source-system change tracking, and file-arrival-based ingestion. The right one depends on how the source records changes.

8.5.4Watermark-Based Loading

A watermark records the point up to which data has been successfully processed, e.g. 2026-10-24 00:00:00. The next run extracts records modified after it.

SQL · SQL Server source (illustrative)
SELECT
    CustomerID,
    CustomerName,
    ModifiedDate
FROM dbo.Customers
WHERE ModifiedDate > @LastWatermark
  AND ModifiedDate <= @CurrentWatermark;

@LastWatermark and @CurrentWatermark are parameters the pipeline supplies.

Watermark workflow

  1. Read the last committed watermark.
  2. Pick an upper watermark for this batch.
  3. Extract records in that interval.
  4. Validate and transform.
  5. Apply changes to the target.
  6. Reconcile the batch.
  7. Commit the new watermark only after success.
Why an upper watermark?
Last watermark:    2026-10-24 00:00:00
Current watermark: 2026-10-25 00:00:00

A bounded interval avoids a moving upper boundary during the run, which makes reconciliation much easier.

A timestamp watermark can miss records when
  • Source timestamps are updated late or are unreliable.
  • Records arrive out of order.
  • Many records share timestamps and the boundary is wrong.
  • Records are physically deleted with no deletion marker.

Many pipelines add a lookback window, overlapping intervals, or CDC to cover these risks.

8.5.5Timestamp-Based Extraction

Python
from pyspark.sql import functions as F

last_watermark = "2026-10-24 00:00:00"

incremental_df = source_df.filter(
    F.col("ModifiedDate") > F.to_timestamp(F.lit(last_watermark))
)

Assumes ModifiedDate is a valid timestamp column.

Why modification timestamps matter

A customer created on October 10 and updated on October 24 won't be extracted if you filter only on CreatedDate. For change detection, a reliable modification timestamp is usually the right choice.

Overlapping windows: you can deliberately reread a small interval (say, 15 minutes before the previous watermark) to catch late changes. The target must then be idempotent, so reprocessing a change doesn't create duplicates; Delta MERGE helps when the source has reliable keys and ordering rules.

8.5.6Primary-Key-Based Extraction

SQL
SELECT
    CustomerID,
    CustomerName
FROM dbo.Customers
WHERE CustomerID > @LastCustomerID
ORDER BY CustomerID;

Advantages

  • Simple for append-only sources.
  • Works when keys increase monotonically.
  • Easy to implement.

Limitation

It can't detect updates. If customer 101 changes from John to Jonathan, CustomerID > 102 won't capture it. Best for append-only data or where updates are captured separately.

8.5.7Change Detection

Change detection classifies records as new, modified, or unchanged, using modification timestamps, CDC events, source change tracking, comparison with target records, or hash comparison of selected attributes.

Python · record hash
from pyspark.sql import functions as F

df_hashed = df.withColumn(
    "RecordHash",
    F.sha2(
        F.to_json(F.struct("CustomerName", "City", "Email")),
        256
    )
)
Source record:
CustomerID = 101
City       = Hyderabad
RecordHash = AAA

Target record:
CustomerID = 101
City       = Chennai
RecordHash = BBB

Hashes differ -> update needed

Considerations

  • Define how nulls are represented.
  • Use consistent field order and serialization.
  • Exclude fields that shouldn't trigger updates.
  • Hash collisions are theoretically possible.
  • A hash never replaces the business key.

8.5.8Deduplication in Incremental Loads

Incremental batches can contain duplicates from source retries, overlapping windows, replayed events, reprocessed batches, or duplicate files.

Python
# Fine only if any row per key is acceptable
deduplicated_df = incremental_df.dropDuplicates(["CustomerID"])

# Deterministic: keep the latest version
from pyspark.sql import Window
from pyspark.sql import functions as F

window_spec = (
    Window
    .partitionBy("CustomerID")
    .orderBy(
        F.col("ModifiedDate").desc_nulls_last(),
        F.col("IngestionTimestamp").desc_nulls_last()
    )
)

deduplicated_df = (
    incremental_df
    .withColumn("row_num", F.row_number().over(window_spec))
    .filter(F.col("row_num") == 1)
    .drop("row_num")
)

Add a deterministic tie-breaker if timestamps can be equal.

8.5.9Late-Arriving Data

Late-arriving data shows up after its expected processing time. An order created on October 20 that arrives on October 23 is missed by a pipeline that only processes event dates after October 22.

Common causes

  • Source-system delays.
  • Network failures.
  • Delayed file delivery.
  • Streaming delays.
  • Upstream retries.
  • Clock differences.
  • Backdated corrections.

Handling strategies

  1. Capture ingestion timestamps.
  2. Use lookback windows.
  3. Use CDC.
  4. Reprocess affected business dates.
  5. Use idempotent writes.
TimestampMeaning
Event timeWhen the business event occurred
Source modification timeWhen the source record last changed
Ingestion timeWhen the platform received the record
Processing timeWhen the pipeline processed it

These serve different purposes and aren't interchangeable.

8.5.10Delta MERGE for Incremental Processing

Python
from delta.tables import DeltaTable

target_table = "main.silver.customers"

target = DeltaTable.forName(spark, target_table)

(
    target.alias("target")
    .merge(
        deduplicated_df.alias("source"),
        "target.CustomerID = source.CustomerID"
    )
    .whenMatchedUpdateAll()
    .whenNotMatchedInsertAll()
    .execute()
)

A matching customer is updated; a new customer is inserted.

Important considerations
  • The source should have at most one applicable row per target key; duplicates cause ambiguous merges or failures.
  • Source and target schemas must be compatible with the chosen operations.
  • Deletes need extra logic or CDC information.
  • Updating all columns may be wrong if some target columns are system-managed.

Define the business key, update rules, delete rules, and conflict resolution explicitly.

Hands-On Exercise: Daily CSV Ingestion to Delta

Build a reusable, rerunnable PySpark pipeline that reads daily CSV files, validates and types them, quarantines bad records, deduplicates, and merges into a Delta table with one current row per customer.

The pipeline will

  1. Read multiple daily CSV files and validate the required schema.
  2. Convert source fields into the expected types.
  3. Detect malformed and invalid records.
  4. Remove duplicate customer records.
  5. Write valid data to a Delta table and rejected records to a quarantine table.
  6. Record ingestion metrics.
  7. Support safe reruns of the same batch.

Scenario: an upstream application delivers daily customer files (customers_20261023.csv, customers_20261024.csv, customers_20261025.csv) with columns CustomerID, CustomerName, City, Email, ModifiedDate. The target table should hold one current record per customer.

Python

Step 6: Validate records

Python
invalid_condition = (
    F.col("CustomerID").isNull()
    | F.col("CustomerName").isNull()
    | (F.trim(F.col("CustomerName")) == "")
    | F.col("ModifiedDate").isNull()
)

valid_candidates = typed_df.filter(~invalid_condition)

rejected_df = (
    typed_df
    .filter(invalid_condition)
    .withColumn(
        "RejectReason",
        F.when(F.col("CustomerID").isNull(),
               F.lit("Missing or invalid CustomerID"))
         .when(F.col("CustomerName").isNull()
               | (F.trim(F.col("CustomerName")) == ""),
               F.lit("Missing CustomerName"))
         .when(F.col("ModifiedDate").isNull(),
               F.lit("Missing or invalid ModifiedDate"))
         .otherwise(F.lit("Validation failed"))
    )
)

This is technical validation. Add business rules such as email format or valid city values as needed.

Step 7: Deduplicate the batch

Keep the latest source modification for each customer.

Python
from pyspark.sql import Window
from pyspark.sql import functions as F

window_spec = (
    Window
    .partitionBy("CustomerID")
    .orderBy(
        F.col("ModifiedDate").desc_nulls_last(),
        F.col("SourceFile").desc()
    )
)

deduplicated_df = (
    valid_candidates
    .withColumn("row_num", F.row_number().over(window_spec))
    .filter(F.col("row_num") == 1)
    .drop("row_num")
)

In production, replace SourceFile as tie-breaker with a reliable source sequence or unique event ID.

Steps 8–9: Create the target on the first run, merge on later runs

Python
from delta.tables import DeltaTable

if not spark.catalog.tableExists(target_table):
    # First run: create the table from this batch
    (
        deduplicated_df.write
        .format("delta")
        .mode("overwrite")
        .saveAsTable(target_table)
    )
else:
    # Later runs: merge, never letting older data overwrite newer
    target = DeltaTable.forName(spark, target_table)

    (
        target.alias("target")
        .merge(
            deduplicated_df.alias("source"),
            "target.CustomerID = source.CustomerID"
        )
        .whenMatchedUpdateAll(
            condition="source.ModifiedDate > target.ModifiedDate"
        )
        .whenNotMatchedInsertAll()
        .execute()
    )

The update condition stops an older record from overwriting a newer one, as long as source timestamps are reliable. For equal timestamps, define an explicit conflict rule if competing versions are possible.

The source text ran these as two separate if blocks, so the first run created the table and then immediately merged the same batch into it. That was harmless but wasted work; if/else does each only when needed. In production, define the target schema and table properties explicitly instead of letting the first batch decide them.
