Databricks Monitoring and Troubleshooting

Monitor jobs and pipelines, troubleshoot Spark failures, diagnose data-pipeline problems, set up alerting, and build a production-ready monitoring framework. This is the production-support chapter: pipeline reliability, incident handling, and SLA compliance.

Five questions every monitoring solution must answer
  1. What happened? Which pipeline or task failed?
  2. When? When did it start, finish, or fall behind?
  3. Why? What was the root cause?
  4. What was affected? Which tables, records, or downstream jobs?
  5. What next? Retry, recover, alert, or escalate?
Verified on Spark 4

The framework in 20.6 (wrapper, error classification, retries, schema contract, SLA monitor, alert de-duplication, KPI and slow-run queries) and the skew demo in 20.3.7 were all run locally, and the outputs shown are real. System tables, job settings, and Azure Monitor are Databricks or Azure only and are marked as untested where they appear.

20.1.1What Is Monitoring?

Monitoring is the continuous observation of jobs, pipelines, compute, queries, and data processing to spot failures, performance problems, and operational risks.

The 2 AM failure

The customer ingestion job fails at 2:00 AM. Without monitoring, the business finds out at 9:00 AM from an incomplete report. With it, the failure is detected, the error captured, support notified, and the failing stage (source, ingestion, transformation, or downstream) identified before anyone opens a dashboard.

20.1.2Monitoring Architecture

Five layers

  1. Execution: jobs, notebook/Python/SQL tasks, Spark, streaming.
  2. Telemetry: status, run IDs, times, durations, errors, retries, row counts, compute and query metrics.
  3. Storage: system tables, Delta audit tables, Azure Monitor / Log Analytics, external platforms.
  4. Detection: failures, SLA breaches, slow runs, missing data, odd counts, repeated retries, no success within the expected interval.
  5. Alerting and visualization: job notifications, email, Teams, action groups, incident tools, dashboards.

20.1.4Notebook Execution History and Query History

Notebook history

Shows executed cells, output, exceptions, durations, associated Spark jobs, and logs. Useful for development and interactive debugging, but not a substitute for production monitoring: production code should write structured, queryable records (20.6).

Each count() is a separate Spark job. Count deliberately, not after every step.

Query history

Finds slow and failed SQL statements, large scans, expensive joins, and repeated queries. A report that went from 20 seconds to 15 minutes could be more data, lost pruning, a bad join strategy, skew, contention, or changed logic.

Query history shows which statement and when; diagnosing why may also need the query profile, plan, and Spark UI.

20.1.5Compute Utilization and Cluster Events

Metric (40-minute job)ObservationPossible interpretation
CPUConsistently lowWaiting on I/O, or too little parallelism
MemoryVery highLarge working sets, memory-heavy operations
Shuffle spillHighShuffle data exceeds execution memory

These are clues, not conclusions; correlate several. On classic compute, see the compute's Metrics tab; serverless exposes less infrastructure detail, so rely more on the query profile and Spark UI.

Cluster events (start, terminate, resize, configuration change, driver restart, lost workers) explain failures that the job itself can't. If a job fails after compute terminates unexpectedly, check in order: the run timeline, the compute event log, driver logs, executor logs, cloud or network events, and whether the termination was expected. A job failure and a compute failure are related but distinct; record both.

20.2.1Successful and Failed Runs

Don't treat every non-success state as a failure. These are the result_state values in Databricks' job system tables:

StateMeaningTypical response
SUCCEEDEDCompleted successfullyValidate output if required
FAILED / ERRORCompleted with an errorInvestigate and alert
TIMED_OUTExceeded its timeoutCheck runtime and timeout settings
CANCELLEDCancelled by a userCheck who and why
SKIPPEDNot executed (condition not met)Expected?
BLOCKEDBlocked on an upstream dependencyFind the upstream failure
NULLStill running (intermediate row)Watch duration

Names differ between the UI, the Jobs API, and system tables. Our own audit table (20.6) uses RUNNING, SUCCESS, and FAILED.

20.2.2Execution Duration and Baselines

SQL
SELECT pipeline_name, run_id, start_time, end_time,
       timestampdiff(SECOND, start_time, end_time) AS duration_seconds
FROM retail_dev.ops.pipeline_run_latest
WHERE end_time IS NOT NULL;

Why it matters

The customer load normally takes 12 minutes; today 55, and it still succeeded. That's an early warning: a slow source, more data, an inefficient join, spill, contention, or a changed distribution. Catch degradation before it becomes a failure.

PipelineNormalWarningCritical
Customer load12 min20 min30 min
Product load8 min15 min25 min
Sales aggregation25 min35 min50 min

Don't use one threshold for every job. Rather than hard-coding baselines, derive them from history. This query flags runs that were much slower than that pipeline's own recent runs:

SQL · slow-run detection
-- Successful runs more than 50% slower than the p90 of that pipeline's previous 30 successful runs
WITH history AS (
    SELECT pipeline_name, run_id, start_time, duration_seconds,
           percentile_approx(duration_seconds, 0.9) OVER w AS p90_previous,
           count(*) OVER w                                AS previous_runs
    FROM retail_dev.ops.pipeline_run_latest
    WHERE status = 'SUCCESS'
    WINDOW w AS (PARTITION BY pipeline_name ORDER BY start_time
                 ROWS BETWEEN 30 PRECEDING AND 1 PRECEDING)
)
SELECT pipeline_name, run_id, start_time, duration_seconds, p90_previous,
       round(duration_seconds / p90_previous, 1) AS times_p90
FROM history
WHERE previous_runs >= 5                      -- need a baseline first
  AND duration_seconds > 1.5 * p90_previous
ORDER BY start_time DESC
Output (verified: 9 successful runs of 700–780 s, then one of 2000 s)
pipeline_name  run_id  duration_seconds  p90_previous  times_p90
pl_orders      o9      2000              780           2.6

The 1.5× factor and five-run minimum are starting points; tune them. Compare like with like: a full reload shouldn't be judged against incremental runs.

20.2.3Retry Tracking

Retry these (transient)

  • Temporary network interruptions.
  • Transient service errors.
  • Temporary throttling.
  • Some infrastructure interruptions.

Don't blindly retry (permanent)

  • Invalid data types.
  • Missing required columns.
  • Wrong business logic.
  • Permission failures.
  • Invalid credentials.
  • Duplicate keys violating rules.
Operation fails
      |
Classify the error
      |
      +--> Transient and retry-safe --> wait (2s, 4s, 8s ... capped) --> retry, up to N attempts
      |
      +--> Permanent ------------------> stop, record, alert

The original's retry_operation retried every exception, which it said wasn't production-ready. The framework's retry_transient (20.6.3) retries only errors classified as transient. Tested:

Output (verified)
Timeout twice, then success   -> "ok" after 3 attempts, delays [2, 4]
Schema contract violation     -> raised immediately, attempts: 1

For whole tasks, prefer the job's built-in retry settings (max_retries, min_retry_interval_millis; see 20.2.7). Custom retries suit a single call inside a task, such as one API request.

20.2.4Task-Level and Dependency Failures

Task A: Extract customers   SUCCEEDED
Task B: Extract products    SUCCEEDED
Task C: Transform orders    FAILED     &lt;-- root cause
Task D: Build sales summary BLOCKED / SKIPPED
                            (depends on C)

Record for the failed task

Job ID, job run ID, failed task key, task run ID, error message, attempt number, start and end times, upstream dependencies, and downstream tasks skipped or blocked.

Task D's state is a consequence, not a second problem. Alert on the first failure in the dependency chain; job_task_run_timeline (20.5.4) gives the task-level view.

20.2.5Delayed Jobs and SLA Monitoring

Two different delays

Start delay = actual start − expected start
Completion delay = actual completion − expected completion

Scheduled 2:00–3:00 AM, actual 2:25–3:20 AM: start delay 25 min, completion delay 20 min. Find whether scheduling, queueing, upstream delays, or slow execution caused it.

A data-pipeline SLA might say

  • Complete by 5:00 AM.
  • Process the latest source batch.
  • Meet a completeness threshold.
  • Stay under an agreed failure rate.
  • Data ready before business hours.
Expected completion: 04:30 IST
Actual completion:   04:47 IST

SLA status: BREACHED
Delay:      17 minutes
SLA ≠ duration

A 20-minute run misses its SLA if it starts too late; a 40-minute run meets it if the deadline allows. And three cases need detecting, not one: finished late, still running past the deadline, and never started. A missing record is not a success. 20.6.8 builds a monitor for all three.

An SLA record should hold pipeline, business date, expected and actual times, threshold, breach duration, current status, and notification status.

20.2.6Failure Notifications

Decide which failures alert, who receives them, whether to alert during retries or only on final failure, how to de-duplicate, how to escalate, and how recovery is confirmed. Here's what that looks like in a job's settings (the JSON view or the Jobs API):

JSON · job settings (excerpt)
{
  "name": "pl_retail_daily_load",
  "timeout_seconds": 7200,
  "health": {
    "rules": [
      { "metric": "RUN_DURATION_SECONDS", "op": "GREATER_THAN", "value": 3600 }
    ]
  },
  "email_notifications": {
    "on_failure": ["data-support@example.com"],
    "on_duration_warning_threshold_exceeded": ["data-support@example.com"]
  },
  "notification_settings": {
    "no_alert_for_skipped_runs": true,
    "no_alert_for_canceled_runs": true
  },
  "tasks": [
    {
      "task_key": "extract_customers",
      "notebook_task": { "notebook_path": "/Workspace/retail/extract_customers" },
      "max_retries": 2,
      "min_retry_interval_millis": 120000,
      "retry_on_timeout": false
    }
  ]
}

What each part does

  • on_failure at job level: fires when the run ends failed, after task retries are used up, so no email per retry.
  • health + on_duration_warning_threshold_exceeded: warns when a run exceeds 60 minutes while still running.
  • timeout_seconds: stops a hung run.
  • notification_settings: silences skipped and cancelled runs.
  • Task max_retries / min_retry_interval_millis: built-in retries for transient failures.
Text · a good alert
[PROD] Databricks pipeline failed

Pipeline:       pl_retail_daily_load
Run ID:         83921
Failed task:    transform_orders
Started:        02:00 IST   Failed: 02:18 IST
Error category: SCHEMA_MISMATCH
First action:   Check the source schema change;
                open the failed task's output.

Webhook destinations (Teams, Slack, PagerDuty) are set up by an admin and added under webhook_notifications. The JSON wasn't run here; the keys follow the Jobs API. Never put passwords, tokens, or customer data in alerts. Docs: Job notifications.

df = spark.read.table("retail_dev.bronze.orders")

20.3.2Slow Spark Jobs

CauseTypical symptomInvestigation
Too much data scannedLong read stageInput size, pruning (Chapter 15)
Large shuffleExpensive exchangeShuffle metrics

Workflow

  1. Find the slow run (job run → Spark UI or query profile).
  2. Find the slow stage (timeline, task-duration distribution).
  3. Check input, shuffle, and spill metrics.
  4. Read the plan: df.explain("formatted").
  5. Fix the actual bottleneck.

Typical fixes

  • Filter earlier when semantically valid.
  • Select only needed columns.
  • Avoid unnecessary shuffles.
  • Handle skewed keys.
  • Improve data layout.
  • Choose suitable compute.

Don't just add workers. If one skewed partition or a bad join is the problem, more workers help little.

20.3.3Executor and Driver Failures

Executor failures

Causes: OOM, worker or infrastructure failure, process killed, resource exhaustion, dependency problems. Symptoms: repeated task failures, executors vanishing from the Spark UI, stage retries, eventual job failure.

  1. Find the failed task and stage.
  2. Read executor logs.
  3. One executor or many?
  4. Check memory, disk, CPU.
  5. Read the exception and exit reason.
  6. Does one partition always fail? Then inspect its data.
  7. Decide: data, code, or infrastructure.

Driver failures

The driver coordinates everything, so if it dies the whole application ends even though executors are fine. Causes: driver OOM, collecting large results, huge query plans, too much driver-side metadata, application exceptions.

Python
# Dangerous: pulls every row into driver memory
rows = spark.table("retail_dev.bronze.orders").collect()

# Better: keep the work distributed
(spark.table("retail_dev.bronze.orders")
      .groupBy("order_status").count()
      .show())

Use collect() and toPandas() only when the result is known to be small. The driver log shows "Driver is temporarily unavailable" or similar when it has restarted.

20.3.4Out-of-Memory Errors

Driver memory pressure

  • Collecting large datasets.
  • Large Python objects.
  • Large metadata structures.
  • Driver-side processing of big results.

Executor memory pressure

  • Large joins and aggregations.
  • Caching too much.
  • Oversized partitions.
  • Data skew.
  • Memory-heavy UDFs.

Cache only what you reuse. df.cache() pays off when a DataFrame is used several times and recomputing it is expensive; for a single-use DataFrame it wastes memory. (Serverless doesn't support cache() on DataFrames at all.)

Approach: which process died (driver or executor)? Read the exception and logs, check partition sizes, review joins and aggregations, drop unnecessary caching, avoid large collects, consider another strategy, and resize compute only once you understand the bottleneck.

20.3.5Shuffle Failures

A shuffle redistributes data so rows with the same key meet, e.g. for df.groupBy("customer_id").sum("sales_amount"). Failures are linked to executor loss, disk pressure, network interruptions, huge shuffles, memory pressure, and oversized partitions.

Inspect shuffle read/write volume, spill, stage retry history, executor failures, task-duration variation, and disk. A shuffle isn't a problem in itself; it's normal distributed processing. Reduce unnecessary shuffles and make necessary ones reliable (Chapter 15's AQE and partition sizing help).

20.3.6Data Skew

Skew is uneven data across partitions. If one customer_id (say, a "walk-in customer" placeholder) holds 40% of rows, its partition dwarfs the rest and the stage waits for that one task.

Python · detect and handle skew
from pyspark.sql import functions as F

# 1M orders; customer "C0" (e.g. a 'walk-in' placeholder) has 40% of them
orders = (spark.range(1_000_000)
          .withColumn("customer_id",
                      F.when(F.col("id") % 10 < 4, F.lit("C0"))
                       .otherwise(F.concat(F.lit("C"), (F.col("id") % 5000 + 1).cast("string"))))
          .withColumn("sales_amount", (F.col("id") % 100 + 1).cast("decimal(18,2)")))

# 1. Key frequency: is one key dominant?
orders.groupBy("customer_id").count().orderBy(F.desc("count")).show(3)

# 2. Partition sizes after hashing on the key (what a shuffle on customer_id does)
sizes = (orders.repartition(8, "customer_id")
               .groupBy(F.spark_partition_id().alias("partition")).count())
stats = sizes.agg(F.max("count").alias("largest"),
                  F.expr("percentile(count, 0.5)").alias("median")).first()
print(f"largest partition {stats.largest:,} rows vs median {int(stats.median):,}")

# 3. Two-phase (salted) aggregation: spread the hot key over 16 salts, then combine
salted = (orders
          .withColumn("salt", (F.rand(seed=42) * 16).cast("int"))
          .groupBy("customer_id", "salt").agg(F.sum("sales_amount").alias("partial"))
          .groupBy("customer_id").agg(F.sum("partial").alias("total_sales")))
plain = orders.groupBy("customer_id").agg(F.sum("sales_amount").alias("total_sales"))
print("salted result identical:", salted.exceptAll(plain).isEmpty() and plain.exceptAll(salted).isEmpty())
Output (verified)
+-----------+------+
|customer_id| count|
+-----------+------+
|         C0|400000|
|       C609|   200|
|       C650|   200|
+-----------+------+
largest partition 471,400 rows vs median 75,600
salted result identical: True

How to detect

  • Task-duration distribution (max ≫ median).
  • Input records per task.
  • Shuffle read size per task.
  • Key frequencies (step 1 above; itself costly on huge tables).

How to address

  • AQE skew-join handling (on by default in Databricks) splits oversized partitions in joins.
  • Broadcast a genuinely small dimension.
  • Two-phase aggregation (salting, step 3) for skewed group-bys.
  • Handle special keys separately where business logic allows.

Salting is safe for sums and counts (verified identical above) because partial results combine. It's not safe for every aggregate (e.g. count(DISTINCT …) needs care) and salted joins require replicating the other side. Don't apply it blindly.

20.4.1Schema Mismatch and Invalid Data Types

The pipeline expects customer_id BIGINT; the source now sends STRING. Or a required column disappears or is renamed. The original checked only column names and suggested comparing df.schema for types. The framework's validate_schema_contract does both:

Python
CUSTOMER_CONTRACT = StructType([
    StructField("customer_id", LongType()),
    StructField("customer_name", StringType()),
    StructField("email", StringType()),
    StructField("updated_at", TimestampType()),
])

validate_schema_contract(df, CUSTOMER_CONTRACT)
Output (verified, source sent strings)
SchemaContractError: Schema contract violated:
  type changes ['customer_id: expected bigint,
  got string', 'updated_at: expected timestamp,
  got string']

classify_error -> SCHEMA_MISMATCH

Extra columns are allowed by default (allow_extra_columns=False to forbid). Practice: define expected schemas, validate before transforming, detect type changes, decide whether new columns are allowed, log differences, never cast silently, and have a quarantine policy.

Invalid values (an amount of "ABC"): under ANSI mode a plain cast fails the whole job. Use try_cast to find them, as in Chapter 18:

Python
typed_df = source_df.withColumn("amount_decimal", F.expr("try_cast(amount AS DECIMAL(18,2))"))
invalid_records = typed_df.filter(F.col("amount").isNotNull() & F.col("amount_decimal").isNull())

Then: count and sample them, apply correction or rejection rules, store rejects, alert above a threshold, never silently drop. Also treat blanks, whitespace, and formatted values like "₹1,200" explicitly.

20.4.2Duplicate and Missing Records

Duplicates come from

  • Repeated source events.
  • Overlapping incremental loads.
  • Incorrect joins (fan-out).
  • Retries of non-idempotent appends.
  • Source-system duplication.
  • Missing deduplication.

Missing rows come from

  • Incomplete source extract.
  • Wrong incremental watermark.
  • An inner join dropping unmatched rows.
  • A too-restrictive filter.
  • An unprocessed file.
  • A partial load after failure.
  • Downstream refresh before data was complete.
Python · duplicates on the real key
duplicates = (df.groupBy("order_id", "line_number")
                .count().filter("count &gt; 1"))
Python · source keys missing in target
missing_df = (source_df.select("order_id")
              .join(target_df.select("order_id"),
                    "order_id", "left_anti"))

dropDuplicates keeps an arbitrary row; when duplicates differ, keep the latest by a reliable timestamp with a window (the 20.6 pipeline does this). Compare source and target for the same batch, and remember equal counts don't prove a match. Chapter 18's validation framework covers all of this.

20.4.5Delta Transaction Conflicts

Concurrent operations conflict when they make incompatible changes to overlapping data: e.g. Job A MERGEs customer updates while Job B DELETEs obsolete customers. One fails with an exception such as ConcurrentAppendException or ConcurrentDeleteReadException and must be retried.

SQL · who else wrote the table?
DESCRIBE HISTORY retail_dev.silver.customers LIMIT 20;
-- version, timestamp, operation, userName,
-- job (job id / run id), operationParameters

Troubleshoot and prevent

  • Capture the full exception; identify table and operation.
  • Find overlapping writers and schedules.
  • Retry only if the operation is idempotent (e.g. a MERGE).
  • Give critical tables one owning pipeline.
  • Make MERGE conditions specific (e.g. include the partition or date) so writers touch disjoint data.
  • Don't retry schema or logical conflicts.

A conflict doesn't mean corruption: Delta's optimistic concurrency rejected a commit to protect the table. That's why the framework doesn't classify DELTA_CONFLICT as automatically retryable; add it to TRANSIENT_CATEGORIES only for idempotent writes. Docs: Isolation levels and write conflicts.

20.6Building a Monitoring Framework

We'll build application-level monitoring with PySpark and Delta that records each run's status, timings, row counts, and categorized errors; detects failed, late, overdue, and missing runs against a schedule; and sends de-duplicated alerts. Everything in this section was run on Spark 4.

What changed from the original, and why

The original framework worked but had gaps it partly acknowledged. Fixes, all verified:

  1. An audit-write failure hid the pipeline's error. If the failure record couldn't be written, the audit exception replaced the original. Now the original error is always re-raised and audit failures go to a fallback log (tested: ZeroDivisionError preserved, two fallback lines logged).
  2. Running and overdue runs were invisible, because the record was written only at the end. A RUNNING event is now written at start.
  3. Failed runs got sla_status = MET if they failed before the deadline. Failed runs are now NOT_EVALUATED; the SLA monitor judges each pipeline by its latest attempt.
  4. Errors are categorized (as 20.9 recommends) and sanitized, not stored as raw messages.
  5. The SLA check was conceptual; it's now a working query with a schedule registry and time zones, plus a de-duplicating alert dispatcher.
  6. The sample pipeline kept an arbitrary duplicate and computed its output twice. It now keeps the latest version and counts what was committed.

import json
import re
import sys
import time
from datetime import datetime, timezone

from pyspark.sql.types import (
    LongType, StringType, StructField, StructType, TimestampType,
)

AUDIT_TABLE = "retail_dev.ops.pipeline_execution_audit"

AUDIT_SCHEMA = StructType([
    StructField("pipeline_name", StringType()),
    StructField("run_id", StringType()),
    StructField("batch_id", StringType()),
    StructField("environment", StringType()),
    StructField("status", StringType()),            # RUNNING, SUCCESS, FAILED
    StructField("start_time", TimestampType()),
    StructField("end_time", TimestampType()),
    StructField("duration_seconds", LongType()),
    StructField("source_row_count", LongType()),
    StructField("target_row_count", LongType()),
    StructField("sla_deadline", TimestampType()),
    StructField("sla_status", StringType()),        # MET, BREACHED, NOT_EVALUATED
    StructField("error_type", StringType()),        # category from classify_error
    StructField("error_message", StringType()),     # sanitized, truncated
    StructField("created_at", TimestampType()),
])


# ---------------------------------------------------------------- errors
# First match wins. Patterns are matched against "ExceptionClass: message".
ERROR_PATTERNS = [
    ("SCHEMA_MISMATCH",     ["UNRESOLVED_COLUMN", "Schema contract", "DELTA_FAILED_TO_MERGE_FIELDS"]),
    ("INVALID_DATA",        ["CAST_INVALID_INPUT", "NumberFormatException"]),
    ("AUTHORIZATION",       ["PERMISSION_DENIED", "INSUFFICIENT_PERMISSIONS", "AccessDenied"]),
    ("DELTA_CONFLICT",      ["ConcurrentAppendException", "ConcurrentDeleteReadException",
                             "ConcurrentDeleteDeleteException", "ConcurrentTransactionException",
                             "MetadataChangedException"]),
    ("SOURCE_CONNECTIVITY", ["ConnectionError", "TimeoutError", "Connection refused",
                             "timed out", "UnknownHostException"]),
]
TRANSIENT_CATEGORIES = {"SOURCE_CONNECTIVITY"}   # add DELTA_CONFLICT only for idempotent writes


def classify_error(exc):
    text = f"{type(exc).__name__}: {exc}".lower()
    for category, patterns in ERROR_PATTERNS:
        if any(p.lower() in text for p in patterns):
            return category
    return "UNKNOWN"


_SECRET_PATTERNS = [
    (re.compile(r"(?i)\b(password|pwd|secret|token)\s*[=:]\s*[^;\s,]+"), r"\1=***"),
    (re.compile(r"(?i)bearer\s+[A-Za-z0-9._\-]+"), "Bearer ***"),
    (re.compile(r"dapi[0-9a-f]{16,}"), "dapi***"),
]


def sanitize_message(message, max_length=1000):
    for pattern, replacement in _SECRET_PATTERNS:
        message = pattern.sub(replacement, message)
    return message[:max_length]


def _fallback_log(event, **details):
    """Last resort when the audit table can't be written: one JSON line in the driver log."""
    payload = {"event": event, "ts": datetime.now(timezone.utc).isoformat(), **details}
    print(json.dumps(payload, default=str), file=sys.stderr)


# ---------------------------------------------------------------- audit
def write_execution_audit(spark, **record):
    if record.get("start_time") and record.get("end_time"):
        record["duration_seconds"] = int(
            (record["end_time"] - record["start_time"]).total_seconds())
    record["created_at"] = datetime.now(timezone.utc)
    row = tuple(record.get(field.name) for field in AUDIT_SCHEMA)
    (spark.createDataFrame([row], AUDIT_SCHEMA)
          .write.mode("append").saveAsTable(AUDIT_TABLE))


def evaluate_sla(end_time, sla_deadline):
    if sla_deadline is None:
        return "NOT_EVALUATED"
    return "BREACHED" if end_time > sla_deadline else "MET"


# ---------------------------------------------------------------- wrapper
def execute_monitored_pipeline(spark, pipeline_name, run_id, batch_id, environment,
                               pipeline_function, sla_deadline=None):
    base = dict(pipeline_name=pipeline_name, run_id=run_id, batch_id=batch_id,
                environment=environment, sla_deadline=sla_deadline,
                start_time=datetime.now(timezone.utc))

    # 1. Best-effort RUNNING marker, so overdue runs are visible while still running
    try:
        write_execution_audit(spark, **base, status="RUNNING", sla_status="NOT_EVALUATED")
    except Exception as audit_exc:
        _fallback_log("AUDIT_WRITE_FAILED", stage="start", error=str(audit_exc)[:300], **base)

    # 2. Run the pipeline
    failure = None
    final = dict(base)
    try:
        result = pipeline_function() or {}
        final.update(status="SUCCESS",
                     source_row_count=result.get("source_row_count"),
                     target_row_count=result.get("target_row_count"))
    except Exception as exc:
        failure = exc
        final.update(status="FAILED",
                     error_type=classify_error(exc),
                     error_message=sanitize_message(f"{type(exc).__name__}: {exc}"))

    final["end_time"] = datetime.now(timezone.utc)
    # A failed run delivered nothing, so it can't "meet" an SLA; the SLA monitor
    # judges the pipeline by its latest attempt instead
    final["sla_status"] = (evaluate_sla(final["end_time"], sla_deadline)
                           if failure is None else "NOT_EVALUATED")

    # 3. Final record. An audit failure must never hide the pipeline's own error.
    try:
        write_execution_audit(spark, **final)
    except Exception as audit_exc:
        _fallback_log("AUDIT_WRITE_FAILED", stage="end", error=str(audit_exc)[:300], **final)

    # 4. Re-raise so the job run itself is marked FAILED
    if failure is not None:
        raise failure
    return final


# ---------------------------------------------------------------- retries
def retry_transient(operation, max_attempts=3, base_delay_seconds=2, sleep=time.sleep):
    """Retry only errors classified as transient, with capped exponential backoff."""
    for attempt in range(1, max_attempts + 1):
        try:
            return operation()
        except Exception as exc:
            category = classify_error(exc)
            if category not in TRANSIENT_CATEGORIES or attempt == max_attempts:
                raise
            delay = min(base_delay_seconds * 2 ** (attempt - 1), 30)
            _fallback_log("RETRYING", attempt=attempt, category=category, delay_seconds=delay)
            sleep(delay)


# ---------------------------------------------------------------- schema contract
class SchemaContractError(ValueError):
    pass


def validate_schema_contract(df, expected_schema, allow_extra_columns=True):
    actual = {f.name: f.dataType for f in df.schema}
    missing = [f.name for f in expected_schema if f.name not in actual]
    mismatched = [f"{f.name}: expected {f.dataType.simpleString()}, got {actual[f.name].simpleString()}"
                  for f in expected_schema
                  if f.name in actual and actual[f.name] != f.dataType]
    extra = [c for c in actual if c not in {f.name for f in expected_schema}]

    problems = []
    if missing:
        problems.append(f"missing columns {missing}")
    if mismatched:
        problems.append(f"type changes {mismatched}")
    if extra and not allow_extra_columns:
        problems.append(f"unexpected columns {extra}")
    if problems:
        raise SchemaContractError("Schema contract violated: " + "; ".join(problems))
    return {"extra_columns": extra}

Why the wrapper re-raises

Catching the exception to log it would otherwise make the notebook, and therefore the job run, look successful. Re-raising keeps the job FAILED, so job notifications and retries still work.

What it can't catch

If compute is lost or the run is killed, the except block never runs and only the RUNNING row exists. The SLA monitor shows it as OVERDUE, and 20.9 reconciles audit rows against system-table run history.

Python · customer_pipeline.py
from pyspark.sql import Window, functions as F
from pyspark.sql.types import LongType, StringType, StructField, StructType, TimestampType

SOURCE_TABLE = "retail_dev.bronze.customers"
TARGET_TABLE = "retail_dev.silver.customers"

CUSTOMER_CONTRACT = StructType([
    StructField("customer_id", LongType()),
    StructField("customer_name", StringType()),
    StructField("email", StringType()),
    StructField("updated_at", TimestampType()),
])


def customer_pipeline():
    source_df = spark.table(SOURCE_TABLE)
    validate_schema_contract(source_df, CUSTOMER_CONTRACT)      # fail fast, clear message

    latest_first = Window.partitionBy("customer_id").orderBy(F.col("updated_at").desc())
    cleaned_df = (
        source_df
        .filter(F.col("customer_id").isNotNull())
        .withColumn("_rn", F.row_number().over(latest_first))  # keep the latest version
        .filter("_rn = 1")
        .drop("_rn")
    )

    # Full refresh by design: overwrite replaces the whole target table
    cleaned_df.write.mode("overwrite").saveAsTable(TARGET_TABLE)

    return {
        "source_row_count": source_df.count(),
        "target_row_count": spark.table(TARGET_TABLE).count(),   # what was committed
    }

20.6.4Step 6: SLA Breach Detection (Late, Overdue, Missing)

The wrapper can only judge runs that finish. A separate scheduled check compares the registry against actual runs, which catches runs still going past their deadline and runs that never started. Schedule it every 15 minutes in the early morning.

SQL · sla_check.sql (parameters :run_date and :as_of)
WITH expected AS (
    SELECT pipeline_name, severity,
           make_timestamp(year(:run_date), month(:run_date), day(:run_date),
                          CAST(split(expected_completion, ':')[0] AS INT),
                          CAST(split(expected_completion, ':')[1] AS INT),
                          0, sla_timezone) AS deadline          -- converted to UTC instant
    FROM retail_dev.ops.pipeline_sla_registry
    WHERE active
),
runs AS (                                                       -- latest attempt per pipeline
    SELECT *, row_number() OVER (PARTITION BY pipeline_name ORDER BY start_time DESC) AS attempt_rank
    FROM retail_dev.ops.pipeline_run_latest
    WHERE batch_id = concat('BATCH_', date_format(:run_date, 'yyyyMMdd'))
)
SELECT e.pipeline_name, e.severity, e.deadline, r.run_id, r.status, r.end_time,
       CASE
           WHEN r.run_id IS NULL AND :as_of > e.deadline   THEN 'MISSING'
           WHEN r.run_id IS NULL                           THEN 'NOT_STARTED'
           WHEN r.status = 'RUNNING' AND :as_of > e.deadline THEN 'OVERDUE'
           WHEN r.status = 'RUNNING'                       THEN 'RUNNING'
           WHEN r.status = 'FAILED'                        THEN 'FAILED'
           WHEN r.end_time > e.deadline                    THEN 'BREACHED'
           ELSE 'MET'
       END AS sla_state,
       greatest(0, timestampdiff(MINUTE, e.deadline, coalesce(r.end_time, :as_of))) AS minutes_late
FROM expected e
LEFT JOIN runs r ON r.pipeline_name = e.pipeline_name AND r.attempt_rank = 1
ORDER BY e.deadline

20.6.5Step 7: Failure Alerting with De-duplication

The dispatcher sends one alert per environment + pipeline + run (or date) + state and records every attempt. Since the check runs every 15 minutes, without de-duplication the overdue orders run would alert four times an hour.

Python · alerts.py
from datetime import datetime, timezone

ALERT_LOG_TABLE = "retail_dev.ops.alert_log"
ALERT_STATES = ("FAILED", "BREACHED", "OVERDUE", "MISSING")


def build_alert(environment, finding):
    subject = f"[{environment}] {finding['pipeline_name']}: {finding['sla_state']}"
    body = "\n".join([
        f"Environment: {environment}",
        f"Pipeline: {finding['pipeline_name']}",
        f"Run ID: {finding['run_id'] or 'no run found'}",
        f"State: {finding['sla_state']} ({finding['minutes_late']} min past deadline)",
        f"Deadline (UTC): {finding['deadline']}",
        f"Severity: {finding['severity']}",
        "First action: open the job run, check the failed task and the audit row.",
    ])
    return subject, body


def dispatch_alerts(spark, findings_df, environment, run_date, send):
    """Send one alert per (environment, pipeline, run or date, state); never repeat a sent one."""
    already_sent = set()
    if spark.catalog.tableExists(ALERT_LOG_TABLE):
        already_sent = {r.alert_key for r in
                        spark.table(ALERT_LOG_TABLE).filter("delivery_status = 'SENT'")
                             .select("alert_key").collect()}

    log_rows = []
    for f in findings_df.filter(findings_df.sla_state.isin(*ALERT_STATES)).collect():
        finding = f.asDict()
        alert_key = "|".join([environment, finding["pipeline_name"],
                              finding["run_id"] or str(run_date), finding["sla_state"]])
        if alert_key in already_sent:
            continue
        subject, body = build_alert(environment, finding)
        try:
            send(subject, body)
            status, error = "SENT", None
        except Exception as exc:                  # record it; retry on the next check
            status, error = "FAILED", str(exc)[:300]
        log_rows.append((alert_key, finding["pipeline_name"], finding["sla_state"],
                         finding["severity"], status, error, datetime.now(timezone.utc)))

    if log_rows:
        (spark.createDataFrame(log_rows,
            "alert_key STRING, pipeline_name STRING, alert_type STRING, severity STRING, "
            "delivery_status STRING, delivery_error STRING, created_at TIMESTAMP")
              .write.mode("append").saveAsTable(ALERT_LOG_TABLE))
    return log_rows

20.9Recommended Production Design Improvements

1. Independent run detection

Don't rely only on code reporting its own failure. Use run history (system tables, Jobs API) to see actual run states.

2. Reliable audit writes

Fallback logging (done) plus a reconciliation that finds runs with no audit record (below).

3. Business dates vs timestamps

Store UTC; keep the business time zone (e.g. IST) for SLAs. Never mix naive and UTC timestamps (done in the registry).

4. Batch-level reconciliation

Record the exact batch or watermark processed; compare like with like.

5. Structured error categories

SOURCE_CONNECTIVITY, AUTHORIZATION, SCHEMA_MISMATCH, INVALID_DATA, DELTA_CONFLICT, UNKNOWN… based on observed exceptions (done; extend the patterns as you meet new errors).

6. No unsafe retries

Retry only transient categories on idempotent operations (done).

7. Prevent alert fatigue

Severity levels, de-duplication (done), escalation, acknowledgement tracking. A slightly slow job shouldn't page like a failed finance load.

8. Recovery runbooks

Partial writes, failed incremental batches, wrong watermarks, duplicate loads, failed downstream tasks, late source data.

9. Monitor the Monitoring

The monitor itself can fail silently, which is its own operational risk. Two checks:

SQL · job runs that left no audit record (needs system tables; not run here)
SELECT r.job_id, r.run_id, r.result_state, r.period_end_time
FROM system.lakeflow.job_run_timeline AS r
WHERE r.result_state IS NOT NULL
  AND r.period_end_time &gt;= current_timestamp() - INTERVAL 1 DAY
  AND r.job_id IN (123456789, 987654321)              -- your monitored jobs
  AND NOT EXISTS (
        SELECT 1 FROM retail_dev.ops.pipeline_execution_audit AS a
        WHERE a.run_id = CAST(r.run_id AS STRING));

Any row means the wrapper didn't run, couldn't write, or wasn't given {{job.run_id}}. Also alert if the SLA check job itself hasn't succeeded in the last 30 minutes (a job health rule or its own on_failure notification), and periodically send a test alert to prove delivery works.

20.10Interview Questions and Answers

Try answering each before revealing the answer.

Q1. How do you monitor Databricks jobs in production?
Jobs UI for investigation; system tables (job_run_timeline, job_task_run_timeline) or the Jobs API for automated monitoring; application audit tables for row counts and errors; job notifications and alerts on top.
Q2. Job-level vs task-level monitoring?
Job-level tracks the overall run; task-level identifies which task failed, was skipped or blocked, or ran long, so you find the root cause rather than the consequence.
Q3. How do you detect a pipeline that didn't run?
Keep an expected-run registry and compare it with actual runs; flag MISSING after the deadline. A missing record must never be read as success.
Q4. How do you detect an SLA breach?
Compare completion time with the business deadline (in the business time zone), and separately detect runs still running past it (OVERDUE) and runs that never started (MISSING).
Q5. Troubleshooting a slow Spark job?
Find the slow stage in the Spark UI or query profile, compare task durations, check shuffle, spill, and input sizes, look for skew and memory pressure, read the plan, and fix the actual bottleneck before resizing.
Q6. Causes of executor OOM?
Oversized partitions, large joins and aggregations, excessive caching, skew, memory-heavy UDFs. Determine whether it's data, logic, or configuration before adding memory.
Q7. Identifying data skew?
Max task duration or shuffle read far above the median, plus key-frequency analysis showing a few dominant keys.
Q8. Task retry vs job retry?
Spark retries a failed task inside a run; the orchestrator retries a whole job task as a new attempt. Different levels, different visibility.
Q9. Handling a schema mismatch?
Validate names and types against a defined contract before transforming; on violation, record the difference and stop or quarantine the batch. Don't retry; it's permanent.
Q10. Detecting missing records?
Row-count reconciliation plus key-level left-anti joins, both scoped to the same batch or business period.
Q11. Handling Delta transaction conflicts?
Identify the concurrent writers (DESCRIBE HISTORY), retry only idempotent operations, and if conflicts recur, redesign ownership, schedules, or make writes touch disjoint data.
Q12. Designing a reusable monitoring framework?
Standard audit tables, a wrapper that records start and outcome and re-raises, error categories, an SLA registry and scheduled check, de-duplicated alerts, dashboards, and independent run-history checks for failures the wrapper can't see.
Q13. Preventing duplicates when rerunning?
Batch IDs, deterministic boundaries, MERGE or replaceWhere, processed-batch tracking, reconciliation, and checking what already committed.
Q14. Operational audit tables vs Databricks audit logs?
Audit tables capture application-specific execution and data metrics; platform audit logs capture platform activity (access, permission and configuration changes). Complementary, not interchangeable.
Q15. Integrating with Azure Monitor?
Configure diagnostic settings for the needed audit-log categories to Log Analytics, write alert rules, route through action groups, and keep Databricks-native sources for job history and Spark diagnostics. Watch ingestion cost.
Q16. Why must the wrapper re-raise the exception?
Otherwise the notebook completes normally and the job run shows success, so job notifications and retries never fire.
Q17. Why write a RUNNING record at start?
So runs that hang or are killed are visible as overdue; an end-only record leaves no trace of them.
Q18. Why is result_state sometimes NULL in job_run_timeline?
Runs are sliced hourly; only the final row of a run has result_state. Filter IS NOT NULL for outcomes.
Q19. How do you avoid alert storms from a check that runs every 15 minutes?
De-duplicate on environment + pipeline + run + state, record deliveries, and only alert again for genuinely new incidents or failed deliveries.
Q20. How do you know the monitoring itself is working?
Reconcile job runs against audit records, alert when the monitor job fails or stops running, and periodically test alert delivery.
