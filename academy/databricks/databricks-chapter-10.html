10.1Unity Catalog Fundamentals

10.1.1What Is Unity Catalog?

Simple definition

Unity Catalog is Databricks' centralized governance solution for data and AI assets: one governance layer across workspaces for metadata, access control, discovery, lineage, and auditing.

Without centralized governance

  • Inconsistent permissions across workspaces.
  • Uncontrolled access to sensitive data.
  • Duplicate governance configurations.
  • Hard-to-track data usage.
  • Limited lineage visibility.
  • Difficult auditing of critical data.

What it governs

  • Catalogs, schemas, tables, views.
  • Volumes and functions.
  • Models and other AI assets.
  • External locations and storage credentials.

Plus fine-grained access control, lineage, discovery, auditing, sharing, and sensitive-data governance.

Example: an organization with Finance, Sales, and Engineering keeps customer, transaction, and product data. Finance needs billing information, Sales needs customer and opportunity data, and Engineering needs operational datasets. Unity Catalog lets administrators organize these assets and grant privileges to groups instead of individual employees.

10.1.2Why Is Data Governance Required?

Data governance defines how data is accessed, managed, protected, discovered, and used, so people get the data their jobs need and nothing they aren't authorized to see.

10.1.4Metastore

A metastore is the top-level container for governed metadata and access-control configuration. It manages catalog metadata, object permissions, ownership, lineage, discovery, and governance across the workspaces attached to it. A metastore is typically tied to a cloud region and assigned to selected workspaces.

A metastore doesn't hold the data files themselves; those live in managed storage or external cloud storage.

Important

Don't assume every workspace shares the same metastore. Workspace-to-metastore assignment and workspace-level catalog access must be configured.

10.1.5Catalog

A catalog is the primary logical container within a metastore, often organized by environment, business domain, department, data product, or security boundary.

development
    |
    +-- sales
    +-- finance
    +-- operations

production
    |
    +-- sales
    +-- finance
    +-- operations
SQL
CREATE CATALOG IF NOT EXISTS sales_prod;

SHOW CATALOGS;

USE CATALOG sales_prod;

DESCRIBE CATALOG sales_prod;

Creating a catalog needs metastore privileges. Some organizations use domain catalogs instead and separate environments by naming and governance conventions.

When to create a separate catalog

When there's a real governance boundary: production vs development, finance vs general analytics, highly restricted vs broadly accessible, or independently managed data products. Avoid creating many catalogs without a clear purpose.

10.1.7Table

A table stores structured data in rows and columns. Unity Catalog governs Delta tables and other supported table types.

SQL
CREATE OR REPLACE TABLE sales_prod.customers.customer_master (
    CustomerID INT,
    CustomerName STRING,
    City STRING,
    Email STRING
)
USING DELTA;

INSERT INTO sales_prod.customers.customer_master
VALUES
    (101, 'John', 'Hyderabad', 'john@example.com'),
    (102, 'David', 'Chennai', 'david@example.com');

SELECT *
FROM sales_prod.customers.customer_master;

This replaces the three-column version created in 10.1.6. Every table has a name, schema, storage format, location or managed storage, metadata, an owner, and access permissions.

10.1.8View

A view is a named query over one or more objects; a standard view stores the query, not a copy of the results. To expose only IDs, names, and cities to a reporting group:

SQL
CREATE VIEW sales_prod.customers.customer_summary AS
SELECT
    CustomerID,
    CustomerName,
    City
FROM sales_prod.customers.customer_master;

SELECT *
FROM sales_prod.customers.customer_summary;

Benefits: simpler queries, a controlled interface to the data, reusable logic, and abstraction over table structures.

Security consideration

A view isn't automatically secure just because it omits sensitive columns. Underlying permissions, view type, and access-control behavior must be right. Test the view as the actual identity that will use it.

10.1.9Volume

A volume provides governed access to files that aren't necessarily tabular: CSV, JSON, XML, images, PDFs, configuration files, ML artifacts. For example, daily customer CSVs (customers_20261023.csv, …) can sit in a governed volume.

CREATE VOLUME IF NOT EXISTS sales_prod.bronze.customer_files;

-- External volume (needs storage credential + external location)
CREATE EXTERNAL VOLUME sales_prod.bronze.external_customer_files
LOCATION 'abfss://raw@myaccount.dfs.core.windows.net/customers/';
Python

10.1.10Function

A function encapsulates reusable logic. Databricks supports SQL functions and other types.

SQL
CREATE FUNCTION sales_prod.customers.calculate_discount(
    amount DECIMAL(12, 2),
    discount_percent DECIMAL(5, 2)
)
RETURNS DECIMAL(12, 2)
RETURN amount * discount_percent / 100;

SELECT
    sales_prod.customers.calculate_discount(1000, 10) AS DiscountAmount;
-- 100.00

Why use functions? Reuse business logic, standardize calculations, simplify SQL, reduce duplicated expressions.

Security consideration

Function privileges and execution behavior depend on the function type and security model. Don't assume every function runs with the same permissions or exposes data the same way.

10.2Data Objects

10.2.1Managed Tables

A managed table's data lifecycle is managed by Databricks through the catalog, in the configured managed storage location.

SQL
CREATE TABLE sales_prod.customers.managed_customers (
    CustomerID INT,
    CustomerName STRING
)
USING DELTA;

-- Normally removes the table AND its managed data
DROP TABLE sales_prod.customers.managed_customers;

Characteristics: catalog-managed metadata and storage lifecycle, integrated governance, and full Delta support. Always verify the table type before dropping a production object.

10.2.2External Tables

An external table's metadata is registered in Unity Catalog while its data stays at a specified external location.

SQL
CREATE TABLE sales_prod.customers.external_customers (
    CustomerID INT,
    CustomerName STRING
)
USING DELTA
LOCATION 'abfss://silver@myaccount.dfs.core.windows.net/customers/';

10.2.3Managed Volumes

A managed volume's storage lifecycle is managed by Databricks. Use it for raw source files, ingestion, file-based ML inputs, documents and images, and other non-tabular assets.

SQL + Python
CREATE VOLUME IF NOT EXISTS sales_prod.bronze.raw_files;

df = spark.read.csv(
    "/Volumes/sales_prod/bronze/raw_files/customers.csv",
    header=True
)
Lifecycle

Dropping a managed volume normally deletes its contents too. Evaluate the implications before using one for data that must be independently managed.

10.2.4External Volumes

An external volume governs access to files at an externally managed cloud location: an existing data lake, shared storage, processing files in place, or storage maintained independently of the volume.

SQL
CREATE EXTERNAL VOLUME sales_prod.bronze.external_raw_files
LOCATION 'abfss://raw@myaccount.dfs.core.windows.net/files/';

Requires a storage credential and external location. The path must follow the platform's rules for external volumes and not overlap an existing governed storage object.

10.2.5Views

SQL
-- Assumes the table has an IsActive column
CREATE VIEW sales_prod.customers.active_customers AS
SELECT
    CustomerID,
    CustomerName,
    City
FROM sales_prod.customers.customer_master
WHERE IsActive = true;

SELECT *
FROM sales_prod.customers.active_customers;

Benefits: simpler reporting, reusable logic, logical abstraction, and controlled exposure of selected columns and rows. Validate privileges and underlying access before using a view as a security boundary.

10.2.6Materialized Views

A materialized view stores query results and keeps them current through supported refresh mechanisms, which speeds up expensive, frequently reused queries.

SQL
CREATE MATERIALIZED VIEW sales_prod.reporting.monthly_sales_summary
AS
SELECT
    YEAR(OrderDate) AS OrderYear,
    MONTH(OrderDate) AS OrderMonth,
    SUM(TotalAmount) AS TotalSales
FROM sales_prod.silver.orders
GROUP BY
    YEAR(OrderDate),
    MONTH(OrderDate);

Illustrative. Availability, syntax, refresh behavior, and incremental-refresh eligibility depend on your environment.

10.2.7Functions

Categories include built-in SQL functions (like UPPER()), SQL user-defined functions, Python UDFs, and other supported types.

SQL
SELECT
    CustomerID,
    UPPER(CustomerName) AS CustomerNameUpper
FROM sales_prod.customers.customer_master;

Governance considerations

  • Control who can create or modify functions.
  • Review logic in functions that access sensitive data.
  • Validate function privileges.
  • Prefer built-in functions over UDFs when they can do the job.

10.2.8External Locations

An external location is a securable that pairs a cloud-storage path with a storage credential, controlling how Databricks accesses external storage.

External Location: raw_data_location
    |
    +-- Cloud storage URL
    |
    +-- Storage credential
    |
    +-- Access privileges

Typical workflow

  1. Configure the cloud identity or storage credential.
  2. Define an external location.
  3. Grant the necessary privileges.
  4. Create an external table or volume at an eligible path.
  5. Validate access with the intended identity.

External locations manage approved storage paths, storage access privileges, access to external tables and volumes, and the separation between storage configuration and data objects. They're especially important in Azure Databricks with ADLS Gen2.

10.2.9Storage Credentials

A storage credential represents the identity used to access cloud storage through Unity Catalog. In Azure Databricks this is typically a managed identity (via an Access Connector) or another supported Azure identity.

Prefer managed identities and other identity-based methods over long-lived embedded secrets. Use least privilege and review storage access periodically.

10.3Security and Permissions

10.3.1Unity Catalog Security Model

Unity Catalog uses privilege-based access control: users and groups receive privileges on securable objects (metastore, catalog, schema, table, view, volume, function, external location, storage credential), and their effective permissions determine what they can discover, query, create, or modify.

Least privilege

Grant only what the task needs. Report consumers need read access; data engineers may need read and write on selected schemas; administrators get broader privileges only when their responsibilities require it.

10.3.2GRANT

GRANT assigns a privilege to a user, group, or other principal.

SQL
-- Use the catalog
GRANT USE CATALOG ON CATALOG sales_prod TO `sales_analysts`;

-- Use the schema
GRANT USE SCHEMA ON SCHEMA sales_prod.customers TO `sales_analysts`;

-- Read the table
GRANT SELECT ON TABLE sales_prod.customers.customer_master TO `sales_analysts`;

-- Create tables in a schema
GRANT CREATE TABLE ON SCHEMA sales_prod.customers TO `data_engineers`;
To query a table, a group needs:

  USE CATALOG   on the catalog
       +
  USE SCHEMA    on the schema
       +
  SELECT        on the table
       +
  access to a SQL warehouse
  or other compute
Important distinction

GRANT assigns one privilege. It doesn't automatically grant the prerequisites needed to use an object; the group needs the right privileges at each level.

10.3.3REVOKE

SQL
REVOKE SELECT
ON TABLE sales_prod.customers.customer_master
FROM `sales_analysts`;
Revoking one grant may not remove all access

A user may still get in through another group, a broader inherited privilege, ownership, another grant, or a different authorized path. Review effective access rather than assuming one REVOKE closes every route.

10.3.4Ownership

The owner is the principal responsible for a securable, with important administrative authority, including managing permissions on what it owns.

SQL
ALTER TABLE sales_prod.customers.customer_master
OWNER TO `data_engineers`;

Ownership best practices

  • Prefer groups or service principals for durable operational ownership.
  • Don't leave critical production objects owned by an individual's account.
  • Separate ownership from ordinary read access.
  • Review ownership when teams or applications change.
  • Use administrators only where broad authority is genuinely needed.

10.3.6Privilege Inheritance

Privileges granted at a catalog or schema apply to descendant objects, including objects created later.

SQL
GRANT SELECT
ON SCHEMA sales_prod.customers
TO `sales_analysts`;

This gives read access to every current and future table and view in the schema. That saves repeating grants on each object, but broad grants can expose more than intended.

Best practice

Grant at the narrowest sensible level. For highly sensitive tables, consider whether schema-wide permissions are appropriate or whether per-object grants give better control.

10.3.7Workspace Permissions

Workspace permissions control what users can do inside a workspace (notebooks, jobs, SQL warehouses, folders, dashboards), separately from Unity Catalog data privileges. A user might open a notebook but not query a table, or hold SELECT on a table but lack permission to use the SQL warehouse needed to query it.

Two separate questions

  1. Can the user access the workspace resource?
  2. Can the user access the underlying data?

Both must be evaluated.

Workspace-catalog binding

Restricts which workspaces can access particular catalogs. It complements object privileges rather than replacing them.

10.3.8Service Principals

A service principal is a non-human identity for applications, scheduled jobs, CI/CD pipelines, automated ingestion, production transformations, and application integrations. It keeps production pipelines from depending on an employee's personal identity and supports controlled permissions and lifecycle management.

10.3.9Identity and Access Management

IAM defines how identities are created, authenticated, authorized, and managed. In Databricks it spans account users, groups, service principals, workspace assignments, Unity Catalog privileges, cloud-storage identities, and external application identities.

Access review process

  1. Identify each dataset's business owner.
  2. Define access requirements.
  3. Assign users to groups.

  6. Monitor usage and changes.
  7. Remove access when no longer needed.

10.4Advanced Governance

10.4.1Row Filters

Row filters restrict which rows each user sees, which is useful when groups need different subsets of one table. For example, the Hyderabad sales team should see only Hyderabad customers.

Step 1: Create the filter function, which returns TRUE for rows the current user may see:

SQL
CREATE FUNCTION sales_prod.customers.region_access(region STRING)
RETURNS BOOLEAN
RETURN
    CASE
        WHEN is_account_group_member('sales_admins') THEN TRUE
        WHEN is_account_group_member('hyderabad_sales')
             AND region = 'Hyderabad' THEN TRUE
        ELSE FALSE
    END;

Step 2: Attach it to the table, passing the column the function evaluates:

SQL
ALTER TABLE sales_prod.customers.customer_master
SET ROW FILTER sales_prod.customers.region_access ON (City);

-- To remove it later
ALTER TABLE sales_prod.customers.customer_master
DROP ROW FILTER;

Here the table's City column carries the region. Every query against the table is now filtered automatically for each user.

Important considerations
  • Define how users and groups map to permitted rows.
  • Test with real non-administrator identities.
  • Make sure unauthorized rows can't leak through other objects.
  • Consider the effect on query performance.
  • Review how views, functions, and other paths interact with the filter.

A row filter isn't a substitute for broader access-control design.

10.4.2Column Masks

Column masks control how a column's values appear to different users, protecting emails, phone numbers, tax IDs, bank details, and other sensitive identifiers.

SQL
-- Step 1: the masking function
CREATE FUNCTION sales_prod.customers.mask_email(email STRING)
RETURNS STRING
RETURN
    CASE
        WHEN email IS NULL THEN NULL
        WHEN is_account_group_member('customer_data_admins') THEN email
        ELSE 'REDACTED'
    END;

-- Step 2: attach it to the column
ALTER TABLE sales_prod.customers.customer_master
ALTER COLUMN Email SET MASK sales_prod.customers.mask_email;

-- To remove it later
ALTER TABLE sales_prod.customers.customer_master
ALTER COLUMN Email DROP MASK;
CustomerIDEmail (customer_data_admins)Email (everyone else)
101john@example.comREDACTED
102david@example.comREDACTED

Why column masks? They protect sensitive values, support role-based exposure, avoid maintaining multiple copies of a dataset, and help meet privacy requirements.

Important

A masked value can still leak through other columns, joins, aggregates, or alternate access paths. Review the whole dataset and access model, not one column in isolation.

10.4.6Data Discovery

With thousands of tables, users without good metadata create duplicates or pick the wrong source. Useful metadata includes name, description, column names, owner, business domain, classification, update frequency, quality expectations, and approved use cases.

SQL
COMMENT ON TABLE sales_prod.customers.customer_master
IS 'Curated customer master data for approved sales analytics.';

ALTER TABLE sales_prod.customers.customer_master
ALTER COLUMN CustomerID
COMMENT 'Unique business identifier for a customer.';
Every important production table should have

A meaningful name, a description, a defined owner, clear business meaning, documented key columns, and classification metadata.

10.4.7Tagging and Classification

Tags describe data assets and support governance workflows: identifying sensitive datasets, organizing assets, aiding discovery, and flagging objects that need special controls.

SQL
-- Table-level tags
ALTER TABLE sales_prod.customers.customer_master
SET TAGS (
    'data_domain' = 'sales',
    'classification' = 'confidential',
    'contains_pii' = 'true'
);

-- Column-level tag
ALTER TABLE sales_prod.customers.customer_master
ALTER COLUMN Email SET TAGS ('pii' = 'email');

A customer table holding personal data might be confidential; a public product-reference table, lower.

Tags don't enforce security

Adding classification = confidential doesn't block anyone unless a governance mechanism uses that tag to implement or evaluate a policy. Enforce restrictions with access controls and policies.

10.4.8Sensitive Data Protection

Personal, financial, authentication-related, contact, and confidential business information needs appropriate access, handling, retention, and monitoring.

Recommended controls

  1. Identify sensitive fields.
  2. Classify the data.
  3. Limit access through groups and object privileges.
  4. Use row filters or column masks where appropriate.
  5. Avoid unnecessary copies of sensitive data.
  6. Use approved storage and transfer mechanisms.
  7. Audit relevant access and administrative activity.
  8. Define retention and deletion requirements.
  9. Review access periodically.
  10. Test controls with representative identities.

An analyst counting customers by region doesn't need individual emails. Expose an aggregate or governed view instead of the full table.

Workspace-catalog binding use cases

  • Restrict production data to approved workspaces.
  • Keep development away from sensitive production catalogs.
  • Separate regulated environments.
  • Apply different operational controls per workspace.
Verify all layers

Workspace-to-metastore assignments, catalog bindings, object privileges, compute environment, and cloud-storage configuration. Test from both authorized and unauthorized workspaces. Binding doesn't replace object privileges or storage security.

10.5Data Sharing

10.5.1What Is Delta Sharing?

Delta Sharing is an open protocol for securely sharing data with other users and organizations, without handing over copies of your underlying storage. Recipients can use Databricks or supported non-Databricks clients. Instead of exporting and emailing files to an analytics partner, you share selected data through a governed configuration.

Benefits: controlled external access, less manual file distribution, governed shared assets, selective sharing, and integration with supported analytics tools.

10.5.2Sharing Data Securely

Recommended workflow

  1. Identify the external consumer.
  2. Define the business purpose.
  3. Select the approved data assets.
  4. Remove unnecessary sensitive information.
  5. Configure the appropriate sharing method.
  6. Grant only the necessary access.
  7. Test access with the intended recipient.
  8. Monitor usage where supported.
  9. Review the arrangement periodically.
  10. Revoke access when the agreement ends.
SQL · illustrative
-- 1. Create a share and add approved data
CREATE SHARE IF NOT EXISTS partner_share;

ALTER SHARE partner_share
ADD TABLE sales_prod.reporting.product_reference;

-- 2. Create the recipient
CREATE RECIPIENT IF NOT EXISTS partner_co;

-- 3. Give the recipient access to the share
GRANT SELECT ON SHARE partner_share TO RECIPIENT partner_co;

-- 4. When the agreement ends
REVOKE SELECT ON SHARE partner_share FROM RECIPIENT partner_co;

Requires sharing privileges in your metastore. A recipient on another Databricks account is created with their sharing identifier; others receive an activation link.

Important

Sharing a table doesn't make every column appropriate for external use. Review privacy, contractual, regulatory, and business requirements first.

10.5.3External Data Consumers

External consumers include business partners, vendors, customers, research organizations, and external analytics platforms, using Databricks, another compatible system, or a Delta Sharing client.

10.5.4Data Access Management

Internal users

  • Identity management.
  • Group membership.
  • Unity Catalog privileges.
  • Workspace permissions.
  • Data classification.
  • Audit and review.

External consumers (additionally)

  • Recipient configuration.
  • Share membership.
  • Approved data assets.
  • Sharing credentials or authentication.
  • Contractual controls.
  • Revocation procedures.

Before granting access, ask

  1. Who is the recipient?
  2. What is the business purpose?
  3. Which datasets are required?
  4. Is the data sensitive?
  5. Would a smaller dataset do?
  6. How long is access needed?
  7. Who approves it?
  8. How will access be monitored?
  9. How will access be revoked?

10.5.5Delta Sharing Concepts

A share is a named collection of data assets; a recipient is the identity or party receiving a share; the provider owns or administers the shared data.

Governance considerations

  • Share only approved assets.
  • Review recipient access.
  • Don't expose unnecessary sensitive columns.
  • Understand the sharing mode.
  • Monitor available access information.
  • Revoke recipients when access is no longer required.

Hands-On Exercise: Create a Catalog, Grant Access, and Verify Security

Build a basic governance setup: a catalog, schema, and Delta table with sample data; grant a reporting group read access; prove that authorized users can query it and unauthorized users can't; then revoke and retest.

Prerequisites

  • A Unity Catalog-enabled workspace with an assigned metastore.
  • Permission to create the catalog and schema.
  • A group such as sales_analysts.
  • A test user in that group.
  • A separate test user not in it.
  • Permission to grant and revoke privileges.
Before you start

Creating users and groups may need account-admin access. Never use a production table.

Free Edition and single-user workspaces: you may not be able to create a catalog; if so, create the schema inside an existing catalog you own instead. If you're the only user, you can still do every step except 8, 9, and the retest in 11, which need a second person.

Step 1: Create a catalog

SQL
CREATE CATALOG IF NOT EXISTS governance_lab;

SHOW CATALOGS;

DESCRIBE CATALOG governance_lab;

Step 2: Create a schema

SQL
CREATE SCHEMA IF NOT EXISTS governance_lab.sales;

SHOW SCHEMAS IN governance_lab;

Step 3: Create a Delta table

SQL
CREATE TABLE IF NOT EXISTS governance_lab.sales.customers (
    CustomerID INT,
    CustomerName STRING,
    City STRING
)
USING DELTA;

Step 4: Insert sample records

SQL
INSERT INTO governance_lab.sales.customers
VALUES
    (101, 'John', 'Hyderabad'),
    (102, 'David', 'Chennai'),
    (103, 'Smith', 'Bengaluru');

SELECT *
FROM governance_lab.sales.customers;
CustomerIDCustomerNameCity
101JohnHyderabad
102DavidChennai
103SmithBengaluru

Steps 5–7: Grant catalog, schema, and table access

SQL
-- Step 5: catalog usage (the group must already exist)
GRANT USE CATALOG
ON CATALOG governance_lab
TO `sales_analysts`;

-- Step 6: schema usage
GRANT USE SCHEMA
ON SCHEMA governance_lab.sales
TO `sales_analysts`;

-- Step 7: read access
GRANT SELECT
ON TABLE governance_lab.sales.customers
TO `sales_analysts`;

The group now has the intended read grant, provided all other access conditions are met.

Step 8: Test access as an authorized user

Sign in as a test user who belongs to sales_analysts and run:

SQL
SELECT *
FROM governance_lab.sales.customers;

Expected: the query succeeds and returns three records. If it fails, check group membership, catalog and schema privileges, table privileges, workspace-catalog binding, SQL warehouse or compute permissions, and other access controls.

Step 9: Test access as an unauthorized user

Sign in as a separate user who isn't in sales_analysts and has no other grant, then run the same query.

Expected: access is denied.

Important

Use a genuinely separate test identity. An administrator or the object owner has extra access, so testing as yourself proves nothing about the ordinary-user restriction.

Step 10: Review grants

SQL
SHOW GRANTS ON CATALOG governance_lab;

SHOW GRANTS ON SCHEMA governance_lab.sales;

SHOW GRANTS ON TABLE governance_lab.sales.customers;

These show direct grants on each object. They don't necessarily show every effective permission from group membership, ownership, inheritance, or workspace configuration.

Step 11: Revoke table access

SQL
REVOKE SELECT
ON TABLE governance_lab.sales.customers
FROM `sales_analysts`;

Test again as the authorized user. With no other SELECT grant or ownership, the query should now be denied. The catalog and schema usage privileges remain, but they don't grant SELECT on their own.

Step 12: Clean up

SQL
DROP CATALOG IF EXISTS governance_lab CASCADE;
Warning

CASCADE deletes every contained object and its managed data. Run it only on your dedicated training catalog after confirming there's nothing to keep.

Additional Practice Exercises

1. Governed view

Create a view exposing only CustomerID, CustomerName, and City. Grant the reporting group access to the view and confirm it works without granting access to the underlying table.

2. Managed volume

Create a managed volume, upload a sample CSV, read it in a notebook, and write the cleaned records to a Delta table.

3. Classify a sensitive table

Add a description and tags to a sample customer table. Document the business owner, allowed users, and sensitive columns.

4. Row-level restrictions

Build a multi-region test table and a row filter so a test group sees only its region. Verify permitted and denied records.

5. Column mask

Mask a sensitive test column such as email. Verify results as authorized and unauthorized identities.

6. Data lineage

Build a small pipeline from a source table to a target Delta table, then inspect the lineage and identify upstream and downstream dependencies.

7. Audit information

Identify the audit sources available in your account and which events help investigate permission changes and data access.

8. Workspace boundaries

If you have separate dev and production workspaces, review catalog assignments, bindings, and permissions. Document who can access each environment.
