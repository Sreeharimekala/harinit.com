11.1Introduction to Medallion Architecture

11.1.1What Is Medallion Architecture?

Medallion Architecture is a data design pattern that organizes data into processing layers, each representing a higher level of quality, transformation, and business readiness. Data generally moves from Bronze to Silver, then from Silver to Gold.

🥉 Bronze

Emphasizes preservation and traceability.

🥈 Silver

Emphasizes quality and consistency.

🥇 Gold

Emphasizes business meaning and efficient consumption.

The core principle

Data becomes more refined as it moves through the layers.

11.1.2Why Use Layered Data Processing?

Imagine a retail company receiving daily CSV files of customers, products, orders, and sales. The files may contain duplicate customers, missing IDs, invalid prices, inconsistent date formats, amounts stored as strings, orders referencing nonexistent customers or products, and inconsistent status values.

If every report consumes the raw files directly, each one implements its own cleansing logic, which leads to duplicated work and reports that disagree. Medallion Architecture separates the responsibilities instead:

What each layer does with it

The raw data stays available for investigation instead of being overwritten by cleansing logic. Layering makes pipelines easier to understand, test, troubleshoot, and maintain.

11.1.3Raw Data Versus Curated Data

Raw data is data as received from the source, possibly with ingestion metadata. Curated data has been processed according to defined technical and business rules.

CSV
OrderID,CustomerID,OrderDate,Amount
1001,C001,2026-10-01,1500.50
1002,C002,01-10-2026,2500
1003,C003,INVALID,500

Silver may

  • Convert OrderID to an integer and Amount to a decimal.
  • Keep CustomerID as a string.
  • Parse OrderDate into a date.
  • Identify the invalid date.
  • Quarantine records that can't be corrected safely.

Bronze retains the values as received; Gold calculates total sales by month, city, or category. Notice that row 1002 uses a different date format: parsing it with yyyy-MM-dd gives NULL, so Silver has to treat it as a format problem, not silently guess.

Important

Preserving raw data doesn't mean keeping every file forever without controls. Retention, access, privacy, and storage policies still apply.

11.1.4Data Lineage

Lineage describes where data came from, how it was transformed, and which downstream objects depend on it.

Questions lineage answers

  • Which source file produced this sales record?
  • Which transformation calculated this revenue figure?
  • Which reports depend on this table?
  • Why did a report change after a run?
  • Which downstream datasets need refreshing after a correction?

Implementing lineage: at ingestion, record the source file name, source system, ingestion timestamp, pipeline run ID, batch ID, and source record identifier where available. Unity Catalog also captures lineage for supported operations (Chapter 10).

Application-level metadata and platform lineage complement each other. Platform lineage may not capture every external process or business rule.

11.1.5Separation of Responsibilities

Bronze

  • Read data from source systems.
  • Preserve source values.
  • Add ingestion metadata.
  • Track source files and batches.
  • Handle schema changes safely.
  • Record ingestion failures.

Silver

  • Clean and standardize data.
  • Convert data types.
  • Apply deduplication rules.
  • Validate business keys.
  • Separate valid and invalid records.
  • Reusable, business-independent transformations.

Gold

  • Create fact and dimension tables.
  • Calculate business metrics.
  • Aggregate data for reporting.
  • Implement reporting-specific definitions.
  • Prepare efficient datasets for BI tools.
Design rule

Avoid putting every transformation in one notebook. Separate stages so each can be tested, rerun, and maintained independently.

11.2Bronze Layer

11.2.1What Is the Bronze Layer?

Bronze is the first persisted layer in the lakehouse. It captures source data reliably while preserving enough information to investigate ingestion and quality issues. Bronze tables are usually Delta tables.

Names
bronze.customers_raw
bronze.products_raw
bronze.orders_raw
bronze.sales_raw
Unity Catalog names
-- catalog.schema.table
retail_dev.bronze.customers_raw
retail_dev.bronze.products_raw
retail_dev.bronze.orders_raw
retail_dev.bronze.sales_raw

The catalog and schema must exist, and the executing identity needs the required privileges.

11.2.2Raw Data Ingestion

Suppose this file arrives at /Volumes/retail_dev/landing/customers/customers_20261025.csv:

CSV
CustomerID,CustomerName,Email,City
C001,Ravi,ravi@example.com,Hyderabad
C002,Priya,priya@example.com,Chennai
C003,Arun,arun@example.com,Bengaluru
Python
from pyspark.sql import functions as F

source_path = (
    "/Volumes/retail_dev/landing/customers/"
    "customers_20261025.csv"
)

customers_df = (
    spark.read
    .option("header", True)
    .option("inferSchema", False)
    .csv(source_path)
)

display(customers_df)

With inferSchema set to False, every value stays a string. That preserves the source representation and postpones type validation until Silver.

CSV doesn't enforce a schema. Column names, delimiters, quoting, encoding, and malformed rows must be handled according to the source contract.

11.2.3Creating a Bronze Delta Table

Add ingestion metadata to the DataFrame:

Python
bronze_customers_df = (
    customers_df
    .withColumn("_source_file", F.col("_metadata.file_path"))
    .withColumn("_ingested_at", F.current_timestamp())
    .withColumn("_source_system", F.lit("RETAIL_CSV"))
    .withColumn("_batch_id", F.lit("retail_batch_20261025_001"))
)

display(bronze_customers_df)
Why _metadata.file_path?

Older examples use F.input_file_name(), which isn't supported on Unity Catalog shared and serverless compute. The hidden _metadata column works on file sources everywhere (you used it in Chapter 8).

ColumnPurpose
_source_fileThe source file path
_ingested_atThe ingestion timestamp
_source_systemThe source system
_batch_idThe ingestion batch
SQL + Python
CREATE SCHEMA IF NOT EXISTS retail_dev.bronze;

(
    bronze_customers_df.write
    .format("delta")
    .mode("append")
    .saveAsTable("retail_dev.bronze.customers_raw")
)
append is not duplicate-safe

append adds rows; it doesn't stop the same file being loaded twice. In production, use a durable batch ID, a source-file manifest, Auto Loader file tracking (Chapter 12), or another ingestion ledger so retries don't duplicate data.

11.2.4Preserving Source Data

Avoid destructive business transformations in Bronze. Don't replace " hyderabad " with "Hyderabad" in the only persisted copy. Keep the source value in Bronze and standardize it in Silver, so the team can still investigate source formatting changes, unexpected values, conversion failures, source-system defects, and incorrect mappings.

Adding technical metadata to Bronze is fine; changing business values isn't.

For strict audit requirements, also keep the original files in immutable or access-controlled storage. A Delta table doesn't preserve the exact bytes or serialization of every source file.

11.2.5Handling Source Schema Changes

Before:
CustomerID,CustomerName,City

After:
CustomerID,CustomerName,City,Country

Before accepting a new column, check

  • Is the new field expected?
  • Has the source contract changed?
  • Can downstream transformations handle it?
  • Does it need validation or masking?
  • Is the change backward-compatible?

For a Delta append, schema evolution can be enabled explicitly:

Python
(
    bronze_customers_df.write
    .format("delta")
    .mode("append")
    .option("mergeSchema", "true")
    .saveAsTable("retail_dev.bronze.customers_raw")
)
Use deliberately

Don't turn on mergeSchema in every pipeline: unexpected source columns become permanent table columns. Define an approved schema policy and record schema changes.

11.2.6Handling Bad CSV Records

Malformed records include missing or extra fields, invalid quoting, unexpected delimiters, and bad encoding. Spark's CSV reader has PERMISSIVE, DROPMALFORMED, and FAILFAST modes. To capture bad rows in PERMISSIVE mode, give Spark an explicit schema that includes the corrupt-record column:

Python
from pyspark.sql.types import StructType, StructField, StringType

customers_schema = StructType([
    StructField("CustomerID", StringType()),
    StructField("CustomerName", StringType()),
    StructField("Email", StringType()),
    StructField("City", StringType()),
    StructField("_corrupt_record", StringType()),   # receives bad rows
])

raw_df = (
    spark.read
    .format("csv")
    .option("header", True)
    .schema(customers_schema)
    .option("mode", "PERMISSIVE")
    .option("columnNameOfCorruptRecord", "_corrupt_record")
    .load(source_path)
)

display(raw_df.filter(F.col("_corrupt_record").isNotNull()))

Tested with a file containing one row with an extra field and one row with missing fields: both were flagged, and the full original line appeared in _corrupt_record.

CustomerIDCustomerNameEmailCity_corrupt_record
C002Priyapriya@example.comChennaiC002,Priya,priya@example.com,Chennai,EXTRA
C003ArunNULLNULLC003,Arun
PERMISSIVE doesn't catch everything

Unexpected business values aren't parsing errors. For important pipelines, keep separate controls for: (1) file-level failures, (2) parsing failures, (3) schema validation failures, and (4) business data-quality failures. Never silently discard invalid source records.

11.3Silver Layer

11.3.1What Is the Silver Layer?

Silver holds cleaned, standardized, validated, and deduplicated data (silver.customers, silver.products, silver.orders, silver.sales) with defined quality rules and predictable types. Records that fail validation should be clearly identified and isolated, never silently mixed into trusted datasets.

11.3.2Data Cleansing

Common operations: trimming spaces, normalizing case, converting empty strings to nulls, standardizing dates, validating numbers, applying approved code mappings, and handling invalid records.

Python
from pyspark.sql import functions as F

customers_clean_df = (
    spark.table("retail_dev.bronze.customers_raw")
    .withColumn("CustomerID", F.trim(F.col("CustomerID")))
    .withColumn("CustomerName", F.trim(F.col("CustomerName")))
    .withColumn("Email", F.lower(F.trim(F.col("Email"))))
    .withColumn("City", F.initcap(F.trim(F.col("City"))))
    .withColumn(
        "City",
        F.when(F.col("City") == "", None)
         .otherwise(F.col("City"))
    )
)
Notes

In production, convert empty strings to null for every relevant field, not only City. Be careful with case normalization: right for cities and emails, wrong for case-sensitive identifiers or source codes.

11.3.3Data Type Conversion

Bronze values are strings; Silver converts them to proper types.

Python
orders_raw_df = spark.table("retail_dev.bronze.orders_raw")

orders_typed_df = (
    orders_raw_df
    .withColumn("OrderID", F.expr("try_cast(OrderID AS BIGINT)"))
    .withColumn("OrderDate", F.expr("try_cast(OrderDate AS DATE)"))
    .withColumn("Amount", F.expr("try_cast(Amount AS DECIMAL(18,2))"))
)

try_cast returns NULL when a value can't be converted, instead of failing the whole query. For dates in a specific format, use an explicit parser, and use its try_ version:

Python
orders_typed_df = orders_raw_df.withColumn(
    "OrderDate",
    F.expr("try_to_date(OrderDate, 'yyyy-MM-dd')")
)
to_date vs try_to_date

Databricks runs Spark SQL in ANSI mode by default on serverless and SQL warehouses (and Spark 4 everywhere). In ANSI mode, F.to_date("INVALID", "yyyy-MM-dd") fails the whole job with CANNOT_PARSE_TIMESTAMP. try_to_date returns NULL instead, so the row can be quarantined. Verified on Spark 4.

Use the date format in the source contract. Never guess ambiguous dates like 01-02-2026.

11.3.4Deduplication

Duplicates appear when a source exports a record twice, a file is resent, a pipeline retries an append, or incremental loads overlap.

Python · simple
customers_dedup_df = customers_clean_df.dropDuplicates(["CustomerID"])

But dropDuplicates(["CustomerID"]) doesn't define which record wins when duplicates differ. Production code needs a deterministic rule: latest source update timestamp, highest sequence number, most recently ingested (if approved), or source-system priority.

Python · deterministic
from pyspark.sql import Window
from pyspark.sql import functions as F

dedup_window = (
    Window
    .partitionBy("CustomerID")
    .orderBy(
        F.col("SourceUpdatedAt").desc_nulls_last(),
        F.col("_ingested_at").desc_nulls_last()
    )
)

customers_dedup_df = (
    customers_clean_df
    .withColumn("_row_number", F.row_number().over(dedup_window))
    .filter(F.col("_row_number") == 1)
    .drop("_row_number")
)

Assumes a SourceUpdatedAt column exists. Add a tie-breaker in case two rows have identical ordering values.

Don't dedupe on full rows when you know the key

Two rows with the same business key but different attributes may be a real update, not a duplicate.

RuleExample

Python
valid_orders_df = orders_typed_df.filter(
    F.col("OrderID").isNotNull()
    & F.col("CustomerID").isNotNull()
    & F.col("OrderDate").isNotNull()
    & F.col("Amount").isNotNull()
    & (F.col("Amount") >= 0)
)

invalid_orders_df = orders_typed_df.filter(
    F.col("OrderID").isNull()
    | F.col("CustomerID").isNull()
    | F.col("OrderDate").isNull()
    | F.col("Amount").isNull()
    | (F.col("Amount") < 0)
)

Keep the two conditions logically consistent so no record falls out of both outputs. The single rejection_reason column in 11.3.7 makes that automatic.

11.3.6Business-Key Validation

A business key identifies a real-world entity: Customer → CustomerID, Product → ProductID, Order → OrderID, Order line → OrderID + ProductID + LineNumber. It isn't the same as a generated surrogate key in a dimensional model.

Python
# Required keys
valid_customers_df = customers_dedup_df.filter(
    F.col("CustomerID").isNotNull()
    & (F.col("CustomerID") != "")
)

# Duplicate keys
duplicate_customer_keys_df = (
    customers_clean_df
    .groupBy("CustomerID")
    .count()
    .filter(F.col("count") > 1)
)

# Orders referencing unknown customers
customers_keys_df = (
    spark.table("retail_dev.silver.customers")
    .select("CustomerID")
    .distinct()
)

orphan_orders_df = orders_typed_df.join(
    customers_keys_df,
    on="CustomerID",
    how="left_anti"
)

A left-anti join returns rows from the left side with no match on the right side, which is exactly what you need to find orphaned orders.

11.3.7Handling Invalid Records

Strategies

  1. Reject: exclude from trusted Silver data.
  2. Quarantine: store with the rejection reason.
  3. Correct: apply a documented, deterministic fix.
  4. Default: only when business rules allow it.
  5. Fail the pipeline: when a critical threshold is breached.
Record vs batch problems

A missing customer name is a record-level issue. A completely missing OrderID column is a batch-level schema failure that should stop the run.

SQL · minimal quarantine table
CREATE TABLE IF NOT EXISTS retail_dev.silver.orders_quarantine
USING DELTA
AS
SELECT
    CAST(NULL AS STRING) AS OrderID,
    CAST(NULL AS STRING) AS CustomerID,
    CAST(NULL AS STRING) AS OrderDate,
    CAST(NULL AS STRING) AS Amount,
    CAST(NULL AS STRING) AS rejection_reason,
    CAST(NULL AS TIMESTAMP) AS quarantined_at
WHERE 1 = 0;

A real quarantine schema should keep all relevant source columns as received, plus source metadata, batch ID, and error details.

Python · assign a reason
orders_classified_df = orders_typed_df.withColumn(
    "rejection_reason",
    F.when(F.col("OrderID").isNull(), "INVALID_ORDER_ID")
     .when(F.col("CustomerID").isNull(), "MISSING_CUSTOMER_ID")
     .when(F.col("OrderDate").isNull(), "INVALID_ORDER_DATE")
     .when(F.col("Amount").isNull(), "INVALID_AMOUNT")
     .when(F.col("Amount") < 0, "NEGATIVE_AMOUNT")
     .otherwise(None)
)
Two writes aren't one transaction

Writing valid rows to Silver and invalid rows to quarantine are two separate table writes. If both must succeed or fail together, design an explicit transaction or orchestration strategy.

11.3.8Incremental Transformations

Incremental pipelines process new or changed records instead of recomputing all history. Approaches: process newly arrived files, filter by source update timestamp, use source-system change tracking, Change Data Feed (where enabled), Auto Loader, or a batch ledger.

Python · teaching example
incremental_df = (
    spark.table("retail_dev.bronze.orders_raw")
    .filter(
        F.col("_ingested_at") >=
        F.lit("2026-10-25 00:00:00").cast("timestamp")
    )
)
Not a production watermark

A real watermark accounts for late-arriving data, retry windows, timestamp precision, and the difference between ingestion time and source update time. Store it in a persisted checkpoint or batch ledger instead of hard-coding it.

11.4Gold Layer

11.4.1What Is the Gold Layer?

Gold holds datasets designed for analysis and reporting, with clear business definitions, stable types, documented grain, and appropriate access controls.

Typical tables
gold.dim_customer
gold.dim_product
gold.dim_date
gold.fact_sales
gold.daily_sales_summary
gold.monthly_sales_summary

Grain = what one row represents

  • dim_customer: one row per customer (or per version).
  • dim_product: one row per product (or per version).
  • fact_sales: one row per order line.
  • daily_sales_summary: one row per date (plus any other dimensions).
Rule

Document the grain before you build a fact table.

11.4.2Fact Tables

A fact table stores measurable business events: sales transactions, order lines, payments, returns, inventory movements.

11.4.4Creating a Gold Fact Table

Assuming Silver has orders, order_items, customers, and products:

SQL
CREATE OR REPLACE TABLE retail_dev.gold.fact_sales
USING DELTA
AS
SELECT
    oi.OrderID,
    oi.ProductID,
    o.CustomerID,
    CAST(o.OrderDate AS DATE) AS OrderDate,
    CAST(oi.Quantity AS BIGINT) AS Quantity,
    CAST(oi.UnitPrice AS DECIMAL(18,2)) AS UnitPrice,
    CAST(oi.Quantity * oi.UnitPrice AS DECIMAL(18,2)) AS SalesAmount
FROM retail_dev.silver.order_items oi
INNER JOIN retail_dev.silver.orders o
    ON oi.OrderID = o.OrderID;

Validate before production

  • OrderID is unique at the order grain.
  • Order items have the expected line grain.
  • The join doesn't multiply rows.
  • Quantity and price are valid.
  • Currency and discount rules are correct.
CREATE OR REPLACE = full refresh

It rebuilds the whole table from the query. Fine for full refreshes, not for blindly maintaining large incremental production tables (use MERGE there; see 11.5.4).

11.4.5Aggregated Tables

Aggregates make common reporting queries simpler and often faster.

SQL
CREATE OR REPLACE TABLE retail_dev.gold.daily_sales_summary
USING DELTA
AS
SELECT
    OrderDate,
    ProductID,
    SUM(SalesAmount) AS TotalSales,
    SUM(Quantity) AS TotalQuantity,
    COUNT(DISTINCT OrderID) AS TotalOrders
FROM retail_dev.gold.fact_sales
GROUP BY
    OrderDate,
    ProductID;

This groups by product ID; to group by category, join the product dimension and group by its category.

Watch out for non-additive measures

Never average daily averages. Recalculate average selling price from total revenue ÷ total quantity. Likewise, TotalOrders (a distinct count) can't be summed across days or products.

11.4.6KPI Calculations

SQL
-- Total sales
SELECT SUM(SalesAmount) AS TotalSales
FROM retail_dev.gold.fact_sales;

-- Total quantity sold
SELECT SUM(Quantity) AS TotalQuantitySold
FROM retail_dev.gold.fact_sales;

-- Number of orders
SELECT COUNT(DISTINCT OrderID) AS TotalOrders
FROM retail_dev.gold.fact_sales;

-- Average order value
SELECT
    SUM(SalesAmount) / NULLIF(COUNT(DISTINCT OrderID), 0) AS AverageOrderValue
FROM retail_dev.gold.fact_sales;

-- Sales by month
SELECT
    DATE_TRUNC('MONTH', OrderDate) AS SalesMonth,
    SUM(SalesAmount) AS TotalSales
FROM retail_dev.gold.fact_sales
GROUP BY DATE_TRUNC('MONTH', OrderDate)
ORDER BY SalesMonth;

NULLIF(…, 0) avoids division by zero. Every production KPI needs a written definition: does "sales" include tax, shipping, cancelled orders, returns, discounts?

11.4.7Reporting Views

SQL
CREATE OR REPLACE VIEW retail_dev.gold.vw_sales_by_customer AS
SELECT
    c.CustomerID,
    c.CustomerName,
    c.City,
    SUM(f.SalesAmount) AS TotalSales,
    COUNT(DISTINCT f.OrderID) AS TotalOrders
FROM retail_dev.gold.fact_sales f
INNER JOIN retail_dev.gold.dim_customer c
    ON f.CustomerID = c.CustomerID
GROUP BY
    c.CustomerID,
    c.CustomerName,
    c.City;

Views give reporting a stable interface and avoid duplicated logic. A standard view doesn't store results; performance depends on the underlying tables and query plan.

11.5Pipeline Design

A correct transformation is only part of a production pipeline. It must also manage dependencies, retries, reprocessing, and failure recovery.

11.5.1Bronze-to-Silver Transformations

Typical steps

  1. Read new or changed Bronze data.
  2. Validate the source schema.
  3. Normalize strings and null values.
  4. Convert data types.
  5. Detect duplicate business keys.
  6. Apply deterministic deduplication.
  7. Validate relationships and business rules.
  8. Write valid records to Silver.
  9. Write rejected records to quarantine.
  10. Record batch metrics and status.
Python
from pyspark.sql import functions as F

bronze_orders_df = spark.table("retail_dev.bronze.orders_raw")

typed_orders_df = (
    bronze_orders_df
    .withColumn("OrderID", F.expr("try_cast(OrderID AS BIGINT)"))
    .withColumn("CustomerID", F.trim(F.col("CustomerID")))
    .withColumn("OrderDate", F.expr("try_cast(OrderDate AS DATE)"))
    .withColumn("Amount", F.expr("try_cast(Amount AS DECIMAL(18,2))"))
)

classified_orders_df = typed_orders_df.withColumn(
    "rejection_reason",
    F.when(F.col("OrderID").isNull(), "INVALID_ORDER_ID")
     .when(F.col("CustomerID").isNull(), "MISSING_CUSTOMER_ID")
     .when(F.col("OrderDate").isNull(), "INVALID_ORDER_DATE")
     .when(F.col("Amount").isNull(), "INVALID_AMOUNT")
     .when(F.col("Amount") < 0, "NEGATIVE_AMOUNT")
     .otherwise(None)
)

valid_orders_df = classified_orders_df.filter(F.col("rejection_reason").isNull())
invalid_orders_df = classified_orders_df.filter(F.col("rejection_reason").isNotNull())

Next, write both outputs using a defined retry and audit strategy.

11.5.2Silver-to-Gold Transformations

Typical steps

  1. Read validated orders and order items.
  2. Join to validated customers and products where required.
  3. Enforce the intended grain.
  4. Calculate measures such as sales amount.
  5. Generate or look up dimension keys.
  6. Apply business-specific rules.
  7. Write fact and dimension tables.
  8. Recalculate affected aggregates.
  9. Run reconciliation checks.
Protect the grain

If the fact is at order-line level, a one-to-many join must never produce multiple fact rows for one order line.

11.5.3Dependency Management

Ingest Customers   --> Clean Customers   --+
Ingest Products    --> Clean Products    --+
Ingest Orders      --> Clean Orders      --+--> Build Fact Sales
Ingest Order Items --> Clean Order Items --+          |
                                                      v

                                                      |
                                                      v

The fact-building task mustn't start until every required Silver dataset is ready. Lakeflow Jobs (formerly Databricks Workflows, covered in Chapter 14) orchestrate tasks with explicit dependencies: ingestion, data-quality validation, transformation, reconciliation, notification, and downstream refresh tasks. Configure dependencies explicitly instead of relying on manual run order.

11.5.4Idempotent Processing

An operation is idempotent when repeating it with the same inputs produces the same intended final result.

RunRows for OrderID 1001
After run 1 (append)1
After run 2 (same file appended)2 ✗
After run 2 (MERGE on OrderID)1 ✓

Ways to achieve idempotency

  • Track processed files and batches.
  • Use a stable source record identifier.
  • Deduplicate by business key and ordering rule.
  • Use Delta MERGE to insert new and update changed records.
  • Replace a well-defined partition when reprocessing it.
  • Make aggregates deterministic.
  • Persist checkpoints and status.
SQL
MERGE INTO retail_dev.silver.customers AS target
USING retail_dev.silver.customers_staging AS source
ON target.CustomerID = source.CustomerID

WHEN MATCHED THEN UPDATE SET
    target.CustomerName = source.CustomerName,
    target.Email = source.Email,
    target.City = source.City

WHEN NOT MATCHED THEN INSERT (
    CustomerID, CustomerName, Email, City
)
VALUES (
    source.CustomerID, source.CustomerName, source.Email, source.City
);
MERGE isn't automatically safe

It needs a proper match key and exactly one source row per key. Deduplicate the source first, or the merge fails with multiple matching source rows (Chapter 9). Handle source deletions explicitly if they occur.

11.5.5Restartability

Task 1: Ingest customers    ✓
Task 2: Ingest products     ✓
Task 3: Ingest orders       ✓
Task 4: Build fact sales    ✓
Task 5: Build sales summary ✗ failed

-> rerun Task 5 only

A restartable design

  • Persists completed Bronze data.
  • Makes each transformation repeatable.
  • Tracks task and batch status.
  • Stores metadata identifying the failed stage.
  • Supports rerunning failed tasks.
  • Avoids publishing incomplete Gold data.
  • Ensures retries don't duplicate records.

Restartability means a pipeline can resume or rerun after failure without corrupting data. The right restart boundary depends on the source, transformation, and write strategy.

11.5.6Reprocessing Historical Data

Needed when a business rule changes, source data is corrected, a conversion defect is fixed, columns are added, history was missing, or a reporting definition changes. Parameterize the processing range:

Python
start_date = "2026-10-01"
end_date = "2026-10-25"

orders_to_reprocess_df = (
    spark.table("retail_dev.silver.orders")
    .filter(
        (F.col("OrderDate") >= F.lit(start_date).cast("date"))
        & (F.col("OrderDate") <= F.lit(end_date).cast("date"))
    )
)

This only selects existing Silver records. A real reprocessing pipeline reads the authoritative source, recalculates, and identifies every dependent fact, dimension, aggregate, and report that must be rebuilt. In a job, pass the dates as job parameters (Chapter 14).

11.6.7Step 5: Clean Customers into Silver

Trim strings, normalize email and city, and remove duplicate customer IDs with a deterministic rule.

Python
from pyspark.sql import functions as F
from pyspark.sql import Window

customers_bronze_df = spark.table("retail_dev.bronze.customers_raw")

customers_clean_df = (
    customers_bronze_df
    .withColumn("CustomerID", F.trim(F.col("CustomerID")))
    .withColumn("CustomerName", F.trim(F.col("CustomerName")))
    .withColumn("Email", F.lower(F.trim(F.col("Email"))))
    .withColumn("City", F.initcap(F.trim(F.col("City"))))
)

customer_window = (
    Window
    .partitionBy("CustomerID")
    .orderBy(
        F.col("_ingested_at").desc(),
        F.col("_source_file").desc()
    )
)

customers_dedup_df = (
    customers_clean_df
    .withColumn("_rn", F.row_number().over(customer_window))
    .filter(F.col("_rn") == 1)
    .drop("_rn")
)

valid_customers_df = customers_dedup_df.filter(
    F.col("CustomerID").isNotNull()
    & (F.col("CustomerID") != "")
    & F.col("CustomerName").isNotNull()
    & (F.col("CustomerName") != "")
)

(
    valid_customers_df.write
    .format("delta")
    .mode("overwrite")
    .option("overwriteSchema", "true")
    .saveAsTable("retail_dev.silver.customers")
)

Here the duplicate rows are identical (same batch, same file), so either one may win. In production, order by a source update timestamp or another approved tie-breaker. This is a full refresh from Bronze, and keeping customer history would need a different (SCD) design.

11.7Production Best Practices

1. Naming conventions

bronze.customers_raw
bronze.orders_raw
silver.customers
silver.orders
gold.dim_customer
gold.dim_product
gold.fact_sales
gold.daily_sales_summary

Don't mix raw and curated datasets in one schema without a clear reason.

2. Metadata standards

Bronze: _source_system, _source_file, _ingested_at, _batch_id, _pipeline_run_id

Silver/Gold: _created_at, _updated_at, _record_status, _source_updated_at

Only include columns with a clear operational or business purpose.

3. Data-quality rules

  • Customer IDs can't be null.
  • Product IDs unique at the chosen grain.
  • Order dates valid; quantities positive; prices nonnegative.
  • Order items reference valid products and orders.
  • Sales totals reconcile within tolerance.

Count failures, and decide whether each rule warns, quarantines, or fails.

4. Performance

  • Select only required columns; filter early when safe.
  • Avoid unnecessary shuffles; inspect plans.
  • Prefer incremental over repeated full rebuilds.
  • Use Delta maintenance based on measured query patterns.
  • Right-size compute; watch for skew and small files.
  • Don't partition every table automatically.

5. Security and governance

  • Grant consumers Gold, not raw data, by default.
  • Least privilege; restrict sensitive fields.
  • Masks and row filters where needed.
  • No credentials in notebooks or code.
  • Managed identities / service principals.
  • Review audit logs; define retention and deletion.

6. Monitoring and alerting

  • Job status, task duration, file arrival.
  • Row counts, rejected counts, freshness.
  • Duplicate-key and orphan-record counts.
  • Reconciliation differences.
  • Gold update time and Power BI refresh status.

A job can succeed technically and still produce incomplete business data, so monitor quality too.

11.8Knowledge Check

Try answering each question before revealing the answer.

1. What are the three layers of Medallion Architecture?
Bronze (raw), Silver (cleaned and validated), and Gold (business-ready).
2. Why should Bronze preserve source values?
It keeps source evidence for investigation, replay, and auditing, so cleansing mistakes can be found and fixed by reprocessing.
3. What is the difference between a business key and a surrogate key?
A business key identifies an entity in the business domain (e.g. CustomerID); a surrogate key is an internal identifier generated for the data model (e.g. CustomerKey), useful for SCDs.
4. Why is dropDuplicates() insufficient for conflicting records?
It doesn't define which record wins when rows share a key but have different attributes. Use a window with deterministic ordering instead.
5. What is a quarantine table?
A table that stores rejected or invalid records along with diagnostic information such as the rejection reason, source file, and batch ID.
6. What does idempotency mean in a data pipeline?
Repeating the same processing with the same inputs produces the same intended final state, with no duplicate side effects.
7. Why should a fact table have a documented grain?
Grain defines what one row represents, which prevents joins from multiplying rows and aggregations from double counting.
8. When would you use Delta MERGE instead of a full-table overwrite?
For controlled inserts and updates on a large or incrementally maintained table, when there's a stable match key and the source has been deduplicated to one row per key.
9. Why is an inner join potentially dangerous when validating foreign keys?
Unmatched records disappear silently instead of being flagged. In the project, order item 1004/P002 vanishes from the fact unless the Step 9 anti-join check catches it.
10. What is the difference between Power BI Import and DirectQuery?
Import stores data in the Power BI semantic model and needs refreshes; DirectQuery sends queries to Databricks at report time.
11. Why should a pipeline record batch IDs and source filenames?
They support traceability, duplicate prevention, troubleshooting, and targeted reprocessing.
12. What should happen if a critical data-quality rule fails?
Follow a defined policy: reject or quarantine records, notify owners, or fail the affected stage. Never silently continue.
