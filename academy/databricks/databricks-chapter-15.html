15.1Understanding Performance

15.1.1Why Do Spark Jobs Become Slow?

Spark splits work into tasks across a cluster, but distribution has costs. Common causes of slowness: inefficient joins, excessive shuffling, data skew, small files, poor partitioning, too little compute, memory pressure, GC overhead, Python UDFs, repeated scans, stale statistics, weak filtering, wrong join conditions, and poor data layout.

TableRowsPurpose
fact_sales500 millionSales transactions
dim_customer2 millionCustomer attributes
dim_product100,000Product attributes
dim_date10,000Calendar attributes

Slow vs optimized

Slow: reads all 500M rows, shuffles heavily, joins before filtering, hits skewed keys, writes excessive intermediate data. 20+ minutes.

Optimized: filters early, reads only needed columns, broadcasts genuinely small dimensions, mitigates skew, improves data skipping. Much faster, depending on workload.

15.1.2Understanding Spark Execution Plans

Spark's optimizer (Catalyst) turns SQL or DataFrame code into an execution strategy in three steps:

1. Logical plan: what

Read fact_sales → read dim_customer → join on customer_id → group by customer_name → sum sales.

Rewritten with predicate pushdown, column pruning, constant folding, expression simplification, and join reordering where beneficial.

3. Physical plan: how

The concrete operators Spark runs, such as which join algorithm and where data is exchanged.

What to look for

  1. Unnecessary full-table scans?
  2. Filters applied before expensive work?
  3. Unneeded columns read?
  4. Broadcast where appropriate?
  5. Large Exchange operators?
  6. Repeated scans of one source?
  7. Unexpectedly expensive sorts or aggregations?
  8. A Python UDF blocking optimizations?
Interview tip

explain() shows the planned strategy. The Spark UI shows what actually happened, and with AQE they can differ. Use both.

15.1.4Stage-Level Analysis

Spark splits a job into stages at shuffle boundaries, the points where data must be redistributed.

Python
result = (
    sales
    .groupBy("customer_id")
    .sum("sales_amount")
)
Stage 1:  Read sales
             |
          Partial aggregation (per partition)
             |
          Shuffle by customer_id
---------------------------------- boundary
Stage 2:  Final aggregation

Different stages have different bottlenecks: stage 1 may be limited by reading, stage 2 by shuffle, stage 3 by skew. Optimizing the wrong stage wastes time. For each slow stage, inspect input size, shuffle read/write, the task-duration distribution, spill, failed tasks, executor utilization, and GC time.

Diagnosis pattern

200 tasks finish in 30 s but one takes 8 min, and that task read far more data: skew. All tasks slow: more likely insufficient compute, large input, expensive operations, or storage.

15.1.6Shuffle Read and Shuffle Write

A shuffle redistributes data across partitions. It happens in joins, grouping, sorting, windows, deduplication, and repartitioning. To sum sales per customer, all of a customer's rows must meet in one place.

Terms

Shuffle write: data upstream tasks write out for redistribution.

Shuffle read: data downstream tasks fetch from that output.

Why it's expensive

Network transfer, serialization, disk I/O, sorting, extra memory, and spill.

Reduce unnecessary shuffle

  1. Filter early.
  2. Select only needed columns.
  3. Avoid unnecessary repartition().
  4. Use appropriate join strategies (broadcast small tables).
  5. Reduce data before joins where logically valid.
  6. Avoid repeated wide transformations.
  7. Address skew.

A shuffle isn't always bad; many operations need one to be correct. Avoid unnecessary or excessively expensive ones.

15.1.7Executor Utilization

SymptomPossible causes
Low CPU, little task activityWaiting on I/O, too few parallel tasks, dependency bottlenecks
High CPUCPU-heavy transformations, complex expressions, serialization
High memory pressureLarge joins/aggregations, excessive caching, oversized partitions
Many idle executorsToo few runnable tasks, serialized dependencies, overprovisioning

Optimize by checking there are enough tasks for parallelism, looking for stages waiting on dependencies, reviewing partition sizes, avoiding unnecessary caching, and sizing compute to measured needs. More executors don't help if the workload can't use the parallelism.

15.1.8Memory Consumption

Spark uses memory for

Execution (shuffles, sorts, hash aggregations, join hash tables) and storage (cached data).

Pressure causes

Disk spills, heavy garbage collection, slow tasks, executor failures, out-of-memory errors.

If a join's hash table outgrows execution memory, Spark spills to disk or changes strategy, and runtime jumps. Inspect executor memory, storage vs execution memory, spill, GC time, failures, and task input sizes.

Principle

Don't solve every memory problem by adding memory. Filtering, reducing data before joins, and fixing skew often help more.

15.2Join Optimization

The best join strategy depends on each side's size, available statistics, the join condition, data distribution, memory, and whether one side can be broadcast efficiently.

15.2.1Broadcast Joins

A broadcast join copies a small table to every executor, so the large table joins locally without being shuffled. With fact_sales at 100 GB and dim_product at 20 MB, broadcasting the product table avoids shuffling 100 GB.

Python
from pyspark.sql import functions as F

sales = spark.table("retail_dev.perf_lab.fact_sales")
products = spark.table("retail_dev.perf_lab.dim_product")

result = sales.join(F.broadcast(products), on="product_id", how="inner")
Without broadcast:

Fact table  -- Shuffle --+
                         +-- Join
Dimension   -- Shuffle --+
With broadcast:

       Broadcast dimension
        /       |       \
       v        v        v
   Executor  Executor  Executor
       ^        ^        ^
       |        |        |
     Fact partitions (not shuffled)

Use when

  • One side is genuinely small.
  • The join type supports it.
  • It fits comfortably in executor memory.
  • Network and memory costs are acceptable.

Risks of broadcasting too much

  • Memory pressure on driver and executors.
  • Network traffic.
  • Executor failures.
  • Slower execution.
Automatic broadcasts

Spark broadcasts automatically when it estimates a side is below spark.sql.autoBroadcastJoinThreshold (10 MB by default in Apache Spark; Databricks may adjust this and AQE can also convert joins at runtime). In the exercise's tests, all three dimension joins were broadcast automatically with no hints at all. Don't broadcast a table just because it's called a "dimension"; measure its size.

15.2.2Sort-Merge Joins

The default for joining two large datasets on equality. Spark (1) shuffles both sides by join key, (2) sorts each partition, and (3) merges matching keys. With fact_sales at 500 GB and dim_customer at 50 GB, broadcasting isn't sensible, so sort-merge is appropriate.

Advantages

Scales to large datasets; no side needs to fit in memory.

Disadvantages

Shuffle and sort costs; skewed keys create long tasks.

For large joins: filter first, project only needed columns, keep statistics current, address skew, avoid transforming join keys, and inspect the actual plan.

15.2.4Join Hints

Hints tell the optimizer which strategy you prefer. In SQL, they go immediately after SELECT and name the table alias:

SQL
-- Broadcast p
SELECT /*+ BROADCAST(p) */
    f.order_id, p.product_category, f.sales_amount
FROM retail_dev.perf_lab.fact_sales f
JOIN retail_dev.perf_lab.dim_product p
    ON f.product_id = p.product_id;

-- Prefer sort-merge with c
SELECT /*+ MERGE(c) */ f.order_id, c.customer_name
FROM retail_dev.perf_lab.fact_sales f
JOIN retail_dev.perf_lab.dim_customer c ON f.customer_id = c.customer_id;

-- Prefer shuffled hash with c
SELECT /*+ SHUFFLE_HASH(c) */ f.order_id, c.customer_name
FROM retail_dev.perf_lab.fact_sales f
JOIN retail_dev.perf_lab.dim_customer c ON f.customer_id = c.customer_id;
Python equivalents
sales.join(products.hint("broadcast"), "product_id")
sales.join(customers.hint("merge"), "customer_id")
sales.join(customers.hint("shuffle_hash"), "customer_id")
Hints are preferences, not guarantees

Support depends on join type and runtime. Use hints only after inspecting the plan, and re-check the plan afterwards. A broadcast hint on an unexpectedly large table is especially risky, because it can crash executors.

15.2.5Data Skew

Skew is uneven data distribution. If 30 million of 100 million fact rows have customer_id = UNKNOWN, the partition holding that key does far more work than the rest.

Customer IDRecords
C101100
C102200
C103300
UNKNOWN30 million

Effects

199 tasks finish in 20 s; 1 takes 12 min and holds up the stage. Poor parallelism, long stages, high memory, spill, and wasted compute cost.

Spot it in the Spark UI (wide spread of task durations, uneven input or shuffle read, large spill on a few tasks), then confirm with the key distribution:

SQL
SELECT customer_id, COUNT(*) AS record_count
FROM retail_dev.perf_lab.fact_sales
GROUP BY customer_id
ORDER BY record_count DESC
LIMIT 20;

Mitigation options (roughly in order)

  1. Check AQE is enabled; it splits skewed sort-merge join partitions automatically.
  2. Broadcast the other side if it's small, since broadcast joins aren't affected by skew.
  3. Filter out invalid or unneeded records (is UNKNOWN even needed?).
  4. Process the hot key separately and UNION the results.
  5. Salt, only when the semantics allow (next section).

15.2.6Skew Mitigation Using Salting

Salting splits a hot key into several sub-keys (UNKNOWN_0, UNKNOWN_1, …) so its rows spread across partitions. The trick is preserving correct results.

Python · salted aggregation
from pyspark.sql import functions as F

N = 8  # number of salt buckets
fact = spark.table("retail_dev.perf_lab.fact_sales")

salted_totals = (
    fact
    .withColumn("salt", (F.rand() * N).cast("int"))
    # Phase 1: partial sums per (key, salt) spread hot keys
    .groupBy("customer_id", "salt")
    .agg(F.sum("sales_amount").alias("partial_sales"))
    # Phase 2: combine the partials per key
    .groupBy("customer_id")
    .agg(F.sum("partial_sales").alias("total_sales"))
)
Python · salted join (hot key only)
HOT = 0   # customer_id of 'UNKNOWN'
dim = spark.table("retail_dev.perf_lab.dim_customer")

# Fact: random salt for the hot key, 0 for others
fact_s = fact.withColumn("salt",
    F.when(F.col("customer_id") == HOT,
           (F.rand() * N).cast("int"))
     .otherwise(F.lit(0)))

# Dimension: REPLICATE the hot row once per salt
dim_s = dim.withColumn("salt", F.explode(
    F.when(F.col("customer_id") == HOT,
           F.sequence(F.lit(0), F.lit(N - 1)))
     .otherwise(F.array(F.lit(0)))))

joined = fact_s.join(dim_s, ["customer_id", "salt"])
Verified correct

On the 2-million-row generated dataset (30% hot key), both salted versions returned exactly the same results as the unsalted queries: identical totals for all 199,834 customers, and identical join row count (2,000,000) and country totals.

Salting can silently break results

Forget to replicate the hot dimension row for every salt value, and most hot-key fact rows vanish from an inner join. Forget phase 2, and you get several rows per key. Salting is rarely needed on Databricks, because AQE skew handling usually covers it. Use it only after confirming skew is the real bottleneck.

15.2.7Adaptive Query Execution (AQE)

Before running, Spark only estimates intermediate sizes. AQE re-optimizes at each shuffle boundary using actual runtime statistics:

AQE featureWhat it does
Coalesce shuffle partitionsMerges many tiny shuffle partitions into fewer reasonable ones
Switch join strategiesConverts a sort-merge join to a broadcast join if one side turns out small
Skew-join optimizationSplits oversized partitions of a sort-merge join into smaller tasks
Python
spark.conf.get("spark.sql.adaptive.enabled")                    # 'true' by default (Spark 3.2+, Databricks)
spark.conf.get("spark.sql.adaptive.skewJoin.enabled")           # skew handling
spark.conf.get("spark.sql.adaptive.coalescePartitions.enabled") # partition coalescing

AQE plans show as AdaptiveSparkPlan isFinalPlan=false before running. After execution, the Spark UI's SQL tab shows the final plan, which may differ.

Important

AQE is an optimization layer, not a substitute for good modeling, suitable joins, or analysis. On serverless compute it's always on and most Spark configs can't be changed.

15.2.8Handling Large Fact Tables

The best approach is usually to reduce work before expensive operations.

SQL · original
SELECT f.order_id, f.sales_amount, c.customer_name
FROM retail_dev.perf_lab.fact_sales f
JOIN retail_dev.perf_lab.dim_customer c
    ON f.customer_id = c.customer_id
WHERE f.order_date >= DATE '2026-01-01';
SQL · explicit filter-first
WITH filtered_sales AS (
    SELECT order_id, customer_id, sales_amount
    FROM retail_dev.perf_lab.fact_sales
    WHERE order_date >= DATE '2026-01-01'
)
SELECT f.order_id, f.sales_amount, c.customer_name
FROM filtered_sales f
JOIN retail_dev.perf_lab.dim_customer c
    ON f.customer_id = c.customer_id;
Same plan?

Usually yes. Catalyst pushes the filter and prunes columns in both. The rewrite is clearer, not necessarily faster. Compare the physical plans rather than assuming.

Techniques: (1) filter early, (2) select only required columns, (3) broadcast small dimensions and use distributed joins for large ones, (4) improve data skipping with layout and statistics, (5) address skew, (6) avoid unnecessary sorts, global windows, and repeated repartitioning.

15.3Partition Optimization

Three different things called "partitions"

(1) Spark execution partitions: in-memory chunks, one per task. (2) Storage partitions: Hive-style folders such as order_date=2026-10-20/. (3) File organization and clustering: how rows are arranged within files. Related, but not interchangeable.

15.3.1Repartition Versus Coalesce

Python · repartition (shuffle)
df.repartition(200)                  # 200 balanced partitions
df.repartition(200, "customer_id")   # partition by key
Python · coalesce (no full shuffle)
df.coalesce(20)   # merge down to 20 partitions
Featurerepartition()coalesce()
Main purposeRedistribute dataReduce partitions
Full shuffleYesNo (merges existing partitions)
Increase partitionsYesNo
BalanceRebalances evenlyMay keep uneven sizes
CostCan be expensiveUsually cheaper

repartition when you need more parallelism, rebalancing, or a specific key partitioning. coalesce when you need fewer, reasonably balanced partitions without a full redistribution.

Don't coalesce(1) large data

It funnels everything through one task and can even pull upstream work onto a single core. Use it only for genuinely small outputs.

15.3.2Partition Pruning

orders/
  order_date=2026-10-20/
  order_date=2026-10-21/
  order_date=2026-10-22/   &lt;- only this one is read
  order_date=2026-10-23/
SQL
SELECT *
FROM orders
WHERE order_date = DATE '2026-10-22';

When a query filters on a partition column, Spark skips irrelevant folders, reducing files read, bytes scanned, I/O, and runtime. Verify with explain("formatted") (look for PartitionFilters) and the actual "files read" metrics.

Partition pruningData skipping
Skips folders using partition-column filtersSkips files using per-file min/max statistics (15.5.7)

15.3.3Shuffle Partition Settings

Python
spark.conf.get("spark.sql.shuffle.partitions")          # default '200'
spark.conf.set("spark.sql.shuffle.partitions", "400")   # classic compute; or "auto" on Databricks

Too few

Large partitions, long tasks, high memory, spill.

Too many

Task and scheduling overhead, tiny partitions, sometimes tiny output files.

Should you always use 200? No. A fixed value can't suit every workload. With AQE coalescing, a generous value is usually safe because AQE merges small partitions. Databricks also supports "auto" to let the platform choose. Change it only after looking at task metrics.

15.3.4File Partitioning

sales/
  year=2025/
    month=01/
    month=02/
  year=2026/
    month=01/
    month=02/

Benefits

Partition pruning; easy management of date ranges; efficient range processing.

Risks

Too many partitions, small files, uneven sizes, no benefit if the column isn't filtered.

A good partition column is frequently filtered, has manageable cardinality, distributes data reasonably, and matches access patterns. Partitioning a big fact table by date can help; partitioning by a high-cardinality customer_id is almost always a mistake.

Databricks guidance

For Delta tables, Databricks recommends not partitioning tables smaller than about 1 TB, and using liquid clustering (15.5.6) for new tables instead.

15.3.5Small-File Problems

Table size:        100 GB
File count:        100,000
Average file size: ~1 MB  (100 GB / 100,000)

Cost of small files

File listing, metadata processing, task scheduling, query planning, and per-file read overhead all grow with file count.

Common causes: frequent small streaming writes, over-partitioning, very frequent micro-batches, many tiny input files, repeated small incremental updates.

SQL · Delta compaction
-- Compact small files (and recluster, for clustered tables)
OPTIMIZE retail_dev.perf_lab.fact_sales;

-- Check file count and size
DESCRIBE DETAIL retail_dev.perf_lab.fact_sales;   -- numFiles, sizeInBytes

Also consider fewer write partitions, liquid clustering, optimized writes / auto compaction, and predictive optimization, which runs OPTIMIZE automatically on Unity Catalog managed tables.

15.3.6Output File Sizing

Thousands of tiny files slow every later read; a handful of huge files limits read parallelism. For 20 GB of output, 200 files is about 100 MB each, while 20,000 files is about 1 MB each. The former usually suits analytics better.

Python
df.coalesce(20).write.format("delta").saveAsTable("retail_dev.perf_lab.sales_copy")

This reduces write tasks but doesn't guarantee exactly 20 files; partitioned writes, max-records-per-file, and optimized writes all affect file count.

Best practices: avoid one file per tiny group; avoid excessive partition counts; monitor file sizes after repeated incremental writes (DESCRIBE DETAIL); compact with OPTIMIZE; don't force single files without a reason.

15.3.7Partition-Column Selection

ColumnDistinct valuesAs a partition column?
order_date3,650Possibly, for a very large table filtered by date (or by month)
customer_id5 millionNo: millions of tiny folders
country20Maybe, if heavily filtered and data is balanced
product_category100Maybe, depending on query patterns

Decision process

  1. Identify common filters.
  2. Measure the dataset size.
  3. Count distinct values.
  4. Estimate data per partition (aim for at least ~1 GB).
  5. Consider file counts.
  6. Test representative queries.
  7. Compare scan metrics and runtime.

Traditional partitioning isn't always best for modern Delta tables; liquid clustering adapts to several filter columns without fixed folders.

15.4Memory Management

15.4.1Driver Memory

The driver plans queries, schedules tasks, tracks progress, and collects results. Problems come from collect() on large data, huge local objects, very complex plans, too much metadata, and driver-side Python over big data.

Python · ✗ dangerous
rows = spark.table(
    "retail_dev.perf_lab.fact_sales"
).collect()        # every row to the driver
Python · ✓ distributed
summary = (
    spark.table("retail_dev.perf_lab.fact_sales")
    .groupBy("order_date")
    .sum("sales_amount")
)
summary.show(20)   # only 20 rows reach the driver

Keep large-scale processing distributed. Use the driver for coordination and small results.

15.4.2Executor Memory

Executors use memory for joins, sorts, aggregations, shuffles, and cached data. If working memory is exceeded, Spark spills or fails.

Improve memory behavior

  • Read fewer columns; filter early.
  • Avoid oversized partitions.
  • Address skew.
  • Use suitable join strategies.
  • Don't cache what isn't reused.
  • Choose suitable compute.

Before adding memory, check for

  • An oversized partition.
  • A too-large broadcast.
  • Skew.
  • Excessive caching.
  • A huge shuffle.
  • …or a genuine need for more resources.

15.4.3Garbage Collection

The JVM reclaims memory from unused objects. Workloads creating many short-lived objects, or holding many objects, spend time collecting instead of computing.

Symptoms and causes

Symptoms: high GC time, long tasks, memory pressure, variable runtimes.
Causes: large hash tables, object-heavy processing, excessive caching, big joins, oversized partitions.

Strategies

Prefer built-in functions over Python UDFs; avoid unnecessary caching; process less data; right-size partitions; check GC as a share of task time (a rule of thumb: worry above ~10%).

15.4.4Out-of-Memory Errors

WhereTypical causes
DriverLarge collect() / toPandas(), driver-side processing, huge metadata, oversized broadcasts (built on the driver)
ExecutorOversized joins, skewed partitions, excessive caching, large broadcast relations
Python workerLarge Python objects, pandas UDF batches, collecting big partitions into Python

Troubleshooting

  1. Identify which component failed.
  2. Read the error and logs.
  3. Find the stage and task.
  4. Review input sizes and partition distribution.
  5. Check spill and GC.
  6. See whether the query can be reduced or restructured.
  7. Add compute only if genuinely needed.

15.4.5Caching and Persistence

Caching keeps an intermediate result for reuse. It helps when a DataFrame is expensive to compute and reused.

Python
sales = (
    spark.table("retail_dev.perf_lab.fact_sales")
    .filter("order_date >= DATE '2026-01-01'")
    .select("customer_id", "product_id", "sales_amount")
    .cache()               # lazy: nothing stored yet
)

sales.count()              # action materializes the cache

customer_summary = sales.groupBy("customer_id").sum("sales_amount")   # reuses cache
product_summary  = sales.groupBy("product_id").sum("sales_amount")    # reuses cache

sales.unpersist()          # release when done
Python · persist with a storage level
from pyspark import StorageLevel

sales = spark.table("retail_dev.perf_lab.fact_sales").persist(StorageLevel.MEMORY_AND_DISK)

Cache when

  • Reused multiple times.
  • Expensive to compute.
  • Fits in the memory budget.
  • Recomputing is costly.

Don't cache when

  • Used only once.
  • Too large for memory.
  • It causes memory pressure.
  • The source is cheap to reread (Delta + disk cache often is).
Serverless

cache() and persist() aren't supported on serverless compute (as noted in Chapter 6). There, write the reused intermediate result to a temporary table instead, or rely on Databricks' automatic disk cache.

cache() is shorthand for a default storage level; persist() lets you choose one. Measure before and after; never cache every intermediate DataFrame.

15.4.6Avoiding Unnecessary Collection to the Driver

Python · ✗ avoid
data = spark.table("retail_dev.perf_lab.fact_sales").collect()

for row in data:      # single-machine loop
    pass
Python · ✓ prefer
result = (
    spark.table("retail_dev.perf_lab.fact_sales")
    .groupBy("order_date")
    .sum("sales_amount")
)

# Small, deliberate driver results only
sample_rows = (spark.table("retail_dev.perf_lab.fact_sales")
               .limit(10).collect())
Key takeaway

Keep large transformations distributed; collect only small results that driver-side logic genuinely needs. The same goes for toPandas().

15.5Advanced Optimization

15.5.1Photon

Photon is Databricks' native (C++), vectorized query engine. It accelerates supported scans, filters, joins, aggregations, and SQL expressions by processing data in columnar batches instead of row by row. SQL warehouses and serverless compute use it by default; on classic clusters it's a checkbox.

Consider Photon when

  • You run substantial SQL / DataFrame workloads.
  • Operations are Photon-supported.
  • Work is CPU-bound (joins, aggregations, Delta writes).

Considerations

  • Not every operator runs in Photon; Python UDFs and some functions fall back.
  • Gains vary by workload.
  • Photon compute has a different price.

Evaluate it: baseline the runtime, run the same workload on Photon compute, check the plan for Photon… operators (and fallback notes), then compare runtime and cost.

15.5.3Predicate Pushdown

Supported filters are pushed into the scan, so less data is read, transferred, and shuffled. Here's the real plan for the exercise query (local Spark 4, Parquet). Every filter appears in PushedFilters:

explain("formatted") · excerpt
(1) Scan parquet spark_catalog.perf_lab.fact_sales
Output [6]: [customer_id, product_id, order_date, date_key, sales_amount, order_status]
PushedFilters: [IsNotNull(order_date), IsNotNull(order_status),
                GreaterThanOrEqual(order_date,2026-01-01),
                EqualTo(order_status,COMPLETED), IsNotNull(customer_id), ...]
ReadSchema: struct&lt;customer_id:bigint,product_id:bigint,order_date:date,
                   date_key:int,sales_amount:decimal(18,2),order_status:string&gt;

Writing the filter earlier in code doesn't guarantee earlier execution, because the optimizer rearranges anyway. Check the plan and scan metrics. If the table holds five years of data but you need October 2026, pushdown plus pruning or skipping can avoid reading the rest.

15.5.4Column Pruning

Columnar formats (Parquet, Delta) read only the columns a query needs. In the excerpt above, ReadSchema lists just the 6 columns the query uses, not the whole table, and order_id isn't read at all.

SQL · ✗
SELECT *
FROM retail_dev.perf_lab.fact_sales;
SQL · ✓
SELECT order_id, customer_id, order_date, sales_amount
FROM retail_dev.perf_lab.fact_sales;

Benefits: less data scanned, less memory, less I/O, cheaper downstream work. Spark prunes automatically as long as nothing downstream needs the columns, but a final SELECT * or collect() forces it to read them all.

15.5.5Statistics

Statistics (row counts, sizes, column min/max/distinct counts) drive join strategy, join order, and broadcast decisions. If Spark thinks a dimension is 10 MB but it's grown to 5 GB, it may choose badly.

SQL
-- Table-level
ANALYZE TABLE retail_dev.perf_lab.dim_customer COMPUTE STATISTICS;

-- Column-level
ANALYZE TABLE retail_dev.perf_lab.dim_customer COMPUTE STATISTICS FOR COLUMNS customer_id;

-- Everything
ANALYZE TABLE retail_dev.perf_lab.fact_sales COMPUTE STATISTICS FOR ALL COLUMNS;

Best practice: know the table's maintenance strategy (predictive optimization can run ANALYZE automatically on Unity Catalog managed tables), refresh statistics after big changes, and compare estimated vs actual sizes with explain("cost"). Statistics improve choices but don't guarantee a strategy.

15.5.6Liquid Clustering

Liquid clustering (Chapter 9) co-locates rows with similar values of chosen columns in the same files, which improves data skipping without rigid partition folders. You can change the keys later without rewriting the table.

SQL
-- New clustered copy
CREATE TABLE retail_dev.perf_lab.fact_sales_clustered
CLUSTER BY (order_date, customer_id)
AS SELECT * FROM retail_dev.perf_lab.fact_sales;

-- Or cluster an existing table, then reorganize its data
ALTER TABLE retail_dev.perf_lab.fact_sales CLUSTER BY (order_date, customer_id);
OPTIMIZE retail_dev.perf_lab.fact_sales;   -- applies clustering to existing data

-- Let Databricks choose keys from query history (UC managed tables)
ALTER TABLE retail_dev.perf_lab.fact_sales CLUSTER BY AUTO;

Helps

  • Data skipping on clustered columns.
  • Several different filter patterns.
  • Avoiding over-partitioning.
  • Adapting layout as data and keys change.

Choose keys wisely

  • Columns you actually filter on.
  • Up to 4 keys; fewer is better.
  • Not every column.
  • Not rarely filtered high-cardinality columns.

ALTER TABLE … CLUSTER BY only affects new writes until you run OPTIMIZE. Measure files skipped before and after.

15.5.7Data Skipping

Delta records min/max (and null counts) per file for the first 32 columns by default. A file whose order_date range is 2026-01-01 to 2026-01-31 can't contain 2026-10-25, so it's skipped without being opened.

Affected by

File statistics, query filters, data layout and clustering, file sizes, and whether filtered columns have stats.

Improve it

  1. Filter on commonly used columns.
  2. Keep a good layout (cluster / OPTIMIZE).
  3. Put frequently filtered columns among the first 32.
  4. Avoid unnecessary full scans.
  5. Verify files and bytes read in the Query Profile.

Skipping works at file level even on unpartitioned tables. It works best when data is clustered: if every file spans all dates, no file can be skipped.

                 .otherwise(F.concat(F.lit("Customer "), F.col("customer_id"))))

)

# dim_product: 1,000 products in 10 categories
dim_product = (

    .withColumn("product_category", F.concat(F.lit("Category "), F.col("product_id") % 10))
)

# dim_date: 2025-01-01 .. 2026-12-31
dim_date = (
    spark.sql("SELECT explode(sequence(DATE'2025-01-01', DATE'2026-12-31')) AS order_date")
    .withColumn("date_key", F.date_format("order_date", "yyyyMMdd").cast("int"))
    .withColumn("calendar_year", F.year("order_date"))
    .withColumn("calendar_month", F.month("order_date"))
)

# fact_sales: 30% of rows belong to customer 0 -> deliberate skew
fact_sales = (
    spark.range(0, fact_rows).withColumnRenamed("id", "order_id")
    .withColumn("customer_id",
                F.when(F.rand(1) < 0.30, F.lit(0))
                 .otherwise((F.rand(2) * 200_000 + 1).cast("long")))
    .withColumn("product_id", (F.rand(3) * 1_000 + 1).cast("long"))

                F.when(F.rand(6) < 0.85, "COMPLETED").otherwise("CANCELLED"))

The original exercise put the hint after JOIN (JOIN /*+ BROADCAST(p) */ … dim_product p). Spark rejects that with PARSE_SYNTAX_ERROR … near '/*+' (verified on Spark 4). The hint must follow SELECT. With it there, the plan became SortMergeJoin (customer) + BroadcastHashJoin (product) + SortMergeJoin (date), and the 600 result rows were identical to the baseline.

15.8Interview Questions and Answers

Try answering each before revealing the answer.

Q1. Why do Spark jobs become slow?
Excessive shuffles, skew, inefficient joins, large scans, small files, memory pressure, and insufficient or poorly used compute.
Q2. Logical vs physical plan?
The logical plan describes the relational operations (what); the physical plan names the concrete operators Spark will run (how), such as which join algorithm.
Q3. What is a shuffle?
Redistribution of data between partitions (an Exchange in the plan), commonly for joins, aggregations, and sorts. It costs network, disk, and serialization.
Q4. When use a broadcast join?
When one side is small enough to fit comfortably in executor memory and the join type supports it, so the large side isn't shuffled.
Q5. What is a sort-merge join?
A distributed join that shuffles both sides by key, sorts them, and merges matching keys. It's the default for two large equi-joined tables.
Q6. What is data skew?
Uneven distribution where a few keys or partitions hold most of the data, so a few tasks do most of the work.
Q7. How does AQE improve performance?
It re-optimizes at runtime using actual statistics: coalescing shuffle partitions, switching to broadcast joins, and splitting skewed join partitions.
Q8. repartition vs coalesce?
repartition() shuffles to redistribute (can increase or decrease); coalesce() merges partitions without a full shuffle (decrease only).
Q9. What is partition pruning?
Skipping irrelevant storage partitions (folders) when a query filters on partition columns.
Q10. What is data skipping?
Using per-file statistics (e.g. min/max) to skip files that can't match a filter, even on unpartitioned tables.
Q11. What causes executor OOM?
Large joins, oversized or skewed partitions, excessive caching, and large broadcast relations.
Q12. When cache a DataFrame?
When it's expensive to compute and reused several times, and fits without memory pressure (not on serverless).
Q13. What is Photon?
Databricks' native vectorized C++ engine that accelerates supported SQL and DataFrame operations.
Q14. What is liquid clustering?
A Delta layout feature that clusters data by chosen columns to improve data skipping, with keys you can change without rewriting the table.
Q15. How do you prove an optimization worked?
Show identical results (e.g. exceptAll both ways is empty) and better runtime, scan, shuffle, task, and cost metrics under comparable conditions.
Q16. Where does a SQL join hint go?
Immediately after SELECT, naming the table alias: SELECT /*+ BROADCAST(p) */ …. After JOIN it's a syntax error in Spark.
