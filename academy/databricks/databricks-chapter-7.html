Chapter 7 · Lesson 7.1

Introduction to PySpark

7.1.1What is PySpark?

Simple definition

PySpark is the Python API for Apache Spark. It lets you write Python code that Spark executes with its distributed processing engine, across multiple CPU cores or machines.

Imagine 500 million sales records. With pandas you might write:

Python · pandas
import pandas as pd

df = pd.read_csv("sales.csv")

result = (
    df[df["amount"] > 1000]
    .groupby("region")["amount"]
    .sum()
)

print(result)

That works when the data and intermediate results fit in your Python process's memory. With PySpark:

Python · PySpark
from pyspark.sql import functions as F

df = spark.read.csv(
    "/data/sales.csv",
    header=True,
    inferSchema=True
)

result = (
    df.filter(F.col("amount") > 1000)
      .groupBy("region")
      .agg(F.sum("amount").alias("total_sales"))
)

result.show()

Spark can distribute this work across multiple executors, depending on compute resources and the execution plan.

  1. You write Python code.
  2. PySpark builds a Spark execution plan.
  3. The Spark driver coordinates the work.
  4. Spark divides the work into tasks.
  5. Executors process data partitions.
  6. Spark combines the results or writes the output.
Important

PySpark doesn't mean Python itself distributes your code across machines. PySpark talks to Spark's execution engine, which manages the distributed processing.

Common use cases

Processing large CSV, JSON, and Parquet datasets; transforming Delta Lake tables; joining large datasets; cleaning and validating source data; building Bronze → Silver → Gold pipelines; reporting aggregations; streaming; and preparing data for machine learning. A typical Databricks pipeline reads customer data from Azure Data Lake Storage, cleans it with PySpark, and writes Delta tables.

    "city": ["Hyderabad", "Bengaluru", "Chennai"],

PySpark equivalent

    (102, "Bengaluru", 7000),
    (103, "Chennai", 3000)

Both return customers with sales above 4,000. PySpark can distribute the operation when the DataFrame is backed by distributed data and multiple executors are available.

Practical rule

Use pandas for small, local datasets. Use PySpark when you need distributed execution, Databricks integration, or scalable processing.

Schema Management

A schema defines a dataset's structure: column names, data types, nullability, and nested structures. It's essential in production pipelines.

ColumnTypeExample
order_idLong50001
customer_idLong101
order_dateDate2026-10-20
amountDecimal15999.50
order_statusStringCompleted

Without schema management, data can be misread. A monetary amount read as a string makes calculations harder and error-prone.

7.2.1Defining an explicit schema

Python
from pyspark.sql.types import (
    StructType,
    StructField,
    StringType,
    IntegerType,
    LongType,
    DecimalType,
    DateType,
    TimestampType
)

customer_schema = StructType([
    StructField("customer_id", LongType(), False),
    StructField("customer_name", StringType(), True),
    StructField("city", StringType(), True),
    StructField("age", IntegerType(), True)
])

StructType

A schema made up of multiple fields: the whole table structure.

StructField

Defines one column:

StructField("column_name", DataType(), nullable=True)

StructField("customer_id", LongType(), False) defines a long-integer column named customer_id with nullable=False.

Important

nullable=False declares an expectation. It doesn't replace explicit data-quality validation, and it doesn't guarantee every source or transformation will reject nulls.

7.2.2Important PySpark data types

PySpark typePurposeExample
StringTypeText: names, descriptions, codes"Hyderabad"
IntegerType32-bit integer100
LongType64-bit integer, including many identifiers9876543210
DecimalTypeFixed-precision decimal15999.50
DateTypeCalendar date, no time2026-10-25
TimestampTypeDate and time2026-10-25 10:30:00

ArrayTypeCollection of elements["A", "B"]

DecimalType(12, 2)

Up to 12 total digits, 2 after the decimal point, e.g. 1234567890.12. For currency and financial calculations, fixed-precision decimals are generally preferable to floating-point.

TimestampType and time zones

Be deliberate with timestamps from multiple systems. Sources may be UTC, local time, or timezone-free. Don't assume they share an interpretation.

7.2.4Schema inference versus explicit schemas

Schema inference
df = (
    spark.read
    .option("header", True)
    .option("inferSchema", True)
    .csv("/path/to/customers.csv")
)
Explicit schema
df = (
    spark.read
    .option("header", True)
    .schema(customer_schema)
    .csv("/path/to/customers.csv")
)

Inference

Pros: convenient for exploration, less code, good for discovering unfamiliar data.

Cons: extra data inspection, unexpected types, behavior shifts when the source changes, less predictable in production.

Explicit

Pros: expected types are explicit, more predictable, standardizes pipelines, no dependence on inference.

Note

An explicit schema doesn't make malformed input valid. Invalid values may fail conversion, become null under some parsing modes, or be handled per the reader's configured behavior.

SituationRecommended approach
Exploring a new datasetSchema inference can be convenient
Production ingestionPrefer a defined schema
Financial dataUse appropriate decimal precision
Dates and timestampsDefine and validate formats
Nested JSONDefine or carefully inspect the nested schema
Frequently changing sourceCombine schema controls with data-quality checks

Add a column or replace an existing one.

7.3.10union() and unionByName()

Both combine DataFrames vertically.

union(): by position
df1 = spark.createDataFrame(
    [(101, "Ravi")],
    ["customer_id", "customer_name"]

union() aligns by position

combined = df1.unionByName(

Python
inner_df = orders_df.join(
    customers_df,
    on="customer_id",
    how="inner"
)

Returns orders for customers 101 and 102 only. Order 5004 is excluded (customer 104 doesn't exist), and customer 103 is absent (no orders). 7.4.6Multiple-column joins

Sometimes one key isn't enough; for example, product prices that vary by currency. Join on several columns as a composite key:

Python
result_df = order_items_df.join(
    product_prices_df,
    on=["product_id", "currency_code"],
    how="inner"
)

# Explicit condition with aliases
a = order_items_df.alias("a")
b = product_prices_df.alias("b")

result_df = a.join(
    b,
    (
        (F.col("a.product_id") == F.col("b.product_id")) &
        (F.col("a.currency_code") == F.col("b.currency_code"))
    ),
    "left"
)

Illustrative: assumes order_items_df and product_prices_df DataFrames that both have product_id and currency_code columns. Use aliases when column names overlap or the join condition is complex.

7.4.8Conditional aggregations

Duplicate keys are a frequent cause of incorrect aggregations.

Row multiplication

Joining on customer_id gives four rows for customer 101 (each order matches each customer record), so summing the join output gives 6,000 instead of 3,000.

Step 1: Identify duplicate keys

Python
duplicate_customers = (
    customers_df
    .groupBy("customer_id")
    .count()
    .filter(F.col("count") > 1)
)

duplicate_customers.show()

Step 2: Determine the business rule

Don't drop duplicates without investigating. Possible rules: keep the most recently updated record, keep the authoritative source's record, reject conflicting duplicates, or aggregate them if they're legitimately separate events.

Step 3: Deduplicate deterministically

Assuming the customer records carry updated_at and ingestion_timestamp columns:

Python
from pyspark.sql.window import Window

w = Window.partitionBy("customer_id").orderBy(
    F.col("updated_at").desc_nulls_last(),
    F.col("ingestion_timestamp").desc_nulls_last()
)

    customers_df
    .withColumn("row_num", F.row_number().over(w))
    .filter(F.col("row_num") == 1)
    .drop("row_num")
)

Include a reliable tie-breaker in the ordering if records can share timestamps.

7.4.10Null handling

Nulls are missing or unknown values, not zero or an empty string.

Here df stands for any DataFrame with customer_name, city, and age columns.

Python
# Find nulls / non-nulls
df.filter(F.col("customer_name").isNull()).show()
df.filter(F.col("customer_name").isNotNull()).show()

# Replace nulls per column
df_filled = df.fillna({
    "city": "Unknown",
    "age": 0
})

# coalesce(): first non-null expression
df = df.withColumn(
    "display_city",
    F.coalesce(F.col("city"), F.lit("Unknown"))
)
Business meaning first

Only replace nulls in ways that make sense. A missing age replaced with 0 could be mistaken for a real value.

Nulls in joins

In ordinary equality joins, null keys don't match other null keys: rows with null customer_id on both sides won't join. For null-safe equality:

Python
F.col("a.customer_id").eqNullSafe(
    F.col("b.customer_id")
)

Use null-safe joins only when matching two missing keys is logically correct. In most customer and transaction joins, null keys should be investigated, not matched.

7.5.2User-defined functions (UDFs)

A UDF applies custom Python logic to DataFrame values.

Python · UDF version
from pyspark.sql.functions import udf
from pyspark.sql.types import StringType

def categorize_amount(amount):
    if amount is None:
        return "Unknown"
    elif amount >= 10000:
        return "High"
    elif amount >= 5000:
        return "Medium"
    else:
        return "Low"

categorize_udf = udf(categorize_amount, StringType())

df = orders_df.withColumn(
    "amount_category",
    categorize_udf(F.col("amount"))
)
Why UDFs can be slower

Ordinary Python UDFs add serialization and Python execution overhead, and Spark can't optimize their internal logic the way it optimizes built-in expressions.

Python · built-in version (preferred)
df = orders_df.withColumn(
    "amount_category",
    F.when(F.col("amount").isNull(), "Unknown")
     .when(F.col("amount") >= 10000, "High")
     .when(F.col("amount") >= 5000, "Medium")
     .otherwise("Low")
)

Use a UDF when the logic can't reasonably be expressed with built-in functions, you need specialized Python, and you've measured the performance impact and found it acceptable. Pandas UDFs process data in batches and can be faster for some workloads, but test them; they aren't automatically faster.

Important PySpark Performance Practices

1. Prefer built-in functions

F.upper(F.col("customer_name")) beats a Python UDF for simple string conversion.

2. Select only required columns

df.select("customer_id", "customer_name", "city"). Column pruning reduces data processed.

3. Filter early when logically safe

customers_df.filter(F.col("status") == "ACTIVE") reduces downstream work; Spark may push filters to the source.

4. Avoid unnecessary actions

count(), show(), and collect() each trigger computation. Never collect() large datasets.

5. Broadcast small lookups when appropriate

large_df.join(F.broadcast(small_lookup_df), on="product_id", how="left"). Check size, executor memory, and the plan first.

6. Avoid unnecessary repartitioning

df.repartition(8) may add a shuffle. Use it when the benefit justifies the cost.

7. Inspect the execution plan

result_df.explain("formatted") shows scans, exchanges, joins, and other operators.

8. Cache only when reuse justifies it

df.cache() for repeated use; df.unpersist() when done.
