3.1.4Catalog Explorer

Catalog Explorer lets you discover and manage data objects. Unity Catalog organizes data in a three-level namespace: catalog → schema → table. In main.sales.customers, main is the catalog, sales the schema, and customers the table.

main.retail.customers
main.retail.products
main.retail.orders
main.retail.order_items

What you can explore

Depending on permissions and object type: catalog, schema, table and column names, data types, table properties, data previews, permissions, and lineage.

Why is it important?

Given the requirement "Calculate total revenue by customer," you first need to know which catalog and schema hold the data, the table names, which columns identify customers, and which column contains revenue. Catalog Explorer answers these questions. Then you can write:

SQL
SELECT
    customer_id,
    SUM(sales_amount) AS total_revenue
FROM main.retail.sales
GROUP BY customer_id;

Assumes main.retail.sales exists with these columns.

Remember

Catalog Explorer helps you discover data; SQL and notebooks help you work with it.

3.1.5SQL Editor

The SQL editor is an interface for writing and running SQL. It's useful for exploring tables, validating data, aggregations, investigating data quality, analyzing business metrics, and building dashboard queries.

SQL
-- Return up to 10 rows
SELECT *
FROM main.retail.sales
LIMIT 10;

-- Total sales
SELECT
    SUM(sales_amount) AS total_sales
FROM main.retail.sales;

-- Sales by product
SELECT
    product_id,
    SUM(sales_amount) AS total_sales
FROM main.retail.sales
GROUP BY product_id
ORDER BY total_sales DESC;

To run a query you typically need workspace access, permissions on the data, an available SQL execution environment, and valid SQL. You may need to select a SQL warehouse first.

3.1.6Notebooks

A notebook is an interactive environment where you write and run code. Databricks notebooks support Python, SQL, and more, and are used for exploration, ingestion, cleansing, transformation, testing, debugging, and pipeline development. A notebook might contain:

Cell 1 · Markdown
# Customer Data Processing

Objective:
Load customer data and calculate customer counts by city.
Cell 2 · Python
customers = spark.read.table("main.retail.customers")

display(customers)
Cell 3 · SQL
SELECT
    city,
    COUNT(*) AS customer_count
FROM main.retail.customers
GROUP BY city;

These table names are examples. You'll create a sample table in the hands-on exercise later in this chapter.

3.2Notebooks

The most important practical section of this chapter. You'll use notebooks constantly when learning PySpark and building pipelines.

3.2.1Creating Notebooks

  1. Open your Databricks workspace.
  2. Navigate to the workspace or notebook creation menu.
  3. Select the option to create a notebook.
  4. Enter a name, such as Chapter_03_First_Notebook.
  5. Select Python as the default language.
  6. Select the available compute if the interface requires it.
  7. Create the notebook.

Create a notebook named Chapter_03_First_Notebook and use it for all the exercises in this chapter. Menu labels may differ in your workspace.

3.2.2Running Notebook Commands

A notebook contains cells, each holding code or documentation. Run a cell with the notebook's Run control.

Python
print("Welcome to Databricks")
Welcome to Databricks

Running multiple cells

Cell 1
a = 10
b = 20
Cell 2
print(a + b)
# Output: 30
Execution order matters

The second cell uses variables from the first. If you change or rerun earlier cells, rerun later cells too so their results reflect the latest code.

3.2.3SQL Cells

A SQL cell runs SQL directly in a notebook.

SQL
SELECT 10 + 20 AS result;   -- result: 30

SELECT *
FROM main.default.sales_demo;

The second query works after you create the sample table (Chapter 2's exercise), assuming the catalog and schema exist and you have permission.

3.2.4Python Cells

Python cells run Python code, and in Databricks you can use Python with PySpark to process distributed datasets.

Ordinary Python
Python
numbers = [10, 20, 30, 40, 50]

total = sum(numbers)

print(total)
# Output: 150
PySpark
Python
df = spark.range(1, 6)

display(df)
# id: 1, 2, 3, 4, 5

spark.range() creates a Spark DataFrame containing a sequence of numbers.

Remember

Ordinary Python processes local Python objects, while PySpark lets you work with distributed Spark DataFrames.

3.2.5Markdown Cells

Markdown cells document your work; they don't run data-processing logic.

Markdown
# Customer Data Pipeline

## Objective
Load customer data and remove duplicates.

## Steps
1. Read the source table.
2. Validate the customer ID.
3. Remove duplicate records.
4. Write the cleaned data.

Use Markdown to document business requirements, transformation logic, data source details, expected results, known limitations, and troubleshooting instructions. Well-documented notebooks are easier to maintain and hand over.

3.2.6Magic Commands

Magic commands are special notebook commands that change how a cell is interpreted or executed. Common ones:

CommandWhat it does
%pythonRun the cell as Python
%sqlRun the cell as SQL
%mdRender the cell as Markdown documentation
%runRun another notebook and import its definitions
%shRun shell commands, where supported
Important distinction

A magic command is not an ordinary Python function. In a cell starting with %sql, the directive tells the notebook to interpret the whole cell as SQL.

3.2.7The %sql Magic Command

SQL
%sql
SELECT
    100 + 200 AS total;   -- total: 300

You can also create a temporary view and query it:

SQL
%sql
CREATE OR REPLACE TEMP VIEW sample_customers AS
SELECT *
FROM VALUES
    (101, 'Ravi', 'Hyderabad'),
    (102, 'Kumar', 'Chennai'),
    (103, 'Suresh', 'Bengaluru')
AS customers(customer_id, customer_name, city);
SQL
%sql
SELECT *
FROM sample_customers;
Note

A temporary view is session-scoped. Don't treat it as a permanent table.

3.2.8The %python Magic Command

Python
%python

name = "Databricks"

print(f"Welcome to {name}")
# Output: Welcome to Databricks

If the notebook's default language is already Python, you usually don't need %python.

Mixing Python and SQL

Python cell
sales_df = spark.read.table("main.default.sales_demo")
display(sales_df)
SQL cell
%sql
SELECT *
FROM main.default.sales_demo;

Use SQL for relational operations and Python for programmatic transformations, in the same notebook.

3.2.9The %md Magic Command

Markdown
%md

# Sales Data Analysis

## Objective
Calculate total sales by product.

## Validation
Verify the totals against the source data.

The notebook renders this as formatted documentation. You can use headings, lists, tables, and links.

3.2.10The %run Magic Command

%run executes another notebook and makes its definitions available in the calling notebook, which is useful for reusing code.

Workspace
│
├── Common_Functions
└── Main_Pipeline
Common_Functions
def calculate_total(a, b):
    return a + b
Main_Pipeline
%run ./Common_Functions
Main_Pipeline
print(calculate_total(100, 200))
# Output: 300

The relative path must match your actual notebook organization.

When to use it: shared functions, common initialization, reusable transformation logic, and learning or small projects. For larger production projects, also learn Python modules, packages, Git, and Databricks Asset Bundles.

3.2.11Notebook Parameters

Parameters let you reuse a notebook with different inputs. Instead of hardcoding a processing date, pass it in:

Python
dbutils.widgets.text(
    "process_date",
    "2026-10-25",
    "Process Date"
)

process_date = dbutils.widgets.get("process_date")

print(f"Processing sales for {process_date}")

This creates a text widget with a default date and reads its value, which you can then use in a query or transformation:

Python
from pyspark.sql import functions as F

sales_df = spark.read.table("main.default.sales_demo")

filtered_df = sales_df.filter(
    F.col("sale_id") > 0
)

display(filtered_df)

This example doesn't actually filter by process_date because the sample table has no date column. In a real sales table you would use the parameter to filter the right records.

Common parameters: processing date, source table, target table, business unit, environment, and batch identifier.

Security

Avoid concatenating untrusted parameter values directly into SQL strings. Validate inputs and use safe parameter handling.

3.2.12Widgets and Parameterization

Widgets provide notebook inputs. Common types are text, dropdown, combobox, and multiselect; availability and exact APIs may vary.

Python · dropdown
dbutils.widgets.dropdown(
    "environment",
    "dev",
    ["dev", "test", "prod"],
    "Environment"
)

environment = dbutils.widgets.get("environment")

print(environment)   # dev (default selection)
Python · select a table
dbutils.widgets.dropdown(
    "source_table",
    "sales_demo",
    ["sales_demo"],
    "Source Table"
)

source_table = dbutils.widgets.get("source_table")

print(source_table)

For a real multi-table workflow, include only approved table names and validate the selection before using it.

Why widgets help: instead of a separate notebook for every business unit, you reuse one notebook with different validated inputs.

3.2.13Notebook Scheduling

You schedule a notebook through a Databricks Job, for example to run a sales-processing notebook every day at 2:00 AM.

  1. Open the notebook.
  2. Find the scheduling or job-creation option.
  3. Create a new job or add the notebook to an existing one.
  4. Select the appropriate compute.
  5. Configure the schedule.
  6. Configure parameters if needed.
  7. Configure retries and notifications.
  8. Save the configuration.
  9. Run a test execution.
  10. Review the job's run history.

      v

Before scheduling, ensure

  • It runs without manually created state.
  • It uses appropriate permissions.

  • Monitoring and notifications are set up.
Important

Scheduling a notebook does not automatically make it production-ready.

3.3.4Creating Tables

A DataFrame is a logical representation of data and its transformations, not a persistent table. To make the data available through SQL, save it as a table.

Step 1: Save the DataFrame

Python
(
    customers_df.write
    .format("delta")
    .mode("overwrite")
    .saveAsTable("main.default.customers_demo")
)

Assumes the main catalog and default schema exist, you have privileges, and your compute supports the operation. Otherwise replace main.default with a suitable location.

Step 2: Read the table

Python
saved_customers_df = spark.read.table(
    "main.default.customers_demo"
)

display(saved_customers_df)

Step 3: Query it with SQL

SQL
SELECT *
FROM main.default.customers_demo;

3.3.6Saving Notebook Work

Your notebook code and the data it produces are different things.

Saving a notebook

Preserves the notebook content: code cells and documentation.

Saving a table

Persists data in the configured storage and registers the table, for example with saveAsTable.

Best practices

  • Give notebooks descriptive names.
  • Add Markdown documentation.
  • Organize code into logical cells.
  • Use Git for version control where appropriate.
  • Separate development and production environments.
  • Store credentials securely.
  • Don't rely on variables that exist only because you ran earlier cells manually.

3.3.7Exporting Notebooks

Databricks can export notebooks as source code, Databricks archive (.dbc), or other formats the interface offers. Exporting helps you back up exercises, share examples, store code outside the workspace, review changes, and move notebook content between environments.

For ongoing team development, Git integration and controlled deployment are usually better than manually exporting notebooks for every change.

A useful troubleshooting method

  1. Read the complete error message.
  2. Identify whether it's about code, compute, storage, permissions, or networking.
  3. Reproduce the issue with a smaller example.
  4. Check the relevant execution details.
  5. Correct the underlying problem.
  6. Rerun the operation.
  7. Verify that the output is correct.
Careful

Avoid repeatedly rerunning a failed production operation without understanding whether it is safe to retry.

3.4Hands-on Exercise: Build Your First Databricks Data Pipeline

Combine everything you've learned into a small customer pipeline: a simplified version of the Medallion Architecture from Chapter 1.

The pipeline will

  • Create sample data.
  • Remove duplicate customers.
  • Save raw data in a Bronze table.
  • Save cleaned data in a Silver table.
  • Execute SQL queries.
  • Create a Gold summary table.
  • Validate the results.

Before you start

  • A Databricks workspace.
  • A notebook.
  • An available Python/Spark environment.
  • Permission to create tables in a catalog and schema.

Examples use main.default; replace it if needed.

Step 1: Create the sample data

Python
customers = [
    (101, "Ravi", "Hyderabad", 35000),
    (102, "Kumar", "Chennai", 42000),
    (103, "Suresh", "Bengaluru", 28000),
    (104, "Anita", "Hyderabad", 50000),
    (105, "Priya", "Chennai", 45000),
    (102, "Kumar", "Chennai", 42000)
]

columns = [
    "customer_id",
    "customer_name",
    "city",
    "monthly_income"
]

customers_df = spark.createDataFrame(
    customers,
    columns
)

display(customers_df)
Notice

Customer ID 102 appears twice. This duplicate was added deliberately so you can practice data cleansing.

Step 2: Create the Bronze table

The Bronze layer stores the source data before cleansing.

Python
(
    customers_df.write
    .format("delta")
    .mode("overwrite")
    .saveAsTable("main.default.bronze_customers")
)

Step 3: Create the Silver table

Remove exact duplicate records.

Python
bronze_df = spark.read.table(
    "main.default.bronze_customers"
)

silver_df = bronze_df.dropDuplicates()

(
    silver_df.write
    .format("delta")
    .mode("overwrite")
    .saveAsTable("main.default.silver_customers")
)
Important

dropDuplicates() without a subset removes rows identical across all columns. If records with the same customer ID have different values, you need an explicit business rule to decide which record to keep.

Step 4: Validate the record counts

Python
bronze_count = spark.read.table(
    "main.default.bronze_customers"
).count()

silver_count = spark.read.table(
    "main.default.silver_customers"
).count()

print(f"Bronze record count: {bronze_count}")
print(f"Silver record count: {silver_count}")
Bronze record count: 6
Silver record count: 5

This confirms that one exact duplicate record was removed.

Step 5: Query the Silver table using SQL

SQL
SELECT *
FROM main.default.silver_customers;

You should see five records.

Step 6: Create the Gold summary table

The Gold layer holds business-ready data. Calculate customer count and average income by city:

SQL
CREATE OR REPLACE TABLE main.default.gold_customer_summary
USING DELTA
AS
SELECT
    city,
    COUNT(*) AS customer_count,
    ROUND(AVG(monthly_income), 2) AS average_income
FROM main.default.silver_customers
GROUP BY city;

ORDER BY city;
