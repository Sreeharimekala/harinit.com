SQL · "Which categories earn most in each customer city?"
SELECT c.city, p.category, SUM(f.sales_amount) AS total_sales
FROM gold.fact_sales AS f
JOIN gold.dim_customer AS c ON f.customer_key = c.customer_key
JOIN gold.dim_product  AS p ON f.product_key  = p.product_key
GROUP BY c.city, p.category
ORDER BY total_sales DESC;

Advantages: easy to understand, few joins, great for SQL and BI semantic models, consistent reporting across measures. The strong default for analytical warehouses.

A data mart

A curated analytical dataset for one domain or team. The sales mart exposes revenue, product performance, segments, and regions; the finance mart exposes recognized revenue, expenses, profitability, and periods.

In a lakehouse, curated Gold tables serve as marts. Share conformed definitions so marts don't compute the same metric differently.

Important distinction

17.2Dimensional Modeling

Understand the business process and decide what one fact row represents before creating tables.

17.2.1Business Keys

A business key is an identifier from a source system or defined by the business: customer_id, product_id, order_id, store_id, invoice_number. It identifies an entity within its scope, is often meaningful to users, may change, and may not be unique across systems.

Sourcecustomer_idCustomer
CRM1001Ravi
E-commerce1001Priya

Collision!

Same ID, different people. Use a composite key: source_system + customer_id → CRM|1001, ECOM|1001.

This prevents collisions but doesn't match customers across systems; that needs identity-resolution rules.

17.2.2Surrogate Keys

A surrogate key is a warehouse-generated identifier for a dimension row (e.g. customer_key = 10001 for business key C1001).

Why use them?

  1. Business keys may change.
  2. Different sources may reuse IDs.
  3. SCD Type 2 needs several rows per entity.
  4. Facts must point to the correct historical row.
  5. They decouple warehouse joins from source IDs.
Business keySurrogate key
OriginSource / businessWarehouse
IdentifiesAn entityA warehouse row
Changes?May changeStable for its row
In SCD2Same across versionsDifferent per version
ExampleC100110001, 10025
SQL · recommended on Databricks: identity columns
CREATE TABLE gold.dim_customer (
    customer_key BIGINT GENERATED ALWAYS AS IDENTITY,   -- assigned by Delta on insert
    customer_id  STRING,
    customer_name STRING
    -- ...
);

-- Inserts simply omit the key column:
INSERT INTO gold.dim_customer (customer_id, customer_name) VALUES ('C1001', 'Ravi');
Avoid for persistent keys

F.monotonically_increasing_id() is unique per run but not consecutive or repeatable across reruns. MAX(key) + ROW_NUMBER() breaks with concurrent writers. Never regenerate all keys on reload; that breaks every fact reference.

Identity columns

Delta assigns unique, increasing values (gaps are possible), keeps existing keys on updates, and serializes writes to the table, so concurrent loads can't produce duplicate keys. The project uses them.

17.2.3Fact Table Grain

The grain defines what one fact row represents. It's the most important modeling decision.

Grain: one row per order line

Grain: one row per date, store, product
datestoreproductqtyamount
202610251101101000
20261025110252500
2026102521018800

To define grain, ask

  1. What business event is measured?
  2. What uniquely identifies a row?
  3. Can one order have several rows?
  4. Transaction-level or aggregated measures?
  5. Which dimensions will analysts filter by?
Rule

Define the grain before choosing columns. An unclear grain leads to duplicated measures. Joining order-line facts to an order-level table without controlling cardinality multiplies values.

17.2.5Conformed Dimensions

                dim_date
                   |
     +-------------+-------------+
     |             |             |
     v             v             v

A conformed dimension is shared consistently by several fact tables or marts. Without one, teams define fiscal year, segment, category, region, or channel differently, and their reports disagree. Sales and returns must share one product-category definition to be compared.

17.2.6Degenerate Dimensions

A business identifier stored directly in the fact table with no dimension table of its own: order number, invoice number, transaction reference, ticket number.

SQL
-- order_number lives in fact_sales; no dim_order needed
SELECT order_number, SUM(sales_amount) AS order_total
FROM gold.fact_sales
GROUP BY order_number;

Create a separate order dimension only if orders have substantial descriptive attributes of their own.

17.2.7Role-Playing Dimensions

One dimension used in several roles. An order has an order date, ship date, and delivery date, all referencing the same dim_date:

SQL · same table, joined twice with different aliases
SELECT
    order_date.full_date AS order_date,
    ship_date.full_date  AS shipment_date,
    f.sales_amount
FROM gold.fact_sales AS f
LEFT JOIN gold.dim_date AS order_date ON f.order_date_key = order_date.date_key
LEFT JOIN gold.dim_date AS ship_date  ON f.ship_date_key  = ship_date.date_key;

17.3Slowly Changing Dimensions

17.3.1What Is an SCD?

Dimension attributes change: address, city, phone, segment, account status. An SCD policy decides whether to keep the old value or overwrite it. If a customer moves from Hyderabad (2025-01-01) to Chennai (2026-06-01), keeping both rows lets you report historical sales by the city at the time; overwriting loses that context.

17.3.2SCD Types 0, 1, and 2

Type 0: keep the original

Never update. For attributes the business defines as immutable: original registration date, acquisition channel, onboarding date.

Don't use Type 0 just because updating is inconvenient.

Type 1: overwrite

Replace the value; history is lost.

BeforeC1001 · Ravi · Hyderabad
AfterC1001 · Ravi Kumar · Chennai

For spelling corrections, fixing bad values, non-historical attributes.

SQL · Type 1
MERGE INTO gold.dim_customer AS target
USING silver.customer_latest AS source
ON target.customer_id = source.customer_id
WHEN MATCHED THEN UPDATE SET
    target.customer_name = source.customer_name,
    target.city = source.city
WHEN NOT MATCHED THEN INSERT (customer_id, customer_name, city)
    VALUES (source.customer_id, source.customer_name, source.city);

Type 2: keep history with a new row

The old row is closed (end date set, flag false) and a new row with a new surrogate key is inserted.

ColumnPurpose

Type 2 rules

  1. Business key is the same across versions.
  2. Each version gets a new surrogate key.
  3. A change closes the previous version.
  4. A new version is inserted.
  5. Exactly one current row per business key.
  6. Facts reference the version valid at the time.

Half-open intervals: treat validity as effective_from <= t < effective_to, so [2025-01-01, 2026-06-01) and [2026-06-01, 9999-12-31) never both contain the same instant. The far-future end date is a convention; some designs use NULL.

One dimension can mix types per column, e.g. original_registration_date Type 0, email_address Type 1, city and customer_segment Type 2. Define tracked columns explicitly.

Critical principle

Type 2 history alone doesn't guarantee correct historical reports. Each fact must reference the version valid when it happened. Join every fact to the current row and all history is attributed to Chennai.

17.3.5Late-Arriving Dimensions

An order for customer C1005 arrives before C1005 is in dim_customer. Options:

ApproachHowTrade-off
Delay the factHold it until the dimension row arrivesFine for short delays
Inferred memberInsert placeholder C1005 · Unknown · is_inferred = true; fill in attributes when the real record arrivesKeeps the link to the right customer. Often the best choice
Unknown memberPoint the fact at a generic "Unknown" row (e.g. key −1)Keeps integrity but loses the customer link until reprocessed

Define the behavior explicitly, or one customer can end up as several unrelated dimension members.

17.3.6Change Detection

Python · compare columns (null-safe)
from pyspark.sql import functions as F

changes = (
    source_df.alias("s")
    .join(target_df.alias("t"), "customer_id")
    .filter(
        ~F.col("s.city").eqNullSafe(F.col("t.city"))
        | ~F.col("s.customer_segment").eqNullSafe(F.col("t.customer_segment"))
    )
)
# NULL vs NULL -> equal; NULL vs value -> different
Python · hash of tracked attributes
source_hashed = source_df.withColumn(
    "attribute_hash",
    F.sha2(
        F.to_json(F.struct("customer_name", "city", "customer_segment")),
        256,
    ),
)

Hashing considerations

  • Hash only attributes that should trigger a new version.
  • Normalize first if rules require it (trim, case).
  • Handle nulls consistently.
  • Keep a stable column order.
  • Never include load timestamps or other always-changing fields.

A hash detects change; it doesn't define your SCD rules.

17.4Incremental Warehouse Loading

17.4.1What Is Incremental Loading?

Full load:
  Read ALL source records
         |
  Transform all
         |
  Reload the target

Incremental load:
  Read NEW + CHANGED records
         |
  Classify inserts / updates / deletes
         |
  Transform changes
         |
  MERGE into the target

Why, and how to detect changes

Less time, compute, and source load; supports frequent refreshes; scales.

Change sources: modification timestamps, increasing sequence IDs, CDC, Delta Change Data Feed, source change tables, file-arrival tracking, application events. Each has different reliability.

17.4.2Incremental Fact Loading

500 million historical lines, 100,000 new today: process the 100,000.

SQL · watermark extraction
SELECT *
FROM source.sales
WHERE modified_at > :last_successful_watermark;

Safer approaches

  • Composite watermark (modified_at, source_id).
  • CDC where available.
  • Overlap window + dedup/MERGE.
  • Advance the watermark only after the load commits.
  • Record batch IDs and load metadata.
pipeline_namelast_successful_watermarklast_success_time
sales_fact_load2026-10-24 23:59:592026-10-25 00:10:00

Update the control table only after the data is safely committed.

17.4.4MERGE INTO

SQL · Type 1 product merge, updating only real changes
MERGE INTO gold.dim_product AS target
USING silver.product_updates AS source
ON target.product_id = source.product_id
WHEN MATCHED AND (
       NOT (target.product_name <=> source.product_name)
    OR NOT (target.category     <=> source.category)
) THEN UPDATE SET
    target.product_name = source.product_name,
    target.category     = source.category,
    target.updated_at   = current_timestamp()
WHEN NOT MATCHED THEN INSERT (product_id, product_name, category, updated_at)
    VALUES (source.product_id, source.product_name, source.category, current_timestamp());

I added the WHEN MATCHED AND … condition so unchanged rows aren't rewritten. <=> is null-safe equality.

MERGE requirements

  1. Deduplicate the source by the merge key.
  2. The match condition reflects the business logic.
  3. Several source rows matching one target row → error.
  4. Handle nulls intentionally.
  5. Test retries.
  6. Validate insert and update counts (returned by MERGE).
Not a multi-table transaction

A MERGE is atomic for one table. Updating a dimension, inserting facts, and updating a control table are separate commits. Coordinate them with orchestration and load-control logic (Chapter 14).

-- Row-level changes since table version 5

FROM table_changes('silver.customers', 5);
-- _change_type: insert, update_preimage, update_postimage, delete

CDF captures changes to a Delta table; source-system CDC captures changes in an operational database. Different things. CDF must be enabled before the changes happen and is subject to retention.

17.4.6Handling Deleted Source Records

If C1002 is deleted at the source, an incremental "changed rows" query simply never mentions it. You need an explicit strategy:

Detection strategies

  1. CDC delete events.
  2. Soft deletes at the source (is_deleted = true).
  3. Full snapshot comparison: anti-join warehouse keys against a complete snapshot (expensive; beware incomplete snapshots).
  4. Tombstones: explicit deletion markers.
TableCommon approach
Current-state dimensionSoft or controlled delete
SCD Type 2 dimensionKeep history; close the current version (and flag deleted)
Transaction factUsually keep; record reversals
Snapshot factPer snapshot semantics

A source delete doesn't always mean a warehouse delete. Financial audit often requires keeping the original transaction and adding a reversal.

17.4.7Referential Integrity Checks

Delta doesn't enforce foreign keys (Unity Catalog PRIMARY KEY/FOREIGN KEY constraints are informational), so check them yourself:

SQL
-- Orphaned fact references
SELECT f.customer_key, COUNT(*) AS orphan_count
FROM gold.fact_sales AS f
LEFT ANTI JOIN gold.dim_customer AS d ON f.customer_key = d.customer_key
GROUP BY f.customer_key;

-- More than one current version per customer (expect no rows)
SELECT customer_id, COUNT(*) AS current_record_count
FROM gold.dim_customer
WHERE is_current = true
GROUP BY customer_id
HAVING COUNT(*) > 1;

-- Overlapping adjacent SCD periods (expect no rows)
WITH customer_versions AS (
    SELECT customer_id, effective_from, effective_to,
           LEAD(effective_from) OVER (PARTITION BY customer_id
                                      ORDER BY effective_from) AS next_effective_from
    FROM gold.dim_customer
)
SELECT *
FROM customer_versions
WHERE next_effective_from IS NOT NULL
  AND effective_to > next_effective_from;

Also check for gaps (effective_to < next_effective_from), duplicate start dates, and effective_from >= effective_to. On failure: quarantine, assign unknown/inferred keys, delay, alert, or fail the load. Never ignore it.

JOIN gold.dim_product AS p ON f.product_key = p.product_key
GROUP BY p.category;

Checklist: no SELECT *; filter early; join only needed dimensions; good layout (compaction, statistics, data skipping, liquid clustering; partition only when justified); avoid needless casts and nested expressions; read the plan; check actual metrics in the Query Profile. See Chapter 15.

Steps 7–8: Detect new and changed customers

Hash the tracked attributes (name, email, city, segment) and compare with each customer's current version. The result is saved as a table, a fixed snapshot, because Step 9 modifies dim_customer and a view would be re-evaluated against the changed table.

SQL
CREATE OR REPLACE TABLE retail_dev.retail_gold.customer_changes AS
WITH source_hashed AS (
    SELECT
        *,
        SHA2(TO_JSON(NAMED_STRUCT(
            'customer_name', customer_name,
            'email', email,
            'city', city,
            'customer_segment', customer_segment
        )), 256) AS attribute_hash
    FROM retail_dev.retail_gold.customer_stage
)
SELECT
    s.*,
    t.customer_key IS NULL AS is_new_customer       -- no current version yet
FROM source_hashed AS s
LEFT JOIN retail_dev.retail_gold.dim_customer AS t
    ON s.customer_id = t.customer_id
   AND t.is_current = true
WHERE t.customer_id IS NULL                          -- new customer
   OR NOT (s.attribute_hash <=> t.attribute_hash);   -- tracked attribute changed

SELECT customer_id, city, is_new_customer FROM retail_dev.retail_gold.customer_changes;

First run: all 3 customers, is_new_customer = true. Staging must hold at most one record per customer; resolve multiple versions first.

Step 9: Apply SCD Type 2

SQL · A. close the current version of changed customers
MERGE INTO retail_dev.retail_gold.dim_customer AS target
USING retail_dev.retail_gold.customer_changes AS source
ON  target.customer_id = source.customer_id
AND target.is_current = true
WHEN MATCHED THEN UPDATE SET
    target.effective_to = source.source_updated_at,
    target.is_current   = false,
    target.updated_at   = current_timestamp();
SQL · B. insert the new versions (key assigned automatically)

    customer_id, customer_name, email, city, customer_segment,
    effective_from, effective_to, is_current, attribute_hash, created_at, updated_at
)
SELECT
    customer_id, customer_name, email, city, customer_segment,
    CASE WHEN is_new_customer
         THEN TIMESTAMP '1900-01-01 00:00:00'   -- first version: valid for all history
         ELSE source_updated_at                 -- later version: valid from the change
    END,
    TIMESTAMP '9999-12-31 00:00:00',
    true,
    attribute_hash,
    current_timestamp(),
    current_timestamp()
FROM retail_dev.retail_gold.customer_changes;

17.7Production Design Considerations

1. Idempotency

Rerunning the same input must not add effects. Use stable business keys, deduplicated staging, MERGE, batch IDs, load-control tables, retry-safe key assignment (identity columns), and reconciliation.

2. Late-arriving facts

Delay, inferred members, unknown keys with reprocessing, or a controlled resolution step. Pick one and apply it consistently.

3. Historical corrections

A correction effective three months ago needs more than close-and-insert: find the affected version, split or adjust periods, insert the corrected version, check overlaps and gaps, reassign affected facts, reconcile.

4. Concurrency

Two jobs on one dimension can duplicate keys, close the same version twice, or create two current rows. Give each dimension one owning job, use safe key generation, and orchestrate.

5. Auditability: track per load

Pipeline name, batch ID, source watermark, start/end time, records processed, inserts/updates/deletes, rejects, reconciliation status, failure details.

17.8Interview Questions and Answers

Try answering each before revealing the answer.

Q1. OLTP vs OLAP?
OLTP runs operational transactions (many small writes); OLAP serves analytical queries (large reads, joins, aggregations).
Q2. What is a star schema?
A central fact table joined directly to denormalized dimension tables.
Q3. What is a snowflake schema?
A dimensional model where some dimensions are normalized into further related tables (e.g. product → category → department).
Q4. What is a fact table?
A table recording business events or measurements at a defined grain, with dimension keys and numeric measures.
Q5. What is a dimension table?
A table of descriptive attributes used to filter, group, and interpret facts.
Q6. What is fact-table grain?
The precise definition of what one fact row represents, e.g. one order line.
Q7. What is a business key?
An identifier from a source system or the business, e.g. customer_id.
Q8. What is a surrogate key?
A warehouse-generated identifier for a dimension row or version, e.g. an identity column.
Q9. Why are surrogate keys needed for SCD Type 2?
Each historical version needs its own key so facts can reference the exact version valid when they occurred.
Q10. Conformed dimension?
A dimension shared consistently across fact tables or marts, e.g. one dim_date for sales, returns, and inventory.
Q11. Degenerate dimension?
A business identifier kept in the fact table without its own dimension table, e.g. order number.
Q12. Role-playing dimension?
One dimension used in several roles, e.g. dim_date as order date, ship date, and delivery date via aliases.
Q13. SCD Type 1?
Overwrites the attribute; history is lost.
Q14. SCD Type 2?
Closes the current row and inserts a new version when a tracked attribute changes, preserving history.
Q15. Business vs surrogate key in Type 2?
The business key is the same across versions; each version has a different surrogate key.
Q16. Why effective dates?
They define when each version is valid, enabling point-in-time lookups and correct historical attribution.
Q17. Late-arriving dimension?
A fact arrives before its dimension record; handle with delay, inferred member, or unknown member.
Q18. Change detection?
Determining whether tracked attributes differ from the current version, via null-safe comparisons or a hash.
Q19. Incremental loading?
Processing only new or changed records instead of reloading everything.
Q20. CDC?
Capturing source inserts, updates, and deletes so they can be applied downstream incrementally.
Q21. MERGE INTO is used for?
Matching source to target rows to apply inserts, updates, and deletes in one atomic operation per table.
Q22. Handling deleted source records?
CDC delete events, soft-delete flags, tombstones, or snapshot comparison, often as a soft delete or reversal rather than a physical delete.
Q23. Referential integrity?
Every fact key references a valid dimension row (or an approved unknown/inferred member). Delta doesn't enforce it, so check with anti-joins.
Q24. Data reconciliation?
Comparing source and target counts, measures, and keys at the right grain to prove completeness and accuracy.
Q25. Materialized view?
A view whose results are stored and refreshed, speeding up repeated expensive queries at the cost of storage and refresh.
Q26. How does Power BI connect to Databricks?
Via the Azure Databricks connector using a SQL warehouse's hostname and HTTP path with approved authentication.
Q27. Why can SCD Type 2 still give wrong historical reports?
If facts are joined to the current version instead of the version valid at transaction time, or if first versions start too late so lookups fail (exactly the bug fixed in this project).
Q28. View vs materialized view?
A view stores the query and recomputes on read; a materialized view stores maintained results.
Q29. Why must loads be idempotent?
Retries and reruns are routine; idempotency stops them from duplicating or corrupting data.
Q30. Biggest risk in an SCD Type 2 implementation?
Wrong change detection, key assignment, effective-date boundaries, or fact-to-version resolution. These corrupt history silently while the pipeline "succeeds".
