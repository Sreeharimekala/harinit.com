Data Quality, Testing, and Reconciliation

Prove your data is right, not just that your job finished. The six dimensions of data quality; reusable validation for counts, keys, nulls, types, and business rules; source-to-target reconciliation; unit, integration, and regression tests for PySpark; idempotent, retry-safe pipelines; and audit, error, and reject tables with alerts. 18.1Data Quality Fundamentals

18.1.1What Is Data Quality?

Data quality is how well data meets the requirements of its intended use. A pipeline can succeed technically and still produce wrong results: 100,000 source rows but 98,000 in the target; a null customer ID; a forbidden negative amount; an order loaded twice; a misread date; a report showing yesterday's data.

          Source data
               |
      Data quality checks
          /         \
         v           v
    Valid data    Invalid data
         |           |
         v           v
  Target tables   Reject tables
         |
  Reconciliation
         |
  Audit and alerts
The goal

Not just to detect errors, but to control what happens when they're found: route bad rows aside, stop publication, and tell someone.

18.1.2Completeness

Is the expected data present? If the source holds 1,000 sales but the target 950, 50 may be missing. Checks: source vs target counts, missing business keys, required columns, files, dates or partitions, expected transactions.

SQL
SELECT
    (SELECT COUNT(*) FROM silver.sales_source) AS source_count,
    (SELECT COUNT(*) FROM gold.fact_sales)     AS target_count;
Python
source_count = source_df.count()
target_count = target_df.count()

if source_count != target_count:
    print("Completeness validation failed")
Equal counts don't prove completeness

One missing row plus one duplicated row gives the same count. The project demonstrates exactly this: the count check passes while the key checks fail. Always compare keys and measures too.

18.1.3Accuracy

Are the values correct? With the rule sales = quantity × price, order O1002 (3 × 200) should be 600, not 800.

OrderQtyPriceSales
O100125001,000 ✓
O10023200800 ✗
Python
from pyspark.sql import functions as F

invalid_sales = source_df.filter(
    ~F.col("sales_amount").eqNullSafe(
        F.col("quantity") * F.col("unit_price"))

display(invalid_sales)

Recalculate derived values; validate totals against trusted sources and reference data; verify currency and unit conversions and mappings. Real rules include discounts, taxes, returns, and rounding, and some accuracy questions need an authoritative external source.

18.1.4Consistency

Does data agree across tables and systems? If one current-state table says C1001 lives in Hyderabad and another says Chennai, something's wrong, unless one deliberately keeps history. Define the business meaning before comparing.

SQL · referential consistency
SELECT f.customer_key
FROM gold.fact_sales AS f
LEFT ANTI JOIN gold.dim_customer AS d ON f.customer_key = d.customer_key;

Also: matching IDs across systems, consistent categories, date/time-zone and currency conventions, and metrics that agree across reports.

18.1.5Validity

Does data follow the required format, domain, or rule?

ColumnValidity rule
EmailAccepted email format

Python · one condition, two outputs
is_valid = (
    F.col("customer_id").isNotNull()
    & (F.col("quantity") > 0)
    & (F.col("sales_amount") >= 0)
)

valid_records   = source_df.filter(is_valid)
invalid_records = source_df.filter(~is_valid | is_valid.isNull())
Why the isNull()?

A null quantity makes quantity > 0 null, not false, so the row matches neither filter(is_valid) nor filter(~is_valid) and silently vanishes. Including is_valid.isNull() sends it to invalid records, so every row lands in exactly one bucket. (Here customer_id.isNotNull() is never null itself, but nullable comparisons are.) In production, also record why each row failed.

18.1.6Uniqueness

Are keys that should be unique actually unique? With key (order_id, line_number), a second O1001 / 1 row is a duplicate.

SQL
SELECT order_id, line_number, COUNT(*) AS duplicate_count
FROM silver.sales_source
GROUP BY order_id, line_number
HAVING COUNT(*) > 1;
Python
duplicates = (
    source_df.groupBy("order_id", "line_number")
    .count()
    .filter(F.col("count") > 1)
)

A business key is often composite (order_id + line_number, or with source_system for multi-source warehouses). Define it from the real grain.

18.1.7Timeliness

Is the data available when needed? If yesterday's sales must be on the dashboard by 7:00 AM and the pipeline finishes at 11:00, the data is correct but not timely.

SQL · freshness
SELECT MAX(source_updated_at) AS latest_source_timestamp FROM silver.sales_source;
SELECT MAX(source_updated_at) AS latest_target_timestamp FROM gold.fact_sales;

-- Hours since the target last received data
SELECT timestampdiff(HOUR, MAX(source_updated_at), current_timestamp()) AS hours_stale
FROM gold.fact_sales;

Compare against the business SLA, considering time zones and whether the source is expected to be active.

18.2Validation Framework

A validation framework runs checks, records results, and decides whether the pipeline continues, so every notebook doesn't reinvent its own checks.

18.2.1Framework Architecture

  Source -> Transformations -> Target
                  |
          Validation framework
        /         |          \
  Count check  Key checks  Rule checks
        \         |          /
          Validation results
            /           \
      Audit table    Error table
            |
    Pass / fail decision
            |
  Continue or fail pipeline

Responsibilities

  1. Receive source and target datasets.
  2. Execute configured checks.
  3. Compute expected vs actual results.
  4. Record every result.
  5. Identify failures.
  6. Decide: continue or stop.
  7. Leave enough detail to investigate.

18.2.2Count, Key, Duplicate, and Null Checks

Python · record count
def validate_record_count(source_df, target_df):
    source_count = source_df.count()
    target_count = target_df.count()
    return {
        "check_name": "RECORD_COUNT",
        "source_count": source_count,
        "target_count": target_count,
        "difference": source_count - target_count,
        "status": "PASS" if source_count == target_count else "FAIL",
    }

Counts aren't enough when the target…

  • Intentionally filters invalid records.
  • Aggregates source rows.
  • Retains historical versions.
  • Covers a different load window.
  • Contains duplicates.

Define a fitting reconciliation rule for those.

SQL · primary-key checks
-- Null key parts
SELECT COUNT(*) AS null_key_count
FROM silver.sales_source
WHERE order_id IS NULL OR line_number IS NULL;

-- Duplicate keys
SELECT order_id, line_number, COUNT(*) AS record_count
FROM silver.sales_source
GROUP BY order_id, line_number
HAVING COUNT(*) > 1;

Three different duplicate metrics

Python · reusable key helpers
from functools import reduce

def find_duplicate_keys(df, key_columns):
    return df.groupBy(*key_columns).count().filter(F.col("count") > 1)

def find_null_keys(df, key_columns, check_blank_strings=False):
    conditions = [F.col(c).isNull() for c in key_columns]
    if check_blank_strings:                  # string keys: "" or "   " are also missing
        conditions += [F.trim(F.col(c)) == "" for c in key_columns]
    return df.filter(reduce(lambda a, b: a | b, conditions))

duplicate_keys = find_duplicate_keys(source_df, ["order_id", "line_number"])
null_keys = find_null_keys(source_df, ["order_id", "line_number"])

Pass composite keys as configuration rather than hard-coding one column. A null check alone misses empty or whitespace-only string IDs.

18.2.3Data Type Validation

Expected: quantity INT, sales_amount DECIMAL(18,2). Incoming text: "three", "ABC". Use try_cast: a non-null input that casts to null is invalid.

Python
typed_df = (
    raw_df
    .withColumn("quantity_cast", F.expr("try_cast(quantity AS INT)"))
    .withColumn("sales_amount_cast", F.expr("try_cast(sales_amount AS DECIMAL(18,2))"))
)

invalid_types = typed_df.filter(
    (F.col("quantity").isNotNull() & F.col("quantity_cast").isNull())
    | (F.col("sales_amount").isNotNull() & F.col("sales_amount_cast").isNull())
)

Plain CAST raises an error in ANSI mode (Chapter 11), which is why try_cast is used. Keep the raw input so invalid rows can be investigated and reprocessed.

18.2.4Business-Rule Validation

Domain rules: quantity > 0; order date not in the future; discount within limits; customer exists; currency approved; net sales reconcile.

Python · rules as named configuration
business_rules = [
    {"rule_name": "POSITIVE_QUANTITY",       "condition": "quantity > 0"},
    {"rule_name": "NON_NEGATIVE_DISCOUNT",   "condition": "discount_amount >= 0"},
    {"rule_name": "DISCOUNT_WITHIN_GROSS",   "condition": "discount_amount <= quantity * unit_price"},
    {"rule_name": "ORDER_DATE_NOT_FUTURE",   "condition": "order_date <= current_date()"},
    {"rule_name": "REQUIRED_ORDER_ID",       "condition": "order_id IS NOT NULL"},
]

for rule in business_rules:
    failures = source_df.filter(f"NOT coalesce({rule['condition']}, false)").count()
    print(rule["rule_name"], "FAIL" if failures else "PASS", failures)

coalesce(…, false) treats a null result as a violation. Adjust rules to your model (e.g. negative quantities for returns). Only run approved expressions from configuration, never untrusted SQL.

18.3Automated Testing

Two kinds of checking

Tests check that pipeline logic is right (run before deployment, on small known data). Validations check that real data is right (run in production, every load). You need both.

Python · transformations.py
from pyspark.sql import DataFrame, Window
from pyspark.sql import functions as F


def calculate_net_sales(df: DataFrame) -> DataFrame:
    return df.withColumn(
        "net_sales",
        F.col("quantity") * F.col("unit_price") - F.col("discount_amount"),
    )


def deduplicate_sales(df: DataFrame) -> DataFrame:
    """Keep one row per (order_id, line_number): the latest updated_at wins."""
    latest_first = Window.partitionBy("order_id", "line_number") \
                         .orderBy(F.col("updated_at").desc())
    return (df.withColumn("_rn", F.row_number().over(latest_first))
              .filter("_rn = 1").drop("_rn"))


def assert_no_duplicate_keys(df: DataFrame, key_columns: list) -> None:
    duplicates = df.groupBy(*key_columns).count().filter(F.col("count") > 1)
    if not duplicates.isEmpty():
        raise AssertionError(f"Duplicate keys found for {key_columns}")
Python · tests/test_transformations.py
from datetime import datetime
from decimal import Decimal

import pytest

from retail_pipeline.transformations import (
    assert_no_duplicate_keys, calculate_net_sales, deduplicate_sales)

SALES_SCHEMA = ("order_id STRING, quantity INT, "
                "unit_price DECIMAL(10,2), discount_amount DECIMAL(10,2)")


def test_calculate_net_sales(spark):
    df = spark.createDataFrame(
        [("O1001", 2, Decimal("100.00"), Decimal("10.00")),
         ("O1002", 1, Decimal("500.00"), Decimal("0.00"))], SALES_SCHEMA)

    result = {r["order_id"]: r["net_sales"] for r in calculate_net_sales(df).collect()}

    assert result == {"O1001": Decimal("190.00"), "O1002": Decimal("500.00")}


def test_calculate_net_sales_empty_input(spark):
    df = spark.createDataFrame([], SALES_SCHEMA)
    assert calculate_net_sales(df).count() == 0


def test_deduplicate_keeps_latest_version(spark):
    df = spark.createDataFrame(
        [("O1001", 1, 100.0, datetime(2026, 10, 25, 9)),
         ("O1001", 1, 150.0, datetime(2026, 10, 25, 11)),   # newer, conflicting value
         ("O1002", 1, 200.0, datetime(2026, 10, 25, 9))],
        "order_id STRING, line_number INT, sales_amount DOUBLE, updated_at TIMESTAMP")

    result = {r["order_id"]: r["sales_amount"] for r in deduplicate_sales(df).collect()}

    assert result == {"O1001": 150.0, "O1002": 200.0}


def test_assert_no_duplicate_keys_raises(spark):
    df = spark.createDataFrame([("O1001", 1), ("O1001", 1)],
                               "order_id STRING, line_number INT")
    with pytest.raises(AssertionError):
        assert_no_duplicate_keys(df, ["order_id", "line_number"])

18.4Pipeline Reliability

18.4.1Idempotency and Retry Safety

Repeating the same logical operation must not add effects. A plain append run twice gives two copies of O1001; a MERGE on the business key gives one.

SQL
MERGE INTO gold.fact_sales AS target
USING silver.sales_batch AS source
ON  target.order_id = source.order_id
AND target.line_number = source.line_number
WHEN MATCHED THEN UPDATE SET target.sales_amount = source.sales_amount
WHEN NOT MATCHED THEN INSERT (order_id, line_number, sales_amount)
    VALUES (source.order_id, source.line_number, source.sales_amount);

Risky (not retry-safe)

  • Appending the same records again.
  • Incrementing totals without tracking events.
  • Sending a notification on every retry.
  • New random business IDs each run.
  • Advancing the watermark before the write commits.

Safer sequence

  1. Identify the batch.
  2. Read its source records.
  3. Validate.
  4. Transform deterministically.
  5. Commit the target write.
  6. Record completion.
  7. Then advance the watermark.

Checklist: stable keys; deduplicated source before merging; deterministic logic; no new IDs on retry; processed-batch tracking; retry-safe side effects; validate after reprocessing.

18.4.2Transaction Handling

Each Delta write or MERGE is atomic for one table. A load that (1) updates a dimension, (2) inserts facts, (3) writes a reconciliation summary, (4) advances the watermark is four commits. If step 2 fails, step 1 already happened.

Safer strategies

  • Stage before publishing.
  • Track batch status explicitly.
  • Make each step retry-safe.
  • Publish only after checks pass.
  • Advance watermarks after commits.
  • Design recovery for partial failures.

18.4.3Failure Recovery

100,000 records staged, 80,000 written, then failure. A blind restart might append duplicates.

Pipeline failure
      |
Identify failed step
      |
Inspect batch status
      |
Check target commit state
      |
Choose safe retry strategy
      |
Reprocess or resume
      |
Reconcile source and target
      |
Mark batch complete

Recovery checklist

  • Which batch failed?
  • Did the target write commit? (Delta history shows commits.)
  • Was the watermark advanced?
  • Is the source still available?
  • Is the operation idempotent?
  • Could duplicates appear?
  • Does the audit table show the right state?
  • Does reconciliation pass afterwards?

18.4.4Partial-Load Prevention

Source
  |
Staging table
  |
Validation --- failure ---> reject / alert
  |
Target MERGE
  |
Reconciliation --- failure ---> recovery
  |
Mark batch complete

Approaches

  1. Stage before publishing.
  2. Batch identifiers on every record.
  3. Validate before promotion: counts, keys, schema, rules.
  4. Control publication: don't mark complete until writes and checks succeed.
  5. Preserve the last good state (e.g. atomic replace; Delta time travel for rollback).

A staging table doesn't prevent partial loads by itself; the pipeline must enforce the publication rules.

18.4.5Reprocessing Failed Batches and Consistency

batch_idstatussourcetarget
B001COMPLETED10,00010,000
B002FAILED15,00012,000
B003COMPLETED8,0008,000

Reprocess B002

  1. Identify its source records.
  2. Determine what committed.
  3. Keep the batch ID; record a new run ID for the attempt.
  4. Reprocess with retry-safe logic.
  5. Rerun all validations.
  6. Update the audit record.
  7. Confirm reconciliation.

Don't blindly rerun appends. Decide whether to replay the original snapshot or the latest source state. Consistency spans the whole model: a dimension updated while facts keep obsolete keys creates orphans and misattribution. Use referential checks, SCD date validation, reconciliation, batch controls, and idempotent merges.

18.5Operational Controls

A supportable pipeline can answer: when did it start, which batch, how many rows in/inserted/updated, which check failed, where are the rejects, did it reconcile, who ran it, and was the data published?

18.5.1Audit Tables and Batch Identifiers

SQL · pipeline execution audit
CREATE TABLE IF NOT EXISTS retail_dev.ops.pipeline_audit (
    audit_id STRING, pipeline_name STRING, batch_id STRING, run_id STRING,
    source_name STRING, target_name STRING,
    start_time TIMESTAMP, end_time TIMESTAMP,
    source_count BIGINT, target_count BIGINT,
    inserted_count BIGINT, updated_count BIGINT, rejected_count BIGINT,
    status STRING,                 -- STARTED, STAGED, VALIDATED, COMPLETED, FAILED
    error_message STRING
);

batch_id vs run_id

batch_id = the logical data batch (e.g. BATCH_20261025_001, from a business date, file, or extract ID).

run_id = one execution attempt. A retry keeps the batch ID and gets a new run ID, so all attempts link to one batch. In a job, use {{job.run_id}} (Chapter 14).

Python
from uuid import uuid4

batch_id = "BATCH_20261025_001"   # stable for the data
run_id = str(uuid4())             # unique per attempt

Batch IDs support reconciliation, recovery, reprocessing, auditability, and traceability. Keep one execution table plus a separate validation-results table rather than one ever-wider row.

reject_reason = (
    F.when(F.col("order_id").isNull() | F.col("line_number").isNull(), "MISSING_KEY")
     .when(F.col("customer_id").isNull(), "MISSING_CUSTOMER")
     .when(F.col("quantity").isNull() | (F.col("quantity") <= 0), "INVALID_QUANTITY")
     .when(F.col("sales_amount").isNull() | (F.col("sales_amount") < 0), "INVALID_AMOUNT")
)   # first matching rule = primary reason; NULL = valid

classified = source_df.withColumn("reject_reason", reject_reason)

valid_df = classified.filter(F.col("reject_reason").isNull()).drop("reject_reason")
reject_df = (classified.filter(F.col("reject_reason").isNotNull())
             .withColumn("batch_id", F.lit(batch_id))
             .withColumn("rejected_at", F.current_timestamp()))

One reason column means every row is either valid or rejected, never both and never lost, so source = accepted + rejected holds (18.7.2). Record all violations instead if the business needs them. Error tables: enough context, minimal sensitive data, original source ID, stable categories, searchable by batch, defined retention.

18.6Hands-On Project: Build a Reusable Validation Framework

Build a framework that takes source and target DataFrames; checks counts, missing keys, duplicate keys, null keys, and amounts; writes every result to a Delta audit table and failures to an error table; supports CRITICAL vs WARNING severity; and raises an exception when critical checks fail.

  Source DataFrame      Target DataFrame
          \                  /
       run_validation_suite(...)
     /       |        |        |        \
 Count   Missing   Duplicate  Null    Amount
         keys      keys       keys   (Decimal)
     \       |        |        |        /
        write_validation_result(...)
             /                \
  ops.validation_audit   ops.validation_errors
             |
        enforce(results) -> raise if any CRITICAL check FAILED
What changed from the original, and why

1. The original framework crashed on every passing check. It built audit rows with spark.createDataFrame(rows, column_names). On a PASS, error_message is None, and Spark can't infer a column type from None, so it raised [CANNOT_DETERMINE_TYPE] (verified on Spark 4). The new version uses explicit schemas. 2. Amount reconciliation uses Decimal, not float. 3. Severity levels (CRITICAL → FAIL, WARNING → WARN) were added. 4. A runnable four-scenario test replaces assumptions.

18.6.2Step 3: The Framework Code

Put this in a notebook (or a dq_framework.py file you import). It contains the result writer, five checks, the suite runner, and the enforcement step:

Python · dq_framework.py
from datetime import datetime, timezone
from decimal import Decimal
from uuid import uuid4

from pyspark.sql import functions as F
from pyspark.sql.types import StructType, StructField, StringType, TimestampType

AUDIT_TABLE = "retail_dev.ops.validation_audit"
ERROR_TABLE = "retail_dev.ops.validation_errors"

# Explicit schemas: a PASS row has error_message = None, and Spark cannot
# infer a type from None, so createDataFrame would fail without these.
AUDIT_SCHEMA = StructType([
    StructField(name, StringType()) for name in [
        "validation_id", "pipeline_name", "batch_id", "source_table", "target_table",
        "check_name", "severity", "expected_value", "actual_value", "difference_value",
        "status", "error_message"]
] + [StructField("validated_at", TimestampType())])

ERROR_SCHEMA = StructType([
    StructField(name, StringType()) for name in [
        "error_id", "validation_id", "pipeline_name", "batch_id", "source_table",
        "target_table", "check_name", "severity", "error_message"]
] + [StructField("detected_at", TimestampType())])


def _as_str(value):
    return None if value is None else str(value)


def write_validation_result(spark, ctx, check_name, expected, actual, difference,
                            passed, severity="CRITICAL", error_message=None):
    """Append one audit row (and one error row if the check failed)."""
    validation_id = str(uuid4())
    status = "PASS" if passed else ("FAIL" if severity == "CRITICAL" else "WARN")
    now = datetime.now(timezone.utc)

    audit_row = (validation_id, ctx["pipeline_name"], ctx["batch_id"], ctx["source_table"],
                 ctx["target_table"], check_name, severity, _as_str(expected),
                 _as_str(actual), _as_str(difference), status, error_message, now)
    spark.createDataFrame([audit_row], AUDIT_SCHEMA) \
        .write.mode("append").saveAsTable(AUDIT_TABLE)

    if not passed:
        error_row = (str(uuid4()), validation_id, ctx["pipeline_name"], ctx["batch_id"],
                     ctx["source_table"], ctx["target_table"], check_name, severity,
                     error_message or "Validation failed", now)
        spark.createDataFrame([error_row], ERROR_SCHEMA) \
            .write.mode("append").saveAsTable(ERROR_TABLE)

    return {"validation_id": validation_id, "check_name": check_name,
            "status": status, "severity": severity, "error_message": error_message}


def _any_null(key_columns):
    condition = F.lit(False)
    for column_name in key_columns:
        condition = condition | F.col(column_name).isNull()
    return condition


# ---------------------------------------------------------------- checks
def validate_record_count(spark, ctx, source_df, target_df, severity="CRITICAL"):
    source_count, target_count = source_df.count(), target_df.count()
    difference = source_count - target_count
    passed = difference == 0
    message = None if passed else (
        f"Record count mismatch: source={source_count}, target={target_count}, "
        f"difference={difference}")
    return write_validation_result(spark, ctx, "RECORD_COUNT", source_count, target_count,
                                   difference, passed, severity, message)


def validate_missing_keys(spark, ctx, source_df, target_df, key_columns, severity="CRITICAL"):
    missing = (source_df.select(*key_columns).dropDuplicates()
               .join(target_df.select(*key_columns).dropDuplicates(),
                     on=key_columns, how="left_anti"))
    missing_count = missing.count()
    message = None if missing_count == 0 else f"Source keys missing in target: {missing_count}"
    result = write_validation_result(spark, ctx, "MISSING_TARGET_KEYS", 0, missing_count,
                                     missing_count, missing_count == 0, severity, message)
    return result, missing


def validate_duplicate_keys(spark, ctx, df, key_columns, severity="CRITICAL"):
    duplicates = df.groupBy(*key_columns).count().filter(F.col("count") > 1)
    group_count = duplicates.count()
    message = None if group_count == 0 else f"Duplicate key groups: {group_count}"
    result = write_validation_result(spark, ctx, "DUPLICATE_KEYS", 0, group_count,
                                     group_count, group_count == 0, severity, message)
    return result, duplicates


def validate_null_keys(spark, ctx, df, key_columns, severity="CRITICAL"):
    null_rows = df.filter(_any_null(key_columns))
    null_count = null_rows.count()
    message = None if null_count == 0 else f"Rows with null key values: {null_count}"
    result = write_validation_result(spark, ctx, "NULL_KEYS", 0, null_count,
                                     null_count, null_count == 0, severity, message)
    return result, null_rows


def validate_amount(spark, ctx, source_df, target_df, column="sales_amount",
                    tolerance=Decimal("0.00"), severity="CRITICAL"):
    """Compare totals with Decimal arithmetic (no float rounding)."""
    source_total = source_df.agg(F.sum(column)).first()[0] or Decimal("0")
    target_total = target_df.agg(F.sum(column)).first()[0] or Decimal("0")
    difference = Decimal(source_total) - Decimal(target_total)
    passed = abs(difference) <= tolerance
    message = None if passed else (
        f"{column} mismatch: source={source_total}, target={target_total}")
    return write_validation_result(spark, ctx, f"AMOUNT_{column.upper()}", source_total,
                                   target_total, difference, passed, severity, message)


# ---------------------------------------------------------------- suite
def run_validation_suite(spark, ctx, source_df, target_df, key_columns, amount_column=None):
    results = [validate_record_count(spark, ctx, source_df, target_df)]
    results.append(validate_missing_keys(spark, ctx, source_df, target_df, key_columns)[0])
    results.append(validate_duplicate_keys(spark, ctx, target_df, key_columns)[0])
    results.append(validate_null_keys(spark, ctx, source_df, key_columns)[0])
    if amount_column:
        results.append(validate_amount(spark, ctx, source_df, target_df, amount_column))
    return results


def enforce(results):
    """Raise if any CRITICAL check failed (WARN results are recorded, not raised)."""
    failed = [r["check_name"] for r in results if r["status"] == "FAIL"]
    if failed:
        raise RuntimeError("Critical data validation failed: " + ", ".join(failed))

Design notes

  • ctx bundles pipeline, batch, and table names so every check gets them in one argument.
  • Missing-key and null-key checks also return the offending rows for investigation.
  • Null keys are checked on the source (where they originate); duplicates on the target (what consumers see).
  • WARNING checks are recorded as WARN but don't stop the pipeline.
Production considerations

Audit and error writes are separate commits; if one fails they can disagree, so monitor audit-write failures. Each check runs its own count(), which is fine for most batches, but on huge tables combine metrics in one aggregation. Filter source and target to the same batch and grain before validating.

Step 6: Fail the pipeline on critical failures

Python · last cell of the notebook
enforce(results)    # raises RuntimeError if any CRITICAL check returned FAIL

Raising marks the notebook task as failed, so the job can notify, stop dependent tasks, and show the failure (Chapter 14). Don't auto-retry data-quality failures: the same input fails the same way, and it needs a correction, not another attempt.

To demote a check, pass severity="WARNING" to it in your own suite; it's then recorded as WARN and doesn't stop the pipeline.

This only holds if every row is classified exactly once (the single reject_reason column in 18.5.3 guarantees it). A non-zero unclassified count means records were lost.

18.9Interview Questions and Answers

Try answering each before revealing the answer.

Q1. The six dimensions of data quality?
Completeness, accuracy, consistency, validity, uniqueness, timeliness.
Q2. Are equal record counts proof of quality?
No. Duplicates can offset missing rows, values can be wrong, and relationships can break, all with matching counts.
Q3. Source-to-target reconciliation?
Comparing the intended source with the target using counts, business keys, measures, and rules at the same scope and grain.
Q4. Unit vs integration test?
A unit test checks one isolated component; an integration test checks components working together (read → transform → write → validate).
Q5. Regression testing?
Verifying that changes haven't broken behavior that previously worked.
Q6. Why golden datasets?
Known inputs with known outputs let you detect any change in transformation results after code changes.
Q7. Idempotency?
Repeating the same logical operation produces no additional effects.
Q8. Why can retries duplicate data?
A retried non-idempotent append writes the same records again.
Q9. How to prevent partial loads?
Staging, batch IDs, validation gates, controlled publication, retry-safe writes, and completion-state tracking.
Q10. Batch ID vs run ID?
Batch ID identifies the logical data group; run ID identifies one execution attempt, so retries share a batch ID but differ in run ID.
Q11. Audit table?
A record of executions, data movement, validation results, and status.
Q12. Error table vs reject table?
Error tables record failure diagnostics; reject tables keep the failed records for investigation and reprocessing.
Q13. Null-key validation?
Checking required key columns for nulls (and, for strings, blanks).
Q14. Detect duplicate keys in PySpark?
df.groupBy(*keys).count().filter("count > 1").
Q15. Handling a count mismatch?
Record expected and actual values and the batch, apply the severity policy, and fail or quarantine the batch when critical.
Q16. Validating data types?
Compare against the expected schema and test conversions with try_cast; route failures through a rejection policy.
Q17. Why key-level source-to-target checks?
They identify exactly which records weren't loaded or are misrepresented.
Q18. Row-level vs aggregate validation?
Aggregate compares summaries (counts, totals); row-level compares individual records or keys.
Q19. How do you test a PySpark transformation?
Build a small input DataFrame in a pytest fixture session, run the function, and assert on the collected output.
Q20. When a critical validation fails?
Record it, keep diagnostics, don't mark the batch complete, raise to fail the task, and alert.
Q21. Why test empty datasets?
Empty input may be valid or may signal an outage; the expected behavior must be explicit and tested.
Q22. Handling schema changes?
Validate the incoming schema, apply the approved evolution policy, and test downstream transformations.
Q23. Making a pipeline safe to reprocess?
Stable keys, deterministic logic, idempotent writes, batch tracking, and reconciliation after retries.
Q24. Can a pipeline succeed while data quality fails?
Yes. Technical success doesn't prove the data meets business requirements.
Q25. Designing a reusable framework?
Common check functions, config-driven rules, standard audit tables with explicit schemas, batch IDs, severity levels, reject handling, and a shared pass/fail decision.
