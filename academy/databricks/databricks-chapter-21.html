Databricks DevOps and CI/CD

Manage Databricks code with Git, deploy the same job to development, test, and production with Databricks Asset Bundles, automate testing and deployment with GitHub Actions or Azure DevOps, and provision platform resources with Terraform.

Don't do this

Your customer pipeline works in development. Someone copies the notebooks into production, edits table names by hand, and hopes it works. Nobody can later say which version ran when something broke.

Do this

  1. Store code in Git.
  2. Review and test changes.
  3. Validate the deployment configuration.
  4. Deploy to test.
  5. Get approval for production.
  6. Deploy with automation.
  7. Verify the production job.
  8. Roll back or recover if needed.
By the end of this chapter you will be able to
  1. Manage Databricks projects with Git.
  2. Organize notebook and Python code for deployment.
  3. Create dev, test, and prod configurations.
  4. Define and deploy jobs with Asset Bundles.
  5. Automate tests and deployments with GitHub Actions or Azure DevOps.
  6. Manage parameters and secrets securely.
  7. Provision resources with Terraform.
  8. Build an end-to-end deployment pipeline.
What was actually tested

The complete example project in this chapter was built and checked locally: 6 unit tests pass (and fail when the logic is broken), both bundle YAML files pass the official bundle schema from Databricks CLI v1.22.1, both GitHub workflows pass actionlint, and the Terraform configuration passes validate and produces a real plan with Databricks provider v1.95.0. Deploying to a workspace wasn't possible from here. The project is attached as a zip so you can push it to your own repository.

21.1Version Control

21.1.1What Is Version Control?

Version control tracks changes to code and configuration over time. It answers: who changed the pipeline, what changed, why, which version is in production, can we restore an earlier one, and what is waiting for approval? In a Databricks project, Git manages Python and SQL files, tests, bundle configuration, job definitions, deployment scripts, and documentation.

Python · version 1
df = spark.read.table("retail_dev.bronze.customers")
df.write.mode("append").saveAsTable("retail_dev.silver.customers")
# Rerunning appends everything again: duplicates

With Git

When you replace the append with a MERGE, Git shows exactly what changed, reviewers approve it, tests run, and the release is traceable. Without it, you can't establish which code was running when a failure occurred.

Bash · a feature from start to PR
git switch main && git pull
git switch -c feature/customer-dedup

# ... edit code, run tests ...
git status
git diff                     # review before staging
git add src tests
git diff --staged            # review what will be committed
git commit -m "Keep latest customer version during dedup"
git push -u origin feature/customer-dedup
# then open a pull request

Good commits

  • Small and focused on one change.
  • Tested where practical.
  • Message explains the purpose: "Add duplicate customer key validation", not "Updated code".
  • No credentials, no large generated files.

Branch strategy

main plus short-lived feature/*, bugfix/*, and hotfix/* branches is enough for most data teams. Long-lived branches drift apart and make merging painful. Protect main: require a PR, passing CI, and at least one approval.

21.1.6Managing Notebook Changes

Notebooks can be versioned, but outputs and metadata make diffs noisy. Keep business logic in Python modules and notebooks thin. In Databricks, a Git folder (Workspace → Create → Git folder) clones your repository into the workspace so you can branch, commit, and pull from the UI.

Source-format notebooks

A .py file whose first line is # Databricks notebook source is a notebook in source format: plain Python that diffs cleanly, with cells separated by # COMMAND ----------. The project's src/customer_load.py uses it, which matters because a bundle's notebook_task must point at a notebook.

Best practices: no secrets or production config in notebooks; keep them focused; reuse shared functions; remove exploratory cells before release; test logic outside notebooks. Treat production notebooks and deployment configuration as software.

21.2Deployment

Deployment publishes code and configuration (notebooks, Python, job definitions, task dependencies, parameters, compute, pipelines, permissions, libraries) into an environment. Uploading code isn't the end: the deployed job must be configured correctly and verified.

A successful dev run isn't proof of production readiness. Production deployments must be repeatable: deploying the same release twice should update the existing job, not create a duplicate. Bundles behave this way because they track what they deployed.

The original kept separate config/dev.yml and config/prod.yml files and bundle variables, two sources of truth for the same values. In this chapter's project, the bundle target is the single source: each target sets one variable, catalog, and every table name is derived from it (21.3.5).

21.2.3Parameter Management

Parameters let a pipeline receive values (environment, tables, business date, batch ID, mode, paths) without code changes. For a notebook task, job parameters arrive as widgets, so the notebook only needs dbutils.widgets.get.

Validate parameters; don't trust them

A production job shouldn't accept any target table it's given. The project's validate_parameters rejects unknown environments, a catalog that doesn't match the environment, and tables outside that catalog, so a dev job can't be pointed at prod_catalog. All three rejection cases are unit-tested (21.3.7).

21.2.4Secrets During Deployment

Secrets must never be in

  • Git repositories.
  • Bundle configuration.
  • Notebook source.
  • Plain job parameters (visible in run details).
  • Build logs or deployment output.

Where they go

  • Runtime secrets (database passwords): secret scopes / Key Vault, read with dbutils.secrets.get(scope, key). The scope and key are references, not the secret.
  • Deployment credentials (the CI service principal): GitHub environment secrets or Azure DevOps variable groups, or no secret at all with workload identity federation.
  • Prefer managed identities wherever supported.

21.3Databricks Asset Bundles

The most important topic in this chapter. A bundle defines Databricks resources (jobs, pipelines, their code, environment targets, variables, permissions) as files in Git, and the Databricks CLI deploys them. Recent documentation calls them Declarative Automation Bundles; the commands are the same.

Without bundles

  1. Create the job by hand in dev.
  2. Recreate it by hand in test.
  3. Recreate it by hand in prod.
  4. Set parameters separately each time.
  5. Check permissions and compute manually.

Environments drift apart.

With bundles

  1. Define the job once.
  2. Define environment targets.
  3. Validate.
  4. Deploy to dev and test.
  5. Deploy the same definition to prod.

Consistent, reviewable, repeatable.

21.3.3The Bundle Configuration: databricks.yml

YAML · databricks.yml
bundle:
  name: retail-customer-pipeline

include:
  - resources/*.yml

variables:
  catalog:
    description: Unity Catalog catalog for this environment
  run_as_sp:
    description: Application ID of the service principal that runs the job
    default: ""

targets:
  dev:
    mode: development          # prefixes names with [dev <you>], pauses schedules
    default: true
    workspace:
      host: https://adb-1111111111111111.11.azuredatabricks.net
    variables:
      catalog: dev_catalog

  test:
    mode: production
    workspace:
      host: https://adb-2222222222222222.12.azuredatabricks.net
      root_path: /Workspace/Shared/.bundle/${bundle.name}/${bundle.target}
    variables:
      catalog: test_catalog
      run_as_sp: 00000000-0000-0000-0000-000000000002
    run_as:
      service_principal_name: ${var.run_as_sp}

  prod:
    mode: production
    workspace:
      host: https://adb-3333333333333333.13.azuredatabricks.net
      root_path: /Workspace/Shared/.bundle/${bundle.name}/${bundle.target}
    variables:
      catalog: prod_catalog
      run_as_sp: 00000000-0000-0000-0000-000000000003
    run_as:
      service_principal_name: ${var.run_as_sp}
    permissions:
      - group_name: dbx-production-support
        level: CAN_VIEW
      - group_name: dbx-platform-admins
        level: CAN_MANAGE

How the targets differ

  • mode: development (dev): prefixes resource names with [dev your.name], pauses schedules, deploys to your own folder. Several developers can share a workspace without clashing.
  • mode: production (test, prod): real names, active schedules, plus safety checks on the deployment.
  • root_path: a shared folder, so deployments don't depend on whoever ran them.
  • run_as: the job runs as a service principal, never as the deployer.
  • permissions (prod): support can view, admins manage.
Changes from the original, and why

The original declared three variables (catalog, source_table, target_table) per target, and nothing stopped them disagreeing (e.g. a test catalog with prod tables). Here each target sets only catalog, and tables are derived from it. Test and prod also gained run_as, root_path, and permissions, which the original didn't have, so its prod job would have run as whoever deployed it.

Replace the hosts and service-principal application IDs with yours. Mode settings don't replace workspace isolation or approvals (Chapter 19).

21.3.4Define the Job

YAML · resources/customer_job.yml
resources:
  jobs:
    retail_customer_load:
      name: retail-customer-load-${bundle.target}

      parameters:
        - name: environment
          default: ${bundle.target}
        - name: catalog
          default: ${var.catalog}
        - name: source_table
          default: ${var.catalog}.bronze.customers
        - name: target_table
          default: ${var.catalog}.silver.customers
        - name: run_id
          default: "{{job.run_id}}"

      tasks:
        - task_key: load_customers
          notebook_task:
            notebook_path: ../src/customer_load.py   # relative to this YAML file
          max_retries: 1
          min_retry_interval_millis: 120000
          retry_on_timeout: false

      email_notifications:
        on_failure:
          - data-support@example.com

      schedule:
        quartz_cron_expression: "0 0 2 * * ?"       # 02:00 daily
        timezone_id: Asia/Kolkata

Points to notice

  • Job parameters (not task base_parameters) are visible on the job and passed to the notebook as widgets.
  • ${bundle.target} and ${var.catalog} are resolved per target.
  • {{job.run_id}} is resolved at run time (it feeds Chapter 20's monitoring).
  • No cluster is defined, so the task runs on serverless compute (works on Free Edition). Add job_clusters for classic compute.
  • One retry, two minutes apart, for transient failures only (Chapter 20).

Path resolution

Paths in a resource file are relative to that file, so ../src/customer_load.py goes up from resources/. During deploy the bundle uploads src/ to the target's workspace folder and rewrites the path. A wrong path is one of the most common validation errors.

21.3.5The Pipeline Code and Its Tests

Python · src/retail/transformations.py
from pyspark.sql import Window, functions as F


def clean_customers(df):
    """Drop rows without an ID; keep the latest version of each customer."""
    latest_first = Window.partitionBy("customer_id").orderBy(
        F.col("updated_at").desc(), F.col("customer_name").desc())   # name breaks exact ties
    return (
        df.filter(F.col("customer_id").isNotNull())
          .withColumn("_rn", F.row_number().over(latest_first))
          .filter("_rn = 1")
          .drop("_rn")
    )


ALLOWED_ENVIRONMENTS = {"dev", "test", "prod"}


def validate_parameters(environment, catalog, source_table, target_table):
    """Refuse to run with inconsistent settings, e.g. a dev job writing to prod."""
    if environment not in ALLOWED_ENVIRONMENTS:
        raise ValueError(f"Unsupported environment: {environment!r}")
    if catalog != f"{environment}_catalog":
        raise ValueError(f"Catalog {catalog!r} does not belong to environment {environment!r}")
    for table in (source_table, target_table):
        if not table.startswith(f"{catalog}."):
            raise ValueError(f"Table {table!r} is outside catalog {catalog!r}")
Python · src/customer_load.py (notebook in source format)
# Databricks notebook source
# The line above makes Databricks treat this .py file as a notebook,
# which notebook_task requires.

from retail.transformations import clean_customers, validate_parameters

environment = dbutils.widgets.get("environment")      # job parameters arrive as widgets
catalog = dbutils.widgets.get("catalog")

target_table = dbutils.widgets.get("target_table")

print(f"Environment={environment} source={source_table} target={target_table}")

# COMMAND ----------

# Full refresh by design; incremental pipelines would MERGE instead (Chapter 17)
cleaned_df.write.mode("overwrite").saveAsTable(target_table)

print(f"Rows written: {spark.table(target_table).count()}")
Fixes to the original pipeline file

1. It wasn't a notebook. The original customer_pipeline.py lacked the # Databricks notebook source header but was deployed with notebook_task, which needs a notebook. 2. Widgets were re-declared. Calling dbutils.widgets.text(…) isn't needed when job parameters supply the values. 3. Fragile imports. from transformations import … relied on the working directory; the logic is now a package (retail) that both the notebook and the tests import the same way. 4. Arbitrary dedup. dropDuplicates kept a random row; the latest version now wins, with a tie-breaker.

from datetime import datetime

import pytest

from retail.transformations import clean_customers, validate_parameters

SCHEMA = "customer_id INT, customer_name STRING, updated_at TIMESTAMP"


def test_removes_null_ids_and_keeps_latest_version(spark):
    rows = [
        (1, "Alice",   datetime(2026, 10, 1)),
        (2, "Bob",     datetime(2026, 10, 1)),
        (2, "Bob K.",  datetime(2026, 10, 5)),      # newer version of customer 2
        (None, "Unknown", datetime(2026, 10, 1)),
    ]
    result = clean_customers(spark.createDataFrame(rows, SCHEMA))

    assert {r.customer_id: r.customer_name for r in result.collect()} == {
        1: "Alice", 2: "Bob K."}


def test_empty_input(spark):
    assert clean_customers(spark.createDataFrame([], SCHEMA)).isEmpty()


def test_accepts_matching_parameters():
    validate_parameters("dev", "dev_catalog",
                        "dev_catalog.bronze.customers", "dev_catalog.silver.customers")


@pytest.mark.parametrize("env, catalog, target", [
    ("dev",  "prod_catalog", "prod_catalog.silver.customers"),   # dev job pointed at prod
    ("dev",  "dev_catalog",  "prod_catalog.silver.customers"),   # target outside catalog
    ("qa",   "qa_catalog",   "qa_catalog.silver.customers"),     # unknown environment
])
def test_rejects_unsafe_parameters(env, catalog, target):
    with pytest.raises(ValueError):
        validate_parameters(env, catalog, f"{catalog}.bronze.customers", target)

21.3.6Validate, Deploy, and Run

Bash · development cycle
databricks bundle validate -t dev      # check config, resolve variables
databricks bundle deploy -t dev        # upload code, create/update the job
databricks bundle run -t dev retail_customer_load   # run it and wait for the result
databricks bundle summary -t dev       # what's deployed, with links

databricks bundle destroy -t dev       # remove your dev copy when finished

Validation catches

  • YAML indentation errors.
  • Unknown or misspelled keys.
  • Missing required properties.
  • Wrong file paths.
  • Undefined variables.
  • Authentication and workspace problems.

validate contacts the workspace, so it needs credentials. It doesn't prove the logic is right; tests and a real run do.

After deploy and run, verify

  1. The job exists with the expected name.
  2. Tasks and parameters are correct.
  3. Source and target tables are this environment's.
  4. The deployed code is the intended commit.
  5. Run-as identity and permissions are right.
  6. The run succeeds and data checks pass.
  7. Audit rows are recorded (Chapter 20).

Schema check, done here: without a workspace, I validated both YAML files against the official bundle JSON schema (databricks bundle schema, CLI v1.22.1): 0 errors for each, while a deliberately misspelled key (max_retires) was rejected. Your editor can use the same schema for autocomplete.

Then promote: validate and deploy with -t test, run and test there, and after approval -t prod. Never use the prod target as a test environment. The deploying identity needs permission to deploy, and the "Service Principal User" role on the run-as service principal.

Two workflows: CI on every pull request, Deploy on every merge to main.

on:
  pull_request:
    branches: [main]

permissions:
  contents: read

jobs:
  unit-tests:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4

      - uses: actions/setup-python@v5
        with:
          python-version: "3.11"

      - uses: actions/setup-java@v4          # PySpark 4 needs Java 17+

          java-version: "17"

      - name: Install test dependencies
        run: pip install -r requirements-dev.txt

      - name: Run unit tests
        run: pytest

  validate-bundle:
    needs: unit-tests
    runs-on: ubuntu-latest
    environment: dev                         # holds the dev service principal's secrets

      DATABRICKS_CLIENT_ID: ${{ secrets.DATABRICKS_CLIENT_ID }}
      DATABRICKS_CLIENT_SECRET: ${{ secrets.DATABRICKS_CLIENT_SECRET }}
    steps:
      - uses: actions/checkout@v4
      - uses: databricks/setup-cli@main      # pin to a release tag or commit SHA in real use
      - name: Validate bundle against the dev workspace
        run: databricks bundle validate -t dev
YAML · .github/workflows/deploy.yml
name: Deploy

on:
  push:
    branches: [main]                         # every merge to main
  workflow_dispatch:                         # manual runs, e.g. redeploy a release tag

concurrency:
  group: deploy                              # never two deployments at once
  cancel-in-progress: false

permissions:
  contents: read

jobs:
  deploy-test:
    runs-on: ubuntu-latest
    environment: test
    env:
      DATABRICKS_CLIENT_ID: ${{ secrets.DATABRICKS_CLIENT_ID }}
      DATABRICKS_CLIENT_SECRET: ${{ secrets.DATABRICKS_CLIENT_SECRET }}
    steps:
      - uses: actions/checkout@v4
      - uses: databricks/setup-cli@main
      - run: databricks bundle validate -t test
      - run: databricks bundle deploy -t test
      - name: Smoke test (waits; fails this workflow if the job run fails)
        run: databricks bundle run -t test retail_customer_load

  deploy-prod:
    needs: deploy-test
    runs-on: ubuntu-latest
    environment: production                  # required reviewers must approve first
    env:
      DATABRICKS_CLIENT_ID: ${{ secrets.DATABRICKS_CLIENT_ID }}
      DATABRICKS_CLIENT_SECRET: ${{ secrets.DATABRICKS_CLIENT_SECRET }}
    steps:
      - uses: actions/checkout@v4
      - uses: databricks/setup-cli@main
      - run: databricks bundle validate -t prod
      - run: databricks bundle deploy -t prod
      - name: Record what was deployed
        run: |
          echo "Deployed commit ${{ github.sha }} to prod" >> "$GITHUB_STEP_SUMMARY"
          databricks bundle summary -t prod >> "$GITHUB_STEP_SUMMARY"

One-time GitHub setup

  1. Settings → Environments: create dev, test, production.
  2. In each, add secrets DATABRICKS_CLIENT_ID and DATABRICKS_CLIENT_SECRET for that environment's deployment service principal.
  3. On production: add required reviewers and restrict it to the main branch.
  4. Branch protection on main: require PRs and the CI checks.

Why it's built this way

  • Environment-scoped secrets: the test job can't read prod credentials.
  • bundle run waits and fails the workflow if the job fails, so a broken release stops before prod.
  • concurrency prevents overlapping deployments.
  • The step summary records which commit reached prod.
  • permissions: contents: read: least privilege for the workflow token.

Both workflows pass actionlint. The original CI installed unpinned pyspark and had the import problem above; this one installs pinned versions from requirements-dev.txt and sets up Java explicitly. Pin databricks/setup-cli to a release or commit SHA in real use. To avoid storing a client secret at all, use GitHub OIDC workload identity federation. Docs: GitHub Actions.

21.4.3Azure DevOps

The same flow with Azure Repos and Azure Pipelines: a CI stage, then deployment jobs bound to environments, where approvals and checks live.

YAML · azure-pipelines.yml
trigger:
  branches:
    include: [main]

pr:
  branches:
    include: [main]

pool:
  vmImage: ubuntu-latest

stages:
  - stage: CI
    jobs:
      - job: unit_tests
        steps:
          - task: UsePythonVersion@0
            inputs:
              versionSpec: "3.11"
          - script: pip install -r requirements-dev.txt
            displayName: Install test dependencies
          - script: pytest
            displayName: Run unit tests

  - stage: Deploy_Test
    dependsOn: CI
    condition: and(succeeded(), eq(variables['Build.SourceBranch'], 'refs/heads/main'))
    variables:
      - group: databricks-test                 # variable group holding the test SP secret
    jobs:
      - deployment: deploy_test
        environment: retail-test
        strategy:
          runOnce:
            deploy:
              steps:
                - checkout: self
                - script: curl -fsSL https://raw.githubusercontent.com/databricks/setup-cli/main/install.sh | sudo sh
                  displayName: Install Databricks CLI
                - script: |
                    databricks bundle validate -t test
                    databricks bundle deploy -t test
                    databricks bundle run -t test retail_customer_load
                  displayName: Validate, deploy, smoke test
                  env:
                    DATABRICKS_CLIENT_ID: $(DATABRICKS_CLIENT_ID)
                    DATABRICKS_CLIENT_SECRET: $(DATABRICKS_CLIENT_SECRET)   # secrets must be mapped explicitly

  - stage: Deploy_Prod
    dependsOn: Deploy_Test
    variables:
      - group: databricks-prod
    jobs:
      - deployment: deploy_prod
        environment: retail-prod               # approvals and checks are configured on this environment
        strategy:
          runOnce:
            deploy:
              steps:
                - checkout: self
                - script: curl -fsSL https://raw.githubusercontent.com/databricks/setup-cli/main/install.sh | sudo sh
                  displayName: Install Databricks CLI
                - script: |
                    databricks bundle validate -t prod
                    databricks bundle deploy -t prod
                  displayName: Validate and deploy
                  env:
                    DATABRICKS_CLIENT_ID: $(DATABRICKS_CLIENT_ID)
                    DATABRICKS_CLIENT_SECRET: $(DATABRICKS_CLIENT_SECRET)

Create variable groups databricks-test and databricks-prod (ideally linked to Key Vault) and environments retail-test and retail-prod, with an approval check on retail-prod. Secret variables aren't visible to scripts unless mapped in env:, as above. Deployment jobs don't check out code automatically, hence checkout: self. This file was syntax-checked only. Docs: Azure Pipelines.

21.4.4Deployment Approvals

Who approves

A data platform owner, release manager, production support lead, business owner, or designated change approver, configured as GitHub required reviewers or Azure DevOps environment approvals.

What they confirm

  • Tests passed and the change was reviewed.
  • The right target environment.
  • Release notes are complete.
  • The rollback and recovery plan is understood.
  • The change is authorized.

Automation doesn't remove the approval; it enforces it.

21.4.5Rollback and Release Management

A release can bring wrong transformations, missing config, bad permissions, slowdowns, wrong table names, failed runs, or bad data. Rollback must cover code and data.

Bash · tag releases, roll back code
# Tag every production release
git tag -a v1.1.0 -m "Keep latest customer version"
git push origin v1.1.0

# Roll back option A: revert the bad commit;
# the normal PR + deploy flow ships the fix
git revert &lt;bad-commit-sha&gt;

# Option B: redeploy a known-good tag
# (GitHub: Actions → Deploy → Run workflow →
#  choose tag v1.0.0; approval still applies)
SQL · recover data with Delta
-- Which version was written before the release?
DESCRIBE HISTORY prod_catalog.silver.customers;

-- Restore it (a new commit; history is kept)
RESTORE TABLE prod_catalog.silver.customers
  TO VERSION AS OF 41;

-- Then rebuild downstream tables that read
-- the bad data

Time travel only works while the old files still exist: VACUUM removes them after the retention period (7 days by default). Data recovery may instead mean rerunning a corrected pipeline or reprocessing a batch. Release steps: identify the version, capture the config, validate in test, deploy, run checks, monitor, redeploy last-good if needed, recover data, record the incident.

A release record holds version or commit, description, environment, test results, approvals, timestamp, deploying identity, post-deployment status, and recovery reference. During an incident, knowing the exact deployed commit saves hours.

21.5Infrastructure as Code

Infrastructure as Code (IaC) defines infrastructure in version-controlled files rather than by clicking: workspaces, Unity Catalog metastores and assignments, access configuration, compute policies, SQL warehouses, storage, and supporting cloud resources. Manual setup leads to drift, missing resources, inconsistent permissions, and untracked changes.

21.5.2Example Configuration

The original example declared a provider, a variable, and an output, but no resources, so applying it would do nothing. This one manages the Chapter 19 compute policy and who may use it, for any environment:

HCL · infra/main.tf
terraform {
  required_version = ">= 1.6"
  required_providers {
    databricks = {
      source  = "databricks/databricks"
      version = "~> 1.95" # pin a minor range; upgrade deliberately
    }
  }

  # Shared, locked, encrypted state (never commit .tfstate files)
  backend "azurerm" {
    resource_group_name  = "rg-retail-platform"
    storage_account_name = "stretailtfstate"
    container_name       = "tfstate"
    key                  = "databricks-workspace.tfstate" # override per environment
  }
}

# Authentication comes from the environment (e.g. ARM_CLIENT_ID / ARM_TENANT_ID with
# OIDC in CI, or DATABRICKS_CLIENT_ID / DATABRICKS_CLIENT_SECRET), never from this file
provider "databricks" {
  host = var.databricks_host
}

variable "databricks_host" {
  description = "Workspace URL, e.g. https://adb-1111111111111111.11.azuredatabricks.net"
  type        = string
}

variable "environment" {
  description = "dev, test or prod"
  type        = string
  validation {
    condition     = contains(["dev", "test", "prod"], var.environment)
    error_message = "environment must be dev, test or prod."
  }
}

variable "max_workers" {
  description = "Upper limit for autoscaling job clusters"
  type        = number
  default     = 4
}

# A compute policy (Chapter 19), managed as code
resource "databricks_cluster_policy" "jobs" {
  name = "retail-${var.environment}-jobs"
  definition = jsonencode({
    "autotermination_minutes" = { type = "range", minValue = 10, maxValue = 60, defaultValue = 30 }
    "autoscale.max_workers"   = { type = "range", maxValue = var.max_workers, defaultValue = 2 }
    "spark_version"           = { type = "allowlist", values = ["auto:latest-lts"], defaultValue = "auto:latest-lts" }
    "custom_tags.Environment" = { type = "fixed", value = var.environment }
    "custom_tags.CostCenter"  = { type = "fixed", value = "CC-RETAIL-01" }
  })
}

# Who may use it
resource "databricks_permissions" "jobs_policy_usage" {
  cluster_policy_id = databricks_cluster_policy.jobs.id

  access_control {
    group_name       = "dbx-data-engineers"
    permission_level = "CAN_USE"
  }
}

output "jobs_policy_id" {
  value = databricks_cluster_policy.jobs.id
}

21.5.3Workspace Provisioning and State

Terraform (azurerm + databricks providers)
   |
   +--> Resource group
   +--> VNet + subnets (Chapter 19)
   +--> Azure Databricks workspace
   +--> Access connector (managed identity)
   +--> Storage account for Unity Catalog
   |
   +--> Metastore assignment
   +--> Groups, compute policies, warehouses
   +--> Catalogs, schemas, grants

Automated environment setup

With variables per environment, the same configuration creates dev, test, and prod identically, so a new environment is a new .tfvars file plus a reviewed plan. Some identity and workspace settings still need extra automation or admin steps; check the provider docs for each resource.

Separate state per environment (a different backend key), so a dev change can never plan against prod.

Protect the state

State records every managed resource and can contain secrets. Keep it in a remote backend (Azure Storage, as configured above) with locking, encryption, and restricted access; never commit .tfstate files. Run production apply only from the CI/CD pipeline after plan review, not from laptops.

21.6Hands-On Project: Deploy a Job from Development to Production

Take the customer pipeline from a Git repository through dev, test, and an approved production release. Every file is shown above and included in the attached zip.

          Git repository (feature branch)
                     |
                Pull request
                     |
        CI: pytest (6 tests) + bundle validate -t dev
                     |
                Merge to main
                     |
     Deploy: validate + deploy -t test + smoke run
                     |
         Approval (production environment)
                     |
         validate + deploy -t prod + summary
                     |
          Production verification (Chapter 20)

Step 1: Create the repository

Unzip the attached project, run git init, commit, and push to a new GitHub (or Azure Repos) repository named retail-databricks.

Step 2: Run the tests locally

pip install -r requirements-dev.txt then pytest. Expect 6 passed (needs Java 17+). Break the sort order and watch a test fail.

Step 3: Configure the bundle

In databricks.yml, set your workspace hosts and service-principal application IDs. On Free Edition, keep only the dev target and point it at a catalog you can write to: create dev_catalog if your workspace allows it, or set catalog: workspace and relax the catalog check in validate_parameters.

Step 4: Validate and deploy to dev

databricks bundle validate -t dev, deploy -t dev, then run -t dev retail_customer_load. Confirm the job is named [dev you] retail-customer-load-dev, reads dev_catalog, and its schedule is paused.

Step 5: Set up CI

Create the GitHub environments and secrets (21.4.2). Open a PR: both CI jobs should pass. Try a PR that breaks a test and confirm it can't merge.

Step 6: Deploy to test

Merge. The Deploy workflow validates, deploys, and runs the job in test. Verify the tables, output rows, no duplicate keys, run-as identity, and permissions.

Step 7: Approve and deploy to production

The workflow pauses at production. Before approving, check the commit, CI and test results, expected impact, and recovery plan. After approval it deploys and records the commit in the run summary. Never use personal credentials for this.

Step 8: Verify production

The job exists, runs as the prod service principal, targets prod_catalog, has monitoring on (Chapter 20), and its first run passes data-quality checks (Chapter 18).

Step 9: Practice a rollback (in test)

Merge a deliberately bad change, then roll back by reverting it or redeploying the previous tag. Re-run the tests, check the job configuration, and use RESTORE if data was affected. Document the steps.

21.8Interview Questions and Answers

Try answering each before revealing the answer.

Q1. What is CI/CD?
Automating validation, testing, and deployment. CI validates every change; continuous delivery keeps changes releasable through approval; continuous deployment releases automatically once checks pass.
Q2. Why use Git for Databricks projects?
History, collaboration, code review, and the ability to say exactly which version was deployed when an incident occurred, and to restore an earlier one.
Q3. What are Databricks Asset Bundles?
Configuration-as-code for Databricks resources (jobs, pipelines, their code, targets, variables, permissions), deployed repeatably with the Databricks CLI. Now also called Declarative Automation Bundles.
Q4. Bundle vs CI/CD pipeline?
The bundle defines what gets deployed; the CI/CD pipeline automates when and how: testing, validating, approving, and deploying it.
Q5. Deploying the same job to dev and prod?
Define the job once with variables, set per-environment values in bundle targets, validate, deploy to dev, test in test, and deploy the same approved commit to prod.
Q6. Development vs production mode in bundles?
Development mode prefixes names with the user, pauses schedules, and deploys to a personal folder; production mode keeps real names and schedules and adds deployment safety checks.
Q7. Why externalize configuration?
So identical code runs in every environment, with environment values supplied by deployment rather than edited into code.
Q8. Managing secrets in CI/CD?
Environment-scoped CI secrets or workload identity federation for deployment credentials, secret scopes or managed identities at runtime; never in Git, bundle files, job parameters, or logs.
Q9. Testing PySpark transformations in CI?
pytest with a local SparkSession fixture, small controlled DataFrames, assertions on business behavior (nulls, duplicates, rules, empty input), plus integration tests in a test workspace.
Q10. Who should a production job run as?
A dedicated service principal set with run_as, never the person or pipeline that deployed it.
Q11. What is Terraform used for?
Declaring and managing infrastructure: cloud resources and Databricks platform objects such as workspaces, policies, warehouses, groups, and permissions.
Q12. Terraform and bundles together?
Yes: Terraform for platform resources, bundles for application jobs and pipelines, with each resource owned by exactly one tool.
Q13. Why is Terraform state important?
It maps configuration to real resources so plans are correct; it can hold secrets, so it needs a locked, encrypted, access-controlled remote backend.
Q14. A rollback strategy?
Redeploy a known-good tagged release (or revert), and recover affected data with RESTORE or reprocessing, then document the incident.
Q15. Preventing dev code from writing prod tables?
Separate workspaces and catalogs with bindings, target-driven config, parameter validation that rejects mismatched catalogs, and restricted prod permissions.
Q16. Deployment vs execution?
Deployment publishes the job definition and code; execution runs it. A deployment can succeed and the run still fail, so smoke-test after deploying.
Q17. Securing a production deployment pipeline?
Dedicated deployment identity, environment-scoped secrets, protected branches, required reviews and approvals, bundle validation, automated tests, recorded versions, and post-deployment checks.
