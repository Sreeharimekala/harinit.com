Chapter 24 · Lesson 24.1

Project Overview

Business scenario

A retail company runs customer, product, order, inventory, and payment systems. Data is scattered, reports are slow, and nobody can reconcile them with the sources. The platform must answer:

  1. What are total sales, and are they rising?
  2. Which products and customers drive revenue?
  3. Which products are low on stock?
  4. How have customer details changed?
  5. Are pipelines running, and is the data complete and accurate?
  6. What does processing cost?

You will

  • Build an end-to-end pipeline over six datasets.
  • Ingest incrementally into Bronze.
  • Clean and validate into Silver.
  • MERGE incrementally and keep SCD2 history.
  • Model Gold facts and dimensions.
  • Automate quality checks and reconciliation.
  • Orchestrate with Lakeflow Jobs; monitor failures and missed schedules.
  • Optimize, secure, report, and deploy.

Payments vs order items: a fan-out trap

Joining order items to payments and summing sales multiplies amounts, since each item repeats for every payment. In the project data this naive join reports 277,000.00 when true sales are 163,500.00 (verified). Always aggregate payments to the order level first (24.13).

For inventory, confirm whether the source sends movements, snapshots, or both; summing snapshots double-counts.

Step 4: Build the Bronze Layer

Bronze stores source data with minimal change: preserve values, capture ingestion metadata, support replay, keep source identifiers and file lineage. It must never silently drop records.

Metadata columnPurpose
_source_fileOriginal file (_metadata.file_path)
_ingestion_timestampWhen it was ingested; also the tie-breaker for equal updated_at
_source_systemSource application
_batch_idWhich delivery (used to log rejects once)
_rescued_dataUnexpected or unparseable fields
Python · Auto Loader for real files (Chapter 12 pattern)
from pyspark.sql import functions as F

base = "/Volumes/retail_dev/landing/retail_files"

(spark.readStream.format("cloudFiles")
    .option("cloudFiles.format", "csv")
    .option("header", "true")
    .option("cloudFiles.schemaLocation", f"{base}/_schemas/customers")
    .option("cloudFiles.schemaEvolutionMode", "rescue")     # unexpected columns go to _rescued_data
    .load(f"{base}/incoming/customers/")
    .withColumn("_source_file", F.col("_metadata.file_path"))
    .withColumn("_ingestion_timestamp", F.current_timestamp())
    .withColumn("_source_system", F.lit("RETAIL_APP"))
    .writeStream
    .option("checkpointLocation", f"{base}/_checkpoints/customers")
    .trigger(availableNow=True)                              # process what's there, then stop
    .toTable("retail_dev.bronze.customers_raw"))

One stream and one checkpoint per source. Never delete a checkpoint between runs, or files are reprocessed. availableNow suits scheduled jobs and is the trigger serverless supports. Rescue mode keeps unexpected data but doesn't replace schema validation. For six small daily files, batch reads are fine too.

Chapter 24 · Lesson 24.7

Step 5: Implement Incremental Ingestion

Files

Auto Loader's checkpoint remembers which files were processed, so each run ingests only new files.

Databases

Prefer CDC or source change tracking. A timestamp watermark is a fallback: updates can arrive late, timestamps can tie, and sources correct old rows. Define handling for deletes, late updates, and overlapping windows.

SQL
CREATE TABLE IF NOT EXISTS retail_dev.ops.ingestion_watermarks (
    source_name               STRING,
    last_successful_watermark TIMESTAMP,
    updated_at                TIMESTAMP
);

Safe sequence

  1. Read the last committed watermark.
  2. Extract updated_at > watermark − overlap (e.g. 15 min) up to a fixed upper bound.
  3. Append to Bronze.
  4. Validate the batch.
  5. Only then commit the upper bound as the new watermark.

The overlap re-reads a few already-loaded rows on purpose; that's harmless because Silver keeps the latest version per key. Advancing the watermark before data is persisted causes silent data loss (Chapter 18).

Step 6: Build the Silver Layer

Silver standardizes types and text, validates required fields and rules, logs rejects, and keeps the latest version of each business key. Rebuilding Silver from all of Bronze is deterministic, so rerunning it is always safe; at larger scale, process only new Bronze rows and MERGE (24.9).

Python · src/silver.py
# Databricks notebook source
# Rebuilds every Silver table from Bronze: clean, validate, and keep the latest
# version of each business key. Deterministic, so it is safe to rerun.
from pyspark.sql import Window, functions as F

BATCH_ID = dbutils.widgets.get("batch_id") if "dbutils" in globals() else BATCH_ID  # noqa: F821


def latest_per_key(df, keys):
    """Newest source version wins; ingestion time breaks timestamp ties."""
    w = Window.partitionBy(*keys).orderBy(F.col("updated_at").desc_nulls_last(),
                                          F.col("_ingestion_timestamp").desc())
    return df.withColumn("_rn", F.row_number().over(w)).filter("_rn = 1").drop("_rn")


# ---------------------------------------------------------------- customers
customers = (spark.table("retail_dev.bronze.customers_raw")
    .withColumn("customer_id", F.upper(F.trim("customer_id")))
    .withColumn("customer_name", F.trim("customer_name"))
    .withColumn("email", F.lower(F.trim("email")))
    .withColumn("city", F.initcap(F.trim("city")))
    .withColumn("state", F.initcap(F.trim("state")))
    .withColumn("customer_segment", F.upper(F.trim("customer_segment"))))

reason = (F.when(F.col("customer_id").isNull() | (F.col("customer_id") == ""), "MISSING_CUSTOMER_ID")
           .when(F.col("customer_name").isNull() | (F.col("customer_name") == ""), "MISSING_CUSTOMER_NAME"))
customers = customers.withColumn("rejection_reason", reason)

(customers.filter("rejection_reason IS NOT NULL")
    .filter(F.col("_batch_id") == BATCH_ID)        # log each bad record once, in its own batch
    .withColumn("rejection_timestamp", F.current_timestamp())
    .write.mode("append").saveAsTable("retail_dev.ops.rejected_customers"))

(latest_per_key(customers.filter("rejection_reason IS NULL").drop("rejection_reason"), ["customer_id"])
    .select("customer_id", "customer_name", "email", "city", "state", "customer_segment", "updated_at")
    .write.mode("overwrite").saveAsTable("retail_dev.silver.customers"))

# ---------------------------------------------------------------- other entities
simple = {
    "products":    (["product_id"],        "product_id IS NOT NULL AND unit_price >= 0"),
    "orders":      (["order_id"],          "order_id IS NOT NULL AND customer_id IS NOT NULL"),
    "order_items": (["order_item_id"],     "order_item_id IS NOT NULL AND quantity > 0 AND discount_amount >= 0"),
    "payments":    (["payment_id"],        "payment_id IS NOT NULL AND order_id IS NOT NULL"),
}
for name, (keys, rule) in simple.items():
    df = spark.table(f"retail_dev.bronze.{name}_raw").filter(rule)
    (latest_per_key(df, keys).drop("_source_system", "_batch_id", "_ingestion_timestamp")
        .write.mode("overwrite").saveAsTable(f"retail_dev.silver.{name}"))

# Inventory events are immutable: just remove re-delivered duplicates
(spark.table("retail_dev.bronze.inventory_raw")
    .dropDuplicates(["inventory_event_id"])
    .drop("_source_system", "_batch_id", "_ingestion_timestamp")
    .write.mode("overwrite").saveAsTable("retail_dev.silver.inventory"))

Fixes from testing

Rejects were logged again on every run. Because Silver rebuilds from all of Bronze, the bad batch-1 record was re-logged in batches 2 and 3 (verified: 3 copies). Logging only rows whose _batch_id is the current batch records it once. Ties: the original's dedup ordered only by updated_at; ingestion time now breaks ties, so the re-sent C002 can't win. Normalization: IDs are upper-cased and state is title-cased too, so c001 and C001 are one customer.

One reason column per row records the first failing rule; use the Chapter 18 framework if you need all violations. Validity rules per entity: products need a non-negative price, items a positive quantity and non-negative discount, orders a customer.

Step 7: Implement Delta Lake MERGE

MERGE INTO updates matches and inserts new rows in one transaction. The product dimension (Type 1: overwrite changes) is a clean example:

SQL · sql/03_dim_product.sql
MERGE INTO retail_dev.gold.dim_product AS t
USING retail_dev.silver.products AS s
ON t.product_id = s.product_id
WHEN MATCHED AND (   t.product_name       IS DISTINCT FROM s.product_name
                  OR t.category           IS DISTINCT FROM s.category
                  OR t.current_unit_price IS DISTINCT FROM s.unit_price)
THEN UPDATE SET product_name = s.product_name, category = s.category,
                current_unit_price = s.unit_price, updated_at = s.updated_at
WHEN NOT MATCHED
THEN INSERT (product_id, product_name, category, current_unit_price, updated_at)
     VALUES (s.product_id, s.product_name, s.category, s.unit_price, s.updated_at);

Rules for a safe MERGE

  • One source row per key: the original merged straight from bronze.customers_raw, which holds every delivery. With duplicates Delta fails with DELTA_MULTIPLE_SOURCE_ROW_MATCHING_TARGET_ROW_IN_MERGE. Merge from deduplicated Silver.
  • Update only when something changed (IS DISTINCT FROM, the null-safe comparison, equivalent to NOT (a <=> b)).
  • Decide how deletes arrive.
  • Make it safe to retry.

Step 8: Implement SCD Type 2 for Customer History

SQL · sql/02_dim_customer_scd2.sql
-- Step A: close the current version of customers whose tracked attributes changed.
-- The timestamp guard stops an older, replayed record from overriding a newer version.
MERGE INTO retail_dev.gold.dim_customer AS t
USING retail_dev.silver.customers AS s
ON t.customer_id = s.customer_id AND t.is_current = TRUE
WHEN MATCHED
  AND s.updated_at > t.source_updated_at
  AND (   t.customer_name    IS DISTINCT FROM s.customer_name
       OR t.email            IS DISTINCT FROM s.email
       OR t.city             IS DISTINCT FROM s.city
       OR t.state            IS DISTINCT FROM s.state
       OR t.customer_segment IS DISTINCT FROM s.customer_segment)
THEN UPDATE SET is_current = FALSE, effective_to = s.updated_at;

-- Step B: insert a current version for every customer that has none:
-- brand-new customers and the ones just closed in step A.
-- A customer's FIRST version is valid from 1900-01-01 so that orders placed
-- before the customer record reached us still find a matching version.
INSERT INTO retail_dev.gold.dim_customer
    (customer_id, customer_name, email, city, state, customer_segment,
     effective_from, effective_to, is_current, source_updated_at)
SELECT s.customer_id, s.customer_name, s.email, s.city, s.state, s.customer_segment,
       CASE WHEN known.customer_id IS NULL
            THEN TIMESTAMP '1900-01-01 00:00:00'          -- first version ever
            ELSE s.updated_at END,                         -- a change
       CAST(NULL AS TIMESTAMP), TRUE, s.updated_at
FROM retail_dev.silver.customers AS s
LEFT JOIN (SELECT DISTINCT customer_id FROM retail_dev.gold.dim_customer) AS known
       ON known.customer_id = s.customer_id
WHERE NOT EXISTS (SELECT 1 FROM retail_dev.gold.dim_customer d
                  WHERE d.customer_id = s.customer_id AND d.is_current = TRUE);

The original's first versions started at load time

The original gave a new customer effective_from = updated_at, and its sample data set updated_at to the load time. Any order placed before the load then matches no version, so a point-in-time fact join silently drops it. Tested with one customer loaded today and an order from 1 October: 0 fact rows with the original rule, 1 with the fix. A customer's first version now starts at 1900-01-01. (Chapter 17 found the same bug.)

Other improvements, all tested

  • Replay guard: step A only closes a version if the incoming record is newer. C002 re-sent with an old timestamp changed nothing.
  • Simpler step B: insert wherever a customer has no current version (new customers and those closed in step A), instead of comparing every attribute again.
  • Retry-safe: if step B fails after step A, rerunning inserts the missing versions. Running Gold twice more after batch 2 changed nothing (5 versions, 5 facts, 163,500.00 before and after).

Still to handle in production

  • Several changes for one customer in one batch (process them in order).
  • Late changes older than the current version.
  • Deleted or deactivated customers.
  • Equal timestamps (tie-breakers).
  • Concurrent writers.

Lakeflow Declarative Pipelines' AUTO CDC (STORED AS SCD TYPE 2) handles ordering and late data for you once the pattern is understood.

Fact grain: one row per order item. The grain decides correct aggregation and joins.

Business rule: sales are items of COMPLETED orders (others recognize revenue at shipment, invoice, or payment; document your choice). The fact MERGE finds, for each order, the customer version valid on the order date, and keeps the fact in sync as orders complete or are cancelled:

SQL · sql/04_fact_sales.sql
MERGE INTO retail_dev.gold.fact_sales AS t
USING (
    SELECT oi.order_item_id, oi.order_id, o.order_date, c.customer_key, oi.product_id,
           oi.quantity, oi.unit_price, oi.discount_amount,
           CAST(oi.quantity * oi.unit_price - oi.discount_amount AS DECIMAL(14,2)) AS sales_amount
    FROM retail_dev.silver.order_items AS oi
    JOIN retail_dev.silver.orders AS o
      ON o.order_id = oi.order_id
    JOIN retail_dev.gold.dim_customer AS c                      -- the version valid on the order date
      ON  c.customer_id = o.customer_id
      AND CAST(o.order_date AS TIMESTAMP) >= c.effective_from
      AND (c.effective_to IS NULL OR CAST(o.order_date AS TIMESTAMP) < c.effective_to)
    WHERE o.order_status = 'COMPLETED'                          -- business rule: sales = completed orders
) AS s
ON t.order_item_id = s.order_item_id
WHEN MATCHED AND (   t.quantity        IS DISTINCT FROM s.quantity
                  OR t.unit_price      IS DISTINCT FROM s.unit_price
                  OR t.discount_amount IS DISTINCT FROM s.discount_amount
                  OR t.customer_key    IS DISTINCT FROM s.customer_key)
THEN UPDATE SET quantity = s.quantity, unit_price = s.unit_price,
                discount_amount = s.discount_amount, sales_amount = s.sales_amount,
                customer_key = s.customer_key
WHEN NOT MATCHED
THEN INSERT (order_item_id, order_id, order_date, customer_key, product_id,
             quantity, unit_price, discount_amount, sales_amount)
     VALUES (s.order_item_id, s.order_id, s.order_date, s.customer_key, s.product_id,
             s.quantity, s.unit_price, s.discount_amount, s.sales_amount)
WHEN NOT MATCHED BY SOURCE                                      -- e.g. order later cancelled
THEN DELETE;

SQL · sql/07_reconciliation.sql
-- Financial reconciliation: completed-order sales in Silver vs the fact table
WITH expected AS (
    SELECT SUM(oi.quantity * oi.unit_price - oi.discount_amount) AS amount
    FROM retail_dev.silver.order_items AS oi
    JOIN retail_dev.silver.orders AS o ON o.order_id = oi.order_id
    WHERE o.order_status = 'COMPLETED'
),
actual AS (SELECT SUM(sales_amount) AS amount FROM retail_dev.gold.fact_sales)
SELECT e.amount AS silver_sales, a.amount AS fact_sales, e.amount - a.amount AS difference
FROM expected AS e CROSS JOIN actual AS a;

-- Payment reconciliation: aggregate payments to the ORDER grain before comparing
WITH paid AS (
    SELECT order_id,
           SUM(CASE WHEN payment_status IN ('SUCCESS', 'REFUND') THEN amount ELSE 0 END) AS net_paid
    FROM retail_dev.silver.payments
    GROUP BY order_id
),
sold AS (
    SELECT order_id, SUM(sales_amount) AS sales
    FROM retail_dev.gold.fact_sales
    GROUP BY order_id
)
SELECT s.order_id, s.sales, COALESCE(p.net_paid, 0) AS net_paid,
       s.sales - COALESCE(p.net_paid, 0) AS outstanding
FROM sold AS s
LEFT JOIN paid AS p ON p.order_id = s.order_id
ORDER BY s.order_id;

# job (blocking publication) if a CRITICAL check fails. WARNING checks are
# recorded and alerted on but don't stop the run.
from datetime import datetime, timezone

BATCH_ID = dbutils.widgets.get("batch_id") if "dbutils" in globals() else BATCH_ID   # noqa: F821
SQL_DIR = "../sql" if "dbutils" in globals() else SQL_DIR                             # noqa: F821

    "SILVER_DUPLICATE_CUSTOMER_IDS": "CRITICAL",
    "ORDERS_WITHOUT_CUSTOMER": "WARNING",          # customers can arrive late; held back, not lost
    "ITEMS_WITHOUT_PRODUCT": "WARNING",
    "CUSTOMERS_WITH_MULTIPLE_CURRENT_VERSIONS": "CRITICAL",
    "FACT_DUPLICATE_ORDER_ITEMS": "CRITICAL",
    "NEGATIVE_STOCK": "WARNING",
    "SALES_RECONCILIATION_UNEXPLAINED": "CRITICAL",
}


def statements(path):
    text = open(path).read()
    return [s for s in text.split(";") if any(l.strip() and not l.strip().startswith("--") for l in s.splitlines())]


results = [(r.check_name, int(r.failures)) for r in spark.sql(statements(f"{SQL_DIR}/06_quality_checks.sql")[0]).collect()]

# Reconciliation: any difference must be explained by orders held back for a missing customer
recon = spark.sql(statements(f"{SQL_DIR}/07_reconciliation.sql")[0]).first()
held_back = spark.sql("""
    SELECT COALESCE(SUM(oi.quantity * oi.unit_price - oi.discount_amount), 0) AS amount
    FROM retail_dev.silver.order_items oi
    JOIN retail_dev.silver.orders o ON o.order_id = oi.order_id
    WHERE o.order_status = 'COMPLETED'
      AND NOT EXISTS (SELECT 1 FROM retail_dev.gold.dim_customer c WHERE c.customer_id = o.customer_id)
""").first().amount
unexplained = (recon.difference or 0) - held_back
results.append(("SALES_RECONCILIATION_UNEXPLAINED", int(unexplained != 0)))

now = datetime.now(timezone.utc)
rows = [(BATCH_ID, name, SEVERITY.get(name, "CRITICAL"), failures,
         "PASS" if failures == 0 else ("FAIL" if SEVERITY.get(name, "CRITICAL") == "CRITICAL" else "WARN"), now)
        for name, failures in results]
(spark.createDataFrame(rows, "batch_id STRING, check_name STRING, severity STRING, failures BIGINT, status STRING, checked_at TIMESTAMP")
      .write.mode("append").saveAsTable("retail_dev.ops.validation_audit"))

for r in rows:
    print(f"{r[1]:<42} {r[2]:<8} failures={r[3]:<3} {r[4]}")
print(f"sales: silver={recon.silver_sales} fact={recon.fact_sales} "
      f"held back for missing customers={held_back} unexplained={unexplained}")

failed = [r[1] for r in rows if r[4] == "FAIL"]
if failed:
    raise RuntimeError(f"Critical quality checks failed for {BATCH_ID}: {failed}")

SQL
DESCRIBE HISTORY retail_dev.gold.fact_sales;
SELECT * FROM retail_dev.gold.fact_sales VERSION AS OF 5;     -- inspect
RESTORE TABLE retail_dev.gold.fact_sales TO VERSION AS OF 5;  -- roll back

Time travel isn't a backup: it's limited by log and file retention and VACUUM, and doesn't survive storage loss or table replacement. Define retention, backups, RPO/RTO, and rebuild procedures. Here, Bronze is the true safety net: keep its retention long enough to rebuild everything downstream.
