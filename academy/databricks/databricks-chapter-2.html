Databricks Architecture

In Chapter 1 you learned what Databricks is and how it compares with Spark, Fabric, and Synapse. This chapter shows how Databricks actually works behind the scenes, from the workspace and control plane down to drivers, executors, stages, and partitions.

By the end of this lesson you should be able to explain
  • How a Databricks workspace is organized.
  • What the control plane and compute plane do.
  • How compute processes data stored in cloud storage.
  • The differences between all-purpose, job, serverless, and SQL compute.
  • How Databricks interacts with ADLS Gen2, Amazon S3, and Google Cloud Storage.
  • The roles of drivers, executors, jobs, stages, tasks, and partitions.
  • What happens when you execute a SQL query or PySpark notebook.

Most examples use Azure Databricks because it relates closely to Azure Data Factory, Azure Synapse Analytics, and Azure Data Lake Storage.

2.1Core Architecture

2.1.1What Is a Databricks Workspace?

Simple definition

A Databricks workspace is an environment where you develop, execute, manage, and monitor data engineering and analytics workloads. Think of it as your working environment for Databricks. When you log in, you typically interact with a workspace containing notebooks, queries, jobs, pipelines, and other resources.

Example: you work for a retail company and need to read customer data from SQL Server, load it into a Delta table, clean it with PySpark, create a Gold table for reporting, schedule the pipeline daily, and monitor execution. You can develop and manage much of this work through a Databricks workspace.

What does a workspace contain?

Remember

A workspace is not the same thing as a cloud storage account or a cluster. A workspace is where you manage your work. Compute executes it, and storage holds the data.

2.1.2What Is the Control Plane?

Simple definition

The control plane manages the Databricks environment and coordinates operations such as workspace interfaces, job orchestration, and compute management. Think of it as the management layer of the platform. When you click a notebook, submit a job, or configure compute, you interact with control-plane services.

Example: you open a notebook called load_customers, write the code below, and click Run.

Python
df = spark.read.table("main.bronze.customers")

display(df)

The platform needs to coordinate several activities:

  1. Receive your execution request.
  2. Validate access and execution permissions.
  3. Determine the configured compute resource.
  4. Submit or coordinate the work.
  5. Track execution status.
  6. Return results to the notebook interface.
Note

The control plane does not itself perform every data-processing operation. The actual execution takes place in the appropriate compute environment.

What does the control plane manage?

  • Workspace interfaces and APIs.
  • Job and workflow management.
  • Compute provisioning and management.
  • Access to workspace resources.
  • Execution coordination.
  • Operational metadata and status.

The precise division of responsibilities depends on the cloud and compute architecture.

Real-world analogy: an airport

The control tower coordinates aircraft movements, aircraft engines provide the power to move, and the airport's fuel storage holds fuel.

AirportDatabricks
Control towerControl plane
Aircraft enginesCompute resources
Fuel storageData storage
Flight operationsData processing jobs

This is an analogy to help you remember the concepts, not an exact technical mapping.

2.1.3What Is the Compute Plane?

Simple definition

The compute plane is where data-processing workloads execute. When you run a PySpark transformation that joins two large datasets, compute resources perform the actual processing. Depending on the workload, compute may be provisioned in a classic architecture or provided through serverless infrastructure.

Example: with two tables, main.silver.customers and main.silver.orders, you execute:

SQL
SELECT
    c.customer_id,
    c.customer_name,
    COUNT(o.order_id) AS total_orders
FROM main.silver.customers AS c
LEFT JOIN main.silver.orders AS o
    ON c.customer_id = o.customer_id
GROUP BY
    c.customer_id,
    c.customer_name;

The compute environment reads the required data, performs the join, aggregates the results, and returns the output.

What does the compute plane contain?

Depending on the architecture: driver processes, worker nodes, Spark executors, SQL execution engines, CPU and memory, temporary processing resources, and network connections to data sources.

Not every workload uses the same execution architecture. SQL warehouses and serverless compute have platform-specific implementation details.

2.1.6Storage and Compute Separation

This is one of the most important concepts in modern cloud data engineering.

What it means

Data can remain in persistent storage while processing resources are provisioned, scaled, or terminated independently. In a typical Databricks lakehouse, the data stays in cloud object storage while compute processes it.

Example: 2 TB of sales data sits in ADLS Gen2, and two separate compute resources work on it.

          ADLS GEN2
       2 TB SALES DATA
              |
              |
      +-------+-------+
      |               |
      v               v
  Compute A        Compute B
  Daily ETL        Data Analysis
      |               |
      v               v
  Process Data     Query Data

Both workloads can access the same underlying data, subject to permissions and the table's concurrency capabilities. The data does not need to be copied into a separate permanent store just because a different compute resource is used.

What happens when compute stops?

  • The persistent data remains in cloud storage.
  • The compute resource stops consuming resources once terminated.
  • The data can be processed again later.
  • Another authorized compute resource can access the data.
Watch out

Temporary processing state, local disks, cached data, and other transient resources may not survive termination.

Benefits

BenefitWhat it means
1. Independent scalingStorage capacity and processing capacity can be managed separately.
2. Better resource utilizationYou do not need to keep every processing resource running continuously.
3. Workload flexibilityDifferent compute resources can process the same governed data.
4. Potential cost savingsCompute can be stopped when not needed, although storage and other services may still incur charges.
5. Persistent dataTerminating compute does not normally delete the underlying persistent tables.
Important clarification

Separation does not mean no data is transferred during processing. Spark must still read data from storage, move intermediate results between tasks when necessary, and write results back to storage.

2.1.7How a Databricks Job Executes

Now let's connect the concepts. Your company runs a daily pipeline that must read source data, remove duplicates, calculate total sales by product, and write the result to a Delta table.

Step 1: Create the notebook

Python
sales_df = spark.read.table("main.bronze.sales")

clean_sales_df = sales_df.dropDuplicates()

product_sales_df = (
    clean_sales_df
    .groupBy("product_id")
    .sum("sales_amount")
)

(
    product_sales_df.write
    .format("delta")
    .mode("overwrite")
    .saveAsTable("main.gold.product_sales")
)

This assumes the source and target tables exist or can be created, the data types are suitable, and the required privileges are available.

Production note

overwrite replaces the target table's data. Production pipelines often use incremental processing or MERGE INTO instead.

Steps 2–8: From job to result

  1. Configure a job that executes the notebook: task type, compute selection, parameters, schedule, retry policy, and notifications.
  2. Start the job manually or on schedule. The control plane coordinates execution and the selected compute is made available.
  3. Initialize execution. For a classic Spark workload, the driver coordinates the application, obtains information about the data, and plans the computation.
  4. Read data from the Bronze Delta table. How much is read depends on the query, file layout, partition pruning, and other optimizations.
  5. Process data: remove duplicates, group by product, calculate totals. Some operations may shuffle data between tasks.
  6. Write the results to the Gold Delta table.
  7. Record status. If the job fails, inspect the failure details, fix the issue, and rerun or repair the workflow.

2.2Compute Concepts

2.2.1What Is Compute?

In cloud computing, compute refers to the processing resources used to execute applications and workloads: CPU, memory, processing engines, network resources, and temporary storage. In Databricks, compute processes your SQL, PySpark, and other supported workloads.

Persistent Storage
100 Million Records
         |
         v
   Databricks Compute
         |
         v
Read / Filter / Join / Aggregate
         |
         v
   Sales Summary Table

If compute is insufficient

  • Slow query execution.
  • Long processing times.
  • Memory errors.
  • Excessive task failures.
  • Poor resource utilization.
Remember

More compute does not automatically solve every problem. Inefficient joins, data skew, unnecessary shuffles, and poor file layouts can also cause performance issues.

2.2.2Compute Resources and Their Purpose

Compute optionPrimary purpose
All-purpose (interactive) computeDevelopment, exploration, and interactive workloads
Job computeScheduled or automated jobs
Serverless computeManaged execution for supported workloads
SQL warehouseSQL analytics, dashboards, and BI queries

The exact choices and terminology depend on your workspace, cloud, and product configuration.

Example: you have three tasks. Task A, experimenting with PySpark code, needs an interactive environment. Task B, a daily ETL pipeline at 2:00 AM, needs compute suited to automation. Task C, letting 50 analysts run SQL, needs a suitable SQL warehouse. Using one compute configuration for all three may be inefficient.

2.2.3All-Purpose Compute

All-purpose compute, commonly called interactive compute, is intended for interactive development and exploration: notebook development, testing PySpark code, exploring data, debugging transformations, interactive analysis, and collaborating with other developers.

Python
df = spark.read.table("main.bronze.customers")

display(df.limit(100))

You inspect the output and modify the code several times. Interactive compute lets you run cells repeatedly while developing.

Advantages

  • Convenient for development.
  • Supports iterative experimentation.
  • Useful for troubleshooting.
  • Supports interactive data exploration.

Disadvantages

  • Running compute unnecessarily can increase costs.
  • Long-running interactive resources may be underutilized.
  • May not be the best choice for production jobs.
Best practice

Use interactive compute for development, and evaluate job-specific compute or serverless options for production workloads.

2.2.4Job Compute

Job compute is intended for automated workloads such as scheduled ETL jobs and production pipelines. For example, your company loads sales data every day at 2:00 AM:

Daily Sales Pipeline
        |
        v
Load Bronze
        |
        v
Clean Silver
        |
        v
Aggregate Gold
        |
        v
Validate Results

Why job-specific compute?

  • Compute can be associated with automated workloads.
  • Job execution can be monitored independently.
  • Resources can be configured for the workload.
  • Compute lifecycle can be managed around execution.

Depending on the platform configuration, the job may use dedicated job compute or serverless compute.

Important distinction

Do not assume every Databricks job automatically creates a new cluster. Execution depends on the selected compute configuration, and job tasks can use different compute options.

2.2.5Serverless Compute

Serverless compute lets Databricks manage much of the underlying compute provisioning and infrastructure lifecycle for supported workloads. You focus more on the workload and less on configuring infrastructure. Depending on the service, the platform can manage provisioning, scaling, and other operational aspects.

Advantages

  • Less infrastructure management.
  • Faster access to compute in supported configurations.
  • Managed scaling for supported workloads.
  • Simpler operational experience.

Limitations and considerations

  • Availability depends on cloud, region, workspace configuration, and workload type.
  • Not every classic compute option is available in serverless.
  • Networking and data access requirements still matter.
  • Pricing and performance must be evaluated.
Is serverless always cheaper?

No. It may reduce operational overhead and improve utilization, but the most cost-effective option depends on workload duration, consumption, configuration, and pricing.

2.2.6SQL Warehouses

A SQL warehouse provides compute optimized for SQL analytics and supported BI workloads. It is a central component of Databricks SQL. A business analyst querying the Gold table main.gold.daily_sales might run:

SQL
SELECT
    sales_date,
    SUM(total_sales) AS revenue
FROM main.gold.daily_sales
GROUP BY sales_date
ORDER BY sales_date;

The SQL warehouse executes the query, and results appear in the SQL editor or a supported BI client. Common uses: SQL queries, dashboards, business intelligence, ad hoc analysis, Power BI connectivity, and concurrent analytical queries.

2.2.7Classic versus Serverless Compute

Classic compute runs in the customer-managed cloud environment according to the Databricks deployment model; you generally have more responsibility for configuring compute and networking. With serverless compute, Databricks manages more of the infrastructure and compute lifecycle for supported workloads.

2.2.8Selecting Compute for Different Workloads

ScenarioPossible starting choiceReason

How should you size compute?

Start with these questions:

  • How much data will be processed?
  • Is the workload CPU-intensive or memory-intensive?
  • Does it require a distributed Spark job?
  • How frequently does it run?
  • What is the expected execution time?
  • Does it have strict latency requirements?
  • What is the budget?
  • Does it require special networking or libraries?
Rule of thumb

Start with a reasonable configuration, measure performance, and optimize based on actual results. Avoid choosing the largest configuration without evidence the workload needs it.

2.3Storage Architecture

2.3.1What Is Cloud Object Storage?

Cloud object storage stores data as objects, each commonly consisting of data, metadata, and a key or identifier. Examples include Azure Blob Storage and ADLS Gen2, Amazon S3, and Google Cloud Storage. Object storage is widely used for data lakes and lakehouses because it can hold large amounts of data in many formats.

             |

Why is object storage useful?

  • Stores large amounts of data.
  • Supports many file formats.
  • Storage and compute managed separately.
  • Integrates with cloud data platforms.
  • Can underpin Delta tables.

Object storage itself does not provide all the table-management features of a lakehouse. Table formats and platform services add those capabilities.

2.3.5Data Stored in Cloud Storage versus Data Processed by Compute

Suppose a company has 500 GB of sales data in ADLS Gen2 and starts a Databricks job to calculate sales by product.

What is stored?

The persistent data files remain in cloud storage.

What is processed?

Compute reads the necessary files and performs the calculations.

Where do results go?

Back to cloud storage, for example as a Delta table.

When the job completes?

Compute may be terminated or returned to an available state; persistent data remains and can be processed again later.

What about caching?

Spark may cache data in memory or on disk to improve performance. Cached data is not the same as the persistent source data, and you should not assume it survives compute termination.

2.3.6Managed Tables versus External Tables

Databricks tables are logical objects registered in the metastore and associated with underlying data. The key distinction is whether Databricks manages the storage lifecycle or the table points to an externally specified location.

Managed table

Databricks manages the storage location and lifecycle according to catalog and table rules. You do not specify a storage location:

SQL
CREATE TABLE main.sales.customers (
    customer_id BIGINT,
    customer_name STRING,
    city STRING
);

External table

Associated with a specified storage location whose lifecycle is managed externally:

SQL
CREATE TABLE main.sales.external_customers (
    customer_id BIGINT,
    customer_name STRING,
    city STRING
)
USING DELTA
LOCATION 'abfss://curated@retailstorage.dfs.core.windows.net/customers/';

Assumes the location exists or can be initialized, permissions are configured, and the location contains compatible data or is suitable for a new table.

FeatureManaged tableExternal table
Storage locationManaged by DatabricksExplicitly associated with an external location
Data lifecycleGoverned by managed-table rulesStorage lifecycle managed externally
Table metadataManaged by the catalogRegistered in the catalog
Storage administrationMore platform-managedRequires coordination with external storage management
Common use caseData primarily managed through DatabricksData that must remain at a controlled external location
What happens when you drop a table?

Dropping a managed table can remove its underlying data according to retention and lifecycle rules. Dropping an external table generally removes only its catalog registration, leaving the files in place. Always verify the lifecycle implications before dropping production tables.

Use managed tables when Databricks should manage the storage lifecycle. Use external tables when data must stay at a specific external location or external storage management is part of your architecture. In Unity Catalog, implement both with appropriate governance and storage configuration.

2.4Processing Architecture

How Spark processes data internally. This section is especially important for interviews and for troubleshooting slow pipelines.

2.4.1Driver Node

Simple definition

The driver coordinates the execution of a Spark application. It maintains application information, plans execution, schedules tasks, and coordinates work with executors.

Python
df = spark.read.table("main.bronze.sales")

result = (
    df.groupBy("product_id")
      .sum("sales_amount")
)

display(result)

For this code, the driver helps determine what operations must be performed, how the execution plan is organized, which tasks need to run, how task execution is coordinated, and how results and status are handled.

Important clarification

The driver does not necessarily perform all the data processing itself. In a distributed workload, executors process partitions in parallel while the driver coordinates.

If the driver fails, the Spark application can be interrupted. The effect on the overall job depends on compute configuration, recovery capabilities, and the workload. Monitor driver failures in production and investigate their causes.

2.4.2Worker Nodes

Simple definition

Worker nodes are compute nodes that provide resources for distributed processing. In a classic Spark architecture, worker nodes host executor processes.

               DRIVER
                 |
        +--------+--------+
        |        |        |
        v        v        v
     Worker 1 Worker 2 Worker 3
        |
        v
     Worker 4

What do workers do?

  • Process data partitions.
  • Run tasks.
  • Perform joins and aggregations.
  • Execute transformations.
  • Manage intermediate processing data.

One driver and four workers; the actual scheduling topology is more complex.

Do all workloads require worker nodes? No. Some SQL and serverless workloads abstract away the underlying worker infrastructure, so you may never manage workers directly.

2.4.3Executors

Simple definition

An executor is a process that runs tasks and manages processing resources for a Spark application. Executors typically run on worker nodes in a classic Spark cluster.

Suppose Spark divides a dataset into 20 partitions. Tasks are scheduled to process them, and executors run those tasks using available CPU and memory.

               DRIVER
                  |
           Task Scheduling
                  |
        +---------+---------+
        |                   |
        v                   v
    Executor 1          Executor 2
        |                   |
    Partitions           Partitions

Illustrative. Executor, partition, and task counts are configured or determined by the execution plan and runtime.

2.4.4Tasks

Simple definition

A task is a unit of work that Spark executes on a partition. For many common operations, a stage has one task per partition.

Task metrics help you find

  • Slow partitions.
  • Data skew.
  • Executor failures.
  • Excessive processing overhead.
  • Uneven workload distribution.

If one task processes far more data than the others, the whole stage may take longer than expected.

2.4.5Jobs

In Spark, a job is a unit of execution triggered by an action or another execution request.

Python
df = spark.read.table("main.bronze.sales")

df.count()

count() requires Spark to compute the number of records, which can trigger a Spark job. Common actions include count(), collect(), show(), writing a DataFrame, and displaying a DataFrame in an environment that triggers evaluation. Some actions trigger more than one job.

Databricks Job versus Spark job

This distinction is critical.

A Databricks Job can contain multiple tasks, and a single notebook task can execute multiple Spark jobs.

2.4.6Stages

Simple definition

A stage is a group of Spark tasks that can execute without crossing a shuffle boundary. Spark commonly splits a job into multiple stages when data must be redistributed between tasks.

2.4.7Partitions

Simple definition

A partition is a logical division of a dataset used to distribute processing work, allowing Spark to process different parts of a dataset independently.

       100 Million Records

     ...         ...         ...

The number of partitions depends on the source data, execution plan, configuration, and transformations.

Too few partitions

  • May limit parallelism.
  • May create large tasks.
  • Can cause uneven resource utilization.

Too many partitions

  • Excessive task overhead.
  • Increased scheduling overhead.
  • Many small output files.

Repartition versus coalesce

Python
# Redistributes data; generally causes a shuffle
df_repartitioned = df.repartition(20)

# Reduces partitions, usually avoiding a full shuffle
df_coalesced = df.coalesce(5)
Use carefully

Changing partition counts does not automatically improve performance. The right count depends on the workload and available compute.

2.4.8Distributed Processing

Distributed processing divides work across multiple processing resources. With 500 million sales records, a single machine may be too slow; Spark splits the dataset into partitions and executes tasks across executors.

Advantages

  • Work divided across resources.
  • Large datasets processed in parallel.
  • Compute capacity chosen per workload.
  • Independent tasks run concurrently.

Limitations

Distribution adds overhead. For small datasets Spark may be slower than a local tool because it must plan and coordinate execution. For large workloads, performance depends on partitioning, data layout, compute, and transformation design.

2.4.9Parallel Execution

Parallel execution means multiple tasks run simultaneously. If a stage has 100 independent tasks and the compute has enough capacity, many of them can run at once.

  • Partitioning divides the dataset into logical units.
  • Tasks process partitions during a stage.
  • Parallelism describes how much work can execute simultaneously.
Example

100 partitions does not mean 100 tasks run at the same moment. If the compute can run only 10 tasks concurrently, Spark runs roughly 10 at a time and the rest wait for free resources.

Putting It All Together: How Spark Executes a Query

You run this PySpark code against a table with 100 million sales records:

Python
sales_df = spark.read.table("main.bronze.sales")

result_df = (
    sales_df
    .filter("sales_amount > 1000")
    .groupBy("product_id")
    .sum("sales_amount")
)

display(result_df)
  1. Notebook submits the request. The platform coordinates it with the selected compute.
  2. Driver plans execution and builds or uses an optimized execution plan.
  3. Spark reads the data from storage. Predicate pushdown and data skipping can reduce the files read.
  4. Data is processed in partitions. The filter removes rows where sales_amount is not above 1,000.
  5. Aggregation is performed per product, which may require a shuffle to bring each product's records together.
  6. Executors process tasks on partitions according to the plan.
  7. Results are returned to the notebook display.

Objective: understand how Databricks reads data from storage, processes it through Spark, and produces results.

Step 1: Create a sample table

If you have a workspace and permission to create tables in the schema, run:

Scenario 1: Slow pipeline

Your Databricks job takes three hours to process a large sales table. What would you investigate?

  • Stage and task durations.
  • Shuffle metrics.

  • Partition counts.

Scenario 2: Job completed, data remains

You terminate a compute resource after a successful ETL run. Does the Delta table disappear? In a normal persistent table setup, no. Terminating compute does not itself delete the underlying persistent table data.

A notebook fails because it cannot access an ADLS Gen2 path. What would you investigate?

  • DNS and network connectivity.
