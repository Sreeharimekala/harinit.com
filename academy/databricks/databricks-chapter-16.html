Streaming Fundamentals

16.1.1What Is Data Streaming?

Streaming is the continuous processing of data as new records become available, instead of waiting for a complete dataset.

ScenarioStreaming application
E-commerceCalculate sales as orders arrive
BankingDetect possibly fraudulent transactions
IoTMonitor equipment temperature
RetailTrack inventory changes
LogisticsTrack vehicle locations
Web analyticsCount visits as they happen
Data engineeringProcess files as they land

One million orders a day

Batch: collect all day → run at midnight → update reports → available next morning.

Streaming: receive orders as created → process continuously → update aggregates as data arrives → available within seconds or minutes.

Streaming doesn't mean every record is instant. Latency depends on the source, trigger, workload, and capacity.

16.1.2Batch Versus Streaming

RecoveryRerun the failed batchResume from checkpoints and source offsets
Typical useDaily warehouse loadsFraud detection, live monitoring

16.1.3What Is Real-Time Processing?

"Real-time" means fast enough for the business requirement. There's no single threshold: fraud detection needs seconds, an operations dashboard tolerates a minute, IoT alerting may need sub-second, and a sales dashboard is fine every few minutes.

PatternHow it works
BatchA defined dataset at scheduled intervals
Micro-batchSmall batches of new data, repeatedly. The standard Structured Streaming model.
Continuous / real-time modeLower-latency execution models with specific limitations; not interchangeable with every micro-batch feature

Each micro-batch is a separate, small execution of the same computation. That gives incremental processing, low latency without per-record tasks, support for stateful operations, and progress recorded in checkpoints after every batch.

Interval trade-off: shorter intervals lower latency but add scheduling overhead; longer intervals are more efficient but delay results. Choose by latency and throughput needs.

16.1.6What Is a Streaming DataFrame?

A streaming DataFrame represents data arriving over time rather than a fixed dataset. Create one with spark.readStream:

Python
sales_stream = (
    spark.readStream
    .format("json")
    .option("maxFilesPerTrigger", 10)          # at most 10 new files per micro-batch
    .schema("""
        order_id STRING,
        store_id STRING,
        product_id STRING,
        quantity INT,
        sales_amount DOUBLE,
        event_time TIMESTAMP
    """)
    .load("/Volumes/retail_dev/streaming_lab/landing/sales/")
)

print(sales_stream.isStreaming)                                    # True
print(spark.read.table("retail_dev.sales.orders").isStreaming)     # False

filtered_sales = (

Lazy until you write

Defining a streaming DataFrame starts nothing. The query begins when you call a streaming write (writeStream … .toTable() / .start()). Streaming file sources need an explicit schema.

16.1.7Streaming Execution

Query lifecycle

  1. Define the source.
  2. Apply transformations.
  3. Configure the sink.
  4. Set a checkpoint location.
  5. Configure the trigger.
  6. Start the query.
  7. Monitor it.
  8. Stop it when required.
Python
query = (
    filtered_sales.writeStream
    .format("delta")
    .outputMode("append")
    .option("checkpointLocation",
            "/Volumes/retail_dev/streaming_lab/checkpoints/sales_raw/")
    .trigger(processingTime="30 seconds")   # classic compute
    .toTable("retail_dev.streaming_lab.sales_raw")
)

query.awaitTermination()   # block the cell until the query ends
query.stop()               # stop it deliberately

The query checks for new data about every 30 seconds; a slow batch delays the next. Interactively, skip awaitTermination() so you can inspect status. In production, run long-lived streams as jobs or pipelines, not notebook cells left open.

16.2.3What Is a Streaming Query?

The running computation that reads new data, transforms it, and writes results.

Python
query = (
    sales_stream.filter("sales_amount > 0")
    .writeStream
    .format("delta")
    .outputMode("append")
    .option("checkpointLocation",
            "/Volumes/retail_dev/streaming_lab/checkpoints/valid_sales/")
    .queryName("valid_sales")                 # optional, shows in the UI
    .toTable("retail_dev.streaming_lab.valid_sales")
)

print(query.id, query.name, query.isActive)

progress = query.lastProgress     # dict for the most recent micro-batch
if progress:
    print(progress)

Progress includes batch ID, input and processed rows per second, batch duration, source offsets, and state metrics.

Active ≠ healthy

A query can be active while no data flows. Monitor freshness and row counts, not just status.

Interview: can append mode be used with every streaming aggregation?
No. Append only emits rows that will never change. A windowed aggregation with a watermark can emit each window once it's final. A running groupBy("store_id") total is never final, so it needs update or complete mode.

An omitted trigger isn't a fixed interval: the next micro-batch starts immediately when data is waiting.

16.2.6Checkpointing

A checkpoint stores source offsets, completed-batch metadata, and operator state, everything needed to resume exactly where the query left off.

Best practices

  1. Durable storage (a volume or cloud path).
  2. One checkpoint per query.
  3. Never delete production checkpoints as routine troubleshooting.
  4. Keep paths stable across restarts.
  5. Understand source retention and sink behavior.
  6. Treat changes to stateful logic as checkpoint-compatibility changes.
  7. Test recovery before production.
Can two queries share one checkpoint?
No. Sharing a checkpoint corrupts progress tracking and makes recovery unreliable. Give every query its own path.
Can I delete a checkpoint to fix an error?
Not without understanding the consequences. A new checkpoint resets progress and state, which can mean reprocessing, duplicates, or lost state. Only do it deliberately, as a planned reset or new query lineage.

16.2.7Stateful Processing

Stateful processing keeps information between micro-batches. A running total per store must remember each store's current total:

EventStoreSalesRunning total
1A₹1,000₹1,000
2A₹2,000₹3,000
3A₹500₹3,500
StatelessStateful
Select columnsGroup by store and sum
Filter recordsCount per store
Rename columnsDeduplicate over time
Cast typesStream-stream joins

Stateful operations: aggregations, windowed aggregations, deduplication, stream-stream joins, session windows, custom state. State grows with every new key unless a watermark allows old state to be dropped.

16.2.8Stream Failure Recovery

Common causes

Cluster termination, network issues, invalid input, schema mismatches, permission errors, source connectivity, sink write failures, memory exhaustion, incompatible checkpoint changes.

Query fails
    |
Identify the error
    |
Check source and sink
    |
Validate checkpoint
    |
Fix the underlying issue
    |
Restart with the SAME checkpoint
    |
Validate completeness and duplicates
Python
try:
    query.awaitTermination()
except Exception as exc:
    print("Streaming query failed:", exc)
    raise            # re-raise so a job marks the run as failed (Chapter 14)

Catching the error doesn't recover the query. In production, use job retries and notifications, and make sure retries are safe for the sink.

Recovery ≠ exactly-once output

Resuming from the right offset doesn't guarantee one copy of every event in an external system. A foreachBatch function might write to an API and fail before Spark records the batch, so the retry writes it again. Sink logic must handle replays (16.3.7).

16.3.1Event Time and Processing Time

OrderEvent timeArrival time
100110:00:0510:00:06
100210:00:1010:00:11
100310:00:0810:00:30

Order 1003 happened at 10:00:08 but arrived 22 seconds late. It belongs in the 10:00–10:01 minute.

Three different clocks

Event created 10:00:05 (event time) → arrives 10:00:10 (arrival time) → Spark processes it at 10:00:15 (processing time).

Event time is when it happened, from the data. Processing time is when Spark handled it.

Python
# If event_time arrives as a string, parse it (mind the source's time zone)
sales_with_event_time = sales_stream.withColumn("event_time", F.to_timestamp("event_time"))
Best practice

Use event time for business aggregations ("sales per 5 minutes") so late arrivals land in the right window. Use processing time only when the requirement is about when the platform handled data.

16.3.2Watermarks

A watermark tells Spark how late data may arrive, which lets it finalize event-time windows and drop old state.

Python
windowed_sales = (
    sales_stream
    .withWatermark("event_time", "10 minutes")
    .groupBy(F.window("event_time", "5 minutes"), "store_id")
    .agg(F.sum("sales_amount").alias("total_sales"))
)

How it's calculated

watermark = max(event_time seen so far) − 10 minutes

A window [10:00, 10:05) is final once the watermark passes 10:05, which needs an event at 10:15 or later. Then append mode writes it and its state is dropped.

What it is not

  • Not a wall-clock wait: Spark doesn't wait 10 minutes per event.
  • Driven by event-time progress: if no newer events arrive, the watermark doesn't move and windows never close.
  • Not a hard guarantee that every event within 10 minutes is counted.

Late events within the threshold update their window while it's still in state; events older than the watermark are dropped from the aggregation.

The #1 streaming surprise

Your windowed aggregation table is empty even though data is flowing. That's expected in append mode until later events push the watermark past each window's end. The project demonstrates this, verified by simulation.

16.3.4Deduplication

Duplicates come from producer retries, upstream resends, double publishing, batch retries, and source replays.

order_idstore_idsales_amount
1001A100
1002A250
1001A100
Python · three approaches
# 1. Unbounded: remembers every order_id forever (state grows without limit)
dedup_1 = sales_stream.dropDuplicates(["order_id"])

# 2. Watermark + event_time in the key: bounded state, but a duplicate
#    that arrives with a DIFFERENT event_time is NOT detected
dedup_2 = (sales_stream.withWatermark("event_time", "30 minutes")
           .dropDuplicates(["order_id", "event_time"]))

# 3. Recommended (Spark 3.5+ / DBR 13.3+): dedupe by ID alone, with
#    state kept only as long as the watermark requires
dedup_3 = (sales_stream.withWatermark("event_time", "30 minutes")
           .dropDuplicatesWithinWatermark(["order_id"]))
Choose the key by business meaning

If order_id uniquely identifies an event, use it. If an order can legitimately have several events (created, shipped…), deduplicating on order_id discards real data; use an event_id. Decide how late duplicates can arrive and set the watermark to match.

Checklist: stable event ID; how late duplicates may arrive; watermark policy; source replay behavior; legitimate updates aren't discarded; test with realistic duplicates. Streaming dedup isn't end-to-end exactly-once on its own.

16.3.5Stateful Operations in More Detail

Python
store_order_counts = sales_stream.groupBy("store_id").count()
# One state entry per store, kept forever
# (no watermark can finalize a running count)

Control state growth

  • Watermarks for event-time operations.
  • Avoid unnecessary grouping keys.
  • Filter irrelevant records early.
  • Monitor state size (stateOperators in progress).
  • Use the RocksDB state store for large state.

Stream-stream joins: matching an orders stream with a payments stream means keeping records from both sides until a match can no longer arrive. Bound this with watermarks on both streams plus an event-time condition:

Python
orders = orders_stream.withWatermark("order_time", "2 hours")
payments = payments_stream.withWatermark("payment_time", "3 hours")

matched = orders.join(
    payments,
    F.expr("""
        orders.order_id = payments.order_id AND
        payment_time BETWEEN order_time AND order_time + INTERVAL 1 HOUR
    """)
)

Assumes the DataFrames are aliased as orders and payments (.alias("orders")).

16.3.6Exactly-Once Processing Considerations

Exactly-once means each event has one logical effect on the result despite retries. Structured Streaming plus a checkpoint does not guarantee this on its own; three parts must work together:

PartQuestion
1. SourceCan it track progress and replay reliably (offsets, files)?
2. ProcessingCan Spark recover computation and state consistently (checkpoint)?
3. SinkCan the destination avoid duplicate effects when a batch is retried?
Source event (order 1001)
        |
Spark processes 1001
        |
Sink writes 1001
        |
FAILURE before batch is
recorded as complete
        |
Spark retries the batch
        |
Plain append -> 1001 written twice

Strategies

  • Source/sink pairs with documented guarantees (e.g. Delta, which is idempotent per batch with checkpoints).
  • Stable business event IDs.
  • Durable checkpoints.
  • Idempotent external writes.
  • foreachBatch + MERGE on the event ID.
  • Test failure scenarios.
Python · retry-safe upsert with foreachBatch
from delta.tables import DeltaTable

def upsert_sales_batch(batch_df, batch_id):
    # A single micro-batch may itself contain the same order twice.
    # Insert-only MERGE would insert BOTH copies, so dedupe first.
    batch_df = batch_df.dropDuplicates(["order_id"])

    target = DeltaTable.forName(batch_df.sparkSession,
                                "retail_dev.streaming_lab.sales_events")
    (
        target.alias("target")
        .merge(batch_df.alias("source"), "target.order_id = source.order_id")
        .whenNotMatchedInsertAll()          # replays of a batch insert nothing new
        .execute()
    )

query = (
    sales_stream.writeStream
    .foreachBatch(upsert_sales_batch)
    .option("checkpointLocation",
            "/Volumes/retail_dev/streaming_lab/checkpoints/sales_merge/")
    .start()
)

I made two fixes to the original: deduplicating within the batch, and batch_df.sparkSession instead of the global spark (required on serverless / Spark Connect). Before production, confirm order_id is unique and stable, the target exists, how updates should apply, concurrent writers, and retry behavior.

Interview: does Structured Streaming guarantee exactly-once?
It provides exactly-once processing semantics for supported source/sink combinations (replayable source + checkpoint + idempotent sink like Delta). End-to-end exactly-once effects in other systems depend on source replay, checkpoint recovery, sink guarantees, and retry-safe write logic. A non-idempotent external write can duplicate on retry.

Kafka considerations

  • Secure authentication and encryption.
  • Partitions sized for throughput.
  • Checkpoints for recovery.
  • Monitor consumer lag and input rates.
  • Malformed-message handling.
  • Topic retention long enough to recover after an outage.

Alert when

  • The query terminates unexpectedly.
  • No data processed for longer than expected.
  • Batch duration consistently exceeds the trigger interval.
  • Input rate exceeds processed rate for a sustained period.
  • State grows unexpectedly.
  • Quality failures exceed a threshold.
  • Freshness breaches the SLA.

An active query with zero input isn't necessarily broken; consider expected arrival patterns.

16.5.2Checkpoint Management

Production checklist

  • Durable, supported storage.
  • Separate path per query.
  • Restricted access.
  • Excluded from routine cleanup.
  • Documented ownership.
  • Restart after cluster failure tested.
  • Compatibility checked before changing stateful logic.
/Volumes/.../checkpoints/
    sales_bronze/
    sales_silver/
    sales_aggregation/
    inventory_events/
    customer_events/

Changing a checkpoint path starts the query with no memory, which risks reprocessing or lost state. Treat it as a controlled migration.

16.5.3Handling Schema Changes

Original:                New:
order_id     STRING      order_id        STRING
store_id     STRING      store_id        STRING
sales_amount DOUBLE      sales_amount    DOUBLE
                         discount_amount DOUBLE

Approach

  1. Detect: is it compatible?
  2. Validate: optional, required, business-critical?
  3. Decide: reject, quarantine, or accept.
  4. Update downstream transformations.
  5. Test with the existing checkpoint and table.

Checklist: are new columns or type changes allowed? Missing required fields? Malformed records? Does the Delta target need mergeSchema? Will SQL or Power BI break? Is a controlled migration needed? With an explicit schema, new fields are simply ignored until you add them.

16.5.4Recovering from Failures

Incident: target table temporarily unavailable

  1. Is the source still receiving data?
  2. Read the query's exception.
  3. Verify the target and permissions.
  4. Find the last successful batch.
  5. Check the checkpoint.
  6. Does the source retain enough data to resume?
  7. Fix the problem.
  8. Restart with the same checkpoint.
  9. Validate for missing or duplicated records.

Principles

  • Fix the root cause before restarting.
  • Preserve checkpoints unless resetting deliberately.
  • Retry only when safe.
  • Confirm source retention.
  • Validate sink idempotency.
  • Record actions and data checks.

A successful restart doesn't prove the output is complete.

16.5.5Throughput Optimization

If the source produces 50,000 records a minute and the pipeline processes 30,000, the backlog grows forever.

Python
# 1. Filter early
valid_sales = sales_stream.filter("sales_amount > 0")

# 2. Keep only needed columns
slim = sales_stream.select("order_id", "store_id",
                           "sales_amount", "event_time")

Also

  1. Avoid unnecessary shuffles.
  2. Optimize joins (broadcast small static tables).
  3. Manage state (keys, watermarks, RocksDB).
  4. Tune triggers and per-batch limits.
  5. Size compute appropriately.
  6. Avoid tiny files in Delta (OPTIMIZE / auto compaction).

Throughput vs latency: bigger batches raise records/sec but delay each record's visibility. Tune to the SLA.

16.5.6Backpressure and Processing Delays

MetricValue
Incoming / min100,000
Processed / min70,000
Backlog growth / min30,000

Symptoms

Growing delays and Kafka lag, longer micro-batches, input rate above processed rate, growing state, worsening freshness.

Troubleshooting sequence

  1. Is the source sending unusual volume?
  2. Check batch durations and rates.
  3. Find slow stages and tasks in the Spark UI.
  4. Look for skew, expensive joins, big shuffles (Chapter 15).
  5. Check executor CPU and memory.
  6. Inspect state-store metrics.
  7. Review source limits (e.g. maxOffsetsPerTrigger, throughput units).
  8. Scale compute or parallelism if justified.
  9. Retest with realistic traffic.

High delay isn't always "too much data". It could be a slow join, inefficient transform, slow sink, network, or too little compute. Find the bottleneck before scaling.

Step 2: The sales event generator

Run this cell to define the generator. It can add a duplicate and an invalid event, shift event times into the future, and writes each file under a hidden temporary name first, so a half-written file is never picked up.

Python · generator
import json, random, time, uuid
from datetime import datetime, timedelta, timezone
from pathlib import Path

landing_dir = Path(landing_path)
landing_dir.mkdir(parents=True, exist_ok=True)

stores = ["STORE_001", "STORE_002", "STORE_003"]
products = ["PROD_101", "PROD_102", "PROD_103", "PROD_104"]


def generate_sales_events(number_of_events=10, minutes_offset=0):
    """Events stamped 'now' (+ optional offset), one second apart."""
    start = datetime.now(timezone.utc) + timedelta(minutes=minutes_offset)
    events = []
    for i in range(number_of_events):
        quantity = random.randint(1, 5)
        unit_price = round(random.uniform(100, 2000), 2)
        events.append({
            "event_id": str(uuid.uuid4()),
            "order_id": str(uuid.uuid4()),
            "store_id": random.choice(stores),
            "product_id": random.choice(products),
            "quantity": quantity,
            "unit_price": unit_price,
            "sales_amount": round(quantity * unit_price, 2),
            "event_time": (start + timedelta(seconds=i)).isoformat(),
        })
    return events


def write_sales_file(number_of_events=10, minutes_offset=0,
                     add_duplicate=False, add_invalid=False):
    events = generate_sales_events(number_of_events, minutes_offset)
    if add_duplicate:                      # same event_id sent twice
        events.append(dict(events[0]))
    if add_invalid:                        # quantity 0 -> fails validation
        events.append({**events[0], "event_id": str(uuid.uuid4()),
                       "quantity": 0, "sales_amount": 0.0})

    file_name = f"sales_{int(time.time() * 1000)}_{uuid.uuid4().hex[:8]}.json"
    tmp_path = landing_dir / f".{file_name}.tmp"       # hidden while writing
    with tmp_path.open("w", encoding="utf-8") as f:
        for event in events:
            f.write(json.dumps(event) + "\n")
    tmp_path.rename(landing_dir / file_name)           # appears complete

    print(f"Created {file_name} with {len(events)} events")
Python · first batch of data
# 10 events + 1 duplicate + 1 invalid (quantity 0)

# 10 more, one minute later

Tested: files contain one JSON object per line with ISO-8601 UTC timestamps, which Spark parses as TIMESTAMP.

16.6.7Step 7: Stream from Bronze and Deduplicate

Python
bronze_stream = spark.readStream.table("retail_dev.streaming_lab.sales_bronze")

deduplicated_sales = (
    bronze_stream

    .dropDuplicatesWithinWatermark(["event_id"])
)

The original used dropDuplicates(["event_id", "event_time"]). That works for exact copies (and gives the same result here), but misses a duplicate resent with a different timestamp. dropDuplicatesWithinWatermark dedupes on the ID alone with bounded state. It needs Spark 3.5+ / DBR 13.3+; on older runtimes use the original form.

windowed_sales = (

Step 10: Where are my results? Advance the watermark

Query the aggregation table now and it's empty. That's correct. All events so far fall within a minute or two, so the watermark (latest event time − 10 minutes) hasn't passed the end of their 5-minute window, and append mode only writes final windows.

Python · send later events, rerun both queries
# 3 events stamped 20 minutes in the future push the watermark forward

print(agg_query.lastProgress["eventTime"])   # watermark has moved ~20 minutes

Verified in simulation: the 20 counted orders are the 20 genuine events. The duplicate was removed and the invalid event never reached Bronze. Depending on the clock, the first 20 events may straddle two 5-minute windows. The +20-minute events stay in state until even later data arrives.

Want live, changing totals instead?

Use outputMode("update") with foreachBatch + MERGE into the target on (window, store_id), so totals refresh every batch and consumers see provisional values. Append mode gives final, immutable rows; choose by what downstream users need.

Chapter 16 · Lesson 16.8

Interview Questions and Answers

Try answering each before revealing the answer.

Q1. What is Structured Streaming?
Spark's stream-processing engine using the DataFrame/SQL model to process continuously arriving data incrementally.
Q2. Batch vs streaming?
Batch processes a bounded dataset; streaming incrementally processes data as it arrives, with low latency.
Q3. What is a micro-batch?
A set of newly available records processed together in one execution cycle of a streaming query.
Q4. What is a streaming DataFrame?
A DataFrame over a streaming source; its transformations run once a streaming query is started.
Q5. Purpose of readStream?
Defines a streaming source such as files, Auto Loader, Delta tables, or Kafka.
Q6. Purpose of writeStream?
Defines the sink, output mode, checkpoint, and trigger; calling start()/toTable() launches the query.
Q7. The three output modes?
Append (new final rows), update (changed rows), complete (whole result). Availability depends on the query and sink.
Q8. What is a checkpoint?
Durable storage of source offsets, batch metadata, and state that lets a query resume after failure.
Q9. Can queries share a checkpoint?
No. Each query needs its own checkpoint location.
Q10. What is event time?
When the event actually occurred, taken from the data.
Q11. What is processing time?
When Spark processes the event or runs the batch.
Q12. What is a watermark?
A moving event-time threshold (max event time − allowed lateness) that lets Spark finalize windows and drop old state; data older than it is ignored by stateful operators.
Q13. Tumbling window?
Fixed-length, non-overlapping event-time windows.
Q14. Sliding window?
Fixed-length windows that overlap because they start every slide interval; an event can fall into several.
Q15. Auto Loader vs Kafka?
Auto Loader ingests files from cloud storage; Kafka delivers a message-based event stream.
Q16. What is stateful processing?
Retaining information across batches, such as running totals, dedup keys, or join buffers.
Q17. How do you handle duplicate events?
Stable event IDs, dropDuplicatesWithinWatermark (or keyed dedup with a watermark), and idempotent sinks such as MERGE on the event ID.
Q18. What happens when a query fails?
After fixing the cause, it resumes from its checkpoint if source, sink, and logic remain compatible. Output still needs validation for completeness and duplicates.
Q19. How do you monitor a streaming pipeline?
Status, input vs processed rate, batch duration, watermark progress, state size, source lag, and data freshness.
Q20. How do you improve throughput?
Find the bottleneck; optimize transforms and joins, bound state, tune triggers and parallelism, and scale compute when justified.
Q21. What is backpressure?
Input arriving faster than the pipeline can process it, so backlog and latency grow.
Q22. Is Structured Streaming exactly-once?
For supported source/sink combinations with checkpoints, yes. End-to-end effects in external systems depend on idempotent, retry-safe sink logic.
Q23. Why might a windowed aggregation not update immediately?
In append mode with a watermark, a window is written only after the watermark passes its end, which requires later events to arrive.
Q24. What is foreachBatch?
A sink that runs your batch function on each micro-batch (e.g. Delta MERGE, external writes). The function must be retry-safe.
Q25. Long-running query vs availableNow?
A long-running query stays active for future data; availableNow processes what's available and stops, which suits scheduled jobs and serverless.
