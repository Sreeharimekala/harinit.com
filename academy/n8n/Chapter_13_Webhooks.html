13.1

What is a webhook?

A webhook is a mechanism through which one application sends an HTTP request to another application when a particular event occurs. Instead of repeatedly asking an application whether something has changed, the receiving system waits for an event notification.

In n8n, a Webhook Trigger node creates an endpoint URL. An external application sends a request to that URL, and the request can start a workflow.

Example

When a customer submits a website contact form, the website sends the form data to an n8n webhook. n8n can validate the data, save the lead, notify a sales team and send a confirmation response.

Webhook vs polling

WebhookPolling
Source sends a request when an event occurs.Client repeatedly asks the source whether data changed.
Often near real-time and avoids repeated checks.May introduce delay and unnecessary API calls.
Requires a reachable and secured endpoint.Requires scheduled requests and state tracking.
Remember: A webhook is usually an event notification delivered over HTTP. It is not the same as a workflow polling an API on a schedule.
13.2

Webhook architecture

A typical webhook integration has a sender, an HTTP endpoint, a receiver and a response. The sender and receiver agree on the endpoint URL, HTTP method, payload format and any authentication or signature requirements.

Request lifecycle

  1. An event occurs in the source application.
  2. The source sends an HTTP request to the webhook URL.
  3. n8n receives the request and starts the workflow.
  4. The workflow validates and processes the incoming data.
  5. n8n returns an HTTP response according to the webhook response configuration.

Important architecture considerations

  • The sender must be able to reach the webhook URL over the network.
  • For a cloud-hosted n8n instance, the URL is normally publicly reachable subject to network and security controls.
  • For self-hosted n8n behind a firewall or reverse proxy, external routing, TLS and webhook URL configuration must be correct.
  • Consider whether the sender expects an immediate acknowledgement or a response containing the result of processing.
13.3

Webhook Trigger Node

The Webhook node is a trigger node that starts a workflow when it receives an HTTP request at its configured endpoint.

Common configuration fields

SettingPurpose
HTTP MethodDefines which method the endpoint accepts, such as GET or POST.
PathDefines the endpoint path portion of the webhook URL.
AuthenticationControls how the incoming caller is authenticated, when configured.
RespondControls when and how the HTTP response is returned.
OptionsAdditional behaviour such as response data or raw body handling, depending on node version.

Build your first webhook

  1. Create a new workflow.
  2. Add a Webhook node as the trigger.
  3. Choose a method such as POST.
  4. Set a meaningful path, for example customer-lead.
  5. Choose the authentication mode appropriate to your use case.
  6. Save the workflow and use the test URL while developing.
  7. Send a test request and inspect the incoming item.
A successful test should show the incoming request data in the Webhook node's output. The exact output structure depends on the request and node configuration.
13.4

Production vs test webhook URLs

n8n provides separate webhook URLs for testing and production. They serve different lifecycle stages and should not be confused.

Test URLProduction URL
Used while building and testing a workflow.Used by external applications for the active workflow.
Typically listens while the editor is waiting for a test event.Available when the workflow is saved and active/published according to the n8n version and deployment.
Useful for development and debugging.Used for real integrations and live events.
May stop listening when the test session ends.Designed for ongoing incoming events.

Typical URL shape

Test:       https://your-n8n-host/webhook-test/customer-lead
Production: https://your-n8n-host/webhook/customer-lead

The exact base URL and path depend on your n8n deployment and configured webhook path. Use the URLs displayed by the Webhook node rather than constructing them manually.

Common mistake: Configuring an external application with the test URL and then closing the test listener. For live integrations, configure the production URL and ensure the workflow is active/published as required by your n8n version.
13.5

GET and POST webhooks

The Webhook node can be configured to accept a specific HTTP method. Choose the method based on how the sender is designed to communicate.

GET webhookPOST webhook
Often used to retrieve information or receive simple URL parameters.Commonly used to submit event data or a JSON payload.
Parameters are commonly in the URL query string.Data is commonly in the request body.
Be careful not to put secrets or sensitive data in URLs.Validate body size, content type and payload fields.

Example GET request

GET https://your-n8n-host/webhook/customer-status?customerId=1001

The workflow can read the query parameter and use it to retrieve or return customer status.

Example POST request

POST https://your-n8n-host/webhook/customer-lead
Content-Type: application/json

{
  "name": "Asha Rao",
  "email": "asha@example.com",
  "source": "website"
}

POST is a common choice for event notifications because the sender can include a structured JSON payload in the request body.

13.6

Webhook authentication

Authentication protects a webhook endpoint by requiring the caller to prove it is allowed to send requests. The Webhook node offers authentication choices that may include none, basic authentication, header authentication or JWT, depending on the n8n version.

MethodHow it worksUse case
NoneEndpoint accepts requests without a configured credential check.Local experiments or intentionally public endpoints with other controls.
Basic AuthCaller supplies a username and password in an Authorization header.Simple integrations where the sender supports it.
Header AuthCaller supplies a configured secret header and value.System-to-system integrations with shared-secret support.
JWT AuthCaller sends a signed JSON Web Token that n8n validates.Integrations that can issue and sign JWTs.

Header authentication example

POST /webhook/order-event
X-Webhook-Secret: YOUR_SHARED_SECRET
Content-Type: application/json

Configure the expected header name and secret in the n8n credential mechanism supported by the node. The sender must send the matching header. Do not place the secret in the URL.

Authentication proves something about the caller, but it does not prove that the payload is valid or that the caller is authorized to perform every requested business action. Validate the event and enforce business permissions too.
13.7

Receiving JSON payloads

A payload is the data sent by the source application. Many webhook integrations send JSON with an application/json content type.

Example payload

{
  "event": "order.created",
  "eventId": "evt_78421",
  "occurredAt": "2026-11-21T08:30:00Z",
  "data": {
    "orderId": 5001,
    "customerId": 1001,
    "amount": 2499.50,
    "currency": "INR"
  }
}

Typical incoming data areas

  • Body: JSON or other submitted content.
  • Headers: content type, authorization, event signatures and request metadata.
  • Query: parameters included after the question mark in the URL.
  • Path parameters: values represented in the endpoint path, if configured.

In the workflow, inspect the Webhook node output to identify the exact paths. For example, if the incoming body is exposed under body, the order ID may be referenced as {{ $json.body.data.orderId }}. The correct expression depends on the actual output structure; use the expression editor and execution data to confirm.

Payload validation

  • Check required fields such as event type, event ID and record ID.
  • Check data types and acceptable values.
  • Reject or route malformed payloads safely.
  • Do not trust client-provided prices, roles or permissions without server-side validation.
  • Store an event ID or unique key to help prevent duplicate processing.
13.8

Sending webhook responses

After receiving a request, n8n can return an HTTP response to the caller. The response may acknowledge receipt, provide a result, or report a validation error.

Response behaviour

The Webhook node's response setting determines when the caller receives a response. Depending on the available node version/options, common approaches include responding immediately, responding when the last node finishes, or using a dedicated Respond to Webhook node.

ApproachWhen useful
ImmediatelyReturn a quick acknowledgement while workflow processing continues, where supported.
When workflow finishesReturn the workflow result after processing completes.
Respond to Webhook nodeControl the response at a specific point in the workflow, including response body, status and headers.

Example success response

HTTP/1.1 200 OK
Content-Type: application/json

{
  "success": true,
  "message": "Event received",
  "eventId": "evt_78421"
}

Example validation error

HTTP/1.1 400 Bad Request
Content-Type: application/json

{
  "success": false,
  "error": "orderId is required"
}
Response timing matters. Some source systems require a response quickly and may retry if they time out. For long-running processing, acknowledge receipt promptly and process asynchronously when the integration design allows it. Do not claim processing is complete if you have only accepted the event.
13.9

Webhook integrations

Webhooks are widely used to connect applications that publish events. The source application usually provides a configuration page where you register the destination webhook URL and choose which events should be sent.

Common integration examples

Website forms
Form submitted → n8n validates lead → CRM record created → sales notification.
Payment platform
Payment event → verify signature → update order → send receipt workflow.
Git platform
Push or pull-request event → run checks → notify engineering channel.
CRM
Contact updated → synchronize downstream systems → log change.
Support platform
Ticket created → enrich customer data → route to support queue.
Cloud / data platform
Job completed event → trigger downstream workflow → publish status.

Integration steps

  1. Create and test the webhook workflow in n8n.
  2. Activate/publish the workflow and copy its production URL.
  3. Open the source application's webhook or developer settings.
  4. Register the production URL and select event types.
  5. Configure the same authentication/signature method on both sides.
  6. Send a test event from the source platform.
  7. Review n8n executions and verify the expected business action.
  8. Document ownership, retries, failure handling and support contacts.

Example: order-created workflow

Webhook Trigger
    ↓
Validate event type and required fields
    ↓
Check eventId for duplicate delivery
    ↓
Retrieve order details from source API
    ↓
Update SQL / warehouse staging table
    ↓
Send confirmation or operations alert

For data engineering, a webhook can act as an event trigger for an ingestion process. It can notify a pipeline that a file arrived or a source job completed. The downstream workflow should still validate the file, event and source state before loading data.

13.10

Webhook security

A production webhook is an internet-facing or network-accessible entry point. Treat it as an API endpoint and apply layered security rather than relying on an unguessable URL alone.

Security checklist

  • Use HTTPS: protect data and credentials in transit.
  • Enable authentication: use a supported credential or signed-request mechanism.
  • Verify signatures: where the provider supports HMAC or signed webhook events, validate the signature using the raw request body and the provider's documented algorithm.
  • Validate payloads: check schema, required fields, types, size and allowed event types.
  • Prevent replay and duplicates: use timestamps, event IDs, idempotency and deduplication as appropriate.
  • Protect secrets: store shared secrets in credentials or an approved secret store; rotate exposed values.
  • Restrict access: limit workflow editing, credential access and execution permissions.
  • Apply network controls: use IP allowlists or a gateway/WAF when appropriate and supported; do not rely on IP allowlisting alone if source IPs can change.
  • Limit resource usage: set request-size and execution controls, and guard against bursts or abusive traffic.
  • Monitor: log event IDs, outcomes and non-sensitive metadata; alert on unusual volume or repeated failures.
  • Avoid sensitive response data: return only the information the sender needs.

Signature verification concept

Some providers calculate a cryptographic signature using a shared secret and the exact raw request body. The sender includes the signature in a header. The receiver independently calculates the expected signature and compares it securely. The header name, encoding, timestamp rules and algorithm are provider-specific.

Do not invent a signature algorithm or assume every provider uses the same header. Follow the source application's official webhook security documentation. If signature verification requires the raw body, configure n8n to preserve/receive the raw body as supported by your node version.

Practical labs

Lab 1 – Create a basic POST webhook

  1. Create a workflow and add a Webhook node.
  2. Set method to POST and path to training-contact.
  3. Use the test URL and start listening for a test event.
  4. Send a JSON request from an API client, such as Postman or curl.
  5. Inspect the body, headers and query values in the execution data.
curl -X POST "YOUR_TEST_WEBHOOK_URL" \
  -H "Content-Type: application/json" \
  -d '{"name":"Asha","email":"asha@example.com"}'

Lab 2 – Validate and transform the payload

  1. After the Webhook node, add an IF node.
  2. Check whether the required email field exists and is not empty.
  3. Route valid records to an Edit Fields node.
  4. Normalize the email and map fields to a consistent lead structure.
  5. Route invalid records to an error response or controlled logging path.

Lab 3 – Return a custom response

  1. Configure the Webhook node to use the Respond to Webhook node, if available in your version.
  2. Add the Respond to Webhook node after validation.
  3. For valid input, return status 200 and a JSON acknowledgement.
  4. For invalid input, return an appropriate 4xx status and a concise error body.
  5. Test both branches and verify the sender receives the expected response.

Lab 4 – Secure the endpoint

  1. Configure Header Auth or another supported authentication method.
  2. Send a request without the credential and verify it is rejected.
  3. Send a request with the configured credential and verify it is accepted.
  4. Ensure the secret is not included in URLs, workflow output or logs.

Interview questions and answers

  1. What is a webhook?
    A way for one application to send an HTTP request to another when an event occurs.
  2. How is a webhook different from an API call?
    A webhook is typically an event-driven request initiated by the source; a conventional API call is often initiated by a client asking for data or an action. Webhooks themselves use HTTP APIs/protocols.
  3. What is the Webhook Trigger node in n8n?
    A trigger that exposes an endpoint and starts a workflow when it receives a configured HTTP request.
  4. What is the difference between test and production webhook URLs?
    The test URL is for editor-based testing; the production URL is for an active/published workflow's live integration.
  5. When would you use GET versus POST?
    GET commonly reads or passes simple URL parameters; POST commonly submits event data in a request body.
  6. What is a webhook payload?
    The data sent by the source application, commonly JSON.
  7. What information can n8n receive?
    Depending on the request, body data, headers, query parameters and path information.
  8. How do you authenticate a webhook?
    Use a supported method such as basic auth, header auth or JWT, or implement provider-specific signature verification.
  9. What is the Respond to Webhook node?
    A node that lets a workflow control the HTTP response returned to the caller.
  10. Why might a webhook sender retry an event?
    It may not receive a timely successful response, or it may retry after a network or server error.
  11. What is idempotency in webhook processing?
    Ensuring duplicate delivery of the same event does not repeat the business effect.
  12. Why should event IDs be stored?
    They help identify duplicate events and support traceability.
  13. What is webhook signature verification?
    Validating a cryptographic signature supplied by the provider to confirm the request's integrity and origin.
  14. Why is HTTPS important?
    It encrypts requests and credentials in transit and helps protect against interception or modification.
  15. What is replay protection?
    Controls such as timestamps and unique event IDs help prevent an attacker from resending a previously captured valid request.
  16. How do you handle long-running webhook workflows?
    Where the source supports it, acknowledge receipt quickly and perform the heavier processing asynchronously.
  17. Can webhooks trigger data engineering pipelines?
    Yes. They can signal events such as file arrival or upstream job completion, followed by validation and ingestion.
  18. What would you monitor?
    Execution success, failure rates, response times, event volume, duplicate events and authentication failures.
