Core Nodes

Learn the built-in nodes that shape, transform, route, combine, summarize and control data in an n8n workflow. This chapter moves from individual node configuration to practical workflow design.

8.1

Core-node overview

Core nodes are the workflow-building blocks supplied by n8n. They are not all the same kind of tool: some modify data, some decide which path should run, some combine or reshape items, and others control execution timing.

Data transformation

Edit Fields, Code, Aggregate, Summarize, Split Out, Sort, Limit and Filter.

Workflow logic

IF, Switch, Merge and Loop Over Items.

Execution control

Wait and No Operation.

Typical pattern

Receive → clean → validate → route → transform → combine → deliver.

Illustrative diagram, not a screenshot of the n8n editor.
Important foundation: n8n commonly passes data as an array of items. Each item normally contains a json object and may also contain binary data. A node can receive many items and return zero, one or many items depending on its purpose and configuration.
8.2

Edit Fields (Set) node

Data transformation

The Edit Fields node (previously commonly called Set) lets you add, change, rename or remove fields without writing JavaScript. It is usually the first choice for straightforward data shaping.

What it is used for

  • Create new fields such as fullName, processedAt or orderValue.
  • Map incoming fields into a clean output schema.
  • Rename or remove fields that downstream systems do not need.
  • Use expressions to calculate values from incoming data.

Example input

{
  "first_name": "Anita",
  "last_name": "Rao",
  "quantity": 3,
  "unit_price": 250,
  "internal_note": "manual review"
}

Example target fields

fullName     = {{ $json.first_name + " " + $json.last_name }}
quantity     = {{ $json.quantity }}
totalAmount  = {{ $json.quantity * $json.unit_price }}
sourceSystem = "ERP"

Configure the node to keep only the fields you need when building a deliberate output contract. If you want to retain all incoming fields, use the node's relevant include/keep options rather than assuming newly added fields replace the input.

Typical configuration steps

  1. Add Edit Fields after a trigger or data-fetch node.
  2. Choose manual field mapping or JSON output mode where available.
  3. Add a field name and choose an appropriate value/type.
  4. Use an expression for dynamic values.
  5. Execute the node and inspect the output JSON.
Common mistake: accidentally dropping fields needed later. Check whether the node is configured to keep all input fields or only the fields you explicitly define.
8.3

Code node

Custom transformation

The Code node runs JavaScript or Python (availability and supported features depend on the n8n deployment/version) when built-in nodes or expressions are not sufficient. It supports two main execution modes: run once for all items, or run once for each item.

When to use it

  • Complex calculations or multi-step transformations.
  • Custom validation and conditional field creation.
  • Reshaping nested arrays and objects.
  • Logic that would become difficult to maintain using many simple nodes.

JavaScript — run once for all items

const items = $input.all();

return items.map((item) => {
  const quantity = Number(item.json.quantity ?? 0);
  const price = Number(item.json.unit_price ?? 0);

  return {
    json: {
      ...item.json,
      total_amount: quantity * price,
      is_high_value: quantity * price >= 1000,
    },
  };
});

JavaScript — run once for each item

const quantity = Number($json.quantity ?? 0);
const price = Number($json.unit_price ?? 0);

return {
  total_amount: quantity * price,
  is_high_value: quantity * price >= 1000,
};

Use the output shape expected by the selected Code-node mode and language. In all-items mode, return an array of n8n items. In per-item mode, return the item data for the current item as supported by the node's editor/runtime.

Best practices

  • Prefer Edit Fields for simple field mapping.
  • Convert and validate types explicitly; API values may arrive as strings.
  • Handle missing/null values with safe defaults where appropriate.
  • Do not assume external npm packages are available; availability depends on hosting and task-runner configuration.
  • Preserve item relationships when transforming data so expressions referencing earlier nodes continue to work.
  • Keep code focused and add comments for non-obvious business rules.
Rule of thumb: use expressions for small calculations, Edit Fields for ordinary mapping, and Code for custom logic that is clearer in a programming language.
8.4

IF node

Two-way decision

The IF node evaluates one or more conditions and sends items down one of two outputs: true or false. It is useful when a workflow needs a simple yes/no decision.

Example: order validation

Route orders with status = "approved" to fulfilment; send all other orders to a review or exception path.

Condition:
Value 1: {{ $json.status }}
Operation: is equal to
Value 2: approved
Illustrative branching diagram, not an editor screenshot.

Condition types

  • String comparisons: equals, contains, starts with, is empty.
  • Number comparisons: greater than, less than, equals.
  • Boolean checks: true/false.
  • Date/time comparisons and existence checks, depending on the condition type selected.

Use the correct data type. For example, compare numeric values as numbers rather than relying on text comparison.

8.5

Switch node

Multi-way routing

The Switch node routes incoming items to one of multiple outputs based on rules or an expression. Use it when a value can have several categories, instead of building a long chain of IF nodes.

Example: ticket priority

RuleOutput pathExample action
priority = "Critical"CriticalPage on-call team
priority = "High"HighSend urgent notification
priority = "Medium"MediumCreate normal task
Fallback / no rule matchOtherLog or send to triage

Configuration approach

  1. Select the value to evaluate, for example {{ $json.priority }}.
  2. Add a rule for each expected value or range.
  3. Configure what happens when no rule matches.
  4. Connect each output to its relevant action.
  5. Test all expected values, including null and unexpected values.
Use IF for two outcomes. Use Switch when the workflow has three or more meaningful routes or when routing rules are easier to maintain in one place.
8.6

Merge node

Combine branches

The Merge node combines data from two inputs. Its behaviour depends on the selected mode. It can append input items, combine matching items, combine by position, or wait for inputs to arrive before continuing. Available options can change across n8n versions.

Common use cases

  • Combine customer data from a CRM with account details from a database.
  • Join two branches that were processed independently.
  • Append records from two sources into one stream.
  • Synchronize branches before downstream processing.
Mode / conceptWhat it doesUse when
AppendPlaces items from both inputs into one output sequence.You want a combined list, not a field-level join.
Combine by matching fieldsMatches records using selected key fields.Both sources share a key such as customer_id.
Combine by positionPairs items according to their positions.Input item ordering and counts are intentionally aligned.
Choose Branch / pass-through optionsContinues with a selected input, depending on configuration.You need branch synchronization or a particular input's data.

Example: combine source and target counts

Input 1: { "table": "CUSTOMERS", "source_count": 1200 }
Input 2: { "table": "CUSTOMERS", "target_count": 1198 }

Merge by matching field: table

Possible combined result:
{
  "table": "CUSTOMERS",
  "source_count": 1200,
  "target_count": 1198
}
Watch out for: duplicate field names, unmatched keys, item-order assumptions and unexpected many-to-many matches. Decide how unmatched items should be handled and test with duplicate keys.
8.7

Filter node

Keep matching items

The Filter node keeps only the items that satisfy the configured conditions and removes items that do not match. Unlike IF, it does not create separate true and false branches for the two groups.

Example: keep active customers

Condition:
{{ $json.customer_status }}
is equal to
Active

If 100 customer items arrive and 72 are Active, the Filter output contains the 72 matching items. The other 28 do not continue through this node's output.

Filter vs IF

  • Filter: retain only matching items in one stream.
  • IF: split items into true and false outputs so both groups can be processed differently.

Use Filter for simple selection before reporting, API calls or database writes. Use IF when rejected items also need a separate action.

8.8

Sort node

Order items

The Sort node orders incoming items by one or more fields. Sorting changes the sequence of items; it does not inherently remove or aggregate them.

Example

Sort incident records by created_at descending to put the newest incident first, or by severity_rank ascending to put the highest-priority records first if lower numbers represent greater severity.

FieldDirectionExample
created_atDescendingNewest to oldest
customer_nameAscendingA to Z
amountDescendingHighest amount first
Check data types before sorting. Text values such as "100" and "20" may not sort like numeric values. Normalize dates and numbers before sorting.
8.9

Limit node

Restrict item count

The Limit node restricts how many items continue downstream. It is useful for sampling, testing, limiting API operations or processing only a subset of a large result.

Example

Input: 5,000 customer records. Limit: 100. Output: at most 100 records, depending on the configured selection options.

  • Use a small limit while testing a workflow against a real data source.
  • Use it to prevent an accidental large batch of downstream writes.
  • Do not confuse a workflow test limit with complete production processing.
Limit does not mean pagination. If you need every record from an API, configure the API's pagination mechanism rather than limiting the result and assuming the rest will be fetched automatically.
8.10

Aggregate node

Many items → grouped structure

The Aggregate node collects values from multiple incoming items into an aggregated structure. It is useful when you need to package individual records into a list or combine selected fields for a later operation.

Example input items

{ "product": "Keyboard", "qty": 2 }
{ "product": "Mouse", "qty": 4 }
{ "product": "Monitor", "qty": 1 }

Conceptual aggregate result

{
  "products": [
    { "product": "Keyboard", "qty": 2 },
    { "product": "Mouse", "qty": 4 },
    { "product": "Monitor", "qty": 1 }
  ]
}

Depending on the selected aggregation mode and fields, you can aggregate all item data or selected fields. Configure the output field name and decide whether the original fields should also be included.

When to use it

  • Build one API payload containing many detail records.
  • Collect values before sending a summary email.
  • Prepare a nested JSON structure for another system.
8.11

Summarize node

Statistical summary

The Summarize node calculates summary values across incoming items, such as counts, sums, averages, minimums and maximums. It is intended for analytical summaries rather than simply placing records into an array.

Example: daily sales

Input amounts: 100, 250, 150, 500

Count  = 4
Sum    = 1000
Average= 250
Min    = 100
Max    = 500

Where supported by the node configuration, group by a field such as region or business_date to calculate separate metrics for each group.

MetricMeaning
CountNumber of values or records included in the calculation.
SumTotal of numeric values.
AverageArithmetic mean of numeric values.
Min / MaxSmallest and largest values.
Aggregate vs Summarize: Aggregate is for collecting values/records into a structured output. Summarize is for calculating metrics that describe a set of records.
8.12

Split Out node

Array → individual items

The Split Out node takes an array field inside an item and turns each element of that array into a separate n8n item. It is useful when an API returns a parent record containing a list of child records.

Input

{
  "order_id": 501,
  "customer": "Anita",
  "items": [
    { "sku": "KB-01", "qty": 2 },
    { "sku": "MS-02", "qty": 1 },
    { "sku": "MN-03", "qty": 1 }
  ]
}

After splitting the items field

{ "sku": "KB-01", "qty": 2 }
{ "sku": "MS-02", "qty": 1 }
{ "sku": "MN-03", "qty": 1 }

Configure the array field to split. If downstream steps still need parent-level values such as order_id, configure the node to include the other fields where that option is available.

Common pattern

Fetch orders → Split Out order lines → calculate line totals → insert each line into a database.

8.13

Loop Over Items node

Controlled iteration

Loop Over Items (formerly known as Split in Batches) processes items in batches and routes each batch through a loop path. It is useful when a downstream operation should handle a controlled number of records at a time.

Example

You have 1,000 records and configure a batch size of 100. The loop path processes a batch, returns to the loop node, and continues with the next batch until all items have been handled.

Conceptual batch loop. Follow the node's Loop and Done outputs and connect the loop path back as shown in the current editor.

Batch processing pattern

  1. Connect a source that returns many items.
  2. Add Loop Over Items and set the batch size.
  3. Connect the Loop output to the operation to repeat.
  4. Connect the end of that processing path back to the loop node as required by the node's loop pattern.
  5. Connect the Done output to the steps that should run after all batches complete.
A loop is not automatically required just because there are many items: many n8n nodes process all incoming items themselves. Use Loop Over Items when batching or controlled iteration is actually needed.
8.14

Wait node

Pause and resume

The Wait node pauses a workflow execution and resumes it later based on the configured condition. Depending on the chosen mode, it can wait for a duration, until a specified time, or for an external event such as a webhook call.

Common scenarios

  • Wait 30 minutes before sending a reminder.
  • Pause until a chosen date/time.
  • Wait for an external approval or callback through a resume URL.
  • Introduce a delay between steps when the target service requires it.

Example: approval process

  1. Create a purchase request.
  2. Send an approval notification containing the resume link or use an appropriate approval integration.
  3. Pause at the Wait node.
  4. Resume when the configured event occurs.
  5. Continue with approved/rejected handling.
Important: a Wait node does not itself implement a complete approval system. You must design how the approval signal is received, authenticated, correlated to the correct request and validated before the workflow resumes.
8.15

No Operation, do nothing node

Workflow placeholder

The No Operation node intentionally performs no data transformation or external action. It is useful as a placeholder, a clearly named endpoint for a branch, or a temporary connection point while developing a workflow.

Examples

  • Keep an unused branch visually explicit.
  • Provide a harmless destination for a route that intentionally requires no action.
  • Temporarily replace a planned action during development.
  • Make a branch easier to read by adding a named stopping point.

It does not mean “ignore errors” or “continue after a failure” by itself. Error handling must be configured using the appropriate workflow error-handling features.

8.17

Practical labs

Lab 1 — Clean and enrich customer records

Goal: standardize incoming customer data using Edit Fields.

  1. Create a Manual Trigger and provide sample customer JSON using an appropriate data source node or pinned input.
  2. Add Edit Fields.
  3. Create full_name, email_normalized and customer_type.
  4. Remove fields that should not be sent downstream.
  5. Execute and inspect the resulting JSON.

Expected outcome: a consistent customer schema for downstream systems.

Lab 2 — Route incidents by severity

Goal: use Switch for multiple routes.

  1. Prepare incidents with Critical, High, Medium and Low priorities.
  2. Add Switch and evaluate the priority field.
  3. Create a route for each priority.
  4. Connect each output to a different notification or logging action (mock actions are fine).
  5. Test an unexpected priority and confirm the fallback behaviour.

Lab 3 — Filter and sort orders

Goal: keep only approved orders and sort by amount descending.

  1. Prepare at least five sample order items.
  2. Filter on status = approved.
  3. Sort by numeric amount, descending.
  4. Inspect the output order and confirm rejected records are excluded.

Lab 4 — Merge source and target validation counts

Goal: combine two data branches.

  1. Create one branch with source table counts and another with target table counts.
  2. Ensure both branches contain a shared key such as table_name.
  3. Configure Merge to combine by that matching field.
  4. Review matched and unmatched records.
  5. Calculate a count difference in Edit Fields or Code.

Lab 5 — Split and aggregate order lines

Goal: move between parent and child record structures.

  1. Create an order with an array of line items.
  2. Use Split Out on the line-item array.
  3. Calculate line amount for each item.
  4. Use Aggregate to collect the transformed lines into one array.
  5. Compare the original and reconstructed structures.

Lab 6 — Batch processing with a Wait step

Goal: process records in batches and introduce a controlled pause.

  1. Prepare a list of test records.
  2. Use Loop Over Items with a small batch size such as 2 or 3.
  3. Connect a harmless processing step to the Loop output.
  4. Optionally add a short Wait for demonstration, then return to the loop path.
  5. Use the Done output for a final completion message.
  6. Inspect the execution to understand the batch sequence.
Use mock data and harmless actions while learning. Before connecting production databases, email systems or APIs, verify credentials, filters, batch sizes and the number of records that will be changed.

Troubleshooting and design guidance

SymptomLikely causeWhat to check
Expected fields are missingEdit Fields is configured to keep only selected fields.Review include/keep settings and downstream field names.
Code node returns no data or errorsIncorrect return structure, mode mismatch or invalid JavaScript/Python.Confirm execution mode, language, syntax and output shape.
IF sends records to the wrong outputString/number mismatch, whitespace or incorrect condition.Inspect actual input value and type; normalize before comparing.
Switch has no matching routeUnexpected value or no fallback route.Check spelling, case, nulls and fallback handling.
Merge output has duplicatesDuplicate join keys or many-to-many matches.Check key uniqueness and selected merge mode.
Filter returns zero itemsCondition does not match actual values.Inspect input data, data type, casing and null values.
Sort order looks incorrectNumbers/dates are stored as strings or values are inconsistent.Convert values to the intended data type first.
Only some records are processedLimit node or an upstream API pagination setting.Review limits and pagination configuration.
Array is not splitWrong array field path or value is not actually an array.Inspect the input JSON and select the correct field.
Loop never completesLoop-back connection is wrong or loop path does not reach the expected return point.Review Loop and Done outputs and inspect execution progression.
Wait workflow does not resume as expectedResume mode or event configuration is incorrect.Check wait condition, resume endpoint/event and execution status.

Production design principles

  • Define the expected input and output schema for each major workflow section.
  • Validate required fields before making irreversible changes.
  • Use Filter when you only need matching items; use IF when both groups need handling.
  • Use Merge only after deciding the matching key and duplicate behaviour.
  • Use Limit during development, then remove or deliberately configure it for production.
  • Use batching to manage downstream load, but do not add loops unnecessarily.
  • Log rejected records and errors so they can be investigated or replayed.
  • Test empty arrays, nulls, duplicate keys, unexpected values and large inputs.
8.19

Interview questions and answers

  1. What is the Edit Fields node?
    It adds, updates, renames or removes fields using visual mapping and expressions.
  2. When would you use Code instead of Edit Fields?
    When custom logic or complex transformations are clearer and more maintainable in code.
  3. What are the Code node execution modes?
    Run once for all items and run once for each item.
  4. What does the IF node do?
    Routes items to true or false outputs based on conditions.
  5. How is Switch different from IF?
    Switch supports multiple rule-based routes; IF is designed for a two-way decision.
  6. What is the purpose of Merge?
    To combine data from two inputs or branches using a selected merge strategy.
  7. What is the difference between Append and matching-field combination?
    Append places items into one stream; matching-field combination joins records using key values.
  8. How is Filter different from IF?
    Filter keeps matching items in one output; IF separates true and false items into two outputs.
  9. Does Sort change the data values?
    Normally it changes item order, not the field values themselves.
  10. What is the purpose of Limit?
    To restrict how many items continue downstream.
  11. Does Limit implement API pagination?
    No. Pagination must be configured for the API or data source.
  12. What does Aggregate do?
    Collects selected values or records into an aggregated data structure.
  13. What does Summarize do?
    Calculates metrics such as count, sum, average, minimum and maximum.
  14. Aggregate vs Summarize?
    Aggregate builds a collection/structure; Summarize calculates descriptive metrics.
  15. What does Split Out do?
    Converts elements of an array field into separate n8n items.
  16. Give a use case for Split Out.
    Turning an order's line-item array into individual rows for database insertion.
  17. What is Loop Over Items?
    A node for iterating over items in controlled batches.
  18. Should every multi-item workflow use Loop Over Items?
    No. Many nodes process all input items natively; use loops when controlled batching is required.
  19. What is the Loop output?
    The output used for the current batch's processing path.
  20. What is the Done output?
    The output used after all batches have been processed.
  21. What is the Wait node used for?
    Pausing a workflow until a time-based or event-based resume condition is met.
  22. Does Wait itself implement approval logic?
    No. The workflow must receive and validate the approval event or signal.
  23. What does No Operation do?
    It intentionally performs no action and can serve as a placeholder or explicit no-action branch.
  24. How would you design a safe data-load workflow?
    Validate inputs, filter eligible records, transform fields, batch writes if required, log outcomes and route errors for review.
