Real-Time Projects and Capstone

Move from individual nodes and integrations to complete, testable automation solutions. Each project includes a goal, workflow pattern, validation scenarios, and engineering practices. The capstone combines Azure Data Factory, SQL Server, AI analysis, Microsoft Teams, Outlook, and a monitoring assistant.

How to use this manual

  1. Complete the projects in increasing complexity.
  2. Build first with test data and non-production credentials.
  3. Test failure paths, duplicate events, and recovery—not only the happy path.
  4. Document inputs, outputs, owners, credentials, and runbooks.
  5. Keep AI recommendations advisory until validated by an engineer.

Recommended project progression

Beginner: Projects 1–2. Intermediate: Projects 3–6. Advanced: Projects 7–11. Professional: Project 12 and the capstone.

Do not rush to the capstone before you can reliably authenticate to APIs, process JSON, write parameterized SQL, handle retries, and troubleshoot failed executions.

P1

Email Automation · Beginner

Objective

Read messages from a mailbox, normalize sender/subject/date, classify by simple rules, label or move messages, and log the action.

Suggested workflow

Microsoft Outlook or Gmail trigger → normalize fields → Switch/IF categorization → apply label/folder or create task → audit log.

Test scenarios

Test newsletters, invoices, urgent requests, unknown senders, duplicate events, and attachment handling. Use a dedicated test mailbox and least-privilege scopes.

Engineering practice: Avoid marking a message as read or moving it before processing succeeds. Store message IDs to prevent duplicate processing.

Definition of done

  • Happy path works with representative test data.
  • Invalid input and dependency failure are handled visibly.
  • Secrets are stored securely and sensitive data is minimized.
  • Execution can be traced and safely replayed where appropriate.
  • Workflow purpose, owner, dependencies, and support steps are documented.

Suggested common SQL data model

Use a simple, auditable model for monitoring and automation events. Adapt data types and naming conventions to your SQL Server standards.

CREATE TABLE dbo.ADF_PipelineRun
(
    PipelineRunId       nvarchar(100) NOT NULL PRIMARY KEY,
    FactoryName         nvarchar(200) NOT NULL,
    PipelineName        nvarchar(300) NOT NULL,
    RunStatus           nvarchar(30)  NOT NULL,
    RunStartUtc         datetime2(3)  NULL,
    RunEndUtc           datetime2(3)  NULL,
    DurationSeconds     int           NULL,
    ErrorCode           nvarchar(100) NULL,
    ErrorMessage        nvarchar(max) NULL,
    IngestedUtc         datetime2(3)  NOT NULL
        CONSTRAINT DF_ADF_PipelineRun_IngestedUtc DEFAULT SYSUTCDATETIME()
);

CREATE TABLE dbo.MonitoringAlert
(
    AlertId             bigint IDENTITY(1,1) PRIMARY KEY,
    DeduplicationKey    nvarchar(300) NOT NULL,
    PipelineRunId       nvarchar(100) NULL,
    Severity            nvarchar(20)  NOT NULL,
    AlertStatus         nvarchar(30)  NOT NULL,
    AlertSummary        nvarchar(1000) NOT NULL,
    CreatedUtc          datetime2(3) NOT NULL
        CONSTRAINT DF_MonitoringAlert_CreatedUtc DEFAULT SYSUTCDATETIME()
);

This is a starter schema, not a complete production model. Add indexes, constraints, retention, ownership, and update/upsert procedures after defining query patterns.

P8

Build an AI-Powered Data Engineering Monitoring Platform

The capstone monitors Azure Data Factory pipeline executions, stores run history in SQL Server, analyzes failure messages with an LLM, notifies support teams, produces daily health reports, and exposes a governed assistant for operational questions.

Functional requirements

  1. 1. Monitor Azure Data Factory pipelines. Poll or receive ADF run events for selected factories and pipelines. Define scope, frequency, time window, and expected SLA.
  2. 2. Fetch pipeline execution information. Use Microsoft Entra ID service principal or managed identity where supported, grant minimum required ADF monitoring permissions, and call the ADF management REST APIs. Handle pagination and API throttling.
  3. 3. Identify failed pipelines. Normalize statuses such as Queued, InProgress, Succeeded, Failed, and Cancelled. Add rules for duration/SLA breaches and stale runs; do not classify an in-progress run as failed merely because it is still running.
  4. 4. Store execution history in SQL Server. Create a run-history table keyed by pipelineRunId, plus an event/alert table. Use parameterized upserts, UTC timestamps, source factory/pipeline identifiers, status, duration, error code/message, and ingestion timestamp.
  5. 5. Analyze error messages using AI. Send only the required error text and safe metadata to the model. Ask for a structured result: short summary, probable category, evidence, suggested checks, confidence, and whether human review is required.
  6. 6. Generate failure summaries. Validate the model's structured output. Keep original ADF error details alongside AI-generated interpretation. Label AI analysis as advisory, not a confirmed root cause.
  7. 7. Send Teams and Outlook notifications. Route by severity and support ownership. Include pipeline, run ID, environment, start/end time, error summary, execution link, and recommended next step. Deduplicate repeated alerts.
  8. 8. Identify recurring failures. Group failures by normalized error signature, pipeline, activity, and time window. Track counts and recurrence; do not rely solely on an LLM to determine whether two errors are identical.
  9. 9. Generate daily health reports. Calculate total runs, success/failure/cancelled counts, success rate, SLA breaches, top failing pipelines, recurring errors, and data freshness. Include a reporting-period watermark.
  10. 10. Provide an AI-powered monitoring assistant. Allow users to ask questions against governed monitoring tables and curated runbooks. Use read-only SQL access and RAG citations; enforce user authorization and query limits.

Capstone workflow decomposition

WorkflowResponsibilityExpected output
WF01 — ADF Run CollectorPoll ADF runs, paginate, normalize, and checkpoint the lookback window.Normalized run records.
WF02 — Run PersistenceUpsert run history and retain source run IDs.SQL history rows and ingestion metrics.
WF03 — Failure AnalyzerClassify errors using deterministic rules first; request AI summary when useful.Validated failure-analysis JSON.
WF04 — Alert DispatcherDeduplicate, route by severity/owner, and send Teams/Outlook messages.Alert record and delivery status.
WF05 — Daily Health ReportCalculate operational KPIs and distribute a report.Daily report artifact and delivery log.
WF06 — Monitoring AssistantAnswer authorized questions using read-only SQL and curated runbooks.Grounded answer with source/run references.

Important design rules

  • Use a stable run ID as the primary deduplication key.
  • Use UTC internally and convert to local time only for display.
  • Use a lookback window plus overlap/checkpoint to avoid missing late-arriving runs.
  • Keep original error messages and AI summaries in separate fields.
  • Do not let an LLM execute arbitrary SQL or close incidents autonomously.
  • Alert on monitoring-workflow failure as well as monitored-pipeline failure.
  • Use least-privilege identity and protect OAuth tokens/API secrets.
  • Document retention, backup, restore, and incident escalation.
📘

Capstone acceptance criteria

  • Selected ADF pipeline runs are collected reliably, including pagination and status transitions.
  • SQL history is idempotent: rerunning the collector does not create duplicate run records.
  • Failed and SLA-breached runs are detected by deterministic rules.
  • AI summaries are schema-validated and clearly marked as advisory.
  • Teams and Outlook alerts include enough context to act and are deduplicated.
  • Daily health reports reconcile with stored run history.
  • The assistant answers only from authorized data and provides traceable references.
  • Failure, replay, recovery, and backup-restore tests are demonstrated.
