21.1

What is RAG?

Retrieval Augmented Generation combines information retrieval with language generation. Instead of relying only on model training, the workflow searches a controlled knowledge source and supplies relevant passages to the model at answer time.

RAG is useful for internal documentation, runbooks, product manuals, policies and support knowledge that may change more frequently than a model's training data.

21.2

RAG architecture

There are two paths: ingestion/indexing (prepare and store knowledge) and query/answering (retrieve relevant passages and generate a response). Keep them separately observable and repeatable.

21.3

Document ingestion

Ingestion loads documents from approved sources such as cloud storage, SharePoint, databases or uploaded files. Extract text and metadata such as document ID, title, source path, version, modified date and access scope.

  1. Discover new or changed documents.
  2. Download and extract text.
  3. Normalize encoding and remove irrelevant boilerplate.
  4. Attach source metadata and access labels.
  5. Chunk, embed and upsert into the vector store.
  6. Track processed version and handle deletions/updates.
21.4

Document chunking

Chunking splits long documents into smaller passages suitable for embedding and retrieval. Very large chunks can dilute relevance; very small chunks can lose context.

  • Use document structure—headings, paragraphs, tables and sections—where possible.
  • Choose chunk size and overlap empirically.
  • Keep source IDs and page/section metadata with every chunk.
  • Avoid splitting tables or code blocks in ways that destroy meaning.
  • Test retrieval on real questions rather than choosing settings by intuition.
21.5

Text embeddings

An embedding model maps a text chunk to a numeric vector. Similar content tends to have nearby vectors under the chosen similarity metric. Embedding models have dimensions and token limits; vector collections must be configured to match the selected model.

Use a consistent model/version for document and query embeddings. If changing models, plan a re-embedding/reindexing process rather than mixing incompatible vector spaces.

21.6

Vector similarity search

Similarity search ranks vectors by a distance or similarity function such as cosine similarity, dot product or Euclidean distance, depending on the database/index configuration.

  • Top-k: retrieve the best k candidate chunks.
  • Metadata filters: restrict results by source, tenant, date or document type.
  • Threshold: reject weak matches where appropriate.
  • Hybrid search: combine semantic vectors with lexical/keyword matching.
  • Reranking: reorder candidates using a more precise relevance model.
21.7

Vector databases

A vector database stores embeddings and metadata and provides similarity search. Evaluate dimensions, distance metric, filtering, indexing, backups, latency, scale, access control, region, pricing and operational complexity.

Do not use vector similarity for exact joins, financial calculations or authorization decisions. Apply structured filters and source-system permissions separately.

21.8

Pinecone

Pinecone is a managed vector database service. A typical integration creates or selects an index with the expected vector dimension and metric, configures API credentials, and upserts vectors with IDs and metadata. Query operations retrieve similar vectors, often with metadata filters.

Confirm index dimension matches the embedding model output. Plan namespaces/tenant isolation and deletion/update behaviour.

21.9

Qdrant

Qdrant is a vector search engine/database that stores points containing vectors and payload metadata. Configure a collection with the correct vector size and distance metric. Use payload filters to constrain search and stable point IDs for upsert/delete operations.

Secure the endpoint and API key, especially for self-hosted deployments. Monitor collection/index performance and backup strategy.

21.10

Supabase Vector

Supabase can provide PostgreSQL-backed vector storage using the pgvector extension. A common design stores document chunks, embeddings and metadata in a table, then exposes a similarity-search function for retrieval.

Use Row Level Security or another appropriate access-control design where user/tenant data is separated. Do not rely on a prompt instruction to enforce data permissions.

21.11

PostgreSQL with pgvector

pgvector adds a vector data type and similarity operators/indexing options to PostgreSQL. A simplified table might store an ID, chunk text, metadata and embedding vector.

CREATE EXTENSION IF NOT EXISTS vector;

CREATE TABLE document_chunks (
  id bigserial PRIMARY KEY,
  source_id text NOT NULL,
  content text NOT NULL,
  metadata jsonb,
  embedding vector(1536)
);

The dimension above is only an example; set it to the exact output dimension of your embedding model. Choose indexes/operators according to the pgvector version and query strategy.

21.12

Document retrieval

At query time, embed the question, search the vector store, apply metadata/security filters, select useful passages and pass them to the LLM. Return citations or source metadata so users can inspect the evidence.

  1. Normalize the question.
  2. Generate query embedding.
  3. Search top-k with permission filters.
  4. Optionally rerank and remove duplicates.
  5. Build a bounded context prompt.
  6. Generate an answer constrained to retrieved evidence.
  7. Return answer plus document references.
Never let vector similarity decide whether a user is authorized to see a document. Enforce access control before or during retrieval.
21.13

Building AI knowledge assistants

A knowledge assistant lets users ask natural-language questions over approved documents. A production assistant needs ingestion monitoring, version tracking, access filtering, retrieval evaluation, citations, feedback and fallback behaviour.

Production checklist

  • Define content owners and approved sources.
  • Track source version and reindex changed/deleted documents.
  • Preserve source references and page/section metadata.
  • Evaluate retrieval precision/recall with representative questions.
  • Require the model to say when evidence is insufficient.
  • Protect tenant boundaries and sensitive content.
  • Monitor latency, token usage, vector-store costs and user feedback.

Practical labs

Lab 1 – Build a document index

  1. Collect three non-sensitive sample documents.
  2. Extract text and preserve filename/title metadata.
  3. Split text into chunks and inspect chunk boundaries.
  4. Generate embeddings using one selected model.
  5. Upsert vectors and metadata into a test vector store.

Lab 2 – Query the knowledge base

  1. Create a question and generate its embedding.
  2. Run top-k similarity search with metadata filters.
  3. Inspect returned passages and similarity scores.
  4. Pass only relevant passages to the LLM.
  5. Return a concise answer with source references.

Lab 3 – Evaluate retrieval

  1. Write 15 questions with expected source documents.
  2. Measure whether the correct source appears in top-k.
  3. Try different chunk sizes, overlap and top-k values.
  4. Test filters for document type and access scope.
  5. Record retrieval quality and answer groundedness.

Lab 4 – Update and delete lifecycle

  1. Change one source document and record its version.
  2. Reprocess only affected chunks.
  3. Delete or supersede obsolete chunks.
  4. Verify queries no longer retrieve stale content.
  5. Keep an ingestion audit log.

Interview questions and answers

  1. What is RAG?
    Retrieval Augmented Generation retrieves external context and supplies it to an LLM for a grounded response.
  2. What are the two main RAG paths?
    Ingestion/indexing and query-time retrieval/answer generation.
  3. Why chunk documents?
    To create passages small enough for effective embedding and retrieval while preserving useful context.
  4. What is chunk overlap?
    Shared text between adjacent chunks to reduce loss of context at chunk boundaries.
  5. What is an embedding?
    A numeric vector representation of content generated by an embedding model.
  6. What is vector similarity search?
    Ranking stored vectors by a configured distance or similarity measure.
  7. What does top-k mean?
    The number of highest-ranked candidate results returned by retrieval.
  8. What is hybrid search?
    Combining semantic vector retrieval with lexical/keyword search.
  9. Why store metadata with chunks?
    To trace sources, filter by attributes and apply access/retention policies.
  10. What is Pinecone?
    A managed vector database service for storing and querying embeddings.
  11. What is Qdrant?
    A vector search engine/database that stores vectors with payload metadata.
  12. What is pgvector?
    A PostgreSQL extension that adds vector storage and similarity search capabilities.
  13. Why must vector dimensions match?
    The vector index expects vectors with a defined dimension matching the embedding model output.
  14. Does RAG guarantee factual answers?
    No. Retrieval can be poor or incomplete and the model can still generate unsupported claims.
  15. How do you secure a RAG assistant?
    Enforce source permissions during retrieval, isolate tenants, protect credentials and audit access.
