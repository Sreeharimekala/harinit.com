12.1

What is an API?

An Application Programming Interface (API) is a defined way for one software system to request data or actions from another system. It exposes a controlled set of operations without requiring the caller to know the internal implementation.

For example, an order-management system may expose an API that lets n8n retrieve orders, create a customer, or update an order status. n8n acts as the client; the external application hosts the API.

API example

Imagine a service provides this endpoint:

GET https://api.example.com/v1/customers/1001

The API may return a JSON representation of customer 1001. The exact URL, fields, authentication and allowed operations are defined by that service's API documentation.

Why APIs matter in n8n

  • Connect SaaS applications that do not have a dedicated n8n node.
  • Read from or write to databases and business platforms through their APIs.
  • Combine information from multiple systems into one workflow.
  • Automate actions such as creating tickets, updating CRM records or sending notifications.
12.2

REST API fundamentals

REST (Representational State Transfer) is an architectural style commonly used to build web APIs. REST APIs typically expose resources through URLs and use standard HTTP methods to operate on those resources.

Core concepts

  • Resource: the thing being accessed, such as customers, orders or invoices.
  • Endpoint: the URL through which a resource or operation is accessed.
  • HTTP method: indicates the intended action.
  • Representation: the data returned or submitted, often JSON.
  • Stateless request: each request carries the information required to process it; the server does not rely on hidden client session state for the request.
Endpoint exampleMeaning
/v1/customersCustomer collection
/v1/customers/1001One customer
/v1/orders?status=openOrders filtered by status
/v1/orders/5001/itemsItems belonging to an order
Important: REST is a design style, not a guarantee that every API behaves identically. Read the provider's API documentation for endpoint paths, required fields, authentication, limits and response formats.
12.3

HTTP methods

HTTP methods communicate the operation the client wants the server to perform.

MethodCommon purposeExampleTypical behaviour
GETRead dataGET /customers/1001Retrieve a resource; should not change server state.
POSTCreate or trigger an operationPOST /customersSubmit data; may create a new resource.
PUTReplace a resourcePUT /customers/1001Usually sends the complete replacement representation.
PATCHPartially update a resourcePATCH /customers/1001Changes selected fields.
DELETEDelete a resourceDELETE /customers/1001Requests removal of a resource.

GET example

GET /v1/orders?status=OPEN
Accept: application/json

POST example

POST /v1/customers
Content-Type: application/json

{
  "name": "Asha Rao",
  "email": "asha@example.com"
}

PUT versus PATCH

If a customer has name, email and phone fields, a PUT request may require the complete resource representation. A PATCH request may send only the phone field that needs changing. Actual requirements depend on the API.

Be careful with write methods. POST, PUT, PATCH and DELETE can modify production data. Test against a sandbox or test record first, and confirm whether repeating a request is safe.
12.4

HTTP Request node

The HTTP Request node is n8n's general-purpose node for making HTTP requests to external endpoints. It is useful when a service has no dedicated integration node or when you need to call a custom endpoint.

Typical configuration process

  1. Add an HTTP Request node to the workflow.
  2. Select the HTTP method.
  3. Enter the endpoint URL.
  4. Choose or configure authentication.
  5. Add headers, query parameters and a body if required.
  6. Configure response handling and options as needed.
  7. Execute with a safe test request and inspect the output.

Example: retrieve orders

Use a GET request to the endpoint specified by your API provider. The following is a documentation-style example, not a live endpoint:

Method: GET
URL: https://api.example.com/v1/orders
Query parameter: status = OPEN
Header: Accept = application/json

After execution, inspect the node output. Depending on the node settings and API response, you may receive an object, an array of records, or response metadata along with the body.

Dynamic values

Fields can use n8n expressions. For example, a customer ID from an incoming item might be referenced as:

https://api.example.com/v1/customers/{{ $json.customerId }}

Ensure the incoming item actually contains customerId. Use the expression editor to select fields and preview evaluated values.

12.5

Request headers

Headers are key-value metadata sent with an HTTP request. They tell the server how to interpret the request or identify the client.

HeaderPurposeExample
AcceptResponse formats the client can acceptapplication/json
Content-TypeFormat of the request bodyapplication/json
AuthorizationAuthentication credentials or tokenBearer <token>
User-AgentIdentifies the calling client (when required)Application-specific value

Example request

GET /v1/customers
Host: api.example.com
Accept: application/json
Authorization: Bearer YOUR_ACCESS_TOKEN

In n8n, add headers using the HTTP Request node's header parameters or a supported authentication credential. Prefer built-in credential handling for secrets instead of typing tokens directly into workflow fields.

12.6

Query parameters

Query parameters are values appended to a URL after ?. They commonly control filtering, sorting, searching, pagination or optional response fields.

GET https://api.example.com/v1/orders?status=OPEN&limit=100

Here, status and limit are query parameters. Multiple parameters are separated by &.

ParameterPossible meaning
status=OPENReturn open orders only
limit=100Return up to 100 records
page=2Request page 2
sort=createdAtSort by creation time, if supported

Configure query parameters in the node's dedicated Query Parameters section rather than manually concatenating strings when possible. This makes expressions and URL encoding easier to manage.

12.7

Request body

A request body carries data from the client to the API. It is commonly used with POST, PUT and PATCH. Many APIs expect JSON, but some use form data, URL-encoded data, XML or binary content.

JSON body example

{
  "customerId": 1001,
  "status": "APPROVED",
  "comment": "Validated by workflow"
}

Dynamic body values in n8n

{
  "customerId": "{{ $json.customerId }}",
  "status": "{{ $json.newStatus }}"
}

When using the expression editor, you can also set individual fields to expressions. Confirm that values are sent with the correct data types: numeric IDs should not accidentally become strings if the API expects numbers.

Content-Type: For a JSON request body, APIs commonly expect Content-Type: application/json. Follow the API's documentation.
12.8

API responses

An HTTP response is the server's reply to a request. It generally contains a status code, response headers and (often) a response body.

Status code
Indicates the outcome category, such as success or client error.
Headers
Provide metadata such as content type, rate-limit information or pagination links.
Body
Contains returned data or an error description, often in JSON.

Example JSON response

{
  "data": [
    { "id": 1001, "name": "Asha Rao" },
    { "id": 1002, "name": "Ravi Kumar" }
  ],
  "nextPage": 2
}

In n8n, inspect the HTTP Request node's output to understand its structure. If the API nests records under data, downstream nodes should reference that path rather than assuming the records are at the root.

12.9

HTTP status codes

Status codes are grouped into classes. These are common examples; an API may define additional application-specific error codes in its response body.

CodeMeaningTypical next step
200 OKRequest succeededProcess response.
201 CreatedResource createdCapture returned ID/location.
202 AcceptedAccepted for asynchronous processingPoll a status endpoint if required.
204 No ContentSuccess with no response bodyContinue without expecting JSON data.
400 Bad RequestInvalid request or payloadCheck endpoint, parameters and body.
401 UnauthorizedMissing or invalid authenticationCheck token, credentials and expiry.
403 ForbiddenAuthenticated but not permittedCheck scopes, roles and permissions.
404 Not FoundEndpoint or resource not foundCheck URL, API version and ID.
409 ConflictConflict with current resource stateCheck duplicates or version/state rules.
429 Too Many RequestsRate limit exceededWait according to provider guidance.
500 Internal Server ErrorServer-side failureRetry cautiously; capture details.
502 / 503 / 504Gateway, service unavailable or timeoutRetry with backoff when safe.
A 200 response does not always mean the business operation succeeded. Some APIs return an application-level error inside a 200 response body. Validate both HTTP status and response content where the provider requires it.
12.10

Pagination

APIs often split large result sets into pages to reduce response size and server load. A workflow must request each page until the API indicates there are no more records.

Common pagination patterns

  • Page number: ?page=1&limit=100, then page 2, 3, and so on.
  • Offset / limit: ?offset=0&limit=100, then offset 100, 200, etc.
  • Cursor: response provides a next cursor that is sent in the next request.
  • Next URL: response provides a complete URL or link for the next page.

How to implement in n8n

First check whether the HTTP Request node version and the API support built-in pagination options. Configure the pagination parameter or next-page expression according to the provider's response format. If the API uses a custom pattern, build a controlled loop using workflow logic, carrying the next page number or cursor between requests.

Page-number example (conceptual)

Initial page = 1
Page size = 100

Repeat:
  Call GET /orders?page={{ page }}&limit=100
  Process or collect returned records
  If response says another page exists:
      page = page + 1
  Else:
      stop
Avoid infinite pagination loops. Define a reliable stop condition, handle empty pages, and consider a maximum-page safeguard. For cursor APIs, use the exact cursor returned by the server rather than inventing or incrementing one.
12.11

Rate limiting

Rate limiting restricts how many requests a client can make during a time window. For example, an API may allow 100 requests per minute per account. Limits vary by provider, endpoint, user or application.

How to recognize it

  • The API returns HTTP 429 Too Many Requests.
  • Response headers may include limit, remaining-request or reset-time information.
  • The response body may explain the quota or retry delay.

Good practices

  • Read the provider's quota documentation.
  • Use batching or bulk endpoints when available.
  • Reduce unnecessary repeated calls; cache reference data where appropriate.
  • Limit concurrency when many items trigger requests.
  • Respect Retry-After when provided.
  • Use backoff rather than immediately sending another request.
12.12

API retries

A retry repeats a request after a failure. Retries help with temporary network issues, timeouts and service interruptions, but they must be designed carefully.

Exponential backoff

Instead of retrying every second, increase the delay between attempts. A simple pattern is 1 second, 2 seconds, 4 seconds, 8 seconds, subject to a maximum delay and maximum attempt count.

AttemptExample wait
11 second
22 seconds
34 seconds
48 seconds

n8n implementation approaches

  • Use the HTTP Request node's available retry / timeout options where suitable for your n8n version.
  • Use an error workflow or controlled loop with a Wait node for custom retry policies.
  • Set a maximum number of attempts and route exhausted failures to an alert or error log.
  • Capture endpoint, attempt number, status code and error message for diagnosis.
Idempotency matters. Repeating a GET is generally safe. Repeating a POST that creates a payment or order could create duplicates unless the API supports an idempotency key or another deduplication mechanism. Do not blindly retry every 4xx or 5xx response.
12.13

API authentication

Authentication establishes who or what is making the request. Authorization determines what that identity is allowed to do. APIs may use API keys, bearer tokens, OAuth 2.0, basic authentication, signed requests or other mechanisms.

Authentication design checklist

  • Identify the exact authentication method required by the provider.
  • Use n8n credentials or an approved secret store for sensitive values.
  • Request only the permissions needed by the workflow.
  • Use HTTPS so credentials are protected in transit.
  • Plan for token expiry, rotation and revocation.
  • Never expose secrets in workflow names, notes, logs, screenshots or exported examples.
12.14

OAuth 2.0

OAuth 2.0 is an authorization framework that lets an application obtain limited access to a resource on behalf of a user or as an application, without asking the workflow to store the user's password.

Typical authorization-code flow

  1. The user is redirected to the provider's authorization page.
  2. The user signs in and approves requested permissions (scopes).
  3. The provider redirects to the registered callback URL with an authorization code.
  4. The client exchanges the code for an access token, and often a refresh token.
  5. The client sends the access token when calling protected API endpoints.
  6. When the access token expires, a refresh flow may obtain a new one.

OAuth terms

TermMeaning
ClientThe application requesting access (for example, an n8n integration).
Resource ownerThe user or entity that can grant access.
Authorization serverIssues tokens after the required authorization process.
Access tokenCredential used to access protected resources.
Refresh tokenCredential used to obtain a new access token when supported.
ScopeDefines the permissions being requested.
Redirect URIRegistered callback destination for the authorization response.

Many n8n integrations support OAuth credential setup. The exact fields and callback URL depend on the node, n8n deployment and provider. Register the callback URL shown by n8n in the provider's developer portal.

Treat access and refresh tokens as secrets. Do not manually paste them into Code nodes or workflow data unless there is a carefully controlled, documented reason.
12.15

Bearer tokens

A bearer token is a credential: whoever possesses it may be able to use the permissions associated with it. It is commonly sent in the HTTP Authorization header.

Authorization: Bearer ACCESS_TOKEN_VALUE

In n8n, use the appropriate credential or authentication option. If the API specifically requires a bearer token, configure it there rather than hardcoding it in an expression.

Security practices

  • Keep tokens out of source code and shared workflow exports.
  • Use HTTPS only.
  • Grant minimum required scopes.
  • Rotate or revoke exposed tokens immediately.
  • Do not write full authorization headers to logs.
12.16

API keys

An API key is a value issued by a provider to identify or authenticate an application. Depending on the provider, it may be sent in a header or as a query parameter.

Header-based example

GET /v1/products
X-API-Key: YOUR_API_KEY

Query-string example

GET https://api.example.com/v1/products?api_key=YOUR_API_KEY

Header-based transmission is generally preferable when the provider supports it, because URLs are more likely to appear in logs, browser history and monitoring systems. Always follow the provider's documented method.

API keyOAuth 2.0
Often identifies an application or project.Provides delegated or application authorization using tokens.
May be long-lived until rotated or revoked.Access tokens are often short-lived; refresh may be supported.
Permission granularity depends on provider.Scopes and consent commonly define access.
Simple for some service-to-service integrations.Useful when access must be granted without sharing a user's password.

Practical labs

Lab 1 – Call a public test API

Goal: understand a basic GET request and JSON output. Use a public test service such as JSONPlaceholder, and verify its current documentation and usage guidance before relying on it.

  1. Create a new n8n workflow and add a Manual Trigger.
  2. Add an HTTP Request node.
  3. Set method to GET and use https://jsonplaceholder.typicode.com/posts/1.
  4. Execute the node and inspect the returned JSON fields.
  5. Add an Edit Fields node and retain only the fields id, title and userId.

Lab 2 – Send a POST request

Goal: submit JSON to a test endpoint.

  1. Use the same test service's posts endpoint: https://jsonplaceholder.typicode.com/posts.
  2. Choose POST and configure a JSON body with a sample title, body and userId.
  3. Execute and inspect the response, including the returned ID.
  4. Remember that public test services may simulate writes rather than persist them.

Lab 3 – Handle API errors

  1. Call a deliberately invalid test URL or resource.
  2. Observe the status code and error output.
  3. Configure the workflow's error handling approach for your n8n version.
  4. Route failure details to a log or notification, without including credentials.

Lab 4 – Design a paginated integration

  1. Choose an API with documented pagination.
  2. Identify its page, offset or cursor mechanism.
  3. Configure built-in pagination if supported, or construct a controlled loop.
  4. Stop when the API provides no next page/cursor.
  5. Test with a small page size and verify no records are skipped or duplicated.

Production-ready API workflow pattern

Recommended operational controls

  • Set sensible timeouts and bounded retry counts.
  • Respect rate limits and provider retry guidance.
  • Validate response shape before downstream processing.
  • Log request correlation IDs and non-sensitive error details.
  • Protect credentials and restrict who can edit or execute workflows.
  • Use idempotency or deduplication for operations that create or update records.
  • Monitor workflow failures, duration, record counts and API quota usage.

Interview questions and answers

  1. What is an API?
    An interface that allows software systems to exchange data or invoke operations through a defined contract.
  2. What is a REST API?
    An API designed around resource-oriented URLs and standard HTTP semantics, commonly returning JSON.
  3. What is the difference between GET and POST?
    GET retrieves data; POST submits data, often to create a resource or initiate an operation.
  4. PUT versus PATCH?
    PUT commonly replaces a resource representation; PATCH applies partial changes.
  5. What is an endpoint?
    A URL identifying an API resource or operation.
  6. What are HTTP headers?
    Metadata sent with a request or response, such as content type and authorization.
  7. What are query parameters?
    URL parameters commonly used for filtering, sorting and pagination.
  8. What is a request body?
    The payload sent to an API, often JSON for create or update operations.
  9. What does HTTP 201 mean?
    The request succeeded and a resource was created.
  10. What is the difference between 401 and 403?
    401 indicates missing or invalid authentication; 403 indicates the caller is not permitted to perform the operation.
  11. What does 429 mean?
    The client exceeded a rate limit or request quota.
  12. What is pagination?
    Retrieving a large result set in smaller pages or cursor-based segments.
  13. What is cursor pagination?
    The API returns a cursor that identifies where the next request should continue.
  14. What is rate limiting?
    A restriction on request volume during a defined time window.
  15. What is exponential backoff?
    A retry strategy that increases the delay between successive attempts.
  16. Why should POST retries be treated carefully?
    Repeated requests may create duplicate resources or repeat a business action.
  17. What is idempotency?
    A property where repeating the same operation has the same intended effect as performing it once.
  18. What is OAuth 2.0?
    An authorization framework for granting limited access using tokens rather than sharing a user's password with the client.
  19. What is a bearer token?
    A token whose possession grants the permissions associated with it.
  20. What is an API key?
    A provider-issued key used to identify or authenticate an application or project.
  21. Where should API secrets be stored in n8n?
    In n8n credentials or an approved secret-management mechanism, not hardcoded in workflow logic.
  22. What is the HTTP Request node used for?
    Making configurable HTTP calls to APIs and web services from a workflow.
  23. How do you handle an API returning 429?
    Respect the provider's retry guidance, wait as directed, reduce request volume and retry with bounded backoff.
  24. How would you design a reliable API integration?
    Use secure credentials, validation, pagination, rate-limit handling, bounded retries, idempotency, logging and monitoring.
