Learning objectives

Chapter overview

A trigger is the entry point that starts a workflow execution. Choosing the right trigger determines when automation runs, how input data arrives and what operational controls are needed.

UnderstandRecognize event-driven, scheduled, polling and manual starts.
ConfigureSet schedules, webhook endpoints, form fields and event filters.
ControlHandle timezones, duplicate events, polling windows and conditions.

What is a trigger?

Trigger fundamentals

A trigger node starts a new workflow execution when a configured event happens or a configured schedule fires. A Manual Trigger is started by a person during development or testing.

Common trigger models

ModelHow it worksTypical use
ManualA user explicitly starts a test.Development and troubleshooting.
ScheduledA time-based rule starts an execution.Daily reporting, periodic checks.
Webhook / push eventAn external system sends a request or event.Order created, payment event.
Pollingn8n periodically checks a source for new or changed data.Mailbox or database checks.
Application eventAn integration listens for or checks a supported app event.New issue, new row, new message.
Selection rule: Prefer push/webhook events when the source supports reliable event delivery. Use polling when push events are unavailable or unsuitable. Use Schedule Trigger for time-driven work, not as a substitute for a true event when immediacy is required.
6.1

Manual Trigger

1 · Manual Trigger

The Manual Trigger starts a workflow when a user manually executes it from the editor. It is primarily used for building, testing and debugging workflows.

How it works

User clicks test / execute ↓ Manual Trigger ↓ Connected workflow nodes

Typical use cases

  • Test a SQL query or API request.
  • Validate expressions and data transformations.
  • Run a one-off data cleanup after review.
  • Develop a workflow before adding a production trigger.

How to configure

  1. Create a new workflow.
  2. Add the Manual Trigger node.
  3. Connect it to the next node, such as Edit Fields or HTTP Request.
  4. Configure the downstream node.
  5. Click the test or execute control.
  6. Inspect the execution and node outputs.

Important points

  • Manual Trigger does not itself listen for external events or run on a schedule.
  • It is useful for controlled tests with known inputs.
  • For repeatable tests, provide representative test data using suitable nodes or pinned data where supported.
Exercise: Add Manual Trigger → Edit Fields. Create employee_id, employee_name and department. Run it and inspect the output.
6.2

Schedule Trigger

2 · Schedule Trigger

The Schedule Trigger starts a workflow at configured times or intervals. It is commonly used for recurring operational tasks.

Common scheduling patterns

RequirementExample
Every few minutesCheck for pending records every 10 minutes.
HourlyCollect operational metrics every hour.
DailyGenerate a report every day at 8:00 AM.
WeeklySend a weekly summary every Monday.
MonthlyRun a month-end validation.
Custom cronRun on a specified minute, hour, day or month pattern.

Configuration example

Requirement: run a daily operational summary at 8:00 AM India Standard Time.

  • Node: Schedule Trigger
  • Frequency: daily
  • Time: 08:00
  • Timezone: Asia/Kolkata (verify workflow or instance timezone configuration)

Important considerations

  • The workflow generally needs to be saved and published/activated for automatic scheduled execution, depending on the current n8n release lifecycle.
  • Verify the workflow or instance timezone. A correct cron expression with the wrong timezone runs at the wrong local time.
  • Consider daylight-saving time for regions that observe it.
  • Consider what happens if a previous run is still in progress when the next schedule fires.
  • Make scheduled jobs safe against duplicate processing and partial failures.
Do not confuse: Schedule Trigger defines when a workflow starts. The Wait node pauses an execution already in progress; it is not a replacement for a recurring schedule.
6.3

Webhook Trigger

3 · Webhook Trigger

A Webhook Trigger provides an HTTP endpoint that an external application can call to start a workflow. The incoming request can contain data in its URL, query parameters, headers or request body.

Common use cases

  • Receive an order-created event from an e-commerce platform.
  • Receive a payment status notification.
  • Start a workflow when an external application sends a callback.
  • Expose an internal automation endpoint to an approved application.

Typical configuration elements

SettingPurpose
HTTP methodDefines accepted request method, such as GET or POST.
PathDefines the endpoint path.
AuthenticationControls who can call the endpoint, where configured.
Response modeControls when and how the HTTP caller receives a response.
Response dataDefines the response content when configured in the node or with Respond to Webhook.

Test URL versus production URL

n8n provides a test webhook URL for development and a production webhook URL for active workflow use. The test URL is used while listening for a test event in the editor. The production URL is used when the workflow is active/published according to the release lifecycle. Configure the external system with the correct URL.

Example request payload

{
  "event": "order.created",
  "order_id": 98765,
  "customer": {
    "name": "Alex Morgan",
    "email": "alex@example.com"
  },
  "amount": 2499
}

Security and reliability

  • Use authentication or signature verification where supported and appropriate.
  • Use HTTPS for public endpoints.
  • Validate the request body and required fields.
  • Do not trust a caller-provided event name or amount without validation.
  • Protect against replay and duplicate delivery with an idempotency key or event ID.
  • Return an appropriate response and avoid exposing internal error details.
  • For public deployments, configure the correct webhook base URL and reverse proxy settings.
Exercise: Create a Webhook Trigger with POST method. Send a test JSON payload using an API client and inspect the received body in the execution data.
6.4

Form Trigger

4 · Form Trigger

The n8n Form Trigger starts a workflow when a user submits a form. It is useful when an automation needs a simple user-facing input page without building a separate front end.

Typical use cases

  • IT service request intake.
  • Access request submission.
  • Employee onboarding information.
  • Data correction requests.
  • Approval or feedback collection.

Form workflow pattern

User opens form ↓ Enters fields and submits ↓ Form Trigger receives submission ↓ Validate → Store → Notify / route

Common form design elements

ElementExample
Text fieldRequester name or ticket title.
Email fieldRequester email address.
DropdownRequest category or priority.
TextareaIssue description.
Required validationEnsure mandatory fields are supplied.
Submit / response pageShow a confirmation after submission.

Example: support request form

{
  "requester": "Alex Morgan",
  "email": "alex@example.com",
  "category": "Access",
  "priority": "High",
  "description": "Unable to access reporting workspace"
}

Best practices

  • Collect only the information required for the process.
  • Mark mandatory fields and validate email formats.
  • Do not collect passwords or secrets in a general-purpose form.
  • Restrict access or add authentication where the form contains sensitive information.
  • Validate submitted values again inside the workflow.
  • Provide a clear success or failure response.
Terminology: n8n's built-in Form Trigger is different from a third-party form integration trigger such as Typeform or Jotform. Each has its own authentication, event and field configuration.
6.5

Email Trigger

5 · Email Trigger

An email trigger starts a workflow when a matching email is received or detected. In n8n, the built-in Email Trigger (IMAP) can monitor an email account using IMAP. Other email integrations may offer their own trigger nodes and event mechanisms.

Typical use cases

  • Process incoming support requests.
  • Extract invoice details from email attachments.
  • Classify messages and route them to teams.
  • Monitor alerts arriving in a dedicated mailbox.

Email automation pattern

New email detected ↓ Email Trigger (IMAP / app trigger) ↓ Read sender, subject, body, attachments ↓ Filter / classify / extract ↓ Create ticket or notify team

What to configure or verify

AreaWhat to check
ConnectionIMAP host, port, encryption and account authentication.
MailboxCorrect folder or mailbox to monitor.
Search criteriaUnread status or supported filters, if available.
AttachmentsWhether attachment data is downloaded and how binary data is represented.
Polling behaviourHow frequently messages are checked and how processed messages are handled.

Important email considerations

  • Use a dedicated mailbox where possible.
  • Protect OAuth tokens or mailbox credentials.
  • Prevent reprocessing using message IDs or a processed-state mechanism.
  • Validate attachment type and size before processing.
  • Be careful with untrusted email content and links.
  • Plan for mail server throttling and temporary connection failures.
Note: Email Trigger (IMAP) is not the same as an email action node such as Send Email. One detects incoming messages; the other sends messages. App-specific triggers may use a different provider API and polling model.
6.6

Database Triggers and Polling Patterns

6 · Database triggers and polling patterns

Many databases do not provide a universal event trigger that n8n can subscribe to in the same way as a webhook. A common design is scheduled polling: n8n periodically queries for new or changed rows and starts processing them.

6.1 Database trigger versus polling

PatternHow it worksConsiderations
Native database event / notificationDatabase emits or exposes an event mechanism that a compatible integration can listen to.Requires database-specific support, setup and permissions.
Polling queryn8n runs a query on an interval to find new or changed rows.Simple and broadly applicable, but not instantaneous.
Change tracking / CDC feedA database or data platform exposes change records for consumers.More scalable for some cases, but requires infrastructure and careful checkpointing.
Outbox patternApplication writes business data and an event record in the same transaction; automation consumes the outbox.Improves reliable event handoff when designed correctly.

6.2 Example: poll for new orders

Suppose a SQL table contains orders with order_id, created_at and status. A scheduled workflow can query rows created since the last successful checkpoint.

SELECT
    order_id,
    created_at,
    status
FROM dbo.Orders
WHERE created_at > @LastSuccessfulTimestamp
ORDER BY created_at, order_id;

This is a conceptual SQL example. The parameter and checkpoint storage must be implemented for your database and workflow design; do not paste the placeholder parameter into a node without defining it.

6.3 Watermark and checkpoint design

  • Use a stable unique key, such as order_id.
  • Store the last successfully processed timestamp or sequence value.
  • Use a deterministic ordering, such as timestamp plus primary key.
  • Consider an overlap window to catch late-arriving or same-timestamp records.
  • Deduplicate records using a unique event or business key.
  • Advance the checkpoint only after successful processing, or use a durable work queue/outbox pattern.
  • Handle updates as well as inserts if the requirement includes changed records.

6.4 Example: overlapping polling window

Instead of querying strictly after the last timestamp, a design may look back several minutes and deduplicate by primary key. This helps handle delayed commits or timestamp precision issues, but it means duplicate handling is mandatory.

6.5 Database-specific triggers

Some n8n integrations expose database trigger nodes or notification-based mechanisms for specific platforms and configurations. For example, the Postgres Trigger node is database-specific; do not assume the same capability exists for every SQL database. Always inspect the supported node documentation and required database permissions.

Production guidance: Avoid an uncontrolled full-table scan every minute. Use indexed columns, incremental predicates, reasonable polling intervals, pagination or batching, and monitor database load.
6.7

Application Event Triggers

7 · Application event triggers

Application event triggers start workflows when an event occurs in a connected service. Examples include a new CRM contact, a new issue, a new file, a new form response or a new message.

Examples by application

ApplicationPossible eventAutomation idea
Gmail / OutlookNew email or message detectedClassify and route support requests.
GitHub / GitLabNew issue, pull request or repository event (node-dependent)Notify engineering or create a work item.
Google SheetsNew or updated row, where supportedValidate and load submitted data.
Salesforce / HubSpotNew or updated CRM record, where supportedSync customer information.
Slack / TeamsMessage or supported eventStart an approval or incident workflow.
Cloud storageNew file or object eventValidate and process uploaded files.

7.1 Push versus polling application triggers

Push / webhook stylePolling style
Provider sends an event to a registered endpoint.n8n checks the provider periodically.
Usually lower event latency.Latency depends on polling interval.
Requires endpoint registration and provider support.Requires API access and polling limits to be respected.

7.2 Things to check for each app trigger

  • Which event types are supported by the node.
  • Whether it uses webhooks, polling or another mechanism.
  • Required OAuth scopes, API keys or permissions.
  • Polling interval and provider API rate limits.
  • How the integration identifies already-seen events.
  • Whether the provider retries webhook delivery.
Rule: Do not assume every application trigger is real-time. Read the node documentation to identify whether it uses a webhook subscription or periodic polling.

Cron Scheduling Concepts

8 · Cron scheduling concepts

Cron is a compact expression format for describing recurring time schedules. n8n's Schedule Trigger supports interval-based and cron-style scheduling options; confirm the expression format and supported fields in your version.

8.1 Five-field cron structure

┌──────── minute        (0 - 59)
│ ┌────── hour          (0 - 23)
│ │ ┌──── day of month  (1 - 31)
│ │ │ ┌── month         (1 - 12)
│ │ │ │ ┌ day of week   (0 - 7, convention-dependent)
│ │ │ │ │
* * * * *

8.2 Examples

Cron expressionMeaning
0 8 * * *Every day at 08:00.
*/15 * * * *Every 15 minutes.
0 9 * * 1-5At 09:00 Monday to Friday, subject to day-of-week convention.
30 18 * * 5At 18:30 on Friday, subject to day-of-week convention.
0 0 1 * *At midnight on the first day of each month.

8.3 Special characters

SymbolCommon meaningExample
*Every allowed value* * * * *
,List of values0 8,17 * * *
-Range0 9 * * 1-5
/Step interval*/10 * * * *

8.4 Timezone and daylight saving

  • Confirm the workflow timezone or instance timezone used by the Schedule Trigger.
  • Use an IANA timezone such as Asia/Kolkata when that is the intended local timezone.
  • For daylight-saving regions, consider skipped or repeated local times during clock changes.
  • Test the next expected run time before activating a critical schedule.
Cron caution: Cron implementations can differ in field count and day-of-week semantics. Validate the expression in the n8n node UI or documentation rather than assuming every external cron calculator uses the same convention.
6.9

Trigger Conditions

9 · Trigger conditions

Trigger conditions determine which events should start useful downstream processing. Depending on the trigger, filtering can be configured in the trigger node, at the source application, in a query, or immediately after the trigger with a Filter or IF node.

9.1 Common condition examples

Trigger sourceConditionPurpose
EmailSender is a support mailbox or subject contains “Incident”Process only relevant emails.
Webhookevent == "order.created"Handle only order-created events.
Database pollingstatus = 'NEW'Retrieve unprocessed rows.
Application eventRecord type equals “Case”Ignore unrelated event types.
ScheduleRun only on business daysAvoid unnecessary weekend runs.

9.2 Filter after trigger

Trigger → Validate event payload → IF / Filter ↙ ↘ Match No match ↓ ↓ Process event Stop / ignore

9.3 Trigger filter versus workflow filter

Filter at source / triggerFilter after trigger
Reduces irrelevant events or records before downstream processing, if supported.Receives the event, then decides whether to continue.
Can reduce API calls and execution volume.Provides flexible logic and easier inspection of received payload.

9.4 Validation checklist

  • Check required fields exist.
  • Validate event type and source identity.
  • Validate timestamp, IDs and data types.
  • Reject or quarantine malformed payloads.
  • Deduplicate repeated events.
  • Log why an event was ignored where auditability matters.
Design principle: Treat external trigger payloads as untrusted input. Validate them before performing write operations or invoking downstream systems.
6.10

Multiple Trigger Workflows

10 · Multiple trigger workflows

A workflow can contain more than one trigger node. Each trigger provides a separate entry point into the workflow. When one trigger fires, it starts an execution through the path connected to that trigger.

10.1 Example: two ways to start a report

Manual Trigger ───────┐ ├→ Shared report logic → Generate → Notify Schedule Trigger ─────┘

This design can allow a developer to test the same downstream logic manually while the scheduled trigger runs it automatically. Keep in mind that trigger-specific input data may differ, so normalize the payload before shared processing.

10.2 Example: webhook and schedule

Webhook Trigger → Normalize event ─┐ ├→ Shared validation → Process Schedule Trigger → Fetch pending ───┘

This can be useful when the system supports immediate event processing but also needs a periodic reconciliation run. The two entry paths should be designed so they do not process the same business record twice.

10.3 Design considerations

  • Use clear node names to identify each trigger source.
  • Normalize different payload structures before shared downstream nodes.
  • Consider whether one trigger can start while another execution is still processing.
  • Use idempotency keys or deduplication to prevent duplicate business actions.
  • Keep security and authentication appropriate for each entry path.
  • Test each trigger independently and then test shared logic.
  • Do not assume all triggers fire together; each trigger is an independent start mechanism.

10.4 When to use separate workflows instead

Use separate workflows when trigger security, ownership, deployment lifecycle, error handling or business logic differs substantially. Shared logic can be moved into a reusable sub-workflow when that improves maintainability.

Important: Multiple trigger nodes do not mean a single execution starts from every trigger at once. Each event or manual start creates its own workflow execution.
