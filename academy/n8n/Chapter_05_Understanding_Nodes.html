Learning objectives

Chapter overview

A node is the building block of an n8n workflow. This chapter teaches you to select the right node, configure it, understand the data it receives and produces, and troubleshoot its execution.

RecognizeIdentify node categories and their roles.
ConfigureSet parameters, credentials and options.
Understand dataInspect input items, JSON and output items.
DebugTest nodes and interpret execution results.
Terminology note: “Trigger” and “action” describe a node's role in a workflow. “Core”, “app integration”, “AI” and “community” describe broad node families or origins. These categories can overlap: an app integration may provide both a trigger node and an action node.
5.1

What is a node?

1 · Node fundamentals

A node is an individual component in n8n that performs a specific task. Nodes are placed on the workflow canvas and connected to form an automation.

Examples include receiving a webhook, reading rows from a database, calling an API, transforming JSON, checking a condition or sending an email.

[Trigger] → [Retrieve data] → [Transform data] → [Business rule] → [Action]

1.1 Anatomy of a node

PartMeaning
Node nameThe label displayed on the canvas.
Node typeThe underlying implementation or integration, such as HTTP Request or Gmail.
Input connectorReceives data from an upstream node for nodes that use main input.
Output connectorPasses results to downstream nodes; some nodes have multiple outputs.
ParametersConfigure what operation the node performs.
SettingsConfigure supported node-level behaviour.
Execution resultShows whether the node ran and what it produced.

1.2 Example

For an employee notification workflow:

Schedule Trigger → Microsoft SQL → Edit Fields → IF → Outlook

Each node performs one responsibility. The database node retrieves information, Edit Fields shapes the data, IF applies a rule and Outlook sends a message.

Design principle: Prefer clear, single-purpose nodes and meaningful node names. A workflow is easier to test and maintain when each step has an understandable responsibility.
5.2

Trigger Nodes

2 · Trigger nodes

2.1 What is a trigger node?

A trigger node starts a workflow when a configured event or condition occurs. A workflow can also be started manually for testing. Trigger nodes generally begin an execution rather than receiving ordinary main input from a previous node.

2.2 Common trigger types

TriggerHow it startsExample
Manual TriggerA user starts a test run.Test an employee data workflow.
Schedule TriggerA configured schedule or interval.Run a daily report at 8 AM.
WebhookAn external system sends an HTTP request.Receive an order-created event.
App TriggerA supported event in an integrated application.New email or new CRM record.
Polling triggerPeriodically checks a service for new events.Check a mailbox or external API.

2.3 Trigger workflow pattern

Event / Schedule / Manual start ↓ Trigger node ↓ Business workflow

2.4 Important considerations

  • Configure the trigger's event, schedule or webhook settings correctly.
  • For webhook triggers, distinguish test URLs from production URLs where the node provides both.
  • Ensure the workflow is published or active as required for automatic trigger-based runs.
  • For polling triggers, understand the polling interval and API rate limits.
  • Consider duplicate events and make downstream processing safe to retry.
Practical task: Create a Manual Trigger workflow, then create a separate Schedule Trigger workflow. Test the manual one and inspect the scheduled trigger's timezone and interval settings.
5.3

Action Nodes

3 · Action nodes

Action nodes perform work after a workflow has started. They commonly interact with applications, retrieve or update records, send messages, or carry out a business operation.

Action typeExample node operationBusiness use
Read / retrieveGet a row, fetch a record, list filesRetrieve source data.
CreateCreate a CRM contact or ticketRegister a new business record.
UpdateUpdate a spreadsheet or database rowSynchronize information.
SendSend email or chat messageNotify a team.
DeleteDelete a supported recordRemove obsolete data, with safeguards.

3.1 Example: alert notification

Webhook Trigger → Parse alert → Create incident → Send Teams notification

3.2 Trigger versus action

Trigger nodeAction node
Starts a workflow when an event occurs or a schedule fires.Performs an operation during an execution.
Examples: Webhook, Schedule Trigger, Gmail Trigger.Examples: Send Email, Create Ticket, Insert Row.
Careful with write actions: Test create, update and delete operations against non-production data first. Use filters and idempotency controls to avoid accidental duplicate or destructive changes.
5.4

Core Nodes

4 · Core nodes

Core nodes provide general-purpose capabilities used across many workflows. They are not tied to one external application.

NodePurposeExample
IFRoutes items based on a condition.Salary greater than 50,000?
SwitchRoutes data across multiple cases.Route incidents by severity.
MergeCombines data from multiple inputs.Combine employee and department data.
Loop Over ItemsProcesses items in batches or a loop pattern.Process a large list in controlled batches.
Edit Fields (Set)Adds, changes or selects fields.Rename fields or prepare an email payload.
CodeRuns custom JavaScript or Python where supported by the node's current options.Calculate a derived value.
FilterKeeps items that meet conditions.Keep only failed pipeline runs.
LimitRestricts the number of items.Process a small sample.
WaitPauses execution until a configured condition or time.Wait before retrying or continuing.
HTTP RequestMakes HTTP calls to APIs and endpoints.Retrieve data from a REST API.

4.1 Example: IF node

Input item → IF: status equals "Failed" ↙ ↘ True False ↓ ↓ Send alert Continue flow

4.2 Example: Edit Fields node

Input JSON:

{
  "first_name": "Alex",
  "last_name": "Morgan",
  "monthly_salary": 60000
}

You can create a field such as full_name and map it from the first and last name values using an expression. The node can also be configured to include or exclude other input fields.

Remember: Core nodes often shape the logic and data flow between trigger and app-integration nodes. They are the building blocks of complex automations.
5.5

App Integration Nodes

5 · App integrations

App integration nodes connect n8n to external products and services. A supported app may provide trigger events, action operations, or both.

5.1 Examples of app integrations

Application categoryExamplesPossible automation
Email and collaborationMicrosoft Outlook, Gmail, Slack, TeamsRead messages and send notifications.
DatabasesMicrosoft SQL, PostgreSQL, MySQLQuery, insert or update records.
ProductivityGoogle Sheets, NotionMaintain operational trackers.
CRM and supportSalesforce, HubSpot, ZendeskCreate contacts, tickets and updates.
Cloud storageGoogle Drive, OneDrive, S3Upload, download or process files.

5.2 Example: database to email

Schedule Trigger → Microsoft SQL: Execute query → IF: rows found? ↓ yes Microsoft Outlook: Send email

5.3 Credentials

Many integrations require credentials such as OAuth2, API keys, username/password or another supported authentication method. Use n8n's credential management rather than hardcoding secrets into node parameters or Code nodes.

5.4 What if an app operation is missing?

Check the node's supported operations and the service API. The HTTP Request node can often call an API endpoint when a dedicated node does not expose the operation you need. You must still handle authentication, pagination, rate limits and response errors.

Practical task: Add an app node you use at work or in a test account. Explore its available resources and operations without executing any write action against production data.
5.6

AI Nodes

6 · AI nodes

AI nodes support workflows that use language models and related components to interpret text, generate responses, classify information, retrieve context or call tools.

6.1 Common AI components

ComponentRoleExample
AI AgentCoordinates model reasoning and tool use for a task.Investigate a support request using connected tools.
Chat ModelProvides language-model responses.Connect a supported model provider.
MemoryProvides conversation context where configured.Retain relevant chat history.
ToolAllows an agent to invoke a supported capability.Search a knowledge base or query an approved API.
EmbeddingsConverts text into vector representations.Prepare documents for semantic retrieval.
Vector StoreStores and retrieves vector data.Find relevant knowledge-base passages.
Text / information extractionExtracts structured information from unstructured content.Extract invoice fields.

6.2 Conceptual AI Agent architecture

6.3 Example: incident classification

New incident → AI Agent → classify severity and summarize ↓ Approved notification tool ↓ Support team

6.4 Important AI considerations

  • Model output can be incorrect; validate critical decisions.
  • Restrict tools to the minimum permissions needed.
  • Do not expose secrets or sensitive data in prompts unnecessarily.
  • Monitor token usage, latency and provider costs.
  • Use structured output and validation when downstream systems expect a strict schema.
  • Human approval should be considered for high-impact actions.
Important: An AI Agent is not simply a regular action node. It can decide whether and how to use connected tools within its configured scope. Design permissions and guardrails carefully.
5.7

Community Nodes

7 · Community nodes

Community nodes are packages contributed by third-party developers or the n8n community. They can add integrations or capabilities that are not available in the built-in node set.

7.1 Why use community nodes?

  • Connect to niche or specialized services.
  • Access additional operations.
  • Use community-built functionality.
  • Extend self-hosted n8n for specific requirements.

7.2 Community node installation concept

7.3 Before installing a community node

  1. Verify the package name and maintainer.
  2. Review source code, release history and issue activity where possible.
  3. Check permissions and dependencies.
  4. Understand that a node package runs within your n8n environment and may have access to sensitive runtime resources.
  5. Test in a non-production instance.
  6. Keep the package updated and remove it if no longer required.

7.4 Availability and installation

Installation methods and eligibility vary by deployment type, version and plan. Self-hosted instances may support UI, manual or environment-variable installation methods, subject to configuration. Managed cloud environments may restrict installation to supported or verified packages.

Security: Treat a community node like third-party software. Do not install an unknown package in a production instance without security review. n8n's security audit can report community and custom nodes.
5.8

Node Inputs and Outputs

8 · Inputs and outputs

8.1 What is input?

Input is the data a node receives from a previous node or from its trigger context. For many regular nodes, n8n passes data as an array of items. Each item commonly contains a json object and may also contain binary data.

8.2 What is output?

Output is the data produced by a node. Downstream nodes can use this output as their input. A node may return zero, one or many items depending on its operation and input.

8.3 Example item structure

[
  {
    "json": {
      "employee_id": 101,
      "employee_name": "Alex",
      "monthly_salary": 60000
    }
  },
  {
    "json": {
      "employee_id": 102,
      "employee_name": "Jordan",
      "monthly_salary": 55000
    }
  }
]

8.4 Input-to-output example

Suppose a Code node receives a monthly salary and adds an annual salary field:

const items = $input.all();

return items.map(item => ({
  json: {
    ...item.json,
    annual_salary: item.json.monthly_salary * 12
  }
}));

For a salary of 60,000, the output includes annual_salary: 720000.

8.5 JSON and binary data

JSON is commonly used for structured fields such as IDs, names, dates and statuses. Binary data is used for file content such as images, PDFs and spreadsheets. Some nodes accept or produce binary data alongside JSON metadata.

8.6 Data mapping and expressions

Expressions let you reference data from earlier nodes. For example, {{ $json.employee_name }} references the employee_name field on the current item. The input panel can help you inspect fields and map them into node parameters.

Debugging rule: When a downstream node behaves unexpectedly, inspect the exact input item it received. Do not assume the upstream node produced the field or data type you expected.
5.9

Node Configuration

9 · Node configuration

Node configuration defines what the node does and how it performs the operation. The exact fields vary by node.

9.1 Common configuration areas

AreaWhat you configure
ParametersResource, operation, field values, conditions, URL, method and other node-specific inputs.
CredentialsAuthentication used to connect to an external service.
OptionsAdditional behaviour such as pagination, response handling or other node-specific settings.
SettingsSupported node execution behaviour, such as error handling options.
ExpressionsDynamic values sourced from incoming or earlier workflow data.

9.2 Example configuration: HTTP Request

ParameterExampleExplanation
MethodGETHTTP operation to perform.
URLhttps://api.example.com/employeesEndpoint to call (placeholder example).
AuthenticationPredefined credentialUse the configured authentication method when required.
Query parametersdepartment=ITOptional filters sent to the API.
Response formatJSONHow the response is interpreted, where configurable.

9.3 Example configuration: IF

Configure a numeric condition such as monthly_salary greater than 50000. Ensure the incoming field is numeric rather than a text string where possible.

9.4 Illustrative node picker

9.5 Configuration best practices

  • Use descriptive node names.
  • Use credentials for secrets; avoid hardcoding them.
  • Use expressions for dynamic values.
  • Validate data types and required fields.
  • Review pagination, timeout and retry behaviour for API calls.
  • Test with representative sample data.
  • Document non-obvious business rules.
5.10

Node Execution

10 · Node execution

10.1 What happens when a node executes?

  1. The workflow execution reaches the node through a connected path, or the node is tested individually where supported.
  2. The node resolves its configured parameters and expressions.
  3. It reads input data if the node uses main input.
  4. It performs its operation, such as a calculation, API request or database query.
  5. It produces output items or an error.
  6. n8n passes output along the connected path according to workflow logic.

10.2 Test step versus full workflow execution

Test step / execute nodeExecute workflow
Runs a selected node for development and validation, using available input data.Runs the workflow from its trigger or manual start through the connected execution path.
Useful for tuning a node's configuration.Useful for testing end-to-end behaviour.

10.3 Node execution states

State / indicatorMeaning
SuccessThe node completed successfully.
RunningThe node is currently processing.
ErrorThe node failed; inspect the error details.
Skipped / not executedThe workflow path did not execute that node, for example because another branch was selected.

10.4 Common reasons for failure

  • Invalid parameters or expressions.
  • Missing or expired credentials.
  • Incorrect data type or missing input field.
  • External API outage, timeout or rate limit.
  • Database connectivity or SQL errors.
  • Insufficient permissions.
  • Unexpected empty or malformed response.

10.5 Troubleshooting sequence

Open execution → Find failed node → Read error → Inspect input → Check parameters / credentials → Test node → Re-run workflow → Confirm output
Operational practice: For production workflows, define how failures are detected, retried, logged and escalated. A node showing success does not automatically mean the business result is correct; validate the output.

Practical Lab: Build a multi-node employee workflow

Hands-on lab

Objective: Use a trigger, core nodes, data mapping, an IF condition and an action-style output.

Workflow design

Manual Trigger → Edit Fields → Code → IF ↙ ↘ True False ↓ ↓ High Salary Standard Salary

Step 1 — Manual Trigger

Create a new workflow and add Manual Trigger.

Step 2 — Edit Fields

Create these fields:

FieldValueType
employee_id101Number
employee_nameAlexString
departmentData EngineeringString
monthly_salary60000Number

Step 3 — Code node

const items = $input.all();

return items.map(item => ({
  json: {
    ...item.json,
    annual_salary: item.json.monthly_salary * 12
  }
}));

Step 4 — IF node

Set the condition to monthly_salary greater than 50000. Connect both outputs to separate Edit Fields nodes or other safe output steps. Set a status field such as salary_category to High or Standard.

Step 5 — Execute and inspect

  1. Run the workflow.
  2. Inspect the input and output of Edit Fields.
  3. Verify annual salary equals 720000.
  4. Confirm the true branch is taken for 60000.
  5. Change monthly salary to 45000 and run again; confirm the false branch is taken.
