Workflow Logic and Control Flow

Understand how n8n decides what runs, when it runs, which branch receives data, how records are iterated, and how workflows can call other workflows. Learn to design predictable, maintainable automation rather than simply connecting nodes in a straight line.

9.1

Control-flow foundations

Workflow logic describes the path an execution follows through the nodes of an n8n workflow. A workflow can run in a straight sequence, split into branches, evaluate conditions, process records in batches, wait for another event, or invoke another workflow.

Sequence

Run connected steps in a defined dependency order.

Parallel paths

Start independent branches from a common point and let them progress independently.

Decision paths

Use IF or Switch to choose the route based on data.

Reusable execution

Move common logic into a sub-workflow and call it when needed.

Conceptual control-flow map. Actual execution depends on node connections, conditions, branch completion and node settings.
Key distinction: the visual position of nodes on the canvas does not define execution order. Connections and node behaviour define the workflow path.
9.2

Sequential execution

Step-by-step flow

Sequential execution means a downstream step depends on an upstream step. A connected path runs in dependency order: a later node needs the earlier node's output before it can process that data.

Example: daily sales report

  1. Schedule Trigger starts the workflow.
  2. Database node retrieves sales rows.
  3. Edit Fields standardizes the fields.
  4. Summarize calculates totals.
  5. Email node sends the report.

Important points

  • Use a sequence when each step needs the result of the previous step.
  • Inspect the output of each node while developing the workflow.
  • Keep independent operations out of a strict chain if they do not depend on one another.
  • A node may output zero items; depending on the path and node behaviour, downstream nodes may then have no items to process.
9.3

Parallel execution

Independent branches

Parallel execution describes independent branches that can progress from the same upstream point. For example, after a new customer is created, one branch may update a CRM and another may send a welcome email.

Two independent paths are shown. A later Merge or synchronization step may be needed if the workflow must wait for both paths and combine their results.

How to design parallel paths

  1. Identify tasks that do not depend on each other's outputs.
  2. Connect each task to the common upstream node.
  3. Keep branch-specific transformations and actions separate.
  4. If a later step needs both results, explicitly design the synchronization and merge behaviour.
Do not assume: two branches always finish in a fixed order, or that simply drawing their paths near each other combines their data. Use Merge when branch results must be brought together, and test the exact behaviour in your n8n version.

Example use cases

  • Send the same event to CRM and a notification service.
  • Write audit details to a log while independently updating a business system.
  • Retrieve customer profile and order history from separate services.
9.4

Conditional execution

Run based on data

Conditional execution means that a node or path runs only when a defined condition is satisfied. In n8n, the IF node is commonly used for a true/false decision, while Filter retains only matching items in one stream.

Example: data quality check

IF condition:
{{ $json.email }}
is not empty

True path  → Continue customer registration
False path → Record validation failure

For numeric checks, make sure the value is numeric. For example, a threshold condition for an invoice can be based on Number($json.amount) or an explicit numeric field after conversion.

Conditional execution design

  • Choose the business rule before configuring the node.
  • Handle missing, null, blank and unexpected values explicitly.
  • Decide what should happen to records that fail validation.
  • Keep the condition readable and test boundary values.
A good workflow does not silently discard invalid business records. Route them to a review, rejection or logging path when traceability matters.
9.5

Branching workflows

Multiple paths

Branching is the design pattern of sending an execution down different paths based on a decision or event. An IF node creates two decision outputs. A Switch node is suitable for multiple categories or rules.

Example: support-ticket routing

Ticket categoryRouteAction
CriticalOn-call pathPage support immediately
Data issueData engineering pathCreate investigation task
Access requestAccess pathStart approval workflow
OtherGeneral queueCreate standard ticket

Branching guidelines

  • Name branches by business meaning, not only “branch 1” and “branch 2”.
  • Include a fallback route for unrecognized values when using category routing.
  • Avoid duplicating large blocks of identical logic in every branch.
  • Use a sub-workflow for repeated processing shared by several routes.
9.6

Multiple conditions

AND / OR / rule sets

Real workflows often require more than one condition. For example, an order may be eligible for automatic fulfilment only when it is approved, payment is complete and the order total is below a defined review threshold.

Example business rule

Eligible for automatic processing when:
status = "Approved"
AND payment_status = "Paid"
AND total_amount <= 5000

AND vs OR

OperatorMeaningExample
ANDEvery condition must be true.Approved AND paid.
ORAt least one condition must be true.Priority is Critical OR High.

Combining conditions in n8n

  • Use the IF node's condition groups and combinator options for straightforward decisions.
  • Use Switch rules when routing to several outputs.
  • Use an expression or Code node for complex business rules that are difficult to express clearly with standard conditions.
Be careful with mixed AND/OR logic. Add groups deliberately and test each combination. Parentheses and grouping can change the meaning of a rule.

9.7

Looping

Repeat a processing path

Looping repeats a set of workflow steps. In n8n, Loop Over Items (previously called Split in Batches) is the built-in node commonly used to process incoming items in batches. Many n8n nodes already handle multiple items, so a loop should be used when controlled iteration is required—not automatically for every list.

Typical batch loop

  1. Receive a collection of records.
  2. Loop Over Items selects the next batch.
  3. Run the processing steps for that batch.
  4. Return to the loop node through the loop path.
  5. When no more batches remain, continue from the Done output.
Simplified pattern. Follow the Loop and Done outputs and connect the processing path back according to the node's current configuration.

Batch size considerations

  • Small batches reduce the amount of work sent to a downstream service at once.
  • Large batches may improve throughput but can increase memory use or cause API/database limits.
  • Test with realistic record sizes and downstream rate limits.
  • Use retries and error handling carefully to avoid duplicate writes.
9.8

Iterating through records

Per-record processing

Iteration means applying a processing action to individual records in a collection. n8n passes items between nodes, and many nodes automatically process each incoming item. The key is to understand whether the node operates on all items, the current item, or a batch.

Example: process employee records

Input:
[
  { "employee_id": 101, "name": "Ravi" },
  { "employee_id": 102, "name": "Meena" },
  { "employee_id": 103, "name": "Arun" }
]

Conceptual processing:
For each employee item:
  validate required fields
  look up employee details
  update the record
  record the result

Do I need Loop Over Items?

SituationRecommended approach
A normal node supports multiple input items and can process them in one execution.Connect the node directly; no explicit loop may be needed.
Only a limited number should be processed at a time.Use Loop Over Items with a suitable batch size.
An array is nested inside one item's JSON.Use Split Out first if each array element must become its own item.
Custom per-item logic is required.Use a suitable node mode, expressions or Code node.
Think in terms of items and arrays. A collection of n8n items is not the same thing as one item containing a nested array.
9.9

Combining workflow branches

Synchronization and merge

After parallel or conditional processing, you may need to bring data from two paths together. The Merge node is the common tool for combining two inputs. The correct mode depends on whether you want to append records, match them by a key, combine by position or pass through a selected branch.

Example: enrich a customer record

  • Branch A retrieves customer profile details.
  • Branch B retrieves the customer's loyalty information.
  • Merge combines the results using a shared customer identifier.
  • A downstream node creates the enriched customer record.

Checklist before merging

  • Do both branches contain the key needed to match records?
  • Is the key unique on each side?
  • What should happen when one side has no match?
  • Could duplicate keys create multiple output combinations?
  • Does the downstream node expect one item per customer or a list?
A Merge node is not simply a visual connector. Configure its mode and matching behaviour intentionally. Verify how it handles unmatched items and duplicate keys with test data.
9.10

Sub-workflows

Reusable workflow design

A sub-workflow is a separate n8n workflow called by another workflow. It helps organize a large automation into smaller, reusable units with a clear responsibility and input/output contract.

Why use sub-workflows?

  • Reuse the same processing logic from multiple parent workflows.
  • Separate business functions such as validation, notification or data enrichment.
  • Make complex automations easier to test and maintain.
  • Keep the parent workflow focused on orchestration.

Example architecture

Conceptual architecture showing reusable workflows. A parent can call different sub-workflows as needed.

Good sub-workflow candidates

Reusable functionPossible inputsPossible outputs
Validate customerCustomer ID, name, emailValidation status, error details
Send notificationRecipient, subject, messageDelivery result, message ID
Load a data batchTable name, records, batch IDRows processed, load status

Design principles

  • Give the sub-workflow one clear responsibility.
  • Define required input fields and expected output fields.
  • Validate inputs near the start of the sub-workflow.
  • Decide whether errors should stop the parent, be returned as data, or be handled through a separate error workflow.
  • Document any credentials, environment assumptions or side effects.
9.11

Execute Workflow node

Call another workflow

The Execute Sub-workflow node (often referred to as Execute Workflow) lets one workflow start another workflow. The parent passes input data to the child workflow. Depending on the node's configuration, the parent can wait for the called workflow to finish and receive its output.

Typical setup

  1. Create the child workflow.
  2. Start it with the appropriate trigger for workflows called by another workflow (commonly the Execute Sub-workflow Trigger / When Executed by Another Workflow trigger).
  3. Define which input fields the child workflow expects.
  4. In the parent, add the Execute Sub-workflow node and select the child workflow.
  5. Configure input mapping and whether to wait for completion, where the option is available.
  6. Test with a small sample and inspect both parent and child executions.

Example input contract

{
  "customer_id": 2045,
  "notification_type": "welcome",
  "email": "customer@example.com"
}

Conceptual child workflow

When Executed by Another Workflow
          |
          v
Validate input
          |
          v
Build notification
          |
          v
Send email
          |
          v
Return result:
{
  "status": "sent",
  "customer_id": 2045
}

Wait for completion vs continue

BehaviourMeaningConsideration
Wait for child completionParent execution waits for the child result before continuing.Useful when the next parent step depends on the child's output.
Do not wait / asynchronous pattern, where supportedParent continues without depending on the child result immediately.Useful for fire-and-forget work, but you need separate monitoring and error visibility.
Exact labels and options may differ by n8n version. Confirm the current Execute Sub-workflow node options and child trigger settings in your editor. Do not assume an asynchronous call will return the child's final output to the parent.

Sub-workflow vs ordinary node sequence

  • Use an ordinary sequence when logic is simple and only used once.
  • Use a sub-workflow when logic is reusable, independently maintainable or large enough to deserve its own boundary.
9.12

Common workflow design patterns

Pattern A — Validate, route and process

Trigger
  → Edit Fields (normalize)
  → IF (required fields valid?)
      True  → Switch (route by type)
                → business action
      False → log validation issue

Pattern B — Parallel enrichment

Trigger
  → split into independent paths
      Path A: fetch customer profile
      Path B: fetch account status
  → Merge using customer_id
  → build enriched record

Pattern C — Reusable processing

Parent workflow
  → prepare standard input
  → Execute Sub-workflow
       Child: validate → transform → return result
  → inspect child result
  → continue parent workflow

Pattern D — Large data processing

Fetch records (with pagination if required)
  → Loop Over Items (batch size)
  → process current batch
  → return to loop
  → Done → final summary
Build workflows around clear business stages. A useful workflow should make it easy to answer: what started it, what data is being processed, why a path was selected, and how completion or failure is handled.
9.13

Practical labs

Lab 1 — Sequential sales reporting

Goal: build a straight-line workflow.
  1. Start with a Manual Trigger.
  2. Use sample sales records.
  3. Normalize the fields with Edit Fields.
  4. Summarize total sales.
  5. Prepare a final report object.
  6. Inspect each node's output in sequence.

Expected result: a predictable report object generated through dependent steps.

Lab 2 — Parallel customer onboarding

Goal: execute independent actions from one customer event.
  1. Prepare one customer record.
  2. Create two branches: one for a CRM update and one for a welcome notification.
  3. Use mock or test actions while learning.
  4. Inspect each branch's execution.
  5. If both results are required later, configure a Merge step and test it.

Lab 3 — Multi-condition order approval

Goal: apply AND/OR business rules.
  1. Prepare orders with different status, payment and amount values.
  2. Use IF to test Approved AND Paid AND amount within the threshold.
  3. Route eligible orders to a processing path.
  4. Route rejected orders to review.
  5. Test all combinations, including missing values.

Lab 4 — Ticket routing with Switch

Goal: build a multi-branch workflow.
  1. Prepare Critical, High, Medium, Low and unexpected categories.
  2. Use Switch to create a route for each supported category.
  3. Connect each route to a distinct test action.
  4. Configure and test fallback behaviour.

Lab 5 — Batch iteration

Goal: process records in controlled batches.
  1. Create at least 12 sample items.
  2. Add Loop Over Items and set a batch size of 3.
  3. Connect a harmless processing step to the Loop output.
  4. Connect the processing path back to the loop as required.
  5. Use Done for a final completion summary.
  6. Review the execution to identify each batch.

Lab 6 — Reusable sub-workflow

Goal: call a child workflow from a parent.
  1. Create a child workflow with the appropriate sub-workflow trigger.
  2. Define required inputs such as customer_id and email.
  3. Validate the inputs and return a simple result object.
  4. Create a parent workflow with sample input data.
  5. Call the child using Execute Sub-workflow.
  6. Inspect the parent and child execution data.
For all labs, use test data and mock actions first. Add production credentials only after confirming the workflow's routing, item counts, error paths and side effects.
9.14

Troubleshooting and best practices

ProblemPossible reasonWhat to inspect
A downstream node does not runUpstream node returned zero items, branch was not selected, or execution stopped.Inspect upstream output, branch output and execution status.
Only one branch appears to runConditional routing selected one path, or the other branch has no items.Check IF/Switch conditions and the actual input values.
Parallel results are not available togetherNo explicit merge/synchronization step or wrong Merge mode.Configure Merge deliberately and inspect both inputs.
Loop processes records repeatedlyLoop-back wiring or processing path is incorrect.Review Loop and Done outputs and the return connection.
Some records are skippedFilter/IF condition, empty items, or upstream pagination/limit.Inspect item counts at each stage and test edge cases.
Sub-workflow receives missing valuesParent input mapping and child input contract do not match.Compare parent output, mapped inputs and child trigger schema.
Parent does not have expected child outputChild output structure or wait behaviour differs from expectation.Check Execute Sub-workflow settings and inspect child execution.
Workflow is difficult to maintainToo many duplicated branches or unclear node responsibilities.Refactor common logic into sub-workflows and name paths clearly.

Production checklist

  • Give every branch a clear business purpose.
  • Handle both valid and invalid data.
  • Define how empty input and zero-item outputs should behave.
  • Use explicit Merge behaviour when branches must be combined.
  • Use loops only for genuine batching or iteration requirements.
  • Define sub-workflow input/output contracts.
  • Plan for child workflow failures and parent error handling.
  • Make workflows observable with meaningful names, logs and error notifications.
  • Test boundary cases and duplicate events before production deployment.
9.15

Interview questions and answers

  1. What is workflow control flow in n8n?
    It is the logic that determines which nodes execute, in what order, and under which conditions.
  2. What is sequential execution?
    A connected sequence where downstream processing depends on upstream output.
  3. What is parallel execution?
    Independent branches progress from a common point without requiring one branch's output for the other.
  4. Does canvas position decide execution order?
    No. Connections and node behaviour determine the execution path.
  5. How do you implement conditional execution?
    Use IF or Filter depending on whether you need separate true/false paths or one filtered output.
  6. How is branching different from a sequential workflow?
    Branching creates alternative or independent paths; sequential flow follows a dependent chain.
  7. When would you use Switch?
    When a value must be routed to several possible outputs.
  8. How do you implement multiple conditions?
    Use AND/OR condition groups in IF, Switch rules, expressions or Code for complex logic.
  9. What is the difference between AND and OR?
    AND requires every condition to be true; OR requires at least one condition to be true.
  10. What is looping?
    Repeating a processing path for items or batches.
  11. What is Loop Over Items used for?
    Processing records in controlled batches.
  12. Does every list need a loop?
    No. Many n8n nodes process multiple items automatically.
  13. What is the difference between an item and an array inside an item?
    An item is an n8n data unit; an array may be a field nested inside that item's JSON.
  14. How can you process nested array elements individually?
    Use Split Out to convert array elements into individual n8n items.
  15. How do you combine two workflow branches?
    Use Merge with an appropriate mode and matching strategy.
  16. What is a sub-workflow?
    A separate workflow called by another workflow to perform a reusable task.
  17. Why use sub-workflows?
    To improve reuse, modularity, testing and maintainability.
  18. What does Execute Sub-workflow do?
    It invokes another workflow and passes input data to it.
  19. Which trigger is used by a called workflow?
    Typically the When Executed by Another Workflow / Execute Sub-workflow Trigger node.
  20. What is an input contract?
    A documented set of required and optional fields that the called workflow expects.
  21. When should a parent wait for a child workflow?
    When subsequent parent steps depend on the child's result.
  22. What is a risk of fire-and-forget execution?
    The parent may continue without immediately knowing whether the child succeeded or failed.
  23. What happens if an upstream node returns zero items?
    There may be no items for downstream nodes to process along that path.
  24. How would you design a scalable data-processing workflow?
    Use clear stages, pagination where needed, batching where useful, validation, reusable sub-workflows and monitoring/error handling.
