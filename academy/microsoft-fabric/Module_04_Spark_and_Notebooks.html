What is Apache Spark?

Apache Spark is an open-source distributed processing engine. It splits a large dataset into pieces called partitions, sends each piece to a different worker, processes them all at the same time, and combines the results. It keeps data in memory where it can, which makes it much faster than older disk-based systems.

You can write PySpark without knowing what happens underneath — until something is slow or crashes. Then you need this lesson. It explains the Driver and Executors, why Spark is "lazy", what a shuffle is, and the handful of rules that keep jobs fast.

Lazy Evaluation: Transformations vs Actions

This is the concept that surprises every beginner. Spark does nothing until you ask for a result.

Transformations — build the plan

Return a new DataFrame. Nothing runs yet.

select()  filter()  where()
withColumn()  drop()  dropDuplicates()
groupBy()  join()  orderBy()

Actions — run the plan

Return a value or write data. Now Spark executes.

show()  count()  collect()  first()  take()
display()
write.saveAsTable()
Lazy evaluation in actionPySpark
df2 = df.filter(df.Amount > 1000)          # transformation: instant, nothing processed
df3 = df2.select("CustomerName", "Amount") # transformation: still nothing

df3.count()                                # ACTION: now Spark runs filter + select + count

Why be lazy? Because seeing the whole chain lets the optimiser combine steps, push filters down to the file scan, and skip columns it never needs. Eager execution would run each line in isolation.

A shuffle costs network transfer, disk I/O, serialisation and memory. You can't avoid them entirely — a groupBy("Country") genuinely needs all India rows together — but you can make them cheaper by shuffling less data: filter first, drop unneeded columns first.

The Five Performance Rules

1
Filter early
df.filter(col("Country") == "India") before the join or groupBy. Less data flows into every later step and every shuffle.
2
Select only needed columns
df.select("CustomerID", "Amount") rather than carrying 50 columns through the pipeline. Parquet / Delta only read the columns you ask for.
3
Never collect() a large DataFrame
It pulls every row into the Driver's small memory and crashes the session. To look at data use display(df.limit(100)) or df.show(20).
4
Be deliberate about shuffles
Each join, groupBy, orderBy and distinct is a shuffle. Don't sort data you won't display; don't distinct() "just in case".
5
Cache only what you reuse
df.cache() keeps a DataFrame in memory for repeated use. Great when you run five aggregations on the same cleaned data; wasteful for a DataFrame used once.

Two Things That Go Wrong

1. Out of memory

WhereCauseFix
Drivercollect() or toPandas() on millions of rowsUse limit(); keep processing in Spark
ExecutorA huge join or shuffle, or over-cachingFilter and select first, fix partitioning, uncache, or scale up if justified

2. Data skew

Skew is when one partition is far bigger than the others. Three tasks finish in seconds; the fourth runs for an hour, and the whole stage waits.

P1 — 1 GBdone
P2 — 1 GBdone
P3 — 1 GBdone
P4 — 100 GBstill running… everyone waits

Typical cause: grouping or joining on a key where one value dominates (India = 95 M rows, UK = 1 M). Fixes: choose a different key, pre-aggregate, or repartition on a better-distributed column (Lesson 4.10).

Fabric Spark Compute

  • Session start-up — the first cell takes ~10–30 s while executors are provisioned; a starter pool makes this fast
  • Autoscaling — Fabric adds executors when load rises and releases them when idle (dynamic allocation), so a 100 MB job and a 5 TB job both work without manual sizing
  • Environments — workspace admins can define Spark settings and libraries; most beginners use the default
  • Monitoring — the Spark UI under the notebook's Monitor tab shows jobs, stages, task durations, shuffle read/write and failed tasks — your first stop when something is slow

Hands-On: Watch Spark Work

Run each line and watch the job counterPySpark
data = [(1, "India", 1000), (2, "USA", 2000), (3, "India", 3000), (4, "UK", 1500)]
df = spark.createDataFrame(data, ["ID", "Country", "Amount"])

print(df.rdd.getNumPartitions())          # how many partitions?

filtered = df.filter(df.Amount > 1500)    # transformation — no job appears
filtered.count()                          # action — a job runs (1 stage, narrow)

df.groupBy("Country").sum("Amount").show()  # action — a job with 2 stages (the shuffle)

Open the Monitor tab after the last cell: you'll see the second stage that the groupBy shuffle created.

The Driver coordinates a Spark application: it holds the SparkSession, builds the execution plan from your code and schedules tasks. Executors do the work on data partitions. An action (count, show, write) triggers a job; the job is split into stages at shuffle boundaries; each stage runs one task per partition. Transformations are lazy — they only build the plan — so Spark can optimise before running. Narrow transformations (filter, select) work inside a partition; wide ones (groupBy, join, orderBy) require a shuffle, which is expensive. Filter early, select fewer columns, avoid collect(), and watch for data skew.

The DataFrame is the object you work with in PySpark — it looks like a table and behaves like one, but it is spread across the cluster. This lesson is your reference for the operations you will use every day: select, filter, add columns, handle NULLs, aggregate, join. Keep it open while you work.

3. Filtering Rows

filter() and where() are identical. Use col("X") or df.X for the column.

df.filter(col("Country") == "India")
df.where(df.Amount > 3000)

# Several conditions: wrap EACH in parentheses and use &  |  ~  (not  and / or / not)
df.filter((col("Country") == "India") & (col("Amount") > 3000))
df.filter((col("Country") == "India") | (col("Country") == "USA"))
df.filter(~(col("Country") == "UK"))
df.filter(col("Country") != "UK")

df.filter(col("Country").isin("India", "USA"))
df.filter(col("CustomerName").startswith("A"))
df.filter(col("CustomerName").like("A%"))
The most common beginner error: df.filter(col("A") > 1 and col("B") > 2). Python's and doesn't work on Spark columns — you get a confusing "Cannot convert column into bool". Use & with parentheses around each side.

4. Adding and Changing Columns

withColumn("name", expression) adds a column, or replaces it if the name exists. DataFrames are immutable, so it returns a new DataFrame — assign it.

df2 = df.withColumn("Tax", col("Amount") * 0.10)                 # calculation
df2 = df2.withColumn("Total", col("Amount") + col("Tax"))         # from other columns
df2 = df2.withColumn("SourceSystem", lit("SQLServer"))            # constant value → lit()

# Conditional column: when / otherwise (like SQL CASE)
df2 = df2.withColumn(
    "CustomerType",
    when(col("Amount") >= 4000, "Platinum")
    .when(col("Amount") >= 3000, "Premium")
    .otherwise("Standard")
)

df2 = df2.withColumnRenamed("CustomerName", "Customer")           # rename
df2 = df2.withColumn("Amount", col("Amount").cast("double"))      # change type

Spark SQL

If you already know SQL, you can use Spark without writing much Python at all. Spark SQL runs ordinary SQL on DataFrames and Delta tables — distributed across the cluster, with the same optimiser. This lesson shows how to expose a DataFrame to SQL and the SQL features data engineers use most, including window functions.

Same Engine, Two Syntaxes

The Essentials

Standard SQL you already know works as expected:

-- Select, alias, filter, sort
SELECT CustomerName AS Customer, Amount
FROM sales
WHERE Country IN ('India', 'USA')
  AND Amount BETWEEN 2000 AND 4000
  AND CustomerName LIKE 'A%'
ORDER BY Country, Amount DESC;

-- Aggregate, group, filter groups
SELECT Country,
       COUNT(*)      AS Customers,
       SUM(Amount)   AS TotalSales,
       AVG(Amount)   AS AverageSale,
       MAX(Amount)   AS BiggestSale
FROM sales
WHERE Amount > 1000              -- WHERE: filters rows BEFORE grouping
GROUP BY Country
HAVING SUM(Amount) > 5000;       -- HAVING: filters groups AFTER aggregation

-- Derived columns and CASE
SELECT CustomerName, Amount,
       Amount * 0.10 AS Tax,
       CASE WHEN Amount >= 3000 THEN 'Premium'
            WHEN Amount >= 2000 THEN 'Standard'
            ELSE 'Basic' END AS CustomerType
FROM sales;

-- DISTINCT and NULL handling
SELECT DISTINCT Country FROM sales;
SELECT COUNT(DISTINCT Country) AS Countries FROM sales;
SELECT CustomerName, COALESCE(Country, 'Unknown') AS Country FROM sales WHERE Country IS NULL;

-- String and date functions
SELECT UPPER(TRIM(CustomerName)) AS Name, LENGTH(CustomerName) AS Len FROM sales;
SELECT CAST(SaleDate AS DATE) AS SaleDate, YEAR(SaleDate) AS Yr, MONTH(SaleDate) AS Mth FROM orders;

Reading the syntax: OVER (PARTITION BY Country ORDER BY Amount DESC) means "within each country, ordered by amount, highest first". ROW_NUMBER always gives 1, 2, 3; RANK gives ties the same number.

The pattern you'll use constantly: top-N per group / latest record per key

WITH Ranked AS (
    SELECT *,
           ROW_NUMBER() OVER (PARTITION BY Country ORDER BY Amount DESC) AS rn
    FROM sales
)
SELECT CustomerName, Country, Amount
FROM Ranked
WHERE rn = 1;                      -- top customer in each country

Swap Country for CustomerID and Amount DESC for UpdatedDate DESC, and the same query de-duplicates a source to its latest row per key — essential before a MERGE (Lesson 4.9).

The Cleaning Toolkit

Imports used throughoutPySpark
from pyspark.sql.functions import (col, trim, upper, lower, initcap, regexp_replace, when,

1. Column names

Spaces and hyphens in names break SQL. Fix them once, right after reading:

# A few columns
df = (df.withColumnRenamed("Customer ID", "CustomerID")
        .withColumnRenamed("Sale Amount", "SaleAmount"))

# All columns automatically
for old in df.columns:
    df = df.withColumnRenamed(old, old.strip().replace(" ", "_").replace("-", "_"))

2. Whitespace and case

df = df.withColumn("CustomerName", trim(col("CustomerName")))          # "  John  " → "John"
df = df.withColumn("Country", upper(trim(col("Country"))))             # " india" → "INDIA"
df = df.withColumn("CustomerName", initcap(col("CustomerName")))       # "JOHN KUMAR" → "John Kumar"

3. Standardising values

When the same thing is written several ways:

# Simple mapping
df = df.replace({"IND": "INDIA", "IN": "INDIA", "US": "USA"}, subset=["Country"])

# Rule-based with when()
df = df.withColumn("Country",
    when(col("Country").isin("IN", "IND", "India", "india"), "INDIA")
    .when(col("Country").isin("US", "United States"), "USA")
    .otherwise(upper(trim(col("Country")))))

4. NULLs — fill or drop?

df = df.fillna({"CustomerName": "Unknown", "Country": "UNKNOWN"})   # optional fields → fill
df = df.dropna(subset=["SaleID"])                                   # required key → drop (or quarantine)
SituationAction
Optional text field is NULLFill with "Unknown"
Required ID / business key is NULLReject → quarantine
Numeric measure is NULLDepends — 0 can be wrong (missing ≠ zero). Ask the business.
Date is NULLUsually reject or flag; never invent a date
Don't blindly fillna(0) on every numeric column. A missing salary filled with 0 will drag down every average. Decide per column.

5. Duplicates — always by business key

df = df.dropDuplicates()               # only removes rows identical in EVERY column
df = df.dropDuplicates(["SaleID"])     # removes repeated sales — what you usually want

If two rows share a key but differ (e.g. an updated amount), dropDuplicates keeps an arbitrary one. To keep the latest, use the window pattern from Lesson 4.4 / 4.9.

6. Numbers that arrived as text

df = df.withColumn("Amount", col("Amount").cast("double"))                       # "2500" → 2500.0
df = df.withColumn("Amount", regexp_replace(col("Amount"), ",", "").cast("double"))  # "2,500" → 2500.0
df = df.withColumn("Amount", regexp_replace(col("Amount"), "[₹$,]", "").cast("double"))  # "₹2,500.00" → 2500.0
df = df.withColumn("Phone",  regexp_replace(col("Phone"), "[^0-9]", ""))           # "(987) 654-3210" → "9876543210"

A value that can't be converted becomes NULL rather than raising an error — so check for new NULLs after casting.

7. Dates and timestamps

df = df.withColumn("OrderDate", to_date(col("OrderDate"), "dd/MM/yyyy"))                  # "22/08/2026"
df = df.withColumn("OrderDate", to_date(col("OrderDate"), "yyyy-MM-dd"))                  # "2026-08-22"
df = df.withColumn("CreatedTs", to_timestamp(col("CreatedTs"), "yyyy-MM-dd HH:mm:ss"))

# Invalid dates ("ABC", "31/02/2026") become NULL — find them
bad_dates = df.filter(col("OrderDate").isNull())

8. Validation and business rules

# Basic email format check
invalid_email = df.filter(~col("Email").rlike(r"^[A-Za-z0-9._%+-]+@[A-Za-z0-9.-]+\.[A-Za-z]{2,}$"))

# Business rules as a single boolean expression
is_valid = ((col("Amount") >= 0) &
            (col("Quantity") > 0) &
            col("SaleID").isNotNull() &
            (col("OrderDate") <= current_date()))

The Production Pattern: Quarantine, Don't Delete

A beginner filters bad rows out and moves on. The rows vanish, nobody knows, and the row count is mysteriously short. The professional pattern splits the data in two and keeps both:

Raw DataFrame
↓ clean (trim, case, cast, dedupe)
Validation rules
↙           ↘

Cleaned data is worthless until it is saved somewhere every tool can read. In Fabric that means a Delta table. The write itself is one line — the skill is choosing the right mode (overwrite, append or merge), controlling the schema, and not producing thousands of tiny files.

Controlling the Schema

Delta enforces the schema: an append whose columns don't match the table fails. That protects you from a bad file. When the change is intentional, opt in:

# New source has an extra Country column → add it to the table
df.write.format("delta").mode("append").option("mergeSchema", "true").saveAsTable("Sales")

# Rebuilding the table with a deliberately different schema
df.write.format("delta").mode("overwrite").option("overwriteSchema", "true").saveAsTable("Sales")
Never leave mergeSchema permanently on in a production append. A source that suddenly renames Amount to amount would silently give you two columns, half-empty each. Validate schema changes; don't auto-accept them.

Write Performance: The Small-Files Problem

Each Spark partition becomes at least one file. A DataFrame with 200 partitions written every 5 minutes produces 57,000 files a day — and every later query has to open all of them.

❌ 100 rows → 200 tiny files

Metadata overhead dominates; queries slow to a crawl.

✅ 1 M rows → 8 files of ~128 MB

Fast scans, efficient compression.

# Reduce partitions before a write (no shuffle — cheap)
df.coalesce(8).write.format("delta").mode("append").saveAsTable("Sales")

# Rebalance to N even partitions (shuffle — use when data is skewed)
df.repartition(8).write.format("delta").mode("append").saveAsTable("Sales")

Rules of thumb: batch small loads together rather than writing every few seconds; aim for files of 100 MB–1 GB; and run OPTIMIZE periodically (Lesson 4.8) to compact what accumulates anyway.

Delta Operations: Update, Delete, Time Travel & Maintenance

Module 2 explained what Delta Lake is. This lesson is about using it from a notebook: changing rows in place, looking at (and restoring) earlier versions, and keeping a table healthy over months of daily loads.

Thirty-Second Recap

📦 Parquet files
The data, column by column
+
📜 _delta_log/
JSON log of every change: which files are "live", schema, version history
= a table with ACID transactions, UPDATE / DELETE / MERGE and time travel

Each write — overwrite, append, update, delete, merge — commits a new version in the log. The old Parquet files are not deleted; they are just no longer referenced. That is what makes time travel possible.

Changing Rows in Place

Plain Parquet can't do this. Delta can, from SQL or Python:

Spark SQL
UPDATE Sales
SET Amount = Amount * 1.10
WHERE Country = 'INDIA';

DELETE FROM Sales
WHERE Amount <= 0;

INSERT INTO Sales VALUES
  (5001, 'Rahul', 'INDIA', 900);
PySpark (DeltaTable API)
from delta.tables import DeltaTable
t = DeltaTable.forName(spark, "Sales")

t.update(
    condition = "Country = 'INDIA'",
    set = {"Amount": "Amount * 1.10"})

t.delete("Amount <= 0")

Every statement is one atomic transaction: it fully succeeds or leaves the table untouched. Readers running at the same time see either the old version or the new — never a half-updated table.

Schema Enforcement

Try to insert a row whose types don't match and Delta refuses:

INSERT INTO Sales VALUES (5002, 'Meera', 'INDIA', 'ABC');
-- AnalysisException: cannot cast 'ABC' to DOUBLE

That error is a feature. The alternative — a CSV silently turning your numeric column into text — is far worse.

Restore — the undo button

Loaded a bad file in version 3? Put the table back:

RESTORE TABLE Sales TO VERSION AS OF 2;

Restore itself is recorded as version 4 — nothing is ever lost from the history. Time travel is only possible while the old files still exist, which brings us to maintenance.

Maintenance: OPTIMIZE and VACUUM

Daily appends and merges leave a table with hundreds of small files and many old, unreferenced ones. Two commands keep it healthy:

CommandWhat it doesRun
OPTIMIZE Sales;Compacts small files into ~1 GB files (bin-packing). Queries get faster. Data unchanged.After large loads, or weekly
OPTIMIZE Sales ZORDER BY (CustomerID);Also co-locates rows with similar values, so filters on that column skip more filesFor columns you filter on but don't partition by
VACUUM Sales;Physically deletes files no longer referenced by any version older than the retention period (default 7 days). Frees storage.Weekly / monthly
After VACUUM, you can no longer time-travel to versions whose files were removed. Don't shorten the retention period below 7 days unless you're sure no job reads old versions.

Fabric also offers automatic compaction and the V-Order write optimisation for Power BI performance — both on by default in Lakehouse tables, so OPTIMIZE is needed less often than in raw Spark.

MERGE: Upserts & Incremental Loads

You have met MERGE in SQL (Modules 2 and 3). Here it becomes the centrepiece of the notebook: the DeltaTable API in PySpark, the options that give you precise control, the one mistake that corrupts data (a bad key), and the complete incremental-load pattern from staging to validated Silver table.

What MERGE Does

For every incoming row, MERGE asks: does a row with this key already exist in the target?

↓ match on business key
Exists in target?
yes ↙                ↘ no

↓
Target table — no duplicates

UPDATE + INSERT = UPSERT. One atomic operation; re-running it is safe.

MERGE INTO Customers AS t

WHEN MATCHED THEN UPDATE SET *
WHEN NOT MATCHED THEN INSERT *;

Taking Control: Explicit Columns and Conditions

UpdateAll / InsertAll are fine when source and target have identical columns. Real tables have audit columns the source knows nothing about — and you don't want CreatedDate overwritten on every update:

Explicit MERGE with audit columnsPySpark
(target.alias("t")
    .merge(source_df.alias("s"), "t.CustomerID = s.CustomerID")
    .whenMatchedUpdate(
        condition = "s.Amount <> t.Amount OR s.City <> t.City",   # only if something changed
        set = {
            "CustomerName": "s.CustomerName",
            "City":         "s.City",
            "Amount":       "s.Amount",
            "UpdatedDate":  "current_timestamp()"          # CreatedDate untouched
        })
    .whenNotMatchedInsert(
        values = {
            "CustomerID":   "s.CustomerID",
            "CustomerName": "s.CustomerName",
            "City":         "s.City",
            "Amount":       "s.Amount",
            "CreatedDate":  "current_timestamp()",
            "UpdatedDate":  "current_timestamp()"
        })
    .execute())
ClauseFires whenTypical use
whenMatchedUpdateAll()Key existsSimple upsert, identical schemas
whenMatchedUpdate(condition, set)Key exists AND condition trueProtect audit columns; skip no-op updates
whenMatchedDelete(condition)Key exists AND condition trueSource flags the row as deleted
whenNotMatchedInsertAll()Key missingSimple upsert
whenNotMatchedInsert(condition, values)Key missing AND condition truee.g. only insert active customers

Handling deletes

If the source sends an IsDeleted flag, MERGE can act on it. Two options:

Hard delete
.whenMatchedDelete(
    condition = "s.IsDeleted = true")
.whenMatchedUpdateAll()
.whenNotMatchedInsertAll()
Soft delete (preferred)
.whenMatchedUpdate(
    condition = "s.IsDeleted = true",
    set = {"IsActive": "false",
           "UpdatedDate": "current_timestamp()"})
.whenMatchedUpdateAll()
.whenNotMatchedInsertAll()

Soft delete keeps the row for history and auditing; reports filter on IsActive = true. Clause order matters — Delta evaluates whenMatched clauses top to bottom and uses the first whose condition is true.

The Key Is Everything

The merge condition must identify exactly one target row per source row. t.Country = s.Country matches thousands of rows and will overwrite all of them with one source record. t.CustomerName = s.CustomerName fails on the second "John". Use the stable business key — CustomerID, OrderID — or a composite: "t.CustomerID = s.CustomerID AND t.ProductID = s.ProductID".

Duplicate source rows break MERGE

If the source has two rows for CustomerID 101, Delta doesn't know which one to apply and raises "Cannot perform MERGE as multiple source rows matched". Always de-duplicate the source first — and keep the latest row, not an arbitrary one:

from pyspark.sql.window import Window
from pyspark.sql.functions import row_number, col

latest = Window.partitionBy("CustomerID").orderBy(col("UpdatedDate").desc())

source_df = (source_df
    .withColumn("rn", row_number().over(latest))
    .filter(col("rn") == 1)
    .drop("rn"))

Production notebookPySpark
from delta.tables import DeltaTable
from pyspark.sql.functions import col, trim, upper, row_number, current_timestamp, max as max_
from pyspark.sql.window import Window

# 1. Watermark
wm = spark.sql("SELECT WatermarkValue FROM PipelineWatermark WHERE TableName = 'Customers'").first()[0]

# 2. Source — only rows changed since the watermark
src = (spark.read.table("Bronze_Customers")
         .filter(col("UpdatedDate") > wm))

# 3. Clean + validate
src = (src.withColumn("CustomerName", trim(col("CustomerName")))
          .withColumn("Country", upper(trim(col("Country"))))
          .filter(col("CustomerID").isNotNull()))

# 4. Latest row per key
w = Window.partitionBy("CustomerID").orderBy(col("UpdatedDate").desc())
src = src.withColumn("rn", row_number().over(w)).filter(col("rn") == 1).drop("rn")

if src.count() == 0:
    print("Nothing to merge");
else:
    # 5. MERGE
    target = DeltaTable.forName(spark, "Customers")
    (target.alias("t")
        .merge(src.alias("s"), "t.CustomerID = s.CustomerID")
        .whenMatchedUpdate(set={"CustomerName": "s.CustomerName", "Country": "s.Country",
                                "Amount": "s.Amount", "UpdatedDate": "current_timestamp()"})
        .whenNotMatchedInsert(values={"CustomerID": "s.CustomerID", "CustomerName": "s.CustomerName",
                                      "Country": "s.Country", "Amount": "s.Amount",
                                      "CreatedDate": "current_timestamp()", "UpdatedDate": "current_timestamp()"})
        .execute())

    # 6. Validate, then advance the watermark (only on success)
    dupes = spark.table("Customers").groupBy("CustomerID").count().filter(col("count") > 1).count()
    assert dupes == 0, "Duplicate keys after MERGE"
    new_wm = src.agg(max_("UpdatedDate")).first()[0]
    spark.sql(f"UPDATE PipelineWatermark SET WatermarkValue = '{new_wm}' WHERE TableName = 'Customers'")

MERGE Performance

MERGE has to find matching rows, so on a billion-row target it can be slow. Keep it fast by:

  • Merging only changed rows (watermark) — never the whole source
  • Adding a partition filter to the condition when you can: "t.Year = 2026 AND t.CustomerID = s.CustomerID"
  • Running OPTIMIZE … ZORDER BY (CustomerID) on the target so key lookups skip files
  • Keeping the target's files well-sized (Lesson 4.8)

Delta MERGE compares source rows to a target table on a business key and, in one atomic operation, updates matches and inserts new rows (an upsert), optionally deleting or soft-deleting flagged rows. In PySpark you use DeltaTable.forName(...).merge(source, condition).whenMatchedUpdate…().whenNotMatchedInsert…().execute(); explicit column mappings protect audit columns like CreatedDate. The key must be unique and stable, and the source must be de-duplicated to its latest row per key first (window + row_number). MERGE is idempotent, which makes it the standard for incremental loads: read watermark → changed rows → clean → dedupe → MERGE → validate → update watermark.

Partitioning

"Partition" is the most overloaded word in Spark, and it means two different things. Beginners mix them up constantly, and interviewers love asking about it. This lesson separates them, shows the commands for each, and gives you the checklist for deciding whether to partition a table at all.

Two Kinds of Partitioning

1. Spark partitions — processing

How a DataFrame is split across executors in memory, right now. Controls parallelism and how many files a write produces.

df.rdd.getNumPartitions()
df.repartition(8)
df.coalesce(2)

2. Table partitions — storage

How a Delta table's files are organised on disk, permanently into folders by a column's values. Controls how much data a query has to read.

df.write.partitionBy("Year", "Month")
  .saveAsTable("Sales")

repartition() = memory, for this job.   partitionBy() = disk, forever. They are independent — you can use either, both or neither.

Part 1: Spark Partitions

When Spark reads a file or table it decides how many pieces to split it into — usually one per ~128 MB of input, or one per Parquet file. Each piece becomes one task (Lesson 4.2).

Inspect and changePySpark
df = spark.range(0, 1_000_000)
print(df.rdd.getNumPartitions())        # e.g. 8

df2 = df.repartition(16)                # 16 even partitions — a full shuffle
df3 = df.repartition("Country")         # one partition per Country value (+ hashing)
df4 = df.repartition(8, "Country")      # 8 partitions, rows with the same Country together
df5 = df.coalesce(2)                    # merge down to 2 — no shuffle, just combines neighbours
repartition(n)coalesce(n)
Increase partitionsYesNo
Decrease partitionsYesYes
ShuffleFull shuffle (expensive)None — merges existing partitions
Result balanceEvenCan be uneven
Use forFixing skew; raising parallelism after a filter shrank the dataReducing output files before a write

When to touch Spark partitions

  • Before a write — coalesce(n) so you don't produce 200 tiny files (Lesson 4.7)
  • After a heavy filter — 1 B rows → 1 M rows still in 2,000 near-empty partitions; repartition(16) fixes the overhead
  • To fix skew — repartition(200) spreads a lopsided dataset evenly before an expensive join

Otherwise leave them alone. Spark's defaults and Fabric's adaptive query execution handle most cases.

Part 2: Table (Delta) Partitions

With partitionBy, Delta writes rows into sub-folders named by the column value:

df.write.format("delta").partitionBy("Country").mode("overwrite").saveAsTable("Sales")
Tables/Sales/
├── Country=INDIA/   part-0001.parquet, part-0002.parquet …
├── Country=USA/     part-0001.parquet …
├── Country=UK/      part-0001.parquet …
└── _delta_log/

Why: partition pruning

A query that filters on the partition column only opens the matching folders:

❌ Unpartitioned

WHERE Country = 'INDIA' → scan all files, discard 80 %.

✅ Partitioned by Country

WHERE Country = 'INDIA' → open Country=INDIA/ only. 5× less I/O.

Confirm pruning is happening with EXPLAIN — look for PartitionFilters: [Country = INDIA].

Choosing a Partition Column

The decision rests on one concept: cardinality — the number of distinct values.

ColumnDistinct valuesPartition?Why
Year~10YesFew, large folders; most queries filter by date
Year + Month~120Yes (large tables)Still manageable; monthly queries prune well
Country / Region10–200MaybeGood if queries filter on it — but watch skew (India ≫ others)
Year + Month + Day + Hour~90,000NoTens of thousands of folders of tiny files
CustomerID10 millionNeverOne folder per customer — the small-files problem at its worst
TransactionID / EmailUnique per rowNeverOne file per row
Rule of thumb: partition only when the table is large (tens of GB or more), the column is in most WHERE clauses, it has tens to a few hundred distinct values, and each partition will hold at least ~1 GB. A customer dimension with 100,000 rows should not be partitioned at all.

Date partitioning — the common case

from pyspark.sql.functions import year, month

df = df.withColumn("Year", year("OrderDate")).withColumn("Month", month("OrderDate"))

(df.write.format("delta")
   .partitionBy("Year", "Month")
   .mode("overwrite")
   .saveAsTable("Sales"))
%%sql
SELECT Country, SUM(Amount) AS TotalSales
FROM Sales
WHERE Year = 2026 AND Month = 8        -- prunes to one folder
GROUP BY Country;

Note the filter must use the partition columns (Year, Month), not the original OrderDate, for pruning to work. Keep both.

Partition Skew

Low cardinality is not enough. If one value dominates, that folder becomes huge and one task does all the work:

Country=INDIA900 M rows
Country=USA50 M
Country=UK30 M
Country=OTHER20 M

Here partitioning by Country helps US / UK queries but does nothing for the India query that dominates the workload. Partition by date instead and let Country be a regular filter column — or use ZORDER BY (Country) (Lesson 4.8), which clusters without creating folders.

Production Checklist

  • Is the table large enough (> ~10 GB)? If not, don't partition.
  • Which column appears in most WHERE clauses?
  • Is its cardinality tens-to-hundreds, not thousands-to-millions?
  • Is the data reasonably evenly spread across values?
  • Will each partition hold at least a few hundred MB?
  • Test with EXPLAIN that pruning actually happens.

Hands-On Lab

  1. Read RawSales, print getNumPartitions(), then repartition(8) and print again.
  2. Add Year and Month columns and write Sales partitioned by both.
  3. Run DESCRIBE DETAIL Sales — note partitionColumns and numFiles.
  4. Run EXPLAIN SELECT SUM(Amount) FROM Sales WHERE Year = 2026 AND Month = 8 and find PartitionFilters.
  5. Run the same EXPLAIN with WHERE OrderDate >= '2026-08-01' — pruning doesn't happen. Understand why.
Spark partitions are in-memory chunks of a DataFrame that determine parallelism; repartition(n) redistributes with a shuffle (can increase or decrease), coalesce(n) only decreases without a shuffle and is used before writes to limit file count. Table partitions, set with partitionBy("Year","Month"), physically organise a Delta table into folders so queries filtering on those columns can prune whole folders. Partition only large tables, on low-to-moderate cardinality columns that are frequently filtered, and watch for skew; never partition on high-cardinality keys like CustomerID. For those, use ZORDER instead.

Cell 1 — ParametersPySpark · Parameters

from pyspark.sql.functions import col, trim, upper, current_timestamp, lit
import json

notebookutils.fs.mkdirs(archive_folder)

Cell 3 — Process each filePySpark
for f in files:
    try:
        # Read
        df = (spark.read.option("header", "true").schema(schema).csv(f.path)
                .withColumn("SourceFile", lit(f.name))
                .withColumn("LoadTimestamp", current_timestamp()))

        # Clean
        df = (df.withColumn("CustomerName", trim(col("CustomerName")))
                .withColumn("Country", upper(trim(col("Country"))))
                .dropDuplicates([key_column]))

        # Validate
        if df.filter(col(key_column).isNull()).count() > 0:
            raise ValueError(f"{f.name}: NULL {key_column}")
        row_count = df.count()
        if row_count == 0:
            raise ValueError(f"{f.name}: empty file")

        # Load — MERGE keeps re-runs safe
        if spark.catalog.tableExists(target_table):
            (DeltaTable.forName(spark, target_table).alias("t")
                .merge(df.alias("s"), f"t.{key_column} = s.{key_column}")
                .whenMatchedUpdateAll().whenNotMatchedInsertAll().execute())
        else:
            df.write.format("delta").saveAsTable(target_table)

        # Archive only after success
        notebookutils.fs.mv(f.path, f"{archive_folder}/{f.name}")
        summary.append({"file": f.name, "rows": row_count, "status": "SUCCESS"})
        print(f"✔ {f.name}: {row_count:,} rows")

    except Exception as e:
        summary.append({"file": f.name, "rows": 0, "status": f"FAILED: {e}"})
        print(f"✘ {f.name}: {e}")         # file stays in Raw for retry
Cell 4 — Report backPySpark
failed = [s for s in summary if s["status"] != "SUCCESS"]
print(json.dumps(summary, indent=2))

if failed:
    raise Exception(f"{len(failed)} file(s) failed")       # make the pipeline go red

notebookutils.notebook.exit(json.dumps({"processed": len(summary), "rows": sum(s["rows"] for s in summary)}))

This notebook is parameterised (works for any table), idempotent (MERGE + archive means re-runs don't duplicate), safe (archives only after success), and observable (prints a summary, fails loudly, returns a result).

Best Practices

  • Never hard-code paths or table names — use the parameter cell
  • Separate configuration (Cell 1) from logic
  • Make every notebook idempotent — MERGE on a key, archive processed files
  • Validate before archiving; archive, don't delete, so you can reprocess
  • Catch exceptions to log context, then re-raise
  • Return a structured result with notebookutils.notebook.exit()
  • Name notebooks with a prefix and sequence: NB_01_INGEST_SALES
  • Schedule with a pipeline; use notebook.run for in-flow logic only

In Fabric, Apache Spark runs inside Notebooks and processes data in parallel across executors using lazy evaluation. A data engineer reads files into DataFrames with an explicit schema, cleans them with PySpark (trim, cast, when, dropDuplicates), validates and quarantines bad rows, and writes Delta tables choosing overwrite, append or MERGE by whether rows can change. Delta adds ACID transactions, time travel and OPTIMIZE / VACUUM maintenance. Large tables are partitioned on low-cardinality date columns; Spark partitions are tuned with repartition / coalesce. notebookutils handles files, parameters and orchestration so the notebook can run unattended from a pipeline.
