8.1

Streaming Data & Real-Time Intelligence

Before touching any tool, you need three ideas: what an event is, how streaming differs from batch, and which Fabric item does which job. Once those are clear, the rest of the module is just learning each item in turn.

What Is an Event?

An event is a small record that says something happened, at a particular time. It's usually a JSON message of a few hundred bytes:

{
  "machine_id": "M102",
  "temperature": 87.4,
  "pressure": 43.2,
  "status": "RUNNING",
  "event_time": "2026-08-02T20:15:01Z"
}

One event is boring. A factory with 500 machines sending one every second produces 43 million a day — and the value is in noticing now that M102's temperature has been climbing for five minutes.

DomainEventsWhy "now" matters
ManufacturingSensor readingsStop a machine before it breaks
BankingCard transactionsBlock fraud before the next purchase
E-commerceClicks, add-to-cart, ordersSpot a broken checkout within minutes
LogisticsGPS pingsLive delivery tracking, speeding alerts
IT operationsApplication logs, metricsDetect an error spike and page the on-call engineer

Batch vs Streaming

Batch (Modules 3–7)

  • Data collected, then loaded on a schedule
  • Latency: hours
  • Large loads, complex transformations
  • Pipeline → Lakehouse/Warehouse → Power BI
  • "How did we do yesterday?"

Streaming (this module)

  • Each event processed as it arrives
  • Latency: seconds
  • Small events, simple per-event logic, time windows
  • Eventstream → Eventhouse → Dashboard / Activator
  • "What is happening right now?"

They're not competitors. Most real platforms do both: stream for monitoring and alerts, batch for history, finance and complex models — often over the same data, because an Eventhouse can make its tables available in OneLake as Delta (Lesson 8.4).

Three Streaming Ideas You Need

IdeaMeaningWhy it matters
Event time vs ingestion timeWhen it happened (in the message) vs when Fabric received itA phone offline for 10 minutes sends old events late. Always analyse by event time.
WindowsA stream never ends, so you summarise it in time slices: "average per minute"Aggregations in streams are always per window (Lesson 8.2)
At-least-once deliveryStreaming systems may deliver an event twice rather than lose itDesign queries and alerts to tolerate duplicates

When Not to Stream

  • The source is a nightly file or a database that changes slowly → a pipeline (Module 3) is simpler and cheaper
  • The business looks at the report once a day → "real time" adds cost without value
  • Heavy joins across many large tables, complex business rules → batch in Lakehouse/Warehouse
  • Ask: What decision will someone make in the next few minutes with this data? No answer → batch
An event is a small, time-stamped record of something that happened, such as a sensor reading or a card payment. Streaming processes events continuously with seconds of latency, summarising them in time windows, whereas batch loads collected data on a schedule. Fabric Real-Time Intelligence provides Eventstream to capture, transform and route events, Eventhouse with KQL databases to store and query them, KQL Querysets, Real-Time Dashboards for live visuals, Activator for alerts and automated actions, and the Real-Time hub as a catalog of streams. Streaming suits decisions that must be made in minutes; slower needs are better served by batch.

An Eventstream captures events from sources such as Event Hubs, IoT Hub, Kafka, database CDC, Fabric and Azure events, a custom endpoint or sample data; optionally transforms them in flight with Filter, Manage fields, Aggregate, Group by, Union, Expand, Join or SQL; and routes them to destinations such as Eventhouse, Lakehouse, Activator, derived streams or custom endpoints. Stream aggregations use time windows — tumbling, hopping, sliding, session or snapshot. One stream can feed several destinations, typically raw data to an Eventhouse, aggregates to a Lakehouse and critical events to Activator. Eventstreams run continuously with seconds of latency, unlike scheduled pipelines and dataflows.
8.3

Simulate Streaming Data

You don't need 500 real machines to learn streaming. This lesson gives you three ways to produce a realistic stream — built-in sample data, a Python script sending to a custom endpoint, and a notebook — including the "bad" events (spikes, nulls, late and duplicate messages) that make practice realistic.

Option 1 — Built-In Sample Data

In an Eventstream: Add source → Sample data, pick a dataset (Bicycles, Yellow Taxi, Stock Market, Buses…). It starts streaming immediately. Perfect for learning the canvas; the downside is you can't control the content.

Option 2 — Custom Endpoint + Python (Recommended)

  1. In the Eventstream, Add source → Custom endpoint. Publish.
  2. Select the custom endpoint node → Event Hub tab → copy the connection string – primary key and the event hub name.
  3. On your PC (or a Fabric notebook): pip install azure-eventhub
  4. Run the script below, with the connection string in an environment variable — never pasted into code you share.
# simulate_factory.py — sends realistic machine readings to a Fabric Eventstream
import json, os, random, time, uuid
from datetime import datetime, timedelta, timezone
from azure.eventhub import EventHubProducerClient, EventData

CONN = os.environ["ES_CONNECTION_STRING"]
HUB  = os.environ["ES_EVENTHUB_NAME"]
MACHINES = [f"M{n}" for n in range(101, 111)]
base_temp = {m: random.uniform(65, 80) for m in MACHINES}

def make_event(m):
    now = datetime.now(timezone.utc)
    # slow drift + noise; M105 slowly overheats to give alerts something to find
    base_temp[m] += random.uniform(-0.3, 0.3) + (0.15 if m == "M105" else 0)
    e = {
        "event_id":   str(uuid.uuid4()),
        "machine_id": m,
        "temperature": round(base_temp[m] + random.gauss(0, 0.5), 2),
        "pressure":   round(random.uniform(40, 46), 2),
        "status":     "RUNNING",
        "event_time": now.isoformat(),
    }
    r = random.random()
    if r < 0.01: e["temperature"] = None                          # sensor glitch
    elif r < 0.02: e["event_time"] = (now - timedelta(minutes=8)).isoformat()  # late
    elif r < 0.03: e["status"] = "ERROR"
    return e

producer = EventHubProducerClient.from_connection_string(CONN, eventhub_name=HUB)
with producer:
    while True:
        batch = producer.create_batch()
        for m in MACHINES:
            e = make_event(m)
            batch.add(EventData(json.dumps(e)))
            if random.random() < 0.01:                              # duplicate delivery
                batch.add(EventData(json.dumps(e)))
        producer.send_batch(batch)
        time.sleep(1)

Ten machines, one reading per second each, with a slowly overheating machine and about 1% each of nulls, late events, errors and duplicates. Stop it with Ctrl+C.

Option 3 — From a Fabric Notebook

Paste the same code into a notebook cell (%pip install azure-eventhub first) and replace while True with a fixed number of loops, e.g. for _ in range(600): (10 minutes). Store the connection string in Azure Key Vault and read it with notebookutils.credentials.getSecret(...) rather than in the notebook.

Eventhouse & KQL Databases

An Eventhouse is where streaming data lives. It's built for one job — storing huge volumes of time-stamped data and answering questions about it in seconds, even while new data pours in. This lesson covers its structure, how data gets in, the policies that control cost and speed, and how it shares data with the rest of Fabric.

Eventhouse vs KQL Database

🏠
Eventhouse — FactoryEH
The container and compute. Shares capacity across its databases; monitors ingestion and queries. Creating one also creates a default KQL database with the same name.
🗄️
KQL database — FactoryDB
Holds tables, functions, materialized views, policies. Has its own permissions.
📋

Columnar, compressed, automatically indexed on every column. Append-optimised.

Policies: Cost and Speed Controls

Retention
How long data exists
Data older than the period is deleted automatically. Default ≈ 10 years — usually far too long for telemetry.
Caching
How much is "hot"
Recent data kept on fast local SSD; older data stays queryable from cheaper storage, more slowly.
Update policy
Transform on arrival
When rows land in table A, a function runs and writes the result into table B (Lesson 8.6).
Materialized view
Pre-computed summary
An always-up-to-date aggregation, e.g. latest reading per machine (Lesson 8.6).
// Keep raw readings for 90 days, the last 14 days hot
.alter-merge table SensorReadings policy retention softdelete = 90d recoverability = enabled

.alter table SensorReadings policy caching hot = 14d

// See what's set
.show table SensorReadings policy retention
.show table SensorReadings policy caching
Retention decides whether data exists; caching decides how fast it is. Set caching to cover the period your dashboards and alerts look at (often 7–30 days), and retention to what the business and compliance need. Hot cache is what you pay most for.

An Eventhouse is the Real-Time Intelligence store: a container providing compute for one or more KQL databases, which hold columnar, compressed, automatically indexed tables optimised for time-stamped data such as telemetry and logs. Data arrives mainly through Eventstream, and also through Get data, pipelines, ingest commands and OneLake shortcuts. Retention policies control how long data exists, caching policies how much is kept hot on SSD, update policies transform data on arrival, and materialized views keep aggregations current. With OneLake availability, KQL tables are also written as Delta in OneLake so Spark, Warehouse and Power BI can use the same data.
8.5

KQL Fundamentals

KQL (Kusto Query Language) reads top to bottom like a recipe: start with a table and pass it through a series of steps joined by the pipe |. If you know SQL, you'll be productive in an hour. This lesson covers the dozen operators that handle 90% of real queries, with a SQL translation for each.

Reading a KQL Query

SensorReadings                              // 1. start with all rows
| where EventTime > ago(1h)                 // 2. keep the last hour
| where Temperature > 90                    // 3. keep hot readings
| project MachineId, Temperature, EventTime // 4. keep these columns
| order by Temperature desc                 // 5. hottest first
| take 20                                   // 6. first 20 rows

Each line takes the output of the line above. Filter early (where on time first) — it's the biggest performance win. KQL is case-sensitive for table, column and operator names; == compares strings case-sensitively, =~ ignores case.

.create-or-alter function with (folder = "Monitoring")
HotMachines(threshold: real, lookback: timespan)
{
    SensorReadings
    | where EventTime > ago(lookback) and Temperature > threshold
    | summarize HotReadings = count(), MaxTemp = max(Temperature) by MachineId
}

A KQL Queryset is a Fabric item that saves queries in tabs, connected to one or more databases — your working notebook for KQL. Copilot in the Queryset can draft KQL from plain English; always read what it writes before trusting it.

Hands-On Lab

  3. Add a computed column Level = case(...) with OK/Warning/Critical, and count readings by level.

KQL is a read-only query language in which a query starts with a table and pipes it through operators. The core operators are where (filter, ideally on time first), project (choose columns), extend (add computed columns), summarize … by (aggregate, usually with bin() for time buckets), order/sort, top, take, distinct, join and render for charts. Time functions such as ago(), between, bin() and startofday() are central. Management commands start with a dot. let names values and sub-queries, stored functions package reusable logic, KQL Querysets save queries, and explain translates SQL into KQL.
8.6

Query with KQL: Real-Time Analysis

This lesson tackles the questions real-time teams actually ask — "what's the latest reading per machine?", "which machines have gone silent?", "is this spike unusual?" — and shows how to build a mini medallion inside the Eventhouse with update policies and materialized views, so those questions stay fast as data grows.

Recipe 1 — Parse Raw JSON

If Eventstream lands each event as a single JSON column, parse it with parse_json and dot notation:

RawEvents
| extend d = parse_json(Payload)
| project EventId     = tostring(d.event_id),
          MachineId   = tostring(d.machine_id),
          Temperature = toreal(d.temperature),
          Pressure    = toreal(d.pressure),
          Status      = tostring(d.status),
          EventTime   = todatetime(d.event_time)

Recipe 2 — Latest Reading per Machine

SensorReadings
| summarize arg_max(EventTime, *) by MachineId

arg_max(EventTime, *) returns the whole row with the highest EventTime for each machine — the "current state" tile on every operations dashboard. It also removes duplicates: summarize arg_max(EventTime, *) by EventId keeps one copy of each event.

Recipe 3 — Silent Machines

SensorReadings
| summarize LastSeen = max(EventTime) by MachineId
| where LastSeen < ago(2m)
| extend SilentFor = now() - LastSeen

A machine that stops sending is often a bigger problem than one sending high values. (This finds machines that have sent something before; to catch machines that never reported, compare with a machine reference table using a leftanti join.)

Recipe 4 — Late Events

SensorReadings
| extend IngestedAt = ingestion_time()
| extend DelaySec = datetime_diff('second', IngestedAt, EventTime)
| summarize AvgDelay = avg(DelaySec), MaxDelay = max(DelaySec), Late = countif(DelaySec > 60) by MachineId

ingestion_time() is when the row arrived. Analyse by EventTime, but watch delay — a jump means a network or device problem.

Recipe 5 — Above Threshold for N Minutes

SensorReadings
| where EventTime > ago(15m)
| summarize AvgTemp = avg(Temperature) by MachineId, Minute = bin(EventTime, 1m)
| summarize HotMinutes = countif(AvgTemp > 90), Minutes = count() by MachineId
| where HotMinutes >= 5

Using sustained averages instead of single readings avoids alerting on one noisy spike.

Recipe 6 — Anomaly Detection

SensorReadings
| where EventTime > ago(6h)
| make-series AvgTemp = avg(Temperature) default = real(null)
      on EventTime from ago(6h) to now() step 5m by MachineId
| extend AvgTemp = series_fill_linear(AvgTemp)
| extend Anomalies = series_decompose_anomalies(AvgTemp, 2.5)
| mv-expand EventTime to typeof(datetime), AvgTemp to typeof(real), Anomalies to typeof(int)
| where Anomalies != 0

make-series builds an evenly spaced series per machine (filling gaps), and series_decompose_anomalies flags points that break the usual pattern (+1 = unusually high, −1 = unusually low). Remove the last two lines and add | render anomalychart with (anomalycolumns = Anomalies) to see them on a chart.

Recipe 7 — Join with Reference Data

let Machines = datatable(MachineId:string, Line:string, MaxTemp:real)
[
    "M101","Line A",90.0,  "M102","Line A",90.0,
    "M105","Line B",85.0,  "M107","Line B",95.0
];
SensorReadings
| where EventTime > ago(10m)
| summarize arg_max(EventTime, Temperature) by MachineId
| join kind=leftouter Machines on MachineId
| extend OverLimit = Temperature > MaxTemp

In production the reference table would be a KQL table or a OneLake shortcut to a Lakehouse dimension. Put the smaller table on the right of a join.

Update policy: Bronze → Silver automatically

// 1. A function that turns raw rows into clean rows
.create-or-alter function ParseRawEvents()
{
    RawEvents
    | extend d = parse_json(Payload)
    | project EventId     = tostring(d.event_id),
              MachineId   = tostring(d.machine_id),
              Temperature = toreal(d.temperature),
              Pressure    = toreal(d.pressure),
              Status      = tostring(d.status),
              EventTime   = todatetime(d.event_time)
    | where isnotempty(MachineId) and isnotnull(EventTime)
}

// 2. Run it every time rows land in RawEvents
.alter table SensorReadings policy update
@'[{"IsEnabled": true, "Source": "RawEvents", "Query": "ParseRawEvents()", "IsTransactional": false}]'

// 3. Raw is only needed briefly
.alter-merge table RawEvents policy retention softdelete = 7d

The function's output columns must match the target table's schema. Only new rows are processed after the policy is created.

Materialized views: Gold that maintains itself

.create materialized-view with (backfill = true) MachineMinute on table SensorReadings
{
    SensorReadings
    | summarize AvgTemp = avg(Temperature), MaxTemp = max(Temperature), Readings = count()
             by MachineId, Minute = bin(EventTime, 1m)
}

.create materialized-view MachineLatest on table SensorReadings
{
    SensorReadings
    | summarize arg_max(EventTime, *) by MachineId
}

// Query like a table
MachineLatest
| project MachineId, Temperature, Status, EventTime

A materialized view is one summarize over a source table, kept up to date in the background. Dashboards that query MachineMinute instead of millions of raw rows stay fast forever.

Performance Habits

  • Filter on time first, then on other columns
  • has (whole term) is much faster than contains (substring)
  • project only the columns you need before joins
  • Query materialized views for dashboards, raw tables for investigation
  • Keep the period your dashboards use inside the hot cache

Hands-On Lab

  1. Create ParseRawEvents() and the update policy; confirm new rows appear in SensorReadings.
  2. Create MachineLatest and MachineMinute materialized views.
  3. Run recipes 3, 5 and 6 — find the overheating machine (M105) and the silent machine.
  4. Count duplicate event IDs, then de-duplicate with arg_max(EventTime, *) by EventId.
Real-time KQL analysis relies on a few patterns: parse_json for raw payloads, arg_max to get the latest row per key and to de-duplicate, max(EventTime) to find silent devices, ingestion_time() to measure lateness, sustained-threshold checks over binned averages, make-series with series_decompose_anomalies for anomaly detection, and joins with reference data. Within an Eventhouse a medallion pattern uses an update policy to transform raw rows into a clean table as they arrive, and materialized views to maintain aggregations such as per-minute summaries and latest state, keeping dashboards fast. Filtering on time first, using has instead of contains and sizing the hot cache are key performance habits.
8.7

Real-Time Dashboards

A Real-Time Dashboard is a set of tiles, each driven by a KQL query, that refreshes on its own every few seconds. It's the "control-room screen" of Real-Time Intelligence. This lesson shows how to build one, make it interactive with parameters, keep it fast with base queries, and decide when to use it instead of Power BI.

Anatomy of a Dashboard

PartWhat it is
Data sourceA connection to a KQL database (or Azure Data Explorer / Azure Monitor)
TileOne KQL query + one visual (stat, table, time chart, bar, pie, map, anomaly chart…)
PageGroups tiles: "Overview", "Machine detail"
ParameterA filter at the top (time range, machine, line) used inside tile queries
Base queryA shared query that many tiles start from — written once, maintained once
Auto refreshHow often tiles re-run their queries

Build It

  1. + New item → Real-Time Dashboard (or from a KQL table in the Real-Time hub, or "Pin to dashboard" from a Queryset).
  2. New data source → your Eventhouse KQL database.
  3. Add tile → write the query → Run → + Add visual → choose the visual and its columns → Apply.
  4. Arrange and resize tiles; add pages; Save.

Factory Overview — Tile Queries

TileVisualQuery

Use conditional formatting on the table tile (e.g. Temperature > 90 red, > 85 amber) — the eye finds problems before reading numbers.

Parameters

Parameters appear as filters at the top. Each has a variable name with an underscore prefix that you use in tile queries:

ParameterTypeIn queries
Time range (built in)Time range picker_startTime, _endTime
MachineSingle selection, values from a query: SensorReadings | distinct MachineId_machine
MachineMinute
| where Minute between (_startTime .. _endTime)
| where isempty(_machine) or MachineId == _machine    // "All" = empty value
| project Minute, MachineId, AvgTemp
Use parameters inside the query as early as possible — they make tiles faster, not just filterable. A tile that ignores _startTime/_endTime scans everything every refresh.

Base Queries

// Base query named "Readings" (variable _Readings)
SensorReadings
| where EventTime between (_startTime .. _endTime)
| where isempty(_machine) or MachineId == _machine
// Tiles start from it
_Readings | summarize Errors = countif(Status == "ERROR") by MachineId
_Readings | summarize P95 = percentile(Temperature, 95) by bin(EventTime, 5m)

Change the filter logic once and every tile follows.

Auto Refresh

Manage → Auto refresh: enable it, set a minimum interval (the fastest any viewer may choose) and a default rate. Viewers can change the rate within that limit. Every refresh re-runs every tile on the page, so:

  • Pick the slowest refresh that still serves the decision — 30 s–1 min is plenty for most operations screens
  • Point tiles at materialized views, not raw tables
  • Fewer, focused tiles per page; move detail to a second page

Sharing and Permissions

Share the dashboard like any Fabric item. Viewers also need to be able to read the data: either grant them access to the KQL database, or configure the data source to use the dashboard editor's identity so viewers see data without database permissions (decide deliberately — that second option exposes whatever the editor can see).

Hands-On Lab

  1. Create Factory Overview with the five tiles above, with conditional formatting on the current-temperature table.
  2. Add a Machine parameter and a base query; convert two tiles to use _Readings.
  3. Enable auto refresh (minimum 10 s, default 30 s) and watch M105's line climb.
  4. Add a second page "Machine detail" with an anomaly chart (Lesson 8.6 recipe 6).
A Real-Time Dashboard is a Fabric item made of tiles, each a KQL query with a visual, organised into pages and connected to KQL database data sources. Parameters — including the built-in time range (_startTime, _endTime) and query-driven lists — filter tiles and improve performance when used early in queries. Base queries share common logic across tiles. Auto refresh re-runs tiles on a default rate within a minimum interval set by the editor. Sharing requires viewers to have access to the data or a data source configured with the editor's identity. Real-Time Dashboards suit live operational monitoring; Power BI suits business reporting over semantic models.

Activator: Alerts & Actions

Dashboards need someone watching. Activator watches for you: it monitors data, and when a condition is met — per machine, per customer, per order — it sends an email or Teams message, or starts a pipeline or notebook. This lesson covers how Activator thinks and how to write rules that alert on real problems, not noise.

The most common Activator mistake is alerting on every reading. Use "becomes", add a duration, and add a filter (e.g. only Status = RUNNING) so people trust the alerts that do arrive.

  2. Create a rule: Temperature becomes greater than 90 and stays for 3 minutes, filtered to Status = RUNNING. Action: email yourself.

Activator is Fabric's no-code detection and action engine. It tracks objects (such as machines, keyed by an ID) and their properties over time, evaluates rules per object, and runs actions: email, Teams messages, running Fabric items such as pipelines and notebooks, or Power Automate custom actions. Data can come from Eventstream, Real-Time Dashboard tiles, KQL Querysets, Power BI visuals and Fabric or Azure events. Good rules avoid alert fatigue by firing when a value becomes true rather than on every event, requiring it to persist for a duration, detecting state changes and missing heartbeats, and filtering to relevant objects.
