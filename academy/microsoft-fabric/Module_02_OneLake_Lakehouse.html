What is OneLake?

OneLake is the unified, centralized data lake for Microsoft Fabric. It serves as a single storage layer for all Fabric workloads, allowing different services to access the same data without creating multiple copies.

Think of OneLake as the "OneDrive for Data", where all organizational data is stored securely and can be shared across analytics workloads.

Why OneLake?

Before OneLake, organizations often stored data in multiple locations, leading to:

Duplicate data

Higher storage costs

Data inconsistency

Complex data integration

Difficult data governance

OneLake solves these challenges by providing a single source of truth for all data.

All Fabric workloads store their data in OneLake.

2. Single Copy of Data

Instead of storing multiple copies, OneLake stores one copy that can be accessed by different services.

Example:

A sales dataset is stored once in OneLake.

Data Engineers clean it.

Data Scientists build ML models.

Analysts create Power BI reports.

Everyone works on the same data.

OneLake stores data using Delta Lake (Parquet-based) format.

Benefits include:

ACID transactions

Compatibility with Apache Spark

6. Shortcuts

This enables data virtualization and reduces storage duplication.

Interview Questions

Answer: OneLake is the unified, centralized data lake in Microsoft Fabric that stores and manages data for all Fabric workloads.

2. Why is OneLake called the "OneDrive for Data"?

Answer: Because it provides a single, centralized location for storing and sharing organizational data across multiple analytics services, similar to how OneDrive centralizes file storage.

Answer: By storing a single copy of data that can be accessed by different Fabric workloads, eliminating the need for multiple copies.

In Fabric, a Lakehouse is built on OneLake and commonly uses Delta Lake tables stored in Parquet format.

7. Why Delta Lake?

Imagine two users are updating analytical data simultaneously.

With simple files, managing consistency can become difficult.

Delta Lake provides capabilities such as:

ACID Transactions

Schema Enforcement

Schema Evolution

Table Versioning

Time Travel

MERGE / UPDATE / DELETE support

Reliable batch processing

This makes data-lake storage behave more like a managed analytical table system.

26. Lakehouse vs Warehouse — when to choose?

Choose Lakehouse when:

✓ You work heavily with Spark

✓ You need files + tables

✓ You have structured and semi-structured data

✓ You use Python / PySpark

✓ You want Medallion Architecture

✓ Data engineering is a major requirement

Choose Warehouse when:

✓ Team primarily uses T-SQL

✓ Data is strongly relational

✓ Traditional warehouse development is preferred

✓ Star schema is central

✓ SQL-based BI workloads dominate

They aren't necessarily mutually exclusive.

What is the Files Section?

The Files section in a Microsoft Fabric Lakehouse is a storage area where you can upload and organize raw or processed data files. These files are stored in OneLake and are available for data engineering, data science, and analytics workloads.

Unlike the Tables section, files in the Files area are not automatically registered as database tables. They remain as files until you load or transform them into tables.

Why Use the Files Section?

The Files section is commonly used to:

Store raw data from external sources.

Keep backup copies of datasets.

Organize data into folders.

Store files before transforming them into Delta tables.

Share files across Fabric workloads.

What is Delta Lake?

Delta Lake is an open-source storage framework that enhances data lakes with ACID transactions, schema management, versioning, and high-performance data processing.

In Microsoft Fabric, all Lakehouse tables are stored in Delta Lake format, making them reliable, scalable, and optimized for analytics.

Think of Delta Lake as a smart layer on top of Parquet files that adds database-like capabilities to data stored in OneLake.

Why Delta Lake?

Traditional data lakes often face challenges such as:

Data corruption due to concurrent writes

Duplicate records

No transaction support

Difficult schema management

Limited recovery options

Delta Lake solves these issues by adding reliability and advanced data management features.

Components of Delta Lake

1. Parquet Files

The actual table data is stored in Apache Parquet, a columnar file format.

Benefits:

Efficient storage

Optimized for big data

2. Delta Log

Every Delta table contains a hidden folder called:

_delta_log

This transaction log stores:

Table versions

Inserts

Updates

Deletes

Schema changes

Metadata

The Delta Log ensures that every operation is tracked and recoverable.

ACID Transactions

Delta Lake supports full ACID properties.

PropertyDescription
AtomicityA transaction either completes fully or not at all.
ConsistencyData remains valid before and after each transaction.
IsolationMultiple users can work simultaneously without conflicts.
DurabilityCommitted changes are permanently stored.

Example of Atomicity

Suppose you insert 10,000 sales records.

If the process fails after inserting 7,000 rows:

Without Delta Lake: Partial data may remain.

With Delta Lake: The entire transaction is rolled back, preventing incomplete data.

Time Travel

One of Delta Lake's most powerful features is Time Travel.

It allows you to:

View previous versions of a table.

Recover accidentally deleted data.

Audit historical changes.

Compare data across versions.

Example scenario:

Version 1 → Original Data

Version 2 → New Records Added

Version 3 → Records Updated

Version 4 → Incorrect Data Loaded

You can query or restore Version 3 if needed.

Schema Enforcement

Schema Enforcement prevents invalid data from being written.

Example:

Table schema:

CustomerID INT

CustomerName STRING

Amount DECIMAL

Attempting to load:

CustomerID = "ABC"

will fail because "ABC" is not an integer.

This helps maintain data quality.

Schema Evolution

Business requirements change over time.

Suppose the original table has:

| CustomerID | Name | Amount |

Later, a new column is introduced:

| CustomerID | Name | Amount | City |

Delta Lake can automatically accommodate the new column (when enabled), allowing schemas to evolve without recreating the table.

Versioning

Each modification creates a new table version.

Example:

VersionOperation
0Table created
1Initial data loaded
2New records inserted
3Data updated
4Records deleted

This version history enables auditing and recovery.

28. Interview question — Managed vs Shortcut Tables

A strong answer is:

Managed tables provide greater control over the table and data lifecycle, while shortcuts are useful for reducing data duplication and sharing or accessing existing data.
