2.1

OneLake: The Foundation

Every piece of data in Microsoft Fabric is stored in one place called OneLake. Before we talk about Lakehouses, tables or SQL, we need to understand this single storage layer — because everything else in this module is built on top of it.

What is OneLake?

OneLake is the unified, centralised data lake for Microsoft Fabric. It is a single storage layer that all Fabric workloads share, so different services can use the same data without creating multiple copies.

Think of OneLake as "OneDrive for data" — one place where your organisation's data lives, available to every team and every tool.

The Problem OneLake Solves

❌ Before OneLake

  • Each team keeps its own copy of the data
  • Higher storage costs
  • Numbers don't match between reports
  • Complex integration between systems
  • Hard to govern and secure

✅ With OneLake

  • One copy of the data, used by everyone
  • Lower storage costs
  • A single source of truth
  • Built into every Fabric workload
  • One security model (Entra ID + workspace roles)

Where OneLake Sits

Every Fabric workload writes to OneLake and reads from OneLake. There is no separate storage account to configure — it just works.

What is a Lakehouse?

A Lakehouse is the main place where you store and work with data in Fabric. The name is a clue: it is a Data Lake and a Data Warehouse combined into one item. Let's see why that combination matters.

The Old Way: Two Separate Systems

Traditionally, organisations ran two separate systems and constantly moved data between them:

🌊 Data Lake

Cheap, flexible storage for any kind of file.

  • CSV, JSON, Parquet
  • Images, logs
  • Raw and semi-structured data

🏛️ Data Warehouse

Structured, fast SQL analytics.

  • Fact and dimension tables
  • SQL queries
  • Business reporting

The Fabric Way: One Lakehouse

Lakehouse = Data Lake flexibility (Files) + Data Warehouse analytics (Tables) — in one item, on OneLake.

In Fabric, a Lakehouse is built on OneLake and stores its tables in Delta Lake format (explained in Lesson 2.4). The same data can be read by Spark, by SQL and by Power BI — no moving, no copying.

When to choose which?

Choose a Lakehouse when…

  • You work heavily with Spark / PySpark
  • You need both files and tables
  • Data is structured and semi-structured
  • Data engineering is a major requirement
  • You want a Medallion architecture

Choose a Warehouse when…

  • Your team primarily uses T-SQL
  • Data is strongly relational
  • A star schema is central
  • SQL-based BI workloads dominate
They are not mutually exclusive. A common design is Sources → Lakehouse (engineering) → Warehouse (SQL / BI) → Power BI. Many projects also feed Power BI directly from the Lakehouse Gold layer.
A Lakehouse in Microsoft Fabric combines the flexibility of a data lake with the structured analytics of a data warehouse. It is built on OneLake and has a Files area for raw data and a Tables area for Delta Lake tables. Data engineers process the data with Apache Spark, SQL users query it through the SQL Analytics Endpoint, and Power BI consumes it through the semantic model using Direct Lake — all from a single copy of the data.

Files vs Tables

Inside every Lakehouse there are two areas: Files and Tables. Beginners often mix them up. The simple rule: Files is where raw data lands; Tables is where clean, queryable data lives.

📁 The Files Area

The Files area is a storage space where you upload and organise raw or processed data files. Files here are kept exactly as uploaded — they are not automatically registered as database tables.

Why use Files?

  • Land raw data from external systems (daily CSV from stores, logs, exports)
  • Keep an untouched backup of original datasets for auditing
  • Store training datasets, images or documents for data science
  • Stage data before transforming it into a Delta table

Organise with folders

Files support folders; Tables do not. A clean folder structure makes data easy to find and manage:

Files
├── raw/            ← untouched source files
│     ├── sales_2025.csv
│     └── sales_2026.csv
├── reference/      ← lookup data
│     ├── customers.csv
│     └── products.csv

Separate raw, processed and archive data. Never edit raw files in place — keep the original so you can always reprocess it.

📊 The Tables Area

The Tables area holds structured data stored as Delta Lake tables. Unlike files, tables are registered in the Lakehouse catalog, which means they are instantly available to SQL, Spark notebooks, pipelines and Power BI.

Characteristics of a Lakehouse table

  • Stored in Delta Lake format in OneLake
  • Registered in the catalog — visible to every tool
  • Queryable with SQL and Spark
  • ACID compliant (safe concurrent reads and writes)
  • Automatically exposed through the SQL Analytics Endpoint
  • Usable by Power BI without copying data

2.4

Parquet & Delta Lake

Every table in a Fabric Lakehouse is a Delta table. To understand why, we first need to know about Parquet (how the data is stored on disk) and then Delta Lake (the smart layer that turns a pile of files into a reliable table).

Step 1 — Parquet: Column-Oriented Storage

Parquet is an open file format designed for analytics. A normal CSV stores data row by row; Parquet stores it column by column.

Row-oriented (CSV)

1, Ravi,  India, 50000
2, John,  USA,   70000
3, David, UK,    60000

Column-oriented (Parquet)

Customer_ID:   1, 2, 3
Customer_Name: Ravi, John, David
Country:       India, USA, UK
Revenue:       50000, 70000, 60000

Why it matters: an analytics query like SUM(Revenue) only needs the Revenue column. With Parquet, the engine reads just that column instead of every row — far less data, far faster queries, and much better compression.

Step 2 — Delta Lake: Parquet + a Transaction Log

Parquet alone is just files. It has no idea which files belong to which table, what changed, or what to do when two users write at the same time. Delta Lake fixes this by adding a transaction log.

📦 Parquet Files
The actual data
  • part-0001.parquet
  • part-0002.parquet
  • part-0003.parquet
+
📜 _delta_log
The transaction log
  • Which files make up the table
  • Every insert / update / delete
  • Schema and version history
= DELTA TABLE  (reliable, versioned, database-like)

Think of Delta Lake as a smart layer on top of Parquet that gives data-lake files the behaviour of a database table.

What Delta Lake Gives You

1. ACID Transactions

A
Atomicity
A write either completes fully or not at all.
C
Consistency
Data is always valid before and after a change.
I
Isolation
Many users can read and write at once without conflicts.
D
Durability
Once committed, a change is permanent.

Example: you insert 10,000 sales rows and the job fails after 7,000. Without Delta, 7,000 half-loaded rows remain. With Delta, the whole transaction is rolled back — your table is never left in a partial state.

2. Time Travel & Versioning

Every change creates a new version. You can query or restore any previous version — handy for audits and for undoing mistakes.

v0
Table created
v1
Initial load
v2
Rows inserted
v3
Rows updated
v4
Bad data loaded ⚠️

Loaded incorrect data in v4? Simply query or restore v3.

3. Schema Enforcement

Delta refuses data that doesn't match the table's columns and types. If CustomerID is INT and a file tries to load "ABC", the write fails — protecting data quality.

4. Schema Evolution

When you do want the structure to change (e.g. add a City column), Delta can accommodate the new column without recreating the table.

5. UPDATE, DELETE and MERGE

Plain Parquet files cannot be updated — you would have to rewrite them. Delta supports UPDATE, DELETE and MERGE (upsert) natively. You will use these in Lesson 2.10.

Delta Lake vs Plain Parquet

FeatureParquetDelta Lake
Storage formatParquetParquet + _delta_log
ACID transactionsNoYes
Time travelNoYes
Schema enforcementLimitedYes
Schema evolutionLimitedYes
UPDATE / DELETEDifficult (rewrite files)Native
Version historyNoYes
ReliabilityModerateHigh

Performance Benefits

  • Columnar reads — only the columns you ask for are read
  • Data skipping — the log stores min/max stats, so irrelevant files are skipped
  • Predicate pushdown — filters are applied while reading, not after
  • Compression — similar values in a column compress extremely well

Common Issues & Fixes

IssueCauseFix
Schema mismatchIncoming data has different columns / typesValidate the source, or enable schema evolution
Duplicate recordsSame file loaded twice with INSERTUse MERGE instead of repeated INSERT
Slow queriesToo many small files, no partitioningOptimise the table; partition very large tables
Delta Lake is an open-source storage framework that adds ACID transactions, schema enforcement, schema evolution, versioning and time travel on top of Parquet files. A Delta table is Parquet data files plus a _delta_log transaction log that records every change. Microsoft Fabric stores all Lakehouse tables as Delta tables, which is why they support UPDATE, DELETE and MERGE and can be queried reliably by Spark, SQL and Power BI at the same time.
2.5

Medallion Architecture

Now that you know what a Lakehouse is and how Delta tables work, the next question is: how do you organise the tables? The most common answer in Fabric is the Medallion Architecture — three layers named Bronze, Silver and Gold.

The Three Layers

🥉 BRONZE
Raw data, exactly as received
🥈 SILVER
Cleaned & standardised
🥇 GOLD
Business-ready, for reports

Easy memory trick: Bronze = Raw, Silver = Clean, Gold = Business.

🥉
Bronze — Raw layer
Tables like customers_raw, orders_raw, sales_raw. Minimal or no transformation; keeps the source structure and full history. This is the ingestion layer.
🥈
Silver — Cleaned layer
Tables like customers, orders, sales. Duplicates removed, NULLs handled, data types corrected, dates and currencies standardised, records validated, tables joined.
🥇
Gold — Business layer
Tables like fact_sales, dim_customer, daily_sales, customer_360. Aggregated, modelled and optimised for Power BI, KPIs and dashboards.

Traditionally Power BI imported a copy of the data into its own storage. With Direct Lake, Power BI reads the Delta tables straight from OneLake — no copy, no scheduled refresh of a duplicate dataset.

Keep the number of layers to three unless you have a strong reason. Bronze keeps you safe (you can always reprocess), Silver is reusable by every team, and Gold is tuned for one purpose: reporting.
Medallion Architecture organises Lakehouse data into three layers. Bronze holds raw data exactly as ingested from source systems. Silver holds cleaned, de-duplicated and standardised data. Gold holds business-ready, aggregated tables — often modelled as a star schema with fact and dimension tables — which feed the semantic model and Power BI via Direct Lake. Spark notebooks or pipelines move data from one layer to the next.
2.6

Managed Tables vs Shortcuts

A table in your Lakehouse can either own its data (a Managed Table) or point to data stored somewhere else (a Shortcut). The only question that matters is: where is the data physically stored, and who manages it?
FABRIC LAKEHOUSE
↙        ↘
MANAGED TABLEData stored & managed in this Lakehouse's OneLake storage
SHORTCUTA pointer to data that lives elsewhere — no copy made

Managed Tables

A managed table is one whose data and metadata are owned by the Lakehouse. When you write a DataFrame with saveAsTable or run CREATE TABLE, you get a managed Delta table:

df_sales.write.format("delta").mode("overwrite").saveAsTable("sales")
lh_sales_bronze
└── Tables
    └── sales
        ├── part-0001.parquet     ← data, owned by Fabric
        └── _delta_log/           ← transaction log

Fabric manages the full lifecycle: CREATE → INSERT / UPDATE / MERGE → DROP. Dropping the table removes its data too.

Shortcuts

A OneLake Shortcut is a logical reference to data located somewhere else — exactly like a Windows shortcut pointing to a folder. The shortcut is not another copy of the files; the original data stays where it is.

One copy. Fabric reads the source directly through the shortcut.

What Happens If…?

A shortcut is not an ETL process. It gives you access to data — it does not clean it, remove duplicates or apply business rules. For transformation you still use Spark notebooks, Dataflow Gen2 or pipelines.

When to Use Which

Use a Managed Table when…

  • Fabric should own the curated dataset
  • You transform the data (Silver / Gold)
  • You need full lifecycle control
  • Analytics must not depend on the source being online

Use a Shortcut when…

  • The data already exists elsewhere
  • The dataset is very large (avoid copying TBs)
  • Multiple teams need the same data
  • Another team or system owns the data
  • You want fast onboarding of an existing lake

Shortcuts may not be ideal when the source is unreliable, its schema changes often, external permissions are hard to manage, or you need heavy transformation before use. In those cases ingest into a managed table instead.

Q: You have 50 TB of historical data already in ADLS Gen2. Do you copy it all into Fabric?
Not necessarily. If the format is compatible, I would create a OneLake Shortcut to the ADLS data and use it as the Bronze / raw layer — avoiding a 50 TB copy. I would then build managed Delta tables for Silver and Gold, where cleansing, standardisation and business transformations happen, so Fabric owns the curated data while the raw data stays in place.

Four Ways to Connect External Data

1
📤 Upload Files
Lakehouse → Files → Upload → pick a CSV, Excel, JSON or Parquet file. Simplest option; good for one-off or small datasets. (Lesson 2.8)
2
🔁 Data Pipeline
Create a pipeline → add a Copy Data activity → configure the source (SQL Server, Oracle, SAP, REST, S3, ADLS) → set the Lakehouse as destination → run or schedule. Best for recurring loads from databases.
3

A visual, low-code Power Query experience. Connect to many sources, clean and shape the data, then load into Lakehouse tables. Best when transformation is needed on the way in.
4
🔗 OneLake Shortcut
Lakehouse → Files or Tables → New Shortcut → choose the external location → authenticate. The data is available instantly without copying. (Lesson 2.6)

Security Checklist

  • Use Microsoft Entra ID authentication wherever the source supports it
  • Grant only the permissions required (least privilege)
  • Never hard-code credentials — use connections and secure stores
  • Audit external connections regularly

You can bring it in by uploading files, running a Data Pipeline (Copy Data), using Dataflow Gen2 for low-code transformation, or creating a OneLake Shortcut. Importing copies the data into OneLake for fast, offline-safe analytics; a Shortcut references the data in place to avoid duplication and stay current. The choice depends on performance, storage and data-freshness needs.

1. Select, Filter and Sort

-- All rows and columns
SELECT * FROM Sales;

-- Only the columns you need
SELECT CustomerName, Amount FROM Sales;

-- Filter rows with WHERE
SELECT * FROM Sales WHERE Country = 'India';

-- Multiple conditions
SELECT * FROM Sales WHERE Country = 'India' AND Amount > 500;

-- Sort (ASC = smallest first, DESC = largest first)
SELECT * FROM Sales ORDER BY Amount DESC;

-- First 3 rows only (T-SQL uses TOP, not LIMIT)
SELECT TOP 3 * FROM Sales ORDER BY Amount DESC;

-- Pattern match: names starting with A
SELECT * FROM Sales WHERE CustomerName LIKE 'A%';

-- Unique values
SELECT DISTINCT Country FROM Sales;

2. Aggregate Functions

Aggregates collapse many rows into one number:

SELECT COUNT(*)    AS TotalSales   FROM Sales;   -- 5
SELECT SUM(Amount) AS TotalRevenue FROM Sales;   -- 5270
SELECT AVG(Amount) AS AverageSale  FROM Sales;   -- 1054
SELECT MAX(Amount) AS HighestSale  FROM Sales;   -- 2500
SELECT MIN(Amount) AS LowestSale   FROM Sales;   -- 120

3. GROUP BY and HAVING

GROUP BY gives one aggregate per group. HAVING filters those groups after aggregation:

-- Total sales per country
SELECT Country, SUM(Amount) AS TotalSales
FROM Sales
GROUP BY Country;

-- Only countries with more than 1000 in sales
SELECT Country, SUM(Amount) AS TotalSales
FROM Sales
GROUP BY Country
HAVING SUM(Amount) > 1000;
CountryTotalSales
India1970
USA2500
UK800
WHERE vs HAVING — a classic interview question. WHERE filters individual rows before grouping; HAVING filters the grouped results after GROUP BY.

4. Joining Tables

A JOIN combines rows from two tables where a column matches. Aliases (s, c) keep the query short:

SELECT
  s.CustomerName,
  c.City,
  s.Amount
FROM Sales s
JOIN Customers c
  ON s.CustomerName = c.CustomerName;
CustomerNameCityAmount
JohnNew York2500
AnitaHyderabad1200
DavidLondon800

Priya and Rahul are missing because they have no matching row in Customers — an inner join only returns matches.

5. Column Aliases and Dates

-- Rename output columns
SELECT CustomerName AS Customer, Amount AS SalesAmount FROM Sales;

-- Date filtering (on a table with an OrderDate column)
SELECT * FROM Orders WHERE OrderDate >= '2026-01-01';

6. Save a Query as a View

A view is a saved query that behaves like a table. Use it for queries you run often:

CREATE VIEW HighValueSales AS
SELECT * FROM Sales WHERE Amount > 1000;

SELECT * FROM HighValueSales;

Query Performance Tips

  • Select only the columns you need — avoid SELECT * in production
  • Filter as early as possible with WHERE
  • Avoid unnecessary joins
  • Use the right data types (numbers as numbers, dates as dates)
  • Partition very large tables where appropriate

Real-World Example

A retail analyst runs these queries daily against the Sales Delta table: total daily revenue, sales by country, top-selling products, customers above ₹10,000, and monthly trends. The results feed a Power BI dashboard for management — all from the same Lakehouse, no data copied.

The SQL Analytics Endpoint is a built-in T-SQL interface for querying Delta tables in a Lakehouse. You can SELECT, filter with WHERE, sort with ORDER BY, aggregate with COUNT / SUM / AVG, group with GROUP BY and HAVING, combine tables with JOIN, and save queries as views. Hands-On: Create & Manage Delta Tables

So far you have created a table by loading a CSV. In this final lab you will create Delta tables three different ways and then change the data with INSERT, UPDATE, DELETE and MERGE — the operations that make Delta Lake different from plain files.
In a Fabric Lakehouse, every table you create is a Delta table by default. You never have to specify the format.

Three Ways to Create a Delta Table

Method 1 — SQL (Spark SQL in a notebook)

CREATE TABLE Sales
(
  SaleID        INT,
  CustomerName  STRING,
  Country       STRING,
  Product       STRING,
  Amount        DECIMAL(10,2)
);

SELECT * FROM Sales;   -- empty for now

Method 2 — Load from a file

Upload a CSV to Files, right-click → Load to Tables, name it, confirm the schema and click Load — exactly what you did in Lesson 2.8.

Method 3 — PySpark DataFrame

data = [
    (1, "John",  "USA",   "Laptop",  2500),
    (2, "Anita", "India", "Mobile",  1200),
    (3, "David", "UK",    "Monitor",  800)
]
columns = ["SaleID", "CustomerName", "Country", "Product", "Amount"]

df = spark.createDataFrame(data, columns)
df.write.mode("overwrite").saveAsTable("Sales")

(A fourth way — Data Pipelines — loads from external systems automatically; see Lesson 2.7.)

Changing Data

INSERT — add rows

INSERT INTO Sales VALUES
(4, 'Priya', 'India', 'Tablet',   650),
(5, 'Rahul', 'India', 'Keyboard', 120);

UPDATE — change existing rows

UPDATE Sales SET Amount = 1500 WHERE SaleID = 2;

DELETE — remove rows

DELETE FROM Sales WHERE SaleID = 5;
Each of these creates a new version in the _delta_log. If you make a mistake, Time Travel (Lesson 2.4) lets you go back.

MERGE — update and insert in one step (upsert)

This is the most important operation for daily loads. Suppose a table NewSales arrives each night with some rows that already exist (changed) and some that are new:

MERGE INTO Sales AS Target
USING NewSales AS Source
ON Target.SaleID = Source.SaleID

WHEN MATCHED THEN            -- row exists → update it
  UPDATE SET
    Target.Amount  = Source.Amount,
    Target.Product = Source.Product

WHEN NOT MATCHED THEN        -- row is new → insert it
  INSERT (SaleID, CustomerName, Country, Product, Amount)
  VALUES (Source.SaleID, Source.CustomerName, Source.Country,
          Source.Product, Source.Amount);

Why MERGE instead of delete-and-reload? It is faster, keeps history intact, avoids duplicates, and the table is never empty mid-load.

Best Practices

  • Use a reliable business key (e.g. SaleID) for MERGE matching
  • Prefer MERGE over delete-and-reload for incremental loads
  • Define appropriate data types up front — fixing them later is harder
  • Keep the raw file in Files for auditing
  • Validate data before loading into production tables
  • Periodically optimise large tables (compact small files) and partition very large ones

Real-World Example

A retail company receives Sales.csv every day. The file lands in Files, is loaded into the Sales Delta table, and a nightly MERGE inserts new orders and updates changed ones. Analysts query the table through the SQL endpoint, and Power BI shows near-real-time sales — with full version history available if anything needs to be audited or rolled back.

A Delta table is a table stored in Delta Lake format — Parquet files plus a transaction log — and is the default table type in a Fabric Lakehouse. You can create one with CREATE TABLE, by loading a file, from a PySpark DataFrame with saveAsTable, or via a pipeline. Delta tables support INSERT, UPDATE, DELETE and MERGE; MERGE performs an upsert (update matching rows, insert new ones) in a single operation and is the standard pattern for incremental loads.
