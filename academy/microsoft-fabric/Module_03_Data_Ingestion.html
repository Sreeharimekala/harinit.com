3.1

Data Factory in Fabric

In Module 2 you loaded a CSV by hand. Real organisations have hundreds of tables in dozens of systems that change every day — nobody uploads those manually. Data Factory is the part of Fabric that connects to those systems and moves the data in automatically. This lesson explains what it is and where it sits.

What is Data Factory?

Data Factory in Microsoft Fabric is the platform's data integration and orchestration experience. It connects to data sources, ingests (copies) data, transforms it, and coordinates the whole workflow from start to finish. If you know Azure Data Factory (ADF), most concepts will feel familiar.

Fabric Data Factory = Connect + Ingest + Transform + Orchestrate

The Problem It Solves

Enterprise data is scattered across many systems. Before anyone can analyse it, it has to be extracted → copied → cleaned → transformed → scheduled → stored. Data Factory does all of these steps.

3.2

Pipelines: Activities, Parameters & Control Flow

A pipeline is the container for everything Data Factory does. Think of it as a recipe: a list of steps (activities), run in order, some of them conditional. This lesson covers the building blocks you need before you can build a real one.

Pipelines and Activities

A Pipeline is a collection of Activities that together perform a data workflow. Each activity is a single operation — copy data, run a notebook, run a stored procedure, wait, loop.

Every production pipeline needs a failure branch. If a copy fails at 2 AM, you want to know at 2 AM — not when a manager opens an empty dashboard at 9 AM.

Connections and Gateways

Before a pipeline can touch an external system it needs a Connection: the server, database, authentication method and credentials. Connections are created once and reused across pipelines.

Monitoring

After a run, the monitoring view answers: did it run? did it succeed? how long did it take? which activity failed and why? A typical Copy Activity result:

Pipeline:      PL_SQLServer_To_Lakehouse
Status:        Succeeded
Rows read:     150,000
Rows written:  150,000
Duration:      00:02:15
Throughput:    1.1 MB/s
Rows read should equal rows written. If they don't, something was dropped — investigate before the data reaches a report.

Naming Conventions

Give every item a prefix that says what it is. It makes a workspace with 200 items readable:

PL_SQL_TO_BRONZE          ← Pipeline
PL_BRONZE_TO_SILVER
NB_CLEAN_CUSTOMERS        ← Notebook
DFG_CUSTOMER_CLEANING    ← Dataflow Gen2
LH_SALES                 ← Lakehouse

Best Practices

  • Use parameters — never hard-code table names, dates or paths
  • Build one metadata-driven pipeline instead of one pipeline per table
  • Always add a failure branch (log + notify)
  • Keep DEV / TEST / PROD workspaces separate
  • Follow least-privilege: the pipeline's identity should only read what it needs
  • Monitor every scheduled run; alert on failures and on unusual row counts
A pipeline is an orchestration container made of activities connected by success / failure / completion dependencies. Parameters are inputs that make a pipeline reusable; variables hold values during execution. Lookup, ForEach and If provide control flow, which enables metadata-driven ingestion — one parameterised pipeline that loads many tables from a configuration table. Pipelines are scheduled and monitored for status, duration, rows read / written and errors.
3.3

Copy Activity

Of all the activities, Copy Activity is the one you will use most. Its job is deliberately simple: read data from a source and write it to a destination. This lesson covers how it is configured and tuned; the three labs at the end of the module use it for real.
SOURCESQL Server · Oracle · Blob · ADLS · REST · S3
→
COPY ACTIVITYread → map → write
→
DESTINATIONLakehouse · Warehouse · ADLS · SQL

The Five Things You Configure

1
Source
Where the data comes from. Pick a connection, then a table — or write a query to select specific columns, filter rows or join tables.
2
Destination (Sink)
Where it goes. For a Lakehouse: choose Tables (creates a Delta table) or Files (lands the raw file). Choose whether to overwrite or append.
3
Mapping
Which source column goes to which destination column. If the names match, Fabric maps them automatically; otherwise map them yourself and check data types.
4
Settings — performance
Degree of parallelism, partitioning for large tables, staging, file format. Only matters when data volumes are large.
5
Settings — fault tolerance
What to do with bad rows (skip and log, or fail the run), retry count and timeout.

Table or Query as the Source?

Select a table

Simplest. Copies every column and every row.

Good for: small tables, reference data, first load.

Write a query

SELECT CustomerID, CustomerName,
       Country, ModifiedDate
FROM dbo.Customers
WHERE ModifiedDate > '2026-08-21';

Good for: choosing columns, filtering at the source, joins, incremental loads.

Filter at the source. A WHERE clause in the source query means fewer rows leave the database. Filtering after copying 100 million rows is the single most common performance mistake.

Performance for Large Tables

Instead of copying one big table in one stream, Copy Activity can split the work and run it in parallel:

Orders table50 million rows
↓ partition by OrderDate ↓
Partition 12024
Partition 22025
Partition 32026
↓ written in parallel ↓
Lakehouse Delta table
  • Parallel copy — several streams at once
  • Partitioning — split by a date or ID range
  • Prefer Parquet over CSV when the source is files
  • Select only needed columns and filter at the source
  • Index the filter column (ModifiedDate, OrderDate) in the source database

Full Load vs Incremental Load

Full load

Copy everything, every run.

  • Simple
  • First-time migration
  • Small or reference tables

Incremental load

Copy only new or changed rows.

  • Needs a watermark column
  • Far less data moved
  • Essential for large tables

Incremental loading is important enough to get its own lesson — see 3.8.

Can Copy Activity Transform Data?

Only lightly — column mapping, type conversion and format changes (CSV → Parquet). It is not for cleaning, de-duplicating or joining. For that you add a Dataflow Gen2 or a notebook after the copy.

Copy ActivityDataflow Gen2
Primary purposeMove dataTransform data
Large-volume movementExcellentGood
Complex transformationsLimitedStrong (Power Query)
Best forIngestion into BronzeCleansing into Silver

Common Errors

ErrorLikely causeFix
Connection failureWrong credentials, firewall, gateway offlineTest the connection; check gateway status
Mapping / type errorSource VARCHAR → destination DECIMAL with bad valuesFix mapping; clean or cast at the source
Duplicate rowsFull load run repeatedly in append modeUse overwrite, or incremental + MERGE
TimeoutHuge table, slow query, no indexFilter at source, partition, add index
Copy Activity is the Data Factory pipeline activity that moves data from a source to a destination. You configure the source (table or query), the destination, column mapping, and performance / fault-tolerance settings. It supports full and incremental loads and many connectors, and performance is improved by filtering at the source, parallel copy and partitioning. It performs only light transformation — for cleansing you use Dataflow Gen2 or a notebook.

Under the Hood: the M Language

Every visual step generates code in Power Query's M language. You don't need to write M to start, but seeing it helps for advanced cases. Filtering to Country = "India" produces:

Table.SelectRows(Source, each [Country] = "India")

Query Folding — the Performance Concept to Know

When the source is a database, Power Query tries to push your transformations back to the source as SQL. This is called query folding.

❌ Without folding

100M
rows transferred

All rows are pulled into Fabric, then filtered.

✅ With folding

50K
rows transferred

The filter becomes a WHERE clause in the source; only matching rows move.

Do filtering and column removal early in your steps — those fold well. Some steps (custom functions, certain text operations) break folding, and everything after them runs in Fabric.

Dataflow Gen2 vs Power Query in Power BI Desktop

Same engine, different place. In Power BI Desktop, the cleaning logic is locked inside one report. In a Dataflow, the cleaned table lands in the Lakehouse and every report, notebook and SQL user can reuse it:

Best Practices

  • Remove unneeded columns and filter rows first (preserves folding)
  • Set correct data types early and handle NULLs deliberately
  • Keep the step list short and readable — a Dataflow with 60 steps is hard to maintain
  • Name them DFG_CUSTOMER_CLEANING, not Dataflow 3
  • Watch for schema changes in the source — a renamed column breaks the flow
  • Monitor refresh failures
Dataflow Gen2 is Fabric's low-code data transformation tool, part of Data Factory, built on Power Query and the M language. You connect to a source, apply visual transformations recorded as Applied Steps — filter, join, group, remove duplicates, change types — and write the result to a Lakehouse or Warehouse table. Query folding pushes transformations to the source database for performance. A pipeline can orchestrate a Dataflow as one step in a larger workflow.

Decision Guide

Use Dataflow Gen2 when…

  • The team already knows Power Query
  • Standard cleansing: dedupe, NULLs, types, renames
  • Joins, filters and simple aggregations
  • Business analysts need to maintain the logic

Use a Notebook when…

  • Transformations are complex or algorithmic
  • Very large data needing Spark parallelism
  • You need Python libraries or custom functions
  • Engineers want version-controlled code

Rule of thumb: simple / medium transformation → Dataflow Gen2; complex / large-scale → Notebook; moving data → Copy Activity; coordinating all of them → Pipeline.

3.6

Database & File Sources: SQL Server, Blob Storage, ADLS Gen2

Copy Activity works the same way for every source, but the sources themselves behave differently. This lesson explains the three you will meet most often — a relational database (SQL Server), object storage (Azure Blob) and a data lake (ADLS Gen2) — and what is special about each. REST APIs get their own lesson next.

🗃️ SQL Server (and Azure SQL Database)

SQL Server is a relational database — data lives in tables with fixed columns and types. It typically holds a company's operational data: customers, orders, inventory, finance. Fabric copies these tables into a Lakehouse so analysts can query them without slowing down the live application.

Two flavours

On-premises SQL Server

Runs inside the company network. Fabric needs an on-premises data gateway to reach it.

Azure SQL Database

Cloud-hosted. Fabric connects directly; no gateway needed.

What makes SQL Server easy for incremental loads

Relational tables usually have a ModifiedDate or an increasing ID column. That makes it simple to ask "give me only rows changed since yesterday" — the watermark pattern in Lesson 3.8.

SELECT CustomerID, CustomerName, Country, Email, ModifiedDate
FROM dbo.Customers
WHERE ModifiedDate > '2026-08-21 00:00:00';   -- only the changes
Make sure the watermark column (ModifiedDate) has an index in SQL Server. Without one, the incremental query scans the whole table and the benefit disappears.

☁️ Azure Blob Storage

Blob Storage is Microsoft's general-purpose object storage — a place to put files of any kind: CSV, JSON, Parquet, images, logs, backups. Many systems export daily files here, which Fabric then picks up.

The three building blocks

Storage Account   retailstorage          ← the namespace (like a drive)
└── Container     sales                  ← a top-level grouping (like a root folder)
    ├── Blob      sales_2026_08_20.csv   ← an individual file
    ├── Blob      sales_2026_08_21.csv
    └── Blob      sales_2026_08_22.csv
Blob typeUsed for

Authentication

Account key, Shared Access Signature (SAS) token, or Microsoft Entra ID / managed identity (preferred — no long-lived secret to leak).

🏞️ Azure Data Lake Storage Gen2 (ADLS)

ADLS Gen2 is Blob Storage with a hierarchical namespace switched on. That one feature turns a flat bucket of files into a real file system with directories — and that is what makes it suitable for an enterprise data lake.

Hierarchical namespace — why it matters

Blob (flat)

container/
├── file1.csv
├── file2.csv
└── "raw/sales/file3.csv"  ← just a long name

"Folders" are only a naming convention. Renaming a folder means renaming every file.

ADLS Gen2 (hierarchical)

container/
├── raw/
│   └── sales/ file3.csv
├── processed/
└── curated/

Real directories. Fast renames, and permissions (ACLs) can be set per folder.

FeatureAzure Blob StorageADLS Gen2
Object storageYesYes (built on Blob)
Hierarchical namespaceNoYes
Folder-level permissions (ACLs)NoYes
Big-data analyticsSupportedOptimised
Typical useGeneral files, backups, exportsEnterprise data lake
OneLake Shortcut supportLimitedYes

Simple rule: Blob = general-purpose file storage. ADLS Gen2 = data lake for analytics.

How a data lake is usually organised

companydatalake
├── sales/
│   ├── raw/        ← landing zone (CSV / JSON)
│   ├── processed/  ← cleaned (Parquet)
│   └── curated/    ← business-ready (Delta)
├── finance/
│   ├── raw/  processed/  curated/
└── customer/
    ├── raw/  processed/  curated/

Domain first, then stage — the same Bronze / Silver / Gold idea, expressed as folders.

Date-partitioned folders

Daily files are often stored by date. This makes "load only today's file" trivial and lets queries skip irrelevant folders:

sales/
└── year=2026/
    └── month=08/
        ├── day=20/ sales.parquet
        ├── day=21/ sales.parquet
        └── day=22/ sales.parquet   ← today, process this one

File Formats: CSV vs Parquet

Whatever the storage, the file format matters a lot for performance:

FeatureCSVParquet
StoragePlain text, row by rowBinary, column by column
CompressionPoorExcellent
Schema (types)Not stored — must be inferredEmbedded in the file
Analytics speedSlowerMuch faster
Human readableYesNo
Accept CSV from source systems if you must, but convert to Parquet (or straight to a Delta table) as soon as it lands. Also avoid thousands of tiny files — they slow every engine down; combine them into larger files.

SQL Server is a relational source: Fabric connects via a connection (and a gateway if on-premises) and typically uses a ModifiedDate watermark for incremental loads. Azure Blob Storage is general-purpose object storage organised as storage account → container → blob; ADLS Gen2 builds on it by adding a hierarchical namespace and folder-level ACLs, making it the standard enterprise data lake. ADLS data can be copied into OneLake with Copy Activity or referenced in place with a OneLake Shortcut. For files, Parquet is strongly preferred over CSV for analytics.

REST API Sources

Modern SaaS applications — CRM, payments, e-commerce, HR systems — don't give you database access. They give you an API. This lesson explains how REST APIs work and the four things that make API ingestion different: authentication, JSON, pagination and rate limits.

What is a REST API?

A REST API lets one application ask another for data over HTTP — the same protocol your browser uses. You send a request to a URL called an endpoint; the API sends back a response, almost always in JSON.

The Four API Challenges

1. Authentication

Almost every API needs you to prove who you are:

MethodHow it worksNotes
API keyA secret string sent in a header: x-api-key: ABC123Simple; common for SaaS
Basic authUsername + passwordLeast secure; avoid for production
Bearer tokenHeader: Authorization: Bearer <token>Usually obtained via OAuth
OAuth 2.0App → auth server → short-lived access token → APIMost secure; tokens expire and refresh
Store keys and tokens in the Fabric connection, never typed into a pipeline expression or notebook. A key in plain text ends up in source control sooner or later.

2. Pagination

APIs never return a million rows in one response. They return a page (say 1,000 rows) and expect you to ask for the next one until there are none left:

Request 1?page=1
→
Request 2?page=2
→
Request 3?page=3
→ … until empty →
Lakehouseall rows
StyleExample

Offset / limit?offset=0&limit=1000, ?offset=1000&limit=1000
Cursor?cursor=abc123 (the API gives you the next cursor)
Next URLThe response includes "next": "https://…/orders?page=2"

Copy Activity's REST connector has built-in pagination rules for these patterns. Forgetting pagination is the number-one API bug — the pipeline "succeeds" but only loads the first 1,000 rows.

3. Rate limits

Providers cap how often you can call them (e.g. 1,000 requests per hour). Exceed it and you get 429. Defences: incremental extraction (fewer calls), efficient page sizes, and retry with exponential backoff.

4. Nested JSON

Real APIs are rarely flat:

What the API returns

    "id": 1001,

Flattening nested objects needs Dataflow Gen2 or a Spark notebook.

The robust pattern is to land the raw JSON in Lakehouse Files (Bronze), then flatten into a Delta table (Silver). You keep the original for reprocessing.

Incremental Loading from an API

Most APIs offer a parameter like updatedAfter, modifiedSince or fromDate. Pass your last watermark and you only receive the changes:

3.8

Incremental Loads

Every previous lesson mentioned "incremental loading". Here is the full picture. It is the single most important design pattern in data ingestion: load only what changed, not the whole table, every time. Get this right and your pipelines are fast and cheap; get it wrong and you get duplicates or missing rows.

The Problem with Full Loads

An Orders table has 50 million rows. Each day about 100,000 are inserted or updated.

❌ Full load, every night

50,000,000
rows copied daily

Hours of runtime, heavy network and compute — to re-copy 49.9 million rows that haven't changed.

✅ Incremental load

100,000
rows copied daily

Minutes. Only the rows that are new or changed since the last successful run.

Full loadIncremental load
Rows processedAllNew + changed
Runtime & costHighLow
ComplexitySimpleModerate (needs a watermark + MERGE)
Use forFirst load, small / reference tablesEvery regular load of a large table

The Watermark

A watermark is simply a bookmark: "I have successfully processed everything up to this point." Each run reads the bookmark, loads what came after it, and moves the bookmark forward.

Run 1
Watermark = 2026-08-20 → load rows modified after 20 Aug → success → new watermark = 2026-08-21
Run 2
Watermark = 2026-08-21 → load rows modified after 21 Aug → success → new watermark = 2026-08-22
Run 3
Watermark = 2026-08-22 → load rows modified after 22 Aug → failed → watermark stays at 2026-08-22
Run 4
Watermark = 2026-08-22 → retries the same window, nothing is lost

Four ways to detect changes

MethodHowExample filterCatches deletes?
Watermark columnA ModifiedDate / UpdatedAt columnWHERE ModifiedDate > '2026-08-21'No
Increasing IDAn ever-growing key (insert-only tables)WHERE OrderID > 1003No
Change TrackingDatabase records which rows changedBuilt-in SQL Server featureYes
Change Data Capture (CDC)Database logs every insert / update / deleteBuilt-in SQL Server featureYes

Where to keep the watermark: a control table

Never keep the watermark only inside the pipeline. Store it in a small table so it survives, is visible, and can be reset by hand if needed:

CREATE TABLE PipelineWatermark
(
    TableName       VARCHAR(100),
    WatermarkValue  DATETIME2,
    LastRunDate     DATETIME2
);
TableNameWatermarkValueLastRunDate

The Incremental Pipeline Design

Five activities, always in this order:

1. Lookupread watermark
→
2. Copy ActivityWHERE ModifiedDate > @watermark
→
3. Staging tablenew / changed rows
→
4. MERGEinto Delta table
→
5. Update watermarkonly on success

Step 2 — the source query

SELECT CustomerID, CustomerName, Country, ModifiedDate
FROM dbo.Customers
WHERE ModifiedDate > '2026-08-21 00:00:00';   -- @watermark from the Lookup

Step 4 — MERGE: update what exists, insert what's new

The staging table holds a mix: some rows already exist in the target (they were updated), some are brand new. MERGE handles both in one statement (you met it in Module 2):

MERGE INTO Customers AS Target
USING CustomerStage AS Source
ON Target.CustomerID = Source.CustomerID

WHEN MATCHED THEN
  UPDATE SET Target.CustomerName = Source.CustomerName,
             Target.Country      = Source.Country,
             Target.ModifiedDate = Source.ModifiedDate

WHEN NOT MATCHED THEN
  INSERT (CustomerID, CustomerName, Country, ModifiedDate)
  VALUES (Source.CustomerID, Source.CustomerName, Source.Country, Source.ModifiedDate);
Staging101 John (changed) · 104 Rahul (new)
→ MERGE →
Customers101 updated · 104 inserted · others untouched

Step 5 — the golden rule

Update the watermark only after the MERGE succeeds. If you move the bookmark first and the load then fails, the next run starts after the failed window — those rows are silently lost forever. This is the most common incremental-load bug.

Incremental Patterns by Source

SourceHow to find "what's new"
SQL ServerWatermark column (ModifiedDate), Change Tracking or CDC
Blob / ADLS filesNew date-partitioned folder, file-name pattern, file modified time, or a processed-file tracking table
REST APIParameter such as ?updatedAfter=<watermark>, or an API-provided cursor

Three Hard Cases

1. Deleted rows

If a row is deleted in the source, a ModifiedDate filter never sees it — the row simply stops appearing. Your Lakehouse keeps it forever. Options:

  • CDC / Change Tracking — the database tells you about deletes
  • Soft delete — the source sets IsDeleted = 1 instead of deleting (and updates ModifiedDate)
  • Periodic reconciliation — occasionally compare source and target keys and remove the orphans

2. Late-arriving data

A row can be committed with a ModifiedDate slightly earlier than your watermark (clock skew, long transactions). Use a small overlap window and let MERGE de-duplicate:

WHERE ModifiedDate >= DATEADD(minute, -5, @LastWatermark)

3. Re-running a pipeline

Pipelines get re-run — after a failure, or by accident. An idempotent pipeline produces the same result however many times it runs. MERGE on a business key gives you this; plain INSERT does not.

Common Problems and Their Causes

SymptomCauseFix
Duplicate rowsINSERT instead of MERGE; or overlap window without MERGEMERGE on a stable business key
Missing rowsWatermark updated before the load succeededUpdate watermark last, only on success
Old rows reappear / wrong valuesLate-arriving data missedAdd an overlap window
Deleted rows still presentWatermark can't see deletesCDC, soft delete or reconciliation
Incremental run as slow as fullNo index on the watermark columnIndex ModifiedDate in the source

Best Practices

  • Choose a reliable watermark: ModifiedDate, UpdatedAt, sequence ID or change version
  • Store the watermark in a control table, not in the pipeline
  • Update it only after a fully successful load
  • Use MERGE on a business key so re-runs are safe (idempotent)
  • Add a small overlap window for late-arriving rows
  • Compare source and target row counts after each run
  • Plan for deletes up front — ask the source team how deletions happen
An incremental load processes only new or changed rows since the last successful run, using a watermark — a stored value such as the maximum ModifiedDate — to identify them. The pipeline reads the watermark, extracts rows beyond it, MERGEs them into the Delta table (update matches, insert new), and only then advances the watermark. Deletes need CDC, a soft-delete flag or reconciliation; late-arriving rows are handled with an overlap window plus MERGE. The result is a fast, idempotent pipeline that moves a fraction of the data a full load would.

POWER BI
Fabric Data Factory is the ingestion and orchestration layer. A pipeline coordinates Copy Activities that move data from SQL Server, cloud storage and REST APIs into OneLake, with Dataflow Gen2 or notebooks transforming it through Bronze, Silver and Gold. Production pipelines are parameterised and metadata-driven, load incrementally using a watermark and MERGE, handle failures with a dedicated branch, and are validated by comparing row counts — because a green status alone never proves the data is right.
