Make pipelines, notebooks, queries and reports fast — and keep your Fabric capacity bill under control — by measuring first and fixing the real bottleneck.

10.1

Performance Mindset & Capacity

In Fabric, every notebook, pipeline, query and report draws from one shared pool of compute: your capacity. A slow job isn't just annoying — it uses capacity other workloads need, and can slow down everyone's reports. This lesson explains how capacity is measured and shared, and the method for improving performance without guessing.

Capacity in One Picture

F64 capacity64 Capacity Units (CU)
→ shared by →
Spark notebooks
Pipelines
Warehouse / SQL
Power BI
Eventhouse
TermMeaning
SKUCapacity size: F2, F4 … F64 … F2048. The number is the Capacity Units per second.
CU-secondsHow usage is measured: a job using 8 CU for 100 seconds consumes 800 CU-seconds.
Interactive operationsUser-triggered and short: report queries, ad-hoc SQL. Their usage is smoothed over ~5 minutes.
Background operationsScheduled or long: pipelines, notebooks, refreshes. Smoothed over 24 hours.
BurstingA job can briefly use more than the capacity size — the excess is paid back from future capacity.
ThrottlingIf future capacity is used up too far ahead, Fabric first delays interactive requests, then rejects interactive and eventually background ones.
Throttling affects the whole capacity. One badly written notebook running every 15 minutes can push a capacity into overage — and the CFO's dashboard starts timing out. Performance work protects everyone sharing the capacity.

Speed vs Cost

Faster usually means cheaper: a job finishing in 10 minutes on the same compute consumes half the CU-seconds of one taking 20 minutes. But "faster by adding a bigger pool" can cost more. Always compare CU consumed, not just duration.

The Method: Measure → Find → Fix → Verify

  1. Measure a baseline: duration, CU consumed (Capacity Metrics app), rows processed, files read.
  2. Find the bottleneck — the one stage, query or table responsible for most of the time (Lesson 10.6). It's rarely where you'd guess.
  3. Fix one thing at a time, starting with the biggest win.
  4. Verify against the baseline. Keep the change only if it helped.

Where the Big Wins Usually Are

1Do less work: incremental loads instead of full reloads; filter and select columns early10–100×10.4, 10.7
2Table layout: right file sizes, compaction, clustering, V-Order where reads matter2–10×10.2
3Avoid expensive operations: shuffles, skew, Python UDFs, collect()2–10×10.4

Hands-On Lab

  1. Ask your admin to install (or give you access to) the Microsoft Fabric Capacity Metrics app.
  2. Find your capacity's top 5 items by CU consumption over the last 14 days.
  3. Pick your most expensive notebook or pipeline; note its duration and CU as the baseline for this module.
Fabric workloads share a capacity measured in Capacity Units; usage is counted in CU-seconds. Interactive operations are smoothed over about five minutes and background operations over 24 hours; jobs can burst above the capacity size and pay it back later, and sustained overuse leads to throttling — delays then rejections — that affects every workload on the capacity. Performance work therefore follows a measure, find, fix, verify method, prioritising doing less work (incremental processing, early filtering), good Delta layout, avoiding expensive operations such as shuffles and UDFs, and compute settings, before scaling up the capacity.
10.2

Delta Table Layout

Every engine in Fabric — Spark, SQL, Power BI Direct Lake — reads the same Delta files, so how those files are laid out affects them all. Module 4 introduced the small-files problem, OPTIMIZE and partitioning. This lesson builds the complete layout toolkit and shows which settings suit which consumer.

What "Good Layout" Means

✗ Fragmented

FactSales/
  part-00001.parquet    2 MB
  part-00002.parquet    1 MB
  ... 18,400 files, avg 3 MB
  rows mixed randomly

Every query opens thousands of files; filters can't skip any.

✓ Compact and clustered

FactSales/
  part-00001.parquet  512 MB  2024-01..03
  part-00002.parquet  498 MB  2024-04..06
  ... 120 files
  rows grouped by OrderDate

Few files; a date filter skips most of them using min/max statistics.

The Layout Toolkit

FeatureWhat it doesWhen
Optimize writeCombines data before writing so each write produces fewer, larger filesPartitioned tables, frequent small writes, MERGE/UPDATE/DELETE
Auto compactionAfter a write, checks for too many small files and compacts them automaticallyMicrosoft's recommended hands-off default for most tables
OPTIMIZERewrites small files into large ones on demandScheduled maintenance, after big loads; needed to apply clustering
V-OrderFabric-specific sorting and encoding inside Parquet files; much faster reads, slower writesTables read by Power BI Direct Lake and SQL; not for write-heavy Bronze
PartitioningSeparate folders per value (e.g. Year)Very large tables with a low-cardinality filter column (Module 4)
Z-OrderCo-locates similar values inside files during OPTIMIZEOlder approach; filter columns with high cardinality
Liquid clusteringDeclares clustering columns on the table; OPTIMIZE keeps data grouped by them; columns can be changed laterModern replacement for partitioning + Z-Order on large tables
VACUUMDeletes files no longer referenced (old versions)Regularly, respecting time-travel needs (default retention 7 days)
-- Spark SQL in a notebook
-- Table-level settings
ALTER TABLE gold.FactSales SET TBLPROPERTIES (
    'delta.autoOptimize.optimizeWrite' = 'true',
    'delta.autoOptimize.autoCompact'   = 'true',
    'delta.parquet.vorder.enabled'     = 'true'
);

-- Liquid clustering (instead of PARTITIONED BY)
CREATE TABLE gold.FactSales_LC
CLUSTER BY (OrderDate, StoreKey)
AS SELECT * FROM gold.FactSales;

OPTIMIZE gold.FactSales_LC;              -- clustering is applied when OPTIMIZE runs

-- Classic alternatives
OPTIMIZE gold.FactSales ZORDER BY (CustomerKey);
OPTIMIZE gold.FactSales VORDER;
VACUUM  gold.FactSales RETAIN 168 HOURS;
Liquid clustering only reorganises data when OPTIMIZE runs — normal writes don't cluster. On Fabric Runtime 1.3, don't combine liquid clustering with auto compaction (it can trigger full rewrites); newer runtimes add incremental clustering. Check your runtime's documentation before choosing.

Fabric Spark offers predefined resource profiles that set these options together. New workspaces default to writeHeavy, which turns V-Order off for faster ingestion:

Checking a Table's Health

from delta.tables import DeltaTable

def table_health(name):
    d = DeltaTable.forName(spark, name).detail().collect()[0]
    files, size = d["numFiles"], d["sizeInBytes"]
    avg_mb = size / max(files, 1) / 1024**2
    return {"table": name, "files": files,
            "size_gb": round(size / 1024**3, 2),
            "avg_file_mb": round(avg_mb, 1),
            "partitions": d["partitionColumns"],
            "needs_optimize": files > 50 and avg_mb < 64}

for t in ["silver.orders", "gold.FactSales", "gold.DimCustomer"]:
    print(table_health(t))

Run it weekly across your Gold tables (or log the results to a table) and you'll catch fragmentation before users notice.

Hands-On Lab

  1. Write a table with 200 small appends; run table_health. Note the file count.
  2. Run OPTIMIZE; check again. Then turn on auto compaction and repeat the 200 appends.
  3. Create a liquid-clustered copy on OrderDate; compare a date-filtered query's files read (Spark UI → SQL tab).
  4. Check your workspace's resource profile; set readHeavyForPBI for the Gold notebook.
Delta layout affects every Fabric engine. Optimize write reduces files at write time, auto compaction compacts after writes (Microsoft's recommended default), and OPTIMIZE compacts on demand and applies clustering. V-Order speeds up reads for SQL and Direct Lake at some write cost. Large tables are organised with partitioning for low-cardinality filters, Z-Order, or the newer liquid clustering, whose columns can change without rewriting and which is applied when OPTIMIZE runs. Target file sizes depend on the consumer — around 128–256 MB for Spark ETL and larger for SQL and Direct Lake. Resource profiles bundle these settings; new workspaces default to writeHeavy with V-Order off, so Gold tables should use readHeavyForPBI or explicit V-Order. Table health is checked with DeltaTable detail.

Spark Compute Settings

Before changing code, check the compute it runs on. Fabric offers several free or cheap wins: faster session start, a native execution engine that speeds up most Spark SQL and DataFrame code with no code changes, right-sized pools, and session sharing across notebooks.

Pools and Sessions

OptionWhat it isUse it for
Starter poolPre-warmed Medium nodes; sessions start in secondsMost notebooks; interactive work
Custom poolYour node size (Small → XX-Large), node count, autoscale; starts in a few minutesHeavy jobs that need more memory per node, or a fixed size
Autoscale / dynamic allocationAdds and removes nodes/executors with demandJobs with a heavy stage and light stages
High concurrencySeveral notebooks share one sessionPipelines running many notebooks; multiple notebooks open at once
EnvironmentSaved runtime version, libraries, Spark properties and pool, attached to notebooksConsistent settings across a project
Many pipeline "performance problems" are really session start-up: 20 notebooks each starting their own session. Enable high concurrency for pipelines (workspace Spark settings) and use session tags so notebooks reuse sessions.

Native Execution Engine

A vectorised C++ engine (built on Apache Gluten and Velox) that runs Spark operations directly on Parquet/Delta in columnar form. Your code doesn't change; supported operations simply run faster, and unsupported ones fall back to normal Spark automatically. It's generally available on Fabric Runtime 1.3 at no extra cost.

# Per notebook — first cell
%%configure
{
  "conf": { "spark.native.enabled": "true" }
}

Or enable it once for everyone: Environment → Acceleration → Enable native execution engine. Check the Spark UI afterwards — operators running natively appear with "Native"/"Velox" names; a lot of fallbacks means some functions (often Python UDFs) aren't supported.

Sizing

Spark Settings Worth Knowing

spark.conf.get("spark.sql.adaptive.enabled")                 # AQE — on by default; leave it on
spark.conf.set("spark.sql.shuffle.partitions", "400")         # default 200; AQE coalesces small ones
spark.conf.set("spark.sql.autoBroadcastJoinThreshold", 50 * 1024 * 1024)  # broadcast tables up to 50 MB
spark.conf.set("spark.fabric.resourceProfile", "writeHeavy")  # 10.2

Hands-On Lab

  1. Run your baseline notebook on the starter pool; note duration and session start time.
  2. Enable the native execution engine with %%configure; run again and compare.
  3. Create an Environment with native engine on and attach it to the project's notebooks.
  4. Enable high concurrency for pipelines and run a pipeline with several notebooks; compare total time.
Fabric Spark compute options include starter pools for near-instant sessions, custom pools with chosen node size and autoscale, dynamic allocation, high concurrency mode so notebooks share a session, and Environments that standardise runtime, libraries and settings. The Native Execution Engine, a vectorised C++ engine based on Gluten and Velox, accelerates Spark SQL and DataFrame operations on Parquet and Delta with no code changes and falls back automatically for unsupported operations; it is enabled per session with %%configure or in an Environment. Sizing follows the symptom: memory errors often indicate skew or driver-side collection rather than too few nodes, and adaptive query execution should stay on.
10.4

Spark Code Optimization

Most slow Spark jobs are slow for one of five reasons: they read more than they need, they shuffle too much, a join is done the expensive way, one partition is much bigger than the rest (skew), or work is pulled into Python. This lesson shows how to spot each one in the execution plan and fix it.

Reading the Plan

Spark builds a plan before running anything (Module 4.2). explain() shows it — learn to spot four words:

df = (spark.table("silver.orders")
        .filter("order_date >= '2026-01-01'")
        .join(spark.table("silver.customers"), "customer_id")
        .groupBy("region").sum("amount"))
df.explain(mode="formatted")
In the planMeansGood or bad?
PushedFilters: [GreaterThanOrEqual(order_date,…)]Filter applied while reading files✔ Good — less data read
ReadSchema: struct<customer_id, amount, …>Only these columns read✔ Good if short
Exchange hashpartitioning(…)A shuffle — data moved across the network⚠ Expensive; minimise
BroadcastHashJoinSmall table copied to every executor; no shuffle of the big one✔ Good for small dimensions
SortMergeJoinBoth sides shuffled and sortedOK for two big tables; bad if one is small

Fix 1 — Read Less

# ✗ reads every column of every row, filters late
df = spark.table("silver.orders").toPandas()
df = df[df.order_date >= "2026-01-01"]

# ✓ filter and select first; Spark pushes both into the file scan
df = (spark.table("silver.orders")
        .filter(F.col("order_date") >= "2026-01-01")
        .select("order_id", "customer_id", "order_date", "amount"))

Filters on clustered or partitioned columns also let Delta skip whole files using min/max statistics. Filters wrapped in functions on the column (e.g. year(order_date) == 2026) may not skip as well as a plain range filter.

Fix 2 — Broadcast Small Dimensions

from pyspark.sql import functions as F

fact = spark.table("silver.orders")          # 2 billion rows
dim  = spark.table("gold.DimStore")          # 900 rows

joined = fact.join(F.broadcast(dim), "store_id", "left")

Spark broadcasts automatically below spark.sql.autoBroadcastJoinThreshold (10 MB by default) and AQE can switch to broadcast at run time, but an explicit broadcast() guarantees it for dimensions you know are small. Never broadcast something large — it's copied to every executor.

Fix 3 — Shuffle Less

Causes a shuffleCheaper alternative
groupBy, join, distinct, orderBy, window functions, repartitionNecessary often — but filter and project before them
orderBy on the full result just before writingDrop it; Delta doesn't keep row order anyway (use clustering)
distinct() after a join "to be safe"Fix the join key so it doesn't duplicate
repartition(n) to reduce filescoalesce(n) (no shuffle) or optimize write
Several aggregations on the same dataOne groupBy().agg(…) with all of them

Fix 4 — Handle Skew

Skew: one key has far more rows than the others (a "walk-in customer" ID, a NULL key, one huge store). One task gets most of the data, and the whole stage waits for it.

Spark UI → stage → task durations
Diagnosis
199 tasks: 4–6 s · 1 task: 14 min
──►
Skew on the join/group key
  1. Find the key: df.groupBy("customer_id").count().orderBy(F.desc("count")).show(5)
  2. Handle NULLs separately — often the "skewed key" is NULL; filter those rows out of the join and union them back.
  3. Let AQE split it: spark.sql.adaptive.skewJoin.enabled is on by default and splits oversized partitions in sort-merge joins.
  4. Salt the key when AQE isn't enough (e.g. skewed aggregations):
# Two-step aggregation with a salt: spread the hot key over 16 tasks, then combine
SALT = 16
partial = (orders
           .withColumn("salt", (F.rand() * SALT).cast("int"))
           .groupBy("customer_id", "salt")
           .agg(F.sum("amount").alias("amt"), F.count("*").alias("cnt")))
result  = (partial.groupBy("customer_id")
           .agg(F.sum("amt").alias("total_amount"), F.sum("cnt").alias("orders")))

Fix 5 — Keep Work in Spark

SlowFastWhy
Python UDF: @udf def clean(s): return s.strip().upper()F.upper(F.trim("name"))Built-ins run in the JVM / native engine; UDFs move every row to Python and back
Row-by-row logic in a UDFF.when(), F.regexp_replace(), F.expr()Same
Unavoidable custom Python@pandas_udf (vectorised)Processes batches with Arrow — much faster than plain UDFs
df.collect(), df.toPandas() on big dataWrite to a table; limit() before collectingEverything lands on the driver
df.count() after every step "to check"Count once at the end, or log from Delta historyEach action re-runs the whole plan

Caching — Sometimes

customers = spark.table("silver.customers").filter("is_active = true").cache()
customers.count()                          # materialise the cache once
# … used by three later joins …
customers.unpersist()                      # free memory when done

Cache only a DataFrame that is (a) expensive to compute and (b) reused several times. Caching something used once just costs memory.

Hands-On Lab

  1. Run explain("formatted") on a join query; find PushedFilters, Exchange and the join type.
  2. Add F.broadcast() to the dimension; compare the plan and duration.
  3. Create a skewed dataset (90% of rows with one key). Compare a plain groupBy with the salted two-step version in the Spark UI task timeline.
  4. Replace a Python UDF with built-in functions; compare duration.
Spark code is optimised by reading the execution plan: pushed filters and narrow read schemas are good, while Exchange operators indicate shuffles, and SortMergeJoin with a small table indicates a missed broadcast. The main fixes are reading less by filtering and selecting early to enable predicate pushdown and file skipping; broadcasting small dimensions; avoiding unnecessary shuffles such as orderBy before writing, defensive distinct and repartition; handling skew by isolating NULL keys, relying on AQE skew-join handling or salting keys; keeping work in built-in functions rather than Python UDFs, using pandas UDFs when Python is unavoidable; avoiding collect, toPandas and repeated actions; and caching only expensive, reused DataFrames.
10.5

Query Performance: SQL, Direct Lake, KQL

Users don't see your Spark jobs — they see reports and queries. This lesson covers what makes queries fast in each serving engine: the SQL analytics endpoint and Warehouse, Power BI Direct Lake, and Eventhouse KQL, with special attention to Direct Lake guardrails, which catch many teams out.

SQL Analytics Endpoint & Warehouse

Module 6.8 covered Warehouse tuning in depth. The checklist:

  • Right data types (no oversized varchar; date not string; integer keys)
  • Sargable filters — WHERE OrderDate >= '2026-01-01', not WHERE YEAR(OrderDate) = 2026
  • Star schema with integer surrogate keys; select only needed columns
  • Statistics up to date on join/filter columns; result-set caching for repeated queries
  • For Lakehouse tables read through the SQL endpoint: good Delta layout and V-Order (10.2)
  • Find slow queries in queryinsights.long_running_queries and exec_requests_history

Power BI Direct Lake

Direct Lake loads columns straight from Delta/Parquet into memory when a report needs them (Module 2). Speed depends on the table layout and on staying within the capacity's guardrails:

Guardrail (per table)F64 exampleExceeded because…
Parquet files5,000Many small writes, over-partitioning, no compaction
Row groups5,000Small files / small row groups
Rows1.5 billionVery detailed fact table
Model size in memorySKU-dependentToo many / too wide columns loaded

Limits vary by SKU and change over time — check the current Direct Lake guardrails table for your capacity.

Direct Lake on SQL endpoint

If a guardrail is exceeded, or the table is a SQL view, or SQL RLS applies, queries fall back to DirectQuery through the SQL endpoint — they still work but are much slower. Fallback behaviour can be set to Automatic, Direct Lake only, or DirectQuery only.

Direct Lake on OneLake

No DirectQuery fallback: if a table exceeds the guardrails, framing fails and the table can't be queried until it's back within limits. Layout maintenance is not optional here.

Direct Lake checklist

  • Gold tables compacted, V-Order on, large files and row groups (readHeavyForPBI profile)
  • Only columns the reports need — drop unused text columns, especially high-cardinality ones (GUIDs, free text, timestamps to the second)
  • Split date and time; round timestamps; avoid unique IDs in the model unless needed for drill-through
  • Pre-aggregated tables for very large facts (e.g. daily by store), with the detail table only for drill-through
  • Base tables on Delta tables, not SQL views (views force fallback in Direct Lake on SQL)
  • Coordinate VACUUM with framing — removing files a frame still references breaks queries until the model reframes

Use Performance Analyzer in Power BI Desktop (or DAX Studio) to see whether time goes to the DAX query or the visual, and check the semantic model's refresh/framing history.

Eventhouse KQL (Recap from 8.6)

  • Filter on time first; keep dashboard windows inside the hot cache
  • has instead of contains; project early
  • Materialized views for dashboard aggregates; update policies instead of query-time parsing

Which Engine Should Serve the Query?

Interactive BI on a star schemaDirect Lake semantic model

Hands-On Lab

  1. Check file and row-group counts of your Gold fact table against your SKU's Direct Lake guardrails.
  2. Run Performance Analyzer on a slow report page; identify the slowest visual and its DAX query.
  3. Remove two unused high-cardinality columns from the model; compare memory size and query time.
  4. Query queryinsights.long_running_queries for the top 5 slow SQL queries this week.
Query performance depends on the serving engine. For the SQL endpoint and Warehouse it comes from correct data types, sargable filters, star schemas, statistics, result-set caching and good Delta layout, with slow queries found in queryinsights views. Direct Lake reads Delta columns into memory and is bounded by per-SKU guardrails on Parquet files, row groups, rows and memory; Direct Lake on SQL falls back to DirectQuery when they're exceeded or when views or SQL RLS are used, while Direct Lake on OneLake has no fallback and fails instead. Gold tables should be compacted with V-Order, models should contain only needed, low-cardinality columns, large facts may need aggregate tables, and VACUUM must be coordinated with framing. KQL queries rely on time filters, hot cache and materialized views.

Monitoring & Troubleshooting

You can't fix what you can't see. Fabric has a monitoring tool for every level — the whole capacity, a single run, a single Spark stage, a single query. This lesson shows which tool answers which question, and a step-by-step routine for "it's slow" tickets.

Capacity Metrics App: What to Look For

  • CU % over time above 100% for long periods → you're borrowing from the future (bursting)
  • Throttling charts: interactive delay or rejection → users are affected now
  • Top items by CU — the 20% of items using 80% of capacity are your optimisation targets
  • Background vs interactive — a night-time ETL spike smoothed over 24 hours can still eat daytime headroom

SQL: Find the Expensive Queries

-- Slowest query shapes in the last 7 days
SELECT TOP 10
    last_run_command,
    number_of_runs,
    median_total_elapsed_time_ms,
    last_run_total_elapsed_time_ms
FROM queryinsights.long_running_queries
ORDER BY median_total_elapsed_time_ms DESC;

The "It's Slow" Routine

  1. What changed? Data volume, code, schedule, capacity load? Compare with a good run (run history, Delta DESCRIBE HISTORY).
  2. Is the capacity throttled? If yes, everything is slow — look for the noisy neighbour in Capacity Metrics.
  3. Which step? Pipeline Gantt → notebook → Spark stage → operator. Narrow down until one thing explains most of the time.
  4. Why? Match the symptom: many small files, skew, shuffle, fallback, missing statistics, UDF.
  5. Fix one thing, re-measure, and record the before/after in the ticket.

Build Your Own Performance Log

# At the end of every notebook, log one row — then chart it in Power BI
import time
from datetime import datetime, timezone

log = spark.createDataFrame([(
    notebook_name, run_id, datetime.now(timezone.utc),
    round(time.time() - start_time, 1), rows_in, rows_out
)], "notebook string, run_id string, logged_at timestamp, seconds double, rows_in long, rows_out long")
log.write.mode("append").saveAsTable("ops.notebook_perf_log")

A simple trend line of seconds and rows per run catches gradual slowdowns (growing data, fragmenting tables) months before they become incidents.

Hands-On Lab

  1. In Capacity Metrics, find the busiest hour of the last week and the items responsible.
  2. Open a slow notebook run's Spark UI; identify the slowest stage, its shuffle size and the max/median task time.
  3. Add the performance-log cell to two notebooks and build a small trend chart.
Fabric monitoring works at several levels: the Capacity Metrics app shows CU usage, bursting, throttling and top items; the Monitoring hub shows runs across items; pipeline run details show per-activity durations and outputs; the Spark UI and application monitoring reveal slow stages, skew, shuffle and spill; run series analysis compares runs over time; queryinsights views list slow and frequent SQL queries; Performance Analyzer and DAX Studio analyse reports; and workspace monitoring stores logs in an Eventhouse for KQL analysis. Troubleshooting follows a routine — what changed, is the capacity throttled, which step, why — fixing one cause at a time and measuring, supported by a custom performance log to catch gradual slowdowns.

Optimize a Large Dataset: Case Study

This lesson applies the whole module to one realistic problem: a retail sales platform whose fact table has grown to 2 billion rows. The nightly load now takes over three hours, reports have become slow, and the capacity is throttling in the mornings. We'll diagnose it step by step and fix it, measuring each change.

The Situation

📥
Load
Every night, a notebook re-reads all of silver.orders (2.0 bn rows, 5 years), joins 4 dimensions, and overwrites gold.FactSales.
🗂️
Storage
gold.FactSales partitioned by OrderDate (1,800 daily folders), 41,000 files, average 6 MB; V-Order off (workspace created with writeHeavy default).
📊
Reports
Direct Lake model on the SQL endpoint, 38 columns including OrderId (GUID) and OrderTimestamp; pages take 20–40 s.
⚡
Capacity
F64; Capacity Metrics shows the nightly notebook as the top consumer and interactive delays 08:00–10:00.

Step 1 — Measure the Baseline

Step 3 — Fix: Process Only What Changed

from pyspark.sql import functions as F
from delta.tables import DeltaTable

# 1. Read only orders modified since the last successful run (watermark, Module 3/7)
changes = (spark.table("silver.orders")
           .filter(F.col("modified_at") > F.lit(last_watermark))
           .select("order_id", "order_date", "customer_id", "store_id",
                   "product_id", "quantity", "amount", "modified_at"))

# 2. Find the date range touched, to let MERGE skip untouched files
lo, hi = changes.agg(F.min("order_date"), F.max("order_date")).first()

# 3. Upsert into the fact; the date condition prunes the target scan
fact = DeltaTable.forName(spark, "gold.FactSales")
(fact.alias("t")
     .merge(staged.alias("s"),                       # staged = changes + surrogate keys (step 4)
            f"t.OrderId = s.OrderId AND t.OrderDate BETWEEN '{lo}' AND '{hi}'")
     .whenMatchedUpdateAll()
     .whenNotMatchedInsertAll()
     .execute())
The extra t.OrderDate BETWEEN … condition is safe because an order's date never changes, and it lets Delta skip every file outside the changed dates. Without it, MERGE scans all 2 billion rows to look for matches. For loads that replace whole days, .option("replaceWhere", "OrderDate >= '…' AND OrderDate < '…'") with overwrite mode is even simpler.

Step 4 — Fix: Joins and Skew

dim_store    = spark.table("gold.DimStore").select("StoreKey", "store_id")
dim_product  = spark.table("gold.DimProduct").select("ProductKey", "product_id")
dim_customer = (spark.table("gold.DimCustomer")
                .filter("IsCurrent = true").select("CustomerKey", "customer_id"))

# Walk-in orders (NULL customer) skip the customer join entirely → no hot key
known   = changes.filter(F.col("customer_id").isNotNull())
walk_in = (changes.filter(F.col("customer_id").isNull())
                  .withColumn("CustomerKey", F.lit(-1).cast("long")))   # Unknown member

known = (known.join(dim_customer, "customer_id", "left")
              .withColumn("CustomerKey", F.coalesce("CustomerKey", F.lit(-1).cast("long"))))

staged = (known.unionByName(walk_in)
          .join(F.broadcast(dim_store),   "store_id",   "left")
          .join(F.broadcast(dim_product), "product_id", "left")
          .select(F.col("order_id").alias("OrderId"), F.col("order_date").alias("OrderDate"),
                  "CustomerKey", F.coalesce("StoreKey", F.lit(-1)).alias("StoreKey"),
                  F.coalesce("ProductKey", F.lit(-1)).alias("ProductKey"),
                  F.col("quantity").alias("Quantity"), F.col("amount").alias("Amount")))

The Large-Dataset Playbook

  1. Never reprocess history you don't need to: watermarks, MERGE with pruning predicates, replaceWhere.
  2. Keep files large and few: optimize write, auto compaction or scheduled OPTIMIZE.
  3. Organise for the common filter: liquid clustering (or partitioning only for very large, low-cardinality cases).
  4. V-Order for anything Power BI or SQL reads.
  5. Broadcast small dimensions; isolate skewed keys.
  6. Serve summaries to dashboards; detail only on demand.
  7. Measure before and after, and keep monitoring.
Optimising a large dataset starts with a measured baseline, then finding the real bottlenecks — typically full reloads of unchanged history, skewed or shuffled joins, fragmented tables and bloated semantic models. The fixes are incremental processing with watermarks and MERGE conditions that prune target files (or replaceWhere), separating NULL or hot keys and broadcasting small dimensions, rebuilding the table with liquid clustering, V-Order and compaction so it stays within Direct Lake guardrails, slimming the model and adding aggregate tables, and enabling the native engine and session sharing. Each change is verified against the baseline, and data-quality checks confirm the faster pipeline still produces correct results.
