The Medallion Architecture organises a Lakehouse into three layers of Delta tables. Bronze stores source data as received plus audit metadata, so it can be audited and reprocessed. 5.2

Building the Bronze Layer

Bronze is the easiest layer to build and the easiest to get wrong. The temptation is to "just clean it a bit" on the way in — but every change you make in Bronze destroys evidence you'll need later. This lesson covers what Bronze should contain, the audit columns that make it useful, and the one control every Bronze load needs: protection against loading the same data twice.

The Rule: Preserve, Don't Fix

✅ Allowed in Bronze

  • Add technical (audit) columns
  • Make column names Delta-safe (spaces → underscores)
  • Read with a schema — or land everything as string
  • Reject files that can't be read at all

❌ Not in Bronze

  • Trimming, upper-casing, fixing values
  • Removing duplicates or "bad" rows
  • Joins or business rules
  • Aggregations

If the source sends " John ", Bronze keeps " John ". Silver trims it. Then, when someone asks "was the space in the source or did we add it?", Bronze has the answer.

A common production choice is to land every column as string in Bronze. A source that suddenly sends "N/A" in a numeric column then lands safely instead of failing the ingestion — and Silver's casting rules decide what to do with it.

Append — and the Duplicate-Batch Trap

Bronze usually appends: each day's file is added, building a full history. But append has a trap:

A pipeline retry, a manual re-run, or a scheduling overlap doubles the data — and every downstream total doubles with it. A production Bronze load must be idempotent: running it twice gives the same result as running it once.

Cell 2 — Load new files onlyPySpark
from pyspark.sql.functions import lit, current_timestamp, col

# Create the load log once
spark.sql("""
  CREATE TABLE IF NOT EXISTS Bronze_LoadLog
  (SourceFile STRING, TargetTable STRING, BatchID STRING, RowCount BIGINT,
   Status STRING, LoadTimestamp TIMESTAMP) USING DELTA
""")

loaded = {r.SourceFile for r in spark.table("Bronze_LoadLog")
                                  .filter((col("TargetTable") == target_table) & (col("Status") == "SUCCESS"))
                                  .select("SourceFile").collect()}

new_files = [f for f in notebookutils.fs.ls(source_folder)
             if f.name.endswith(".csv") and f.name not in loaded]
print(f"{len(new_files)} new file(s); {len(loaded)} already loaded")

for f in new_files:
    df = (spark.read.option("header", "true").csv(f.path)       # no inferSchema: keep everything as string
            .withColumn("SourceSystem", lit(source_system))
            .withColumn("SourceFile", lit(f.name))
            .withColumn("BatchID", lit(batch_id))
            .withColumn("LoadTimestamp", current_timestamp()))

    rows = df.count()
    df.write.format("delta").mode("append").option("mergeSchema", "true").saveAsTable(target_table)

    spark.createDataFrame(
        [(f.name, target_table, batch_id, rows, "SUCCESS")],
        "SourceFile STRING, TargetTable STRING, BatchID STRING, RowCount BIGINT, Status STRING"
    ).withColumn("LoadTimestamp", current_timestamp()) \
     .write.format("delta").mode("append").saveAsTable("Bronze_LoadLog")
    print(f"✔ {f.name}: {rows:,} rows")

Note mergeSchema here is a deliberate exception to Module 4's warning: Bronze's job is to accept what arrives, so a new source column is added rather than rejected. Silver then decides whether to use it.

Hands-On Lab

  1. Put two CSV files in Files/Raw/Sales. Run the notebook — both load; the log has two rows.
  2. Run it again. "0 new files" — Bronze count unchanged. That's idempotency.

Bronze is the landing and preservation layer. It stores source data with minimal change — often all columns as string — plus audit metadata: SourceSystem, SourceFile, BatchID and LoadTimestamp. No cleansing or business logic happens there, so the raw data can be audited and reprocessed when rules change. Bronze is usually append-only, which makes idempotency essential: track loaded files or batches in a load log (or overwrite by partition) so a re-run doesn't duplicate data. Bronze also needs a retention policy and restricted access.

Money is DECIMAL, not DOUBLE. 0.1 + 0.2 in a double is 0.30000000000000004; across millions of rows, totals drift by paise. Cast financial columns to DecimalType(18, 2) in Silver and every layer above inherits exact arithmetic.

from pyspark.sql.functions import coalesce, upper, trim

        .withColumn("Country", coalesce(col("StdCountry"), upper(trim(col("Country")))))

A new spelling now means inserting a row, not editing and redeploying code. Business users can even maintain the table themselves.

2. Deduplicate — Latest Row per Key

Bronze keeps every version of a record. If customer 101 changed city twice this week, Bronze has three rows. Silver wants the latest one — dropDuplicates would keep an arbitrary one:

from pyspark.sql.window import Window
from pyspark.sql.functions import row_number, col

latest = Window.partitionBy("CustomerID").orderBy(col("UpdatedDate").desc(), col("LoadTimestamp").desc())
df = df.withColumn("rn", row_number().over(latest)).filter("rn = 1").drop("rn")

The second sort column is a tie-breaker: if two rows share the same UpdatedDate, the most recently loaded wins. Always add one — otherwise the "latest" row can differ between runs.

3. Validate — Rules, Reasons and Quarantine

Module 4.6 split data into valid and invalid with one boolean. In a real Silver layer you need to know which rule failed and why, so the source team can fix it.

Define rules in one place

Rules as dataPySpark
from pyspark.sql.functions import col, current_date

rules = {
    "NULL_SALE_ID":      col("SaleID").isNull(),
    "NULL_CUSTOMER_ID":  col("CustomerID").isNull(),
    "NEGATIVE_AMOUNT":   col("Amount") < 0,
    "INVALID_QUANTITY":  (col("Quantity") <= 0) | col("Quantity").isNull(),
    "INVALID_DATE":      col("OrderDate").isNull(),
    "FUTURE_DATE":       col("OrderDate") > current_date(),
}

These rules should come from the business ("Can an order have quantity 0?"), not from guesses. Write them down with the owner's name.

Label every row with the rules it fails

from pyspark.sql.functions import when, lit, concat_ws, array, array_compact, size, explode, desc

df = df.withColumn("FailedRules",
        array_compact(array(*[when(cond, lit(name)) for name, cond in rules.items()])))
df = df.withColumn("DQ_Status", when(size(col("FailedRules")) == 0, "VALID").otherwise("INVALID"))
df = df.withColumn("FailureReason", concat_ws(", ", col("FailedRules")))

5. MERGE into Silver

Silver reflects the current trusted state, so it is maintained with MERGE (Module 4.9): changed rows update, new rows insert, re-runs are safe.

from delta.tables import DeltaTable

valid = df.filter("DQ_Status = 'VALID'").drop("FailedRules", "DQ_Status", "FailureReason") \
          .withColumn("SilverLoadTimestamp", current_timestamp())

if spark.catalog.tableExists("Silver_Sales"):
    (DeltaTable.forName(spark, "Silver_Sales").alias("t")
        .merge(valid.alias("s"), "t.SaleID = s.SaleID")
        .whenMatchedUpdateAll()
        .whenNotMatchedInsertAll()
        .execute())
else:
    valid.write.format("delta").saveAsTable("Silver_Sales")

Silver dimensions such as customers normally hold the latest value only (SCD Type 1). If history matters, it is built in Gold from Silver — Lesson 5.8.

Silver turns Bronze into trusted data. It casts types (DECIMAL for money), standardises text and codes — preferably via reference tables — keeps the latest row per business key using ROW_NUMBER with a tie-breaker, and validates against business-defined rules. Silver also conforms the same entity from different source systems into one standard schema. Valid rows are MERGEd so Silver always reflects the current trusted state and re-runs are idempotent.

Joins for Data Integration

You learned join syntax in Module 4.3. This lesson is about the part that actually goes wrong in production: joins that silently multiply rows and inflate every total, joins that silently drop rows, and joins that crawl. You'll learn to predict a join's result before you run it — and to prove it afterwards.

Know the Cardinality Before You Join

Cardinality is how many rows on each side share a key. Decide what it should be, then check it is:

Prove it: three checks around every enrichment join

Join validationPySpark
from pyspark.sql.functions import col

# 1. BEFORE: the lookup key must be unique
dup_keys = customers.groupBy("CustomerID").count().filter(col("count") > 1)
assert dup_keys.count() == 0, "Customers has duplicate CustomerIDs — dedupe before joining"

# 2. JOIN (left, so no order is lost)
before = orders.count()
enriched = orders.join(customers, "CustomerID", "left")

# 3. AFTER: row count must not change for a many-to-one enrichment
after = enriched.count()
assert before == after, f"Join changed row count {before} → {after}: fan-out!"

# 4. How many failed to match?
unmatched = enriched.filter(col("City").isNull() & col("CustomerID").isNotNull()).count()
print(f"{unmatched} orders have no matching customer")

Four lines of checking turns a silent bug into a failed run with a clear message. Do it on every Gold join.

Join Keys: Watch Out For…

1
NULL keys never match
NULL = NULL is not true in SQL or Spark. Orders with a NULL CustomerID won't join to anything — even a customer row with a NULL ID. Catch NULL keys in Silver validation. (If you truly need NULLs to match, use the null-safe operator eqNullSafe / <=>.)
2
Type and format mismatches
"101" (string) vs 101 (int), "0101" vs "101", "IN " vs "IN". Conform keys in Silver — same type, trimmed, same padding.
3
Composite keys
If uniqueness needs two columns, join on both: orders.join(prices, ["ProductID", "PriceDate"], "left"). Joining on one creates a fan-out.
4
Ambiguous columns
Both sides have CustomerID? Join on the column name ("CustomerID") and Spark keeps one copy. Joining on an expression keeps two — then select("CustomerID") fails as ambiguous. Use aliases: orders.alias("o").join(customers.alias("c"), col("o.CustomerID") == col("c.CustomerID")).

Orphans and Reconciliation

Orphans: facts with no dimension

orphans = orders.join(customers, "CustomerID", "left_anti")    # orders whose customer doesn't exist
display(orphans)

Orphans usually mean the dimension load is behind the fact load (a "late-arriving dimension") or the source has a referential-integrity bug. Report them; don't silently drop them.

Reconciliation: do two systems agree?

Comparing the CRM's customer list with the billing system's? A full outer join classifies every key in one pass:

recon = (crm.alias("a").join(billing.alias("b"), "CustomerID", "full")
           .withColumn("Status",
              when(col("a.Name").isNull(), "ONLY_IN_BILLING")
              .when(col("b.Name").isNull(), "ONLY_IN_CRM")
              .when(col("a.Name") != col("b.Name"), "MISMATCH")

Range (Non-Equi) Joins

Not every join is on equality. Assigning a segment band by amount, or a price that was valid on the order date:

# Segments: Bronze 0–9,999 · Silver 10,000–49,999 · Gold 50,000+
seg = spark.createDataFrame([("Bronze", 0, 9999), ("Silver", 10000, 49999), ("Gold", 50000, 10**12)],
                            ["Segment", "MinRev", "MaxRev"])

customers_seg = customer_revenue.join(
    seg,
    (customer_revenue.Revenue >= seg.MinRev) & (customer_revenue.Revenue <= seg.MaxRev),
    "left")

Range joins are also how a fact finds the right historical version of a Type 2 dimension — Lesson 5.8. Make sure ranges don't overlap, or you're back to row explosion.

Join Performance

Shuffle (sort-merge) join

Both sides are shuffled so matching keys meet on the same executor. Needed when both tables are large. Expensive.

Broadcast join

The small table is copied to every executor; the big table never moves. Much faster. Spark does this automatically for small tables (default threshold ~10 MB); you can force it:

from pyspark.sql.functions import broadcast
fact.join(broadcast(dim_country), "CountryCode", "left")
  • Filter and select before joining — fewer rows and columns to shuffle
  • Broadcast genuinely small tables — dimensions, reference tables (not a 50 GB "dimension")
  • Watch for skew — one key with millions of rows (e.g. CustomerID = -1 "Unknown") makes one task run for ages
  • Check the plan — enriched.explain() shows BroadcastHashJoin or SortMergeJoin

Joins combine datasets on keys, and the main production risks are row explosion and silent data loss. If the lookup side has duplicate keys, a join multiplies fact rows and inflates every total, so you check key uniqueness before joining and row count after (it must not change for a many-to-one enrichment). Inner joins drop facts without a dimension, so enrichment uses left joins and handles misses explicitly; left_anti finds orphans and a full outer join reconciles two systems. NULL keys never match. Range joins handle bands and effective dates. For performance, filter first and broadcast small tables to avoid a shuffle.

Window Functions for Transformation

Module 4.4 introduced window functions in SQL. In transformation work they are everywhere: picking the latest record, ranking products, detecting changes between versions, running totals, moving averages and percentage-of-total. This lesson covers the PySpark API and the six patterns you will use most.

Window vs GroupBy

groupBy — rows collapse

CustomerID | Total
101        | 6000

One row per group. Detail is gone.

window — rows stay

CustomerID | OrderID | Amount | Total
101        | 5001    | 2000   | 6000

Anatomy of a Window

from pyspark.sql.window import Window

w = (Window
       .partitionBy("CustomerID")        # 1. which rows form a group
       .orderBy("OrderDate")             # 2. their order inside the group
       .rowsBetween(Window.unboundedPreceding, Window.currentRow))   # 3. (optional) the frame: which rows to include

df.withColumn("RunningTotal", sum("Amount").over(w))

  .withColumn("CountryRevenue", sum("Revenue").over(w))

No orderBy, no frame — the whole partition. Each product's share of its country's revenue, without a separate groupBy and join.

Performance

  • Always partitionBy on large data — a window without it runs on one task
  • Filter and select columns before the window
  • Several windows with the same partition/order spec share one shuffle — reuse the w variable
  • Beware skewed partitions — one customer with 10 M rows makes one slow task

A window function calculates over a group of related rows while keeping every row, unlike groupBy which collapses them. A window is defined by partitionBy (the group), orderBy (the sequence) and an optional frame (rowsBetween). Core patterns: row_number for latest-record de-duplication; rank vs dense_rank vs row_number for ties and top-N per group; lag / lead to compare with previous or next rows (change detection, gaps, SCD end dates); sum over an unbounded-preceding frame for running totals; a fixed frame for moving averages; and an unordered window for share-of-total. Always partition large data, or Spark processes the window in a single task.

Aggregations & Grain

Aggregation syntax is simple: groupBy().agg(). Getting the right number is not. This lesson is built around one idea — grain, what one row represents — because almost every wrong total on a dashboard comes from aggregating at the wrong grain, counting the wrong thing, or dividing averages that shouldn't be divided.

Grain: Define It Before You Write Code

The grain of a table is a sentence: "one row per ___". Write it at the top of every Gold notebook.

TableGraingroupBy
Silver_OrderLinesOne row per order line— (detail)
FactSalesOne row per order line— (detail)
Gold_DailySalesOne row per date"OrderDate"
Gold_MonthlySalesOne row per year + month + country"Year", "Month", "Country"
Gold_CustomerRevenueOne row per customer"CustomerID"

The groupBy columns are the grain. Add a column by accident and the grain changes:

✅ Intended

.groupBy("Year", "Month", "Country")
→ 12 months × 3 countries = 36 rows

❌ Accidental extra column

.groupBy("Year", "Month", "Country", "CustomerID")
→ 36 × 50,000 customers = 1.8 M rows

Power BI now shows a "Revenue" that has to be re-summed, and "Average Order Value" is meaningless.

The Functions

  .withColumn("Year", year("OrderDate")).withColumn("Month", month("OrderDate"))

Ratios: Calculate After Aggregating

Never average a ratio column, and never sum one. Aggregate the parts, then divide:

❌ Average of margins

Order A: revenue 100,   profit 50  → 50%
Order B: revenue 10,000, profit 1,000 → 10%
avg(margin) = 30%     ← wrong

✅ Margin of totals

sum(profit)  = 1,050
sum(revenue) = 10,100
1,050 / 10,100 = 10.4%   ← right
kpi = (df.groupBy("Country")
         .agg(sum("Revenue").alias("Revenue"), sum("Cost").alias("Cost"),
              countDistinct("OrderID").alias("Orders"))
         .withColumn("Profit", col("Revenue") - col("Cost"))
         .withColumn("ProfitMarginPct",
             when(col("Revenue") != 0, round(col("Profit") / col("Revenue") * 100, 2)))   # NULL, not a crash, if 0
         .withColumn("AOV",
             when(col("Orders") > 0, round(col("Revenue") / col("Orders"), 2))))

The when(… != 0, …) guard returns NULL for a zero denominator instead of a meaningless value. Gold should never contain "infinity" or a divide-by-zero surprise.

Ratios such as margin % and AOV are often better defined as measures in the semantic model (DAX), so Power BI recalculates them correctly at any level a user filters to. Store the additive parts (Revenue, Cost, Orders) in Gold.

    sum(when(col("Amount") >= 10000, col("Amount")).otherwise(0)).alias("HighValueRevenue"),

The Join-Then-Aggregate Trap

Lesson 5.4's row explosion is most dangerous right before an aggregation. Joining Orders (order grain) to OrderLines (line grain) and then summing an order-level column — like shipping charge — counts the charge once per line:

# ❌ Shipping charge is on the order, but we're now at line grain
orders.join(lines, "OrderID").groupBy("Country").agg(sum("ShippingCharge"))   # 3× too high for a 3-line order

# ✅ Aggregate each side to a common grain first, then join
order_ship = orders.groupBy("Country").agg(sum("ShippingCharge").alias("Shipping"))
line_rev   = lines.join(orders.select("OrderID","Country"), "OrderID").groupBy("Country").agg(sum("Amount").alias("Revenue"))
result = line_rev.join(order_ship, "Country", "left")

Validate the Grain

After building any aggregate, prove one row per grain key and that totals reconcile with Silver:

# 1. Exactly one row per grain
dupes = monthly.groupBy("Year", "Month", "Country").count().filter("count > 1").count()
assert dupes == 0, "Grain violated"

# 2. Totals reconcile
silver_total = silver_sales.agg(sum("Amount")).first()[0]
gold_total   = monthly.agg(sum("Revenue")).first()[0]
assert silver_total == gold_total, f"Revenue mismatch: Silver {silver_total} vs Gold {gold_total}"

WHERE vs HAVING (reminder)

filter() before groupBy = WHERE (fewer rows in). filter() after agg = HAVING (fewer groups out). Filtering early is also faster.

Grain defines what one row of a table represents, and the groupBy columns are the grain, so it must be decided before writing an aggregation. Use countDistinct for business entities (orders, customers) when data is at line grain; average order value is total revenue divided by distinct orders, not avg of line amounts. Ratios are computed from aggregated parts, never by averaging ratios, with a guard against zero denominators — or left to semantic-model measures. Aggregates ignore NULLs. Joining a coarser table to a finer one before aggregating double-counts, so aggregate each side to a common grain first. Validate one row per grain key and reconcile totals back to Silver.

Generating surrogate keys

from pyspark.sql.window import Window
from pyspark.sql.functions import row_number, lit, col, coalesce, max as max_

def add_surrogate_key(df, key_col, order_col, existing_table=None):
    """Continue numbering after the current max key, so keys never collide across loads."""
    start = 0
    if existing_table and spark.catalog.tableExists(existing_table):
        start = spark.table(existing_table).agg(max_(key_col)).first()[0] or 0
    w = Window.orderBy(order_col)
    return df.withColumn(key_col, lit(start) + row_number().over(w))
monotonically_increasing_id() looks tempting but produces large, gappy numbers that change between runs — fine for a one-off, wrong for keys that facts depend on. The max + row_number pattern gives stable, compact keys. (The un-partitioned window runs on one task, which is fine for dimension-sized data.)

The "Unknown" member

Every dimension gets a row with key -1. When a fact can't find its dimension (orphan, NULL key, late-arriving customer), it points to -1 instead of being dropped or carrying a NULL key. Reports then show an honest "Unknown" bucket and totals stay correct.

Slowly Changing Dimensions (SCD)

Sreehari lived in Hyderabad in 2025 and moved to Bengaluru in August 2026. A report asks for 2025 sales by city. Should his 2025 orders count under Hyderabad (where he was) or Bengaluru (where he is now)? Dimensions change slowly over time, and the business must decide what happens to history. This lesson covers the SCD types, then builds the important one — Type 2 — properly.

The Question

Overwrite (Type 1)

DimCustomer: 101 → Bengaluru

2025 sales report: Sreehari's orders appear under Bengaluru — even though he was in Hyderabad then. History is rewritten.

Keep history (Type 2)

DimCustomer: 101 → Hyderabad (2025–Aug 2026), 101 → Bengaluru (Aug 2026 →)

2025 sales report: orders correctly under Hyderabad. Current report: Bengaluru.

Neither is "right" in general. It depends on the attribute and the question the business asks. That decision is made per column.

The date convention — get this exactly right

Pick one convention and use it everywhere. This module uses:

  • Dates are inclusive at both ends
  • When a row is closed, EndDate = new StartDate − 1 day
  • The current row has EndDate = 9999-12-31 (not NULL — so BETWEEN just works)
  • The first version starts at 1900-01-01, so facts older than the dimension still find a match

The fact lookup is then simply OrderDate BETWEEN StartDate AND EndDate.

Off-by-one dates lose sales. A common mistake is to close the old row on 2026-08-21 but look it up with OrderDate < EndDate. An order placed on the 21st then matches neither version (not before the 21st, not on or after the 22nd) and falls out of the fact table — or into Unknown. The opposite error (EndDate = new StartDate with inclusive matching) matches both and double-counts it. Choose one convention, and test the boundary day.

Detecting Change with a Hash

Comparing columns one by one is long and breaks on NULLs (NULL != 'Pune' is not true — it's NULL, so the change is missed). Hash the tracked columns instead:

from pyspark.sql.functions import sha2, concat_ws, coalesce, col, lit

tracked = ["CustomerName", "City", "Country", "Segment"]     # Type 2 columns only

def with_hash(df):
    return df.withColumn("HashValue",
        sha2(concat_ws("||", *[coalesce(col(c).cast("string"), lit("~")) for c in tracked]), 256))

coalesce(…, "~") makes NULLs comparable; the || separator stops ("AB","C") and ("A","BC") hashing the same. Now "did anything change?" is one comparison: source.HashValue != target.HashValue.

Type 2 — Why One Plain MERGE Isn't Enough

A changed customer needs two actions: update the current row (close it) and insert a new row. But in a MERGE, one source row can only take one action. The classic Delta solution is to feed changed customers into the MERGE twice:

Silver_Customers (with HashValue)
↓ build the staged source
Every customerMergeKey = CustomerID
Changed customers againMergeKey = NULL
↓ MERGE ON t.CustomerID = s.MergeKey AND t.IsCurrent
Matched + hash differsclose old row
Matched + same hashdo nothing
Not matchedinsert new version / new customer

The copy with MergeKey = NULL can never match (NULL equals nothing), so it always falls through to the insert. That's the trick: one atomic MERGE that both closes and inserts.

from delta.tables import DeltaTable
from pyspark.sql.functions import max as max_

effective_date = "2026-08-22"          # parameter: usually the load date, or the source's change date

dim     = spark.table("DimCustomer")
current = dim.filter("IsCurrent = true")

# 1. Customers whose tracked attributes changed
changed = (src.alias("s")
             .join(current.alias("d"), "CustomerID")
             .filter(col("s.HashValue") != col("d.HashValue"))
             .select("s.*"))

# 2. Staged source: everyone with MergeKey, plus changed rows again with NULL MergeKey
staged = (src.withColumn("MergeKey", col("CustomerID"))
             .unionByName(changed.withColumn("MergeKey", lit(None).cast("bigint"))))

# 3. Pre-assign surrogate keys for any row that ends up inserted (unused keys just leave gaps)
max_key = dim.agg(max_("CustomerKey")).first()[0] or 0
staged = staged.withColumn("CustomerKey",
                           lit(max_key) + row_number().over(Window.orderBy("CustomerID", "MergeKey")))

# 4. One atomic MERGE: close changed rows, insert new versions and new customers
(DeltaTable.forName(spark, "DimCustomer").alias("t")
    .merge(staged.alias("s"), "t.CustomerID = s.MergeKey AND t.IsCurrent = true")
    .whenMatchedUpdate(
        condition = "t.HashValue <> s.HashValue",
        set = {"IsCurrent": "false",
               "EndDate":   f"date_sub(to_date('{effective_date}'), 1)"})
    .whenNotMatchedInsert(values = {
        "CustomerKey":  "s.CustomerKey",
        "CustomerID":   "s.CustomerID",
        "CustomerName": "s.CustomerName",
        "City":         "s.City",
        "Country":      "s.Country",
        "Segment":      "s.Segment",
        "HashValue":    "s.HashValue",
        "StartDate":    f"to_date('{effective_date}')",
        "EndDate":      "to_date('9999-12-31')",
        "IsCurrent":    "true"})
    .execute())

Production Considerations

1
Choose columns deliberately
Only columns the business analyses historically go in tracked. Tracking Email as Type 2 creates a new version every time someone fixes a typo.
2
One change per key per run
If Silver holds three changes for customer 101 since the last run, the MERGE above only records the latest. To keep every intermediate version, process changes in date order — or build versions with lead("StartDate") (Lesson 5.5) from a full change history.
3
Effective date
Use the source's real change timestamp when it exists; the load date is a fallback that's late by however long ingestion took.
4
Late-arriving facts
An order dated last month arrives today. The range join still finds the right version — as long as old versions were never deleted.
5
Run serially
Two loads of the same dimension at once can both compute the same max_key. Orchestrate dimension loads one at a time (Module 3 pipeline dependencies).

A Slowly Changing Dimension handles attributes that change over time. Type 0 keeps the original, Type 1 overwrites (no history), and Type 2 keeps full history by closing the current row and inserting a new version, each with its own surrogate key while the business key repeats; Types 3, 4 and 6 are variations. A Type 2 table has StartDate, EndDate and IsCurrent, and a hash of the tracked columns detects change NULL-safely. Because a changed key needs both an update and an insert, the Delta pattern stages changed rows twice — once with the business key as the merge key, once with NULL — so one atomic MERGE closes old rows and inserts new ones. Facts find the right version with a range join on the order date, so a consistent, inclusive date convention is critical to avoid losing or double-counting boundary-day sales.
