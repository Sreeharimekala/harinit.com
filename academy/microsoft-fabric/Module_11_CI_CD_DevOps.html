11.1

CI/CD Concepts for Fabric

CI/CD (continuous integration and continuous delivery) is a set of habits: keep everything in version control, review changes, test them in a safe environment, and release them the same way every time. This lesson explains what that means in Fabric, what Git can and can't store, and the two main ways to release.

Why Bother?

✗ Editing in production

  • "Who changed this notebook? It worked yesterday."
  • No way back to the previous version
  • A typo breaks the nightly load for everyone
  • DEV and PROD drift apart; nobody knows how

✓ CI/CD

  • Every change has an author, date and reason
  • Roll back with one revert
  • Changes reviewed, then tested in TEST before PROD
  • PROD is changed only by the release process

Environments = Workspaces

→

→
Sales-TESTtest data, UAT
→
Sales-PRODreal users

What Goes in Git — and What Doesn't

✓ Item definitions (code & metadata)

  • Notebook code and parameter cells
  • Pipeline JSON (activities, parameters, expressions)
  • Dataflow Gen2 queries
  • Semantic model (TMDL) and report definitions
  • Lakehouse/Warehouse definitions (Warehouse schema as a SQL project)
  • Environments, variable libraries, KQL items…

✗ Not in Git

  • Table data and files in OneLake
  • Run history, schedules (in some cases), permissions
  • Connection credentials and secrets
  • Workspace settings
Git is not a backup of your data. Deploying a Lakehouse to PROD creates an empty Lakehouse; the tables are created and filled by your pipelines and notebooks there. Plan for table creation (idempotent DDL) as part of the release — Lesson 11.7.

Two Ways to Release

A. Deployment pipelinesB. Git-based, with code
HowFabric UI copies items DEV → TEST → PRODA CI/CD pipeline (GitHub Actions / Azure DevOps) deploys from the repo to each workspace using fabric-cicd or the REST API
Environment differencesDeployment rules, variable librariesparameter.yml replacement, variable libraries
ApprovalsFabric permissions; optional manual stepsPR reviews, environment approvals in GitHub / ADO
Best forSmall–medium teams, Power BI-heavy, getting startedLarger teams, existing DevOps practice, full automation
Lessons11.411.6

Both start with Git integration in DEV (Lesson 11.2). Many teams combine them: Git + PRs for development, deployment pipelines for promotion.

CI/CD in Fabric means keeping item definitions in Git, reviewing changes through pull requests, and promoting them through separate DEV, TEST and PROD workspaces using a repeatable process rather than manual edits. Git stores definitions — notebooks, pipelines, dataflows, semantic models, reports, lakehouse and warehouse definitions, environments and variable libraries — but not data, credentials, run history or most permissions, so releases must also create tables and configure connections. Releases use either Fabric deployment pipelines, with deployment rules and variable libraries for environment differences, or Git-based automation with tools such as fabric-cicd in GitHub Actions or Azure DevOps.
11.2

Git Integration

Git integration connects a workspace to a branch in a Git repository. From then on, Fabric shows which items have changed, and you commit workspace changes to Git or update the workspace from Git. This lesson walks through connecting, the daily commit/update cycle, what the files look like, and the limits.

Before You Start

  • Tenant setting Users can synchronize workspace items with their Git repositories enabled (and the GitHub-specific setting if you use GitHub)
  • Supported provider: Azure DevOps (same tenant), GitHub or GitHub Enterprise (cloud)
  • You're Admin of the workspace (only admins connect, disconnect and change branches)
  • A repository and branch exist; ideally an empty folder for this workspace

Connect

  1. Workspace → Workspace settings → Git integration.
  2. Choose provider. Azure DevOps signs in with your Entra account; GitHub uses a connection with a personal access token.
  3. Pick organisation/owner, repository, branch (e.g. main) and Git folder (e.g. /sales).
  4. Connect and sync. If the workspace has items and the folder is empty, they're committed; if the folder has content and the workspace is empty, items are created from Git.

Branch Out: Your Own Workspace

Several people editing one DEV workspace step on each other. Instead, use Source control → Branch out to new workspace: Fabric creates a new branch from the current one and a new workspace connected to it. You develop there, commit, and open a pull request to merge into main. When merged, DEV shows "Update required".

Branching out copies item definitions only — the new workspace's lakehouses are empty, and workspace settings aren't copied. Point feature-workspace notebooks at a shared DEV lakehouse (via a variable library) or load a small sample.

Limits to Know

  • Not every item type is supported — check the current supported-items list; some are preview
  • Commits are size-limited (125 MB) — never put data files in a Git-connected folder
  • Only Admins manage the Git connection; Contributors and above can commit and update
  • Renaming or moving items in Git and in the workspace at the same time causes conflicts — do one or the other

Hands-On Lab

  1. Create a repo and connect Sales-DEV to main, folder /sales.
  2. Change a notebook; commit with a message. View the diff in the repo.
  3. Edit a file directly in the repo (e.g. a pipeline parameter default) and Update the workspace.
  4. Branch out to feature/null-customers; make a change there and commit.
Fabric Git integration connects a workspace to a branch and folder in Azure DevOps, GitHub or GitHub Enterprise. Workspace admins manage the connection; contributors commit workspace changes to Git and update the workspace from Git, with status icons showing uncommitted changes, required updates and conflicts. Items are serialised as readable files — notebooks as .py, pipelines as JSON, semantic models as TMDL — with a .platform file per item, enabling diffs and reviews, but data is never stored. Branch out creates a feature branch and its own workspace, so developers work in isolation and merge through pull requests. Not all items are supported and commits are size-limited.
11.3

GitHub, Azure DevOps & Branching

Git integration works the same with either provider, but the surrounding setup differs: how Fabric signs in, how pull requests and approvals work, and where your automated pipelines run. This lesson covers both, plus the branching strategy that suits most Fabric teams.

GitHub vs Azure DevOps

GitHub / GitHub EnterpriseAzure DevOps
Fabric signs in withA connection using a personal access token (fine-grained recommended: one repo, Contents read/write)Your Entra ID account (same tenant)
Pull requestsPull requests, CODEOWNERS, required reviewsPull requests, branch policies, required reviewers
AutomationGitHub ActionsAzure Pipelines (YAML)
SecretsRepository / environment secretsVariable groups, Key Vault link
Approvals before PRODEnvironments with required reviewersEnvironments with approvals and checks
Work trackingIssues, ProjectsBoards (work items linked to commits)

Choose whichever your organisation already uses — the Fabric side is almost identical.

Setting Up GitHub

  1. Create a private repo, e.g. contoso/fabric-sales, with a README and main branch.
  2. Create a fine-grained personal access token limited to that repo, with Contents: Read and write; set an expiry and calendar reminder to renew.
  3. In Fabric Git integration, choose GitHub, add the connection with the token and repo URL, pick branch and folder.
  4. Protect main: require pull requests, at least one approval, and passing checks; disallow force pushes.
  5. Add a CODEOWNERS file so the right people review the right folders.
# .github/CODEOWNERS
/sales/*.Notebook/        @contoso/data-engineers
/sales/*.SemanticModel/   @contoso/bi-developers
/sales/*.Report/          @contoso/bi-developers

Setting Up Azure DevOps

  1. Create a project and an Azure Repos Git repository.
  2. Connect Fabric (Azure DevOps option signs in automatically with your Entra account).
  3. Branch policies on main: minimum reviewers, linked work items, build validation.

A Branching Strategy That Works

feature/*feature workspaces
→ PR + review →
mainconnected to DEV
→ release →
TEST
→ approval →
PROD
  • Short-lived feature branches — days, not months; merge often to avoid big conflicts
  • main is always deployable and connected to DEV
  • TEST and PROD are not Git-connected in this pattern; they're deployed to (deployment pipeline or fabric-cicd)
  • Hotfix: branch from main, fix, PR, release through TEST quickly — never edit PROD directly
An alternative some teams use is one branch per environment (dev, test, prod) each connected to its workspace, promoting by merging between branches. It's simple to picture but makes environment-specific values harder and encourages "merge conflicts as releases". The single-main pattern above is usually easier.

What Reviewers Should Check

  • No hardcoded workspace IDs, lakehouse IDs, server names or secrets
  • Notebooks: parameter cell present; no leftover display() of large data; no collect() on big tables
  • Pipelines: Fail activities on failure paths; retries and timeouts set (Module 7)
  • Schema changes accompanied by migration scripts (11.7)
  • Semantic models: no accidental removal of measures used by reports

Hands-On Lab

  1. Set up a GitHub repo with branch protection and CODEOWNERS; connect Sales-DEV.
  2. From your feature workspace, commit a change and open a pull request; review the notebook diff.
  3. Merge, then Update Sales-DEV from Git.
Fabric Git integration supports GitHub, GitHub Enterprise and Azure DevOps. GitHub connections use a personal access token — ideally fine-grained and scoped to one repository — while Azure DevOps uses the user's Entra identity in the same tenant. Both provide pull requests, review rules (CODEOWNERS or branch policies), secrets, environment approvals and automation through GitHub Actions or Azure Pipelines. A common strategy uses short-lived feature branches with their own workspaces, merged by reviewed pull requests into an always-deployable main connected to DEV, with TEST and PROD deployed to rather than edited, and hotfixes following the same path.
11.4

Deployment Pipelines

A deployment pipeline is a Fabric item that links a series of workspaces as stages — typically Development, Test and Production — and copies item definitions from one stage to the next with a click (or an API call). It shows what's different between stages and lets you change environment-specific settings automatically with deployment rules.

Set Up

  1. + New → Deployment pipeline; name it Sales release.
  2. Define stages (default three; you can have up to 10, e.g. DEV, TEST, UAT, PROD).
  3. Assign a workspace to each stage: Sales-DEV, Sales-TEST, Sales-PROD. Each workspace can belong to only one pipeline.
  4. Optionally make a stage public (visible to consumers) — usually only Production.

Compare and Deploy

  • Deploy all, or select items to deploy (Fabric warns if a selected item depends on one you didn't select)
  • Add a deployment note — it appears in the deployment history
  • Items in the target are paired with source items; renaming a paired item doesn't break pairing
  • Backward deployment (e.g. PROD → TEST) is possible for items that don't exist in the earlier stage — useful to rebuild a lost TEST

What Deployment Does — and Doesn't — Copy

Copied

  • Item definitions: notebook code, pipeline JSON, model metadata, report layout
  • Lakehouse/Warehouse definitions (schema where supported)
  • Item relationships, re-pointed to items in the same stage where possible

Not copied

  • Data in tables and files
  • Workspace permissions and settings
  • Semantic-model data — refresh after deploying an Import model
  • Some schedules and credentials (configure once per stage)

Deployment Rules

In each target stage, click the rules icon to set values that should replace the source values during deployment:

Rule typeApplies toExample
Data source ruleSemantic models, dataflows, some itemsDEV sql-dev.contoso.com → PROD sql-prod.contoso.com
Parameter ruleSemantic models (Power Query parameters)Environment = "PROD"
Default lakehouse ruleNotebooksPoint the notebook at lh_gold in Sales-PROD

Rules are set once per stage and applied on every deployment. For values that many items share — and for pipelines, which rules don't cover — use a variable library (Lesson 11.5).

Permissions

Restrict who can deploy to Production by giving only the release managers (or a service principal) Contributor on the PROD workspace. Deployment pipelines can also be driven by the Fabric REST API, so a GitHub Action or Azure DevOps job can trigger "deploy TEST → PROD" after an approval.

Hands-On Lab

  1. Create Sales release with three stages; assign the three workspaces.
  2. Deploy DEV → TEST. Change a notebook in DEV, compare, view the diff, deploy again with a note.
  3. Add a default-lakehouse rule for the notebook in TEST and PROD; deploy and check which lakehouse it uses.
  4. Look at the deployment history.
A Fabric deployment pipeline links workspaces as stages — typically Development, Test and Production, up to ten — and deploys item definitions from one stage to the next, either all items or selected ones, showing differences and keeping a history with notes. It copies definitions and relationships but not data, permissions or credentials. Deployment rules replace environment-specific values per stage — data source rules, parameter rules and default lakehouse rules for notebooks — while variable libraries cover shared values and pipelines. Deploying requires pipeline admin rights plus Contributor on both workspaces, and pipelines can be automated through the REST API.

Environment Management

The same notebook must read sql-dev in DEV and sql-prod in PROD, write to a different lakehouse, and email a different team on failure. The golden rule: the item definition is identical in every environment; only configuration differs. This lesson shows the tools that make that possible.

Variable Libraries

A variable library is a Fabric item holding named variables, each with a default value and alternative value sets (e.g. TEST, PROD). Each workspace has one active value set, chosen once per stage — so after deployment, every item automatically picks up the right values.

VariableTypeDefault (DEV)TESTPROD

source_databaseStringSalesDevSalesTestSales
gold_lakehouseItem referencelh_gold (DEV)lh_gold (TEST)lh_gold (PROD)
alert_emailStringdev-team@contoso.comqa@contoso.comdata-oncall@contoso.com
sample_percentInteger10100100

In a notebook

vl = notebookutils.variableLibrary.getLibrary("vl_sales")

server   = vl.source_server
database = vl.source_database
sample   = int(vl.sample_percent)

df = spark.table("silver.orders")
if sample < 100:
    df = df.sample(fraction=sample / 100, seed=42)

In a pipeline

Open the pipeline's Library variables pane, add references to library variables, then use them in expressions:

@pipeline().libraryVariables.alert_email
@pipeline().libraryVariables.source_database
Deploying the variable library copies its variables and value sets, but each stage keeps its own active value set — so a deployment never accidentally switches PROD to the DEV values.

Connections and Secrets

  • Create one connection per environment (e.g. conn-sales-sql-dev, conn-sales-sql-prod), each with its own credentials, owned by a service account or workspace identity — not a person
  • Reference the connection ID through a variable library or replace it at deployment (parameter.yml, 11.6)
  • Secrets that code needs go in Azure Key Vault: notebookutils.credentials.getSecret(vault_url, "secret-name")
  • Never commit a .env file, token or connection string to the repo — add a .gitignore and secret scanning

Spark Environments

The Environment item (Module 10.3) holds the runtime version, libraries (e.g. great_expectations==1.x) and Spark properties. Keep it in Git and deploy it like any item, so DEV and PROD notebooks run with the same libraries — "works in DEV, fails in PROD" is very often a library version difference.

Hands-On Lab

  1. Create vl_sales with the variables above and TEST/PROD value sets.
  2. Use it in a notebook (server, sample) and in a pipeline (alert email).
  3. Deploy to TEST; set TEST's active value set to TEST; run and confirm the values.
  4. Move one secret into Key Vault and read it with getSecret.
Environment management keeps item definitions identical across DEV, TEST and PROD while configuration differs. Variable libraries hold named variables with a default and alternative value sets; each workspace has an active value set, which deployments don't change, and notebooks read values with notebookutils.variableLibrary while pipelines use library variables in expressions. Connections are created per environment and owned by service principals or workspace identities, secrets live in Azure Key Vault, and Spark Environment items keep libraries consistent. Hardcoded names, IDs and paths, environment checks in code, and editing PROD directly are anti-patterns.
11.6

Deploy Across Workspaces with Code

For full automation, deployment becomes code: when a pull request merges into main, a GitHub Actions or Azure DevOps pipeline deploys the repository's items to TEST, waits for approval, then deploys to PROD. Microsoft's open-source fabric-cicd Python library does the heavy lifting. This lesson builds that pipeline.

The Flow

PR merged to main
→
CI: checkslint, parameter validation
→
Deploy → TESTfabric-cicd
→
Smoke tests
→ approval →
Deploy → PROD

Step 1 — A Service Principal

  1. Register an app in Entra ID (e.g. sp-fabric-deploy); create a client secret or, better, federated credentials (OIDC) for GitHub/ADO.
  2. Fabric admin enables the tenant setting allowing service principals to use Fabric APIs (scoped to a security group containing the SP).
  3. Add the SP as Contributor (or Member) on Sales-TEST and Sales-PROD.
  4. Store tenant ID, client ID and secret as GitHub environment secrets / ADO variable group.

Step 2 — parameter.yml: Environment Replacements

fabric-cicd finds values in the item files and replaces them per environment while deploying:

# sales/parameter.yml
find_replace:
  # DEV gold lakehouse ID → the TEST / PROD lakehouse IDs
  - find_value: "8c2d7a9e-1111-4b6e-9f3a-0d5e2c7b1a11"
    replace_value:
      TEST: "5f1e0b2c-2222-4c8d-8e1f-3a6b9d0c2b22"
      PROD: "a7c3e9d1-3333-4f2a-b6c5-7e8d0f1a3c33"
  # DEV workspace ID → target workspace IDs
  - find_value: "0e9b4c1a-4444-4d3f-a2b1-c8e7f6d5a444"
    replace_value:
      TEST: "$workspace.id"
      PROD: "$workspace.id"

($workspace.id is a fabric-cicd dynamic value meaning "the workspace being deployed to". Prefer variable libraries for values a person might change; use parameter.yml for IDs embedded in definitions.)

Step 3 — The Deploy Script

# deploy/deploy.py
import argparse, os
from azure.identity import ClientSecretCredential
from fabric_cicd import FabricWorkspace, publish_all_items, unpublish_all_orphan_items

p = argparse.ArgumentParser()
p.add_argument("--environment", required=True)          # TEST or PROD
p.add_argument("--workspace-id", required=True)
args = p.parse_args()

credential = ClientSecretCredential(
    tenant_id=os.environ["AZURE_TENANT_ID"],
    client_id=os.environ["AZURE_CLIENT_ID"],
    client_secret=os.environ["AZURE_CLIENT_SECRET"],
)

workspace = FabricWorkspace(
    workspace_id=args.workspace_id,
    environment=args.environment,
    repository_directory="sales",
    item_type_in_scope=["Lakehouse", "Environment", "VariableLibrary", "Notebook",
                        "DataPipeline", "SemanticModel", "Report"],
    token_credential=credential,
)

publish_all_items(workspace)            # create or update every item in scope
unpublish_all_orphan_items(workspace)   # remove items deleted from the repo
unpublish_all_orphan_items deletes items in the target that aren't in the repo. That's what keeps PROD identical to Git — but run it only on workspaces fully managed by this process, and never against a workspace where people create items by hand.

Step 4a — GitHub Actions

# .github/workflows/deploy-fabric.yml
name: Deploy Fabric Sales
on:
  push:
    branches: [main]
    paths: ["sales/**"]

jobs:
  deploy-test:

    environment: test

      - uses: actions/setup-python@v5

      - run: pip install fabric-cicd
      - run: python deploy/deploy.py --environment TEST --workspace-id "${{ vars.WORKSPACE_ID }}"
        env:
          AZURE_TENANT_ID:     ${{ secrets.AZURE_TENANT_ID }}
          AZURE_CLIENT_ID:     ${{ secrets.AZURE_CLIENT_ID }}
          AZURE_CLIENT_SECRET: ${{ secrets.AZURE_CLIENT_SECRET }}

  deploy-prod:
    needs: deploy-test
    runs-on: ubuntu-latest
    environment: production          # required reviewers configured on this environment
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-python@v5
        with: { python-version: "3.12" }
      - run: pip install fabric-cicd
      - run: python deploy/deploy.py --environment PROD --workspace-id "${{ vars.WORKSPACE_ID }}"
        env:
          AZURE_TENANT_ID:     ${{ secrets.AZURE_TENANT_ID }}
          AZURE_CLIENT_ID:     ${{ secrets.AZURE_CLIENT_ID }}
          AZURE_CLIENT_SECRET: ${{ secrets.AZURE_CLIENT_SECRET }}

Each GitHub environment (test, production) holds its own WORKSPACE_ID variable and secrets; the production environment requires a reviewer to approve before the job runs.

Code-based deployment uses a CI/CD pipeline in GitHub Actions or Azure DevOps, triggered by merges to main, that deploys repository items to each workspace with Microsoft's fabric-cicd library. A service principal, allowed to use Fabric APIs and given Contributor on target workspaces, authenticates the deployment, with secrets held in GitHub environments or ADO variable groups. FabricWorkspace defines the target, environment, repository folder and item types; publish_all_items creates or updates items and unpublish_all_orphan_items removes items no longer in Git. parameter.yml replaces environment-specific IDs during deployment. Environment approvals gate PROD, and the Fabric REST API, CLI and Terraform provider cover further automation.
11.7

Capstone: A Complete Release Process

This lesson puts the module together into a release process you can adopt as-is: from a developer's feature branch to a verified production release, including the parts teams most often forget — creating tables, changing schemas safely, testing after deployment and rolling back.

The End-to-End Flow

1
Develop
Branch out to feature/142-null-customers workspace; build and test against DEV data (variable library points at the shared DEV lakehouse).
2
Commit & PR
Commit with a clear message; open a PR to main; CODEOWNERS review; CI checks pass.
3
Integrate
Merge; Sales-DEV updates from Git (or is deployed by the pipeline); run the end-to-end pipeline in DEV.
4
Release to TEST
Automatic deploy; run migrations; run the master pipeline; smoke tests and data checks.
5
Approve
Business/UAT sign-off; release manager approves the PROD environment.
6
Release to PROD
Deploy; migrations; smoke tests; announce; monitor the next scheduled run.

Tables and Schema Changes

Deployment copies definitions, not data or (for Lakehouses) tables. Make table creation and changes part of the release, written so they can run any number of times safely (idempotent):

# nb_migrations — run by the release pipeline in every environment after deployment
spark.sql("""
CREATE TABLE IF NOT EXISTS gold.FactSales (
    OrderId STRING, OrderDate DATE, CustomerKey BIGINT, StoreKey BIGINT,
    ProductKey BIGINT, Quantity INT, Amount DECIMAL(18,2)
) USING DELTA
""")

# Additive change: add a column only if it isn't there yet
cols = [c.name for c in spark.table("gold.FactSales").schema]
if "DiscountAmount" not in cols:
    spark.sql("ALTER TABLE gold.FactSales ADD COLUMNS (DiscountAmount DECIMAL(18,2))")

# Record what ran
spark.sql("""
CREATE TABLE IF NOT EXISTS ops.schema_migrations (version STRING, applied_at TIMESTAMP)
""")
spark.sql("INSERT INTO ops.schema_migrations VALUES ('2026.08.142', current_timestamp())")
Change typeSafe approach
Add a columnAdditive — deploy code that tolerates both old and new schema, then add the column
Rename a columnAdd new → backfill → switch readers → drop old in a later release (or Delta column mapping)
Change a typeNew column or rebuild the table from Silver; never in place on PROD without a backup (Delta time travel helps)
Warehouse schemaWarehouse definitions are in Git as a SQL database project; for data-preserving changes, use migration scripts run by a pipeline
Semantic modelCheck impact analysis before removing measures/columns used by reports

Post-Deployment Tests

# nb_smoke_tests — fail the release if any check fails
checks = {
    "fact has rows for yesterday":
        spark.sql("SELECT COUNT(*) c FROM gold.FactSales WHERE OrderDate = date_sub(current_date(), 1)").first().c > 0,
    "no orphan store keys":
        spark.sql("SELECT COUNT(*) c FROM gold.FactSales WHERE StoreKey IS NULL").first().c == 0,
    "migration recorded":
        spark.sql("SELECT COUNT(*) c FROM ops.schema_migrations WHERE version = '2026.08.142'").first().c == 1,
}
failed = [name for name, ok in checks.items() if not ok]
if failed:
    raise Exception(f"Smoke tests failed: {failed}")
print("All smoke tests passed")

The release pipeline can run these notebooks through the Fabric job API (or a pipeline that contains them) and stop if they fail.

Rollback

What went wrongRoll back by
Bad code in a notebook/pipeline/reportgit revert the merge → normal release (fast, because it's automated)
Bad data written to a tableDelta RESTORE TABLE … TO VERSION AS OF n (Module 4); Warehouse clone/time travel (Module 6)
Wrong configuration valueFix the variable library value / active value set — no code release needed
Broken deployment pipeline stageRedeploy the previous good state from the earlier stage, or backward-deploy
Rollback is only fast if releasing is fast. Teams that release small changes often rarely need to roll back, and when they do, it's one revert and one release.

Release Checklist

  • All work merged through reviewed PRs; nothing edited directly in TEST/PROD
  • No hardcoded IDs/servers/secrets; variable library values set for every stage
  • Migrations idempotent and recorded
  • Deployed to TEST; master pipeline run; smoke tests and data checks pass
  • Impact analysis reviewed for model/report changes; UAT sign-off
  • PROD approval; deploy; migrations; smoke tests
  • Release notes (PR links) shared; next scheduled run monitored

A complete Fabric release process runs from a feature branch and workspace, through a reviewed pull request into main and DEV, to an automated TEST deployment followed by idempotent migrations, a pipeline run and smoke tests, then an approved PROD deployment with the same steps. Because deployments copy definitions rather than tables or data, table creation and schema changes are scripted to be safely re-runnable and recorded, with breaking changes done in additive stages. Post-deployment tests fail the release on problems. Rollback uses git revert for code, Delta or Warehouse time travel for data, and variable library changes for configuration, which is fast when releases are small and automated.
