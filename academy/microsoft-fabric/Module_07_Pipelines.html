Activities & Dependencies

A pipeline is a set of activities joined by dependencies. You've used a few activities already. A pipeline is activities connected by dependency conditions: Upon success, Upon failure, Upon completion and Upon skip. Activities with no dependency run in parallel; multiple dependencies into one activity are ANDed. Activities fall into data movement (Copy, Delete, Get Metadata), transformation (Notebook, Dataflow Gen2, Stored procedure, Script, KQL) and control flow (Lookup, ForEach, If, Switch, Until, Filter, Wait, variables, Invoke pipeline, Fail), plus integration and notification (Web, Semantic model refresh, Teams, Outlook). Production activities need a sensible timeout, retries for transient network work only, and secure input/output for sensitive values. Every activity returns JSON output that later activities reference with @activity('name').output.
7.2

Expressions & Dynamic Content

Almost any field in a pipeline — a table name, a file path, a SQL query, a parameter value — can be dynamic: calculated when the pipeline runs instead of typed in. That's what turns one pipeline into a reusable tool. This lesson teaches the expression language and gives you a recipe book of the expressions you'll need most.

Two Ways to Write Dynamic Content

Click any field, then Add dynamic content (or press Alt+Shift+D) to open the expression builder.

Whole value: starts with @

@pipeline().parameters.TableName

The entire field is the result of the expression. Keeps the type (number, boolean, array).

Inside text: @{ … }

Files/Raw/@{pipeline().parameters.TableName}/@{formatDateTime(utcNow(),'yyyy-MM-dd')}.csv

String interpolation — expressions embedded in text. Result is always a string.

Pipeline fields become dynamic with expressions: a value starting with @ is a whole expression that keeps its type, and @{ … } interpolates expressions inside text. Expressions reference pipeline().parameters, variables('x'), activity('name').output (and .error.message on failure), item() inside ForEach, and system values such as pipeline().RunId and TriggerTime. Built-in functions cover strings (concat, replace, split), dates (utcNow, formatDateTime, addDays), logic (equals, if, coalesce, empty) and conversion (string, int, json). Names are case-sensitive, and expressions are limited to 8,192 characters, so complex logic belongs in a notebook or procedure.

⚠️ The parallel ForEach trap

Variables are pipeline-scoped — there's one copy shared by every iteration of a loop. In a parallel ForEach, iterations overwrite each other:

ForEach (parallel)
→
Customers: Set CurrentTable = Customers
Orders: Set CurrentTable = Orders
Products: Set CurrentTable = Products
→
Log "loaded @{variables('CurrentTable')}"may log "Products" three times
  • Inside a parallel loop, use @item() directly — never copy it into a variable
  • Append variable is the exception: appending to an array from parallel iterations is designed for this
  • If an iteration genuinely needs its own variables, move the loop body into a child pipeline (each run has its own variables) and call it with Invoke pipeline
  • Or set the ForEach to Sequential — slower, but safe

Parameter, Variable, or Config Table?

ValuePut it in
Something a person or trigger chooses per run (date, table, mode)Parameter
Something calculated during the run (batch ID, row count, status)Variable
Something that describes many objects and changes over time (100 tables, their keys, load types, active flags)Config table read by Lookup (Lesson 7.4)
Something that differs per environment (server names, workspace IDs)Variable library / deployment rules (Module 11)

Hands-On Lab

  1. Create parameters LoadDate, LoadType, TableList (Array). Set a BatchID variable from the current time.
  2. Build a parallel ForEach over TableList that sets a variable CurrentTable then waits 5 s and appends CurrentTable to an array. Run it — observe the wrong values.
  3. Fix it by appending @item() directly. Run again.
  4. Run the pipeline manually with LoadType = FULL and a past LoadDate, and confirm the values flow into a Notebook activity's base parameters.
Parameters are read-only inputs supplied when a run starts — by a user, schedule, event trigger or parent pipeline — and are referenced with pipeline().parameters; give them defaults so scheduled runs need no input and backfills just override them. Variables are set during the run with Set variable or Append variable and are referenced with variables(). Variables are pipeline-scoped, so setting one inside a parallel ForEach causes iterations to overwrite each other: use item() directly, Append variable, a sequential loop, or a child pipeline per item. Credentials belong in connections, not parameters; values describing many objects belong in a config table; environment-specific values belong in variable libraries or deployment rules.
7.4

Lookup: Driving Pipelines from Data

Lookup reads a small amount of data — one value or a short list — so later activities can act on it. It's how a pipeline knows what to load (a config table), from where (a watermark), and whether to continue (a validation query). This lesson covers its two output shapes, its limits, and the main patterns.

Two Output Shapes

The First row only checkbox changes the output completely — the most common source of Lookup errors:

☑ First row only — one value

{
  "firstRow": {
    "WatermarkValue": "2026-08-21T23:59:59"
  }
}
@activity('Get Watermark').output.firstRow.WatermarkValue

☐ First row only — a list

{
  "count": 3,
  "value": [
    {"TableName":"Customers","LoadType":"INCREMENTAL"},
    {"TableName":"Products", "LoadType":"FULL"},
    {"TableName":"Orders",   "LoadType":"INCREMENTAL"}
  ]
}
@activity('Get Config').output.value     → feed to ForEach
@activity('Get Config').output.count     → how many

Limits

  • Returns at most 5,000 rows — extra rows are silently dropped
  • Output at most 4 MB — larger and the activity fails
  • A query or procedure must return exactly one result set
Lookup is for control data, not business data. If you need 50,000 file names or customer IDs, you're using the wrong tool: process them inside a notebook or a Copy activity, or page through them (an outer loop of child-pipeline runs, each looking up one slice).

Pattern 1 — Config Table → ForEach

CREATE TABLE ops.PipelineConfig
(
    TableName        varchar(100),
    SourceSchema     varchar(50),
    SourceTable      varchar(100),
    TargetTable      varchar(100),
    LoadType         varchar(20),     -- FULL / INCREMENTAL
    WatermarkColumn  varchar(100),
    KeyColumns       varchar(200),
    LoadOrder        int,
    IsActive         bit
);
SELECT TableName, SourceSchema, SourceTable, TargetTable, LoadType, WatermarkColumn, KeyColumns
FROM ops.PipelineConfig
WHERE IsActive = 1
ORDER BY LoadOrder;

Add a table to the load → insert a row. Pause a table → set IsActive = 0. No pipeline change, no deployment.

Pattern 2 — Watermark

SELECT WatermarkValue FROM ops.Watermark WHERE TableName = '@{item().TableName}'

First row only: ON. Used in the Copy source query (Lesson 7.2 recipe) — the incremental pattern from Module 3.8.

Pattern 3 — Gate: Is There Anything to Do?

SELECT COUNT(*) AS NewRows FROM stg.Orders
Lookup Count
→
If @greater(activity('Lookup Count').output.firstRow.NewRows, 0)

Pattern 4 — Validation

SELECT
    SUM(CASE WHEN CustomerID IS NULL THEN 1 ELSE 0 END) AS NullKeys,
    COUNT(*) - COUNT(DISTINCT OrderID)                  AS DuplicateKeys
FROM stg.Orders

Then an If condition: when either is greater than 0, route to a Fail activity with a clear message (Lesson 7.7).

Hands-On Lab

  1. Create ops.PipelineConfig with three active tables and one inactive.
  2. Lookup it (first row only OFF), run in debug, and inspect count and value.
  3. Turn first row only ON and watch your output.value expression fail. Switch back.
  4. Add a count-gate Lookup + If that skips the load when staging is empty.
The Lookup activity reads a small result from a table, query, stored procedure or file so later activities can use it. With First row only it returns output.firstRow.Column; without it, output.value (an array) and output.count, typically fed to a ForEach. Lookup returns at most 5,000 rows and 4 MB and needs exactly one result set, so it's for control data — config tables that drive metadata-driven pipelines, watermarks for incremental loads, row-count gates and validation queries — not for business data, which belongs in Copy or a notebook.
7.5

Control Flow: ForEach, Switch, If, Until

Control-flow activities make a pipeline loop, branch and wait. Each is simple on its own; the skill is knowing their limits — why you can't nest a ForEach, what parallelism really does to your source system, and how to stop an Until loop from running forever. Filter, Get Metadata and Wait round out the set.

Choosing the batch count

More parallelism isn't automatically faster. Each iteration opens connections and consumes capacity units:

✗ Batch count 50 against an on-prem SQL Server

50 simultaneous queries saturate the source and the gateway; copies throttle, time out and retry. Total time goes up, and the source DBA calls you.

✓ Start low and measure

Start at 4–8 for databases, higher for files in cloud storage. Increase while total duration keeps dropping; stop when it doesn't.

No ForEach inside ForEach

Container activities can't be nested freely — most importantly, you can't put a ForEach or Until inside another ForEach. The fix is always the same: put the inner logic in a child pipeline and call it with Invoke pipeline.

The expression must return a boolean. Common building blocks: equals, greater, less, empty, contains, and, or, not.

Switch

Switch compares one string to a list of cases. It replaces nested Ifs:

Switch @item().LoadType
FULL →
Copy (overwrite)
INCREMENTAL →
Copy (watermark query, append)
SCD2 →
Notebook SCD2 merge
Default →
Fail "Unknown LoadType @{item().LoadType}"
Always put a Fail activity in the Default case. Otherwise a typo like INCREMNTAL in the config table matches nothing, does nothing, and the run shows green.

Until

Until repeats its activities until the expression becomes true (it checks after each pass, so it always runs at least once). Use it for polling:

Until @variables('Done')timeout 02:00:00
→ inside →
Get Metadata exists?
→
Set Done = exists
→
Wait 300 s
  • Always set the Until timeout explicitly — the default is days, not minutes
  • Put a Wait inside — a loop with no wait hammers the source and burns capacity
  • After the loop, check whether it ended because the condition came true or because it timed out, and Fail with a clear message on timeout
  • Waiting for a file to land? An event trigger (Lesson 7.8) is usually better than polling

Hands-On Lab

  1. Build Lookup → ForEach (batch 4) → Switch on LoadType with FULL, INCREMENTAL and a Fail default. Add a row with a misspelled LoadType and confirm the run fails clearly.
  2. Try to drag a ForEach inside a ForEach — note the restriction. Refactor the inner loop into a child pipeline.
  3. Build Get Metadata → Filter (.csv only) → ForEach Copy for a landing folder.
  4. Build an Until that waits for a file _SUCCESS, with a 10-minute timeout and a 60-second Wait.
ForEach iterates over an array, sequentially or in parallel (batch count 20 by default, 50 maximum, up to 100,000 items); the right parallelism depends on what the source can handle. Containers can't nest ForEach or Until, so inner loops move into a child pipeline called with Invoke pipeline, which also gives each item its own variables. If Condition branches on a boolean; Switch branches on a string and should always fail in its Default case. Until repeats until a condition is true and needs a timeout and a Wait inside. Get Metadata lists files or checks existence, and Filter keeps matching items, together forming the folder-processing pattern.

Calling Notebooks, Procedures & Child Pipelines

Pipelines orchestrate; notebooks and stored procedures do the heavy lifting. This lesson shows how to pass values into them, how to get results back out, and how to break a large workflow into parent and child pipelines.

The Notebook Activity

Passing values in

In the notebook, mark one cell as the parameter cell (cell menu → Toggle parameter cell) and give defaults:

table_name = "Orders"
load_date  = "2026-08-21"
batch_id   = "MANUAL"

Getting a result back

End the notebook with notebookutils.notebook.exit(). Return a JSON string so you can send back several values:

import json
result = {"status": "OK", "rows_in": rows_in, "rows_out": rows_out, "rejected": rejected}
notebookutils.notebook.exit(json.dumps(result))
@json(activity('NB Clean Orders').output.result.exitValue).rows_out
exit() ends the notebook successfully. If the notebook finds a problem the pipeline should treat as a failure, raise an exception instead — raise ValueError("12 orders with NULL CustomerID") — so the activity fails and your failure path runs.

Session settings

  • Many notebooks in one pipeline each start a Spark session. Enable high concurrency for pipelines in the workspace Spark settings so notebooks can share a session (and tag related activities with the same session tag)
  • A notebook's default Lakehouse is taken from the notebook; to switch per environment use deployment rules or variable libraries (Module 11)

Invoked pipelineThe child — in this workspace or another (the newer Invoke pipeline can also call pipelines in Azure Data Factory or Synapse through a connection)

Why split?

  • Each child can be run and tested on its own — re-run just Silver after a fix
  • Stays under the 120-activity limit; no nested-ForEach restriction
  • Each child run gets its own variables (safe in parallel loops)
  • Clearer monitoring: the Monitoring hub shows each child run with its own status

A child can return values to the parent by setting a pipeline return value (Set variable activity → Pipeline return value option), read by the parent as @activity('Invoke child').output.pipelineReturnValue.Name.

A Notebook activity passes values through base parameters that override the notebook's parameter cell, and the notebook returns a value with notebookutils.notebook.exit — ideally a JSON string read with json(output.result.exitValue). To fail the pipeline, the notebook should raise an exception, not exit. The Stored procedure activity runs one procedure with typed parameters; the Script activity runs any T-SQL and can return result sets. Large workflows are split into parent and child pipelines with Invoke pipeline, which keeps each pipeline testable, avoids nesting limits, isolates variables and can return values to the parent. Other integration activities include Semantic model refresh, Dataflow Gen2, Web, KQL, Teams and Outlook.

Error Handling, Retries & Logging

A pipeline that fails loudly is easy to fix. A pipeline that fails silently — shows green while half the tables didn't load — is a disaster discovered by a business user weeks later. This lesson shows how pipeline status is really decided, the error-handling patterns that keep failures visible, when to retry, and how to log every run.

How the Pipeline's Final Status Is Decided

This surprises almost everyone. Adding a failure path can turn a failed run into a successful one:

DesignCopy fails →Pipeline status
Copy alone—Failed
Copy on failure → Log errorLog error succeedsSucceeded ⚠️
Copy on success → Next, on failure → Log errorLog runs, Next is skippedFailed
Copy on failure → Log error → FailLogged, then failed on purposeFailed ✔

The rule: the run succeeds if the error was handled — a failure path ran successfully and nothing else on the "leaf" path failed. Logging an error counts as handling it. So the safe pattern is log, then Fail.

The Fail Activity

Fail message:  @concat('Load of ', item().TableName, ' failed: ', activity('Copy Table').error.message)
Error code:    LOAD_COPY_FAILED

Fail stops the run with your message and code, which appear in the Monitoring hub and in alert emails. Use it for: failures you've logged, validation failures (null keys, row-count mismatch), Switch default cases, and Until timeouts.

The Standard Pattern: Try / Catch / Finally

Log STARTScript: insert audit row
→
Invoke workthe "try" block
success →
Log SUCCESS
failure →
Log FAILED + error
→
Teams alert
→
Fail

Putting the work in one child pipeline (or a container) gives one failure arrow to catch everything inside it — instead of a failure arrow from every activity.

Retry — Only for Transient Errors

✓ Retry helps

  • Network timeout, connection reset
  • Source throttling (HTTP 429), service briefly unavailable (503)
  • Gateway restarting
  • Database deadlock victim

✗ Retry wastes time

  • Invalid SQL, missing table or column
  • Wrong credentials / permission denied
  • Data errors (bad type, duplicate key)
  • Notebook raised a validation error

So: Copy, Lookup and Web against remote sources → retry 2–3, interval 60–300 s. Notebooks, procedures and validation → retry 0, and fail fast with a clear message.

Make Re-Runs Safe (Idempotency)

After a failure, someone will re-run the pipeline. A re-run must not duplicate data:

Load styleSafe to re-run?How to make it safe
Overwrite whole table✔ Yes—
MERGE on a key✔ Yes—
Append✘ DuplicatesDelete the batch/date first, or replace the partition, or append to staging then MERGE
Watermark✔ If updated lastUpdate the watermark only after the target load succeeds

Logging: Audit and Error Tables

CREATE TABLE ops.PipelineRunLog
(
    RunId         varchar(50),
    PipelineName  varchar(200),
    TableName     varchar(200),
    Status        varchar(20),       -- RUNNING / SUCCESS / FAILED
    RowsRead      bigint,
    RowsWritten   bigint,
    StartTime     datetime2(6),
    EndTime       datetime2(6),
    ErrorMessage  varchar(4000)
);
-- On failure path (Script activity)
UPDATE ops.PipelineRunLog
SET Status = 'FAILED',
    EndTime = SYSUTCDATETIME(),
    ErrorMessage = LEFT('@{replace(activity('Copy Table').error.message, '''', '''''')}', 4000)
WHERE RunId = '@{pipeline().RunId}' AND TableName = '@{item().TableName}';

The replace(…, '''', '''''') doubles any single quotes in the error text so it doesn't break the SQL string. With this table you can answer "what failed last night, and why?" with one query — and build a Power BI page on it.

Hands-On Lab

  1. Build Copy → (failure) Log error, point Copy at a missing table, run it: note the pipeline shows Succeeded.
  2. Add a Fail activity after the log. Re-run: now Failed, with your message.
  3. Create ops.PipelineRunLog and write START, SUCCESS and FAILED rows (escaping quotes in the error).

A pipeline run counts as succeeded if a failure was handled — a failure-path activity ran successfully — so logging an error can hide a failure; the fix is to log and then use the Fail activity with a custom message and error code. A try/catch/finally design wraps the work in a child pipeline with a success path that logs success and a failure path that logs, alerts and fails. Retries suit transient errors such as timeouts and throttling, not logic or data errors. Loads should be idempotent, with watermarks updated only after success, and every run should write to an audit/error table keyed by RunId, plus alerts via Teams, Outlook, run notifications or Activator.

Set it up from the pipeline's Add trigger button (or from the Real-Time hub): choose the storage source, the event types (file created / deleted), and filters such as "subject begins with /Files/Landing/" and "ends with .csv".

Inside the pipeline, read which file fired the trigger:

@pipeline()?.TriggerEvent?.FileName
@pipeline()?.TriggerEvent?.FolderPath

The ?. makes the expression return null (instead of failing) when the run wasn't started by an event — so the same pipeline still works when you run it manually. Combine with coalesce() to fall back to a parameter.

Storage events can be delivered more than once, and one upload tool may create several events for one file. Design the pipeline to tolerate duplicate runs: idempotent loads (Lesson 7.7), or a processed-files log checked at the start.

Schedule or event?

SituationUse

Concurrency

If a run is still going when the next schedule fires, both run at once — and may write the same tables. Set the pipeline's concurrency setting to 1 so extra runs queue (up to 100 queued runs per pipeline) instead of overlapping.

Investigating a failure — in order

  1. Open the failed run; find the first red activity (later reds are usually consequences).
  2. Read its error message and its input — most failures are a wrong value produced by an expression.
  3. For a Notebook, open the snapshot and read the failing cell's traceback.
  4. Fix the cause, then Rerun from failed activity — successful activities aren't repeated (only safe if they're idempotent).

Hands-On Lab

  3. Run it manually too — confirm the ?. expression returns null rather than failing.
  4. Force a failure, investigate in the Monitoring hub, fix, and use Rerun from failed activity.
Pipelines start on demand (Run button or REST API), on a schedule (by minute, hour, day or week, with time zone; up to 20 schedules per pipeline), from a parent pipeline, or from events such as files created or deleted in OneLake or Blob storage, which are built on Activator and can filter by folder and extension. The triggering file is available via pipeline()?.TriggerEvent?.FileName. Events can be delivered more than once, so loads must tolerate duplicates. Concurrency set to 1 prevents overlapping runs. The Monitoring hub shows all runs with activity-level inputs, outputs, durations and errors, and a failed run can be rerun from the failed activity.

Dimensions before facts

A single parallel ForEach ignores LoadOrder. Two simple solutions: run the ForEach sequentially, or use two ForEach activities — one for LoadOrder = 1 (dimensions, in parallel) followed by one for LoadOrder = 2 (facts, in parallel). The second is faster.

Should one failed table stop everything?

By default, a failed child makes the ForEach fail after all iterations finish — other tables still load. Then the master's failure path alerts and fails, and Silver/Gold don't run on incomplete data. That's usually the right behaviour. Query the RunLog to see exactly which table failed and re-run with TableName as a filter.

A metadata-driven framework separates what to load from how to load it. Control tables hold the table list, load type, keys, load order and watermarks, plus a run log. A master pipeline sets a batch ID, looks up active config rows and runs a ForEach that invokes a child pipeline per table. The child logs start, switches on load type (full copy, or incremental copy filtered by the watermark, then updates the watermark from the loaded data), logs success or the error, and fails if anything went wrong. After ingestion, the master runs Silver and Gold transformations and refreshes the semantic model, with Teams alerts on success and failure. New tables are added by inserting config rows, without changing pipelines.

Fabric pipelines orchestrate data work with activities connected by success, failure, completion and skip dependencies. Expressions make them dynamic using parameters, variables, activity outputs and item() in loops. Lookup reads control data such as config and watermarks; ForEach, If, Switch and Until provide control flow, with child pipelines replacing nested loops. Notebooks and stored procedures do the transformation work with parameters in and results out. Robust pipelines log and then Fail rather than silently handling errors, retry only transient failures, and load idempotently. Runs are started by schedules, storage events or APIs, observed in the Monitoring hub, and generalised into a metadata-driven framework driven by config tables.
