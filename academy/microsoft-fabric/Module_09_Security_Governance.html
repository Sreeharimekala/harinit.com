Security & Governance

Decide who can see what, protect sensitive data wherever it travels, and know what data you have, where it came from and who owns it.

📚 8 Lessons  |  🎯 Beginner Friendly  |  🔐 Hands-On Lab  |  DP-700 Track
What you will learn in this module: Security in Fabric isn't one switch — it's layers. This module walks through them from the outside in: who can enter a workspace, which items they can open, which tables, rows and columns they can read in each engine, how sensitivity labels and DLP protect data that leaves Fabric, and how Microsoft Purview catalogs, classifies and traces it. Module 6.9 already covered Warehouse T-SQL security in detail; here it's placed in the bigger picture and compared with the alternatives. 9.1

The Fabric Security Model

Every request to Fabric passes through several gates, each answering a different question. Knowing which gate answers which question is the key to designing security that works — and to debugging "why can't Priya see this table?" in minutes instead of hours.

Security vs Governance

Security — "who can access?"

  • Sign-in, network, workspace roles
  • Item permissions
  • Table, row and column rules
  • Enforced: access is allowed or denied

Governance — "what do we have, and how should it be handled?"

  • Catalog, ownership, endorsement
  • Classification, sensitivity labels
  • Lineage, audit, DLP policies
  • Makes data findable, trusted and compliant

The Layers

1
Identity & tenant
Microsoft Entra ID sign-in, MFA, Conditional Access; Fabric admin portal tenant settings (who may create workspaces, share externally, export data…).
2
Network
Private links, managed private endpoints, trusted workspace access, outbound access protection — for organisations that must keep traffic off the public internet.
3
Workspace roles
Admin, Member, Contributor, Viewer — what someone can do with everything in a workspace (Lesson 9.2).
4
Item permissions
Share one item (a Warehouse, a report) without granting the whole workspace (Lesson 9.2).
5
Data-level security
Which tables, rows and columns: OneLake security, SQL GRANT/RLS/CLS/masking, semantic-model RLS/OLS (Lessons 9.3–9.5).
6
Information protection
Sensitivity labels that travel with data, DLP policies that detect and restrict sensitive content (Lesson 9.6).
7
Governance & audit
Purview catalog, lineage, endorsement, domains, audit logs (Lesson 9.7).

Control Plane vs Data Plane

Control planeData plane
QuestionCan you manage this item? Create, edit, delete, run, shareCan you read this data? Which tables, rows, columns
Controlled byWorkspace roles, item permissionsOneLake security, SQL permissions, semantic-model roles
Typical holderEngineers and developersAnalysts and business users
Fine-grained data rules (OneLake security roles, Warehouse RLS, semantic-model RLS) apply to Viewers and people with item-level read access. Admins, Members and Contributors of a workspace can generally read and change all of its data and bypass those rules. So: never give a data consumer an edit role in the workspace that holds sensitive data.

Design Principles

  • Least privilege — the lowest role that lets someone do their job
  • Groups, not people — assign Entra security groups; joining/leaving the company is then an HR process, not a Fabric task
  • Separate builders from consumers — engineers in the engineering workspace; analysts get Viewer or item access, often in a separate reporting workspace
  • Secure once, close to the data — define rules where every engine respects them, then test from each engine
  • Defence in depth — labels and DLP still protect data if a permission is set wrong
Fabric security is layered: Entra ID identity and tenant settings, optional network isolation, workspace roles, item permissions, data-level security (OneLake security, SQL GRANT/RLS/CLS/masking, semantic-model RLS/OLS), information protection with sensitivity labels and DLP, and governance through Purview catalog, lineage, endorsement and audit. Workspace roles and item permissions form the control plane — who can manage items — while data-level rules form the data plane — which tables, rows and columns can be read. Fine-grained rules apply to Viewers and item-level readers; Admins, Members and Contributors can bypass them, so consumers should never hold edit roles. Good design uses least privilege, Entra groups, separation of builders and consumers, and defence in depth.
9.2

Workspace Roles & Item Permissions

Workspace roles are the first and broadest gate. This lesson explains exactly what each role can do, when to share a single item instead, what each item permission unlocks, and how to lay out workspaces so roles stay simple.

The Four Workspace Roles

Update/delete the workspace, add or remove admins✔
Add members and lower roles✔✔
Share items, manage item permissions✔✔**

Roles can be given to users, Entra security groups, Microsoft 365 groups, distribution lists and service principals (for automation). If someone is in several groups, they get the highest role among them.

Item Permissions: Sharing One Thing

Select an item → Share (or Manage permissions). The person gets access to that item only, not the workspace. What they can do depends on the boxes you tick:

PermissionApplies toAllows
ReadAll itemsOpen the item and see its metadata; connect to the SQL endpoint (but no table data unless granted in SQL)
ReadDataLakehouse SQL endpoint, WarehouseRead all tables through SQL (respects SQL RLS/CLS)
ReadAllLakehouse, WarehouseRead the underlying OneLake files directly (Spark, OneLake APIs) — bypasses SQL-level rules
BuildSemantic modelsBuild new reports on the model
ReshareAll itemsShare the item onward
WriteSome itemsEdit the item
ReadAll is the dangerous one. SQL row- and column-level security protects the SQL door; ReadAll opens the file door, where those SQL rules don't apply. Grant it only to engineers who genuinely need Spark access to all the data — or use OneLake security (Lesson 9.3), which protects both doors.

Workspace Layout Patterns

By environmentRetail Sales – Data Engineering [DEV] · [TEST] · [PROD]Developers edit DEV; only the deployment process changes PROD (Module 11)
By layerRetail Sales – Data Engineering [DEV] (Bronze/Silver/Gold) · Retail Sales – Analytics [DEV] (Warehouse, model, reports)Analysts never get a role where raw PII lives
By domainFinance · HR · SalesEach domain owns its data and access (Lesson 9.7)

Shortcuts make the layer pattern cheap: the reporting workspace can shortcut to Gold tables without copying data — and OneLake security on the source still applies.

Workspace Identity

A workspace can have its own managed workspace identity in Entra ID. Connections can authenticate as the workspace rather than as a person, so pipelines don't break when the engineer who created the connection leaves — and you can grant that identity access to firewall-protected Azure storage (trusted workspace access).

Hands-On Lab

  1. Create Entra groups (or use test accounts): sg-fabric-sales-engineers, sg-fabric-sales-analysts.
  2. Give engineers Contributor on Retail Sales – Data Engineering [DEV]. Give analysts nothing there.
  3. Share wh_sales_reporting with analysts with Read only; confirm they can connect but not query tables. Then add ReadData.
  4. Open Manage access and review: is anyone an Admin who shouldn't be?
Workspace roles grant permissions on everything in a workspace: Admins manage the workspace and all access, Members can add people and share, Contributors create and edit items and read and write all data, and Viewers can view items and read data subject to data-level rules. Roles should be assigned to Entra groups and service principals; a user in several groups gets the highest role. Item permissions share a single item: Read to connect, ReadData to query via SQL, ReadAll to read OneLake files directly (bypassing SQL rules), Build for semantic models, Reshare and Write. Workspaces are typically split by environment, layer or domain so consumers never hold roles where raw sensitive data lives, and workspace identity lets connections authenticate without personal accounts.
9.3

OneLake Security

SQL security only protects data accessed through SQL. Spark notebooks, OneLake APIs and shortcuts read the files underneath. OneLake security defines access once, on the data itself — tables, folders, rows and columns — so the same rule applies whichever engine reads it.

The Problem It Solves

✗ SQL rules only

RLS on the SQL analytics endpoint: Priya sees only South rows in SQL and Power BI. But give her ReadAll for a notebook, and Spark reads every row from the Delta files.

✓ OneLake security

A role "South Analysts" grants FactSales with a row filter Region = 'South'. Spark, the SQL endpoint, Power BI and shortcuts all return South rows only.

Anatomy of a Role

ComponentMeaningExample
DataTables or folders the role can accessTables/dbo/FactSales, Tables/dbo/DimCustomer
PermissionWhat the role allowsRead
MembersWho gets it — Entra users/groups, or "everyone with Read on the item"sg-fabric-sales-south
ConstraintsRow filters and column restrictions inside those tablesRows: Region = 'South' · Columns: hide Email, Phone

Create roles from the Lakehouse ribbon → Manage OneLake security. Admins and Members can manage them.

Rules to Remember

  • Roles apply to users with Viewer role or item Read access — Admin, Member and Contributor bypass them
  • Once roles are in use, users who aren't in any role see no data. The built-in DefaultReader role gives all readers everything — remove or narrow it when you start securing
  • A user in several roles gets the union (most permissive combination) of them
  • Row filters are simple SQL-style predicates on the table's own columns
  • Shortcuts: security is defined where the data lives; a shortcut in another Lakehouse enforces the source's roles

With the SQL Analytics Endpoint

The Lakehouse SQL analytics endpoint can run in one of two modes for OneLake security:

ModeBehaviourUse when
User identityQueries run as the user; OneLake security roles are enforced in SQL tooYou want one set of rules for every engine
Delegated identityQueries read OneLake as the item owner; you secure SQL with GRANT/RLS/CLS as in Module 6.9You prefer SQL-native security for SQL users

Where Each Mechanism Fits

ItemMain data-level mechanism
Lakehouse (Spark + SQL + shortcuts)OneLake security roles
WarehouseT-SQL GRANT/DENY, RLS, CLS, DDM (Module 6.9)
Semantic modelModel RLS and OLS (Lessons 9.4–9.5)
KQL databaseDatabase roles; row-level security policies in KQL

Hands-On Lab

  1. In lh_sales_gold, open Manage OneLake security; review DefaultReader.
  2. Create role SouthAnalysts: tables FactSales + DimCustomer, row filter on Region, hide Email; add a test user with Viewer access.
  3. As that user, query from a notebook and the SQL endpoint — confirm both return South rows and no Email.
  4. Create a shortcut to FactSales in another Lakehouse and confirm the same filtering.
OneLake security defines data access on a Lakehouse (and other supported items) once, at the storage layer, so the same rules apply across Spark, the SQL analytics endpoint, Power BI and shortcuts. A role specifies data (tables or folders), permission, members and constraints such as row filters and hidden columns. Roles apply to Viewers and users with item Read access, not to Admins, Members or Contributors; users outside any role see nothing once DefaultReader is removed; and multiple roles combine as a union. Security is enforced at the source of a shortcut. The SQL analytics endpoint can use user identity, enforcing OneLake roles, or delegated identity, relying on SQL permissions.
9.4

Row-Level Security

Row-level security (RLS) lets everyone use the same table and the same report, while each person sees only their own rows — South managers see South sales, North managers see North. Fabric offers RLS in three places. This lesson shows each, how to make RLS dynamic with a security table, and how to choose.

The Idea

FactSales (all rows)
What each user sees
North · South · East · West
── Ravi (South) ──►
South only
North · South · East · West
── Anita (North, East) ──►
North + East
North · South · East · West
── CFO (all) ──►
All regions

The user runs the same query (SELECT * FROM FactSales, or opens the same report). The filter is added silently by the engine, based on who they are.

The Security Mapping Table

Hard-coding "South" into a role per region doesn't scale. Instead, keep a table of who-sees-what, maintained by the business (or loaded from HR):

UserEmailRegion
ravi@contoso.comSouth
anita@contoso.comNorth
anita@contoso.comEast
cfo@contoso.com*

Adding a person or changing their region is now a row change — no security redesign.

Option 1 — Warehouse / SQL Endpoint (T-SQL)

Covered fully in Module 6.9. In short: a predicate function plus a security policy.

CREATE FUNCTION sec.fn_RegionFilter(@Region varchar(50))
RETURNS TABLE
WITH SCHEMABINDING
AS
RETURN
    SELECT 1 AS allowed
    FROM sec.UserRegion AS ur
    WHERE ur.UserEmail = USER_NAME()
      AND (ur.Region = @Region OR ur.Region = '*');
GO
CREATE SECURITY POLICY sec.SalesRegionPolicy
ADD FILTER PREDICATE sec.fn_RegionFilter(Region) ON dbo.FactSales
WITH (STATE = ON);

Applies to every SQL query — SSMS, notebooks using the SQL endpoint, DirectQuery reports.

Option 2 — OneLake Security Row Filter

A row constraint inside a OneLake security role (Lesson 9.3). Applies to Spark, SQL (user identity mode), shortcuts and Direct Lake. Simple predicates on the table's own columns — one role per distinct filter, so best for a small number of fixed groups (e.g. one role per region group).

Option 3 — Semantic Model (DAX)

Defined in Power BI Desktop (Modeling → Manage roles) or the web modeling view. Applies to everyone using reports on that model.

Static role

Role "South"   Table: DimRegion   Filter:  [Region] = "South"

Dynamic role (one role for everyone)

Role "Regional"   Table: DimRegion   Filter:
VAR Allowed =
    CALCULATETABLE (
        VALUES ( UserRegion[Region] ),
        UserRegion[UserEmail] = USERPRINCIPALNAME ()
    )
RETURN
    "*" IN Allowed || [Region] IN Allowed

The filter on DimRegion flows through the model's relationships to FactSales. Keep the UserRegion table hidden from report users.

  1. Create the role; publish the model.
  2. In the service: model → Security → add Entra groups to the role.
  3. Test with View as / Test as role, entering another user's email.
Model RLS only restricts Viewers (workspace Viewer, or users with Read/Build on the model). Workspace Admins, Members and Contributors see all rows, whatever roles you add them to. Test with a real Viewer account, not your own.

RLS and Direct Lake

Where RLS is definedDirect Lake behaviour
Semantic model (DAX)✔ Stays in Direct Lake mode — the recommended place for report security
OneLake security (Direct Lake on OneLake)✔ Enforced for the user's identity
SQL endpoint / Warehouse T-SQL RLS (Direct Lake on SQL)Falls back to DirectQuery so SQL can apply the filter — slower

Which RLS Should I Use?

Users read data through…Put RLS in…
Power BI reports onlyThe semantic model
SQL tools (SSMS, Excel via SQL, other apps)Warehouse / SQL endpoint T-SQL
Spark notebooks, shortcuts and SQL from a LakehouseOneLake security
Several of the aboveEach door that's open — driven from the same mapping table so the rules can't drift apart

Hands-On Lab

  1. Create sec.UserRegion in the Warehouse and apply the T-SQL policy; test with EXECUTE AS USER or a test account.
  2. Build a semantic model with the dynamic DAX role; test as two users with different regions.
  3. Put the CFO's * row in and confirm they see all regions.
  4. Add a test user as workspace Contributor and observe that RLS no longer applies to them.
Row-level security filters rows by user identity so everyone shares one table and report but sees only permitted rows, usually driven by a user-to-region mapping table so access changes are data changes. In Fabric RLS can be defined in the Warehouse or SQL endpoint with a predicate function and security policy, in OneLake security role row filters, or in the semantic model with DAX roles using USERPRINCIPALNAME(). Model RLS is the best choice for Power BI and keeps Direct Lake mode, whereas SQL RLS forces Direct Lake on SQL to fall back to DirectQuery. RLS only restricts Viewers and item-level readers, so it must be tested with a viewer account, and every open access path needs its own enforcement from the same mapping.
9.5

Object- & Column-Level Security

RLS hides rows. Sometimes you need to hide columns (salary, national ID, phone number) or whole tables (an HR table in a shared model). This lesson covers object-level security in semantic models, column-level security in SQL and OneLake, and dynamic data masking — and when each is the right tool.

Four Ways to Hide Things

MechanismHidesWhereUser experience
OLS (object-level security)Tables or columnsSemantic modelObject doesn't exist for them; visuals using it show an error
CLS (column-level security)ColumnsWarehouse / SQL endpoint (GRANT), OneLake securitySelecting the column fails (SQL) or it's absent (OneLake)
DDM (dynamic data masking)Column valuesWarehouse / SQL endpointColumn visible but masked: rXXX@XXXX.com
Separate table / modelEverything sensitiveDesignRestricted users never get access to the item at all

OLS in a Semantic Model

OLS is set per role, using an external tool such as Tabular Editor (or by editing the model's TMDL definition):

  1. Create the role in Power BI Desktop (it can have no row filter).
  2. Open Tabular Editor from External tools; select the role → Table Permissions.
  3. Set the Employee table to None, or DimEmployee[Salary] column permission to None.
  4. Save, publish, assign groups, test with View as.
Role "General Staff"
  Table permissions:   Employee        → None
  Column permissions:  DimEmployee.Salary   → None
                       DimEmployee.NationalId → None
Measures that reference a hidden column are hidden too. Design reports so restricted users have their own pages or report — a visual that errors with "can't display" looks broken, even if security is working perfectly.

CLS in the Warehouse (Recap from 6.9)

-- Analysts can read every column except salary and national ID
GRANT SELECT ON dbo.DimEmployee
    (EmployeeKey, EmployeeName, Department, HireDate) TO [sg-fabric-hr-analysts];

-- SELECT * now fails for them; they must list allowed columns

Dynamic Data Masking (Recap)

ALTER TABLE dbo.DimCustomer ALTER COLUMN Email
    ADD MASKED WITH (FUNCTION = 'email()');
ALTER TABLE dbo.DimCustomer ALTER COLUMN Phone
    ADD MASKED WITH (FUNCTION = 'partial(0,"XXX-XXX-",4)');

GRANT UNMASK TO [sg-fabric-customer-service];
Masking is a convenience, not a strong control: someone who can query the column can sometimes infer values (WHERE Email LIKE 'a%'). For truly sensitive data, use CLS/OLS so the column can't be queried at all.

Choosing

NeedUse
Report users must never see salary in Power BIOLS in the model (and don't expose the column in SQL to them either)
SQL analysts must not query national IDsCLS via GRANT on columns
Spark users and shortcuts must not read PII columnsOneLake security column restriction
Support staff need to recognise a customer but not see full emailDDM
Only HR may know the HR table existsSeparate item or workspace for HR

Hands-On Lab

  1. In Tabular Editor, create a role hiding DimEmployee[Salary]; test a visual that uses it.
  2. In the Warehouse, GRANT column-level SELECT to a test group; try SELECT * as that user.
  3. Mask Email and Phone; compare what a masked user and an UNMASK user see.
Object-level security in a semantic model hides tables or columns per role, configured with Tabular Editor or TMDL; hidden objects and dependent measures behave as if they don't exist, so reports must be designed for restricted users. Column-level security in the Warehouse uses GRANT SELECT on specific columns, and OneLake security can also restrict columns across engines. Dynamic data masking shows masked values unless UNMASK is granted, but is a convenience rather than a strong control. The choice depends on the access path — Power BI, SQL or Spark — and highly sensitive data may belong in a separate item or workspace.
9.6

Sensitivity Labels & DLP

Permissions decide who can open an item. But once someone exports a report to Excel and emails it, permissions are left behind. Sensitivity labels travel with the data, telling people how to handle it and — with protection — controlling who can open the exported file. DLP policies detect sensitive content automatically and warn, alert or restrict access.

Sensitivity Labels

Labels are defined once by your compliance team in Microsoft Purview Information Protection and used across Microsoft 365 and Fabric. A typical set:

LabelMeaningFabric exampleProtection on export
PublicSafe for anyonePublished product catalogueNone
GeneralInternal useSales targets by regionHeader/footer marking
ConfidentialLimited audience; harm if leakedCustomer contact details, marginsEncrypted: employees only
Highly ConfidentialSevere harm if leakedSalaries, health data, M&AEncrypted: named groups only

A label is visible in the item header and in the workspace list, so everyone sees how to treat the data at a glance.

How Labels Get Applied

WayHow
ManuallyItem header or settings → Sensitivity label
Default labelA label policy sets a label on new items automatically (e.g. General)
Mandatory labelingUsers must choose a label before saving
Inheritance from data sourcesA semantic model picks up the label of a labeled source it connects to
Downstream inheritanceLakehouse → semantic model → report → dashboard: new downstream items get the label (by default, never lowering an existing stricter label)
ProgrammaticallyAdmin REST APIs to label in bulk

Labels Travel on Export

ReportHighly Confidential
→ Export →
Excel / PDF / PowerPointsame label + encryption
→ emailed outside →
Recipient can't open it

Labels with protection settings encrypt the exported file, so access control continues outside Fabric. This is why labels are a key part of defence in depth.

A label doesn't grant or remove access inside Fabric by itself — Ravi still needs workspace or item permissions. Labels classify and protect; roles and permissions control access.

Data Loss Prevention (DLP) Policies

DLP policies are created in the Purview portal by security admins. For Fabric they scan items when data changes and look for sensitive information types (credit-card numbers, national IDs…) or specific labels:

ActionWhat happens
Policy tipA warning appears on the item: "This lakehouse contains credit card numbers"
AlertEmail to admins/owners; alert recorded in the Purview portal
Restrict accessAccess limited to the data owner or to internal users only; guests lose access

Fabric DLP covers semantic models and an expanding set of items — lakehouses, warehouses, KQL, SQL and mirrored databases — some still in preview. Policies apply to workspaces on Fabric or Premium capacity, and use the custom policy option.

Labels vs Classification vs Permissions

AnswersWhat kind of data is this? (email, credit card)How sensitive is this item and how must it be handled?Who may access it?

Hands-On Lab

  1. Ask your admin to confirm the tenant setting allowing users to apply sensitivity labels, and which labels are published to you.
  2. Label lh_sales_gold Confidential; create a semantic model and report from it and check the inherited labels.
  3. Export a report visual to Excel and check the file's label.
  4. (With a Purview admin) review whether a DLP policy covers your workspace, and what tips appear.
Sensitivity labels from Microsoft Purview Information Protection classify Fabric items by sensitivity, such as Public, General, Confidential and Highly Confidential. They are applied manually, by default or mandatory label policies, by inheritance from data sources and downstream to dependent items, or by API. Labels travel with exported Excel, PDF and PowerPoint files and can encrypt them, extending protection beyond Fabric, but they don't grant or remove access within Fabric. Purview DLP policies scan Fabric items for sensitive information types or labels and respond with policy tips, alerts or restricted access. Classification describes the type of data, labels describe sensitivity and handling, and permissions control access.
9.7

Microsoft Purview & Governance

As a platform grows to hundreds of tables and reports, new questions appear: Which table is the official customer list? Who owns it? Where does this number come from? What breaks if I change this column? Governance answers them. Some tools are built into Fabric; Microsoft Purview extends them across the whole organisation.

The Questions Governance Answers

QuestionTool
What data do we have, and where?OneLake catalog, Purview Unified Catalog
Which version can I trust?Endorsement: Promoted, Certified, Master data
Who is responsible for it?Item owner, domains, catalog data owners/stewards
Is it sensitive?Classification, sensitivity labels (9.6)

Who did what, when?Audit logs
Is it good quality?Purview data quality, your own checks (Module 5)

Built into Fabric

OneLake catalog

The OneLake catalog (left navigation) lets anyone find items they have access to across workspaces — filter by type, domain, endorsement, owner, label — and see details, lineage and permissions. It's the first place a new analyst should look before building yet another copy of the customer table.

Workspace → Lineage view shows how items connect. On any item, Impact analysis lists everything downstream — including in other workspaces — and how many people viewed it recently, and can notify their owners before you change something. Run it before renaming a column or dropping a table.

Domains

Fabric admins can group workspaces into domains (Sales, Finance, HR) with domain admins and contributors. Domains support a data-mesh style: each business area owns its data, while the catalog can be filtered by domain and some tenant settings delegated to domain admins.

Purview hub and audit

The Purview hub in Fabric (Settings) gives admins and owners reports on endorsement and label coverage, and links into Purview. Every significant user action — viewing a report, exporting data, changing permissions — is recorded in the Microsoft Purview audit log, searchable by compliance admins.

A Governance Checklist for Every Gold Asset

  • Clear, consistent name and a description
  • Owner (a person and a team) recorded
  • Endorsed: Promoted while in testing, Certified when approved
  • Sensitivity label applied
  • In the right domain
  • Lineage visible end to end (no undocumented manual uploads)
  • Business terms (e.g. "Net Revenue") defined in the glossary and used consistently

Hands-On Lab

  1. Open the OneLake catalog; filter to your workspace and review owners and labels.
  2. Promote wh_sales_reporting; write a description for it.
  3. Open Lineage view, then run Impact analysis on wh_sales_reporting.
  4. (If Purview is available) find your Fabric items in the Purview Unified Catalog and check classifications.
Governance makes data findable, trusted, owned and compliant. Within Fabric, the OneLake catalog helps users discover items; endorsement marks items as Promoted, Certified (by authorised reviewers) or Master data; lineage view and impact analysis show where data comes from and what depends on it; domains group workspaces by business area for data-mesh ownership; and the Purview hub and audit log report on coverage and activity. Microsoft Purview extends this organisation-wide with a Data Map that scans Fabric and other sources, automatic classification, a Unified Catalog with glossary terms and data products, cross-system lineage, data quality, information protection, DLP and audit.

Securing a Fabric solution end to end starts with Entra groups per audience, then separates engineering, Gold and reporting workspaces so consumers never hold edit roles where raw data lives. Consumers get item permissions — Read and ReadData without ReadAll for SQL users — and Warehouse GRANTs restrict columns. OneLake security roles give Spark users filtered, column-restricted access, after removing DefaultReader. Semantic-model RLS and OLS secure reports while keeping Direct Lake. Sensitivity labels and certification mark the assets. Every rule is verified with a test matrix using real test accounts, and access is reviewed regularly and deployed as code.

Fabric security and governance work in layers. Entra ID and tenant settings control sign-in; workspace roles and item permissions control who can manage and open items, with Admins, Members and Contributors bypassing data-level rules. Data-level security comes from OneLake security roles for cross-engine table, row and column access, Warehouse T-SQL permissions, RLS, CLS and masking, and semantic-model RLS and OLS. Sensitivity labels and Purview DLP protect sensitive data even after export. Governance — the OneLake catalog, endorsement, domains, lineage, impact analysis, audit and the Purview Data Map and Unified Catalog — makes data discoverable, trusted and compliant. Every configuration should be verified with test accounts.
